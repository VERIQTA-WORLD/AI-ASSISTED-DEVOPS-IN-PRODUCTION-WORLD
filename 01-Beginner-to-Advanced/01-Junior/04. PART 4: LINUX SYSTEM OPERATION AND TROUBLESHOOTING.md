# PART 4: LINUX SYSTEM OPERATION AND TROUBLESHOOTING

## Goal

Move from using Linux commands to reasoning about Linux system health.

Part 3 established the Linux operating model:

```text
Application
    ↓
Service
    ↓
Process
    ↓
Users / Permissions
    ↓
Files
    ↓
Kernel
    ↓
Hardware / Resources
```

You learned how to inspect files, permissions, processes, services, packages, users, groups, and basic system state.

Part 4 changes the question.

Instead of:

```text
Which Linux command should I run?
```

you must begin asking:

```text
What is the symptom?

How large is the impact?

Which layer is unhealthy?

Which resource is constrained?

Which process or subsystem is responsible?

Is the observed condition normal for this workload?

What changed?

What evidence supports the hypothesis?

What evidence contradicts it?

What is the safest corrective action?

How will recovery be verified?
```

The purpose of Linux troubleshooting is not to produce command output.

It is to turn system evidence into a defensible technical conclusion.

The core workflow throughout this Part is:

```text
Symptom
   ↓
Scope
   ↓
Expected State
   ↓
Observed State
   ↓
Resource / Failure Domain
   ↓
Evidence
   ↓
Responsible Process / Component
   ↓
Application Evidence
   ↓
Hypothesis
   ↓
Safe Test
   ↓
Root Cause
   ↓
Corrective Action
   ↓
Verification
```

---

# 1. FROM COMMAND OPERATOR TO TROUBLESHOOTER

A command operator sees:

```text
Application is slow
```

and starts running commands.

A troubleshooter first asks:

```text
Slow for whom?

Since when?

Every request or some requests?

One server or every server?

One application or the entire machine?

Did anything change?

Is the system actually resource constrained?

Which resource?

Which process?

Is that process the cause or merely another victim?
```

That distinction matters.

A process showing high CPU may be the cause.

It may also be legitimate work triggered by a different problem.

A process consuming memory may be leaking memory.

It may also be intentionally caching data.

A disk showing 100% capacity may explain an application failure.

Or the application may be writing to another filesystem entirely.

Troubleshooting requires relationships.

---

# 2. SYMPTOM IS NOT ROOT CAUSE

This principle governs the entire Part:

```text
Symptom
≠
Root Cause
```

Consider:

```text
Website is slow
```

That is a symptom.

Possible causes include:

```text
CPU saturation
Memory pressure
Swap activity
Storage latency
Filesystem full
Inodes exhausted
Application lock contention
Database latency
DNS delay
Network dependency
External API latency
Application bug
Excessive logging
Resource limits
Traffic increase
Misconfiguration
```

The correct response is not to choose one randomly.

The correct response is to eliminate possibilities using evidence.

---

# 3. SYMPTOM, EVIDENCE, CONDITION, AND ROOT CAUSE

These concepts should not be mixed together.

## Symptom

What is observed externally.

Example:

```text
API responses take 12 seconds.
```

## Evidence

A measured or observed fact.

Example:

```text
One application process is consuming approximately one CPU core continuously.
```

## Contributing Condition

Something making the problem worse.

Example:

```text
The host has limited CPU headroom.
```

## Root Cause

The underlying reason the incident occurred.

Example:

```text
A newly deployed application version entered an unintended CPU-intensive loop for a class of requests.
```

Do not write an incident conclusion such as:

```text
Root cause: CPU was high.
```

unless you have established why CPU became high and why that condition caused the incident.

# 4. ESTABLISH CONTEXT BEFORE TROUBLESHOOTING

Before investigating a system, establish where you are.

Useful initial checks:

```bash
hostname
whoami
date
uptime
```

Then determine the operating system:

```bash
cat /etc/os-release
```

Kernel:

```bash
uname -r
```

Architecture:

```bash
uname -m
```

Why?

Because:

```text
Correct Command
+
Wrong Host
=
Wrong Action
```

and:

```text
Correct Diagnosis
+
Wrong Environment
=
Wrong Conclusion
```

# 5. FIRST QUESTION: WHAT IS THE SCOPE?

Suppose the report says:

> The application is slow.

Determine:

```text
One user?
Some users?
All users?

One endpoint?
All endpoints?

One process?
One service?

One host?
All hosts?

One availability zone?
Entire environment?

Application only?
Whole operating system?
```

Scope dramatically changes the investigation.

If every service on one host is slow:

```text
Host-level resource problem
```

becomes more plausible.

If one endpoint on one application is slow while the rest of the host is healthy:

```text
Application-specific problem
```

becomes more plausible.

Do not assume either without evidence.

---

# 6. TIME IS PART OF THE EVIDENCE

Every troubleshooting investigation needs a timeline.

Record:

```text
When did the symptom begin?

Is it still happening?

Was it sudden or gradual?

Was there a deployment?

Configuration change?

Traffic increase?

Package update?

Restart?

Backup?

Scheduled job?

Disk growth?

Certificate rotation?

Infrastructure change?
```

A useful timeline may look like:

```text
13:55  Deployment completed
14:02  Latency begins increasing
14:04  CPU rises
14:05  Alert fires
14:07  Error rate increases
14:10  Investigation begins
```

Correlation does not automatically prove causation.

But it gives you something to investigate.

# 7. THE FIRST-LINE SYSTEM HEALTH MODEL

For a slow Linux system, begin with a broad view.

```text
Application Slow
      ↓
Confirm Scope and Time
      ↓
System Health
      │
      ├── CPU
      ├── Memory
      ├── Swap
      ├── Load
      ├── Disk Capacity
      ├── Inodes
      ├── I/O
      ├── Processes
      ├── Open Files
      ├── Sockets
      └── Logs
      ↓
Identify Abnormal Layer
      ↓
Identify Responsible Process / Resource
      ↓
Application Evidence
      ↓
Root Cause Investigation
```

This is not a command checklist.

You should not mechanically run every command for every incident.

Use evidence to narrow the investigation.

---

# 8. CPU: WHAT ARE YOU ACTUALLY MEASURING?

CPU troubleshooting starts with understanding what CPU usage means.

A CPU can spend time:

```text
running application code

running kernel code

idle

handling interrupts

waiting in conditions reported by tools as I/O wait

servicing virtualized workloads
```

Different tools expose these categories differently.

A high CPU percentage is not inherently bad.

A production server exists to perform work.

The important question is:

```text
Is CPU demand preventing the workload from meeting its expected behavior?
```

---

# 9. CPU UTILIZATION VERSUS CPU SATURATION

These are related but different ideas.

## Utilization

How busy the CPU is.

## Saturation

Whether more runnable work exists than available CPU capacity can promptly execute.

A system may have high utilization and still perform correctly.

For example:

```text
CPU utilization: high
Latency: normal
Queueing: controlled
Throughput: expected
```

This may be healthy.

Another system may show:

```text
CPU utilization: high
Runnable work: growing
Latency: increasing
Requests: timing out
```

This is much more concerning.

Therefore:

```text
High Utilization
≠
Automatically Unhealthy
```

---

# 10. INSPECT CPU WITH `top`

Run:

```bash
top
```

`top` provides a live view of:

- system load
- CPU activity
- memory
- swap
- processes
- per-process CPU
- per-process memory

Do not immediately sort the process list and kill the first process.

Start at the system level.

Ask:

```text
Is the system generally CPU busy?

Is one process dominant?

Are many processes competing?

Is the CPU mostly idle?

Is there substantial I/O-related waiting?

Is this persistent or transient?
```

---

# 11. CPU CATEGORIES

Depending on the `top` implementation and environment, CPU lines may expose categories such as:

```text
us
sy
ni
id
wa
hi
si
st
```

Common interpretations include:

```text
us
user-space execution

sy
kernel/system execution

ni
niced user processes

id
idle

wa
I/O wait accounting

hi
hardware interrupt handling

si
software interrupt handling

st
virtualization steal time
```

Do not interpret any single field without system context.

---

# 12. USER CPU

High user CPU can indicate application code performing substantial computation.

Possible explanations:

- legitimate workload
- compression
- encryption
- compilation
- data processing
- application loop
- inefficient code
- traffic increase

Therefore:

```text
High User CPU
↓
Which Process?
↓
What Is It Doing?
↓
Is That Work Expected?
```

---

# 13. SYSTEM CPU

High system CPU indicates significant CPU time in kernel execution.

Possible areas for investigation may include:

- networking
- filesystem activity
- system calls
- kernel work
- high process/thread activity
- interrupt-related work

It does not automatically mean:

```text
Kernel bug
```

Again, evidence first.

---

# 14. I/O WAIT REQUIRES CAREFUL INTERPRETATION

Tools may expose CPU time categorized as I/O wait.

Do not translate:

```text
wa = 30%
```

into:

```text
Disk is 30% utilized.
```

They are not equivalent.

Linux CPU accounting around I/O wait has nuances, especially on multicore systems. Treat it as a clue that should be correlated with storage and workload evidence rather than a complete storage diagnosis.

---

# 15. IDENTIFY CPU-CONSUMING PROCESSES

Snapshot:

```bash
ps aux --sort=-%cpu | head -n 15
```

Then inspect the exact process:

```bash
ps -p <PID> -o user,pid,ppid,stat,%cpu,%mem,etime,cmd
```

Questions:

```text
Which process?

Which user?

Which parent?

How long has it existed?

What command started it?

How much CPU?

Is the process expected?

Did it begin near the incident time?
```

# 16. CPU TROUBLESHOOTING PATH

Use:

```text

      ↓

      ↓

      ↓

   /       \

 ↓           ↓
```

# 17. LAB: CREATE CONTROLLED HIGH CPU

Use a disposable lab.

Start a CPU-consuming process:

```bash
yes > /dev/null &
```

Capture:

```bash
CPU_PID=$!
```

Inspect:

```bash
ps -p "$CPU_PID" -o pid,ppid,stat,%cpu,%mem,etime,cmd
```

Then:

```bash
top
```

Observe.

Do not assume the percentage will display identically on every machine. CPU count, scheduler behavior, tool conventions, and environment can affect presentation.

Terminate gracefully:

```bash
kill "$CPU_PID"
```

Verify:

```bash
ps -p "$CPU_PID"
```

# 18. MEMORY: FREE MEMORY IS NOT THE WHOLE STORY

Linux uses memory for more than application allocations.

Memory may be used for:

- processes
- kernel structures
- filesystem cache
- buffers
- shared memory
- page cache
- other kernel-managed purposes

Therefore:

```text
Low "free" memory
≠
Automatically Memory Crisis
```

A more useful question is:

```text
How much memory can the system make available for new workload without severe pressure?
```

---

# 19. INSPECT MEMORY

Run:

```bash
free -h
```

Typical fields may include:

```text
total
used
free
shared
buff/cache
available
```

Do not focus only on:

```text
free
```

The `available` estimate is often more operationally useful for understanding memory that can be made available for additional workload without swapping heavily.

Exact calculations and fields depend on the system and tool version.

---

# 20. `/proc/meminfo`

Inspect:

```bash
cat /proc/meminfo
```

Important fields may include:

```text
MemTotal
MemFree
MemAvailable
Buffers
Cached
SwapTotal
SwapFree
```

Do not memorize every field.

Understand the relationship:

```text
Kernel Memory State
      ↓
/proc/meminfo
      ↓
Utilities such as free
      ↓
Human-readable summary
```

---

# 21. MEMORY PRESSURE

Memory utilization and memory pressure are not identical.

A system may use most physical memory productively through cache while remaining healthy.

Memory pressure becomes more concerning when the system struggles to satisfy memory demand efficiently.

Evidence may include:

- low available memory
- active reclaim
- swapping
- increasing latency
- allocation failures
- OOM events
- workload stalls

The investigation should combine evidence rather than use one threshold.

---

# 22. IDENTIFY MEMORY-CONSUMING PROCESSES

Use:

```bash
ps aux --sort=-%mem | head -n 15
```

Then:

```bash
ps -p <PID> -o user,pid,ppid,stat,%cpu,%mem,rss,vsz,etime,cmd
```

Two terms you may encounter:

```text
RSS
VSZ
```

A simplified beginner model:

```text
RSS
→ resident memory currently associated with the process in physical memory

VSZ
→ virtual address space size
```

Do not assume:

```text
VSZ = actual RAM consumed
```

It does not.

---

# 23. PROCESS MEMORY IS MORE COMPLEX THAN ONE NUMBER

Processes may use:

- private memory
- shared libraries
- shared mappings
- anonymous memory
- file-backed mappings
- page cache interactions

Therefore:

```text
Memory Investigation
≠
Sort by One Column and Stop
```

At Junior first-line level, identify suspicious processes and gather evidence.

Deeper application memory profiling belongs to application-specific and advanced Linux investigation.

---

# 24. INSPECT PROCESS MEMORY THROUGH `/proc`

For a process:

```bash
cat /proc/<PID>/status
```

Look for fields such as:

```text
VmSize
VmRSS
```

where available.

A more detailed view may be available through:

```bash
cat /proc/<PID>/smaps_rollup
```

subject to kernel support and permissions.

The kernel exposes extensive per-process runtime information through `/proc/<PID>`.

---

# 25. MEMORY GROWTH OVER TIME

One memory snapshot does not prove a leak.

Suppose:

```text
14:00 RSS = 500 MB
```

You cannot conclude:

```text
Memory leak.
```

You need trend evidence.

For example:

```text
14:00  500 MB
14:10  700 MB
14:20  900 MB
14:30  1.1 GB
```

Then ask:

```text
Did workload increase?

Is caching expected?

Does memory stabilize?

Does garbage collection occur?

Does the application release memory?

Did a deployment change behavior?
```

A leak is a hypothesis until supported.

---

# 26. SWAP

Swap provides disk-backed space that the kernel can use as part of virtual memory management.

Inspect:

```bash
free -h
```

and:

```bash
swapon --show
```

where available.

You may also inspect:

```bash
cat /proc/swaps
```

---

# 27. SWAP USAGE DOES NOT AUTOMATICALLY MEAN FAILURE

A system can have some swap used and still operate correctly.

Do not conclude:

```text
Swap Used
=
Memory Crisis
```

More useful questions include:

```text
Is swap activity increasing?

Is the system under memory pressure?

Are workloads stalling?

Is latency increasing?

Is active memory repeatedly being moved between RAM and swap?
```

---

# 28. SWAP ACTIVITY

Where `vmstat` is available:

```bash
vmstat 1
```

You may encounter columns such as:

```text
si
so
```

commonly representing swap-in and swap-out activity.

The first line of `vmstat` may represent values since boot or otherwise differ from subsequent interval samples depending on implementation.

Do not interpret one line without understanding the tool.

Observe several intervals.

---

# 29. `vmstat` AS A SYSTEM VIEW

Run:

```bash
vmstat 1 10
```

This can provide evidence about:

- runnable tasks
- blocked tasks
- memory
- swap
- I/O
- system activity
- CPU

The exact column names and meanings should be verified with:

```bash
man vmstat
```

on the system being investigated.

The important point is that `vmstat` helps correlate multiple resource dimensions over time.

# 31. OUT OF MEMORY EVENTS

Under severe memory pressure, Linux may invoke out-of-memory handling and terminate a process.

Do not assume a disappeared process crashed internally.

It may have been terminated by the kernel.

Investigate kernel/system logs.

Depending on the system:

```bash
journalctl -k
```

Search:

```bash
journalctl -k | grep -i -E 'oom|out of memory|killed process'
```

You may also inspect:

```bash
dmesg
```

subject to permissions and environment.

---

# 32. OOM EVIDENCE

A process disappearing is the symptom.

Evidence may show:

```text
Kernel reports out-of-memory condition.

Kernel reports a process was killed.
```

Then the investigation becomes:

```text
Why did memory pressure become severe?
```

not merely:

```text
Why did application.exe disappear?
```

---

# 33. OOM SCORE

Linux exposes OOM-related information for processes through `/proc`.

For example:

```bash
cat /proc/<PID>/oom_score
```

and:

```bash
cat /proc/<PID>/oom_score_adj
```

The kernel uses OOM-related scoring as part of victim selection.

At Junior level:

**inspect; do not tune these values casually.**

Changing OOM behavior without understanding system design can make future failures worse.

---

# 34. LAB: CONTROLLED MEMORY PRESSURE

Do not intentionally exhaust memory on a shared machine.

Use a disposable VM with known limits.

Rather than attempting to crash the host, create a bounded memory consumer.

If Python is installed:

```bash
python3 - <<'PY'
import time
data = bytearray(200 * 1024 * 1024)
print("Allocated approximately 200 MiB")
time.sleep(120)
PY
```

In another terminal inspect:

```bash
free -h
```

and:

```bash
ps aux --sort=-%mem | head
```

The exact impact depends on the lab size.

Do not increase the allocation blindly.

The objective is observation, not system destruction.

---

# 35. DISK HAS MULTIPLE MEANINGS

When someone says:

```text
Disk problem
```

they may mean:

```text
Filesystem capacity full

Inodes exhausted

Storage latency high

Device errors

Read/write throughput saturated

Filesystem mounted read-only

Application cannot write

Wrong filesystem/path

Storage unavailable
```

These are different failures.

---

# 36. FILESYSTEM CAPACITY

Inspect:

```bash
df -h
```

This shows mounted filesystem capacity in human-readable units.

Focus on the filesystem containing the affected path.

Do not simply inspect the first row.

Suppose:

```text
/var
```

is full while:

```text
/
```

has plenty of free capacity.

An application writing to `/var` may still fail.

---

# 37. PATH TO FILESYSTEM MAPPING

To inspect the filesystem containing a particular path:

```bash
df -h /var/log
```

or:

```bash
df -h /opt/application
```

This is better than assuming which filesystem owns the path.

Think:

```text
Application Path
      ↓
Mounted Filesystem
      ↓
Capacity
```

---

# 38. FIND LARGE DIRECTORIES

If a filesystem is full, you need to understand what consumes space.

Example:

```bash
du -x -h --max-depth=1 /var 2>/dev/null
```

GNU `du` supports this style; options vary across implementations.

Another useful approach:

```bash
du -xsh /var/* 2>/dev/null
```

Do not immediately delete the largest directory.

First determine:

```text
What owns the data?

Is it expected?

Is it active?

Is retention configured?

Can it be safely removed?

Will the application recreate it?

Is deletion the correct long-term fix?
```

---

# 39. `df` AND `du` ANSWER DIFFERENT QUESTIONS

Conceptually:

```text
df
→ filesystem-level space usage

du
→ space attributed to reachable directory/file trees
```

Their results can differ.

That difference can itself become troubleshooting evidence.

One classic reason is a deleted file that remains open by a running process.

---

# 40. DELETED BUT OPEN FILES

On Unix-like systems, deleting a pathname does not necessarily immediately release the underlying storage if a running process still has the file open.

Conceptually:

```text
Process
   ↓
Open File Descriptor
   ↓
File Data

Pathname deleted
   ↓
Directory entry removed

But process still references file
   ↓
Storage may remain allocated
```

This can produce:

```text
df says filesystem is full

du cannot find equivalent visible data
```

---

# 41. FIND DELETED OPEN FILES

Where `lsof` is installed:

```bash
sudo lsof +L1
```

or:

```bash
sudo lsof | grep '(deleted)'
```

depending on what you need.

Do not automatically kill the process.

Determine:

```text
Which process?

Which file?

How large?

Why was it deleted?

Can the service be safely restarted?

Is log rotation misconfigured?

Will restarting affect users?
```

---

# 42. INODES

Filesystem capacity is not only bytes.

Filesystems also require metadata structures for filesystem objects.

You can have free storage capacity while being unable to create new files because available inodes are exhausted.

Inspect:

```bash
df -i
```

---

# 43. INODE EXHAUSTION

Possible symptom:

```text
Application cannot create file.
```

You inspect:

```bash
df -h
```

and see free space.

You might incorrectly conclude:

```text
Disk is fine.
```

Then:

```bash
df -i
```

shows inode exhaustion.

A common pattern can be huge numbers of small files.

Therefore:

```text
Free Bytes
≠
Guaranteed Ability to Create Files
```

---

# 44. FINDING LARGE NUMBERS OF FILES

If inode usage is unexpectedly high, investigate directories containing many files.

For a controlled scope:

```bash
find /suspected/path -xdev -type f | wc -l
```

But be cautious.

Running large recursive scans on heavily loaded production filesystems can itself consume resources.

Start with known application directories where possible.

# 45. LAB: FILESYSTEM CAPACITY INVESTIGATION

On your lab:

```bash
df -h
```

Then:

```bash
df -h "$HOME"
```

Then:

```bash
df -i "$HOME"
```

Create:

```bash
mkdir -p "$HOME/veriqta-troubleshooting-lab/files"
```

Create several files:

```bash
for i in $(seq 1 1000); do
    : > "$HOME/veriqta-troubleshooting-lab/files/file-$i"
done
```

Inspect:

```bash
du -sh "$HOME/veriqta-troubleshooting-lab/files"
```

Then:

```bash
find "$HOME/veriqta-troubleshooting-lab/files" -type f | wc -l
```

Observe:

```text
Many files
does not necessarily mean
large byte consumption.
```

This helps separate inode usage from capacity usage.

Clean up after the lab.

---

# 46. STORAGE I/O

Capacity tells you:

```text
Can more data fit?
```

I/O performance asks:

```text
How quickly can storage requests be serviced?
```

A filesystem can have:

```text
70% free space
```

while storage performance is poor.

Capacity and performance are different dimensions.

---

# 47. STORAGE I/O TOOLS

Where installed, tools such as:

```bash
iostat
```

can provide storage and CPU-related statistics.

A commonly useful form with the `sysstat` implementation is:

```bash
iostat -xz 1
```

However:

- `iostat` may not be installed
- fields vary by version
- device behavior differs
- virtual/cloud storage complicates interpretation

Always check:

```bash
iostat --version
```

and:

```bash
man iostat
```

when relying on detailed metrics.

---

# 48. DO NOT DIAGNOSE STORAGE FROM ONE METRIC

Storage analysis may involve:

```text
latency
throughput
operations per second
queueing
utilization
request size
read/write pattern
device type
cloud volume limits
application behavior
```

A single percentage does not explain all of these.

At Junior level, your responsibility is to identify credible evidence that storage may be involved and escalate with that evidence when deeper analysis is required.

---

# 49. PER-PROCESS I/O

Linux exposes process I/O accounting where supported:

```bash
cat /proc/<PID>/io
```

The kernel documents per-process I/O statistics through `/proc/<PID>/io`.

This can help connect:

```text
System I/O Activity
↓
Specific Process
```

Permissions may restrict access.

---

# 50. LOAD AVERAGE

Run:

```bash
uptime
```

You may see:

```text
load average: 2.15, 1.90, 1.42
```

These represent load averages over approximately:

```text
1 minute
5 minutes
15 minutes
```

But load average is frequently misunderstood.

---

# 51. LOAD AVERAGE IS NOT CPU PERCENTAGE

On Linux, load average reflects tasks that are runnable and tasks in uninterruptible sleep, commonly associated with waiting for I/O. It is therefore not simply CPU utilization.

This matters enormously.

You can have:

```text
High Load
+
Low CPU Utilization
```

if many tasks are blocked in uninterruptible waits.

Therefore:

```text
High Load
≠
Automatically CPU Saturation
```

---

# 52. INTERPRETING LOAD REQUIRES CPU CONTEXT

Suppose:

```text
Load average = 4
```

Is that high?

You need context.

Check CPU count:

```bash
nproc
```

where available.

Or:

```bash
lscpu
```

A load value cannot be interpreted sensibly without considering:

- CPU count
- workload type
- runnable tasks
- blocked tasks
- historical baseline

Even then, it is evidence rather than a health verdict.

---

# 53. LOAD TREND

Suppose:

```text
1 min:  12
5 min:   8
15 min:  3
```

This suggests recent load has increased.

Conversely:

```text
1 min:   3
5 min:   8
15 min: 12
```

may suggest the load is declining.

Do not treat these values as precise instantaneous measurements.

Use them as trend indicators.

---

# 54. RUNNABLE AND BLOCKED TASKS

Use:

```bash
vmstat 1
```

Columns commonly include:

```text
r
b
```

which can help indicate runnable and blocked tasks.

Exact interpretation should be checked against the system's `vmstat` documentation.

This can help answer:

```text
Is load related to runnable work?

Are tasks blocked?

Is the CPU busy?

Is I/O involved?
```

---

# 55. PROCESS STATES

Part 3 introduced process states.

Now they become diagnostic evidence.

Using:

```bash
ps -eo pid,ppid,user,stat,etime,cmd
```

you may encounter states such as:

```text
R
S
D
T
Z
```

A simplified model:

```text
R
running or runnable

S
interruptible sleep

D
uninterruptible sleep

T
stopped/traced

Z
zombie
```

Additional characters may appear because `STAT` can contain state plus flags.

Always consult:

```bash
man ps
```

for the implementation in use.

---

# 56. `D` STATE

A task in `D` state is in uninterruptible sleep.

This is commonly associated with waiting in kernel operations such as certain I/O paths.

Do not conclude:

```text
D state = broken disk
```

Possible causes can involve different kernel-managed resources.

But many tasks accumulating in `D` state alongside high load and storage symptoms is important evidence.

---

# 57. ZOMBIE PROCESSES

A zombie is a process that has exited but whose parent has not yet collected its termination status.

It does not mean:

```text
The process is still actively executing.
```

The zombie itself is not consuming normal execution CPU.

If zombie counts grow, investigate the parent process and application behavior.

Do not try to "kill the zombie" as if it were a normal running process.

---

# 58. PROCESS RELATIONSHIPS

Troubleshooting frequently requires understanding:

```text
Parent
↓
Child
↓
Worker
```

For example:

```text
systemd
  ↓
application-master
  ├── worker-1
  ├── worker-2
  └── worker-3
```

If one worker fails, the master may remain.

If the master fails, workers may behave differently depending on the application.

---

# 59. INSPECT PROCESS TREE

Where available:

```bash
pstree -p
```

Or:

```bash
ps -eo pid,ppid,user,stat,etime,cmd --forest
```

This helps answer:

```text
Who created this process?

Is this a worker?

Is this process managed by the application?

Is this an orphaned or unexpected process?

Which service hierarchy does it belong to?
```

---

# 60. PROCESS AGE

A process that has existed for:

```text
90 days
```

and suddenly consumes CPU presents a different question from a process that started:

```text
2 minutes ago
```

immediately after a deployment.

Inspect:

```bash
ps -p <PID> -o pid,lstart,etime,cmd
```

This helps correlate process lifetime with incident timelines.

---

# 61. THREADS

A process may contain multiple threads.

Where useful:

```bash
ps -L -p <PID>
```

or interactive tools may expose thread views.

At Junior level, you do not need deep thread debugging.

You should understand:

```text
One Process
Can Contain
Many Threads
```

and that application CPU consumption may be distributed among them.

---

# 62. OPEN FILES

A process interacts with resources through file descriptors.

Despite the name, file descriptors can refer to more than ordinary files.

They may represent:

- files
- sockets
- pipes
- devices
- other kernel objects

Inspect a process:

```bash
ls -l /proc/<PID>/fd
```

Permissions may restrict access.

---

# 63. FILE DESCRIPTOR MODEL

Conceptually:

```text
Process
  │
  ├── FD 0 → standard input
  ├── FD 1 → standard output
  ├── FD 2 → standard error
  ├── FD 3 → file
  ├── FD 4 → socket
  └── FD 5 → pipe
```

File descriptors are central to Linux application operation.

---

# 64. `lsof`

Where installed:

```bash
lsof -p <PID>
```

can show open resources associated with a process.

You may use it to investigate:

- open files
- sockets
- deleted files
- log files
- working directories
- libraries

Do not assume `lsof` exists on minimal systems.

---

# 65. FILE DESCRIPTOR EXHAUSTION

Processes and systems have limits on open file descriptors.

A process reaching its limit may produce errors such as:

```text
Too many open files
```

Inspect shell limit:

```bash
ulimit -n
```

For a running process, limits may be visible through:

```bash
cat /proc/<PID>/limits
```

Look for:

```text
Max open files
```

---

# 66. COUNT PROCESS FILE DESCRIPTORS

For a process you have permission to inspect:

```bash
ls /proc/<PID>/fd | wc -l
```

This provides a count of currently visible descriptors.

Do not conclude there is a leak simply because the count is high.

Ask:

```text
Is the count increasing?

What workload is active?

What is the configured limit?

What kinds of descriptors are open?

Does the application close them?
```

---

# 67. SOCKETS

Applications communicate through sockets.

A socket may represent:

- TCP connection
- UDP endpoint
- Unix domain socket
- listening endpoint

A process can be running perfectly while the expected socket is absent.

Therefore:

```text
Process Running
≠
Application Listening
```

---

# 68. `ss`

Modern Linux systems commonly provide:

```bash
ss
```

Inspect listening TCP and UDP sockets:

```bash
ss -lntup
```

Permissions affect whether process information is visible.

Common option concepts:

```text
-l  listening
-n  numeric
-t  TCP
-u  UDP
-p  process information
```

Check:

```bash
ss --help
```

or:

```bash
man ss
```

on the system.

---

# 69. APPLICATION LISTENING CHECK

Suppose your application should listen on:

```text
TCP 8080
```

Inspect:

```bash
ss -lntp
```

You are asking:

```text
Is anything listening on TCP port 8080?

On which local address?

Which process owns it?
```

This is more precise than:

```text
Application is running.
```

---

# 70. LISTENING ADDRESS MATTERS

Consider:

```text
127.0.0.1:8080
```

versus:

```text
0.0.0.0:8080
```

These are operationally different.

An application bound only to loopback may work locally while being unreachable from external interfaces.

Networking is covered more deeply later.

For now, recognize:

```text
Port Number Alone
≠
Complete Socket State
```

# 71. SOCKET STATES

TCP connections may appear in states such as:

```text
LISTEN
ESTAB
TIME-WAIT
CLOSE-WAIT
SYN-SENT
```

Do not memorize every TCP state yet.

At this stage, learn to distinguish:

```text
Listening for connections

Established connection

Connection lifecycle state
```

# 72. SYSTEM LOGS

Logs provide historical evidence.

On systemd-based systems:

```bash
journalctl
```

can expose journal records.

Useful filters include:

```bash
journalctl --since "10 minutes ago"
```

and:

```bash
journalctl --since "2026-10-01 14:00" --until "2026-10-01 14:20"
```

Use the actual incident time.

---

# 73. SERVICE LOGS

For a systemd service:

```bash
journalctl -u <service>
```

Recent entries:

```bash
journalctl -u <service> -n 100
```

Follow:

```bash
journalctl -u <service> -f
```

Time-bound:

```bash
journalctl -u <service> --since "15 minutes ago"
```

Logs should be correlated with the incident timeline.

---

# 74. SYSTEM VERSUS APPLICATION LOGS

Do not assume the system journal contains everything.

An application may log to:

```text
/var/log/application/

standard output

standard error

remote logging platform

container runtime

application-specific file

cloud logging service
```

Ask:

```text
Where does this application actually log?
```

---

# 75. KERNEL MESSAGES

Kernel evidence may be relevant for:

- OOM events
- device problems
- filesystem issues
- driver events
- networking events
- hardware-related conditions

On systemd systems:

```bash
journalctl -k
```

may provide kernel messages.

Another interface:

```bash
dmesg
```

Access can be restricted.

---

# 76. `dmesg` IS NOT "THE APPLICATION LOG"

`dmesg` concerns kernel messages.

Do not search it first for every application failure.

Use the correct evidence source.

```text
Application Error
→ application/service logs

Service Management Error
→ service manager logs

Kernel / Device / OOM Event
→ kernel messages
```

There can be overlap, but the distinction helps structure investigations.

---

# 77. TIME-BOUND LOG INVESTIGATION

Suppose the application became slow at:

```text
14:12
```

Do not start by reading thousands of lines from boot.

Use the relevant time window.

For example:

```bash
journalctl --since "14:05" --until "14:20"
```

Then narrow further.

Troubleshooting efficiency comes from reducing irrelevant evidence.

---

# 78. ERROR MESSAGE DOES NOT AUTOMATICALLY MEAN ROOT CAUSE

Suppose logs show:

```text
Database request timed out.
```

That could mean:

```text
Database slow

Network problem

Connection pool exhausted

Database overloaded

Application timeout too aggressive

DNS problem

Downstream dependency unavailable
```

The error message tells you what the application observed.

It does not always tell you why it happened.

---

# 79. EXIT CODES

Part 3 introduced exit status.

Now use it diagnostically.

Run:

```bash
command
echo $?
```

General convention:

```text
0
→ success

non-zero
→ command-specific failure or alternate outcome
```

Do not assume every non-zero code means the same thing.

Consult command/application documentation.

---

# 80. CAPTURE EXIT STATUS IMMEDIATELY

The shell variable:

```bash
$?
```

contains the status of the most recently completed foreground pipeline/command according to shell semantics.

Therefore:

```bash
failing-command
echo $?
```

is useful.

But:

```bash
failing-command
some-other-command
echo $?
```

reports the status associated with `some-other-command`, not necessarily the original failure.

Context matters.

---

# 81. SERVICE EXIT INFORMATION

For systemd-managed services:

```bash
systemctl status <service>
```

may show process exit information.

You can also inspect properties:

```bash
systemctl show <service> \
  --property=ExecMainCode \
  --property=ExecMainStatus \
  --property=Result
```

Interpret these in the context of the service and systemd documentation.

An exit status tells you how execution ended.

It does not necessarily tell you the root cause.

---

# 82. SIGNALS IN TROUBLESHOOTING

Signals may explain why a process disappeared.

A process may terminate because:

```text
it exited normally

it returned an error

it received SIGTERM

it received SIGKILL

it crashed because of a fatal signal

the kernel terminated it during OOM handling
```

These are operationally different.

---

# 83. DO NOT ASSUME "PROCESS DIED" MEANS "APPLICATION CRASHED"

Investigate:

```text
Who or what terminated it?

Was shutdown intentional?

Was there a deployment?

Did systemd stop it?

Did an operator kill it?

Did the kernel kill it?

Did the process encounter an internal failure?
```

Logs and service metadata help distinguish these possibilities.

---

# 84. RESOURCE PRESSURE

Utilization answers:

```text
How much resource appears to be in use?
```

Pressure asks:

```text
Are workloads being delayed because the resource is contended?
```

These are not identical.

Modern Linux kernels may expose Pressure Stall Information through:

```text
/proc/pressure/cpu
/proc/pressure/memory
/proc/pressure/io
```

PSI quantifies workload stall time caused by CPU, memory, and I/O contention.

---

# 85. INSPECT PSI

Where supported:

```bash
cat /proc/pressure/cpu
```

```bash
cat /proc/pressure/memory
```

```bash
cat /proc/pressure/io
```

You may see fields such as:

```text
some avg10=...
some avg60=...
some avg300=...
full avg10=...
```

Availability depends on kernel configuration and environment.

Do not treat PSI as a replacement for all other tools.

Use it as additional evidence.

---

# 86. `some` AND `full`

At a high level:

```text
some
```

indicates time during which at least some tasks are stalled by the resource.

For memory and I/O, `full` represents periods where all non-idle tasks are simultaneously stalled on that resource. CPU `full` has special system-level semantics and should not be interpreted identically.

At Junior level, the important concept is:

```text
Resource Pressure
→ workload is losing productive time because of contention
```

---

# 87. BASELINES MATTER

Suppose CPU is:

```text
75%
```

Is that abnormal?

You need context.

Maybe the service normally runs:

```text
70–80%
```

Or perhaps it normally runs:

```text
5–10%
```

The same value can mean different things.

Useful context:

```text
Normal baseline

Incident value

Trend

Workload volume

Recent changes

Historical behavior
```

Without baseline, interpretation is weaker.

# 89. LAB: HIGH CPU INCIDENT

## Scenario

The application becomes slow.

Monitoring reports high CPU.

Create a controlled CPU consumer:

```bash
yes > /dev/null &
```

Record:

```bash
CPU_PID=$!
```

Do not begin by using the known PID.

Pretend you do not know the cause.

---

## Step 1: Confirm System State

```bash
uptime
```

Then:

```bash
top
```

Observe several updates.

---

## Step 2: Identify CPU Consumers

```bash
ps aux --sort=-%cpu | head -n 15
```

Identify the suspicious PID.

---

## Step 3: Inspect Exact Process

```bash
ps -p <PID> -o user,pid,ppid,stat,%cpu,%mem,lstart,etime,cmd
```

Questions:

```text
Which user owns it?

What command is it?

How old is it?

Who is its parent?

Is its CPU use persistent?
```

---

## Step 4: Inspect Parent

```bash
ps -p <PPID> -o user,pid,ppid,stat,etime,cmd
```

Build the process relationship.

---

## Step 5: Determine Whether It Is Expected

In the lab:

```text
yes > /dev/null
```

has no legitimate production purpose.

In a real incident, this step requires application context.

---

## Step 6: Correct

For the lab:

```bash
kill "$CPU_PID"
```

---

## Step 7: Verify

```bash
ps -p "$CPU_PID"
```

Then:

```bash
top
```

Verify CPU behavior returns toward baseline.

---

## Root Cause Statement

Do not write:

```text
CPU was high.
```

Write:

```text
A continuously running `yes` process generated sustained CPU demand.
The process was identified as the dominant CPU consumer.
After terminating the controlled lab process, CPU utilization returned toward baseline.
```

# 103. APPLICATION PROCESS EXISTS BUT DOES NOT RESPOND

This is one of the most important troubleshooting scenarios.

Suppose:

```bash
ps
```

shows the application.

Therefore someone concludes:

```text
Application is healthy.
```

That conclusion is invalid.

A process can exist while:

- sleeping normally
- blocked on disk I/O
- waiting on network I/O
- waiting on a lock
- deadlocked
- waiting on another process
- stuck in application logic
- unable to reach a dependency
- listening on the wrong address
- not listening at all
- overloaded
- accepting connections but failing requests

# 115. DON'T RANDOMLY RESTART

Restarting can:

- restore service
- destroy transient evidence
- reset counters
- clear process state
- close sockets
- release leaked resources
- hide the actual failure
- make reproduction harder

Sometimes restart is necessary to restore service.

But understand the tradeoff:

```text
Recovery
versus
Evidence Preservation
```

During an active incident, user impact may make recovery the priority.

The decision should be intentional.

---

# 116. DON'T RANDOMLY KILL PROCESSES

Before:

```bash
kill <PID>
```

ask:

```text
What is this process?

Who owns it?

What service owns it?

Will it restart?

Does it hold important state?

Could termination corrupt work?

Will users be affected?

Do I have authorization?
```

A PID is not enough context.

---

# 117. DON'T RANDOMLY CLEAR LOGS

If disk is full because of logs, do not immediately:

```text
delete all logs
```

Those logs may contain the evidence required to understand why the filesystem filled.

Instead:

```text
Confirm filesystem

Identify large files

Determine ownership

Determine retention

Preserve required evidence

Apply safe recovery

Fix growth/rotation problem

Verify
```

---

# 118. DON'T DROP CACHES AS A GENERIC MEMORY FIX

You may encounter internet advice suggesting modifications to kernel cache behavior or manually dropping caches.

Do not use such actions as a generic response to:

```text
Memory looks high.
```

Linux intentionally uses otherwise available memory for useful caching.

Kernel tuning should be based on a specific, understood problem and appropriate documentation.

---

# 119. DON'T DISABLE SWAP JUST BECAUSE SWAP IS USED

Similarly:

```text
Swap Used
```

does not automatically mean:

```text
Disable Swap.
```

Changing memory architecture without understanding workload requirements can make behavior worse.

Investigate first.

---

# 120. DON'T CHANGE KERNEL PARAMETERS CASUALLY

Linux exposes runtime kernel settings through interfaces such as `/proc/sys`.

Some can materially affect system behavior.

The kernel documentation explicitly warns that some filesystem-related sysctl settings can disrupt system operation if changed incorrectly.

At this level:

```text
Inspect
Understand
Verify Documentation
Escalate When Necessary
```

Do not tune blindly.

# 121. EVIDENCE QUALITY

Not all evidence is equal.

Weak:

```text
Server feels slow.
```

Better:

```text
API latency increased.
```

Stronger:

```text

```

```text
Host load rose during the same period.
```

Then:

```text

```

```text

```

The investigation becomes progressively more specific.

# 122. OBSERVATION VERSUS INFERENCE

Separate:

```text
Observed:
Process 4182 uses high CPU.
```

from:

```text
Inference:
Process 4182 may be contributing to application latency.
```

from:

```text
Confirmed:
Stopping the controlled workload returned CPU and latency to baseline.
```

This prevents premature conclusions.

# 123. HYPOTHESIS-DRIVEN TROUBLESHOOTING

A hypothesis should be testable.

Weak:

```text
Linux is broken.
```

Better:

```text

```

Test:

```text

Are runnable tasks queueing?

Does application latency correlate?

```

Do not defend your first guess.

# 139. ESCALATION IS PART OF TROUBLESHOOTING

A Junior engineer is not expected to solve every Linux failure.

# 155. THE PART 4 TROUBLESHOOTING HABIT

When an application is slow, do not ask:

```text
Which command fixes high CPU?
```

Ask:

```text
Is CPU actually the constrained resource?

If yes, which process is consuming it?

Is that consumption expected?

What caused the process behavior?

Did traffic change?

Did code change?

Did configuration change?

What do the application logs show?

Does resource behavior correlate with user impact?

What evidence would disprove my theory?
```

When memory is low, do not ask:

```text
Which process should I kill?
```

Ask:

```text
Is the system actually under memory pressure?

How much memory is available?

Is swap active?

Which process owns memory?

Is usage stable or growing?

Is caching expected?

Was there an OOM event?

Why did demand increase?
```

When a filesystem is full, do not ask:

```text
What can I delete?
```

Ask:

```text
Which filesystem?

Which path?

Bytes or inodes?

Which data grew?

Which process owns it?

Is growth expected?

Is a deleted file still open?

What can be safely removed?

Why did retention or capacity controls fail?
```

When a process exists but the application is frozen, do not ask:

```text
Should I kill -9 it?
```

Ask:

```text
What state is the process in?

Is it using CPU?

Is it waiting?

What files are open?

What sockets exist?

What dependency is it waiting for?

What do the logs show?

Can I preserve useful evidence before recovery?
```

# 157. READY FOR PART 5

Linux troubleshooting has now established a critical principle:

```text
An Application Failure
Does Not Automatically Mean
An Application Problem
```

The application may be healthy internally but unable to communicate.

A service may be running but unreachable.

A process may listen on the wrong interface.

DNS may resolve incorrectly.

A route may be missing.

A port may be blocked.

A connection may time out.

A remote dependency may be unreachable.

# PART 5: NETWORKING FUNDAMENTALS FOR DEVOPS
