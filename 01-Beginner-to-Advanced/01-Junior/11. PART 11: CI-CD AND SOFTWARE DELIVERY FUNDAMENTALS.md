# PART 11: CI/CD AND SOFTWARE DELIVERY FUNDAMENTALS

## Goal

Understand how source changes move through automated validation and deployment workflows.

By the end of this Part, the learner should understand how a change moves from a developer's workstation through automated checks, artifact creation, deployment, and post-deployment verification.

The learner should be able to answer:

```text
What changed?

What triggered the pipeline?

Which jobs ran?

Where did they run?

What was validated?

Which tests passed?

Which tests failed?

Was an artifact created?

Which exact artifact was created?

Were security checks performed?

Was that artifact deployed?

Which environment received it?

Did the deployment command succeed?

Is the deployed application actually healthy?

If something failed, where did it fail?

What evidence proves the failure?
```

The central mental model is:

```text
Commit
   ↓
Pipeline Trigger
   ↓
Validate
   ↓
Test
   ↓
Build
   ↓
Security Checks
   ↓
Artifact
   ↓
Deploy
   ↓
Verify
```

A more complete production-oriented model is:

```text
Engineer
   ↓
Source Change
   ↓
Local Validation
   ↓
Git Commit
   ↓
Push / Pull Request
   ↓
Pipeline Trigger
   ↓
Pipeline Created
   ↓
Jobs Scheduled
   ↓
Runner / Agent
   ↓
Source Checkout
   ↓
Dependency Preparation
   ↓
Lint / Static Validation
   ↓
Tests
   ↓
Build
   ↓
Security Checks
   ↓
Immutable Artifact
   ↓
Artifact Repository / Container Registry
   ↓
Environment Promotion
   ↓
Deployment
   ↓
Application Startup
   ↓
Health Verification
   ↓
Release Evidence
```

The most important principle in this Part is:

> Pipeline success is not the same as application health.

A second principle is equally important:

> Automation should make a delivery process more repeatable and observable. It should not turn an unsafe manual process into a faster unsafe process.

---

# 1. THE PROBLEM SOFTWARE DELIVERY MUST SOLVE

Consider the application from Parts 8 and 10.

An engineer changes the application.

The new version must eventually reach an environment where someone can use it.

Without automation, the process might look like:

```text
Developer changes code

Developer runs some tests

Developer builds something

Developer logs into a server

Developer copies files

Developer stops old application

Developer starts new application

Developer checks whether it works
```

This can work.

But it creates important questions:

```text
Did every engineer perform the same steps?

Were all tests executed?

Were dependency versions consistent?

Was the correct commit built?

Was the correct artifact deployed?

Was the server changed manually?

Was anything forgotten?

Can another engineer reproduce the deployment?

Can the previous version be identified?

Can the deployment be audited?

Can the previous version be restored?

Was the application verified after deployment?
```

These are software delivery problems.

---

# 2. THE MANUAL DELIVERY PROBLEM

Imagine three engineers deploying the same application.

Engineer A:

```text
runs tests
builds image
deploys
checks health
```

Engineer B:

```text
builds image
deploys
```

Engineer C:

```text
builds locally
copies files manually
restarts service
```

All three may describe their process as:

```text
deployment
```

But the processes are not equivalent.

This inconsistency creates risk.

---

# 3. AUTOMATION DOES NOT AUTOMATICALLY CREATE SAFETY

A common mistake is:

```text
Manual Process
      ↓
Put Commands in Pipeline
      ↓
Safe CI/CD
```

That conclusion is wrong.

If the original process is unsafe:

```text
No tests

No artifact identity

No rollback plan

No deployment verification

Credentials in scripts

Uncontrolled production access
```

automating it may simply execute the unsafe process faster.

The better model is:

```text
Understand Delivery Process
        ↓
Identify Required Controls
        ↓
Define Verification
        ↓
Automate Repeatable Steps
        ↓
Preserve Evidence
        ↓
Control Deployment Authority
```

---

# 4. WHAT CI/CD MEANS

The abbreviation:

```text
CI/CD
```

is commonly used to describe automated software integration and delivery practices.

But it can refer to different concepts:

```text
Continuous Integration

Continuous Delivery

Continuous Deployment
```

These terms should not be treated as identical.

---

# 5. CONTINUOUS INTEGRATION

Continuous Integration, or CI, is the practice of integrating changes frequently and validating those changes automatically.

A simplified model:

```text
Code Change
    ↓
Commit / Push
    ↓
Automated Validation
    ↓
Tests
    ↓
Build
    ↓
Feedback
```

The objective is to detect integration problems early.

---

# 6. CI IS NOT JUST "RUNNING A PIPELINE"

A pipeline existing does not automatically mean a team practices effective Continuous Integration.

Useful CI normally requires:

```text
frequent integration

automated validation

repeatable tests

fast enough feedback

clear failure reporting

consistent build process
```

A pipeline that nobody trusts provides limited value.

---

# 7. CONTINUOUS DELIVERY

Continuous Delivery generally means keeping software in a state where it can be released through a reliable, repeatable process.

Conceptually:

```text
Commit
   ↓
Validate
   ↓
Test
   ↓
Build
   ↓
Artifact
   ↓
Deploy to Pre-Production
   ↓
Verify
   ↓
Ready for Controlled Release
```

A human decision or approval may still control whether the change reaches production.

---

# 8. CONTINUOUS DEPLOYMENT

Continuous Deployment goes further.

Changes that satisfy the required automated controls can automatically progress into production without requiring a manual release decision for every deployment.

Conceptually:

```text
Commit
   ↓
Automated Validation
   ↓
Automated Tests
   ↓
Automated Build
   ↓
Automated Security Controls
   ↓
Artifact
   ↓
Automated Deployment
   ↓
Automated Verification
   ↓
Production
```

This requires substantial confidence in:

```text
tests

deployment process

observability

rollback or recovery

security controls

change safety
```

---

# 9. CONTINUOUS DELIVERY VERSUS CONTINUOUS DEPLOYMENT

A useful distinction:

```text
Continuous Delivery
=
Software remains deployable through a reliable automated process.
Production release may still require an explicit decision.
```

```text
Continuous Deployment
=
Qualified changes automatically progress to production.
```

Do not use the terms interchangeably.

---

# 10. CI/CD IS A DELIVERY SYSTEM

Think of CI/CD as a system.

It has:

```text
inputs

triggers

configuration

execution infrastructure

jobs

dependencies

credentials

artifacts

environments

deployment targets

outputs

logs

failure modes
```

This means CI/CD must be operated and troubleshot like any other production system.

---

# 11. THE PIPELINE

A pipeline is an automated workflow containing one or more jobs that perform parts of the software delivery process.

Example:

```text
Pipeline
   │
   ├── Validate
   │
   ├── Test
   │
   ├── Build
   │
   ├── Security
   │
   ├── Publish
   │
   ├── Deploy
   │
   └── Verify
```

The exact implementation differs between CI/CD platforms.

The engineering concepts remain portable.

---

# 12. PIPELINE CONFIGURATION

Pipeline definitions are commonly stored as code.

Examples include:

```text
.github/workflows/*.yml

.gitlab-ci.yml

Jenkinsfile
```

depending on the platform.

The exact syntax differs.

The important principle is:

> The delivery process should be understandable, reviewable, and version controlled.

---

# 13. PIPELINE AS CODE

Pipeline-as-code gives teams the ability to:

```text
review delivery changes

track history

compare revisions

test modifications

require approval

identify who changed behavior

revert configuration changes
```

This connects directly to Part 6:

```text
Git
   ↓
Pull Request
   ↓
Review
   ↓
Pipeline Definition
```

---

# 14. PIPELINE CONFIGURATION IS PRODUCTION CODE

A one-line application change might affect one feature.

A one-line pipeline change could affect:

```text
every build

every deployment

every environment

credential access

artifact publication

production releases
```

Therefore:

> CI/CD configuration deserves engineering review.

---

# 15. PIPELINE TRIGGER

Something must cause the pipeline to begin.

Common triggers include:

```text
push

pull request

merge request

tag

schedule

manual action

API event

upstream pipeline
```

Not every pipeline should run every job for every trigger.

---

# 16. TRIGGER EXAMPLE

A team may choose:

```text
Pull Request
     ↓
Lint
Test
Build
Security Checks
```

while:

```text
Merge to Main
     ↓
Lint
Test
Build
Security Checks
Publish Artifact
Deploy Staging
Verify Staging
```

and:

```text
Release Approval
     ↓
Deploy Production
Verify Production
```

The exact design is a team decision.

---

# 17. TRIGGERS DEFINE AUTHORITY

Triggers are not merely convenience.

They help answer:

```text
Who can cause this action?

From which branch?

Under which conditions?

For which environment?
```

A production deployment trigger is therefore part of the security model.

---

# 18. STAGES

A stage is a logical phase of a pipeline.

Example:

```text
Validate
   ↓
Test
   ↓
Build
   ↓
Security
   ↓
Deploy
   ↓
Verify
```

Stages help communicate ordering and intent.

---

# 19. JOBS

A job is an executable unit of pipeline work.

For example:

```text
Stage: Validate

Jobs:
├── YAML Validation
├── Shell Lint
└── Application Lint
```

Another stage:

```text
Stage: Test

Jobs:
├── Unit Tests
└── Configuration Tests
```

Jobs are where commands actually execute.

---

# 20. STAGE VERSUS JOB

Do not confuse them.

```text
Stage
=
Logical pipeline phase
```

```text
Job
=
Executable unit of work
```

A stage can contain multiple jobs.

---

# 21. JOB PARALLELISM

Suppose two tests do not depend on each other:

```text
Test Stage
   ├── Unit Tests
   └── Lint
```

They may be able to execute in parallel.

This can reduce pipeline duration.

But parallel execution is appropriate only when the jobs are actually independent.

---

# 22. JOB DEPENDENCIES

Some jobs require outputs from earlier jobs.

Example:

```text
Build Image
    ↓
Image Digest
    ↓
Deploy Image
```

The deployment should not invent or rebuild a different artifact.

It needs the identity of the artifact created earlier.

---

# 23. PIPELINE DEPENDENCY GRAPH

A pipeline does not always have to be purely linear.

Example:

```text
              ┌── Lint ───────┐
Commit ───────┤                ├── Build ── Security ── Deploy
              └── Unit Tests ──┘
```

Both validation jobs can run independently.

The build waits until required validation succeeds.

---

# 24. RUNNERS AND AGENTS

Pipeline commands need somewhere to execute.

Different systems use terms such as:

```text
runner

agent

worker

executor
```

Conceptually:

```text
Pipeline Platform
       ↓
Schedules Job
       ↓
Runner / Agent
       ↓
Executes Commands
       ↓
Reports Result
```

---

# 25. RUNNER IS COMPUTE

A runner is not an abstract magic execution environment.

It ultimately uses compute resources.

Depending on platform and configuration, this could involve:

```text
virtual machine

container

physical machine

cloud-hosted runner

self-hosted runner
```

The environment affects pipeline behavior.

---

# 26. RUNNER ENVIRONMENT MATTERS

A job may depend on:

```text
operating system

CPU architecture

installed tools

runtime versions

network access

filesystem

credentials

Docker availability

cloud access
```

Therefore:

```text
Works on my laptop
```

does not prove:

```text
Works on runner
```

---

# 27. HOSTED VERSUS SELF-HOSTED RUNNERS

A CI/CD platform may provide hosted runners.

Organizations may also operate their own runners.

Self-hosted runners can provide:

```text
custom software

private network access

specialized hardware

organization-controlled execution
```

But they also create responsibilities around:

```text
patching

isolation

credential exposure

network access

capacity

cleanup

monitoring
```

---

# 28. RUNNERS ARE PART OF THE TRUST BOUNDARY

A runner may temporarily receive:

```text
source code

credentials

deployment tokens

cloud permissions

artifacts

registry access
```

Therefore runner security matters.

A compromised runner can become a serious security problem.

---

# 29. JOB WORKSPACE

When a job runs, it typically receives a working directory containing the repository or required files.

Conceptually:

```text
Runner
   ↓
Workspace
   ↓
Repository Checkout
   ↓
Commands Execute
```

Do not assume files created in one job automatically exist in another.

---

# 30. JOBS MAY BE EPHEMERAL

Many CI environments use temporary execution environments.

A job may:

```text
start

receive source

execute commands

upload outputs

finish

lose local workspace
```

Therefore important outputs must be deliberately preserved.

---

# 31. ARTIFACTS

An artifact is an output produced by a build or pipeline process that needs to be preserved, distributed, inspected, or deployed.

Examples:

```text
compiled binary

application package

test report

coverage report

archive

container image

SBOM

deployment manifest
```

Different artifact types may be stored differently.

---

# 32. JOB ARTIFACT VERSUS DEPLOYABLE ARTIFACT

These concepts can overlap but should not be collapsed.

A job may upload:

```text
test-results.xml
```

as a pipeline artifact.

That does not make it the application release artifact.

The deployable artifact might instead be:

```text
container image
```

stored in a registry.

---

# 33. BUILD ONCE, PROMOTE THE SAME ARTIFACT

A strong delivery principle is:

```text
Build
   ↓
Artifact A
   ↓
Test Artifact A
   ↓
Deploy Artifact A to Staging
   ↓
Verify Artifact A
   ↓
Promote Artifact A
```

Avoid:

```text
Build for Test
   ↓
Rebuild for Staging
   ↓
Rebuild Again for Production
```

when those rebuilds can produce materially different artifacts.

---

# 34. WHY REBUILDING DURING PROMOTION IS RISKY

Suppose:

```text
Staging
```

tests:

```text
Image A
```

but production deployment rebuilds and produces:

```text
Image B
```

You can no longer confidently say:

```text
The exact artifact tested in staging
is the artifact running in production.
```

Artifact identity matters.

---

# 35. ARTIFACT IDENTITY

For the Part 10 container:

```text
repository

tag

digest
```

help identify what was built.

For important deployments, the pipeline should preserve enough information to answer:

```text
Which commit produced this artifact?

Which pipeline produced it?

Which image digest was deployed?

Which environment received it?
```

---

# 36. SOURCE IDENTITY

Git already provides a useful source identity:

```text
commit SHA
```

A common delivery relationship is:

```text
Git Commit SHA
      ↓
Pipeline
      ↓
Container Image
      ↓
Image Digest
      ↓
Deployment
```

This creates traceability from running software back toward source.

---

# 37. DEPENDENCIES

Applications require dependencies.

The pipeline itself also requires dependencies.

Examples:

```text
language runtime

package manager

Docker CLI

build tool

test framework

linting tool

security scanner

deployment CLI
```

A missing pipeline dependency can fail a job before application logic is tested.

---

# 38. DEPENDENCY VERSIONING

Avoid assuming:

```text
latest
```

always means:

```text
safe and reproducible
```

Tool versions can change behavior.

Where appropriate, make important pipeline dependencies intentional and review updates deliberately.

---

# 39. VALIDATION

Validation asks:

```text
Is this input structurally acceptable?
```

Examples:

```text
YAML parses

Dockerfile syntax is valid

shell script passes static checks

configuration schema is valid

required files exist
```

Validation is different from testing application behavior.

---

# 40. LINTING

Linting analyzes source or configuration for patterns that may indicate:

```text
syntax problems

style violations

suspicious constructs

common mistakes

unsafe patterns
```

Examples vary by language and technology.

Linting is useful.

It is not proof that the software works.

---

# 41. LINT SUCCESS DOES NOT PROVE CORRECTNESS

A script can be perfectly formatted and logically wrong.

A Dockerfile can parse successfully and build a broken application.

A YAML file can be valid YAML and still contain incorrect platform configuration.

Therefore:

```text
Syntax Valid
≠
Semantically Correct
≠
Application Healthy
```

---

# 42. TESTS

Automated tests provide evidence about expected software behavior.

Examples include:

```text
unit tests

integration tests

API tests

configuration tests

smoke tests
```

This Part focuses on understanding their role in the pipeline rather than designing an enterprise testing strategy.

---

# 43. UNIT TESTS

Unit tests typically validate small units of application behavior.

Conceptually:

```text
Input
 ↓
Function / Component
 ↓
Expected Output
```

They are often fast enough to run early in the pipeline.

---

# 44. INTEGRATION TESTS

Integration tests validate interactions between components.

Examples:

```text
application ↔ database

application ↔ API

service ↔ queue

service ↔ cache
```

They usually require more environment setup than isolated unit tests.

---

# 45. SMOKE TESTS

A smoke test provides basic evidence that a deployed system is functioning at a minimal expected level.

Example:

```text
Deploy
   ↓
GET /health
   ↓
Expected Response
```

A smoke test is not a complete application test suite.

It answers a smaller question:

```text
Does the deployed system appear basically usable?
```

---

# 46. TEST FAILURE IS USEFUL

A failed test is not a pipeline inconvenience to bypass.

It is evidence.

Ask:

```text
Which test failed?

What was expected?

What was observed?

Did the code change?

Did the test change?

Did a dependency change?

Is the runner environment different?

Is the failure reproducible?
```

---

# 47. BUILD

The build stage converts source into a deployable or distributable artifact.

For Part 10:

```text
Source
   ↓
Dockerfile
   ↓
docker build
   ↓
Container Image
```

The CI pipeline should automate that process consistently.

---

# 48. BUILD SUCCESS DOES NOT PROVE RELEASE SUCCESS

A successful build means:

```text
the build process completed successfully
```

It does not prove:

```text
tests passed

image is secure

image was published

deployment succeeded

application started

application is healthy
```

These are separate states.

---

# 49. SECURITY CHECKS

Security checks can be integrated into software delivery.

Examples include:

```text
dependency scanning

container image scanning

secret detection

static application security testing

configuration scanning

software composition analysis
```

Exact capabilities depend on tooling.

---

# 50. SECURITY CHECKS ARE CONTROLS, NOT MAGIC

A scanner can detect some known problems.

It cannot prove:

```text
This application is secure.
```

Pipeline security controls provide evidence within their scope.

They do not eliminate security engineering.

---

# 51. SECURITY CHECK PLACEMENT

Some security checks can happen before build:

```text
source secret detection

source static analysis
```

Others require the built artifact:

```text
container image vulnerability scanning

SBOM analysis
```

Therefore a pipeline may contain security controls at several points.

---

# 52. FAILING SECURITY CHECKS

Organizations need defined policies for:

```text
what constitutes failure

which severity blocks deployment

how exceptions work

who approves exceptions

how long exceptions remain valid
```

Do not randomly suppress security findings just to make a pipeline green.

---

# 53. PUBLISH

After building the Part 10 image, the pipeline can publish it to a registry.

Mental model:

```text
Build Image
    ↓
Identify Image
    ↓
Authenticate to Registry
    ↓
Push
    ↓
Record Digest
```

The registry becomes the distribution point for the deployable artifact.

---

# 54. PUBLISHING REQUIRES AUTHORITY

A build job may only need:

```text
read source
```

A publishing job may need:

```text
write registry
```

A deployment job may need:

```text
modify environment
```

These are different permission levels.

Do not give every job every permission.

---

# 55. LEAST PRIVILEGE IN PIPELINES

Use:

```text
Job
   ↓
Required Action
   ↓
Minimum Required Permission
```

Not:

```text
Pipeline
   ↓
Administrator Credential
   ↓
Everything
```

CI/CD credentials can have enormous blast radius.

---

# 56. PIPELINE SECRETS

Pipelines often require sensitive values such as:

```text
registry credentials

deployment credentials

API tokens

cloud credentials

signing credentials
```

These should not be committed directly into pipeline configuration.

---

# 57. BAD SECRET HANDLING

Do not write:

```yaml
REGISTRY_PASSWORD: "my-real-password"
```

into a repository.

Do not store secrets in:

```text
Git history

Dockerfiles

plain configuration files

pipeline logs

AI prompts
```

---

# 58. SECRET STORES AND CI/CD VARIABLES

CI/CD platforms provide mechanisms for storing sensitive values separately from source-controlled pipeline definitions.

The exact terminology varies:

```text
secrets

credentials

protected variables

environment secrets
```

The concept is:

```text
Pipeline Definition
        ↓
References Secret Name
        ↓
Platform Supplies Secret at Runtime
```

---

# 59. MASKING IS NOT A COMPLETE SECURITY MODEL

A platform may mask secret values in logs.

Do not conclude:

```text
Masked
=
Impossible to expose
```

A job with access to a secret may still misuse or leak it.

Secret access must be restricted.

---

# 60. SECRET SCOPE

Ask:

```text
Which job needs the secret?

Which environment?

Which branch?

Which repository?

Which runner?

For how long?
```

The smallest appropriate scope reduces risk.

---

# 61. LONG-LIVED CREDENTIALS

Long-lived credentials create persistent exposure.

Where supported and appropriate, modern CI/CD designs can use short-lived or workload-based identity instead of storing long-lived static cloud credentials.

The Junior-level principle is:

> Prefer the least powerful credential for the shortest necessary lifetime.

---

# 62. NEVER PRINT SECRETS FOR DEBUGGING

Avoid commands such as:

```text
echo "$SECRET"
```

just to prove the variable exists.

Instead verify presence without revealing value where possible.

For example, a script can test:

```text
Is variable set?
```

without printing its contents.

---

# 63. ENVIRONMENTS

A deployment environment represents a target such as:

```text
development

test

staging

production
```

An environment is more than a branch name.

It represents where software actually runs.

---

# 64. SOURCE BRANCH IS NOT DEPLOYMENT ENVIRONMENT

Do not assume:

```text
branch = environment
```

as a universal law.

A branch is a Git concept.

An environment is an operational target.

A workflow may map them together, but they remain different concepts.

---

# 65. ENVIRONMENT PROMOTION

Promotion means moving an approved artifact through delivery environments.

Conceptually:

```text
Artifact A
   ↓
Development
   ↓
Verification
   ↓
Staging
   ↓
Verification
   ↓
Production
```

The important idea is:

```text
Artifact A
```

remains identifiable throughout the process.

---

# 66. PROMOTE ARTIFACTS, NOT SOURCE ASSUMPTIONS

A mature mental model is:

```text
Commit
   ↓
Build Artifact
   ↓
Qualify Artifact
   ↓
Promote Artifact
```

rather than:

```text
Rebuild whatever happens to be on the branch
for every environment.
```

---

# 67. DEPLOYMENT

Deployment means making a particular version of software available in a target environment through the environment's deployment mechanism.

Depending on architecture, this could involve:

```text
starting a container

updating a service

copying an artifact

updating infrastructure configuration

changing an image reference
```

This Part uses a simple non-production Docker environment.

---

# 68. DEPLOYMENT IS NOT RELEASE

Depending on system design, software can be deployed without immediately exposing a feature to users.

Conceptually:

```text
Deployment
=
Software placed into environment
```

```text
Release
=
Functionality made available to intended users
```

They may occur together in simple systems.

They are not inherently identical.

---

# 69. DEPLOYMENT COMMAND SUCCESS IS NOT DEPLOYMENT VERIFICATION

Suppose:

```text
docker run
```

returns successfully.

That proves only a limited thing.

The application might:

```text
exit seconds later

listen on wrong port

lack configuration

fail dependency checks

return HTTP 500
```

Therefore:

```text
Deployment Command Success
≠
Deployment Success
```

---

# 70. VERIFY

Verification asks whether the deployed result reached the expected state.

For the Part 10 application:

```text
Container Running?
        ↓
Expected Image?
        ↓
Expected Port?
        ↓
Health Endpoint?
        ↓
Expected HTTP Status?
        ↓
Expected Application Behavior?
```

---

# 71. DELIVERY VERIFICATION MODEL

Use:

```text
Action
   ↓
Expected State
   ↓
Inspection
   ↓
Evidence
   ↓
Conclusion
```

Example:

```text
Action:
Deploy image digest X

Expected:
Application responds on staging health endpoint

Inspection:
HTTP request to /health

Evidence:
HTTP 200 with expected response

Conclusion:
Basic deployment verification passed
```

---

# 72. ROLLBACK CONCEPT

Rollback means returning from a problematic deployment toward a previously known version or state.

Simplified:

```text
Version A
   ↓
Deploy Version B
   ↓
Version B Fails
   ↓
Restore Version A
```

But real rollback can be more complicated.

---

# 73. ROLLBACK IS NOT ALWAYS SAFE

Suppose Version B performs a database migration.

Returning application code to Version A may fail if Version A cannot work with the new schema.

Therefore:

```text
Old Artifact Available
≠
Rollback Guaranteed Safe
```

Rollback planning must consider state.

---

# 74. ROLLBACK VERSUS ROLL-FORWARD

Sometimes the safer response is:

```text
Version B
   ↓
Problem
   ↓
Create Version C
   ↓
Deploy Fix
```

rather than restoring Version A.

This is often called rolling forward.

At Junior level, understand that recovery strategy depends on the failure.

---

# 75. PIPELINE LOGS

Every job should produce useful execution evidence.

Logs may show:

```text
commands

tool output

warnings

errors

timestamps

test results

build results
```

When a pipeline fails, logs are usually one of the first sources of evidence.

# 79. YAML VALIDITY VERSUS PIPELINE VALIDITY

A file can be:

```text

```

```text
invalid CI/CD configuration
```

Therefore:

```text

≠

```

# 80. TROUBLESHOOTING SYNTAX FAILURE

```text
exact validation error

file

indentation

expected platform syntax

current official documentation
```

Do not randomly rearrange YAML until the error disappears.

Understand the schema.

```text
✓

✗
```

# 83. DO NOT DISABLE TESTS TO GET GREEN

```text

   ↓

   ↓

```

The pipeline color is not the objective.

# 84. MISSING SECRET

A deployment job may fail because a required secret is unavailable.

Possible causes include:

```text

wrong secret name

wrong environment

secret scope restriction

branch restriction

job lacks environment access

secret expired
```

---

# 85. TROUBLESHOOTING MISSING SECRET

Do not print the secret.

Check:

```text

Is this job allowed to access it?

Is the correct environment referenced?

Is the current branch/tag permitted?

Did the secret expire?

Is the variable name spelled correctly?
```

# 86. PERMISSION PROBLEM

A job may authenticate successfully but lack authorization.

Example:

```text

Push denied
```

or:

```text

Deployment denied
```

This is not necessarily an authentication problem.

# 87. AUTHENTICATION VERSUS AUTHORIZATION

Recall:

```text

=
Who are you?
```

```text
Authorization
=
What are you allowed to do?
```

Pipeline troubleshooting must distinguish them.

---

# 88. MISSING DEPENDENCY


Possible root causes:

```text

wrong runner image

wrong PATH

setup step missing

tool installed in previous job only

version changed
```

Do not assume application failure.

# 89. RUNNER PATH DIFFERENCES

They apply here too.

A tool may work locally because:

```text

```

while the non-interactive CI environment does not load the same configuration.

Therefore pipeline scripts should not depend on undocumented workstation state.

# 90. FAILED BUILD

```text
required file missing
```

Use the exact failing build step as evidence.

# 91. FAILED DEPLOYMENT

A deployment job may fail because:

```text

artifact missing

wrong image reference

port conflict

configuration missing

deployment command failed
```

Separate deployment mechanism failure from post-deployment application failure.

# 92. DEPLOYED BUT VERIFICATION FAILED

This is an especially important state:

```text

✓

✗
```

It means:

> The deployment mechanism completed, but the expected application state was not verified.

Possible causes include:

```text

network path problem
```

# 93. NEVER MARK VERIFICATION OPTIONAL WITHOUT INTENT

A dangerous pipeline can look like:

```text

✓

```

A stronger pipeline is:

```text

✓

✓

✓
```

# 94. PIPELINE FAILURE IS A STATE TRANSITION

Think:

```text

   ↓

   ↓
Runner Assigned
   ↓
Job Started
   ↓

   ↓

   ↓

```

A failure can happen at any of these layers.

---

# 95. EXIT CODES IN CI/CD

Part 7 now becomes operationally important.

Pipeline jobs often use process exit status to determine success or failure.

Conventionally:

```text
0
=
success
```

```text
non-zero
=
failure
```

If your script incorrectly returns `0` after failure, the pipeline may falsely report success.

---

# 96. FALSE GREEN PIPELINE

Consider:

```bash
deploy_application || echo "deployment failed"
```

Depending on the surrounding shell and script behavior, this may consume the failure and allow later execution.

If the job ultimately exits successfully, the pipeline can appear green even though deployment failed.

Therefore:

> Error handling in pipeline scripts must preserve meaningful failure status.

---

# 97. FALSE RED PIPELINE

The opposite can also occur.

The application may have deployed successfully, but an unrelated cleanup command returns non-zero and causes the job to fail.

The pipeline then reports failure.

This is why scripts need deliberate exit behavior.

---

# 98. PIPELINE SCRIPTS ARE SOFTWARE

Treat scripts used in CI/CD as software.

They need:

```text

error handling

clear inputs

clear outputs

meaningful exit codes

safe defaults

logging

tests where appropriate
```

Part 7 directly supports this.

# 151. PIPELINE TROUBLESHOOTING WORKFLOW

For any failure:

```text
Reported Failure
      ↓
Identify Pipeline
      ↓
Identify Commit
      ↓
Identify Stage
      ↓
Identify Job
      ↓
Identify Failing Command
      ↓
Read Logs
      ↓
Determine Expected State
      ↓
Determine Observed State
      ↓
Inspect Inputs
      ↓
Form Hypothesis
      ↓
Test Hypothesis
      ↓
Correct
      ↓
Rerun
      ↓
Verify
```

---

# 152. DO NOT START BY RERUNNING

A rerun can be useful.

But first ask:

```text
Why did the original run fail?
```

If you rerun immediately, a transient failure may disappear and useful investigation context may be lost.

---

# 153. TRANSIENT VERSUS DETERMINISTIC FAILURE

A deterministic failure occurs consistently given the same relevant conditions.

Example:

```text
syntax error
```

A transient failure may depend on temporary conditions.

Example:

```text
temporary network interruption
```

Do not label a failure transient simply because a rerun passed.

Investigate available evidence.

---

# 154. RETRIES

Retries can help with carefully identified transient operations.

But:

```text
Retry Everything Three Times
```

is not a reliability strategy.

Retries can:

```text
hide failures

increase load

repeat destructive actions

delay feedback
```

Use them intentionally.

---

# 155. PIPELINE TIMEOUTS

Jobs should not run forever.

CI/CD platforms support job or workflow timeout mechanisms.

A timeout can protect against:

```text
hung tests

blocked commands

unresponsive dependencies

infinite loops
```

But a timeout only tells you the job exceeded the permitted duration.

It does not identify root cause.

---

# 156. PIPELINE CACHES

Many CI/CD platforms support caching.

A cache may speed up repeated operations such as dependency retrieval.

Conceptually:

```text
Dependency Download
      ↓
Cache
      ↓
Future Job Reuse
```

But:

```text
Cache
≠
Artifact
```

---

# 157. CACHE VERSUS ARTIFACT

Think:

```text
Cache
=
Performance optimization
```

```text
Artifact
=
Output that must be preserved or consumed
```

Do not depend on a cache as the authoritative release artifact.

---

# 158. CACHE PROBLEMS

Caches can cause confusing failures if:

```text
stale dependency

wrong cache key

cross-branch contamination

tool version changed
```

A useful troubleshooting test may be:

```text
Does the job still fail with a clean cache?
```

Do not clear caches blindly as the first action.

---

# 159. PIPELINE ENVIRONMENT CONSISTENCY

A pipeline should reduce dependence on undocumented runner state.

Prefer explicit setup such as:

```text
runtime version

dependency installation

tool version

working directory

environment variables
```

over:

```text
whatever happens to be installed
```

---

# 160. REPRODUCIBLE BUILD THINKING

A strong build attempts to minimize hidden inputs.

Hidden inputs include:

```text
unversioned dependency

mutable external resource

runner-specific package

local file

current time where it changes artifact behavior

uncontrolled latest tag
```

Perfect reproducibility can be difficult.

The Junior engineer should understand why hidden inputs matter.

---

# 161. PIPELINE CONCURRENCY

Two pipelines may run at the same time.

Example:

```text
Commit A Pipeline
      │
      └── Deploy Staging

Commit B Pipeline
      │
      └── Deploy Staging
```

Now ask:

```text
Which deployment should win?
```

Concurrent deployments can create race conditions.

---

# 162. ENVIRONMENT CONCURRENCY CONTROL

CI/CD systems often provide mechanisms for controlling simultaneous deployments.

The concept is:

```text
One Shared Environment
       ↓
Controlled Deployment Concurrency
```

At Junior level, recognize the problem.

Advanced deployment coordination comes later.

---

# 163. STALE PIPELINE PROBLEM

Imagine:

```text
Pipeline A
starts first
but runs slowly
```

Then:

```text
Pipeline B
starts later
but deploys first
```

Then Pipeline A eventually deploys older code.

The environment may regress.

This is why deployment ordering and concurrency matter.

---

# 164. PIPELINE APPROVALS

Some environments may require an approval before deployment.

Conceptually:

```text
Qualified Artifact
      ↓
Deployment Gate
      ↓
Approval
      ↓
Deploy
```

Approvals should represent a meaningful control.

They should not become automatic button-clicking rituals.

---

# 165. PROTECTED ENVIRONMENTS

CI/CD platforms can restrict who or what may deploy to sensitive environments.

The exact implementation is platform-specific.

The general principle is:

```text
Production Authority
≠
Permission Every Pipeline Job Should Have
```

---

# 166. PULL REQUEST PIPELINE

A pull request pipeline should generally focus on answering:

```text
Is this proposed change acceptable to merge?
```

Possible checks:

```text
lint

tests

build validation

security checks
```

It may not need production deployment authority.

---

# 167. POST-MERGE PIPELINE

After an approved change reaches the main integration branch, the pipeline may:

```text
revalidate

build release artifact

publish artifact

deploy non-production

verify
```

The exact policy depends on the team.

---

# 168. TAG OR RELEASE PIPELINE

Some teams use version tags or release events to initiate release workflows.

Conceptually:

```text
Approved Commit
      ↓
Release Tag
      ↓
Release Pipeline
      ↓
Promote Existing Artifact
```

Do not assume tags automatically make software safe.

---

# 169. PIPELINE SECRETS AND UNTRUSTED CHANGES

A critical security question is:

```text
Can untrusted code access deployment secrets?
```

Pull requests from untrusted contributors require careful secret handling.

Do not expose sensitive credentials simply because a pipeline needs to run tests.

---

# 170. CI/CD IS A SECURITY BOUNDARY

A pipeline can potentially:

```text
read source

build artifacts

publish packages

access cloud resources

deploy software

modify infrastructure
```

Therefore compromise of CI/CD can become compromise of the delivery path.

Treat pipeline changes seriously.

---

# 171. DEPENDENCY INSTALLATION IS SUPPLY-CHAIN ACTIVITY

When the pipeline runs:

```text
package manager install
```

it is retrieving and executing or preparing third-party software.

Therefore dependency selection and integrity matter.

This will become more important in later security Parts.

---

# 172. THIRD-PARTY PIPELINE COMPONENTS

CI/CD ecosystems often allow reusable actions, plugins, templates, or components.

These execute within the delivery system.

Do not treat them as harmless snippets.

Evaluate:

```text
publisher

source

version

permissions

maintenance

trust
```

before adoption.

---

# 173. PINNING PIPELINE DEPENDENCIES

Where a platform supports referencing third-party pipeline components by versions, tags, or immutable identifiers, understand the tradeoff.

Mutable references improve update convenience.

Immutable references improve identity control.

The exact safest mechanism is platform-specific and should follow current platform security guidance.

---

# 174. LOGGING STANDARD

A useful pipeline log should answer:

```text
What is happening?

Which component?

Which artifact?

Which environment?

What failed?

What should be inspected next?
```

Avoid logs that expose secrets.

---

# 175. GOOD JOB NAMES

Prefer:

```text
unit-tests

build-container

scan-container

publish-container

deploy-staging

verify-staging
```

over:

```text
job1

job2

stuff

final
```

Names become troubleshooting navigation.

---

# 176. GOOD FAILURE MESSAGE

Weak:

```text
Error.
```

Better:

```text
Required environment variable STAGING_HOST is not set.
Deployment cannot continue.
```

The message tells the engineer what failed and where.

---

# 177. PIPELINE OBSERVABILITY

Even a basic pipeline should expose:

```text
status

duration

job results

logs

artifact information

deployment result
```

This creates operational visibility into software delivery.

---

# 178. PIPELINE DURATION

Pipeline speed matters because slow feedback can encourage developers to:

```text
batch large changes

skip checks

avoid frequent integration
```

But speed should not be achieved by deleting necessary validation.

Optimize intelligently.

---

# 179. FAIL FAST

Where dependencies permit, place inexpensive, high-value checks earlier.

Example:

```text
Syntax
   ↓
Lint
   ↓
Unit Tests
   ↓
Build
   ↓
Security
   ↓
Deploy
```

There is little value spending ten minutes building an artifact when a ten-second syntax check could already prove the change invalid.

---

# 180. FAIL FAST DOES NOT MEAN HIDE OTHER EVIDENCE

Independent checks can sometimes run in parallel.

For example:

```text
           ┌── Lint ─────────┐
Commit ────┤                 ├── Build
           └── Unit Tests ───┘
```

The pipeline design should balance:

```text
feedback speed

resource usage

dependency order

diagnostic usefulness
```

---

# 181. SUCCESS CRITERIA MUST BE EXPLICIT

A job should have a clear definition of success.

Example:

```text
Unit Test Job Success
=
test command exits successfully
```

```text
Build Job Success
=
expected image built successfully
```

```text
Deploy Job Success
=
deployment mechanism completes
```

```text
Verify Job Success
=
deployed application satisfies defined health check
```

These are different success conditions.

---

# 182. PIPELINE GREEN IS A SUMMARY

A green pipeline summarizes the controls configured in that pipeline.

It does not mean:

```text
software contains no bugs

software contains no vulnerabilities

production will never fail

all business requirements are correct
```

It means the configured required checks passed for that run.

---

# 183. FAILED PIPELINE IS ALSO A SUMMARY

A red pipeline does not necessarily mean:

```text
application code is broken
```

It could mean:

```text
runner unavailable

registry unavailable

credential expired

test failed

build failed

deployment denied

verification failed
```

Locate the failure before describing it.

---

# 184. INCIDENT LANGUAGE FOR PIPELINES

Avoid:

```text
CI is broken.
```

Prefer:

```text
The staging deployment job in pipeline 184 failed while
authenticating to the container registry. Validation, tests,
and image build completed successfully. The deployment
environment was not changed.
```

That statement communicates scope.

---

# 185. EVIDENCE-RICH ESCALATION

If a Junior engineer cannot resolve a pipeline failure, escalate with:

```text
repository

commit SHA

pipeline/run ID

trigger

branch/tag

failed stage

failed job

runner if relevant

failing command

error message

expected behavior

observed behavior

checks already performed

whether any deployment occurred

current environment state
```

This is useful escalation.

---

# 186. BAD ESCALATION

Avoid:

```text
Pipeline doesn't work.
Can someone check?
```

It forces the next engineer to restart the investigation.

# 187. AI-ASSISTED CI/CD

```text
explain test failures
```

# 188. AI CAN GENERATE DANGEROUS PIPELINE CODE

```text
ignored test failures

ignored scanner failures

uncontrolled latest tags
```

# 190. AI LAB

Ask AI to draft one basic pipeline job.

For example:

```text

```

---

# 191. REVIEW EVERY GENERATED LINE

Ask:

```text
What does this keyword mean?

What triggers this job?

Which runner executes it?

Which permissions does it receive?

Which files does it access?

Which commands execute?

Which secrets are available?

What happens if the command fails?

What happens if the command succeeds?

What downstream job depends on it?
```

If you cannot answer, do not treat the generated pipeline as understood.

---

# 192. AI MUST NOT INVENT PROJECT COMMANDS

If the repository uses:

```text
pytest
```

AI should not silently replace it with:

```text
npm test
```

or invent:

```text
make test
```

The pipeline must reflect the real project.

---

# 193. AI MUST NOT INVENT SECRET NAMES

Before accepting:

```text
PRODUCTION_API_TOKEN
```

verify that such a secret actually exists and is appropriate.

Generated names are not evidence of configured infrastructure.

# 194. AI LOG ANALYSIS

```text

job

relevant command

error

expected behavior

recent change

environment
```

Remove sensitive values first.

Then ask AI to:

```text
separate observations from hypotheses

rank checks by evidence value

avoid assuming root cause

identify commands requiring verification
```

# 195. DO NOT SEND SECRETS TO AI

Redact:

```text

private keys

registry credentials

cloud credentials

sensitive internal endpoints where required
```

before sharing logs.

# 196. COMPLETE FAILURE SCENARIO

Reported symptom:

```text
The new version did not reach staging.
```

Start with the pipeline.

---

# 197. PHASE 1: IDENTIFY RUN

Determine:

```text
commit SHA

pipeline ID

branch

trigger

timestamp
```

Do not investigate a different pipeline accidentally.

---

# 198. PHASE 2: IDENTIFY FAILED STAGE

Suppose:

```text
Validate
✓

Test
✓

Build
✓

Security
✓

Publish
✗

Deploy
not run

Verify
not run
```

Now the scope is clear.

---

# 199. PHASE 3: INSPECT PUBLISH JOB

Suppose the log shows registry authorization denied.

Ask:

```text
Did authentication occur?

Which registry?

Which repository?

Which identity?

Does identity have push permission?

Was credential changed?
```

---

# 200. PHASE 4: FORM HYPOTHESIS

Evidence:

```text
registry reachable

credential accepted

push operation denied

read operation succeeds
```

Hypothesis:

```text
The pipeline identity lacks repository write authorization.
```

---

# 201. PHASE 5: TEST

Inspect the configured registry permissions through the approved administrative path.

Confirm whether the identity has:

```text
read
```

but lacks:

```text
write
```

If confirmed, correct the permission according to least privilege.

---

# 202. PHASE 6: RERUN APPROPRIATELY

After correcting the permission:

```text
rerun affected workflow
```

according to the platform's safe process.

Verify:

```text
image published

digest recorded

deploy ran

verification passed
```

---

# 203. ROOT CAUSE STATEMENT

Weak:

```text
Registry issue.
```

Better:

```text
The pipeline successfully validated, tested, built, and scanned
the application image, but the publish job failed because the
pipeline registry identity had read permission without the write
permission required to push the new image. No staging deployment
occurred because the deployment job depended on successful image
publication.
```

This communicates cause and impact.

---

# 204. SECOND FAILURE SCENARIO

Reported:

```text
Pipeline is green but staging is broken.
```

This is a serious signal.

Ask:

```text
Did the pipeline contain deployment verification?
```

If not, the pipeline may have validated only:

```text
deployment command execution
```

rather than:

```text
application outcome
```

---

# 205. ADD MISSING VERIFICATION

The repair is not:

```text
make deployment command green again
```

The delivery process needs an explicit verification stage.

Example:

```text
Deploy
   ↓
Wait Within Defined Bounds
   ↓
Health Request
   ↓
Expected Response
   ↓
Pass / Fail
```

---

# 206. THIRD FAILURE SCENARIO

Reported:

```text
The wrong version is running in staging.
```

Investigate:

```text
expected commit

expected image tag

expected image digest

published image

deployment input

actual running container image
```

Do not assume the registry is wrong.

Trace identity end to end.

---

# 207. SOURCE-TO-RUNTIME TRACE

Use:

```text
Commit SHA
   ↓
Pipeline Run
   ↓
Built Image
   ↓
Registry Digest
   ↓
Deployment Input
   ↓
Running Container
```

At each arrow, verify identity.

This is delivery traceability.

---

# 208. FOURTH FAILURE SCENARIO

Reported:

```text
The pipeline works locally but fails in CI.
```

That phrase is imprecise because pipelines normally execute in CI.

What the engineer often means is:

```text
The same command works on my workstation
but fails on the CI runner.
```

Compare environments.

---

# 209. LOCAL VERSUS RUNNER COMPARISON

Check:

```text
operating system

architecture

runtime version

tool versions

PATH

environment variables

working directory

permissions

network access

filesystem

credentials
```

Do not immediately modify application code.

---

# 210. FIFTH FAILURE SCENARIO

Reported:

```text
Deployment sometimes passes when rerun.
```

Investigate possible transient factors:

```text
network

registry availability

dependency service

race condition

startup timing

resource contention

concurrent deployment
```

Do not automatically add retries.

---

# 211. STARTUP TIMING

A verification job may run before the application is ready.

A naive fix is:

```bash
sleep 60
```

This always waits 60 seconds regardless of whether the application becomes ready after 2 seconds or never becomes ready.

A better conceptual model is:

```text
Retry Health Check
     ↓
Bounded Attempts
     ↓
Bounded Delay
     ↓
Success or Meaningful Failure
```

---

# 212. BOUNDED VERIFICATION

A verification script should have:

```text
maximum attempts

delay

timeout

clear success condition

clear failure condition
```

It should not loop forever.

---

# 213. EXAMPLE VERIFICATION LOGIC

Conceptually:

```text
Attempt health check

If healthy:
    succeed

If not healthy:
    wait briefly
    retry

After maximum attempts:
    fail
```

The exact implementation should be reviewed using Part 7 shell-scripting standards.

---

# 214. PARTIAL EXECUTION

Pipelines can fail after making changes.

Example:

```text
Deployment Job

1. Stop old container
2. Pull new image
3. Start new container
```

Suppose step 2 fails.

Now:

```text
old container stopped

new container not started
```

This is partial execution.

---

# 215. DESIGN FOR PARTIAL FAILURE

Ask:

```text
What happens if failure occurs after each step?
```

For the simple lab, a safer order might involve:

```text
verify image exists

pull image successfully

then replace old container
```

where feasible.

The exact strategy depends on runtime design.

---

# 216. PIPELINE IDEMPOTENCY

Part 7 introduced idempotency.

It matters here.

A deployment job may be retried.

Ask:

```text
Can this job run again safely?

Will it create duplicates?

Will it fail because a resource already exists?

Will it destroy useful state?
```

CI/CD automation should consider repeat execution.

---

# 217. DEPLOYMENT STATE

Do not assume the environment begins clean.

It may contain:

```text
previous container

previous image

existing port binding

existing configuration

persistent volume

partially completed deployment
```

The deployment process should inspect expected state.

---

# 218. ROLLBACK LAB CONCEPT

After a successful staging deployment of:

```text
Version A
```

deploy deliberately broken:

```text
Version B
```

Verification should fail.

Then restore:

```text
Version A
```

using its known artifact reference.

Verify application recovery.

---

# 219. WHAT THE ROLLBACK LAB TEACHES

The learner should understand:

```text
previous artifact must be identifiable

artifact must still be available

deployment mechanism must support restoration

application state must remain compatible

verification must run again
```

Rollback is an engineering procedure, not a magic button.

---

# 220. ROLLBACK VERIFICATION

After rollback:

```text
Rollback Command Completed
```

is not enough.

Verify:

```text
expected previous artifact running

application healthy

expected endpoint responding

critical configuration intact
```

Before granting a pipeline deployment authority, ask:


# 222. CHANGE REVIEW FOR PIPELINES

A pipeline pull request should be reviewed for more than syntax.

Review:

```text
trigger changes

permission changes

secret access

new third-party dependencies

new deployment targets

new destructive commands

artifact changes

verification changes

failure handling
```

---

# 223. HIGH-RISK PIPELINE DIFF

Suppose a pull request changes:

```text
deploy: staging
```

to:

```text
deploy: production
```

The diff may be one line.

The blast radius is not one line.

Review risk based on behavior, not line count.

---

# 224. PIPELINE CHANGE ≠ APPLICATION CHANGE

An application change might affect:

```text
business logic
```

A pipeline change might affect:

```text
how every future application change reaches production
```

Both require appropriate review.

---

# 225. DO NOT DEBUG BY DISABLING SECURITY

Avoid:

```text
disable TLS verification

disable SSH host verification

use administrator token

make registry public

open firewall broadly

disable branch protection
```

simply to prove a pipeline can connect.

Fix the actual trust or permission problem.

---

# 226. DO NOT DEBUG BY EXPOSING SECRETS

Avoid:

```text
print all environment variables

echo tokens

upload credential files as artifacts

paste private keys into logs
```

Troubleshooting must preserve security.

---

# 227. DO NOT DEBUG BY MAKING EVERY FAILURE NON-BLOCKING

A common anti-pattern is:

```text
command || true
```

throughout the pipeline.

This can produce:

```text
Green Pipeline
+
Broken Delivery
```

Use non-blocking behavior only where failure is intentionally acceptable and documented.

---

# 228. REQUIRED VERSUS INFORMATIONAL CHECK

Some jobs may provide information without blocking delivery.

Others are required gates.

Make this distinction intentional.

Example:

```text
Required:
unit tests
```

```text
Potentially informational depending on policy:
certain advisory reports
```

The policy belongs to the engineering organization.

---

# 229. PIPELINE FAILURE MATRIX

| Symptom | Likely investigation area |
|---|---|
| Pipeline not created | trigger, configuration, permissions |
| Pipeline configuration rejected | YAML/platform syntax |
| Job queued indefinitely | runner availability, runner matching |
| `command not found` | runner image, dependency, PATH |
| Test job fails | test output, application change, environment |
| Build fails | Dockerfile, context, dependencies, builder |
| Scanner fails | scanner execution or policy result |
| Registry login fails | authentication |
| Registry push denied | authorization/repository policy |
| Artifact missing | upstream job, artifact publication, dependency |
| Deploy job cannot connect | network, identity, target availability |
| Deploy denied | authorization |
| Container fails to start | image, config, runtime, port, permissions |
| Verify job fails | application health, endpoint, network, dependency |
| Wrong version running | artifact identity/promotion |
| Pipeline passes but app broken | missing/inadequate verification |

# 230. COMMAND-TO-QUESTION MAPPING

Every command should answer a question.

Example:

```text
git rev-parse HEAD
→ Which commit am I building?
```

```text
docker image inspect ...
→ Which image metadata do I have?
```

```text
docker push ...
→ Can this identity publish this artifact?
```

```text
docker inspect ...
→ Which image/configuration is the container using?
```

```text
curl ...
→ Does the deployed application respond as expected?
```

Do not run commands without knowing what evidence they provide.

# 232. "IT DEPLOYED" MUST BECOME PRECISE

Instead of:

```text
It deployed.
```

say:

```text
Pipeline 184 deployed image digest X to the staging environment.
The deployment job completed successfully, and the staging
health endpoint returned the expected success response.
```

That statement contains evidence.

# 233. "THE PIPELINE FAILED" MUST BECOME PRECISE

Instead of:

```text
The pipeline failed.
```

say:

```text
The test stage failed in the unit-tests job. The application
test for invalid configuration expected HTTP 400 but received
HTTP 500. Build and deployment jobs did not run.
```

This is actionable.

# 257. FINAL VERIFICATION MODEL

At each delivery boundary, use:

```text
Action
   ↓
Expected State
   ↓
Inspection
   ↓
Evidence
   ↓
Conclusion
```

For example:

```text
Action:
Build container image

Expected State:
Image exists with expected commit-derived identity

Inspection:
Inspect build result and image metadata

Evidence:
Expected image reference exists

Conclusion:
Build succeeded
```

Then:

```text
Action:
Publish image

Expected State:
Exact image is available in registry

Inspection:
Registry/push evidence

Evidence:
Expected image reference and digest

Conclusion:
Publication succeeded
```

Then:

```text
Action:
Deploy image

Expected State:
Target environment runs exact artifact

Inspection:
Runtime state

Evidence:
Expected image identity

Conclusion:
Deployment mechanism succeeded
```

Then:

```text
Action:
Verify application

Expected State:
Health endpoint returns expected response

Inspection:
HTTP request

Evidence:
Expected HTTP result

Conclusion:
Basic application verification succeeded
```

This prevents one successful step from being mistaken for the entire delivery succeeding.

# 258. FINAL ENGINEERING PRINCIPLE

The purpose of CI/CD is not:

```text
make everything automatic
```

The purpose is to create a delivery process that is increasingly:

```text
repeatable

testable

observable

traceable

controlled

recoverable

secure
```

Automation should reduce uncontrolled variation.

It should not remove engineering judgment.
