# PART 10: CONTAINERS AND DOCKER FUNDAMENTALS

## Goal

Understand why containers exist, how images become running containers, and how to investigate common container failures.

By the end of this Part, the learner should not think of Docker as:

```text
docker build
docker run
docker ps
```

The learner should understand the system underneath those commands.

The central mental model is:

```text
Dockerfile
    ↓
Build
    ↓
Image
    ↓
Registry
    ↓
Pull
    ↓
Container
    ↓
Process
```

But this Part will go further:

```text
Source Code
    ↓
Dependencies
    ↓
Dockerfile
    ↓
Build Context
    ↓
Image Build
    ↓
Image Layers
    ↓
Image
    ↓
Tag / Digest
    ↓
Registry
    ↓
Pull
    ↓
Container Creation
    ↓
Runtime Configuration
    ├── Environment
    ├── Network
    ├── Ports
    └── Storage
    ↓
Container Start
    ↓
Main Process
    ↓
Application Listener
    ↓
Application Health
```

The most important principle is:

> A container is not the application, and a running container does not prove that the application inside it is healthy.

---

# 1. THE PROBLEM CONTAINERS HELP SOLVE

In Part 8, the learner ran an application manually.

That application required more than source code.

It required some combination of:

```text
source code

runtime

libraries

dependencies

configuration

filesystem content

startup command
```

Imagine a developer builds an application on one machine.

It works.

The application is copied to another server.

It fails.

Why?

Possible differences include:

```text
different runtime version

missing package

different library version

missing operating-system dependency

different filesystem layout

different environment variables

different startup command

different permissions
```

This creates the classic operational problem:

```text
"It works on my machine."
```

The important question is:

> What exactly was different between the two machines?

---

# 2. THE MANUAL DEPLOYMENT MODEL

Without a packaging abstraction, deployment might look like:

```text
Provision Server
      ↓
Install Operating System
      ↓
Install Runtime
      ↓
Install Packages
      ↓
Copy Application
      ↓
Create Directories
      ↓
Configure Environment
      ↓
Configure Service
      ↓
Start Application
```

This can work.

Organizations still operate applications this way.

Containers do not make traditional deployment invalid.

Containers solve a different problem:

> How can we package an application and much of its runtime environment into a repeatable artifact?

---

# 3. THE CONTAINER PACKAGING MODEL

Instead of separately configuring every application host with application-specific runtime content:

```text
Application
+
Runtime Requirements
+
Dependencies
+
Filesystem Content
+
Startup Definition
        ↓
Container Image
```

The image can then be distributed.

Conceptually:

```text
Build Once
    ↓
Image
    ↓
Registry
    ↓
Pull
    ↓
Run
```

This improves consistency.

It does not guarantee correctness.

---

# 4. WHAT A CONTAINER IS

A useful beginner definition is:

> A container is an isolated process environment created from an image and configured at runtime.

Do not define a container as:

```text
a lightweight virtual machine
```

That analogy can help initially, but it becomes misleading.

A container is fundamentally associated with processes.

---

# 5. CONTAINER VERSUS VIRTUAL MACHINE

A simplified VM model:

```text
Physical Host
    ↓
Hypervisor
    ├── VM A
    │    ├── Guest OS
    │    └── Application
    │
    └── VM B
         ├── Guest OS
         └── Application
```

A simplified container model on Linux:

```text
Host
 ↓
Host Kernel
 ↓
Container Runtime
 ├── Container A
 │    └── Process
 │
 └── Container B
      └── Process
```

Containers generally share the host kernel rather than each container booting its own complete guest kernel.

---

# 6. WHY THIS DIFFERENCE MATTERS

A virtual machine normally contains a guest operating system environment.

A container image normally packages application userspace content but relies on the host/runtime environment for kernel functionality.

Therefore:

```text
Container
≠
Miniature VM
```

This affects:

```text
startup behavior

isolation model

resource consumption

security model

debugging

filesystem behavior

process lifecycle
```

---

# 7. CONTAINERS STILL USE OPERATING-SYSTEM FUNDAMENTALS

Everything learned in Parts 3 and 4 still matters.

Inside a Linux container there are still concepts such as:

```text
processes

users

UIDs

GIDs

files

directories

permissions

environment variables

signals

exit codes

sockets
```

Containers do not replace Linux knowledge.

They make Linux knowledge more important.

---

# 8. CONTAINERS STILL USE NETWORKING FUNDAMENTALS

Part 5 remains relevant.

Containerized applications still depend on:

```text
IP addresses

ports

sockets

TCP

UDP

DNS

HTTP

TLS

routing
```

Docker adds networking abstractions around these fundamentals.

It does not replace them.

---

# 9. CONTAINERS STILL USE APPLICATION FUNDAMENTALS

Part 8 remains the application model:

```text
Source
 ↓
Dependencies
 ↓
Build
 ↓
Artifact
 ↓
Configuration
 ↓
Runtime
 ↓
Process
 ↓
Port
 ↓

```

Containers add another packaging and execution layer:

```text
Application Artifact
       ↓
Container Image
       ↓
Container
       ↓
Application Process
```

# 10. DOCKER

Docker provides tooling for building, distributing, and running container images.

At this level, the learner will work with:

```text
Dockerfile

Docker image

Docker Engine

Docker CLI

Docker registry

Docker container

Docker network

Docker volume
```

Do not treat these as one object called "Docker."

---

# 11. DOCKER CLI VERSUS DOCKER ENGINE

When you type:

```bash
docker ps
```

the CLI is not itself the container runtime environment.

Conceptually:

```text
Engineer
   ↓
Docker CLI
   ↓
Docker Engine
   ↓
Images / Containers / Networks / Volumes
```

This distinction matters when troubleshooting errors such as:

```text
Cannot connect to the Docker daemon
```

The CLI may be installed correctly while the engine is unavailable.

---

# 12. VERIFY DOCKER BEFORE THE LAB

Start with:

```bash
docker version
```

This can provide information about client and server components when the engine is reachable.

Also inspect:

```bash
docker info
```

The exact output depends on installation and platform.

The important question is:

```text
Can my Docker client communicate with the expected Docker Engine?
```

---

# 13. DO NOT BEGIN BY USING SUDO BLINDLY

If Docker access fails, do not automatically prepend:

```bash
sudo
```

to every command.

First determine why access failed.

Possible reasons include:

```text
Docker Engine not running

wrong Docker context

socket permissions

Docker Desktop not running

remote engine unavailable

installation incomplete
```

Also remember that access to the Docker daemon is highly privileged on typical Docker Engine installations.

Treat that access accordingly.

---

# 14. IMAGE

A container image is a packaged filesystem and metadata used to create containers.

It may include:

```text
runtime

libraries

application code

configuration defaults

filesystem content

startup metadata
```

An image is not a running process.

Mental model:

```text
Image
  ↓
Create Container
  ↓
Start
  ↓
Process
```

---

# 15. IMAGE VERSUS CONTAINER

This distinction is fundamental.

```text
Image
=
Reusable packaged artifact
```

```text
Container
=
Runtime instance created from an image
```

A useful analogy is:

```text
Application Binary
        ↓
Running Process
```

compared with:

```text
Container Image
        ↓
Running Container
```

The analogy is not exact, but it helps establish artifact versus runtime instance.

---

# 16. ONE IMAGE CAN CREATE MANY CONTAINERS

For example:

```text
Image: veriqta-app:1.0
          ↓
     ┌────┼────┐
     ↓    ↓    ↓
Container A  Container B  Container C
```

These containers begin from the same image content but have separate runtime state.

---

# 17. CONTAINER CHANGES DO NOT MODIFY THE ORIGINAL IMAGE

Suppose you start a container and create:

```text
/tmp/example.txt
```

inside it.

That does not rewrite the original image.

The running container has its own writable container layer above the image's read-only layers. Docker documents container-written data as residing in a writable container layer unless external storage is mounted.

Conceptually:

```text
Container Writable Layer
────────────────────────
Image Layer 4
Image Layer 3
Image Layer 2
Image Layer 1
```

---

# 18. IMAGE LAYERS

Docker images consist of layers.

Docker describes each image layer as filesystem changes applied relative to the previous layer. Once created, image layers are immutable.

Conceptually:

```text
Layer 5: Application Code
Layer 4: Application Dependencies
Layer 3: Runtime
Layer 2: OS/User-Space Files
Layer 1: Base Content
```

Together they form the image filesystem view.

---

# 19. WHY LAYERS MATTER

Layers can provide:

```text
reuse

build caching

efficient transfer

shared storage
```

If multiple images use the same unchanged layer, the layer may be reused rather than recreated or downloaded repeatedly.

This is one reason Dockerfile structure matters.

---

# 20. LAYERS ARE NOT SIMPLY "ONE COMMAND = ONE FILE"

Think in filesystem changes.

A layer can contain:

```text
added files

modified files

deleted-path metadata

installed packages

generated content
```

The resulting image presents a combined filesystem view.

---

# 21. IMAGE HISTORY


```bash
docker image history veriqta-app:1.0
```

This helps inspect build history and layer-producing instructions.

Do not assume the output reveals every implementation detail or secret safely.

Secrets should never be intentionally embedded in image build history or layers.

# 22. INSPECTING IMAGE METADATA

Use:

This returns structured image metadata.

Possible information includes:

```text

environment defaults

entrypoint

filesystem layer references
```

Exact fields can vary.

# 23. DOCKERFILE

A Dockerfile is a text file containing instructions used to build an image.

Docker's current Dockerfile reference includes instructions such as:

```text
FROM

RUN

COPY

WORKDIR

ENV

ARG

USER

EXPOSE

CMD

ENTRYPOINT
```

among others.

---

# 24. DOCKERFILE IS BUILD INPUT

A Dockerfile does not itself run your production application.

It describes how an image should be assembled and defines runtime metadata.

Mental model:

```text
Dockerfile
    ↓
docker build
    ↓
Image
```

Then:

```text
Image
    ↓
docker run
    ↓
Container
```

---

# 25. A SIMPLE DOCKERFILE

Suppose the Part 8 application is a small Python web application.

A simplified Dockerfile could look like:

```dockerfile
FROM python:3.13-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .

EXPOSE 8080

CMD ["python", "app.py"]
```

The exact base image and dependency versions should be verified for the project rather than copied blindly.

---

# 26. READ THE DOCKERFILE AS A SEQUENCE

Interpret it:

```text
FROM
↓
Choose starting image

WORKDIR
↓
Set working directory

COPY requirements.txt
↓
Copy dependency definition

RUN pip install
↓
Install dependencies during build

COPY app.py
↓
Add application code

EXPOSE
↓
Document intended application port

CMD
↓
Provide default startup command
```

This is much better than memorizing syntax.

---

# 27. FROM

Example:

```dockerfile
FROM python:3.13-slim
```

`FROM` establishes a base image for the build stage.

That base image becomes part of your software supply chain.

Ask:

```text
Who publishes it?

Which version?

Which architecture?

How frequently is it updated?

What software does it contain?

What vulnerabilities are known?
```

---

# 28. BASE IMAGE CHOICE

Do not choose a base image solely because:

```text
it is small
```

or:

```text
everyone uses it
```

Consider:

```text
required runtime

compatibility

maintenance

security updates

debuggability

package requirements

organizational policy
```

Smaller can be useful.

Smallest is not automatically best.

---

# 29. WORKDIR

Example:

```dockerfile
WORKDIR /app
```

This establishes the working directory for subsequent relevant Dockerfile instructions and the runtime defaults that depend on it.

This is preferable to scattering assumptions about current directories throughout the build.

---

# 30. COPY

Example:

```dockerfile
COPY app.py .
```

This copies content from the build context into the image.

Important:

```text
COPY source
```

must be accessible from the build context.

The Docker builder cannot arbitrarily copy any host file merely because the Dockerfile references it.

---

# 31. BUILD CONTEXT

The build context is the set of files the build can access.

For:

```bash
docker build -t veriqta-app:1.0 .
```

the final:

```text
.
```

means the current directory is supplied as the build context.

Docker's documentation defines build context as the files available to the build and notes that the positional argument to `docker build` specifies it.

---

# 32. BUILD CONTEXT IS NOT A DECORATIVE DOT

Beginners frequently memorize:

```bash
docker build -t app .
```

without knowing what `.` means.

It means:

```text
Use this directory as the build context.
```

That affects:

```text
which files COPY can access

which files may be transferred to the builder

cache behavior

build performance

accidental inclusion risk
```

---

# 33. KEEP BUILD CONTEXT INTENTIONAL

Do not build from a directory containing unnecessary:

```text
credentials

database dumps

SSH keys

large archives

temporary files

Git metadata

local environments

debug artifacts
```

Use an intentionally scoped context.

---

# 34. .dockerignore

A `.dockerignore` file can exclude paths from the build context sent to the builder.

Example:

```text
.git
.env
*.log
__pycache__/
.venv/
```

This can reduce unnecessary context and reduce accidental inclusion.

But:

> `.dockerignore` is not a secret-management system.

Do not place secrets in unsafe locations merely because you expect `.dockerignore` to protect them.

---

# 35. RUN

Example:

```dockerfile
RUN pip install --no-cache-dir -r requirements.txt
```

`RUN` executes a build-time command.

This occurs while creating the image.

It is different from:

```text
CMD
```

which defines runtime behavior.

---

# 36. BUILD TIME VERSUS RUN TIME

This distinction is essential.

```text
Build Time
──────────
FROM
COPY
RUN
...
      ↓
Image
```

Then:

```text
Run Time
────────
Image
 ↓
Container
 ↓
CMD / ENTRYPOINT
 ↓
Process
```

Do not confuse:

```text
RUN
```

with:

```text
docker run
```

They occur in different lifecycle phases.

---

# 37. ENV

A Dockerfile can define environment defaults:

```dockerfile
ENV APP_PORT=8080
```

But be careful.

Environment variables baked into image metadata may be visible through image inspection.

Do not use ordinary Dockerfile `ENV` instructions for secrets.

---

# 38. ARG

`ARG` defines build-time variables.

Do not assume:

```text
ARG
=
safe secret
```

Build arguments are not an appropriate general-purpose secret mechanism.

Build secret mechanisms exist for cases where a build needs sensitive material.

That belongs to more advanced image-building practice.

---

# 39. EXPOSE

Example:

```dockerfile
EXPOSE 8080
```

A critical distinction:

```text
EXPOSE
≠
Publish Port
```

Docker documents `EXPOSE` as metadata indicating the port the application intends to listen on. It does not publish that port to the host.

---

# 40. CMD

Example:

```dockerfile
CMD ["python", "app.py"]
```

This provides a default command for the container.

When the container starts, this ultimately participates in determining the container's main process.

---

# 41. ENTRYPOINT

`ENTRYPOINT` can define the executable that the container runs.

`CMD` and `ENTRYPOINT` can interact.

At Junior level, understand:

```text
ENTRYPOINT
→ establishes executable behavior

CMD
→ can provide default command or default arguments depending on configuration
```

Do not build complex entrypoint scripts until you understand process and signal behavior.

---

# 42. EXEC FORM

You will often see:

```dockerfile
CMD ["python", "app.py"]
```

rather than:

```dockerfile
CMD python app.py
```

The first is exec/JSON form.

For many application containers, exec form helps the intended executable become the direct container process without an unnecessary shell wrapper.

This matters for:

```text
signals

shutdown

process relationships
```

---

# 43. BUILD THE IMAGE

From the application directory:

```bash
docker build -t veriqta-app:1.0 .
```

Interpret:

```text
docker build
→ build an image

-t veriqta-app:1.0
→ assign name and tag

.
→ current directory is build context
```

---

# 44. BUILD SUCCESS DOES NOT PROVE APPLICATION SUCCESS

A successful image build proves that the image build completed.

It does not prove:

```text
container starts

application starts

port is correct

configuration exists

dependencies are reachable

health endpoint works
```

Use:

```text
Build Success
≠
Runtime Success
```


Inspect the specific image:

```bash
docker image inspect veriqta-app:1.0
```

Inspect history:

```bash
docker image history veriqta-app:1.0
```

Record:

```text
repository/name

tag

creation time

size

startup configuration
```

---

# 46. IMAGE NAME

A local image reference may look like:

```text
veriqta-app:1.0
```

A registry-qualified reference might look conceptually like:

```text
registry.example.com/team/veriqta-app:1.0
```

The exact naming rules depend on registry and tooling.

---

# 47. IMAGE TAG

A tag is a human-friendly reference associated with an image.

Examples:

```text
1.0

1.0.3

development

stable

latest
```

Tags help humans and automation refer to images.

But tags need careful reasoning.

---

# 48. `latest` DOES NOT MEAN "NEWEST BY MAGIC"

`latest` is a tag.

Do not interpret it as:

```text
Docker automatically finds whichever image was created most recently.
```

It is a tag name used according to image naming/tagging behavior.

Production workflows should not depend on vague assumptions about `latest`.

---

# 49. TAGS CAN MOVE

In ordinary mutable-tag workflows, the same tag can later be made to reference different image content.

Conceptually:

```text
Monday:

app:1.0
   ↓
Image A
```

Later, if the registry permits tag mutation:

```text
app:1.0
   ↓
Image B
```

Docker Hub now also supports configurable immutable-tag policies, which reinforces the important point: tag mutability is a registry/policy property, not the same concept as image content identity.

---

# 50. IMAGE DIGEST

An image digest is a content-addressable identifier.

It commonly looks like:

```text
sha256:<hash>
```

Docker documents pulling by digest as a way to pin the exact image content rather than relying on a mutable tag.

---

# 51. TAG VERSUS DIGEST

Think:

```text
Tag
→ Human-friendly reference
→ May be mutable depending on registry policy
```

```text
Digest
→ Content-addressed identity
→ Identifies specific content
```

This distinction becomes important for reproducibility and deployment control.

---

# 52. PINNING BY DIGEST

Conceptually:

```text
registry.example.com/team/app@sha256:...
```

identifies specific image content.

However, digest pinning introduces an operational responsibility:

> Updates do not appear automatically.

If a base image receives security updates, a pinned digest must be intentionally updated through the build and release process.

Docker explicitly notes this tradeoff.

---

# 53. REGISTRY

A container registry stores and distributes container images.

Mental model:

```text
Developer / CI
      ↓
Build Image
      ↓
Push
      ↓
Registry
      ↓
Pull
      ↓
Runtime Host
```

Examples include public and private registry services.

The concept matters more than a particular vendor.

---

# 54. REGISTRY IS NOT THE RUNNING CONTAINER

The registry stores distributable image artifacts.

The runtime host pulls image content and creates containers.

```text
Registry
=
Artifact Distribution
```

```text
Container Runtime
=
Execution
```

---

# 55. PUSHING AN IMAGE

A typical flow is:

```text
Local Image
    ↓
Correct Registry Name
    ↓
Authenticate
    ↓
Push
    ↓
Registry Stores Image
```

Docker's current getting-started documentation describes tagging as part of naming where an image will be distributed and pushing as publishing it to a registry.

---

# 56. REGISTRY AUTHENTICATION

Before pushing to a private or authenticated registry, authentication may be required.

For Docker-compatible registries, a command may involve:

```bash
docker login <registry>
```

Exact authentication mechanisms vary.

Prefer provider-supported secure credential mechanisms.

Do not paste long-lived registry passwords into:

```text
Dockerfiles

Git repositories

shell history

documentation

AI prompts
```

---

# 57. PULLING AN IMAGE

Example:

```bash
docker pull <image>:<tag>
```

This downloads required image content from a registry.

If layers already exist locally, Docker may reuse them.

---

# 58. PULL DOES NOT START A CONTAINER

Important:

```text
docker pull
→ obtains image
```

```text
docker run
→ creates/starts a container from an image
```

Do not confuse distribution with execution.

---

# 59. `docker run`

At a high level:

```bash
docker run <image>
```

means:

```text
Find image
    ↓
Pull if required by normal resolution behavior
    ↓
Create container
    ↓
Apply runtime configuration
    ↓
Start container
    ↓
Start main process
```

It combines multiple lifecycle steps.

---

# 60. CREATE VERSUS START VERSUS RUN

Conceptually:

```text
docker create
→ create container without starting it
```

```text
docker start
→ start existing container
```

```text
docker run
→ create + start
```

This distinction becomes useful when troubleshooting lifecycle state.

---

# 61. CONTAINER LIFECYCLE

A simplified lifecycle:

```text
Image
  ↓
Created
  ↓
Running
  ↓
Stopped / Exited
  ↓
Started Again
  ↓
Removed
```

A stopped container can still exist.

An exited container is not necessarily deleted.

---

# 62. LIST RUNNING CONTAINERS

Use:

```bash
docker ps
```

or the explicit form:

```bash
docker container ls
```

This normally shows running containers.

---

# 63. LIST ALL CONTAINERS

Use:

```bash
docker ps -a
```

or:

```bash
docker container ls -a
```

This is critical when troubleshooting:

```text
"My container disappeared."
```

It may simply have exited.

---

# 64. CONTAINER EXITS IMMEDIATELY

One of the most important beginner lessons:

> A container normally remains running while its main process remains running.

If the main process exits:

```text
Main Process Exits
       ↓
Container Stops
```

This is expected container lifecycle behavior.

---

# 65. CONTAINER IS NOT A BACKGROUND VM

A beginner may expect:

```text
Start container
    ↓
Container remains alive forever
```

That is incorrect.

If the configured process completes successfully after 0.2 seconds, the container may also stop after 0.2 seconds.

---

# 66. SIMPLE EXIT EXAMPLE

Run:

```bash
docker run --name veriqta-exit-example alpine:latest echo "hello"
```

The command prints:

```text
hello
```

and finishes.

Now inspect:

```bash
docker ps
```

The container is not running.

Inspect:

```bash
docker ps -a
```

You should see the exited container.

Nothing necessarily failed.

The process completed.

---

# 67. EXIT CODE

Inspect:

```bash
docker inspect veriqta-exit-example
```

Look at the container state information.

The process exit code provides evidence about how the main process terminated.

Recall Part 7:

```text
0
→ conventionally success
```

```text
non-zero
→ conventionally indicates some form of failure
```

Application-specific meanings still matter.

---

# 68. CONTAINER LOGS

Use:

```bash
docker logs <container>
```

Docker's default logging behavior commonly captures the container process's standard output and standard error for retrieval through `docker logs`, subject to logging configuration.

This connects directly to Part 7:

```text
STDOUT

STDERR
```

---

# 69. LOGS ARE ONE OF THE FIRST CHECKS FOR EXITED CONTAINERS

Workflow:

```text
Container Exited
      ↓
docker ps -a
      ↓
Inspect State
      ↓
Inspect Exit Code
      ↓
docker logs
      ↓
Inspect Startup Configuration
      ↓
Identify Cause
```

Do not immediately rebuild the image.

---

# 70. FOLLOW LOGS

For a running container:

```bash
docker logs -f <container>
```

This follows log output.

Stop following with your terminal interrupt when appropriate.

Following logs does not stop the container.

---

# 71. TIMESTAMPS

Where useful:

```bash
docker logs --timestamps <container>
```

Timestamps help correlate:

```text
container startup

application errors

dependency failures

operator changes
```

---

# 72. CONTAINER NAME

Use meaningful names in labs:

```bash
docker run --name veriqta-app ...
```

This makes commands easier to understand than relying entirely on generated container names or IDs.

Names are identifiers.

They do not change application behavior by themselves.

---

# 73. DETACHED MODE

Run in background:

```bash
docker run -d --name veriqta-app ...
```

`-d` means detached mode.

The container continues running without attaching the current terminal to its main process output.

Inspect it separately with:

```bash
docker logs
```

and:

```bash
docker ps
```

---

# 74. PORTS INSIDE CONTAINERS

Suppose the application inside the container listens on:

```text
8080
```

That is the container-side application port.

It does not automatically mean:

```text
Host port 8080 is reachable.
```

---

# 75. PORT PUBLISHING

Example:

```bash
docker run -d \
  --name veriqta-app \
  -p 127.0.0.1:8080:8080 \
  veriqta-app:1.0
```

Interpret:

```text
Host 127.0.0.1:8080
        ↓
Published Mapping
        ↓
Container Port 8080
```

Docker documents the general syntax as host port to container port.

---

# 76. HOST PORT AND CONTAINER PORT DO NOT NEED TO MATCH

Example:

```bash
docker run -d \
  --name veriqta-app \
  -p 127.0.0.1:9000:8080 \
  veriqta-app:1.0
```

Now:

```text
Client
 ↓
Host 127.0.0.1:9000
 ↓
Container :8080
 ↓
Application
```

The application still listens on 8080 inside the container.

---

# 77. WHY BIND TO 127.0.0.1 IN THE LAB

Docker documentation warns that publishing a port without a host IP normally publishes it on host interfaces broadly according to Docker's networking behavior. Binding explicitly to:

```text
127.0.0.1
```

limits this simple local lab to the local host.

This is preferable when external access is unnecessary.

---

# 78. `EXPOSE` VERSUS `-p`

Memorize the distinction conceptually:

```text
EXPOSE 8080
→ image metadata/documentation
```

```text
-p 8080:8080
→ runtime port publication
```

`EXPOSE` does not create the host mapping.

---

# 79. INSPECT PORT MAPPINGS

Use:

```bash
docker port veriqta-app
```

Also:

```bash
docker ps
```

Inspect the `PORTS` column.

Then verify from the host:

```bash
curl -i http://127.0.0.1:8080/health
```

---

# 80. PUBLISHED PORT DOES NOT PROVE APPLICATION HEALTH

Possible state:

```text
Docker Port Mapping Exists
          ↓
Container Running
          ↓
Application Not Listening
```

The request still fails.

Therefore:

```text
Port Published
≠
Application Listening
≠
Application Healthy
```

---

# 81. APPLICATION BIND ADDRESS INSIDE THE CONTAINER

Suppose the application inside the container binds only to:

```text
127.0.0.1:8080
```

That loopback address is inside the container's network namespace.

Publishing the container port does not automatically fix an application that is listening only on container-local loopback when external container-interface traffic is expected.

For a simple containerized web application intended to receive container-network traffic, it commonly needs to bind appropriately, often:

```text
0.0.0.0:8080
```

for IPv4.

---

# 82. NETWORK NAMESPACE MENTAL MODEL

Conceptually:

```text
Host Network
    ↓
Docker Networking
    ↓
Container Network Namespace
    ↓
Container Interface
    ↓
Application Socket
```

The container has its own network view.

Do not assume:

```text
localhost on host
=
localhost inside container
```

They refer to different network namespaces in the normal isolated container model.

---

# 83. `localhost` IS CONTEXTUAL

From the host:

```text
127.0.0.1
```

means the host loopback interface.

From inside a normal isolated container:

```text
127.0.0.1
```

means that container's loopback interface.

This is a frequent source of configuration errors.

# 84. CONTAINER NETWORKS


A standard Docker Engine installation commonly includes built-in networks such as:

```text

host

none
```

Exact availability and behavior can depend on platform.

For this Part, focus primarily on bridge networking and user-defined bridge networks.

---

# 85. DEFAULT BRIDGE

Containers started without an explicit network commonly use Docker's default bridge network on a typical Docker Engine setup.

This is useful for basic learning.

But user-defined networks provide important capabilities and clearer isolation.

Inspect:


Docker documents user-defined bridge networks as providing automatic DNS resolution between containers by name or alias, along with better isolation than placing unrelated containers on the default bridge.

# 87. RUN A CONTAINER ON THE NETWORK

Example:

```bash
  --name veriqta-app \
  --network veriqta-net \
```

Now the container is attached to:

```text
veriqta-net
```

# 88. CONTAINER-TO-CONTAINER COMMUNICATION

Suppose later you have:

```text
web
```

and:

```text
database
```

on the same user-defined network.

Conceptually:

```text
Web Container
     ↓
Docker Network
     ↓
Database Container
```

On an appropriate user-defined bridge, Docker provides container-name/alias DNS resolution.

---

# 89. DO NOT HARDCODE CONTAINER IP ADDRESSES

Container IP addresses can change as containers are recreated.

Prefer appropriate service discovery mechanisms such as names on user-defined networks rather than treating dynamically allocated container IPs as permanent configuration.

---

# 90. ENVIRONMENT VARIABLES

Runtime configuration can be passed to a container.

Example:

```bash
docker run -d \
  --name veriqta-app \
  -e APP_ENV=development \
  -e APP_PORT=8080 \
  -p 127.0.0.1:8080:8080 \
  veriqta-app:1.0
```

This separates some runtime configuration from image content.

---

# 91. IMAGE VERSUS RUNTIME CONFIGURATION

Aim for the conceptual separation:

```text
Image
→ packaged application
```

```text
Runtime Configuration
→ environment-specific settings
```

This allows the same image content to run with appropriate configuration in different environments.

---

# 92. DO NOT BAKE ENVIRONMENT-SPECIFIC SECRETS INTO THE IMAGE

Bad pattern:

```dockerfile
ENV DATABASE_PASSWORD=super-secret-password
```

That secret may become visible through image metadata or distribution.

Do not treat images as secret vaults.

---

# 93. ENVIRONMENT VARIABLES ARE NOT AUTOMATICALLY SECRET

Even runtime environment variables can be observable through:

```text
container inspection

process environment access

debugging tools

logs if application prints them
```

Use appropriate secret-management mechanisms in real environments.

For this Junior Part, the key rule is:

> Configuration and secrets are related concepts, but not all configuration channels are secure secret-storage mechanisms.

---

# 94. INSPECT RUNTIME ENVIRONMENT

For a lab container:

```bash
docker exec veriqta-app env
```

This executes `env` inside the running container if the image contains that command.

Minimal images may not contain familiar debugging utilities.

That absence is not proof the container is broken.

---

# 95. `docker exec`

`docker exec` starts an additional process inside a running container.

Example:

```bash
docker exec veriqta-app env
```

or, if the image contains a shell:

```bash
docker exec -it veriqta-app sh
```

Important:

```text
docker exec
≠
SSH
```

You are asking Docker to start another process in the container.

---

# 96. DO NOT REQUIRE SSH INSIDE NORMAL APPLICATION CONTAINERS

A typical application container does not need an SSH daemon merely so engineers can inspect it.

Use container runtime tooling and observability appropriate to the environment.

Installing SSH inside every container adds unnecessary software and operational complexity.

---

# 97. CONTAINER FILESYSTEM

A running container receives a writable layer above image layers.

Conceptually:

```text
Writable Container Layer
────────────────────────
Read-Only Image Layers
```

If you write:

```text
/app/runtime-data.txt
```

without a mount, that data belongs to the container's writable layer.

---

# 98. CONTAINER REMOVAL AND DATA

Docker documents data in the writable container layer as tied to that container; removing the container removes that writable-layer state.

Therefore:

```text
Write Important Data Into Container Writable Layer
                    ↓
Remove Container
                    ↓
Data May Be Lost
```

Persistent application data requires an intentional storage strategy.

---

# 99. VOLUMES

Docker volumes are persistent data stores managed by Docker.

Docker documents volumes as persisting independently of the lifecycle of the containers that use them.

Conceptually:

```text
Docker Volume
      ↓
Mounted Into Container
      ↓
Application Reads/Writes
```

---

# 100. CREATE A VOLUME

Example:

```bash

```

List:

```bash
docker volume ls
```

Inspect:

```bash
docker volume inspect veriqta-data
```

# 101. MOUNT THE VOLUME

Example:

```bash
docker run -d \
  --name veriqta-app \
  --mount source=veriqta-data,target=/app/data \
  -p 127.0.0.1:8080:8080 \
```

Interpret:

```text
Docker-managed volume:
veriqta-data

Mounted inside container at:

```

# 102. VERIFY VOLUME PERSISTENCE

Write test data through the application or a controlled command.

Remove the container:

```bash

```

This demonstrates:

```text

≠
Volume Lifecycle
```

---

# 103. VOLUME DOES NOT MEAN BACKUP

A persistent Docker volume is not automatically:

```text
backed up

replicated

encrypted according to your requirements

recoverable after host loss
```

Persistence and backup are separate concerns.

---

# 104. BIND MOUNTS

A bind mount maps a host path into the container.

Example:

```bash
docker run --rm \
  --mount type=bind,src="$PWD",dst=/workspace \
  alpine:latest \
  ls -la /workspace
```

Docker distinguishes bind mounts from volumes: bind mounts directly expose a host path, while volumes are managed by Docker.

---

# 105. VOLUME VERSUS BIND MOUNT

Think:

```text
Volume
→ Docker-managed storage
```

```text
Bind Mount
→ Specific host path mapped into container
```

Both can be useful.

They have different operational characteristics.

---

# 106. BIND MOUNT RISK

A writable bind mount gives the container access to modify the mounted host path according to permissions and security controls.

Therefore do not casually mount:

```text
/

$HOME

/etc

sensitive credential directories
```

into application containers.

---

# 107. READ-ONLY MOUNTS

When a container only needs to read host content, use a read-only mount where appropriate.

Example:

```bash
docker run --rm \
  --mount type=bind,src="$PWD/config",dst=/app/config,readonly \
  veriqta-app:1.0
```

Least privilege applies to filesystems too.

---

# 108. VOLUME PERMISSIONS

A mounted volume can exist correctly while the application still cannot write to it.

Why?

Possible mismatch:

```text
Container Process UID/GID
          ↓
Mounted Directory Ownership/Permissions
          ↓
Write Denied
```

This connects directly to Part 3 Linux permissions.

---

# 109. CONTAINER USERS

A process inside a container runs as some user identity.

Inspect where tools permit:

```bash
docker exec veriqta-app id
```

Do not assume:

```text
containerized
=
permissionless
```

Linux user and permission concepts still apply.

---

# 110. RUNNING AS ROOT

Many images historically run processes as root by default unless configured otherwise.

For production-oriented images, prefer a non-root application user where practical and supported.

Docker Scout includes a policy specifically checking for a default non-root user, and Docker recommends the `USER` instruction for that configuration.

---

# 111. BASIC NON-ROOT DOCKERFILE PATTERN

The exact implementation depends on the base image.

Conceptually:

```dockerfile

COPY <files> .

RUN <create-user-and-set-required-ownership>

USER <application-user>

CMD ["<application>"]
```

Do not copy user-creation commands blindly between Linux distributions.

Utilities and defaults differ.

# 112. BASIC IMAGE SECURITY MODEL

At Junior level, image security includes:

# 118. CONTAINER STARTUP

Conceptually:

```text
  ↓

  ↓

    ↓
```

```text
    ↓

    ↓

    ↓
```

# 120. SIGNALS AND CONTAINER SHUTDOWN

```text

```

and process shutdown.

When a container is stopped, the runtime attempts to stop its process according to container runtime behavior and configured stop settings.


```bash

```

# 122. GRACEFUL APPLICATION SHUTDOWN

```text

finish active requests

flush buffers

close connections

release resources
```

Containerization does not remove shutdown engineering.

# 123. CONTAINER RESTART

```text
Restart
≠
Root Cause
```

# 125. `--rm`

# 171. ROOT CAUSE IS NOT "DOCKER PERMISSIONS"

A precise root cause might be:

```text
The application runs as UID 10001, while the mounted directory
is owned by another UID and is not writable by the application's
user or group. The application therefore receives permission
denied when attempting to create its data file.
```

That is much better than:

```text
Docker permission problem.
```

---

# 172. DO NOT SOLVE EVERY PERMISSION PROBLEM WITH ROOT

Running the application as root may make the immediate permission error disappear.

It can also increase privilege unnecessarily.

Correct:

```text
ownership

UID/GID expectations

mount configuration

application permissions
```

instead.

# 192. CONTAINER TROUBLESHOOTING MATRIX

| Symptom | First useful checks |
|---|---|
| Docker command cannot connect | Docker Engine, context, permissions |
| Container missing from `docker ps` | `docker ps -a` |
| Container exits immediately | state, exit code, logs, startup command |
| Image not found | repository, tag, registry, authentication |
| Port cannot publish | host port ownership, existing containers |
| Container runs but HTTP fails | listener, bind address, mapping, logs |
| Configuration missing | runtime environment, config mount |
| Volume write fails | user, UID/GID, ownership, permissions, mount mode |
| Container cannot reach peer | network attachment, name resolution, target port |
| Push fails | registry name, authentication, authorization, repository |
| Pull gets unexpected content | tag, digest, registry |
| Data disappeared | container writable layer vs volume/mount |

# 193. SYMPTOM IS NOT ROOT CAUSE

Symptom:




```text

```


```text
application bound to loopback inside container
```

# 248. OFFICIAL REFERENCE PRINCIPLE

Container behavior, Docker CLI options, Dockerfile features, registry capabilities, and security tooling evolve.

Use current official Docker documentation when exact behavior matters.

Current Docker documentation confirms the core concepts used throughout this Part:

- Dockerfiles define image builds, and images consist of immutable filesystem layers.
- The build context defines the files accessible to a build.
- `EXPOSE` documents intended ports but does not publish them.
- Port publishing maps host ports to container ports, and publishing without a specific host address can expose the port on host interfaces more broadly.
- Docker volumes persist independently of a container's lifecycle, while bind mounts map host paths directly into containers.
- User-defined bridge networks provide container name/alias resolution and scoped container networking.
- Tags and digests serve different purposes; digest references can pin exact image content.
- Docker Scout can analyze image contents and report known vulnerabilities and software inventory information.

The repository standard remains:

```text
Learn the concept.

Understand the mechanism.

Run the lab.

Observe the evidence.

Break it deliberately.

Troubleshoot it.

Repair it.

Verify the repair.

Then automate it later.
```
