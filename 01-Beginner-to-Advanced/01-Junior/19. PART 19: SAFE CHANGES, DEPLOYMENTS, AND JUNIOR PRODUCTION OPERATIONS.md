# PART 19: SAFE CHANGES, DEPLOYMENTS, AND JUNIOR PRODUCTION OPERATIONS

## Goal

Learn how routine production work should be performed safely, deliberately, visibly, and reversibly without treating production as a personal laboratory.

A Junior DevOps engineer may eventually receive access to systems that affect real users, real workloads, real infrastructure, real data, and real business operations.

Technical ability alone does not make someone safe around production.

An engineer may know how to:

- edit configuration
- merge code
- run a pipeline
- restart a service
- modify Terraform
- deploy a container
- change a Kubernetes Deployment
- rotate a credential
- update a package
- modify a firewall rule

and still be unsafe if those actions are performed without understanding:

- why the change is required
- who requested it
- what is being changed
- what could be affected
- what evidence exists before the change
- whether the change has been reviewed
- whether approval is required
- how the change will be verified
- how the system will be recovered if the change fails
- who must be informed
- what must be documented afterward

Production engineering requires both technical execution and operational discipline.

The central mental model for this Part is:

```text
Requested Change
      ↓
Understand
      ↓
Review
      ↓
Plan
      ↓
Assess Risk
      ↓
Approve
      ↓
Execute
      ↓
Verify
      ↓
Observe
      ↓
Document
```

The safe-change principle is:

```text
Know the Current State
        ↓
Define the Desired Change
        ↓
Understand the Risk
        ↓
Prepare Verification
        ↓
Prepare Recovery
        ↓
Make the Smallest Controlled Change
        ↓
Observe the Result
        ↓
Prove the Expected State
```

The most important distinction in this Part is:

```text
Deployment Completed
        ≠
Application Healthy
        ≠
Users Successful
```

A pipeline can be green while the deployed service is broken.

A container can be running while the application is unhealthy.

A Kubernetes Deployment can complete while the application returns errors.

A Terraform apply can succeed while the resulting architecture does not satisfy the intended requirement.

A configuration-management run can report success while application-level behavior remains incorrect.

Production verification must therefore extend beyond the mechanism that performed the change.

---

# 1. PRODUCTION IS NOT A PERSONAL LABORATORY

Laboratories exist so engineers can experiment.

Production exists to provide a service.

The operating assumptions are different.

In a disposable lab, an engineer may intentionally:

- break configuration
- stop services
- delete containers
- destroy infrastructure
- test unverified commands
- try different permissions
- create deliberate failures

because failure is part of the exercise.

In production, every change must be treated as a controlled intervention into a system that may have users, dependencies, data, security requirements, availability objectives, and organizational owners.

The question is not merely:

> Can I make this change?

The production questions are:

> Should this change be made?

> Am I authorized to make it?

> Has it been reviewed?

> What could it affect?

> How will we know whether it worked?

> What happens if it does not?

---

# 2. PRODUCTION ACCESS IS NOT PRODUCTION AUTHORITY

Having technical permission to perform an action does not automatically mean the engineer has organizational authority to perform it.

An account may technically allow:

```text
kubectl apply
```

That does not mean every manifest should be applied.

An account may allow:

```text
terraform apply
```

That does not mean infrastructure should be changed without review.

An account may allow a pipeline to be started.

That does not mean an unapproved release should be deployed.

Always distinguish:

```text
Technical Capability
```

from:

```text
Operational Authorization
```

---

# 3. THE JUNIOR ENGINEER'S PRODUCTION ROLE

At this level, the learner should be capable of participating safely in established production processes.

Typical responsibilities may include:

- preparing a small change
- gathering pre-change evidence
- following an approved runbook
- opening a pull request
- responding to review comments
- running approved validation
- observing CI/CD
- deploying to non-production
- performing documented verification
- assisting with an approved production deployment
- monitoring expected signals
- collecting post-change evidence
- documenting results
- escalating unexpected behavior

The learner is not expected to independently redesign organizational production processes or approve high-risk architectural changes.

---

# 4. THE CHANGE LIFECYCLE

A controlled change can be represented as:

```text
Request
   ↓
Clarify
   ↓
Prepare
   ↓
Review
   ↓
Validate
   ↓
Risk Assessment
   ↓
Approval
   ↓
Execution
   ↓
Technical Verification
   ↓
Service Verification
   ↓
Observation
   ↓
Documentation
   ↓
Closure / Handover
```

Different organizations use different terminology and tooling.

The engineering principles remain similar.

---

# 5. CHANGE REQUESTS

A change should begin with an identifiable reason.

Examples include:

- bug fix
- security update
- configuration correction
- dependency update
- application release
- certificate renewal
- capacity adjustment
- infrastructure modification
- monitoring improvement
- operational maintenance

A useful change request answers:

```text
What needs to change?

Why?

Where?

Who or what is affected?

What is the desired result?

When should it happen?

How will success be verified?
```

---

# 6. TICKETS

Organizations may use tickets to record work.

A ticket can provide:

- problem statement
- requested outcome
- owner
- priority
- affected environment
- related incidents
- implementation notes
- approval information
- evidence
- final outcome

A ticket is not merely bureaucracy.

Used properly, it establishes context and traceability.

---

# 7. A TICKET DOES NOT AUTOMATICALLY MAKE A CHANGE SAFE

This:

```text
Ticket exists
```

does not prove:

```text
Change is understood
Change is correct
Change is approved
Change is low risk
Rollback is possible
```

The ticket is one part of the control process.

---

# 8. WEAK CHANGE REQUEST

Example:

```text
Update production.
```

This is insufficient.

It does not explain:

- what
- why
- where
- risk
- verification
- recovery

---

# 9. BETTER CHANGE REQUEST

```text
Change:
Update checkout application from release A to release B.

Reason:
Release B corrects incorrect timeout handling observed in staging.

Environment:
Production checkout service.

Expected Result:
Checkout requests continue successfully and timeout-related errors decrease.

Validation:
Release B passed automated tests and staging verification.

Verification:
Confirm healthy workload replicas, successful health checks,
successful checkout test, normal error rate, and normal latency.

Recovery:
Restore release A if defined rollback criteria are reached.
```

The exact content depends on the organization.

---

# 10. UNDERSTAND BEFORE CHANGING

Before touching the system, the engineer should be able to explain:

```text
Current State

Desired State

Difference

Reason

Affected Components

Expected Result
```

If the change cannot be explained, execution should stop until the change is understood.

---

# 11. CURRENT STATE

Capture enough current-state evidence to understand what exists before the change.

Depending on the system:

```text
application version

container image

replica count

configuration version

infrastructure plan

service health

resource utilization

error rate

latency

dependency health
```

This creates a baseline.

---

# 12. DESIRED STATE

Define the intended post-change condition.

Example:

```text
Current image:
application:1.4.2

Desired image:
application:1.4.3
```

But desired state should include behavior too:

```text
3 replicas Ready

health endpoint successful

critical request successful

error rate within expected range
```

---

# 13. CHANGE SCOPE

Determine exactly what is being changed.

Ask:

```text
One file?

One service?

One Deployment?

One namespace?

One host?

One environment?

One database?

One network rule?

Multiple regions?
```

Smaller understood scope is generally easier to reason about and recover.

---

# 14. AVOID UNRELATED CHANGES

Suppose the task is:

```text
Change application timeout from 10 seconds to 15 seconds.
```

Do not casually include:

- dependency upgrades
- unrelated refactoring
- logging changes
- formatting changes across dozens of files
- infrastructure redesign

Unrelated changes increase uncertainty.

---

# 15. ONE CHANGE SHOULD HAVE A CLEAR PURPOSE

A reviewer should be able to answer:

> Why does this change exist?

without reconstructing the engineer's thought process.

---

# 16. VERSION CONTROL

Where configuration, infrastructure, or application code is version-controlled, production changes should normally flow through the organization's established version-control process.

Benefits include:

- history
- review
- comparison
- attribution
- rollback reference
- auditability
- collaboration

---

# 17. CREATE A BRANCH

For the lab:

```bash
git switch -c change/application-message
```

Use the branching convention required by the repository.

The branch isolates the proposed change from the main integration branch.

---

# 18. CONFIRM THE BRANCH

Check:

```bash
git status
```

and, with a Git version that supports it:

```bash
git branch --show-current
```

Expected result:

The intended working branch is active.

Never assume branch context before committing or pushing.

---

# 19. MAKE THE SMALLEST REQUIRED CHANGE

Edit only what the approved change requires.

Then inspect:

```bash
git diff
```

Do not commit before reviewing your own diff.

---

# 20. SELF-REVIEW

Before asking another engineer to review the change, inspect it yourself.

Ask:

```text
Did I change only what I intended?

Did I accidentally modify another file?

Did I add credentials?

Did I add debug configuration?

Did I change permissions?

Did I introduce environment-specific assumptions?

Did I leave temporary code?
```

---

# 21. SECRET CHECK

Before committing:

```text
Look for:

API keys
tokens
passwords
private keys
connection strings
sensitive environment files
```

Never assume:

> I can delete it later.

Once sensitive material has entered Git history or another shared system, additional remediation may be required.

---

# 22. LOCAL VALIDATION

Run the appropriate local validation.

Depending on the project this may include:

```text
syntax check

formatter

linter

unit tests

configuration validation

container build

application startup

health request
```

The validation should match the change.

---

# 23. LOCAL SUCCESS IS NOT PRODUCTION SUCCESS

Local testing proves only what was actually tested locally.

Differences may exist in:

- operating system
- runtime
- dependencies
- secrets
- network
- permissions
- resource limits
- cloud services
- Kubernetes configuration

Therefore:

```text
Works Locally
      ≠
Guaranteed Production Success
```

---

# 24. COMMIT

After validation:

```bash
git add <intended-files>
```

Inspect staged content:

```bash
git diff --staged
```

Then commit with a meaningful message.

Example:

```bash
git commit -m "Adjust application timeout configuration"
```

---

# 25. COMMIT MESSAGES

A useful commit message should make the purpose understandable.

Weak:

```text
changes
```

Better:

```text
Adjust checkout timeout configuration
```

---

# 26. PUSH

Push the branch according to repository workflow.

Example:

```bash
git push -u origin change/application-message
```

Then create a pull request.

---

# 27. PULL REQUESTS

A pull request provides a review boundary between:

```text
Proposed Change
```

and:

```text
Accepted Change
```

It allows reviewers to inspect:

- code
- configuration
- tests
- risk
- security
- infrastructure impact
- operational consequences

---

# 28. A PULL REQUEST IS MORE THAN A MERGE BUTTON

A good pull request explains:

```text
What changed?

Why?

How was it tested?

What systems are affected?

What risk exists?

How will it be verified?

How can it be recovered?
```

---

# 29. EXAMPLE PULL REQUEST DESCRIPTION

```text
Change

Update application response configuration for the controlled
production-change lab.

Reason

Validate the full branch → review → CI → staging → production
change workflow.

Testing

Local application test completed.
Container build completed.
Automated CI checks passed.

Infrastructure Impact

No infrastructure resources are expected to change.

Deployment

Deploy to non-production first.
Verify application health and expected response.
Production deployment requires simulated approval.

Verification

Confirm:
- workload is running
- health endpoint succeeds
- expected response is returned
- logs contain no new startup errors
- error and latency signals remain healthy

Rollback

Redeploy the previously verified application version.
```

---

# 30. PEER REVIEW

Peer review introduces another engineer into the decision process.

The reviewer should not merely check:

```text
Does the syntax look correct?
```

The reviewer should consider:

```text
Does the change solve the intended problem?

Is the scope appropriate?

Are assumptions valid?

Is it safe?

Is verification adequate?

Is rollback realistic?

Are secrets protected?

Could another system be affected?
```

---

# 31. REVIEW IS NOT PERSONAL

Review comments are about the change.

The purpose is to improve:

- correctness
- safety
- maintainability
- clarity
- operational reliability

A Junior engineer should learn to respond to review with evidence rather than defensiveness.

---

# 32. REVIEW COMMENTS

When a reviewer asks:

> How do we know this won't change infrastructure?

A useful response is:

```text
The change modifies only the application configuration file.
The infrastructure plan reports no infrastructure changes.
```

Evidence is stronger than reassurance.

---

# 33. APPROVAL

Some changes require explicit approval before execution.

Approval requirements depend on:

- organization
- environment
- risk
- compliance requirements
- system criticality
- change type

Never invent your own approval process.

Follow the organization's process.

---

# 34. APPROVAL IS A CONTROL

Approval asks:

```text
Has an authorized person reviewed the planned change
and accepted that it should proceed?
```

Approval does not guarantee success.

---

# 35. APPROVED DOES NOT MEAN RISK-FREE

Even reviewed changes can fail.

Therefore approval does not replace:

- validation
- rollback planning
- monitoring
- verification

---

# 36. MAINTENANCE WINDOWS

Some changes are performed during defined maintenance windows.

Reasons can include:

- reduced traffic
- coordinated support availability
- expected service interruption
- database maintenance
- infrastructure maintenance
- contractual requirements

---

# 37. MAINTENANCE WINDOW DOES NOT MEAN "BREAK ANYTHING"

A maintenance window provides an agreed time for change.

It does not remove the need for:

```text
planning

verification

communication

rollback

security
```

---

# 38. PRE-CHANGE CHECKS

Immediately before execution, confirm the assumptions used when planning the change are still true.

A useful pre-change model is:

```text
Correct Environment

Correct Identity

Correct Version

Healthy Starting State

Approved Change

Recovery Ready

Monitoring Available
```

---

# 39. VERIFY ENVIRONMENT

Before running a production command, identify the environment explicitly.

Do not rely on terminal color, window position, or memory.

Verify context using the appropriate tool.

---

# 40. VERIFY IDENTITY

Determine:

```text
Which account am I using?

Which role?

Which permissions?

Which cloud account/project/subscription?

Which cluster?

Which namespace?
```

Wrong-context changes are a serious operational risk.

---

# 41. VERIFY VERSION

Before deployment record:

```text
Current version

Target version
```

Do not deploy an ambiguous artifact such as:

```text
whatever was built most recently
```

when the deployment process supports immutable identification.

---

# 42. VERIFY STARTING HEALTH

A change should not begin under the false assumption that the system is healthy.

Check relevant signals.

Example:

```text
Expected replicas available

health endpoint successful

error rate normal

latency normal

dependencies healthy
```

If the system is already degraded, stop and reassess unless the change is specifically intended to correct that degradation.

---

# 43. WHY STARTING HEALTH MATTERS

Suppose latency is already high before deployment.

After deployment latency remains high.

Without a pre-change baseline, the team may incorrectly attribute the condition to the deployment.

---

# 44. PRE-CHANGE EVIDENCE

Record:

```text
timestamp

version

health

replica state

critical metrics

known alerts

relevant dependencies
```

The exact evidence depends on the service.

---

# 45. BACKUPS

Some changes require backup or recovery preparation.

Examples:

- database modification
- persistent storage operation
- configuration replacement
- stateful application change

But:

```text
Backup Exists
```

does not automatically mean:

```text
Recovery Is Possible
```

---

# 46. BACKUP VERIFICATION

Where backup is relevant, ask:

```text
Was it completed?

Is it recent enough?

Is it the correct system?

Is it accessible?

Is restore understood?

Has restore been tested according to organizational requirements?
```

A backup that cannot be restored does not provide the expected recovery capability.

---

# 47. NOT EVERY DEPLOYMENT REQUIRES A NEW BACKUP

Backup requirements depend on the change.

A stateless application image update may have very different recovery requirements from a destructive database migration.

Use the organization's procedure and the actual risk.

---

# 48. DEPLOYMENT PLAN

A deployment plan explains how the change will be executed.

It should be specific enough that another authorized engineer can understand:

```text
what will happen

in what order

against which environment

using which artifact

with what verification
```

---

# 49. EXAMPLE DEPLOYMENT PLAN

```text
1. Confirm production currently runs release A.

2. Confirm application health and baseline metrics.

3. Confirm release B passed non-production verification.

4. Confirm approval.

5. Deploy release B using the approved pipeline.

6. Observe workload rollout.

7. Verify health endpoint.

8. Perform critical functional test.

9. Review error rate and latency.

10. Observe for the defined monitoring period.

11. Document outcome.
```

---

# 50. DEPLOYMENT PLAN SHOULD INCLUDE STOP CONDITIONS

A safe plan should identify conditions that cause execution to stop.

Examples:

```text
Unexpected infrastructure change

Starting environment unhealthy

Required approval missing

Artifact identity unclear

Health checks fail

Error rate exceeds rollback criterion

Unexpected security warning
```

---

# 51. ROLLBACK PLAN

Before deployment ask:

> What will we do if this version is unhealthy?

A rollback plan should identify:

```text
rollback target

rollback mechanism

conditions for rollback

required authority

verification after rollback
```

---

# 52. "WE CAN ROLLBACK" IS NOT A ROLLBACK PLAN

A real rollback plan should be executable.

Weak:

```text
Rollback if necessary.
```

Better:

```text
If release B fails health verification or causes the agreed
error threshold to be exceeded, redeploy previously verified
release A through the approved deployment mechanism.

After rollback:
- verify workload state
- verify health endpoint
- perform critical functional test
- verify error rate
- verify latency
```

---

# 53. ROLLBACK TARGET

Record the exact previous version.

For example:

```text
Previous:
application:1.4.2

Target:
application:1.4.3
```

Avoid:

```text
rollback to previous
```

without identifying what "previous" means.

---

# 54. ROLLBACK MAY NOT ALWAYS BE SAFE

Some changes are not trivially reversible.

Examples:

- destructive database migration
- incompatible schema change
- irreversible data transformation
- deleted resource
- external system change

The Junior engineer should recognize this and escalate rather than invent a recovery procedure.

---

# 55. ROLL FORWARD

Sometimes the correct recovery strategy is not rollback.

A corrected version may need to be deployed instead.

This is often called:

```text
roll forward
```

At Junior level, understand the concept.

The decision should follow the organization's incident and change process.

---

# 56. BLAST RADIUS

Blast radius describes the scope of impact a failed change could produce.

Ask:

```text
One Pod?

One service?

One host?

One availability zone?

All users?

One region?

Every environment?

Shared infrastructure?
```

---

# 57. BLAST RADIUS EXAMPLE

Changing one application's logging configuration:

```text
potentially small scope
```

Changing a shared network policy:

```text
potentially much larger scope
```

The actual risk depends on architecture and implementation.

---

# 58. SHARED COMPONENTS INCREASE CONSEQUENCE

Be especially cautious around:

- shared DNS
- shared networking
- identity systems
- CI/CD infrastructure
- shared Kubernetes components
- organization-wide policies
- shared secret stores
- shared databases

A small configuration change can have a large operational effect when the component is shared.

---

# 59. RISK IS NOT ONLY PROBABILITY

A simple conceptual model is:

```text
Risk
≈
Likelihood of Failure
×
Potential Impact
```

This is a reasoning model, not a universal organizational scoring formula.

Organizations may use formal risk models.

---

# 60. QUESTIONS FOR CHANGE RISK

Ask:

```text
How likely is failure?

How many systems could be affected?

How many users?

Could data be affected?

Could security be affected?

How quickly would failure be detected?

How quickly can we recover?

Has this change been tested?

Is this component shared?
```

---

# 61. LOW-COMPLEXITY DOES NOT ALWAYS MEAN LOW-RISK

A one-line firewall change can affect thousands of users.

A small certificate configuration change can make a service unavailable.

Judge risk by consequences, not line count.

---

# 62. PROGRESSIVE CHANGES

Instead of changing everything simultaneously, systems can sometimes be changed progressively.

Conceptually:

```text
Small Exposure
      ↓
Observe
      ↓
Expand
      ↓
Observe
      ↓
Continue
```

---

# 63. WHY PROGRESSIVE CHANGE HELPS

Progressive changes can reduce blast radius.

If failure appears early:

```text
stop expansion

investigate

rollback if appropriate
```

before every instance or user is affected.

---

# 64. ROLLING DEPLOYMENT

A rolling deployment gradually replaces existing application instances.

Conceptually:

```text
Old Old Old
     ↓
New Old Old
     ↓
New New Old
     ↓
New New New
```

Availability depends on configuration and application behavior.

---

# 65. ROLLING DOES NOT AUTOMATICALLY MEAN SAFE

A rolling deployment can still fail if:

- health checks are weak
- new version is incompatible
- dependencies fail
- configuration is incorrect
- every new instance becomes unhealthy
- application-level behavior is not verified

---

# 66. CANARY CONCEPT

A canary deployment exposes a new version to a limited portion of traffic or capacity before wider rollout.

Conceptually:

```text
Mostly Old Version
+
Small New Version
        ↓
Observe
        ↓
Expand or Stop
```

Implementation belongs to later engineering depth.

At Junior level, understand the safety principle.

---

# 67. BLUE/GREEN CONCEPT

Blue/green deployment maintains separate old and new environments or application sets and switches traffic when the new version is ready.

Conceptually:

```text
Blue = Current

Green = Candidate
```

After verification:

```text
Traffic
   ↓
Green
```

The exact architecture varies.

---

# 68. FEATURE FLAGS

Deployment and release can be separated.

Code may be deployed while a feature remains disabled.

A feature flag can control exposure.

This reinforces:

```text
Deployment
≠
Release
```

---

# 69. CHANGE CONTROL IS NOT A SUBSTITUTE FOR ENGINEERING

A process containing:

```text
ticket

review

approval

window
```

can still produce a bad deployment if nobody performs meaningful technical validation.

Controls should improve engineering decisions, not replace them.

---

# 70. CI BEFORE DEPLOYMENT

The change should pass the required automated validation.

Depending on the project:

```text
format

lint

test

build

security checks

artifact creation
```

---

# 71. PIPELINE SUCCESS

A successful pipeline proves:

```text
the pipeline's defined steps completed according to their success conditions.
```

It proves nothing that the pipeline did not test.

---

# 72. PIPELINE SUCCESS DOES NOT PROVE SERVICE HEALTH

This is one of the most important concepts in the entire Junior curriculum.

```text
Pipeline = Successful
```

can coexist with:

```text
Application = Unhealthy
```

---

# 73. WHY THIS CAN HAPPEN

A pipeline may successfully:

```text
validate syntax

run unit tests

build image

push image

update Deployment
```

while the application later fails because of:

- missing production configuration
- wrong environment variable
- unavailable dependency
- invalid secret
- wrong Service selector
- failed readiness probe
- incorrect production hostname
- insufficient permission
- incompatible external service
- application logic not covered by tests

---

# 74. CI VALIDATES WHAT IT KNOWS

If the pipeline checks:

```text
Does the image build?
```

then successful output means:

```text
The image built according to that step.
```

It does not mean:

```text
Users can successfully use the deployed application.
```

---

# 75. DEPLOYMENT SUCCESS IS ALSO LIMITED

Suppose the deployment command exits successfully.

That may prove:

```text
the deployment system accepted or completed the requested operation.
```

You must separately prove application behavior.

---

# 76. DEPLOYMENT VERIFICATION LAYERS

After deployment verify progressively:

```text
Deployment Mechanism
        ↓
Infrastructure / Workload
        ↓
Process / Container
        ↓
Application Health
        ↓
Dependency Health
        ↓
Critical Function
        ↓
User-Facing Path
```

Use the layers relevant to the system.

---

# 77. WORKLOAD VERIFICATION

For a containerized workload, determine:

```text
Did expected instances start?

Are they stable?

Are they restarting?

Did rollout complete?

Are health checks passing?
```

---

# 78. APPLICATION VERIFICATION

Then determine:

```text
Does health endpoint succeed?

Does expected application response succeed?

Are logs normal?

Can required dependencies be reached?
```

---

# 79. FUNCTIONAL VERIFICATION

A health endpoint may be too shallow.

Example:

```text
/health returns 200
```

while:

```text
checkout transaction fails.
```

Critical functionality may require a separate safe verification.

---

# 80. USER-PATH VERIFICATION

Where safe and appropriate, verify the path users actually depend on.

Conceptually:

```text
Client
  ↓
DNS
  ↓
Entry Point
  ↓
Service
  ↓
Application
  ↓
Dependency
```

This is stronger evidence than checking only the deployment controller.

---

# 81. POST-CHANGE VERIFICATION

Verification asks:

> Did the intended change produce the intended result?

A useful verification model is:

```text
Action
   ↓
Expected State
   ↓
Inspection
   ↓
Evidence
   ↓
Conclusion
```

---

# 82. DEFINE VERIFICATION BEFORE DEPLOYMENT

Do not wait until after deployment to ask:

> How should I check this?

Define success before execution.

---

# 83. EXAMPLE VERIFICATION PLAN

```text
Expected:
Release B running.

Inspect:
Deployment/workload state.

Expected:
Application healthy.

Inspect:
Health endpoint.

Expected:
Critical request works.

Inspect:
Functional request.

Expected:
No abnormal failures.

Inspect:
Logs and error metrics.

Expected:
Performance remains acceptable.

Inspect:
Latency metrics.
```

---

# 84. MONITORING AFTER DEPLOYMENT

A change can initially appear healthy and fail later.

Therefore verification should be followed by observation.

Monitor relevant signals for the defined period.

---

# 85. POST-DEPLOYMENT SIGNALS

Depending on the application:

```text
request rate

error rate

latency

CPU

memory

restart count

replica availability

dependency errors

queue depth

business-critical operation
```

---

# 86. OBSERVATION PERIOD

The appropriate observation period depends on:

- traffic patterns
- system criticality
- change risk
- failure modes
- organizational process

There is no universal number of minutes that proves every deployment healthy.

---

# 87. COMPARE AGAINST BASELINE

Before:

```text

```

can coexist with:

```text

```

Automated checks reduce risk.

They do not eliminate the need for production verification.

# 206. CONFIGURATION DRIFT

```text

```


- troubleshooting
- deployment
- recovery
- audit
- automation
