# PART 14: KUBERNETES FUNDAMENTALS

## Goal

Understand the Kubernetes concepts a Junior DevOps engineer needs to inspect and support containerized workloads without pretending that introductory Kubernetes knowledge equals cluster administration expertise.

By the end of this Part, the learner should be able to enter an existing Kubernetes environment and answer foundational operational questions safely:

```text
Which cluster am I connected to?

Which namespace am I working in?

Which workload owns these Pods?

How many replicas should exist?

How many actually exist?

Which image is running?

Is the Pod scheduled?

Did the container start?

Is it restarting?

Is it Ready?

What do the logs show?

What do the events show?

Which Service selects these Pods?

Does the Service selector actually match the Pod labels?

What configuration is being supplied?

What changed?

What evidence do I have?
```

The learner should **not** leave this Part believing that knowing:

```bash
kubectl get pods
```

makes them a Kubernetes administrator.

Cluster administration includes deeper responsibilities such as control-plane lifecycle, etcd operations and recovery, cluster upgrades, certificate management, networking implementation, storage architecture, admission control, node lifecycle, policy design, security hardening, capacity engineering, and cluster-wide failure recovery.

Those are deliberately outside this Junior Part.

The operational boundary here is:

> Inspect common Kubernetes resources, understand their relationships, perform controlled workload operations, troubleshoot first-line workload failures, collect evidence, make small reviewed corrections, verify recovery, and escalate when the problem crosses into cluster administration.

---

# 1. FROM CONTAINERS TO ORCHESTRATION

Part 10 established:

```text
Dockerfile
    ↓
Build
    ↓
Image
    ↓
Registry
    ↓
Pull
    ↓
Container
    ↓
Process
```

A container solves an important packaging and runtime problem.

It does not by itself solve the operational problem of running many containers across many machines.

Suppose an organization has:

```text
20 applications

100 containers

10 machines
```

Someone must decide:

```text
Which machine runs each container?

What happens if a container exits?

What happens if a machine fails?

How many copies should run?

How does traffic reach the correct containers?

How are configuration values supplied?

How are secrets supplied?

How are application updates performed?

How are failed workloads replaced?

How do operators inspect the current state?
```

That is where orchestration becomes important.

---

# 2. WHY ORCHESTRATION EXISTS

Without orchestration, an operator might manually:

```text
SSH to server01
    ↓
docker run application
```

then:

```text
SSH to server02
    ↓
docker run application
```

then manually configure traffic routing.

If a container dies:

```text
Operator notices
    ↓
Operator connects
    ↓
Operator starts replacement
```

If a server dies:

```text
Operator notices
    ↓
Operator chooses another server
    ↓
Operator starts replacement
    ↓
Operator updates traffic path
```

This becomes difficult at scale.

---

# 3. THE MANUAL SCHEDULING PROBLEM

Imagine:

```text
Node A
CPU available: 2 cores
Memory available: 4 GiB

Node B
CPU available: 8 cores
Memory available: 16 GiB

Node C
CPU available: 1 core
Memory available: 2 GiB
```

A new workload needs somewhere to run.

An orchestration system can participate in deciding where workloads should be placed according to the information and scheduling constraints available to it.

At Junior level, understand:

```text
Workload Requested
      ↓
Scheduler
      ↓
Suitable Node Selected
      ↓
Pod Assigned
```

The deeper scheduling system comes later.

---

# 4. THE REPLACEMENT PROBLEM

Suppose the desired application state is:

```text
3 replicas
```

Current state:

```text
Pod A
Pod B
Pod C
```

Then:

```text
Pod B disappears
```

Current state becomes:

```text
2 replicas
```

A controller responsible for that desired state can work to bring the workload back toward:

```text
3 replicas
```

This is fundamentally different from an operator manually watching every container.

---

# 5. KUBERNETES

Kubernetes is a system for managing containerized workloads and services through API resources, controllers, scheduling, node agents, networking abstractions, and other components.

A useful first mental model is:

```text
Engineer
    ↓
kubectl
    ↓
API Server
    ↓
Kubernetes Resources
    ↓
Controllers
    ↓
Pods
    ↓
Containers
    ↓
Application
```

This model will be refined throughout this Part.

---

# 6. KUBERNETES IS NOT "DOCKER ON MANY SERVERS"

That description hides the most important idea.

Kubernetes is strongly centered on:

```text
Desired State
      ↓
API Objects
      ↓
Control Loops
      ↓
Observed State
      ↓
Reconciliation
```

The engineer often describes what should exist.

Kubernetes components work to move actual state toward that declared state.

---

# 7. CLUSTER

A Kubernetes cluster consists of a control plane and one or more nodes that provide the environment in which workloads can run.

Conceptually:

```text
Kubernetes Cluster
│
├── Control Plane
│
└── Worker Nodes
    ├── Node 1
    ├── Node 2
    └── Node 3
```

A small learning cluster may contain only one node.

Production architectures can contain many.

---

# 8. CLUSTER BOUNDARY

A cluster is an important operational boundary.

Resources such as:

```text
Nodes

Namespaces

Deployments

Pods

Services

ConfigMaps

Secrets
```

exist in the context of a Kubernetes cluster.

Before running any Kubernetes command, establish:

```text
Which cluster?
```

---

# 9. WRONG CLUSTER IS A SERIOUS FAILURE MODE

An otherwise correct command can be dangerous when executed against the wrong cluster.

Example:

```bash
kubectl delete deployment application
```

The syntax can be correct.

The resource name can be correct.

The operator can still be connected to:

```text
production
```

instead of:

```text
lab
```

Therefore:

```text
Correct Command
+
Wrong Cluster
=
Wrong Change
```

---

# 10. CONTROL PLANE

The control plane manages the cluster's desired and observed state.

At a foundational level, important control-plane concepts include:

```text
API Server

Scheduler

Controller Managers

Cluster State Storage
```

The learner does not need to administer these components in this Part.

They do need to understand why they exist.

---

# 11. API SERVER

The Kubernetes API server is the primary API interface to the Kubernetes control plane.

Clients such as `kubectl` communicate with the cluster through the Kubernetes API.

Think:

```text
kubectl
   ↓
API Server
```

not:

```text
kubectl
   ↓
SSH into every node
```

---

# 12. THE API-DRIVEN MODEL

When an engineer creates a Deployment, the general path is:

```text
Engineer
    ↓
kubectl
    ↓
API Request
    ↓
API Server
    ↓
Resource Stored as Cluster State
    ↓
Controllers Observe Desired State
    ↓
Other Components Act
```

This API-driven model is central to Kubernetes.

---

# 13. `kubectl`

`kubectl` is the primary Kubernetes command-line client.

It can be used to:

```text
inspect resources

create resources

update resources

delete resources

view logs

describe resources

inspect events

interact with containers
```

It communicates through the Kubernetes API rather than directly managing container processes on each node.

---

# 14. `kubectl` IS A CLIENT

Do not think:

```text
kubectl = Kubernetes
```

Think:

```text
kubectl
=
Client Used To Communicate With Kubernetes API
```

Other clients can also communicate with the API.

---

# 15. KUBECONFIG

`kubectl` needs information about:

```text
cluster

API server

identity

credentials

context
```

This information is commonly provided through kubeconfig.

By default, `kubectl` commonly looks for:

```text
$HOME/.kube/config
```

and alternative configuration can be selected through mechanisms such as `KUBECONFIG` or `--kubeconfig`.

---

# 16. KUBECONFIG IS SECURITY-SENSITIVE

A kubeconfig can contain or reference credentials capable of accessing a Kubernetes cluster.

Treat it accordingly.

Do not:

```text
commit kubeconfig to public Git

paste credentials into documentation

share privileged kubeconfig casually

send credentials to AI systems
```

---

# 17. CONTEXT

A Kubernetes context ties together information such as:

```text
cluster

user

namespace
```

for `kubectl` operations.

A kubeconfig can contain multiple contexts.

Therefore:

```text
kubectl installed
```

does not answer:

```text
Which cluster am I using?
```

---

# 18. INSPECT CURRENT CONTEXT

Before making changes:

```bash
kubectl config current-context
```

Expected conclusion:

```text
I know which configured context kubectl is currently using.
```

Do not proceed if the result is unexpected.

---

# 19. INSPECT CONFIGURED CONTEXTS

Use:

```bash
kubectl config get-contexts
```

Inspect:

```text
current context

available contexts

cluster mappings

namespace configuration
```

Do not switch contexts casually in a shared or production-sensitive environment.

---

# 20. CONTEXT CHECK IS A SAFETY HABIT

Before:

```text
apply

scale

delete

edit

rollout
```

establish:

```text
Cluster
Namespace
Resource
Intended Change
```

This should become automatic engineering behavior.

---

# 21. WORKER NODES

Kubernetes runs workloads by placing Pods onto nodes.

A node can be a physical or virtual machine and contains the components needed to run assigned Pods.

Conceptually:

```text
Cluster
│
├── Control Plane
│
├── Worker Node 1
│   └── Pods
├── Worker Node 2
│   └── Pods
└── Worker Node 3
    └── Pods
```

---

# 22. NODE COMPONENTS

At foundational level, understand these node-side concepts:

```text
kubelet

container runtime

networking components
```

The kubelet is the primary node agent responsible for managing Pods assigned to its node and working with the container runtime.

---

# 23. KUBELET

A simplified model:

```text
API / Desired Pod State
        ↓
kubelet
        ↓
Container Runtime
        ↓
Containers
```

The kubelet participates in making the Pod specification assigned to its node become actual running containers.

---

# 24. CONTAINER RUNTIME

Kubernetes does not itself execute Linux container processes directly.

The kubelet communicates through the Container Runtime Interface with a compatible container runtime to create and manage containers.

Examples of runtime implementations include environments using:

```text
containerd

CRI-O
```

The Junior learner does not need to administer the runtime in this Part.

---

# 25. DO NOT ASSUME DOCKER ENGINE IS THE KUBERNETES RUNTIME

Learning Docker remains valuable because it teaches:

```text
images

containers

registries

environment variables

ports

logs
```

But a Kubernetes node does not need Docker Engine specifically in order to run container workloads.

Keep:

```text
Container Concepts
```

separate from:

```text
Specific Container Runtime Implementation
```

---

# 26. KUBERNETES RESOURCES

Kubernetes represents desired and observed system information through API objects.

Common resources in this Part include:

```text
Namespace

Pod

Deployment

ReplicaSet

Service

ConfigMap

Secret
```

Each exists for a different purpose.

---

# 27. RESOURCE MANIFEST

Kubernetes resources are commonly represented declaratively using YAML manifests.

A typical resource includes:

```yaml
apiVersion:
kind:
metadata:
spec:
```

The exact schema depends on the resource type.

Kubernetes manifests describe objects submitted to the API.

---

# 28. `apiVersion`

Example:

```yaml
apiVersion: apps/v1
```

This identifies the Kubernetes API group/version used for that resource representation.

Do not invent API versions.

Check current Kubernetes documentation for the resource being used.

---

# 29. `kind`

Example:

```yaml
kind: Deployment
```

This identifies the resource type.

Other examples in this Part:

```text
Namespace

Service

ConfigMap

Secret
```

---

# 30. `metadata`

Metadata commonly includes information such as:

```text
name

namespace

labels

annotations
```

Example:

```yaml
metadata:
  name: veriqta-web
  namespace: veriqta-lab
```

---

# 31. `spec`

The `spec` generally represents the desired configuration of the resource.

Example:

```yaml
spec:
  replicas: 2
```

for a Deployment means:

```text
Desired Replica Count
=
2
```

---

# 32. SPEC VERSUS STATUS

A powerful Kubernetes distinction is:

```text
spec
=
desired state
```

and:

```text
status
=
observed information about current state
```

Do not confuse what you requested with what Kubernetes actually achieved.

---

# 33. DESIRED STATE

Suppose:

```yaml
spec:
  replicas: 3
```

The desired state is:

```text
3 replicas
```

But current state might temporarily be:

```text
2 running
1 pending
```

or:

```text
1 running
2 failing
```

Desired state and current state can differ.

---

# 34. RECONCILIATION

Kubernetes controllers operate control loops that work to bring current state closer to desired state.

Conceptually:

```text
Desired State
      ↓
Controller Observes
      ↓
Current State
      ↓
Difference?
   ↙       ↘
 Yes       No
  ↓
Take Action
  ↓
Observe Again
```

This is reconciliation.

---

# 35. RECONCILIATION IS CONTINUOUS

This is different from:

```text
Run command once
    ↓
Finish
```

Controllers repeatedly observe relevant state and react.

This is why Kubernetes can replace a Pod after it disappears when a higher-level controller still requires that replica.

---

# 36. CONTROLLER

A controller watches state and takes actions to move actual state toward desired state.

Controllers do not all manage the same thing.

Different controllers are responsible for different Kubernetes resources and behaviors.

---

# 37. RECONCILIATION DOES NOT GUARANTEE SUCCESS

Suppose desired state is:

```text
3 healthy replicas
```

but the image name is invalid.

The controller can continue trying to maintain the requested workload.

It cannot make a nonexistent image become valid.

Therefore:

```text
Reconciliation
≠
Magic
```

Bad desired state can be repeatedly enforced.

---

# 38. DECLARATIVELY WRONG

This is the Kubernetes equivalent of an important lesson from Terraform and Ansible:

```text
Declarative
≠
Correct
```

You can declaratively request:

```text
wrong image

wrong port

wrong selector

wrong configuration
```

Kubernetes can faithfully attempt to implement those mistakes.

---

# 39. NAMESPACES

Namespaces provide a way to scope many Kubernetes resources within a cluster.

Conceptually:

```text
Cluster
│
├── Namespace: team-a
│   ├── Deployment
│   └── Service
│
└── Namespace: team-b
    ├── Deployment
    └── Service
```

Namespaces are not separate clusters.

---

# 40. WHY NAMESPACES MATTER

Namespaces help organize and scope resources.

They are commonly used to separate resources by concepts such as:

```text
team

application

environment

purpose
```

Exact organizational models vary.

---

# 41. NAMESPACE IS PART OF RESOURCE IDENTITY

These can be separate resources:

```text
namespace: development
name: api
```

and:

```text
namespace: production
name: api
```

Therefore:

```text
Resource Name Alone
```

may not be enough to identify what you are operating on.

---

# 42. WRONG NAMESPACE FAILURE

You run:

```bash
kubectl get pods
```

and see:

```text
No resources found
```

Possible conclusion:

```text
There are no Pods in the namespace currently being queried.
```

Invalid conclusion:

```text
The cluster has no Pods.
```

Always consider namespace scope.

---

# 43. EXPLICIT NAMESPACE

Use:

```bash
kubectl get pods -n veriqta-lab
```

when you want explicit namespace targeting.

For learning and operational safety, explicit namespace usage is often clearer than relying on hidden context assumptions.

---

# 44. ALL NAMESPACES

For inspection:

```bash
kubectl get pods -A
```

or:

```bash
kubectl get pods --all-namespaces
```

can show Pods across namespaces, subject to authorization.

Do not use cluster-wide scope unnecessarily for changes.

---

# 45. POD

A Pod is the basic Kubernetes workload unit used to run one or more containers together.

For this Junior Part, most application Pods will contain:

```text
one application container
```

Conceptually:

```text
Pod
└── Container
    └── Application Process
```

---

# 46. POD IS NOT A CONTAINER

Do not say:

```text
Pod = Container
```

A Pod can contain multiple containers.

The containers in a Pod share aspects of the Pod's execution environment, including network namespace behavior and certain storage arrangements.

For introductory application workloads:

```text
One Pod
→ Often One Main Application Container
```

is a useful practical starting point.

---

# 47. PODS ARE RELATIVELY EPHEMERAL

Pods are designed as relatively disposable entities.

A replacement Pod is a new Pod with a different UID, even if it represents the same application workload.

Do not treat a Pod like a manually maintained long-lived server.

---

# 48. POD IDENTITY

A Pod has:

```text
name

namespace

UID

labels

status

spec
```

The Pod name may look familiar after replacement, but the underlying Pod identity can change.

---

# 49. DO NOT "FIX THE SERVER" MENTALITY INSIDE A POD

A poor operational pattern is:

```text
Pod broken
    ↓
exec into container
    ↓
manually edit application
    ↓
declare success
```

The Pod may later be replaced.

Your manual fix disappears.

Ask:

```text
Where should the desired configuration actually be defined?
```

---

# 50. POD PHASE

The Kubernetes API defines Pod phases including:

```text
Pending

Running

Succeeded

Failed

Unknown
```

These are high-level lifecycle summaries.

Do not assume the `STATUS` column shown by every `kubectl` command is identical to the Pod's API `phase`.

---

# 51. `Running` DOES NOT MEAN HEALTHY

A Pod can be in a Running phase while the application is:

```text
not Ready

returning errors

unable to reach a dependency

serving incorrect responses
```

Therefore:

```text
Pod Running
≠
Application Healthy
```

---

# 52. POD CONTAINER STATES

Containers within a Pod can be in states such as:

```text
Waiting

Running

Terminated
```

Kubernetes tracks container state separately from the overall Pod phase.

This distinction matters during troubleshooting.

---

# 53. DEPLOYMENT

A Deployment manages a replicated application workload declaratively.

Conceptually:

```text
Deployment
    ↓
ReplicaSet
    ↓
Pods
```

You normally manage the Deployment rather than manually creating and maintaining each individual Pod.

---

# 54. WHY DEPLOYMENTS EXIST

Suppose you want:

```text
3 application replicas
```

Without a higher-level controller:

```text
create Pod 1 manually

create Pod 2 manually

create Pod 3 manually

replace failed Pods manually

update each Pod manually
```

A Deployment provides a higher-level desired-state abstraction for replicated application workloads.

---

# 55. REPLICASET

A ReplicaSet helps maintain a specified number of matching Pod replicas.

In normal Deployment usage:

```text
Deployment
    ↓
ReplicaSet
    ↓
Pods
```

The Deployment manages ReplicaSets as part of rollout behavior.

Junior engineers should understand this ownership chain.

---

# 56. DO NOT NORMALLY EDIT DEPLOYMENT-OWNED REPLICASETS

If a ReplicaSet belongs to a Deployment, manage the desired workload through the Deployment.

Otherwise:

```text
Manual ReplicaSet Change
        ↓
Deployment Controller
        ↓
May Reconcile Against Deployment Intent
```

Work at the correct ownership level.

---

# 57. OWNERSHIP CHAIN

When investigating a Pod, ask:

```text
Who owns this Pod?
```

Typical path:

```text
Pod
    ↑
ReplicaSet
    ↑
Deployment
```

This tells you where a durable workload correction should usually be made.

---

# 58. LABELS

Labels are key/value metadata attached to Kubernetes objects.

Example:

```yaml
metadata:
  labels:
    app: veriqta-web
```

Labels can be used for organization and, critically, for selection relationships.

---

# 59. LABELS ARE OPERATIONAL

A label is not merely decorative.

Labels can influence relationships such as:

```text
Deployment selector
        ↓
Pod labels
```

and:

```text
Service selector
        ↓
Pod labels
```

A wrong label can break workload behavior even when all objects technically exist.

---

# 60. SELECTORS

Selectors identify objects based on labels.

Conceptually:

```text
Selector:
app=veriqta-web
       ↓
Find Objects With:
app=veriqta-web
```

This is a foundational Kubernetes relationship.

---

# 61. DEPLOYMENT SELECTOR

A Deployment's selector must correspond appropriately to the labels on its Pod template.

Conceptually:

```text
Deployment Selector
app=veriqta-web
       ↓
Pod Template Label
app=veriqta-web
```

This relationship allows the controller to identify the Pods belonging to that workload.

---

# 62. SERVICE SELECTOR

A Service can use selectors to identify backend Pods.

Example:

```text
Service Selector
app=veriqta-web
       ↓
Pods
app=veriqta-web
```

If the labels do not match:

```text
Service Exists
+
Pods Exist
+
No Matching Backends
```

The application can still be unreachable through the Service.

---

# 63. SERVICE

A Service provides a stable network abstraction for reaching a set of Pods.

Pods can be replaced.

Pod addresses can change.

A Service provides a stable abstraction over selected backend Pods.

Conceptually:

```text
Client
   ↓
Service
   ↓
Selected Pods
   ├── Pod A
   ├── Pod B
   └── Pod C
```

---

# 64. SERVICE IS NOT THE APPLICATION

A Service does not make a broken application healthy.

It provides network reachability/routing abstraction to selected backends.

Therefore:

```text
Service Exists
≠
Backend Exists
```

and:

```text
Backend Exists
≠
Backend Ready
```

and:

```text
Backend Ready
≠
Application Correct
```

---

# 65. SERVICE TYPES

Kubernetes supports multiple Service types.

For this Junior Part, focus primarily on:

```text
ClusterIP
```

and basic exposure concepts.

`ClusterIP` provides an internal cluster Service abstraction.

Other types such as:

```text
NodePort

LoadBalancer

ExternalName
```

exist, but deeper service exposure architecture belongs later.

---

# 66. PORT RELATIONSHIPS

A Service can involve several port concepts.

A useful beginner model:

```text
Service Port
    ↓
Target Port
    ↓
Application Listening Port
```

Example:

```text
Service:
port 80
    ↓
targetPort 8080
    ↓
Container application:
listens on 8080
```

---

# 67. `containerPort`

A container specification can declare:

```yaml
ports:
  - containerPort: 8080
```

This is useful metadata and can support tooling and readability.

It does not itself cause an application process to listen on that port.

The application must actually bind and listen.

Recall Part 8:

```text
Configuration
    ↓
Process
    ↓
Socket
    ↓
Listening Port
```

Kubernetes does not replace that runtime reality.

---

# 68. SERVICE PORT MISMATCH

Suppose:

```text
Application listens:
8080
```

but Service sends traffic to:

```text
targetPort:
9090
```

Then:

```text
Pod Running
+
Service Exists
+
Selector Matches
+
Wrong Target Port
=
Application Unreachable Through Service
```

This is a common reasoning pattern.

---

# 69. CONFIGMAP

A ConfigMap stores non-secret configuration data for use by workloads.

Examples:

```text
application environment

feature settings

configuration text

non-sensitive endpoints
```

A workload can consume ConfigMap data in different ways, including environment variables or mounted files.

---

# 70. CONFIGMAP IS NOT FOR SECRETS

Do not store:

```text
passwords

private keys

API tokens
```

in a ConfigMap merely because it is convenient.

ConfigMaps are not designed as secret storage.

---

# 71. SECRET

A Kubernetes Secret is an API object intended to hold sensitive data such as credentials or tokens.

However:

```text
Kubernetes Secret
≠
Automatically Safe Under Every Cluster Configuration
```

Access control, storage protection, encryption configuration, RBAC, workload access, logging, and external secret-management architecture still matter.

---

# 72. BASE64 IS NOT ENCRYPTION

Kubernetes Secret manifests may represent data using base64 encoding.

Base64 is an encoding mechanism.

It is not encryption.

Therefore:

```text
Base64
≠
Secret Protection
```

Never treat base64-encoded credentials as safely encrypted.

---

# 73. DO NOT COMMIT REAL SECRETS

Avoid committing real secret values into public repositories.

A Git history can preserve sensitive material even after later deletion.

Use safe dummy values for public labs.

---

# 74. CONFIGURATION FLOW

A useful application model is:

```text
ConfigMap / Secret
        ↓
Pod Specification
        ↓
Container Environment or Files
        ↓
Application
```

Troubleshooting configuration means tracing this chain.

---

# 75. CONFIGURATION EXISTS BUT APPLICATION STILL FAILS

Suppose:

```text
ConfigMap exists
```

That does not prove:

```text
Pod references it correctly

key exists

value is correct

container received it

application interpreted it correctly
```

Always trace end to end.

---

# 76. CONTAINER IMAGES

Kubernetes workloads reference container images.

Example:

```yaml
image: nginx:1.27
```

Conceptually:

```text
Pod Spec
    ↓
Image Reference
    ↓
Registry
    ↓
Image Pull
    ↓
Container Creation
```

---

# 77. IMAGE TAGS

Part 10 established:

```text
Tag
≠
Immutable Identity
```

A tag can potentially refer to different image content over time.

Image digests provide content-addressed identity.

The same principle applies when Kubernetes pulls images.

---

# 78. IMAGE PULL

Before a container can start, the required image must be available to the node's container runtime.

Failures can involve:

```text
wrong image name

wrong tag

registry unavailable

authentication failure

authorization failure

network failure

DNS failure
```

Do not diagnose all image pull failures as:

```text
Kubernetes is broken.
```

---

# 79. PRIVATE REGISTRIES

Private images may require registry credentials.

Kubernetes supports mechanisms for providing image pull credentials.

At Junior level, understand the concept:

```text
Pod Needs Private Image
        ↓
Registry Authentication Required
        ↓
Authorized Credential
        ↓
Image Pull
```

Do not paste real registry passwords into public manifests.

---

# 80. DESIRED STATE EXAMPLE

Deployment:

```text
replicas: 3
image: application:v1
```

Desired:

```text
3 Pods
running application:v1
```

Actual might temporarily be:

```text
Pod A: Running

Pod B: Running

Pod C: ImagePullBackOff
```

The Deployment object existing does not mean the workload is healthy.

---

# 81. HEALTH PROBES

Kubernetes supports application health probes including:

```text
startup probes

readiness probes

liveness probes
```

At Junior level, understand their different purposes.

Do not treat them as interchangeable.

---

# 82. READINESS PROBE

Readiness answers a question similar to:

```text
Should this container currently receive traffic?
```

If readiness fails, the workload can remain running while not being considered ready for Service traffic.

This is different from killing the container.

---

# 83. LIVENESS PROBE

Liveness answers a question similar to:

```text
Should Kubernetes consider this container unhealthy enough
to restart it?
```

A bad liveness probe can create unnecessary restarts.

Therefore:

```text
Liveness Probe
=
Potentially Consequential
```

---

# 84. STARTUP PROBE

A startup probe can protect slow-starting applications from premature liveness/readiness behavior during initialization.

At Junior level, recognize why startup behavior may need separate treatment.

Deeper probe design comes later.

---

# 85. PROBES DO NOT MAKE APPLICATIONS HEALTHY

A probe observes behavior.

It does not repair bad application code.

Poorly designed probes can also produce misleading or harmful behavior.

Therefore:

```text
Probe Configured
≠
Health Strategy Correct
```

---

# 86. LOGS

Container logs are a primary source of application evidence.

Basic command:

```bash
kubectl logs <pod-name> -n <namespace>
```

For a multi-container Pod:

```bash
kubectl logs <pod-name> -c <container-name> -n <namespace>
```

Always know which container you are inspecting.

---

# 87. PREVIOUS CONTAINER LOGS

For a container that restarted, previous-instance logs can be especially useful:

```bash
kubectl logs <pod-name> -n <namespace> --previous
```

This can expose the output from the previous terminated container instance when available.

For `CrashLoopBackOff`, this is often important evidence.

---

# 88. LOGS ARE NOT EVENTS

Application logs answer questions such as:

```text
What did the application process report?
```

Kubernetes events answer questions such as:

```text
What did Kubernetes components report about this resource?
```

Use both.

---

# 89. EVENTS

Events can reveal operational information such as:

```text
scheduling problems

image pull failures

container start failures

probe failures

mount failures
```

A common inspection path is:

```bash
kubectl describe pod <pod-name> -n <namespace>
```

and inspect the Events section.

Kubernetes' own debugging guidance recommends inspecting Pod state and recent events early in Pod troubleshooting.

---

# 90. EVENTS ARE TIME-SENSITIVE EVIDENCE

Events are not a permanent incident archive.

They may be retained for a limited period according to cluster configuration.

Capture important evidence during troubleshooting rather than assuming it will remain forever.

# 113. SECRET LAB


---

# 114. WHY `stringData` IS USED IN THE LAB

`stringData` allows plain strings to be supplied to the Secret API without manually base64-encoding them in the manifest.

The API can represent Secret data differently after creation.

This does not make the value encrypted merely because it is stored as a Secret object.

# 157. CRASHLOOPBACKOFF

`CrashLoopBackOff` commonly appears when a container repeatedly starts, fails, and is restarted, with Kubernetes applying backoff between restart attempts. It is commonly displayed by `kubectl`; it is not one of the Pod API's defined `phase` values.

This distinction matters.

---

# 158. CRASHLOOPBACKOFF IS A SYMPTOM

Do not write:

```text
Root cause:
CrashLoopBackOff
```

That is not enough.

It describes restart/backoff behavior.

The root cause could be:

```text
application crash

missing environment variable

invalid configuration

missing file

dependency failure

permission problem

probe-induced restart

resource-related termination
```

among other possibilities.

It does not automatically identify the exact Service problem.

# 183. LIVENESS CAUTION

A liveness probe can trigger container restarts when it repeatedly fails according to its configured behavior.

Therefore a bad liveness probe can turn:



from Kubernetes' perspective.

Junior engineers should understand this risk before modifying liveness configuration.

# 195. FIRST-LINE TROUBLESHOOTING STANDARD

For a workload problem:

```text
1. Confirm context.

2. Confirm namespace.

3. Identify workload.

4. Inspect Deployment.

5. Inspect ReplicaSet.

6. Inspect Pods.

7. Inspect Pod status.

8. Describe failing Pod.

9. Inspect container state.

10. Inspect logs.

11. Inspect previous logs if relevant.

12. Inspect events.

13. Inspect configuration references.

14. Inspect Service and selectors if connectivity is involved.

15. Verify application behavior.

16. Correct the smallest justified cause.

17. Verify recovery.
```

# 196. DO NOT DELETE PODS AS FIRST RESPONSE

A common weak troubleshooting habit is:

```text

    ↓
Delete Pod
```

A replacement may appear.

But if desired state contains the same error:

```text

    ↓
Replacement Pod
    ↓
Same Failure
```

You have restarted the symptom without understanding the cause.

---

# 197. WHEN POD DELETION IS USEFUL

Deleting a Deployment-managed Pod can be useful for:

```text

specific controlled recovery actions

testing replacement behavior
```

But it is not root-cause analysis.

---

# 198. DO NOT SCALE AS A GENERIC FIX

Another weak pattern:

```text

    ↓

```

If every replica contains the same bad configuration:

```text

```

becomes:

```text

```

Scaling can multiply failure.

# 199. DO NOT RESTART EVERYTHING

Avoid:

```text

restart cluster
```

without evidence.

```text

root cause
```

first.

# 216. API AUTHORIZATION FAILURE

Authentication and authorization are different.

You may successfully authenticate but receive:

```text

```

because your identity lacks permission for the requested operation.

Conceptually:

```text
Who are you?
→ Authentication
```

```text

→ Authorization
```

Do not solve authorization failures by obtaining cluster-admin credentials casually.

```bash

```

# 252. LAB CLEANUP

Before cleanup:

```bash
kubectl get all -n veriqta-lab
```

Confirm these are only disposable lab resources.

Then remove the namespace through the reviewed lab manifest:

```bash
kubectl delete -f namespace.yml
```

Because namespace deletion removes namespaced resources within it, confirm that `veriqta-lab` contains nothing valuable before doing this.

---

# 253. VERIFY CLEANUP

Run:

```bash
kubectl get namespace veriqta-lab
```

The namespace may remain visible temporarily while termination completes.

Do not assume deletion is instantaneous.

Verify eventual removal.

# 284. READY FOR PART 15

The learner can now inspect and support a basic Kubernetes workload.

The next operational question is:

```text
How do we know what a production system is doing over time?
```

A system may be:

```text
deployed successfully

running

Ready

reachable
```

and still suffer:

```text
rising latency

increasing errors

resource pressure

dependency degradation

intermittent failures
```

That leads into:

# PART 15: OBSERVABILITY, LOGGING, METRICS, AND ALERTS

The next mental model becomes:

```text
Production System
      ↓
Telemetry
      ↓
Logs + Metrics + Other Signals
      ↓
Collection
      ↓
Analysis
      ↓
Alerting
      ↓
Investigation
      ↓
Evidence
      ↓
Action
```

The same engineering principle continues:

```text
Resource Exists
≠
Workload Healthy
```

```text
Workload Healthy At One Moment
≠
System Reliable Over Time
```

```text
Alert Fired
≠
Root Cause Known
```

The engineer must continue moving from:

```text
assumption
```

to:

```text
observable evidence
```
