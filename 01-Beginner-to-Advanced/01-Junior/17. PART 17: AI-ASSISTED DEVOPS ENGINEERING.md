# PART 17: AI-ASSISTED DEVOPS ENGINEERING

## Goal

Learn to use AI deliberately across real DevOps tasks while maintaining human ownership of correctness, security, operational risk, and production decisions.

This Part does not teach the learner to replace engineering judgment with prompts.

It teaches the learner to use AI as an engineering accelerator while preserving the disciplines established throughout this curriculum:

- understand the system
- inspect the environment
- collect evidence
- verify versions
- protect credentials
- review changes
- limit blast radius
- test safely
- observe results
- maintain human accountability

The learner should finish this Part able to use AI for real engineering work without confusing:

```text
Generated Output
```

with:

```text
Verified Engineering Knowledge
```

The central model is:

```text
Engineering Problem
        ↓
Collect Evidence
        ↓
Provide Bounded Context
        ↓
AI Assistance
        ↓
Understand the Suggestion
        ↓
Independent Verification
        ↓
Assess Risk
        ↓
Test Safely
        ↓
Observe Evidence
        ↓
Accept / Modify / Reject
        ↓
Engineering Decision
```

The troubleshooting model is:

```text
Observed Symptom
        ↓
Evidence
        ↓
AI-Assisted Hypotheses
        ↓
Rank by Evidence
        ↓
Test Hypothesis
        ↓
New Evidence
        ↓
Eliminate / Strengthen Hypothesis
        ↓
Root Cause
        ↓
Corrective Action
        ↓
Verification
```

The security model remains:

```text
AI Capability
        ≠
AI Authority
```

and:

```text
AI Recommendation
        ≠
Approved Change
```

and:

```text
Plausible Answer
        ≠
Correct Answer
```

---

# 1. AI IN DEVOPS ENGINEERING

AI can assist with many engineering activities.

Examples include:

```text
explanation
research assistance
command interpretation
script drafting
configuration review
log analysis
error interpretation
test generation
documentation
code review
troubleshooting hypotheses
change review
```

AI can reduce the time required to:

```text
understand unfamiliar output

generate a first draft

identify possible causes

summarize large logs

compare configuration

write repetitive code

create test cases

review changes
```

But reducing effort does not transfer responsibility.

The engineer remains responsible for determining whether the result is:

```text
correct

safe

appropriate

compatible

authorized

verified
```

---

# 2. AI ASSISTANCE IS NOT ENGINEERING AUTHORITY

Consider:

```text
AI:
"Run this command."
```

That statement does not answer:

```text
Is the command valid?

Does this version support it?

What does it modify?

Which environment am I in?

Does it require privilege?

Can it destroy data?

Can it expose credentials?

Can I reverse it?

Am I authorized to run it?
```

Those remain engineering questions.

---

# 3. THE JUNIOR ENGINEER'S RESPONSIBILITY

A Junior engineer using AI should be able to say:

```text
I understand what this suggestion does.

I know why I am considering it.

I checked whether it applies to my environment.

I checked the relevant documentation.

I understand the expected effect.

I understand the potential risk.

I tested it within an appropriate boundary.

I observed the result.

I can explain why I accepted or rejected it.
```

If the learner cannot explain those points, the AI has moved faster than the learner's understanding.

---

# 4. AI SHOULD ACCELERATE REASONING, NOT REMOVE IT

Good use:

```text
Engineer investigates
        ↓
AI helps interpret evidence
        ↓
Engineer verifies
        ↓
Engineer decides
```

Poor use:

```text
Problem
    ↓
Ask AI
    ↓
Copy command
    ↓
Run in production
```

The second workflow removes critical engineering controls.

---

# 5. USE CASE: EXPLANATION

AI can explain unfamiliar concepts.

Example request:

```text
Explain the difference between a Kubernetes Deployment,
ReplicaSet, and Pod.

Focus on ownership relationships and reconciliation.
```

This can accelerate learning.

But important technical details should still be checked against authoritative documentation when they affect real changes.

---

# 6. USE CASE: RESEARCH ASSISTANCE

AI can help identify:

```text
concepts to research

relevant terminology

documentation areas

possible version differences

questions that should be answered
```

Example:

```text
I am investigating a Kubernetes Pod that is Pending.

Give me the major evidence categories I should inspect,
but do not propose a remediation yet.
```

This is better than immediately asking:

```text
How do I fix Pending?
```

because the first request preserves investigation.

---

# 7. AI IS NOT THE AUTHORITATIVE DOCUMENTATION

When exact behavior matters, verify against sources appropriate to the technology.

Examples:

```text
official documentation

command help

API documentation

release notes

provider documentation

installed version information

configuration schema
```

AI may remember a command from:

```text
older release

different operating system

different cloud provider

different tool

different edition
```

The environment decides whether the suggestion applies.

---

# 8. USE CASE: COMMAND INTERPRETATION

Suppose you encounter:

```bash
ss -lntp
```

AI can explain:

```text
what ss does

what each option means

what LISTEN means

how local address relates to binding

how process information may appear
```

The engineer can then compare the explanation with:

```bash
ss --help
```

and the actual output.

---

# 9. USE CASE: SCRIPT DRAFTING

AI can produce a first draft of:

```text
Bash script

Python script

validation script

health-check script

deployment helper

log parser
```

The output should be treated as code written by an unfamiliar contributor.

Review it.

Test it.

Do not trust it because it looks clean.

---

# 10. USE CASE: CONFIGURATION REVIEW

AI can review:

```text
Dockerfile

Terraform

Ansible

Kubernetes YAML

CI/CD workflow

systemd unit

Nginx configuration
```

Useful questions include:

```text
What assumptions does this configuration make?

Which lines could be destructive?

Which values are version-dependent?

Which permissions appear broader than necessary?

Which failure cases are not handled?

What should I verify before applying this?
```

---

# 11. USE CASE: LOG ANALYSIS

AI can help summarize logs.

For example:

```text
Here are 80 sanitized application log lines.

Group them by error type.

Build a timeline.

Identify repeated failures.

Do not declare root cause.

List hypotheses supported by specific log evidence.
```

This is substantially better than:

```text
What is wrong?
```

---

# 12. USE CASE: ERROR INTERPRETATION

Suppose Terraform reports an error.

AI can help break it into:

```text
component

operation

resource

reported reason

likely investigation layer
```

But the exact meaning should be validated using:

```text
Terraform output

provider documentation

configuration

state awareness

target API behavior
```

---

# 13. USE CASE: TEST GENERATION

AI can help generate:

```text
unit tests

negative tests

boundary cases

validation tests

failure cases

smoke tests
```

A useful request is:

```text
Review this function and generate tests for:

normal input
empty input
invalid input
boundary values
failure behavior

Do not modify the implementation.
```

The engineer must inspect whether the tests actually test the intended behavior.

---

# 14. USE CASE: DOCUMENTATION

AI can help draft:

```text
README files

runbooks

incident summaries

change descriptions

troubleshooting procedures

architecture explanations

operational checklists
```

Generated documentation must still match the actual system.

Documentation that sounds professional but describes nonexistent behavior is dangerous.

---

# 15. USE CASE: CODE REVIEW

AI can act as another reviewer.

Example:

```text
Review this shell script.

Look specifically for:

quoting errors
unchecked exit status
unsafe temporary files
destructive commands
secret exposure
non-idempotent behavior
unhandled empty variables

Do not rewrite it yet.
```

This focuses the review.

---

# 16. USE CASE: TROUBLESHOOTING HYPOTHESES

AI is especially useful for generating hypotheses.

Suppose:

```text
Application is slow.
```

AI might suggest:

```text
CPU saturation

memory pressure

disk I/O

dependency latency

database contention

network problems

application lock contention
```

These are hypotheses.

None becomes root cause until evidence supports it.

---

# 17. USE CASE: CHANGE REVIEW

Before applying a change, AI can help ask:

```text
What could this affect?

What assumptions does it make?

What should be checked before execution?

What should be verified afterward?

What rollback considerations exist?
```

The engineer still owns the decision.

---

# 18. A BAD AI WORKFLOW

```text
Error Appears
    ↓
Copy Error Into AI
    ↓
Receive Command
    ↓
Copy Command
    ↓
Run Command
    ↓
Hope
```

This is not reliable troubleshooting.

---

# 19. A BETTER AI WORKFLOW

```text
Error Appears
    ↓
Confirm Symptom
    ↓
Collect Evidence
    ↓
Identify Layer
    ↓
Provide Bounded Context
    ↓
Ask AI for Hypotheses
    ↓
Review Suggestions
    ↓
Verify Commands and Assumptions
    ↓
Test Safely
    ↓
Collect New Evidence
    ↓
Conclude
```

---

# 20. PROMPT QUALITY IS AN ENGINEERING INPUT

AI output depends partly on input quality.

Compare:

```text
Fix Kubernetes.
```

with:

```text
Objective:
Restore a Deployment to healthy state.

Environment:
Disposable Kubernetes lab.

Client:
kubectl version already collected.

Observed state:
Deployment desired replicas = 3.
No Pods are Ready.

Expected state:
3 Ready Pods.

Evidence:
kubectl get pods shows ImagePullBackOff.

Recent change:
Container image tag changed.

Constraint:
Do not modify cluster-wide configuration.

Task:
Help me generate investigation hypotheses.
Do not provide remediation until we identify the failing layer.
```

The second request gives the AI a bounded engineering problem.

---

# 21. STRUCTURED ENGINEERING REQUEST

A useful structure is:

```text
Objective

Environment

Version

Observed State

Expected State

Error

Relevant Configuration

Evidence

Constraints

Actions Already Attempted

Requested Assistance
```

Not every request requires every field.

Use what materially affects the problem.

---

# 22. OBJECTIVE

State what you are trying to achieve.

Weak:

```text
Docker broken.
```

Better:

```text
I need the containerized application to listen on port 8080
and respond successfully to GET /health.
```

The objective defines success.

---

# 23. ENVIRONMENT

State the relevant environment.

Examples:

```text
Ubuntu lab VM

local Docker environment

staging Kubernetes namespace

Terraform disposable lab

GitHub Actions workflow

development workstation
```

This matters because commands and behavior vary.

---

# 24. VERSION

Version information can completely change the answer.

Examples:

```text
Docker version

Terraform version

Kubernetes server version

kubectl version

Linux distribution and release

Python version

Ansible version
```

Do not provide version information from memory.

Inspect it.

---

# 25. VERSION EVIDENCE

Examples include:

```bash
terraform version
```

```bash
kubectl version
```

```bash
docker version
```

```bash
python3 --version
```

```bash
ansible --version
```

Use the command appropriate to the installed tool.

---

# 26. OBSERVED STATE

Describe what exists now.

Example:

```text
Pod status:
ImagePullBackOff

Ready:
0/1

Restarts:
0
```

This is evidence.

---

# 27. EXPECTED STATE

Describe what should exist.

Example:

```text
Pod should reach Running.

Ready should become 1/1.

Application should respond successfully to /health.
```

Without expected state, troubleshooting becomes vague.

---

# 28. ERROR

Provide exact error text where safe.

Do not paraphrase:

```text
something about permissions
```

when you can safely provide:

```text
permission denied
```

or the sanitized exact diagnostic.

Exact wording can matter.

---

# 29. RELEVANT CONFIGURATION

Provide only the configuration needed to understand the issue.

Examples:

```text
Deployment container section

Dockerfile

specific Terraform resource

failing CI job

systemd service unit

small script function
```

Avoid dumping an entire repository unnecessarily.

---

# 30. CONSTRAINTS

Constraints prevent inappropriate recommendations.

Examples:

```text
Do not restart production.

Do not delete the resource.

No administrator permissions.

Cannot change cluster-wide settings.

Must preserve data.

Only staging changes are allowed.

Do not install new packages.
```

AI cannot respect constraints it does not know.

---

# 31. ACTIONS ALREADY ATTEMPTED

Tell the AI what has already been tested.

Example:

```text
Already checked:

application process exists

port 8080 is listening

localhost health request succeeds

remote request still fails
```

This narrows the search space.

---

# 32. REQUESTED ASSISTANCE

Be explicit about what you want.

Examples:

```text
Explain the error.

Generate three hypotheses.

Review this script.

Identify assumptions.

Suggest evidence to collect next.

Compare expected and observed state.

Do not provide remediation yet.
```

AI does not always need to provide a solution.

Sometimes the best assistance is a better investigation.

---

# 33. A REUSABLE DEVOPS AI REQUEST TEMPLATE

```text
Objective:
<what I need to achieve>

Environment:
<lab/development/staging/production>
<OS/platform/cloud>

Versions:
<relevant versions>

Expected state:
<what should happen>

Observed state:
<what actually happens>

Error:
<exact sanitized error>

Relevant configuration:
<minimum necessary configuration>

Evidence collected:
<commands and relevant outputs>

Actions already attempted:
<tests already performed>

Constraints:
<what must not be changed or exposed>

Task:
<what I want you to help with>
```

---

# 34. DO NOT TURN THE TEMPLATE INTO CEREMONY

A simple command explanation does not require a twenty-line prompt.

Use context proportional to the task.

The purpose is:

```text
Relevant Context
```

not:

```text
Maximum Possible Context
```

---

# 35. CONTEXT BOUNDARIES

AI can only reason from:

```text
what it already knows

what you provide

what approved tools allow it to inspect

what external sources it can access
```

It does not automatically know your environment.

---

# 36. REPOSITORY CONTEXT

Repository context can include:

```text
source code

configuration

tests

documentation

CI/CD workflows

Terraform

Dockerfiles

Kubernetes manifests
```

Repository access can greatly improve assistance.

It also expands the information boundary.

Part 16's security rules still apply.

---

# 37. SELECTED FILE CONTEXT

Often the AI does not need the entire repository.

Example:

```text
Dockerfile

app.py

deployment.yaml
```

may be sufficient.

Providing selected files can reduce:

```text
noise

data exposure

irrelevant assumptions
```

---

# 38. LOG CONTEXT

Useful log context includes:

```text
timestamp

component

severity

request ID

error

surrounding events
```

Do not remove so much context that event relationships disappear.

---

# 39. COMMAND OUTPUT CONTEXT

Command output can be more valuable than a description.

Compare:

```text
CPU is high.
```

with:

```text
load average: ...
top process: ...
CPU utilization: ...
```

Evidence improves hypothesis quality.

---

# 40. DOCUMENTATION CONTEXT

If you are working from specific documentation, provide or direct the AI to the relevant authoritative material where the tool supports it.

Then ask:

```text
Does this proposed command match this documented version?
```

This reduces reliance on memory alone.

---

# 41. ENVIRONMENT CONTEXT

Environment information can include:

```text
operating system

architecture

cloud provider

container runtime

cluster

namespace

region

CI platform

shell

package manager
```

Only include what matters.

---

# 42. CONTEXT CAN BE WRONG

Providing context does not guarantee correctness.

If you tell AI:

```text
The database is definitely healthy.
```

when it is not, the AI may reason from a false premise.

Separate:

```text
Assumption
```

from:

```text
Verified Evidence
```

---

# 43. LABEL ASSUMPTIONS

Good:

```text
Assumption:
The database is healthy, but I have not verified this yet.
```

Better:

```text
Evidence:
Database health check returned success at 14:03 UTC.
```

The second statement is testable.

---

# 44. CONTEXT FRESHNESS

Infrastructure changes.

A log from:

```text
two hours ago
```

may not describe current state.

A Terraform plan from before another engineer's change may no longer represent current infrastructure.

A Pod name may no longer exist.

Ask:

```text
How fresh is this evidence?
```

---

# 45. CONTEXT CONSISTENCY

Check whether evidence comes from the same:

```text
environment

host

namespace

cluster

account

region

time window

application version
```

Mixing staging logs with production metrics can create convincing false conclusions.

---

# 46. CONTEXT SECURITY

Before providing context to AI, inspect for:

```text
passwords

tokens

private keys

customer information

confidential source code

sensitive logs

internal identifiers
```

Use only approved AI tools and organizational policies.

---

# 47. MINIMUM NECESSARY CONTEXT

Provide enough information to reason.

Do not provide unnecessary sensitive information.

```text
Useful Context
        +
Minimum Exposure
```

is the goal.

---

# 48. HALLUCINATION

An AI hallucination is generated information presented plausibly despite being unsupported, incorrect, or nonexistent.

In DevOps, hallucinations can be dangerous because technical output often looks executable.

---

# 49. NONEXISTENT COMMAND

AI may generate:

```text
tool magical-fix
```

even if the command does not exist.

Never assume command existence.

Verify.

---

# 50. COMMAND DISCOVERY

Use tools such as:

```bash
command -v <command>
```

and:

```bash
<command> --help
```

where appropriate.

The exact verification method depends on the tool.

---

# 51. NONEXISTENT FLAG

A command may exist while the suggested flag does not.

Example pattern:

```text
real-command --invented-option
```

Check:

```bash
real-command --help
```

or the relevant documentation.

---

# 52. VERSION-SPECIFIC FLAG

A flag may be valid in:

```text
version X
```

but absent in:

```text
version Y
```

Therefore:

```text
AI remembers flag
```

does not establish:

```text
installed version supports flag
```

---

# 53. INVALID API

AI can generate:

```text
wrong API version

wrong field

wrong endpoint

wrong resource kind
```

This commonly matters in:

```text
Kubernetes

cloud APIs

Terraform providers

CI/CD schemas
```

Validate against the actual platform.

---

# 54. OBSOLETE SYNTAX

Technical ecosystems evolve.

AI may produce syntax from:

```text
old tutorial

deprecated release

previous API version

legacy configuration format
```

A syntactically plausible example can still be obsolete.

---

# 55. INCORRECT DEFAULT

AI may claim:

```text
The default timeout is X.
```

Defaults are exactly the kind of detail that should be verified.

They may vary by:

```text
version

provider

platform

distribution

configuration
```

---

# 56. FAKE DEPENDENCY

AI may recommend installing a package that:

```text
does not exist

has a similar but wrong name

belongs to another ecosystem

is malicious
```

Never install an unfamiliar dependency solely because AI named it.

---

# 57. DEPENDENCY VERIFICATION

Before installing:

```text
verify package name

verify official source

verify documentation

verify publisher/maintainer

verify expected version

understand why it is needed
```

Part 16's supply-chain rules apply.

---

# 58. UNSAFE REMEDIATION

AI may produce a fix that removes a security control.

Examples:

```text
chmod 777

disable TLS verification

grant administrator

open firewall to everyone

run privileged container

disable authentication
```

The fact that a remediation removes an error does not make it correct.

---

# 59. PLAUSIBLE BUT INCORRECT ROOT CAUSE

AI may say:

```text
The application is slow because CPU is high.
```

But high CPU could be:

```text
cause

effect

expected workload

unrelated workload
```

Correlation does not establish root cause.

---

# 60. AI CONFIDENCE IS NOT EVIDENCE

A response may sound:

```text
certain

detailed

professional

specific
```

and still be wrong.

Do not use writing confidence as a correctness signal.

---

# 61. LONG ANSWER IS NOT STRONGER EVIDENCE

A five-paragraph explanation can be wrong.

A single command output can disprove it.

Engineering decisions should follow evidence.

---

# 62. VERIFICATION WORKFLOW

Every meaningful AI recommendation should pass through:

```text
AI Suggestion
        ↓
Understand Suggestion
        ↓
Check Documentation
        ↓
Inspect Environment
        ↓
Assess Risk
        ↓
Test Safely
        ↓
Observe Result
        ↓
Accept / Reject
```

---

# 63. STEP 1: UNDERSTAND THE SUGGESTION

Before executing:

```text
What does this command do?

What does each important option mean?

What files or resources can it modify?

Does it require elevated privilege?

What should happen if it succeeds?
```

If you cannot explain the action, do not execute it against important infrastructure.

---

# 64. STEP 2: CHECK DOCUMENTATION

Use authoritative documentation for exact behavior.

For local tools, also use:

```text
--help

manual pages

built-in documentation

schema inspection
```

For example, Kubernetes exposes resource schema information through `kubectl explain`; the information is retrieved from the server's OpenAPI data.

---

# 65. STEP 3: INSPECT THE ENVIRONMENT

Determine:

```text
current identity

target environment

tool version

resource state

configuration

permissions
```

A correct command in the wrong environment is still dangerous.

---

# 66. STEP 4: ASSESS RISK

Ask:

```text
Read-only?

Write?

Restart?

Delete?

Replace?

Expose?

Change permissions?

Modify data?

Affect one resource?

Affect many resources?
```

Risk determines how much verification is required.

---

# 67. STEP 5: TEST SAFELY

Prefer:

```text
local environment

disposable VM

temporary container

development environment

dedicated lab

staging environment
```

before important production systems.

---

# 68. STEP 6: OBSERVE RESULT

After action:

```text
collect output

check exit status

inspect logs

inspect state

verify service

compare expected versus observed
```

Do not conclude success because the command returned without obvious error.

---

# 69. STEP 7: ACCEPT OR REJECT

Accept when evidence supports the recommendation.

Modify when the underlying idea is useful but implementation is unsuitable.

Reject when:

```text
command does not exist

flag is unsupported

assumption is false

security risk is unacceptable

environment is incompatible

evidence contradicts it
```

---

# 70. VERIFICATION DEPTH SHOULD MATCH RISK

Low-risk:

```text
Explain this log line.
```

High-risk:

```text
Apply this Terraform plan to production.
```

These should not receive the same verification effort.

---

# 71. READ-ONLY BEFORE WRITE

During troubleshooting, prefer evidence-gathering actions before changes.

Example:

```text
inspect process

inspect logs

inspect events

inspect plan

inspect configuration
```

before:

```text
restart

delete

replace

modify permissions
```

---

# 72. REVERSIBILITY

Before accepting an AI-generated change, ask:

```text
Can this be reversed?

How?

What data could be lost?

What state changes?

What dependency could be affected?
```

Reversibility matters.

---

# 73. BLAST RADIUS

Ask:

```text
One file?

One process?

One host?

One namespace?

One account?

Every server?

Entire production environment?
```

The larger the blast radius, the stronger the review requirements.

---

# 74. AI-ASSISTED TROUBLESHOOTING

The correct model is:

```text
Evidence
    ↓
AI-Assisted Hypotheses
    ↓
Rank by Evidence
    ↓
Test
    ↓
New Evidence
    ↓
Root Cause
```

Not:

```text
Symptom
    ↓
AI Guess
    ↓
Root Cause
```

---

# 75. HYPOTHESIS

A hypothesis is a testable explanation.

Example:

```text
Hypothesis:
The application is unavailable because it is bound only
to loopback.
```

This predicts evidence.

For example:

```text
ss should show 127.0.0.1:<port>
rather than an externally reachable bind address.
```

Now test it.

---

# 76. RANKING HYPOTHESES

AI may generate ten possible causes.

Do not test randomly.

Rank them using:

```text
existing evidence

recent changes

failure scope

likelihood

cost of test

risk of test
```

---

# 77. ASK AI TO SHOW EVIDENCE RELATIONSHIP

Useful request:

```text
For each hypothesis:

1. state which existing evidence supports it
2. state which evidence contradicts it
3. give one safe test
4. state what result would strengthen it
5. state what result would weaken it
```

This forces more disciplined reasoning.

---

# 78. ROOT CAUSE REQUIRES EVIDENCE

A root cause should explain:

```text
why the failure occurred

why the observed symptoms appeared

why corrective action restored expected behavior
```

A plausible narrative alone is insufficient.

---

# 79. LAB 1: AI-ASSISTED LINUX TROUBLESHOOTING

Scenario:

```text
A Linux application is slow.

Monitoring reports high CPU utilization.
```

Do not ask AI:

```text
How do I fix high CPU?
```

First collect evidence.

---

# 80. CONFIRM SYSTEM STATE

Use tools available in the lab, for example:

```bash
uptime
```

```bash
top
```

or:

```bash
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%cpu | head
```

Do not assume identical output across every Linux implementation.

---

# 81. RECORD EVIDENCE

Record:

```text
system load

top CPU process

PID

user

process state

elapsed runtime

command
```

Do not send unrelated sensitive process arguments to an unapproved AI tool.

---

# 82. STRUCTURED AI REQUEST

Example:

```text
Objective:
Identify the next safe investigation steps for high CPU.

Environment:
Disposable Linux lab.

Observed:
Application is slow.
CPU utilization is high.

Evidence:
<sanitized ps/top output>

Constraint:
Do not kill or restart any process yet.

Task:
Generate up to five hypotheses.
For each hypothesis, state the evidence that would support
or weaken it.
```

---

# 83. REVIEW AI RESPONSE

Reject suggestions that immediately say:

```text
kill -9 <pid>
```

without first establishing:

```text
process identity

ownership

expected workload

progress

dependencies

impact
```

---

# 84. INDEPENDENT VERIFICATION

The learner must independently determine:

```text
which process consumes CPU

whether it belongs to the application
```

# 118. DELIBERATELY CONVINCING BUT INCORRECT AI RECOMMENDATION

This exercise is mandatory.

Scenario:

```text
A Kubernetes application is unreachable from another machine.

Evidence collected:

Pod is Running.

Application responds successfully from inside the Pod.

Application responds through the Service from another Pod.

Service endpoints exist.

External access still fails.
```

AI responds:

```text
The application is probably bound only to 127.0.0.1 inside
the container. Change it to 0.0.0.0 and redeploy.
```

This sounds plausible.

It must not be executed yet.

---

# 119. WHY THE RECOMMENDATION IS CONVINCING

A loopback-only bind can indeed prevent external access in some architectures.

The recommendation therefore sounds technically reasonable.

But the existing evidence says:

```text
another Pod successfully reaches the application through the Service
```

That evidence strongly contradicts the claim that the application is reachable only from its own loopback interface.

---

# 120. PROVE THE RECOMMENDATION WRONG

Do not reject it merely because this curriculum says it is wrong.

Collect evidence.

Inspect listening sockets inside the appropriate environment where permitted.

Inspect:

```text

Endpoints / EndpointSlices

target port

application listener
```

Confirm the actual bind behavior.

The learner must establish:

```text

        ↓
Prediction
        ↓
Observed Evidence
        ↓
Prediction Contradicted
        ↓
Hypothesis Rejected
```

# 186. DIFFERENCE BETWEEN EXPLANATION AND APPROVAL

AI may explain a Terraform plan correctly.

That does not mean:

```text
plan should be applied.
```

Explanation answers:

```text
What does this mean?
```

Approval answers:

```text
Should this change proceed under our requirements and controls?
```

Those are different decisions.

---

# 187. DIFFERENCE BETWEEN DIAGNOSIS AND REMEDIATION

AI may correctly identify:

```text
disk is full
```

but propose a dangerous remediation:

```text
delete everything under /var/log
```

Diagnosis can be correct while remediation is wrong.

Review both separately.

---

# 188. DIFFERENCE BETWEEN CORRECT COMMAND AND CORRECT ACTION

A command can be syntactically valid.

Example:

```bash
kubectl delete pod <pod-name>
```

That does not establish that deleting the Pod is the right action.

Engineering decisions require context.

---

# 189. DIFFERENCE BETWEEN POSSIBLE AND APPROPRIATE

AI may identify something technically possible.

Example:

```text
Make service public.
```

The relevant question is:

```text
Should this service be public?
```

Architecture and security requirements decide.

# 194. AI SHOULD NOT INVENT INCIDENT FACTS

# 246. AUTOMATION BIAS

Automation bias is the tendency to trust automated recommendations too readily.

In DevOps this can appear as:

```text
AI said it

scanner said it

pipeline said it

dashboard said it
```

Each system provides evidence.

None eliminates engineering judgment.
