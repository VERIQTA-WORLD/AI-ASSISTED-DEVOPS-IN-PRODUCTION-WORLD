# PART 14: HELM AND APPLICATION PACKAGING

## Goal

Understand how Kubernetes applications can be packaged, configured, distributed, installed, upgraded, inspected, validated, and rolled back using Helm without losing sight of the Kubernetes resources Helm generates underneath.

By the end of this Part, you should be able to take the Kubernetes application developed through the previous Parts and transform its separate manifests into a maintainable Helm chart.

The objective is not merely to learn commands such as:

```bash
helm install
helm upgrade
helm rollback
```

The objective is to understand the complete release path:

```text
Application Requirements
↓
Helm Chart
+
Configuration Values
↓
Template Rendering
↓
Generated Kubernetes Manifests
↓
Kubernetes API
↓
Kubernetes Resources
↓
Controllers
↓
Pods
↓
Application
↓
Operational Verification
```

The central mental model is:

```text
Chart
+
Values
↓
Template Rendering
↓
Kubernetes Manifests
↓
Kubernetes API
↓
Resources
```

A more complete production model is:

```text
Application Source
↓
Container Image
↓
Image Registry
        +
Helm Chart
↓
Chart Registry / Repository
        +
Environment Values
↓
Rendering
↓
Validation
↓
Release
↓
Kubernetes API
↓
Deployment / Service / ConfigMap / PVC / Other Resources
↓
Controllers
↓
Pods
↓
Application
↓
Verification
```

The most important principle in this Part is:

```text
Helm does not replace Kubernetes.

Helm generates and manages Kubernetes resources.
```

---

# 1. THE PROBLEM HELM IS TRYING TO SOLVE

A Kubernetes application rarely consists of one manifest.

A production-style application may require:

```text
Deployment
Service
ConfigMap
Secret references
ServiceAccount
Ingress or Gateway resources
PersistentVolumeClaim
HorizontalPodAutoscaler
PodDisruptionBudget
NetworkPolicy
RBAC resources
Jobs
CronJobs
```

Without packaging, a repository might contain:

```text
kubernetes/
├── deployment.yaml
├── service.yaml
├── configmap.yaml
├── pvc.yaml
├── ingress.yaml
├── serviceaccount.yaml
└── networkpolicy.yaml
```

That can work.

The problem appears when the same application must be installed repeatedly with controlled differences.

For example:

```text
Development
├── replicas: 1
├── APP_ENV: development
├── smaller resources
└── development hostname

Staging
├── replicas: 2
├── APP_ENV: staging
├── moderate resources
└── staging hostname

Production
├── replicas: 4
├── APP_ENV: production
├── larger resources
└── production hostname
```

Copying all Kubernetes manifests for every environment creates duplication:

```text
deployment-dev.yaml
deployment-staging.yaml
deployment-production.yaml

service-dev.yaml
service-staging.yaml
service-production.yaml

configmap-dev.yaml
configmap-staging.yaml
configmap-production.yaml
```

Now a common change might need to be repeated across many files.

That creates opportunities for:

```text
Configuration drift

Copy-and-paste errors

Environment inconsistencies

Missed security changes

Different labels

Different probe configuration

Different resource settings

Difficult release tracking
```

Helm provides one approach to solving this problem.

---

# 2. HELM'S CORE ABSTRACTION

Helm separates:

```text
Application Structure
```

from:

```text
Configurable Values
```

The reusable application structure lives in templates.

Environment or installation-specific configuration is supplied through values.

Conceptually:

```text
Reusable Templates
+
Environment Configuration
↓
Rendered Kubernetes Resources
```

For example:

```text
deployment.yaml template
+
replicaCount: 3
+
image.tag: "2.4.1"
↓
Deployment manifest
```

Helm then submits the resulting resources to Kubernetes during release operations.

---

# 3. HELM IS NOT A KUBERNETES RUNTIME

Helm does not schedule Pods.

Helm does not run containers.

Helm does not implement Services.

Helm does not implement persistent storage.

Helm does not replace:

```text
API Server
Scheduler
Controllers
Kubelet
Container Runtime
CNI
CSI
```

The runtime path remains Kubernetes:

```text
Helm
↓
Rendered Kubernetes Objects
↓
Kubernetes API
↓
Controllers / Scheduler / Kubelet
↓
Application
```

If a Pod enters:

```text
CrashLoopBackOff
```

the underlying failure is still investigated using Kubernetes workload troubleshooting.

If a Service has no endpoints, Helm does not change the networking model learned earlier.

If a PVC remains Pending, Helm does not change the Kubernetes storage model.

This is why Kubernetes fundamentals must come before Helm.

---

# 4. HELM IS NOT MAGIC YAML

A Helm template might contain:

```yaml
replicas: {{ .Values.replicaCount }}
```

After rendering, Kubernetes receives something similar to:

```yaml
replicas: 3
```

Kubernetes does not receive:

```text
.Values.replicaCount
```

That expression belongs to Helm's template layer.

The Kubernetes API receives the generated Kubernetes manifest.

Therefore, when troubleshooting Helm, always ask:

```text
What did Helm actually render?
```

---

# 5. THE FOUR IMPORTANT OBJECTS

A useful beginner-to-production mental model is:

```text
Chart
Values
Rendered Manifest
Release
```

These are related but different.

## Chart

A reusable application package.

## Values

Configuration supplied to that chart.

## Rendered Manifest

The Kubernetes YAML generated from the chart and values.

## Release

An installed instance of the chart managed through Helm.

Do not collapse these concepts into one.

---

# 6. CHART

A chart is a Helm package containing the information needed to generate Kubernetes resources.

Conceptually:

```text
Chart
├── Metadata
├── Default Values
├── Templates
├── Optional Dependencies
├── Optional Schema
└── Documentation
```

A chart is not itself a running application.

It is an application packaging definition.

---

# 7. RELEASE

Suppose the chart is named:

```text
veriqta-app
```

You might install it as:

```text
veriqta-development
```

and separately as:

```text
veriqta-staging
```

and:

```text
veriqta-production
```

These can be different Helm releases created from the same chart.

Conceptually:

```text
veriqta-app chart
        │
        ├── development values
        │       ↓
        │   development release
        │
        ├── staging values
        │       ↓
        │   staging release
        │
        └── production values
                ↓
            production release
```

The chart is reusable.

The releases are installations.

---

# 8. CHART VERSION AND APPLICATION VERSION

These should not be confused.

A chart has a chart version.

It can also describe an application version.

Example:

```yaml
apiVersion: v2
name: veriqta-app
version: 0.3.0
appVersion: "2.1.4"
```

Here:

```text
0.3.0
```

is the chart version.

```text
2.1.4
```

is application-version metadata.

They can change independently.

For example, you might improve:

```text
Resource limits
Probe defaults
Labels
NetworkPolicy templates
```

without changing the application binary itself.

That could justify a chart version change even when the application version remains unchanged.

---

# 9. CHART DIRECTORY STRUCTURE

A typical application chart can contain:

```text
veriqta-app/
├── Chart.yaml
├── values.yaml
├── values.schema.json
├── README.md
├── charts/
├── crds/
└── templates/
    ├── _helpers.tpl
    ├── deployment.yaml
    ├── service.yaml
    ├── configmap.yaml
    ├── serviceaccount.yaml
    ├── ingress.yaml
    └── NOTES.txt
```

Not every chart requires every file.

Understand why each exists before adding it.

---

# 10. `CHART.YAML`

`Chart.yaml` contains chart metadata.

A minimal application chart might begin with:

```yaml
apiVersion: v2
name: veriqta-app
description: Kubernetes application chart for the VERIQTA training application
type: application
version: 0.1.0
appVersion: "1.0.0"
```

Important fields include:

```text
apiVersion
name
version
```

Additional metadata can describe:

```text
description
type
appVersion
kubeVersion
dependencies
sources
keywords
```

Use metadata deliberately rather than treating `Chart.yaml` as boilerplate.

---

# 11. `VALUES.YAML`

`values.yaml` contains default configuration for the chart.

Example:

```yaml
replicaCount: 2

image:
  repository: example/veriqta-app
  tag: "1.0.0"
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80
  targetPort: 8080

config:
  appName: veriqta-app
  appEnv: default
  logLevel: info

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi
```

The purpose is not to move every YAML field into `values.yaml`.

The purpose is to expose configuration that users of the chart genuinely need to control.

---

# 12. DO NOT TEMPLATE EVERYTHING

A common chart-design mistake is turning every Kubernetes field into a value.

That produces charts such as:

```text
deploymentApiVersion:
deploymentKind:
deploymentMetadataName:
deploymentSelector:
deploymentStrategyType:
containerName:
containerPortName:
```

This often makes the chart harder to understand than the Kubernetes YAML it replaced.

Prefer:

```text
Stable implementation details
→ remain in templates

Meaningful deployment choices
→ become values
```

Good chart interfaces are intentionally constrained.

---

# 13. VALUES ARE AN INTERFACE

Treat chart values like an API.

A chart user should understand:

```text
What can I configure?

Which values are required?

Which values are optional?

What are the defaults?

What types are expected?

Which combinations are invalid?

Which values are security-sensitive?
```

A poorly designed values interface makes the chart difficult to operate safely.

---

# 14. TEMPLATES

Files under:

```text
templates/
```

are rendered by Helm's template engine.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
```

If:

```yaml
replicaCount: 3
```

and the release is:

```text
veriqta-production
```

the rendered result includes:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: veriqta-production
spec:
  replicas: 3
```

That rendered YAML is what matters to Kubernetes.

---

# 15. HELM TEMPLATE LANGUAGE

Helm templates use Go template syntax together with Helm-provided objects and functions.

You will commonly encounter:

```text
.Values
.Release
.Chart
.Capabilities
.Template
.Files
```

At this level, the most important are:

```text
.Values
.Release
.Chart
```

Do not try to memorize the entire template language.

Learn to read what data a template consumes and what YAML it produces.

---

# 16. `.VALUES`

`.Values` provides access to configuration values.

If `values.yaml` contains:

```yaml
image:
  repository: example/veriqta-app
  tag: "1.2.0"
```

the template can reference:

```text
.Values.image.repository
```

and:

```text
.Values.image.tag
```

Example:

```yaml
image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

Rendered:

```yaml
image: "example/veriqta-app:1.2.0"
```

---

# 17. `.RELEASE`

`.Release` exposes information about the current Helm release.

Common examples include:

```text
.Release.Name
.Release.Namespace
.Release.Revision
.Release.IsInstall
.Release.IsUpgrade
```

This allows templates to incorporate release context.

Example:

```yaml
metadata:
  name: {{ .Release.Name }}
```

Do not overuse release-specific data when stable chart-generated naming would be clearer.

---

# 18. `.CHART`

`.Chart` provides chart metadata.

For example:

```text
.Chart.Name
.Chart.Version
.Chart.AppVersion
```

This is useful for standardized labels and metadata.

Remember:

```text
Chart.Version
≠
Chart.AppVersion
```

---

# 19. QUOTING VALUES

YAML typing matters.

Consider:

```yaml
value: {{ .Values.config.appEnv }}
```

versus:

```yaml
value: {{ .Values.config.appEnv | quote }}
```

The second explicitly renders the result as a quoted string.

Chart authors should understand expected Kubernetes field types and render accordingly.

Blindly quoting everything is also incorrect because Kubernetes fields can require:

```text
Integer
Boolean
Object
List
```

Template output must match the Kubernetes API schema.

---

# 20. PIPELINES AND FUNCTIONS

Helm templates can transform values using functions.

For example:

```text
value
↓
function
↓
rendered output
```

A common template pattern uses pipelines:

```text
.Values.config.appEnv | quote
```

The important engineering principle is not the syntax itself.

It is:

```text
Input Value
↓
Template Logic
↓
Rendered Kubernetes Value
```

When something is wrong, inspect every stage.

---

# 21. DEFAULT VALUES

Templates can provide defaults.

Conceptually:

```text
User supplied value?
├── Yes → use it
└── No  → use default
```

However, defaults should not hide required production decisions.

For example, silently defaulting a critical storage class or external hostname can create a valid but incorrect deployment.

Use defaults where they are genuinely safe.

---

# 22. REQUIRED VALUES

Some configuration should not have a meaningless default.

A chart can deliberately fail rendering when required information is missing.

Conceptually:

```text
Required value present?
├── Yes → continue rendering
└── No  → fail clearly
```

This is preferable to producing a manifest that is syntactically valid but operationally dangerous.

Examples might include environment-specific values such as:

```text
External hostname

Required service endpoint

Required non-secret identifier
```

depending on the application.

---

# 23. CONDITIONAL TEMPLATES

Charts can conditionally render resources.

Example concept:

```text
ingress.enabled = true
↓
Render ingress resource
```

```text
ingress.enabled = false
↓
Do not render ingress resource
```

This can be useful for genuinely optional capabilities.

Do not use conditionals to create an impossible-to-understand maze of application architectures inside one chart.

---

# 24. LOOPS

Templates can generate repeated structures from values.

For example:

```yaml
config:
  allowedOrigins:
    - https://example-a.invalid
    - https://example-b.invalid
```

can be rendered into an appropriate list or repeated configuration structure.

Loops are useful when the data itself is naturally repeated.

Avoid generating complexity merely to demonstrate template syntax.

---

# 25. NAMED TEMPLATES AND HELPERS

Charts commonly use:

```text
templates/_helpers.tpl
```

for reusable template fragments.

Examples include:

```text
Resource names
Common labels
Selector labels
Chart labels
Service account names
```

Instead of duplicating the same label logic in:

```text
Deployment
Service
ConfigMap
Ingress
```

a helper can centralize it.

---

# 26. HELPER FUNCTIONS SHOULD IMPROVE CONSISTENCY

A good helper can ensure that:

```text
Deployment labels
=
Service selectors
=
Monitoring labels
```

where appropriate.

This reduces copy-and-paste errors.

A helper should not hide so much logic that engineers cannot understand the rendered object.

The final manifest must remain inspectable.

---

# 27. LABEL CONSISTENCY

Helm charts should generate predictable labels.

Useful label dimensions can include:

```text
Application identity

Release identity

Application version

Chart version

Managing tool
```

The exact label strategy should align with the organization's Kubernetes conventions.

Selectors require special care because changing immutable or identity-sensitive selectors can create failed upgrades or replacement requirements.

---

# 28. RENDERING

Rendering transforms:

```text
Templates
+
Values
```

into:

```text
Kubernetes YAML
```

This is the most important Helm operation to understand.

If the rendered manifest is wrong, Kubernetes cannot make it correct.

---

# 29. LOCAL RENDERING

Use:

```bash
helm template <release-name> <chart-path>
```

For example:

```bash
helm template veriqta-lab ./veriqta-app
```

This renders templates locally without installing the release.

Inspect the output.

Ask:

```text
Are resource names correct?

Are namespaces correct?

Are labels correct?

Are selectors correct?

Is the image correct?

Are probes correct?

Are requests and limits correct?

Are storage references correct?

Are configuration values correct?
```

---

# 30. RENDERING IS A TROUBLESHOOTING TOOL

Suppose a Deployment contains:

```yaml
replicas: 0
```

Do not immediately inspect the Kubernetes scheduler.

Trace:

```text
Rendered Deployment
↓
Template
↓
Value Source
```

You might discover:

```text
production-values.yaml
↓
replicaCount: 0
```

The problem exists before Kubernetes scheduling begins.

---

# 31. VALUES PRECEDENCE

Values can come from multiple sources.

Conceptually:

```text
Chart Defaults
↓ overridden by
Supplied Values Files
↓ overridden by
More Specific Supplied Values
↓ overridden by
Command-Line Overrides
```

Exact precedence and command behavior should be understood when multiple value sources are combined.

The practical lesson is:

```text
Final Effective Values
```

may not equal:

```text
values.yaml
```

alone.

---

# 32. ENVIRONMENT-SPECIFIC VALUES

A practical repository might contain:

```text
helm/
└── veriqta-app/
    ├── Chart.yaml
    ├── values.yaml
    ├── values-development.yaml
    ├── values-staging.yaml
    ├── values-production.yaml
    └── templates/
```

Another organization may keep environment configuration outside the chart repository.

The exact repository strategy can vary.

The important principle is:

```text
Reusable Chart
+
Explicit Environment Configuration
```

rather than duplicated charts for every environment.

---

# 33. DEFAULT VALUES SHOULD BE SAFE

A default values file should not silently point at production systems.

Avoid defaults such as:

```text
production database endpoint

production hostname

production credentials

production storage class
```

unless the chart is intentionally production-specific and the decision is explicit.

Safer defaults make accidental installations less dangerous.

---

# 34. DEVELOPMENT VALUES

Development may use:

```yaml
replicaCount: 1

config:
  appEnv: development

resources:
  requests:
    cpu: 50m
    memory: 64Mi
```

This is only an example.

Development values should reflect actual development requirements rather than blindly being "smaller production."

---

# 35. STAGING VALUES

Staging should normally preserve enough production similarity to test meaningful release behavior.

For example:

```text
Same chart

Same Kubernetes resource structure

Same configuration interface

Comparable security model

Comparable probes

Comparable release process
```

while potentially differing in:

```text
Capacity

Replica count

Hostnames

External dependencies

Data

Cost
```

The closer staging is to the production operating model, the more useful release validation can become.

---

# 36. PRODUCTION VALUES

Production values should be deliberate and reviewed.

They may define:

```text
Replica count

Immutable image reference strategy

Resource requests

Resource limits

Ingress/Gateway configuration

Storage configuration

Availability settings

Autoscaling

Production endpoints

Observability settings
```

Production should not be an accidental extension of development defaults.

---

# 37. WRONG ENVIRONMENT VALUES

One of the most dangerous Helm mistakes is:

```text
Correct chart
+
Wrong values
=
Wrong deployment
```

For example:

```text
Production release
+
Development values
```

could produce:

```text
Wrong hostname

Wrong dependency endpoint

Too few replicas

Insufficient resources

Wrong storage class

Debug settings

Wrong feature configuration
```

The templates can render perfectly.

The release can install successfully.

The application can still be operationally wrong.

---

# 38. VALUES FILE NAMES ARE NOT SECURITY BOUNDARIES

A file named:

```text
values-production.yaml
```

does not prove that it contains safe production configuration.

The filename is only a convention.

Review the actual values.

---

# 39. `--SET`

Small values can be overridden from the command line.

Example:

```bash
helm template veriqta-lab ./veriqta-app \
  --set replicaCount=3
```

This can be convenient for:

```text
Testing

Automation

Small explicit overrides
```

But large collections of command-line values quickly become difficult to review and reproduce.

For substantial environment configuration, explicit version-controlled values files are often easier to audit.

---

# 40. REPRODUCIBILITY

A release should be reconstructable from known inputs.

Ideally, you can identify:

```text
Chart version

Application image

Values

Environment

Release revision

Deployment time

Change reference
```

Without this information, reproducing or investigating a deployment becomes harder.

---

# 41. IMAGE VERSIONING INSIDE HELM

A chart should not hide which application artifact it deploys.

Prefer explicit image configuration:

```yaml
image:
  repository: example/veriqta-app
  tag: "1.4.2"
```

or an approved immutable-reference strategy.

Avoid uncontrolled mutable references for production releases where reproducibility matters.

A chart version and an image version are separate release inputs.

---

# 42. IMMUTABLE APPLICATION REFERENCES

A production release is easier to reason about when the container image can be identified precisely.

Conceptually:

```text
Release Revision
↓
Known Chart Version
+
Known Values
+
Known Image Artifact
```

This improves:

```text
Reproducibility

Auditability

Incident investigation

Rollback reasoning
```

---

# 43. `VALUES.SCHEMA.JSON`

Charts can define a schema for values using:

```text
values.schema.json
```

This can enforce expectations such as:

```text
Required fields

Allowed types

Patterns

Ranges

Enumerations
```

For example, a schema can reject:

```text
replicaCount: "three"
```

when an integer is required.

This moves some failures earlier in the release process.

---

# 44. VALIDATION SHOULD FAIL EARLY

Prefer:

```text
Bad Configuration
↓
Validation Failure
```

over:

```text
Bad Configuration
↓
Rendered Manifest
↓
Kubernetes
↓
Broken Runtime
↓
Incident
```

Not every operational mistake can be caught by schema validation, but obvious invalid inputs should be rejected as early as practical.

---

# 45. VALIDATION LAYERS

A useful model is:

```text
Chart Structure
↓
Template Rendering
↓
Values Validation
↓
Generated YAML
↓
Kubernetes Schema / API Validation
↓
Resource Creation
↓
Controller Reconciliation
↓
Pod Readiness
↓
Application Health
```

Passing one layer does not prove the next.

---

# 46. `HELM LINT`

Use:

```bash
helm lint ./veriqta-app
```

Linting can detect a range of chart problems.

A successful lint is useful evidence.

It is not proof that:

```text
The application will deploy.

The image exists.

The Pod will become Ready.

The Service selector is correct.

The database is reachable.

The application is healthy.
```

Therefore:

```text
Lint Success
≠
Release Success
```

---

# 47. TEMPLATE VALIDATION

Render locally:

```bash
helm template veriqta-lab ./veriqta-app
```

For debugging:

```bash
helm template veriqta-lab ./veriqta-app --debug
```

Inspect the generated resources.

This is often the fastest way to answer:

```text
What exactly will Helm generate?
```

---

# 48. CLIENT-SIDE AND SERVER-AWARE DRY RUNS

Helm provides dry-run capabilities that can help inspect release behavior before persistence.

The exact available modes and flags can vary by Helm version.

Current Helm versions distinguish client-side simulation from server-connected simulation in relevant commands.

The operational principle is:

```text
Render Locally
↓
Validate as Much as Possible
↓
Optionally Validate Against Target Cluster
↓
Only Then Perform Real Change
```

Do not blindly copy dry-run flags from old tutorials without checking the installed Helm version.

---

# 49. RENDERING SUCCESS DOES NOT PROVE API ACCEPTANCE

A template can render valid YAML that Kubernetes rejects.

For example:

```yaml
apiVersion: apps/v1
kind: Deployment
```

might be structurally valid YAML while containing an invalid Kubernetes field.

Therefore:

```text
Template Engine Success
≠
Kubernetes API Acceptance
```

---

# 50. API ACCEPTANCE DOES NOT PROVE WORKLOAD HEALTH

Kubernetes may accept:

```text
Deployment
Service
ConfigMap
```

and the Deployment controller may create Pods.

The Pods can still fail because:

```text
Image does not exist

Configuration is wrong

Secret is missing

Probe fails

Application crashes

Storage cannot mount

Dependency unavailable
```

Therefore:

```text
API Accepted Resources
≠
Healthy Application
```

---

# 51. RELEASE SUCCESS DOES NOT PROVE BUSINESS SUCCESS

Even if Helm reports a deployed release, verify the intended outcome.

Ask:

```text
Are Pods Ready?

Is rollout complete?

Are Services populated?

Can expected traffic reach the application?

Are dependencies healthy?

Are errors normal?

Are important metrics normal?

Can the application perform its intended function?
```

The release tool is not the final source of application truth.

---

# 52. INSTALLATION

A basic installation has the form:

```bash
helm install <release-name> <chart>
```

For a local chart:

```bash
helm install veriqta-lab ./veriqta-app
```

Before installation, know:

```text
Current cluster

Target namespace

Release name

Chart version

Values

Expected resources

Expected image

Expected storage impact
```

---

# 53. VERIFY KUBERNETES CONTEXT FIRST

Before a real installation:

```bash
kubectl config current-context
```

Then verify the target namespace and environment.

A perfectly correct Helm command executed against the wrong cluster is still a production failure.

---

# 54. NAMESPACE AWARENESS

A release belongs to a Kubernetes namespace context.

Be explicit.

For example:

```bash
helm install veriqta-lab ./veriqta-app \
  --namespace veriqta-helm-lab
```

Do not depend on an assumed namespace when environment boundaries matter.

---

# 55. RELEASE NAME MATTERS

Release names can influence generated resource names.

A naming strategy should be predictable.

For example:

```text
veriqta-dev

veriqta-staging

veriqta-prod
```

or another organization-approved convention.

Do not allow naming conventions to become the only protection against deploying to the wrong environment.

---

# 56. INSPECT RELEASES

Use:

```bash
helm list -n <namespace>
```

This shows releases visible in that namespace.

Ask:

```text
Which release?

Which namespace?

Which chart?

Which revision?

Which status?
```

# 57. RELEASE STATUS

Inspect:

```bash
helm status <release-name> -n <namespace>
```

Status can provide:

```text
Release state

Revision

Namespace

Deployment information

Release notes

Related resources
```

Use it as one evidence source.

Then inspect Kubernetes itself.

---

# 58. INSPECT INSTALLED MANIFEST

Use:

```bash
helm get manifest <release-name> -n <namespace>
```

This retrieves the manifest associated with the release.

This is extremely useful when comparing:

```text
What chart source says now
```

with:

```text
What release revision generated
```

and:

```text
What Kubernetes currently contains
```

---

# 59. INSPECT RELEASE VALUES

Use:

```bash
helm get values <release-name> -n <namespace>
```

Current Helm also supports retrieving computed values through the appropriate command option.

This helps answer:

```text
Which values actually contributed to this release?
```

Be careful: release values can contain sensitive information if a chart was designed poorly.

Do not dump them casually into public logs or tickets.

# 60. HELM RELEASE HISTORY

Helm maintains release revisions.

Inspect:

```bash
helm history <release-name> -n <namespace>
```

Conceptually:

```text
Revision 1
Initial installation

Revision 2
Application upgrade

Revision 3
Configuration change

Revision 4
Rollback or another upgrade
```

History provides release context.

It is not a complete application audit trail by itself.

---

# 61. REVISION

A release revision identifies a Helm release state in its history.

Revision:

```text
1
```

might be the initial install.

After an upgrade:

```text
2
```

becomes the new revision.

A rollback itself can produce another revision rather than erasing history.

Think:

```text
Release History
=
Sequence of Release States
```

not:

```text
Rollback
=
Time Machine That Deletes History
```

---

# 62. UPGRADES

A Helm upgrade reconciles an existing release using a chart and values.

Basic form:

```bash
helm upgrade <release-name> <chart>
```

Example:

```bash
helm upgrade veriqta-lab ./veriqta-app \
  -n veriqta-helm-lab
```

But never treat upgrade as:

```text
Run command
↓
Hope
```

The safer model is:

```text
Change
↓
Render
↓
Review
↓
Validate
↓
Upgrade
↓
Observe Kubernetes rollout
↓
Verify application
```

---

# 63. REVIEW BEFORE UPGRADE

Before applying an upgrade, determine:

```text
Which chart changed?

Which values changed?

Which resources will change?

Will immutable fields change?

Will resources be recreated?

Will storage change?

Will selectors change?

Will Services change?

Will security configuration change?

Will replicas change?

Will image version change?

Could the application require migration?
```

Helm does not remove the need for change review.

---

# 64. CHART CHANGE VERSUS VALUES CHANGE

An upgrade can result from:

```text
New chart templates
```

or:

```text
New values
```

or both.

These should be distinguished during troubleshooting.

Example:

```text
Same chart
+
new image tag
```

is different from:

```text
new chart
+
same image tag
```

Both can produce a new release revision.

---

# 65. `REUSE-VALUES` REQUIRES CARE

Upgrade behavior can be influenced by whether previous values are reused, reset, or replaced/merged with newly supplied values.

Do not use value-reuse options mechanically.

A chart version may introduce:

```text
New defaults

Removed values

Renamed values

Changed structures
```

Reusing old values without understanding the new chart interface can produce surprising results.

Always review effective values.

---

# 66. ROLLBACK

Helm can roll a release back to a previous revision.

Basic form:

```bash
helm rollback <release-name> <revision> \
  -n <namespace>
```

For example:

```bash
helm rollback veriqta-lab 1 \
  -n veriqta-helm-lab
```

This instructs Helm to create a new release state based on a previous revision.

It does not reverse time outside Helm.

---

# 67. ROLLBACK IS NOT UNIVERSAL RECOVERY

This distinction is critical:

```text
Helm Rollback
≠
Complete System Rollback
```

Helm can restore Kubernetes release configuration from a prior revision.

It cannot necessarily undo:

```text
Database schema migration

Data deletion

External API changes

Message processing

Object-storage mutation

Cloud infrastructure changes outside the release

External secret rotation

User transactions
```

---

# 68. STATEFUL APPLICATION ROLLBACK

Suppose:

```text
Release 5
↓
Application 5
↓
Database migration changes schema
```

Then you execute:

```text
helm rollback
```

Helm may restore an earlier Deployment specification.

But:

```text
Database schema
```

may remain changed.

The old application might no longer understand it.

Therefore:

```text
Application Rollback
```

and:

```text
Data Rollback
```

are different operations.

This connects directly to the storage and data-lifecycle principles from Part 13.

---

# 69. ROLLBACK MUST BE DESIGNED

Before a production upgrade, ask:

```text
Can the application binary roll back?

Is the database migration backward compatible?

Can configuration roll back?

Are persistent data formats compatible?

Are external dependencies compatible?

Will old Pods understand new data?

Will new Pods understand old data?
```

Rollback is an application architecture concern, not merely a Helm feature.

---

For example:

```text

✗
```

or:

```text

✗
```

or:

```text
Resource Creation
✓

Pod Readiness
✗
```

or:

```text
Pods Ready
✓

Application Function
✗
```

These are different failure classes.

# 71. RELEASE FAILURE MODEL

Use:

```text

↓

↓

↓

↓

↓

↓

↓
```

```text

```

and:


# 72. TEMPLATE FAILURE

Example symptoms:

```text

unexpected template expression

type mismatch

template parsing error
```

Investigate:

```text
Template

Expected data structure

Helper templates

Functions

Conditionals
```

Do not troubleshoot the Kubernetes scheduler.

No Kubernetes object may have been generated yet.

---

# 73. INVALID VALUES

Suppose a chart expects:

```yaml
replicaCount: 3
```

but receives:

```yaml
replicaCount:
  minimum: 3
```

The data structure is different.

Template logic may fail or produce invalid output.

Investigate:

```text
Expected values schema
↓
Provided values
↓
Template consumption
```

---

# 74. MISSING VALUE

Suppose:

```text
.Values.image.repository
```

is expected but missing.

Possible outcomes depend on template design:

```text
Rendering failure

Empty output

Invalid image reference

Unexpected default
```

Good chart design should make critical missing values fail clearly.

---

# 75. GENERATED INVALID MANIFEST

A chart can render YAML that is syntactically valid but invalid for Kubernetes.

For example:

```yaml
replicas: "three"
```

might produce valid YAML but an invalid Kubernetes field type.

The troubleshooting path is:

```text
Rendered Manifest
↓
Kubernetes Schema
↓
Rejected Field
```

Fix the chart or values that generated the field.

---

# 76. VALID MANIFEST, BROKEN APPLICATION

Suppose Helm generates:

```yaml
image: example/veriqta-app:does-not-exist
```

The manifest may be accepted.

Then the Pod enters:

```text
ImagePullBackOff
```

Helm templating succeeded.

Kubernetes API acceptance succeeded.

Container startup failed.

This belongs to the Kubernetes workload layer.

---

# 77. VALID RELEASE, WRONG SERVICE SELECTOR

Helm may successfully install:

```text
Deployment
Service
```

but a templating inconsistency could produce:

```text
Deployment label:
app=veriqta

Service selector:
app=veriqta-api
```

The Service can have no matching endpoints.

The release can appear installed.

Traffic fails.

Inspect:

```text
Rendered labels
Selectors
EndpointSlices
Pods
```

Helm does not change the Service-selection model learned in Part 12.

---

# 78. VALUES VALIDATION DOES NOT REPLACE KUBERNETES VALIDATION

A JSON schema might prove:

```text
service.port
=
integer
```

but it cannot automatically prove:

```text
Service selector matches Pod labels.
```

Validation operates at different layers.

Use multiple validation methods.

# 79. DEPENDENCIES

A chart can depend on other charts.

Dependencies are declared in chart metadata and resolved into the chart's dependency structure.

Conceptually:

```text
Parent Chart
├── Application
├── Dependency A
└── Dependency B
```

Dependencies can be useful when components have meaningful lifecycle coupling.

They should not be used merely because two systems communicate.

---

# 80. DEPENDENCY EXAMPLE

Suppose an application chart includes another chart as a dependency.

The parent chart may provide configuration for that dependency.

Conceptually:

```text
Parent Values
↓
Dependency-Specific Values
↓
Dependency Chart
↓
Dependency Resources
```

The resulting resources participate in the overall Helm release.

---

# 81. DEPENDENCY MANAGEMENT

Relevant commands include:

```bash
helm dependency list ./veriqta-app
```

and, where appropriate:

```bash
helm dependency update ./veriqta-app
```

or:

```bash
helm dependency build ./veriqta-app
```

Understand the difference between updating dependency resolution and rebuilding from locked dependency information before using these in controlled delivery workflows.

---

# 82. `CHART.LOCK`

Dependency resolution can produce:

```text
Chart.lock
```

This supports repeatability by recording resolved dependency information.

Treat dependency changes as release changes.

Review:

```text
Dependency name

Version

Source

Resulting resources

Security implications
```

Do not casually update dependencies during an unrelated production release.

---

# 83. DEPENDENCIES EXPAND BLAST RADIUS

If a release manages:

```text
Application
+
Database dependency
+
Cache dependency
```

an upgrade to the release can affect multiple systems.

Ask:

```text
Do these components truly share a lifecycle?

Should they be independently upgraded?

Who owns them?

Do they have separate recovery requirements?
```

Packaging convenience should not override sound service boundaries.

# 91. SECRET-HANDLING CONSIDERATIONS

Helm values can contain sensitive data.

That creates risks because values may appear in:

```text
Values files

Shell history

CI logs

Release information

Rendered manifests

Git repositories

Debug output
```

Do not assume:

```text
Value passed through Helm
=
Secret safely protected
```

---

# 92. DO NOT STORE REAL SECRETS IN ORDINARY VALUES FILES

Avoid:

```yaml
database:
  password: actual-production-password
```

inside a normal Git-tracked values file.

Even if the template creates a Kubernetes Secret, the sensitive value has already existed in the values input and may become part of release information or other operational surfaces.

Use the organization's approved secret-management mechanism.

---

# 93. BASE64 STILL IS NOT ENCRYPTION

If a Helm template generates:

```yaml
data:
  password: <base64-value>
```

the security model has not changed.

As established in Part 13:

```text
Base64
≠
Encryption
```

Helm templating does not turn base64 into a secret-management system.

---

# 94. PREFER SECRET REFERENCES WHERE APPROPRIATE

A chart can be designed to reference an externally managed Kubernetes Secret rather than requiring the secret value itself.

Conceptually:

```text
Secret Management System
↓
Kubernetes Secret
        +
Helm Values
↓
existingSecretName
↓
Deployment references Secret
```

This can reduce the amount of sensitive material Helm itself must process.

The exact implementation depends on the organization's secret architecture.

---

# 95. SECRET NAMES CAN BE VALUES

For example:

```yaml
secrets:
  existingSecret: veriqta-app-runtime
```

Template:

```yaml
envFrom:
  - secretRef:
      name: {{ .Values.secrets.existingSecret | quote }}
```

Helm receives the Secret's identifier rather than the Secret's confidential value.

That does not eliminate all security concerns, but it can reduce secret exposure.

# 99. CUSTOM RESOURCE DEFINITIONS

Charts can contain:

```text
crds/
```

for CustomResourceDefinitions.

CRDs have special lifecycle considerations in Helm.

They are not ordinary templated resources.

At this level, the important lesson is:

```text
CRD Lifecycle
≠
Ordinary Resource Lifecycle
```

Never assume ordinary install, upgrade, rollback, and deletion behavior applies identically to CRDs.

---

# 100. CRD CHANGES ARE HIGH-RISK

A CRD can define an API used by many custom resources.

Changing or deleting it can have cluster-wide consequences.

Before adopting a chart containing CRDs, determine:

```text
Which CRDs?

Who owns them?

Are they already installed?

Which version?

Which controllers use them?

How are upgrades managed?

What happens to existing custom resources?
```

Do not treat CRDs as an invisible implementation detail.

---

# 101. HELM HOOKS

Charts can define hooks that run around release lifecycle events.

Examples include:

```text
Pre-install

Post-install

Pre-upgrade

Post-upgrade

Pre-rollback

Post-rollback

Pre-delete

Post-delete

Test
```

Hooks can be powerful.

They also increase release complexity.

---

# 102. HOOKS ARE NOT ORDINARY RESOURCES

A hook might run a Job:

```text
Before Upgrade
↓
Database Migration Job
↓
Application Upgrade
```

This creates additional failure paths.

Ask:

```text
What if the hook fails?

Can it run twice?

Is it idempotent?

Does it modify persistent data?

How is it cleaned up?

Can rollback undo its effect?
```

---

# 103. DATABASE MIGRATIONS AND HOOKS

A pre-upgrade hook might perform a database migration.

That does not mean Helm rollback can reverse that migration.

For example:

```text
Revision 5
↓
Migration changes database
↓
New application fails
↓
Helm rollback to Revision 4
```

The database may still contain the Revision 5 schema.

This can make Revision 4 incompatible.

Migration design must therefore consider backward compatibility and recovery independently of Helm.

# 104. HELM TESTS

Tests can validate release-specific behavior.

For example:

```text

Does the application return an expected response?
```

This can provide useful post-release evidence.

It is not a replacement for complete production observability or end-to-end validation.

# 108. HELM VERSUS LIVE KUBERNETES STATE

Helm release information and live Kubernetes resources are related but should not be treated as identical views.

Operators can manually modify live resources.

Controllers can modify fields.

Admission systems can mutate objects.

Therefore an incident may require comparing:

```text
Chart source

Release values

Helm-generated manifest

Live Kubernetes object
```

These can differ.

---

# 109. MANUAL CHANGES CREATE OPERATING RISK

Suppose someone executes:

```bash
kubectl edit deployment <name>
```

and changes replicas from:

```text
2
```

to:

```text
5
```

The live object now differs from what the chart would render.

A future Helm upgrade may reconcile fields according to the release operation and chart inputs.

Manual emergency changes should therefore be:

```text
Documented

Reviewed afterward

Reconciled back into source/configuration where appropriate
```

---

# 110. HELM IS NOT GITOPS BY ITSELF

Helm packages and releases applications.

GitOps introduces a broader reconciliation and operational model around declarative desired state stored in version control.

Do not equate:

```text
Using Helm
```

with:

```text
Using GitOps
```

Helm charts can participate in GitOps workflows, but the concepts are distinct.

---

# 111. UNINSTALLATION

A release can be removed using:

```bash
helm uninstall <release-name> -n <namespace>
```

Before uninstalling, understand:

```text
Which resources are managed?

Which persistent data exists?

Which hooks exist?

Which external systems depend on the application?

Which resources might intentionally survive?

Which CRDs are involved?
```

Uninstall is a destructive operation.

---

# 112. UNINSTALL DOES NOT MEAN ALL DATA IS GONE

As established in Part 13:

```text
Workload Lifecycle
≠
Storage Lifecycle
```

PersistentVolumeClaims, PersistentVolumes, underlying storage, backups, or externally managed resources may have different lifecycles.

Never use:

```text
helm uninstall
```

as a data-erasure procedure without understanding the entire storage architecture.

---

# 113. HELM DOES NOT OWN EVERYTHING IT REFERENCES

A chart may reference:

```text
Existing Secret

Existing PVC

External database

Existing ServiceAccount

External DNS record

Cloud-managed resource
```

without creating or owning that object.

Therefore:

```text
Referenced by Release
≠
Owned by Release
```

This distinction matters during upgrades, rollback, and uninstall.

It does not prove the cluster will accept or successfully run them.

`helm status` provides evidence about:

```text

```

It does not prove business functionality.

`helm get manifest` provides evidence about:


It does not alone prove current live runtime behavior.


It does not prove every application function.

```text
Specific tested application behavior.
```

They do not prove every dependency and failure path.

Engineering confidence comes from combining evidence.
