# PART 11: KUBERNETES WORKLOAD ENGINEERING

## Goal

Move from inspecting Kubernetes workloads and applying basic manifests to designing, deploying, operating, updating, and troubleshooting application workloads correctly.

At Junior level, Kubernetes may look like this:

```text
Write YAML
↓
kubectl apply
↓
Pod runs
```

At Mid-Level, that model is too shallow.

A production engineer needs to understand the complete chain:

```text
Application Requirement
↓
Container Image
↓
Workload Manifest
↓
Kubernetes API
↓
Desired State Stored
↓
Controller Reconciliation
↓
Pod Creation
↓
Scheduler Placement
↓
Node
↓
Kubelet
↓
Container Runtime
↓
Application Process
↓
Readiness
↓
Traffic
↓
Continuous Reconciliation
```

The important question is no longer:

```text
Can I deploy an application to Kubernetes?
```

It becomes:

```text
Can I describe the application's desired state,
select the correct workload controller,
provide configuration and secrets safely,
declare realistic resource requirements,
design meaningful health probes,
understand how Pods are scheduled,
perform controlled updates,
detect a failed rollout,
diagnose workload failures from evidence,
and restore a known-good application state?
```

---

# 1. KUBERNETES IS A DESIRED-STATE SYSTEM

Kubernetes is not primarily a system for issuing commands such as:

```text
Start this container.

Now start another one.

Restart that one.
```

The stronger mental model is:

```text
Declare Desired State
↓
Kubernetes Observes Actual State
↓
Controllers Compare Desired and Actual State
↓
Kubernetes Takes Corrective Action
↓
Actual State Moves Toward Desired State
```

This is reconciliation.

Suppose a Deployment declares:

```yaml
replicas: 3
```

The desired state is:

```text
Three replicas should exist.
```

If only two suitable Pods exist, the relevant controllers work toward restoring three.

This is fundamentally different from manually starting three containers.

---

# 2. DESIRED STATE DOES NOT GUARANTEE A HEALTHY APPLICATION

Kubernetes can reconcile infrastructure objects successfully while the application remains broken.

For example:

```text
Deployment exists
✓

ReplicaSet exists
✓

Three Pods exist
✓

Containers are running
✓

Application returns HTTP 500
✗
```

Therefore:

```text
Kubernetes Object Exists
≠
Application Works
```

and:

```text
Pod Running
≠
Pod Ready
```

and:

```text
Pod Ready
≠
Entire Business Service Healthy
```

Each statement proves something different.

Production troubleshooting depends on knowing those boundaries.

---

# 3. THE KUBERNETES WORKLOAD CONTROL PATH

A useful workload lifecycle model is:

```text
Manifest
↓
API Server
↓
Desired State
↓
Controller
↓
Pod
↓
Scheduler
↓
Node
↓
Kubelet
↓
Container Runtime
↓
Container
↓
Application
```

This is a conceptual model rather than a claim that every object passes through exactly one controller in a simple linear sequence.

Different workload resources use different controllers.

The important engineering idea is that several independent components participate in turning declared state into a running application.

---

# 4. WHY THE CONTROL PATH MATTERS FOR TROUBLESHOOTING

Suppose an application is unavailable.

The problem might exist at:

```text
Manifest
↓
API validation
↓
Controller reconciliation
↓
Pod creation
↓
Scheduling
↓
Image retrieval
↓
Container creation
↓
Application startup
↓
Probe evaluation
↓
Service eligibility
↓
Application dependency
```

If you do not know the control path, troubleshooting becomes random command execution.

Instead ask:

```text
How far did the workload get?
```

That question dramatically reduces the search space.

---

# 5. START WITH THE WORKLOAD REQUIREMENT

Do not start by choosing Kubernetes object types.

Start with application behavior.

Ask:

```text
Is this application long-running?

Is every replica interchangeable?

Does each replica require stable identity?

Must one copy run on every node?

Does the task run to completion?

Does it run on a schedule?

Does it require persistent state?

How should it receive configuration?

How should it receive secrets?

How much CPU and memory does it need?

When is it ready?

When should it be restarted?

How does it shut down?

How should it be updated?
```

The workload requirement should determine the Kubernetes design.

---

# 6. PODS

A Pod is Kubernetes' smallest deployable compute object.

A Pod can contain one or more containers.

A common application Pod contains one main application container:

```text
Pod
└── Application Container
```

But a Pod can contain multiple cooperating containers:

```text
Pod
├── Main Application
└── Supporting Container
```

Containers in the same Pod share important runtime context, including networking and selected storage resources.

They are scheduled together.

---

# 7. A POD IS NOT JUST A CONTAINER

A container describes a process runtime.

A Pod adds Kubernetes-level context around one or more containers.

Conceptually:

```text
Pod
├── Metadata
├── Labels
├── Scheduling Requirements
├── Containers
├── Resource Requirements
├── Probes
├── Volumes
├── Restart Policy
└── Security / Runtime Configuration
```

The Pod is the scheduling unit.

Kubernetes schedules Pods onto nodes, not individual containers independently.

---

# 8. PODS ARE EPHEMERAL

A Pod should not normally be treated as a permanent server.

A Pod has an identity and lifecycle, but a replacement Pod is a new Pod.

Think:

```text
Pod A fails
↓
Controller creates Pod B
```

not:

```text
Pod A must exist forever.
```

This has important consequences for:

- local filesystem state
- Pod IP addresses
- manual modifications
- troubleshooting
- deployment design

---

# 9. DO NOT BUILD OPERATIONS AROUND POD NAMES

A Deployment might create Pods such as:

```text
veriqta-api-7b864dd89c-abc12
veriqta-api-7b864dd89c-def34
veriqta-api-7b864dd89c-ghi56
```

These names can change as Pods are replaced.

Operational automation should usually target workloads or labels rather than depending on generated Pod names.

---

# 10. DIRECT POD CREATION

You can create a Pod directly.

For example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: demo
spec:
  containers:
    - name: app
      image: example/app:1.0
```

But directly managed Pods are usually not the right abstraction for long-running production applications.

If the Pod disappears, there is no Deployment or similar workload controller maintaining the intended replica set.

For long-running applications, use an appropriate controller.

---

# 11. CONTROLLERS

Controllers continuously reconcile Kubernetes resources.

The general pattern is:

```text
Desired State
↓
Observe Current State
↓
Difference?
├── No → Continue Watching
└── Yes
    ↓
    Take Corrective Action
```

Controllers are one of the core reasons Kubernetes can recover from many routine workload failures automatically.

---

# 12. REPLICASETS

A ReplicaSet maintains a desired number of matching Pod replicas.

Conceptually:

```text
ReplicaSet
Desired Replicas: 3
↓
├── Pod A
├── Pod B
└── Pod C
```

If one disappears:

```text
ReplicaSet
Desired: 3
Actual: 2
↓
Create replacement
↓
Actual: 3
```

---

# 13. DEPLOYMENTS MANAGE REPLICASETS

For typical stateless application workloads, engineers normally create a Deployment rather than directly managing ReplicaSets.

The relationship is approximately:

```text
Deployment
↓
ReplicaSet
↓
Pods
```

During an update, a Deployment can manage multiple ReplicaSets as it transitions from one application revision to another.

---

# 14. WHY DEPLOYMENTS EXIST

A ReplicaSet can maintain replica count.

A Deployment adds rollout management around ReplicaSets.

This supports operations such as:

- declarative updates
- rolling updates
- rollout status
- rollout history
- controlled rollback

For interchangeable stateless application replicas, Deployment is usually the first workload controller to consider.

---

# 15. BASIC DEPLOYMENT

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: veriqta-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: veriqta-api
  template:
    metadata:
      labels:
        app: veriqta-api
    spec:
      containers:
        - name: api
          image: registry.example.com/veriqta/api:1.0.0
```

Understand every relationship before adding complexity.

---

# 16. DEPLOYMENT SELECTOR RELATIONSHIP

This section:

```yaml
selector:
  matchLabels:
    app: veriqta-api
```

must correspond correctly with the Pod template labels:

```yaml
template:
  metadata:
    labels:
      app: veriqta-api
```

Conceptually:

```text
Deployment / ReplicaSet Selector
↓
Find Pods with:
app=veriqta-api
```

Selectors are control relationships, not decoration.

---

# 17. LABELS

Labels are key/value metadata used to identify and organize Kubernetes objects.

Example:

```yaml
metadata:
  labels:
    app: veriqta-api
    environment: production
    component: backend
```

Labels can support:

- workload selection
- operational queries
- Services
- policy
- organization
- automation

---

# 18. GOOD LABEL DESIGN

Labels should represent useful, stable identifying attributes.

Examples might include:

```text
Application

Component

Environment

Team

Managed-by
```

Do not put arbitrary large or unstructured information into labels.

Annotations are generally more appropriate for non-identifying metadata.

---

# 19. SELECTORS

Selectors identify groups of objects by labels.

For example:

```bash
kubectl get pods -l app=veriqta-api
```

This asks Kubernetes for Pods matching:

```text
app=veriqta-api
```

Selectors are fundamental to Kubernetes relationships.

---

# 20. SELECTOR ERRORS CAN BE SERIOUS

Suppose your workload Pods use:

```yaml
labels:
  app: veriqta-api
```

but another resource selects:

```yaml
selector:
  app: veriqta-web
```

The resources do not match.

The objects may all exist successfully.

But their intended relationship is broken.

This produces an important lesson:

```text
Valid YAML
≠
Correct Resource Relationship
```

---

# 21. NAMESPACES

Namespaces provide a scope for many Kubernetes resources.

For example:

```text
Namespace: development

Namespace: staging

Namespace: production
```

Resources with the same name can exist in different namespaces where that resource type is namespace-scoped.

For example:

```text
development/veriqta-api

production/veriqta-api
```

These are different objects.

---

# 22. NAMESPACE IS PART OF RESOURCE IDENTITY

A common operational mistake is inspecting the right resource name in the wrong namespace.

Always ask:

```text
Which cluster?

Which namespace?

Which workload?
```

before changing anything.

A useful command is:

```bash
kubectl get deployment veriqta-api -n production
```

The namespace should be explicit in production procedures where ambiguity creates risk.

---

# 23. NAMESPACES ARE NOT COMPLETE SECURITY BOUNDARIES BY THEMSELVES

Namespaces are useful organizational and policy scopes.

But simply placing two workloads into different namespaces does not automatically create complete security isolation.

Actual isolation depends on additional controls such as:

- RBAC
- network policy
- admission controls
- workload security settings
- secret access
- cluster configuration

Do not treat namespace creation as equivalent to complete tenancy isolation.

---

# 24. STATEFULSETS

A StatefulSet manages workloads that need properties such as stable Pod identity and ordered behavior.

Conceptually:

```text
StatefulSet
├── database-0
├── database-1
└── database-2
```

The Pod identities are predictable and stable relative to the StatefulSet.

This differs from Deployment-managed Pods, where replicas are generally intended to be interchangeable.

---

# 25. DEPLOYMENT VERSUS STATEFULSET

A simplified comparison:

```text
Deployment
→ interchangeable replicas

StatefulSet
→ replicas with stable identity requirements
```

This does not mean:

```text
StatefulSet
=
database magically becomes reliable.
```

Stateful systems still require correct application-level replication, storage, backup, recovery, and failure handling.

---

# 26. STATEFULSET CONCEPTS AT THIS LEVEL

Understand:

- stable ordinal identities
- stable network identity concepts
- relationship with persistent storage
- ordered creation and termination behavior
- why some stateful applications need these properties

Deep storage engineering comes later.

Do not use StatefulSet merely because an application writes files.

---

# 27. DAEMONSETS

A DaemonSet ensures that a Pod runs on applicable nodes.

Conceptually:

```text
Node A
└── Agent Pod

Node B
└── Agent Pod

Node C
└── Agent Pod
```

Typical use cases include node-local functionality such as:

- log collection agents
- monitoring agents
- networking components
- storage components
- security agents

---

# 28. DAEMONSET VERSUS DEPLOYMENT

Deployment asks:

```text
How many application replicas should exist?
```

DaemonSet asks approximately:

```text
Which applicable nodes should run a copy?
```

These are different workload intentions.

Do not emulate a DaemonSet by manually matching Deployment replica count to node count.

---

# 29. JOBS

A Job represents work intended to run to completion.

Example:

```text
Start
↓
Perform Task
↓
Complete
```

Possible uses include:

- batch processing
- report generation
- one-time maintenance
- controlled data processing

A Job is different from a long-running service.

---

# 30. JOB SUCCESS

A Job needs a meaningful completion model.

For a simple Job:

```text
Container exits successfully
↓
Job progresses toward completion
```

If the workload fails, retry behavior depends on Job and Pod configuration.

The application must return meaningful process exit status.

Kubernetes cannot infer business success from a process that always exits zero.

---

# 31. JOBS MUST BE SAFE TO RETRY WHERE RETRIES ARE POSSIBLE

Suppose a Job:

```text
Charges customer
↓
Crashes
↓
Retries
↓
Charges customer again
```

That is an application design problem.

When Jobs can retry, think carefully about:

- idempotency
- checkpoints
- duplicate work
- external side effects
- partial completion

Kubernetes retry capability does not make arbitrary operations safe to repeat.

---

# 32. CRONJOBS

A CronJob creates Jobs according to a schedule.

Conceptually:

```text
CronJob
↓
Schedule
↓
Job
↓
Pod
↓
Task
```

A CronJob does not directly represent the running task.

It creates Jobs.

---

# 33. CRONJOB ENGINEERING

For scheduled workloads consider:

- schedule
- timezone behavior
- concurrency
- missed schedules
- task duration
- idempotency
- history retention
- failure visibility

Do not assume scheduled execution means exactly-once business processing.

Applications should tolerate the execution semantics appropriate to their workload.

---

# 34. CONFIGURATION SHOULD BE SEPARATE FROM THE IMAGE

Part 10 established:

```text
Build Once
↓
Promote Same Artifact
↓
Configure at Runtime
```

Kubernetes supports this model.

Instead of building:

```text
api-development:1.0

api-staging:1.0

api-production:1.0
```

prefer where appropriate:

```text
Same Image
+
Environment-Specific Configuration
```

This reduces artifact variation between environments.

---

# 35. CONFIGMAPS

A ConfigMap stores non-confidential configuration data.

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: veriqta-api-config
data:
  APP_ENV: "production"
  LOG_LEVEL: "info"
```

Applications can consume ConfigMaps in several ways, including environment variables and mounted files.

---

# 36. CONFIGMAP AS ENVIRONMENT VARIABLES

Example:

```yaml
envFrom:
  - configMapRef:
      name: veriqta-api-config
```

The application can then read configured values from its environment.

But understand the operational behavior of your chosen injection method.

Do not assume that changing a ConfigMap automatically changes the environment of an already-running process.

---

# 37. CONFIGMAP AS FILES

ConfigMaps can also be exposed through volumes.

Conceptually:

```text
ConfigMap
↓
Pod Volume
↓
Files
↓
Application
```

Applications that support configuration reloads can potentially respond differently from applications that read configuration only during startup.

The application behavior matters.

---

# 38. CONFIGURATION CHANGE STRATEGY

Ask:

```text
Does application read configuration only at startup?

Does it watch files?

Does it support reload?

Should configuration changes trigger rollout?

How will configuration version be traced?
```

Do not assume Kubernetes decides application reload semantics for you.

---

# 39. SECRETS

A Kubernetes Secret stores sensitive data intended for workloads or Kubernetes components.

Examples include:

- passwords
- tokens
- keys
- credentials

A Secret is different from a ConfigMap because the data has different security requirements.

---

# 40. BASE64 IS NOT ENCRYPTION

Secret manifests often contain values represented using base64 encoding.

For example:

```yaml
data:
  PASSWORD: <base64-value>
```

Base64 does not make the value confidential.

Anyone who obtains the encoded value can decode it.

Therefore:

```text
Base64
≠
Encryption
```

---

# 41. SECRET SECURITY DEPENDS ON THE CLUSTER

Secret protection involves:

- API authorization
- RBAC
- etcd encryption configuration
- workload permissions
- namespace design
- audit controls
- secret distribution
- external secret-management architecture

A Kubernetes Secret object is useful, but it is not a complete secrets-management strategy by itself.

---

# 42. DO NOT COMMIT REAL SECRETS TO GIT

Bad workflow:

```text
secret.yaml
↓
Real Production Password
↓
Git Commit
↓
Public / Shared Repository
```

Deleting the file later does not guarantee that the secret disappeared from repository history or existing clones.

If a real secret is exposed:

```text
Revoke / Rotate
↓
Then clean repository exposure as required
```

Do not treat deletion as credential revocation.

---

# 43. SECRET AS ENVIRONMENT VARIABLE

A container can receive a Secret value through an environment variable.

Example:

```yaml
env:
  - name: DATABASE_PASSWORD
    valueFrom:
      secretKeyRef:
        name: database-credentials
        key: password
```

This is convenient.

But environment variables have operational exposure considerations.

Use the secret delivery method appropriate to the application and threat model.

---

# 44. SECRET AS VOLUME

Secrets can also be mounted as files.

Conceptually:

```text
Secret
↓
Volume
↓
File
↓
Application
```

This can be useful for:

- certificates
- keys
- credential files

Again, the application must know how to consume and possibly reload the data.

---

# 45. CONFIGURATION AND SECRET FAILURE

A Pod may fail because:

```text
ConfigMap does not exist

Secret does not exist

Required key missing

Wrong value

Wrong filename

Wrong environment variable

Application cannot parse configuration
```

Separate:

```text
Kubernetes could not provide configuration
```

from:

```text
Kubernetes provided configuration,
but application rejected it.
```

These are different failures.

---

# 46. RESOURCE REQUESTS AND LIMITS

Kubernetes workloads should declare resource expectations deliberately.

For CPU and memory, two key concepts are:

```text
Request

Limit
```

They are not interchangeable.

---

# 47. RESOURCE REQUESTS

A request represents the resource amount used by Kubernetes scheduling when deciding where a Pod can fit.

Conceptually:

```text
Pod requests:
CPU: 500m
Memory: 256Mi

Scheduler asks:
Which node can accommodate this request?
```

Requests strongly influence placement.

---

# 48. RESOURCE LIMITS

A limit constrains resource usage according to the resource and runtime enforcement mechanisms.

Conceptually:

```text
Request
→ scheduling expectation

Limit
→ runtime constraint
```

CPU and memory limits behave differently.

Do not assume all resources are enforced identically.

---

# 49. CPU UNITS

CPU is often expressed in cores or millicores.

For example:

```yaml
resources:
  requests:
    cpu: "250m"
```

means:

```text
250 millicores
=
0.25 CPU
```

Similarly:

```text
500m = 0.5 CPU

1000m = 1 CPU
```

---

# 50. MEMORY UNITS

Memory might be expressed as:

```yaml
memory: "256Mi"
```

Be precise about units.

For example:

```text
Mi
```

and:

```text
M
```

are not the same unit.

Do not guess memory values without measuring workload behavior.

---

# 51. REQUESTS AFFECT SCHEDULING

Suppose a Pod requests:

```text
4 CPU
```

but available nodes cannot satisfy the request.

The Pod may remain:

```text
Pending
```

even if actual application CPU usage would initially be tiny.

The scheduler reasons from declared requirements and placement constraints.

---

# 52. LIMITS DO NOT SOLVE CAPACITY PLANNING

Setting:

```yaml
limits:
  memory: 512Mi
```

does not prove:

```text
512Mi is correct for this application.
```

Resource values should come from:

- measurement
- load testing
- runtime observation
- capacity requirements
- safety margin
- performance objectives

Arbitrary limits can create production failures.

---

# 53. CPU LIMIT BEHAVIOR

When a workload reaches an enforced CPU limit, it can experience throttling.

Possible symptoms include:

```text
Higher latency

Lower throughput

Requests timing out
```

without the container necessarily exiting.

This can look like an application-performance problem.

Resource evidence matters.

---

# 54. MEMORY LIMIT BEHAVIOR

Memory behaves differently.

If a container exceeds available memory constraints under relevant conditions, its process may be terminated.

A common Kubernetes symptom is:

```text
OOMKilled
```

This indicates memory-related termination evidence.

It does not by itself tell you why memory demand became too high.

---

# 55. `OOMKILLED` IS NOT THE ROOT CAUSE

The mechanism may be:

```text
Memory limit reached
↓
Process terminated
```

But root-cause possibilities include:

```text
Limit too low

Memory leak

Unexpected traffic

Large request

Large cache

Changed dependency

Workload behavior changed
```

Do not solve every `OOMKilled` event by increasing memory.

---

# 56. RESOURCE CONFIGURATION EXAMPLE

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"
```

Do not copy these values into production.

They are examples.

Production values require workload-specific evidence.

---

# 57. QUALITY OF SERVICE AWARENESS

Kubernetes classifies Pods into Quality of Service classes based on resource configuration.

At this level, understand that resource declarations influence more than scheduling.

They can also affect behavior under node resource pressure.

Detailed eviction and node resource-management internals belong later.

---

# 58. PROBES

Kubernetes provides three major application probe types:

```text
Startup Probe

Readiness Probe

Liveness Probe
```

These answer different questions.

Treating them as interchangeable creates production incidents.

---

# 59. STARTUP PROBE

The startup probe asks:

```text
Has this application successfully started?
```

It is useful for applications with slow or variable initialization.

While a startup probe is active and has not succeeded, liveness and readiness probing are held back.

This protects a legitimately slow-starting application from being killed prematurely by liveness logic.

---

# 60. READINESS PROBE

The readiness probe asks:

```text
Should this Pod currently receive traffic?
```

A failed readiness probe does not normally mean:

```text
Restart the container.
```

It means the container is not considered ready for traffic through matching Services.

That distinction is fundamental.

---

# 61. LIVENESS PROBE

The liveness probe asks approximately:

```text
Is this container in a state where restarting it is appropriate?
```

If liveness repeatedly fails according to configured thresholds, the kubelet restarts the container.

This makes liveness powerful and potentially dangerous.

---

# 62. PROBE MENTAL MODEL

Use:

```text
Startup
→ Has initialization completed?

Readiness
→ Should traffic reach me now?

Liveness
→ Am I unhealthy in a way where restart is appropriate?
```

Do not reduce all three to:

```text
Is HTTP 200 returned?
```

The engineering meaning matters more than the protocol.

---

# 63. READINESS FAILURE CAN BE HEALTHY BEHAVIOR

Suppose an application becomes temporarily overloaded.

It may intentionally fail readiness:

```text
Application process
→ alive

Pod
→ Running

Readiness
→ false

Traffic eligibility
→ removed
```

That can be a valid protection mechanism.

The application may recover without being restarted.

---

# 64. LIVENESS CAN CREATE AN OUTAGE

Suppose a dependency becomes slow.

Every application replica uses a liveness check that requires that dependency.

Dependency slows.

Then:

```text
Pod A liveness fails
↓
restart

Pod B liveness fails
↓
restart

Pod C liveness fails
↓
restart
```

The health mechanism amplifies the incident.

Therefore:

```text
Aggressive Liveness
≠
High Availability
```

Probe design must reflect application failure semantics.

---

# 65. DO NOT MAKE LIVENESS DEPEND ON EVERY EXTERNAL SERVICE

If the application process is healthy but a database is temporarily unavailable, restarting every application process may accomplish nothing.

Ask:

```text
Will restarting this process fix the condition?
```

If the answer is no, the condition may not belong in liveness.

---

# 66. READINESS AND DEPENDENCIES

Readiness may reasonably depend on services that are strictly required to serve useful requests.

But even here, design carefully.

If every Pod marks itself unready because a shared dependency is slow, the result may be:

```text
Zero Ready Pods
```

even though some degraded service might have been preferable.

Health semantics are architecture decisions.

---

# 67. PROBE MECHANISMS

Kubernetes supports probe mechanisms such as:

- HTTP
- TCP
- command execution
- gRPC where applicable

Choose a mechanism appropriate to the application.

Do not install unnecessary tooling inside an image solely because a copied probe example uses it.

---

# 68. HTTP PROBE EXAMPLE

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3
```

The values are examples.

Production values should reflect:

- application response time
- startup behavior
- failure sensitivity
- expected transient conditions

---

# 69. STARTUP PROBE EXAMPLE

```yaml
startupProbe:
  httpGet:
    path: /health
    port: 8080
  periodSeconds: 5
  failureThreshold: 30
```

Conceptually, this permits a startup window based on probe interval and failure threshold.

Do not make the startup allowance arbitrarily huge.

Understand how long healthy startup should actually take.

---

# 70. LIVENESS PROBE EXAMPLE

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3
```

Again, these values are illustrative.

The important question is whether `/health` truly represents a condition where restart is useful.

---

# 71. PROBE TIMING

Important fields include:

```text
initialDelaySeconds

periodSeconds

timeoutSeconds

successThreshold

failureThreshold
```

Their interaction determines how quickly Kubernetes declares success or failure.

Do not tune them independently.

---

# 72. PROBE FAILURE BUDGET

Suppose:

```text
periodSeconds: 10

failureThreshold: 3
```

Then repeated failures can trigger the relevant action after approximately multiple probe periods, subject to probe timing and execution details.

Do not present probe timing as perfectly exact wall-clock arithmetic.

Network delay, probe execution, startup behavior, and kubelet processing can affect observation.

---

# 73. PROBE ENDPOINTS SHOULD BE CHEAP

A health endpoint should not perform expensive operations such as:

```text
Full database scan

Large external API request

Heavy filesystem operation

Expensive authentication flow
```

on every probe.

Remember:

```text
Pods
×
Probe Frequency
×
Probe Cost
=
Operational Load
```

---

# 74. TEST PROBES AS FAILURE MECHANISMS

Do not verify only:

```text
Probe passes.
```

Also test:

```text
What happens when readiness fails?

What happens when liveness fails?

What happens during slow startup?

What happens when endpoint times out?

How long until Kubernetes reacts?

What does the user experience?
```

---

# 75. SCHEDULING FUNDAMENTALS

The scheduler assigns unscheduled Pods to nodes.

Conceptually:

```text
New Pod
↓
No Node Assigned
↓
Scheduler Evaluates Nodes
↓
Suitable Node Selected
↓
Pod Bound to Node
```

After assignment, the kubelet on that node works to run the Pod.

---

# 76. SCHEDULING IS NOT RANDOM

Scheduling can consider factors such as:

- resource requests
- node availability
- placement constraints
- affinity
- anti-affinity
- taints and tolerations
- topology
- volumes
- policy

At Mid-Level, focus first on:

```text
Can this Pod fit?

Is this Node eligible?
```

Advanced scheduling strategy comes later.

---

# 77. PENDING DOES NOT MEAN ONE THING

A Pod in:

```text
Pending
```

has not necessarily failed.

Pending can represent different stages or blockers.

For example:

```text
Pod not scheduled
```

or other startup preparation conditions.

Inspect evidence before deciding what Pending means.

---

# 78. `FAILEDSCHEDULING`

If the scheduler cannot find an eligible node, Kubernetes emits scheduling events.

Possible reasons include:

```text
Insufficient CPU

Insufficient Memory

Node Selector Mismatch

Affinity Constraint

Taint Not Tolerated

Volume Placement Constraint
```

The event often tells you why no node was selected.

---

# 79. TROUBLESHOOT SCHEDULING FROM EVENTS

Start with:

```bash
kubectl describe pod <pod> -n <namespace>
```

Read:

```text
Events:
```

Do not begin by changing resource requests.

First determine what scheduling condition actually failed.

---

# 80. NODE SELECTORS

A Pod can request nodes with matching labels.

Example:

```yaml
nodeSelector:
  workload-type: application
```

Conceptually:

```text
Pod requires:
workload-type=application

Scheduler considers:
nodes carrying that label
```

If no eligible node matches, the Pod can remain unscheduled.

---

# 81. AFFINITY AWARENESS

Affinity provides more expressive placement rules.

Conceptually:

```text
Place this workload near workloads with property X.
```

Anti-affinity can express:

```text
Avoid placing these workloads together.
```

At Mid-Level, understand the purpose and basic failure consequences.

Complex topology architecture belongs later.

---

# 82. TAINTS AND TOLERATIONS AWARENESS

A taint on a node can repel Pods that do not have a matching toleration.

Conceptually:

```text
Node:
Do not place ordinary workloads here.

Pod:
I tolerate this condition.
```

A toleration permits consideration.

It does not necessarily force the Pod onto that node.

---

# 83. DEPLOYMENT ROLLING UPDATES

A Deployment can replace an old application revision gradually.

Conceptually:

```text
Old ReplicaSet
Pods: v1 v1 v1

↓ update

Old ReplicaSet + New ReplicaSet
Pods: v1 v1 v2

↓

Pods: v1 v2 v2

↓

New ReplicaSet
Pods: v2 v2 v2
```

Actual rollout behavior depends on Deployment strategy and configuration.

---

# 84. ROLLINGUPDATE STRATEGY

Important controls include:

```text
maxUnavailable

maxSurge
```

These determine how many replicas may be unavailable and how many extra replicas may exist during a rolling update.

They affect:

- availability
- capacity
- rollout speed
- resource requirements

---

# 85. `MAXUNAVAILABLE`

`maxUnavailable` controls how many desired replicas can be unavailable during the update, subject to Deployment semantics.

A higher value can increase rollout speed but reduce available capacity.

A lower value protects availability but can make rollout slower.

---

# 86. `MAXSURGE`

`maxSurge` controls how many additional Pods can be created above the desired replica count during the rollout.

This improves update flexibility but requires spare cluster capacity.

A rollout strategy can fail operationally if the cluster lacks room for surge Pods.

---

# 87. ROLLING UPDATE REQUIRES CAPACITY

Suppose:

```text
Desired replicas: 10

maxSurge: 2
```

The rollout may temporarily need capacity for more than ten Pods.

If the cluster is already full:

```text
New Pods
↓
Pending
↓
Rollout stalls
```

The application image may be perfectly healthy.

The rollout problem is capacity.

---

# 88. READINESS PROBES PROTECT ROLLOUTS

During a rolling update:

```text
New Pod Created
↓
Container Starts
↓
Readiness Probe
↓
Ready
↓
Counts Toward Available Capacity
```

A new process merely starting should not automatically mean it is ready for traffic.

This is one reason correct readiness design is critical.

---

# 89. BAD READINESS CAN CREATE A BAD ROLLOUT

If readiness says:

```text
Ready
```

before initialization is complete:

```text
Traffic
↓
New Pod
↓
Application not actually ready
↓
Errors
```

Kubernetes followed the health contract it was given.

The contract was wrong.

---

# 90. ROLLOUT STATUS

Observe a Deployment rollout with:

```bash
kubectl rollout status deployment/veriqta-api -n production
```

Do not assume that:

```bash
kubectl apply -f deployment.yaml
```

means:

```text
Rollout succeeded.
```

`apply` and successful application rollout are different outcomes.

---

# 91. ROLLOUT HISTORY

Inspect Deployment rollout history:

```bash
kubectl rollout history deployment/veriqta-api -n production
```

Useful revision information depends on the Deployment's history and change metadata.

Maintain meaningful change traceability outside Kubernetes as well:

```text
Git Commit

CI Build

Image Digest

Deployment Change
```

---

# 92. ROLLBACK

A Deployment can roll back to an earlier revision retained in its rollout history.

Example:

```bash
kubectl rollout undo deployment/veriqta-api -n production
```

But understand exactly what this means.

It changes the Deployment's Pod template toward a previous revision.

---

# 93. KUBERNETES ROLLBACK IS NOT SYSTEM ROLLBACK

Deployment rollback does not automatically reverse:

```text
Database migrations

External API changes

Messages already produced

Data transformations

Object storage changes

Infrastructure changes
```

Therefore:

```text
Deployment Rollback
≠
Complete System Rollback
```

This is the same principle introduced in container engineering.

---

# 94. IMAGE IDENTITY DURING ROLLOUT

Part 10 established:

```text
Tag
≠
Immutable Artifact Identity
```

That still matters in Kubernetes.

For strong release traceability, know the exact image content being deployed.

A human-friendly tag can coexist with digest-based artifact identification.

Do not let mutable image references make production state ambiguous.

---

# 95. BAD ROLLOUT

A rollout may fail because:

```text
Image does not exist

Registry authentication fails

Application crashes

Probe fails

Configuration missing

Secret missing

Resources unavailable

New version is incompatible

New Pods never become Ready
```

The phrase:

```text

```

is not a root cause.

Find the failing layer.


# 102. EVENTS

Events can reveal:

```text

Probe failures

Container restart activity
```

But events are operational observations with limited retention and should not be treated as permanent historical storage.

Collect durable telemetry separately.

---

# 103. POD PHASE VERSUS DISPLAYED STATUS

Kubernetes defines Pod phases such as:

```text
Pending

Running

Succeeded

Failed

Unknown
```

However, `kubectl` may display human-friendly status reasons such as:

```text
CrashLoopBackOff

ImagePullBackOff
```

These are not additional Pod phases.

This distinction matters when reading API state.

---

# 104. `CRASHLOOPBACKOFF`

`CrashLoopBackOff` means a container is repeatedly failing and Kubernetes is delaying repeated restart attempts.

It is not the root cause.

The root cause may be:

```text
Application crash

Bad command

Missing configuration

Bad secret

Permission failure

Dependency failure

Invalid arguments

OOM termination
```

---

# 105. `CRASHLOOPBACKOFF` WORKFLOW

Use:

```text
Pod
↓
Container State
↓
Last Terminated State
↓
Exit Code / Reason
↓
Previous Logs
↓
Events
↓
Configuration
↓
Root Cause
```

Commands may include:

```bash
kubectl describe pod <pod> -n <namespace>
```

and:

```bash
kubectl logs <pod> -c <container> --previous -n <namespace>
```

Do not simply delete the Pod.

A controller will likely create another Pod with the same broken specification.

---

# 106. RESTARTING IS NOT DIAGNOSIS

This pattern:

```text
Pod broken
↓
Delete Pod
↓
New Pod starts
```

may temporarily restore service.

It does not explain the failure.

If the underlying cause remains:

```text
Failure
↓
Replacement
↓
Failure Again
```

Use restarts as operational actions only when justified, not as substitutes for root-cause analysis.

---

Possible causes include:

```text

Wrong tag

Image does not exist

Registry unavailable

Network/DNS problem

Authorization failure
```


# 185. APPLICATION SHUTDOWN IN KUBERNETES

Part 10 established graceful container termination.

Kubernetes workload engineering depends on that behavior.

Conceptually:

```text
Pod Termination Begins
↓
Traffic Eligibility Changes
↓
Kubelet Initiates Container Termination
↓
Application Receives Termination Signal
↓
Grace Period
↓
Application Exits
```

Exact traffic and endpoint timing involves multiple components.

Do not assume termination is instantaneous.

---

# 186. `TERMINATIONGRACEPERIODSECONDS`

Pods can define a termination grace period.

The application should normally be able to complete its intended shutdown within that window.

Setting a huge grace period is not a substitute for understanding shutdown behavior.

Setting an extremely short one can cause forced termination.

Measure real shutdown behavior.

```text
↓
```

It is:

```text
Can I explain how this workload moves
from declared desired state
to a scheduled Pod,
to a running container,
to a ready application;

can I explain which controller owns it,
which configuration it consumes,
which identity and resources it receives,
why its probes represent the correct health semantics,
how it is updated,
how it is rolled back,
what happens when each layer fails,
```
