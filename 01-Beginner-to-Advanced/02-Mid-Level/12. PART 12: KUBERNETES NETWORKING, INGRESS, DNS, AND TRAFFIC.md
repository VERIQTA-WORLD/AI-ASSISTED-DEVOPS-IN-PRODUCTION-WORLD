# PART 12: KUBERNETES NETWORKING, INGRESS, DNS, AND TRAFFIC

## Goal

Understand how traffic reaches Kubernetes workloads, how traffic moves between workloads, how Kubernetes provides stable service discovery over ephemeral Pods, how external HTTP and HTTPS traffic enters a cluster, how network policy changes permitted communication, and how to troubleshoot connectivity failures by identifying the exact layer where the request path stops working.

By the end of this Part, the objective is not merely to know what a Service, Ingress, DNS record, or NetworkPolicy is.

The objective is to reason through a complete request path:

```text
Client
↓
DNS
↓
External Entry Point
↓
Ingress / Gateway
↓
Service
↓
EndpointSlice
↓
Pod IP
↓
Application Port
↓
Application
```

For internal traffic, the path may instead resemble:

```text
Client Pod
↓
Cluster DNS
↓
Service Name
↓
Service ClusterIP
↓
Service Data Plane
↓
EndpointSlice
↓
Backend Pod IP
↓
Application Port
↓
Application
```

A Mid-Level engineer should be able to answer:

```text
Did DNS resolve?

What address did it resolve to?

Can the client reach the entry point?

Did TLS succeed?

Did the ingress or gateway match the request?

Which Service was selected?

Does that Service have usable endpoints?

Which Pods became endpoints?

Is the Service port mapped to the correct application port?

Can the network carry traffic to those Pods?

Does NetworkPolicy permit the connection?

Is the application actually listening?

Did the request reach the application?

Where exactly did the request stop?
```

That is Kubernetes traffic engineering.

---

# 1. KUBERNETES NETWORKING IS A CHAIN OF RELATIONSHIPS

A common mistake is treating Kubernetes networking as one feature.

It is not.

Several different systems cooperate to make an application reachable.

A simplified model is:

```text
Application Process
↑
Container
↑
Pod Network
↑
Service
↑
Ingress / Gateway / Load Balancer
↑
External Network
↑
DNS
↑
Client
```

Each layer has a different responsibility.

A request can fail while every other layer remains healthy.

For example:

```text
DNS
✓

TLS
✓

Ingress
✓

Service
✓

EndpointSlice
✓

Pod Network
✓

Application
✗
```

Or:

```text
DNS
✓

Ingress
✓

Service
✓

EndpointSlice
✗

Application
✓
```

The application can therefore be perfectly healthy while users cannot reach it.

---

# 2. THE CENTRAL TROUBLESHOOTING PRINCIPLE

Do not begin with:

```text
"Kubernetes networking is broken."
```

That statement is too broad to be useful.

Instead identify:

```text
Source
↓
Destination
↓
Protocol
↓
Port
↓
Expected Path
↓
Observed Failure Point
```

For example:

```text
Source:
frontend Pod

Destination:
api Service

Protocol:
TCP / HTTP

Service Port:
80

Target Port:
8080

Expected:
frontend → DNS → Service → Endpoint → api Pod → port 8080

Observed:
DNS succeeds
Service resolves
Service has no endpoints
```

Now the problem is much smaller.

---

# 3. NETWORKING FAILURES ARE DIRECTIONAL

Connectivity should always be described directionally.

Do not say:

```text
frontend and backend cannot communicate
```

when the actual observation is:

```text
frontend cannot establish TCP connection to backend:8080
```

The reverse direction may behave differently.

Always identify:

```text
Source
→
Destination
```

NetworkPolicy, routing, firewalls, return paths, and application behavior can make direction important.

---

# 4. FOUR FUNDAMENTAL COMMUNICATION PROBLEMS

A useful Kubernetes networking model separates communication into:

```text
Container
↔
Container in same Pod
```

```text
Pod
↔
Pod
```

```text
Pod
↔
Service
```

```text
External Client
↔
Service / Application
```

Each path uses different abstractions.

Troubleshooting becomes easier when the failed communication type is identified first.

---

# 5. CONTAINERS INSIDE THE SAME POD

Containers inside one Pod share the Pod's network namespace.

Conceptually:

```text
Pod
│
├── Container A
│
└── Container B
```

Both participate in the same Pod networking context.

They can communicate using:

```text
localhost
```

when processes listen appropriately.

Therefore:

```text
Container A
→ localhost:PORT
→ Container B
```

can be valid inside the same Pod.

This is fundamentally different from communication between separate Pods.

---

# 6. POD NETWORKING

Each ordinary Pod receives an IP address from the cluster's Pod network.

Conceptually:

```text
Node A
├── Pod A → Pod IP
└── Pod B → Pod IP

Node B
├── Pod C → Pod IP
└── Pod D → Pod IP
```

The Kubernetes network model expects Pod networking to support communication between Pods across the cluster, subject to intentional restrictions such as network policy and implementation-specific controls.

The actual networking mechanism is supplied by the cluster's networking implementation.

---

# 7. POD IP ADDRESSES ARE NOT SERVICE IDENTITIES

Suppose a Deployment currently has:

```text
api-abc → 10.244.1.10

api-def → 10.244.2.17

api-ghi → 10.244.3.22
```

A rollout occurs.

The replacement Pods might become:

```text
api-jkl → 10.244.1.31

api-mno → 10.244.2.42

api-pqr → 10.244.3.19
```

Applications should not normally depend on those individual Pod IP addresses as permanent service identities.

This is why Kubernetes provides Services and service discovery.

---

# 8. POD IP LIFETIME

Think:

```text
Pod Lifetime
≈
Pod IP Lifetime
```

rather than:

```text
Application Lifetime
=
One Permanent Pod IP
```

When a Pod is replaced, the replacement can receive a different IP.

Therefore:

```text
Hardcoded Pod IP
→
Fragile dependency
```

A stable abstraction is needed above changing Pods.

That abstraction is commonly a Service.

---

# 9. APPLICATION BINDING STILL MATTERS

Kubernetes networking cannot make an application reachable on an address where it is not listening.

Suppose an application inside a Pod listens only on:

```text
127.0.0.1:8080
```

That generally makes it available only through loopback within that Pod's network namespace.

Traffic arriving at the Pod IP cannot simply be assumed to reach it.

For the VERIQTA training application used throughout the curriculum, a networked container workload may need:

```text
HOST=0.0.0.0
PORT=8080
```

when it is intended to accept traffic through the Pod network.

This creates an important troubleshooting question:

```text
Is Kubernetes unable to route traffic?

or

Is the application not listening where Kubernetes traffic arrives?
```

---

# 10. VERIFY THE APPLICATION BEFORE THE SERVICE

Before blaming a Service, establish whether the backend application itself is functioning.

Questions include:

```text
Is the Pod Running?

Is it Ready?

What is its Pod IP?

Which port should the application listen on?

Is the process actually listening?

Does the application respond locally?

Does it respond through the Pod IP where appropriate?
```

The troubleshooting path should move outward from known facts.

---

# 11. WHY SERVICES EXIST

Pods are replaceable.

Clients need a stable way to locate an application.

Without a Service, a client might need to know:

```text
Pod A IP
Pod B IP
Pod C IP
```

and update that information whenever Pods change.

A Service creates a stable logical network abstraction over a changing backend set.

Conceptually:

```text
Client
↓
Stable Service Identity
↓
Changing Backend Set
├── Pod A
├── Pod B
└── Pod C
```

---

# 12. SERVICE DOES NOT CREATE THE APPLICATION

A Service does not start Pods.

A Service does not repair application code.

A Service does not make an unhealthy process healthy.

It provides a networking abstraction over endpoints.

Therefore:

```text
Service Exists
≠
Backend Exists
```

and:

```text
Service Has ClusterIP
≠
Service Has Usable Endpoints
```

and:

```text
Service Has Endpoints
≠
Application Is Correct
```

---

# 13. SERVICE SELECTORS

A Service commonly identifies backend Pods using labels.

Example Pods:

```yaml
metadata:
  labels:
    app: veriqta-api
```

Service:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: veriqta-api
spec:
  selector:
    app: veriqta-api
  ports:
    - port: 80
      targetPort: 8080
```

Conceptually:

```text
Service Selector
app=veriqta-api
↓
Matching Pods
↓
EndpointSlices
```

The selector creates a critical relationship.

---

# 14. A SERVICE SELECTOR IS NOT A DEPLOYMENT REFERENCE

A Service does not normally say:

```text
Send traffic to Deployment named veriqta-api.
```

It selects Pods based on labels.

This means a Deployment and Service can have similar names while still being disconnected.

Example:

```text
Deployment Pods:
app=veriqta-backend
```

Service:

```text
selector:
app=veriqta-api
```

The Service can exist successfully while selecting no Pods.

---

# 15. VALID YAML CAN CREATE A BROKEN NETWORK

This configuration can be syntactically valid:

```text
Deployment
✓

Service
✓

Ingress
✓
```

while the application remains unreachable because:

```text
Service selector
≠
Pod labels
```

Therefore:

```text
API Accepted Configuration
≠
Correct Traffic Path
```

Relationship verification matters.

---

# 16. SERVICE PORTS

A Service port definition introduces several port concepts.

Example:

```yaml
ports:
  - name: http
    port: 80
    targetPort: 8080
```

Understand them separately.

```text
Service Port
80
```

is the port clients use when connecting to the Service.

```text
Target Port
8080
```

is the backend port to which Service traffic is directed.

---

# 17. PORT MAPPING MENTAL MODEL

Use:

```text
Client
↓
Service:80
↓
Backend Endpoint:8080
↓
Application
```

Do not assume:

```text
Service port
=
container application port
```

They can be different.

---

# 18. `CONTAINERPORT` DOES NOT PUBLISH AN APPLICATION

A Pod specification may contain:

```yaml
ports:
  - containerPort: 8080
```

This documents and names a container port and can be referenced by other configuration.

It does not by itself create external exposure.

The application must actually listen on the expected port.

A Service, Ingress, Gateway, or external mechanism is still required according to the intended traffic path.

---

# 19. NAMED PORTS

Ports can be named.

Example:

```yaml
ports:
  - name: http
    containerPort: 8080
```

A Service can reference that name:

```yaml
ports:
  - port: 80
    targetPort: http
```

Named ports can reduce coupling between Service configuration and numeric backend ports when used correctly.

But names must match correctly.

---

# 20. CLUSTERIP SERVICES

`ClusterIP` is the default Service type.

Conceptually:

```text
Cluster Client
↓
Service ClusterIP
↓
Backend Endpoint
```

A ClusterIP provides a cluster-internal Service address.

It is not normally intended as a directly internet-routable public address.

---

# 21. CLUSTERIP IS A VIRTUAL SERVICE ADDRESS

Do not think of ClusterIP as:

```text
A server with that IP address
```

The Service IP is a virtual abstraction implemented through the cluster's Service data plane.

Conceptually:

```text
10.96.20.10:80
```

may represent:

```text
10.244.1.11:8080

10.244.2.14:8080

10.244.3.19:8080
```

The client uses the Service identity.

The data plane directs traffic toward an appropriate backend endpoint.

---

# 22. SERVICE IP VERSUS POD IP

Keep these separate:

```text
Service IP
→ stable logical frontend
```

```text
Pod IP
→ address of a particular Pod
```

A Service may remain:

```text
10.96.20.10
```

while its backend Pod addresses change repeatedly.

That decoupling is one of the central purposes of the Service abstraction.

---

# 23. ENDPOINTSLICES

Modern Kubernetes represents Service backend endpoints using EndpointSlice resources.

Conceptually:

```text
Service
↓
EndpointSlices
↓
Ready Backend Endpoints
├── Pod IP A : Port
├── Pod IP B : Port
└── Pod IP C : Port
```

EndpointSlices are a critical troubleshooting layer between:

```text
Service
```

and:

```text
Pods
```

---

# 24. WHY ENDPOINTSLICES MATTER

Suppose:

```text
Pods
✓ Running

Service
✓ Exists

DNS
✓ Resolves
```

but:

```text
EndpointSlices
→ no usable backend endpoints
```

Traffic cannot reach those Pods through the Service as expected.

This often points toward:

```text
Wrong selector

Wrong labels

Pods not Ready

Backend relationship problem
```

rather than DNS failure.

---

# 25. INSPECT ENDPOINTSLICES

Use:

```bash
kubectl get endpointslices -n <namespace>
```

For a particular Service, label selection can be useful:

```bash
kubectl get endpointslices \
  -n <namespace> \
  -l kubernetes.io/service-name=<service-name>
```

Then inspect:

```bash
kubectl describe endpointslice <name> -n <namespace>
```

Ask:

```text
Which endpoint IPs exist?

Which ports?

Are they ready?

Which Service owns this slice?

Do those IPs correspond to expected Pods?
```

---

# 26. ENDPOINT READINESS

EndpointSlice contains endpoint conditions, including readiness-related information.

For ordinary Service-backed Pods, Pod readiness influences whether an endpoint is considered ready for normal Service traffic.

This connects Part 11 directly to Part 12:

```text
Readiness Probe
↓
Pod Ready Condition
↓
Endpoint Readiness
↓
Service Traffic Eligibility
```

A bad readiness probe can therefore become a networking symptom.

---

# 27. A SERVICE WITH NO ENDPOINTS

One of the most important Kubernetes troubleshooting states is:

```text
Service exists
↓
Service DNS resolves
↓
ClusterIP exists
↓
No backend endpoints
```

Possible causes include:

```text
Selector mismatch

Wrong labels

Pods not Ready

Pods absent

Wrong namespace assumptions

Workload failure
```

Do not troubleshoot CoreDNS when DNS already returned the correct Service address.

---

# 28. SERVICE DISCOVERY

Applications need a stable way to discover Services.

Kubernetes commonly provides service discovery through cluster DNS.

Instead of configuring:

```text
10.96.20.10
```

an application can use:

```text
veriqta-api
```

or a namespace-qualified Service name.

This separates application configuration from specific Service IP addresses.

---

# 29. CLUSTER DNS

A cluster DNS implementation such as CoreDNS can watch Kubernetes service information and provide DNS records for Services.

Conceptually:

```text
Client Pod
↓
DNS Query
↓
Cluster DNS
↓
Service Name
↓
Service Address
```

DNS answers:

```text
Where should I connect?
```

It does not prove:

```text
The destination application works.
```

---

# 30. DNS NAMES AND NAMESPACES

Suppose a Service is:

```text
Name:
veriqta-api

Namespace:
production
```

A Pod in the same namespace can commonly use:

```text
veriqta-api
```

A client in another namespace should use an appropriately qualified name, such as:

```text
veriqta-api.production
```

A fully qualified cluster DNS name commonly resembles:

```text
veriqta-api.production.svc.cluster.local
```

However, the cluster domain is configurable.

Do not hardcode `cluster.local` as a universal cluster domain assumption.

---

# 31. DNS SEARCH PATHS

Short Service names work because Pod DNS configuration commonly includes namespace and cluster search suffixes.

Inspect a Pod's resolver configuration:

```bash
cat /etc/resolv.conf
```

from an appropriate debugging container or Pod.

You may see:

```text
search <namespace>.svc.<cluster-domain> svc.<cluster-domain> <cluster-domain>
```

Exact contents depend on cluster configuration.

---

# 32. SAME NAME, DIFFERENT NAMESPACE

Suppose both namespaces contain:

```text
Service:
database
```

Then:

```text
production/database
```

and:

```text
staging/database
```

are different Services.

A short lookup:

```text
database
```

depends on the client's namespace search context.

Namespace must therefore be part of DNS troubleshooting.

---

# 33. DNS FAILURE VERSUS SERVICE FAILURE

These are different:

```text
curl: could not resolve host
```

and:

```text
connection refused
```

and:

```text
connection timed out
```

and:

```text
HTTP 503
```

They point toward different layers.

A name-resolution failure should first direct attention toward:

```text
DNS name

Namespace

DNS configuration

DNS service

DNS reachability
```

not immediately toward the application Deployment.

---

# 34. DNS TROUBLESHOOTING PATH

Use:

```text
Expected Name
↓
Resolver Configuration
↓
DNS Query
↓
DNS Answer
↓
Returned Address
↓
Connection Attempt
```

Useful tools, depending on the debugging image, include:

```bash
getent hosts <service-name>
```

or:

```bash
nslookup <service-name>
```

or:

```bash
dig <service-name>
```

Not every container image includes these tools.

Use a dedicated debugging Pod rather than installing troubleshooting packages into production application containers merely for convenience.

---

# 35. DNS SUCCESS DOES NOT PROVE CONNECTIVITY

Suppose:

```bash
nslookup veriqta-api
```

returns:

```text
10.96.20.10
```

You have proved:

```text
Name resolution returned an address.
```

You have not proved:

```text
Service has endpoints.

Traffic can reach endpoint.

NetworkPolicy permits traffic.

Application listens.

HTTP succeeds.
```

Know what each test proves.

---

# 36. HEADLESS SERVICES

A headless Service sets:

```yaml
clusterIP: None
```

Instead of presenting the ordinary Service virtual IP behavior, DNS can expose backend endpoint addresses directly according to the Service configuration.

Conceptually:

```text
Normal Service

DNS
↓
Service ClusterIP
↓
Service Data Plane
↓
Endpoint
```

versus:

```text
Headless Service

DNS
↓
Endpoint Addresses
```

Headless Services are useful when clients need direct endpoint discovery.

They are not simply "Services without networking."

---

# 37. NODEPORT

A `NodePort` Service makes a Service reachable using a port associated with cluster nodes, subject to cluster networking, firewall, proxy implementation, and node-address configuration.

Conceptually:

```text
Client
↓
Node IP : NodePort
↓
Service Data Plane
↓
Endpoint
↓
Pod
```

NodePort also builds on Service functionality.

---

# 38. NODEPORT IS NOT THE SAME AS CONTAINER PORT

Keep these separate:

```text
NodePort
→ port exposed through node-level Service behavior

Service port
→ Service-facing port

targetPort
→ backend endpoint port

containerPort
→ Pod specification metadata for container port
```

A possible path might be:

```text
NodeIP:31080
↓
Service:80
↓
Pod:8080
```

---

# 39. NODEPORT IMPLEMENTATION DETAILS CAN VARY

Do not assume every cluster exposes NodePort identically on every local interface.

Behavior can depend on:

```text
Service proxy implementation

Proxy mode

Node address configuration

Firewall configuration

Cluster distribution
```

Treat NodePort as a Kubernetes Service concept while verifying the implementation used by the actual cluster.

---

# 40. LOADBALANCER SERVICES

A Service of type:

```yaml
type: LoadBalancer
```

requests external load-balancer integration where the environment provides an implementation.

Conceptually:

```text
External Client
↓
External Load Balancer
↓
Kubernetes Service
↓
Backend Endpoint
↓
Pod
```

Kubernetes itself does not magically provide every environment with a physical or cloud load balancer.

The environment must provide the relevant integration or controller.

---

# 41. LOADBALANCER IS ENVIRONMENT-DEPENDENT

In a managed cloud cluster, `LoadBalancer` may cause cloud infrastructure to be provisioned.

In another environment, it may remain without an external address until an appropriate implementation exists.

Therefore:

```text
type: LoadBalancer
```

does not universally mean:

```text
A public cloud load balancer will definitely appear.
```

Always know the cluster environment.

---

# 42. EXTERNAL TRAFFIC HAS MULTIPLE POSSIBLE ENTRY MODELS

External application exposure can involve:

```text
LoadBalancer Service
```

or:

```text
External Load Balancer
↓
Ingress Controller
↓
Service
```

or:

```text
Gateway Implementation
↓
Gateway
↓
Route
↓
Service
```

The exact path depends on architecture.

Never assume every cluster uses the same ingress topology.

---

# 43. INGRESS

Ingress is a Kubernetes API for routing external HTTP and HTTPS traffic toward Services based on routing rules.

Conceptually:

```text
Client
↓
Ingress Entry Point
↓
Host / Path Rule
↓
Service
↓
Endpoint
↓
Pod
```

Ingress is particularly useful for HTTP-aware routing such as:

```text
api.example.com
→ api-service
```

and:

```text
example.com/shop
→ shop-service
```

---

# 44. INGRESS RESOURCE VERSUS INGRESS CONTROLLER

This distinction is critical.

An Ingress resource describes desired routing.

An Ingress controller implements that routing.

Therefore:

```text
Ingress YAML
≠
Traffic Router
```

A cluster can accept an Ingress resource while lacking an appropriate controller to implement it.

---

# 45. INGRESS NEEDS AN IMPLEMENTATION

Conceptually:

```text
Ingress Resource
↓
Ingress Controller Watches Resource
↓
Controller Configures Data Plane
↓
Traffic Can Be Routed
```

If the controller is absent, misconfigured, or not responsible for that Ingress, merely creating the resource does not make the route work.

---

# 46. INGRESSCLASS

Clusters can use IngressClass to identify the controller or class of ingress handling intended for an Ingress.

A route problem may therefore involve:

```text
Ingress exists
↓
Wrong or missing class
↓
Expected controller does not reconcile it
```

Always inspect which implementation is responsible for the resource.

---

# 47. INGRESS HOST ROUTING

Example concept:

```text
Host:
api.example.com
↓
Service:
veriqta-api
```

A client request must carry the expected hostname.

Testing only the entry-point IP without the correct HTTP `Host` header may exercise a different route or default backend.

This distinction is especially important when testing name-based virtual hosting.

---

# 48. INGRESS PATH ROUTING

Ingress can route based on URL path.

Conceptually:

```text
example.com/api
→ api-service
```

```text
example.com/web
→ web-service
```

Troubleshooting should verify:

```text
Hostname

Path

Path type

Backend Service

Backend port
```

A correct Service can appear broken if the request never matches its ingress route.

---

# 49. INGRESS IS PRIMARILY HTTP/HTTPS ORIENTED

Ingress is designed for HTTP and HTTPS routing.

Do not assume an Ingress resource is the generic answer for arbitrary TCP or UDP services.

Other mechanisms may be needed depending on protocol and controller capabilities.

---

# 50. INGRESS API STATUS

Ingress remains a stable Kubernetes API, but its API is frozen.

Kubernetes recommends Gateway API for ongoing evolution of Kubernetes traffic-routing APIs.

This does not mean:

```text
Ingress is removed.
```

It means:

```text
Ingress remains supported
but
new API evolution is focused on Gateway API.
```

Engineers should understand both because existing production environments continue to use Ingress extensively.

---

# 51. GATEWAY API

Gateway API is a family of Kubernetes APIs for service networking and advanced traffic routing.

A useful conceptual model separates responsibilities:

```text
Infrastructure / Cluster Networking
↓
Gateway
↓
Application Routing
↓
Route
↓
Service
```

This creates clearer ownership boundaries than placing every concern into one Ingress object.

---

# 52. GATEWAY API IS AN ADD-ON API FAMILY

Do not assume every Kubernetes cluster automatically supports Gateway API.

The required API resources and an implementation must be installed and configured.

Therefore:

```text
Kubernetes Cluster
≠
Gateway API Automatically Available
```

Verify cluster capability.

---

# 53. GATEWAY API ROLE MODEL

Gateway API intentionally supports separation of concerns between roles such as:

```text
Infrastructure Provider

Cluster Operator

Application Developer
```

Conceptually:

```text
Infrastructure / Platform Team
↓
Gateway Infrastructure
↓
Application Team
↓
Routes
↓
Services
```

This is valuable in shared production platforms where application teams should manage routing without necessarily owning the entire external networking infrastructure.

---

# 54. GATEWAY AND ROUTES

A simplified HTTP model is:

```text
GatewayClass
↓
Gateway
↓
HTTPRoute
↓
Service
```

Think of:

```text
GatewayClass
→ which implementation manages this kind of Gateway
```

```text
Gateway
→ where and how traffic is accepted
```

```text
HTTPRoute
→ how matching HTTP traffic reaches backends
```

Exact capabilities depend on Gateway API version and implementation.

---

# 55. INGRESS VERSUS GATEWAY API

At Mid-Level, understand the architectural distinction rather than memorizing feature tables.

Ingress commonly combines application routing concerns into the Ingress model.

Gateway API provides a more role-oriented and extensible model.

The practical lesson is:

```text
Existing Cluster
→ understand its Ingress architecture
```

and:

```text
Modern / evolving architecture
→ understand Gateway API
```

Do not migrate simply because one API is newer.

Migration requires compatibility, implementation, testing, operational ownership, and rollback planning.

---

# 56. EXTERNAL DNS

External DNS is conceptually separate from Kubernetes cluster DNS.

External clients may resolve:

```text
api.example.com
```

to an external load balancer or gateway address.

Internal workloads may resolve:

```text
veriqta-api.production.svc.<cluster-domain>
```

through cluster DNS.

These are different DNS systems serving different purposes.

---

# 57. COMPLETE EXTERNAL HTTP PATH

A realistic path might be:

```text
User
↓
Public DNS
↓
External Load Balancer
↓
Ingress Controller / Gateway
↓
Routing Rule
↓
Service
↓
EndpointSlice
↓
Pod IP
↓
Application Port
↓
Application
```

Every arrow represents a relationship that can fail.

---

# 58. COMPLETE INTERNAL SERVICE PATH

Internal service-to-service communication may look like:

```text
Frontend Pod
↓
Cluster DNS
↓
api.production.svc.<cluster-domain>
↓
ClusterIP
↓
Service Data Plane
↓
EndpointSlice Backend
↓
API Pod
↓
Application
```

The request may never involve an Ingress controller.

Internal clients should not automatically route through the public entry point when a suitable internal service path exists.

---

# 59. TLS

TLS can protect communication between a client and an entry point.

Conceptually:

```text
Client
↓
TLS Handshake
↓
Server Certificate
↓
Encrypted Application Traffic
```

In Kubernetes architectures, TLS may terminate at different layers.

---

# 60. TLS TERMINATION LOCATIONS

Possible models include:

```text
Client
↓ TLS
Load Balancer
↓ HTTP
Ingress
↓
Service
↓
Pod
```

or:

```text
Client
↓ TLS
Ingress Controller
↓ HTTP
Service
↓
Pod
```

or:

```text
Client
↓ TLS
Gateway
↓ TLS / HTTP
Backend
```

or end-to-end encryption models where traffic remains encrypted deeper into the path.

Do not assume where TLS terminates.

Inspect the architecture.

---

# 61. TLS TERMINATION CREATES A SECURITY BOUNDARY

If TLS terminates at an ingress proxy:

```text
Client
↓ encrypted
Ingress
↓ potentially plaintext
Backend
```

then the connection after termination has different security properties.

Ask:

```text
Where does encryption begin?

Where does it terminate?

Is backend traffic encrypted?

Who owns certificates?

Who can read plaintext?

What trust boundary exists?
```

---

# 62. TLS CERTIFICATES

For HTTPS, verify:

```text
Certificate exists

Certificate is valid for hostname

Certificate is within validity period

Trust chain is accepted

Private key matches intended certificate

Ingress / Gateway references correct secret or certificate mechanism
```

Do not reduce TLS troubleshooting to:

```text
Port 443 is open.
```

TCP connectivity and TLS success are different layers.

---

# 63. TLS FAILURE SIGNATURES

Possible TLS problems include:

```text
Hostname mismatch

Expired certificate

Untrusted issuer

Incomplete chain

Wrong certificate served

Protocol mismatch

TLS terminated at unexpected component
```

A TLS failure can occur even when:

```text
DNS
✓

TCP connection
✓
```

This is why layered troubleshooting matters.

---

# 64. TESTING TLS

Useful tools include:

```bash
curl -v https://api.example.com
```

and where appropriate:

```bash
openssl s_client -connect api.example.com:443 -servername api.example.com
```

The `-servername` value is important for servers using SNI.

Interpret what the command proves.

Do not disable certificate verification as the normal "fix."

---

# 65. SERVICE DATA PLANE

A Service object describes desired Service behavior.

Traffic still needs an implementation that turns that API state into packet forwarding behavior.

A common Kubernetes implementation is:

```text
kube-proxy
```

but clusters can use alternative implementations.

---

# 66. KUBE-PROXY CONCEPT

Conceptually:

```text
Service
+
EndpointSlices
↓
kube-proxy or alternative implementation
↓
Node networking rules / data plane
↓
Backend endpoint
```

kube-proxy watches Service and EndpointSlice information and programs the node's Service forwarding behavior.

---

# 67. KUBE-PROXY IS NOT A USER-SPACE PROXY FOR EVERY CONNECTION

The name can be misleading.

Depending on mode, kube-proxy commonly configures kernel networking mechanisms rather than receiving every application connection and proxying it through a long-running user-space process.

On Linux, implementations can use mechanisms such as:

```text
iptables

nftables
```

and historically:

```text
IPVS
```

Version and configuration matter.

Do not memorize one backend as universally true.

---

# 68. IMPLEMENTATION DETAILS CHANGE

Service implementation is version-dependent.

For example, current Kubernetes releases support multiple kube-proxy modes, while the project's direction and defaults can evolve.

IPVS mode is deprecated in current Kubernetes.

Therefore the correct Mid-Level principle is:

```text
Understand Service semantics first.
↓
Identify actual cluster implementation.
↓
Inspect implementation details only when required.
```

Do not assume every cluster uses iptables.

---

# 69. CNI CONCEPTS

Kubernetes defines networking expectations, but the Pod network requires an implementation.

On Linux clusters, Container Networking Interface integrations are commonly used by container runtimes and network implementations to configure Pod networking.

At this level, understand:

```text
Kubernetes
→ defines networking model and APIs
```

while:

```text
Network implementation
→ makes Pod networking actually work
```

---

# 70. CNI IS NOT ONE PRODUCT

CNI is an interface/specification ecosystem, not a single universal Kubernetes network.

Different clusters can use different networking implementations.

Those implementations can differ in:

```text
Routing

Encapsulation

Native routing

Policy enforcement

Observability

Encryption

Performance characteristics

Service implementation
```

Therefore:

```text
"My cluster uses Kubernetes"
```

does not tell you the complete data-plane architecture.

---

# 71. POD-TO-POD TRAFFIC

A conceptual same-node path might be:

```text
Pod A
↓
Pod Network Interface
↓
Node Networking
↓
Pod B
```

A cross-node path might resemble:

```text
Pod A
↓
Node A Networking
↓
Cluster Pod Network
↓
Node B Networking
↓
Pod B
```

The exact packet path depends on the network implementation.

Do not invent implementation details without inspecting the cluster.

---

# 72. OVERLAY VERSUS ROUTED NETWORKING AWARENESS

Some implementations may encapsulate Pod traffic through an overlay.

Others may integrate Pod routes more directly with the underlying network.

At Mid-Level, understand the distinction conceptually.

Deep routing protocol, encapsulation, eBPF, and CNI implementation internals belong later.

The troubleshooting question is:

```text
What network implementation is this cluster actually using?
```

---

# 73. NETWORKPOLICY

NetworkPolicy provides Kubernetes API objects for controlling allowed traffic at IP and port layers for selected Pods.

It can control:

```text
Ingress
→ traffic entering selected Pods
```

and:

```text
Egress
→ traffic leaving selected Pods
```

But policy enforcement requires a networking implementation that supports NetworkPolicy.

---

# 74. NETWORKPOLICY OBJECT EXISTENCE DOES NOT PROVE ENFORCEMENT

A cluster can accept:

```yaml
kind: NetworkPolicy
```

while the networking implementation does not enforce NetworkPolicy.

Therefore:

```text
NetworkPolicy Created
≠
Traffic Definitely Filtered
```

Before depending on policy for security, verify implementation support.

---

# 75. DEFAULT NETWORKPOLICY BEHAVIOR

In the absence of applicable NetworkPolicies, Pods are normally non-isolated for ingress and egress at the Kubernetes NetworkPolicy layer.

Once a policy selects a Pod for a direction, restrictions for that direction apply according to the allowed rules.

This transition is important:

```text
No applicable ingress isolation
→ traffic allowed by NetworkPolicy layer
```

versus:

```text
Pod selected for ingress isolation
→ only allowed ingress remains
```

---

# 76. INGRESS AND EGRESS ISOLATION ARE SEPARATE

A Pod can be:

```text
isolated for ingress
```

while:

```text
non-isolated for egress
```

or the reverse.

Do not assume one NetworkPolicy automatically creates both directions of isolation.

Read:

```text
podSelector

policyTypes

ingress

egress
```

carefully.

---

# 77. NETWORKPOLICIES ARE ADDITIVE

Applicable NetworkPolicies combine allowed traffic.

They are not processed as an ordered firewall rule list where one policy necessarily overrides another.

Conceptually:

```text
Policy A allows source A
+
Policy B allows source B
=
A and B are allowed
```

where those policies apply.

Do not search for a "first matching NetworkPolicy."

---

# 78. BOTH SIDES CAN MATTER

For Pod-to-Pod communication:

```text
Source Pod
↓
Source Egress Policy
↓
Network
↓
Destination Ingress Policy
↓
Destination Pod
```

For the connection to succeed, the relevant source egress and destination ingress permissions must allow it where those Pods are isolated.

Troubleshooting only the destination policy can miss the source-side restriction.

---

# 79. BASIC DEFAULT-DENY INGRESS

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: veriqta-network-lab
spec:
  podSelector: {}
  policyTypes:
    - Ingress
```

This selects all Pods in the namespace for ingress isolation without defining allowed ingress traffic.

Use only in a disposable lab until the effects are understood.

---

# 80. DEFAULT-DENY EGRESS CAN BREAK DNS

This is one of the most important NetworkPolicy lessons.

Suppose:

```text
Client Pod
↓
DNS Query
↓
Cluster DNS
```

Then a default-deny egress policy can prevent the client from reaching cluster DNS unless DNS traffic is explicitly allowed.

The symptom may appear as:

```text
Service name no longer resolves.
```

The root cause can be:

```text
NetworkPolicy blocked DNS egress.
```

not:

```text
CoreDNS is broken.
```

---

# 81. NETWORKPOLICY SELECTORS

Policies can select traffic using concepts such as:

```text
podSelector

namespaceSelector

ipBlock
```

These answer different questions.

For example:

```text
Which Pods?

Which namespaces?

Which IP ranges?
```

Be precise with YAML structure because combining selectors incorrectly can change policy meaning.

---

# 82. LABELS ARE SECURITY-RELEVANT

Part 11 used labels for workload organization and selection.

NetworkPolicy can make labels part of traffic authorization.

Therefore:

```text
Wrong Label
```

can become:

```text
Wrong Security Behavior
```

Label governance becomes more important as the platform grows.

---

# 83. NETWORKPOLICY IS NOT APPLICATION AUTHORIZATION

NetworkPolicy can restrict network reachability.

It does not replace:

```text
Authentication

Authorization

Application permissions

TLS identity

API authorization
```

A Pod being allowed to establish a network connection does not mean it should be authorized to perform every application operation.

Use defense in depth.

---

# 84. NETWORKPOLICY IS NOT AN HTTP POLICY ENGINE

Standard Kubernetes NetworkPolicy primarily operates at network layers such as:

```text
IP

Protocol

Port
```

It does not natively express ordinary HTTP concepts such as:

```text
GET /admin allowed

POST /payments denied
```

Higher-layer controls require other mechanisms.

# 86. WHAT DNS PROVES

Test:

```bash

```

Possible evidence:

```text

```

Conclusion:

```text

```

Do not conclude:

```text

```

# 87. WHAT TCP CONNECTIVITY PROVES

Suppose:

```bash
nc -vz api.example.com 443
```

succeeds.

This can indicate TCP connectivity to that destination and port.

It does not prove:

```text
TLS certificate is valid.

Ingress route is correct.

Service has endpoints.

Application returns correct response.
```

Also note that `nc` implementations and flags vary across operating systems and images.

---

# 88. WHAT TLS SUCCESS PROVES

A successful TLS handshake can prove that:

```text
A TLS-speaking endpoint was reached
and
certificate validation succeeded under the client's trust conditions.
```

It does not prove:

```text
Correct backend Service received the request.
```

HTTP routing still comes afterward.

---

# 89. WHAT HTTP RESPONSE PROVES

An HTTP response proves that an HTTP-speaking component returned a response.

It does not automatically prove the origin application returned it.

For example:

```text
404
```

could come from:

```text
Ingress default backend

Gateway

Reverse proxy

Application
```

Determine which component generated the response.

```text
↓

```

If direct Pod connectivity works but Service connectivity fails:

```text

likely works

```

This is a powerful isolation technique.

# 92. PORT-FORWARD AS A DIAGNOSTIC TOOL

# 101. TIMEOUT VERSUS REFUSED CONNECTION

A connection refusal and timeout are different observations.

A refusal often indicates that the destination path responded but nothing accepted the requested connection, although exact behavior can vary by networking implementation.

A timeout suggests that no successful response arrived before the client deadline.

Possible timeout causes include:

```text
Dropped traffic

NetworkPolicy

Routing problem

Firewall

Unreachable endpoint

Application accepting but not responding
```

Do not treat timeout as proof of one specific root cause.

---

# 102. HTTP 502, 503, AND 504

Proxy or gateway status codes can provide useful clues, but their exact meaning depends on the component producing them.

Common interpretations include:

```text
502
→ upstream response problem
```

```text
503
→ upstream unavailable / no usable backend / service unavailable
```

```text
504
→ upstream did not respond before gateway timeout
```

Do not diagnose from the number alone.

First identify:

```text
Which component returned the response?
```

---

# 103. OBSERVATION POINTS

A production request path should be observable at multiple boundaries.

Possible observation points include:

```text
Client

DNS

External Load Balancer

Ingress / Gateway

Service

EndpointSlice

Pod

Application

Downstream Dependency
```

If telemetry exists at only one point, localization becomes difficult.

---

# 104. REQUEST IDENTIFIERS

For HTTP systems, request or correlation identifiers can help trace a request across components.

Conceptually:

```text
Client Request ID
↓
Ingress Log
↓
Application Log
↓
Dependency Log
```

This helps distinguish:

```text
Request never reached application
```

from:

```text
Request reached application and failed downstream.
```

Observability engineering is covered more deeply later.

---

# 105. PACKET CAPTURE AWARENESS

When higher-level evidence is insufficient, packet capture can help answer questions such as:

```text
Did packets leave the source?

Did they reach the node?

Did SYN receive a response?

Did traffic reach the destination?
```

Tools such as `tcpdump` may be useful where permitted.

But packet capture requires:

```text
correct interface

correct namespace

appropriate permissions

correct filter

security approval
```

and TLS encryption limits visibility into application payload.

Do not begin every Kubernetes incident with packet capture.

Use it when simpler evidence cannot answer the question.

---

# 106. THE EVIDENCE LADDER

A practical Kubernetes connectivity investigation can follow:

```text
1. Define source and destination

2. Define protocol and port

3. Define expected path

4. Test name resolution

5. Inspect Service

6. Inspect EndpointSlices

7. Inspect backend Pods

8. Verify application listening behavior

9. Test direct backend connectivity

10. Test Service connectivity

11. Inspect NetworkPolicy

12. Inspect Ingress / Gateway

13. Inspect TLS

14. Inspect data-plane implementation if necessary

15. Capture packets only when justified
```

Do not jump directly to CNI internals when the Service selector is wrong.

# 154. SERVICE TRAFFIC POLICY AWARENESS

Services can have traffic policies that influence which ready endpoints are eligible for internal or external traffic.

At Mid-Level, recognize fields such as:

```text
internalTrafficPolicy

externalTrafficPolicy
```

and understand that they can affect traffic behavior.

Do not change them without understanding the availability and source-address consequences in the specific environment.

---

# 155. `EXTERNALTRAFFICPOLICY: LOCAL` AWARENESS

With appropriate Service types, `externalTrafficPolicy: Local` can constrain external traffic to node-local ready endpoints.

This can affect:

```text
Source IP preservation

Load-balancer behavior

Traffic distribution

Node eligibility

Availability during endpoint movement
```

Detailed production traffic engineering belongs at Senior level.

At Mid-Level, know to inspect the field when external traffic behaves differently across nodes.

---

# 156. SESSION AFFINITY AWARENESS

Services can support client-IP-based session affinity.

This can influence which backend receives connections.

Do not assume Service traffic always distributes every request uniformly across Pods.

Long-lived connections, client behavior, proxying, and affinity can all affect observed distribution.

---

# 157. LONG-LIVED CONNECTIONS

A Service generally selects a backend as connections are established.

A long-lived connection can continue communicating with one backend rather than being redistributed on every application message.

Therefore:

```text
3 Pods
```

does not mean:

```text
One existing connection is continuously balanced across all 3.
```

This matters for:

```text
WebSockets

gRPC streams

Database connections

Persistent HTTP connections
```

---

# 158. READINESS AND TRAFFIC DRAINING

During termination and rollout, endpoint state changes interact with traffic routing.

Production systems need to consider:

```text
Pod becomes unavailable for new traffic

Existing requests / connections

Termination signal

Application drain behavior

Grace period
```

Do not assume removing an endpoint instantly eliminates every packet or every existing connection.

Graceful termination requires coordination across layers.

---

# 159. IPV4 AND IPV6 AWARENESS

Kubernetes can operate with:

```text
IPv4

IPv6

Dual-stack
```

depending on cluster configuration.

Do not assume every Pod, Service, or endpoint uses IPv4.

EndpointSlices identify address family.

When diagnosing modern clusters, inspect actual addresses rather than assuming:

```text
10.x.x.x
```

must always appear.

---

# 160. SERVICE ADDRESS FAMILY

A Service may be single-stack or dual-stack depending on cluster capability and Service configuration.

At Mid-Level, understand:

```text
DNS may return A records

DNS may return AAAA records

A cluster may use both
```

Client behavior can differ between address families.

Deep dual-stack networking belongs later.

---

# 161. CONTROL PLANE VERSUS DATA PLANE

This distinction is extremely useful.

Control-plane state includes objects such as:

```text
Service

EndpointSlice

Ingress

Gateway

NetworkPolicy
```

Data plane is what actually carries or filters traffic.

Therefore:

```text
Correct API Object
≠
Correct Packet Forwarding
```

A controller or networking implementation must translate desired state into working behavior.

---

Suppose:


Then:

```text

✓

✗
```

This is when deeper inspection of kube-proxy or the alternative Service implementation becomes justified.

Do not begin there before verifying simpler layers.

# 163. DATA-PLANE IMPLEMENTATION AWARENESS

# 168. DNS IS PART OF RELIABILITY

Applications often depend heavily on DNS.

```text

cannot find

```

Monitor and troubleshoot DNS as infrastructure, not as an afterthought.

# 169. RETRIES CAN AMPLIFY NETWORK INCIDENTS

Suppose:

```text
Backend slows
↓
Clients timeout
↓
Every client retries immediately
↓
Backend receives more traffic
↓
Latency increases
↓
More retries
```

This is a retry storm.

Networking reliability involves application behavior as well as packet delivery.

Retries should be:

```text
bounded

intentional

backed off

appropriate to operation safety
```

Deep distributed-system retry engineering comes later.

---

# 170. TIMEOUTS DEFINE FAILURE BOUNDARIES

A request path can contain multiple timeouts:

```text

Ingress Timeout

Application Timeout

Dependency Timeout
```

If these are poorly aligned, one component can give up while another continues processing.

When troubleshooting:

```text
Which component timed out waiting for what?
```

is often more useful than:

```text
Why is networking slow?
```
