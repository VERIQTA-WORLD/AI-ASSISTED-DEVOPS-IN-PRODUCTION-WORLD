# PART 6: CLOUD INFRASTRUCTURE ENGINEERING

## Goal

Move from basic cloud resource operation to designing, building, maintaining, verifying, and troubleshooting the infrastructure required to run an application safely in a cloud environment.

At Junior level, cloud work often begins with individual resources:

```text
Create a virtual machine

Create a network

Create a storage bucket

Create a firewall rule

Start a database

Configure DNS
```

Those skills are necessary, but production infrastructure cannot be understood as a collection of isolated cloud objects.

A production service depends on relationships:

```text
Identity
↓
Cloud Account Boundary
↓
Region
↓
Virtual Network
↓
Subnets
↓
Routes
↓
Gateways
↓
Security Controls
↓
Load Balancer
↓
Compute
↓
Storage / Database
↓
DNS
↓
Application
```

A failure in one relationship can make healthy resources unusable.

A virtual machine can be running while the application remains unreachable.

A database can be healthy while the application cannot authenticate to it.

A load balancer can exist while every backend target is unhealthy.

A private workload can have correct security rules while lacking a usable route to its dependency.

A storage resource can exist while the workload identity has no permission to access it.

A deployment can be architecturally correct while failing because the account has reached a quota.

Mid-Level cloud engineering therefore requires a change in thinking:

```text
Resource Operation
↓
Resource Relationships
↓
Traffic Flow
↓
Identity Flow
↓
Failure Domains
↓
Availability
↓
Security
↓
Operational Verification
↓
Cost
```

The objective is not to memorize every service offered by every cloud provider.

The objective is to understand the infrastructure system well enough to reason about what happens when it works and when it fails.

---

# 1. CLOUD INFRASTRUCTURE IS A SYSTEM

Consider a production web application.

A simplified request may travel through:

```text
User
↓
DNS
↓
Public IP / Public Endpoint
↓
Load Balancer
↓
Network Security
↓
Private Application Workload
↓
Database
```

The application workload may also require outbound access:

```text
Application
↓
Private Subnet
↓
Route
↓
NAT / Egress Mechanism
↓
External API
```

It may retrieve objects:

```text
Application
↓
Workload Identity
↓
Object Storage API
↓
Bucket / Container / Object
```

It may attach persistent block storage:

```text
Compute
↓
Block Storage
↓
Filesystem
↓
Application Data
```

These are not separate topics.

They form the operating environment of the service.

The first Mid-Level cloud engineering principle is:

> Never troubleshoot a cloud resource without understanding the relationships around it.

---

# 2. THE CLOUD INFRASTRUCTURE REASONING MODEL

For each infrastructure component, determine:

```text
What is it?
↓
Where does it exist?
↓
What contains it?
↓
What does it depend on?
↓
What depends on it?
↓
How is traffic routed to it?
↓
Which identity operates it?
↓
Which security controls apply?
↓
Which failure domain contains it?
↓
How is it observed?
↓
How is it recovered?
↓
What does it cost?
```

This model prevents console-driven troubleshooting.

---

# 3. CLOUD PROVIDER TERMINOLOGY

Major cloud providers use different terminology for similar organizational concepts.

At a simplified level:

```text
AWS
Account

Microsoft Azure
Subscription

Google Cloud
Project
```

These are not technically identical constructs.

Do not treat the words as interchangeable in provider-specific implementation.

They are useful here as examples of boundaries within which cloud resources, permissions, quotas, billing relationships, and policies may operate.

Always use the provider's actual resource model when implementing infrastructure.

---

# 4. ACCOUNTS, PROJECTS, AND SUBSCRIPTIONS

A cloud environment needs an administrative and resource boundary.

Depending on provider and organization, this may help separate:

- production
- staging
- development
- security
- networking
- shared services
- experimentation
- different business units

A weak environment might place everything together without deliberate boundaries:

```text
One Cloud Boundary
├── Production
├── Development
├── Experiments
├── Personal Test Resources
└── Shared Infrastructure
```

This increases the possibility of:

- permission mistakes
- accidental deletion
- unclear ownership
- confusing costs
- quota contention
- policy inconsistency
- larger blast radius

At Mid-Level, understand the boundary in which the service operates even if organization-wide account architecture belongs to more senior scope.

---

# 5. KNOW YOUR CURRENT CLOUD CONTEXT

Before performing cloud operations, determine:

```text
Which identity am I using?

Which account/project/subscription am I targeting?

Which region am I targeting?

Which environment is this?

What permissions do I have?
```

Never assume the current CLI context.

A correct command against the wrong account can be more dangerous than an incorrect command that fails immediately.

---

# 6. RESOURCE HIERARCHY

Cloud resources usually exist within some form of hierarchy.

Conceptually:

```text
Organization
↓
Administrative Boundary
↓
Region
↓
Network
↓
Subnet
↓
Resource
```

Real provider hierarchies differ.

Some resources are:

- global
- regional
- zonal

This distinction affects:

- failure behavior
- naming
- quotas
- placement
- availability
- recovery

---

# 7. REGIONS

A region is a provider-defined geographic infrastructure location.

Region selection affects:

- latency
- service availability
- pricing
- regulatory requirements
- data location
- disaster recovery
- network architecture
- dependency placement

Do not choose a region only because it is first in a console menu.

Ask:

```text
Where are the users?

Where are the dependencies?

Which services are available?

What are the data-location requirements?

What latency is acceptable?

What failure assumptions exist?

What does this region cost?
```

---

# 8. AVAILABILITY ZONES

Cloud regions commonly expose multiple failure-domain locations often called availability zones or zones.

Conceptually:

```text
Region
├── Availability Zone A
├── Availability Zone B
└── Availability Zone C
```

The purpose is to make it possible to distribute workloads across separate infrastructure failure domains.

However, exact zone implementation differs by provider and sometimes by service.

Do not assume:

```text
Three Zones
=
Every Resource Automatically Uses Three Zones
```

A resource may be:

- zonal
- regional
- zone-redundant
- global
- provider-managed across failure domains

Verify the specific service.

---

# 9. FAILURE-DOMAIN THINKING

Suppose an application has three instances:

```text
Region
└── Zone A
    ├── App 1
    ├── App 2
    └── App 3
```

There are three application instances.

But all three share the same zonal failure domain.

If Zone A becomes unavailable:

```text
App 1
→ unavailable

App 2
→ unavailable

App 3
→ unavailable
```

Instance count alone does not provide failure-domain separation.

A stronger design may distribute instances:

```text
Region
├── Zone A
│   └── App 1
│
├── Zone B
│   └── App 2
│
└── Zone C
    └── App 3
```

Now a single-zone failure does not necessarily remove every application instance.

---

# 10. REDUNDANCY IS NOT JUST RESOURCE COUNT

Do not ask only:

```text
How many instances exist?
```

Ask:

```text
Where are they?

Which dependencies do they share?

Which network path do they share?

Which storage do they share?

Which load balancer do they share?

Which identity system do they depend on?

Which database do they depend on?
```

Three application instances behind one failed dependency may still produce total service failure.

---

# 11. MULTI-ZONE DOES NOT MEAN MULTI-REGION

These are different designs.

```text
Multi-Zone
=
Multiple failure domains inside a region
```

while:

```text
Multi-Region
=
Infrastructure across separate regions
```

Do not use the terms interchangeably.

Multi-region architecture introduces significantly more complexity and belongs primarily to later reliability and architecture discussions.

At this stage, understand the distinction.

---

# 12. VIRTUAL NETWORKS

Cloud workloads commonly operate inside software-defined virtual networks.

Provider terminology differs.

Examples include concepts such as:

```text
AWS VPC

Azure Virtual Network

Google Cloud VPC Network
```

These implementations are not identical.

The shared engineering question is:

```text
What network boundary contains the workload,
and how does traffic move through it?
```

---

# 13. ADDRESS SPACE

A virtual network normally requires IP addressing.

Example private address space:

```text
10.20.0.0/16
```

It may be divided into subnets such as:

```text
10.20.10.0/24

10.20.20.0/24

10.20.30.0/24

10.20.40.0/24
```

Subnet planning affects:

- workload placement
- route association
- security boundaries
- address capacity
- future growth
- connectivity with other networks

---

# 14. ADDRESS PLANNING

Do not choose network ranges randomly.

Consider:

```text
Current Workloads

Expected Growth

Other Cloud Networks

On-Premises Networks

VPN Connectivity

Peering

Future Environments
```

Overlapping address spaces can complicate later connectivity.

For example:

```text
Production
10.0.0.0/16

Shared Services
10.0.0.0/16
```

may create routing problems if direct network connectivity is later required.

At Mid-Level, recognize address planning as an engineering decision rather than a form field.

---

# 15. SUBNETS

A subnet divides network address space into smaller network segments.

A production environment might use:

```text
Virtual Network
├── Public / Edge Subnet A
├── Public / Edge Subnet B
├── Private Application Subnet A
├── Private Application Subnet B
├── Private Data Subnet A
└── Private Data Subnet B
```

The exact layout depends on provider and workload requirements.

Do not copy this structure without understanding why each subnet exists.

---

# 16. PUBLIC AND PRIVATE ARE DESIGN PROPERTIES

The labels:

```text
public subnet

private subnet
```

are convenient architectural language.

But the real behavior depends on:

- routing
- public addressing
- gateways
- provider behavior
- firewall/security policy

Do not assume that a subnet becomes secure merely because it is named:

```text
private-subnet
```

Names do not enforce network behavior.

---

# 17. PUBLIC APPLICATION ENTRY POINT

A common production pattern is:

```text
Internet
↓
Public Load Balancer
↓
Private Application Tier
```

The application instances themselves do not necessarily need direct inbound public exposure.

This reduces unnecessary public attack surface.

---

# 18. PRIVATE APPLICATION TIER

Application workloads may reside in private network locations while still requiring:

- package repositories
- external APIs
- telemetry endpoints
- cloud APIs
- software registries

Therefore:

```text
No Direct Public Inbound
```

does not necessarily mean:

```text
No Outbound Connectivity
```

Inbound and outbound requirements must be designed separately.

---

# 19. ROUTE TABLES

Routing determines where network traffic is sent.

A conceptual route table may contain:

```text
Destination        Next Hop

10.20.0.0/16       Local Network

0.0.0.0/0          Internet/Egress Gateway
```

Provider route syntax and behavior differ.

The important reasoning model is:

```text
Destination IP
↓
Matching Route
↓
Next Hop
↓
Next Network Boundary
```

---

# 20. ROUTING IS DIRECTIONAL

When troubleshooting:

```text
A cannot reach B
```

do not inspect only A's outbound path.

Successful communication generally requires a valid path and permitted traffic behavior for the complete exchange.

Think:

```text
Source
↓
Forward Path
↓
Destination
↓
Return Path
↓
Source
```

Cloud networking can hide parts of this through managed services, but the principle remains important.

---

# 21. DEFAULT ROUTES

A route such as:

```text
0.0.0.0/0
```

matches IPv4 destinations not covered by more specific routes according to routing selection behavior.

It is often used to represent a default route.

Do not interpret it automatically as:

```text
Allow all traffic.
```

Routing and security policy are different concerns.

A route determines where traffic should go.

A security control determines whether traffic is permitted under its policy.

---

# 22. GATEWAYS

Gateways connect network boundaries.

Depending on provider and design, gateway concepts may include:

- internet connectivity
- NAT
- VPN
- private connectivity
- transit routing

Do not use the generic word "gateway" as if all gateway services behave identically.

Determine:

```text
What traffic does this gateway handle?

Inbound?

Outbound?

Private?

Internet?

Translated?

Encrypted?

Transitive?
```

---

# 23. INTERNET CONNECTIVITY

Public-facing services require a path from users to the service.

Conceptually:

```text
Internet
↓
Public Endpoint
↓
Network Boundary
↓
Load Balancer
↓
Application
```

For every public service, determine exactly which component owns the public exposure.

Avoid exposing every application instance individually when a controlled public entry point is sufficient.

---

# 24. NAT

Network Address Translation is commonly used when private workloads require outbound communication without receiving unsolicited direct public inbound connections through the NAT mechanism.

Conceptually:

```text
Private Application
10.20.20.15
↓
NAT / Egress Service
↓
Public Source Address
↓
Internet
```

The return traffic for the established outbound flow is translated back toward the private workload according to the service's behavior.

---

# 25. NAT IS NOT UNIVERSAL ACROSS PROVIDERS

Cloud NAT implementations differ.

Do not memorize:

```text
NAT gateway always lives in a public subnet.
```

as a universal cloud rule.

Provider capabilities evolve and differ.

Instead learn:

```text
Private Workload
↓
Route / Egress Selection
↓
Provider NAT Mechanism
↓
External Destination
```

Then verify the implementation for the provider and service version being used.

---

# 26. NAT FAILURE DOMAIN

A NAT or egress component can become part of the service's availability path.

Ask:

```text
What happens if this egress mechanism fails?

Which workloads depend on it?

Is it zonal or regional?

Is redundancy provider-managed?

Are private workloads in other zones dependent on it?
```

Never assume a managed service automatically provides the failure isolation required by the application.

---

# 27. SECURITY CONTROLS

Cloud network security commonly includes controls applied at different layers.

Depending on provider, these may include:

- instance/interface-level rules
- subnet-level rules
- firewall policies
- network ACL-style controls
- managed firewall services

Provider semantics differ.

Important differences may include whether a control is:

```text
Stateful

or

Stateless
```

and where it is applied.

---

# 28. STATEFUL SECURITY CONCEPT

A stateful control tracks connection state.

Conceptually:

```text
Allowed Outbound Request
↓
Connection State Remembered
↓
Associated Return Traffic Permitted
```

Exact behavior depends on the provider service.

---

# 29. STATELESS SECURITY CONCEPT

A stateless control evaluates traffic independently according to its rule model.

This may require explicit consideration of traffic in both directions.

Do not apply security-group assumptions to a network ACL or firewall product without verifying its semantics.

---

# 30. LEAST NETWORK EXPOSURE

Avoid:

```text
Source:
Anywhere

Port:
Everything
```

unless the requirement genuinely demands it and the risk is understood.

Prefer expressing actual communication relationships.

For example:

```text
Internet
→ Load Balancer
→ HTTPS

Load Balancer
→ Application
→ Application Port

Application
→ Database
→ Database Port
```

This makes the architecture easier to understand and reduces unnecessary exposure.

---

# 31. SECURITY RULES SHOULD EXPRESS INTENT

A rule should answer:

```text
Who needs to communicate?

With what destination?

Using which protocol?

On which port?

Why?
```

If nobody can explain why a rule exists, it should be investigated.

---

# 32. COMPUTE

Cloud compute may include:

- virtual machines
- managed instance groups
- scale sets
- containers
- serverless compute

This Part focuses on infrastructure relationships rather than every compute product.

For a compute workload, understand:

```text
Image

CPU

Memory

Network Interface

Subnet

Identity

Storage

Security

Bootstrap

Application Runtime

Health
```

---

# 33. INSTANCE SIZE IS NOT JUST PERFORMANCE

Compute selection affects:

- CPU
- memory
- network capacity
- storage capability
- available architecture
- cost

Do not choose instance size only because:

```text
larger = faster
```

The workload's actual resource behavior should guide selection.

---

# 34. COMPUTE IMAGES

Virtual machines commonly start from images.

Images may define:

- operating system
- installed packages
- security baseline
- runtime dependencies

Ask:

```text
Who maintains the image?

How old is it?

How is it patched?

What software is already installed?

Can the build be reproduced?
```

An unknown image is part of the infrastructure risk.

---

# 35. BOOTSTRAP AND INITIALIZATION

Compute instances may need initialization at launch.

Examples include:

- installing packages
- writing configuration
- starting agents
- retrieving runtime configuration

Do not turn bootstrap scripts into uncontrolled deployment systems.

Bootstrap should have:

- clear responsibility
- logs
- failure detection
- repeatability awareness
- secret-handling controls

---

# 36. INSTANCE METADATA

Cloud compute platforms commonly expose metadata about running workloads.

Metadata may include information such as:

- instance identity
- network information
- region or zone
- attached identity information
- initialization data

Metadata mechanisms are provider-specific and security-sensitive.

Do not expose metadata endpoints through application proxies or retrieve sensitive metadata casually.

Treat metadata access as part of the workload security model.

---

# 37. AUTOSCALING CONCEPTS

Autoscaling changes compute capacity according to defined conditions.

Conceptually:

```text
Demand Increases
↓
Scaling Signal
↓
Desired Capacity Increases
↓
New Instances Start
↓
Health Checks Pass
↓
Instances Receive Traffic
```

Scale-in reverses part of this process.

---

# 38. AUTOSCALING IS NOT INSTANT

New capacity may require time for:

- provisioning
- boot
- package initialization
- application startup
- registration
- health checks
- cache warming

Therefore:

```text
CPU High
↓
Add Instance
```

does not imply immediate recovery.

---

# 39. AUTOSCALING REQUIRES HEALTHY APPLICATION DESIGN

If the application requires local manual configuration on every new server, automatic scaling becomes difficult.

Autoscaling works best when instances can be created reproducibly.

Ask:

```text
Can a new instance become operational without a human logging into it?
```

---

# 40. LOAD BALANCING

A load balancer distributes traffic across eligible backend targets.

Conceptually:

```text
Clients
        ↓
  Load Balancer
   ↙        ↘
App A      App B
```

Production load balancing may also provide:

- health checking
- TLS termination
- routing rules
- connection handling
- metrics

Capabilities vary by provider and load balancer type.

---

# 41. LOAD BALANCER FRONTEND AND BACKEND

Think in two directions.

Frontend:

```text
Client
↓
Listener / Frontend
↓
Load Balancer
```

Backend:

```text
Load Balancer
↓
Target Group / Backend Pool
↓
Application Target
```

A working frontend does not prove the backend is healthy.

---

# 42. HEALTH CHECKS

A load balancer usually needs a way to determine whether a target should receive traffic.

A health check may evaluate:

```text
Protocol

Port

Path

Expected Response

Interval

Timeout

Success Threshold

Failure Threshold
```

Exact settings depend on provider and service.

---

# 43. HEALTH CHECK DESIGN

Weak health endpoint:

```text
HTTP 200
```

returned regardless of application state.

Potentially stronger health evaluation:

```text
Is the process serving?

Is the required application initialization complete?

Can the service perform the minimum operation required to serve traffic?
```

Do not make health checks unnecessarily expensive or dependent on every external system either.

Health-check design is an application and reliability decision.

---

# 44. UNHEALTHY TARGET DOES NOT MEAN LOAD BALANCER FAILURE

Suppose:

```text
Load Balancer
→ reachable

Target
→ unhealthy
```

Possible causes include:

- wrong health-check port
- wrong health-check path
- application not listening
- security rule blocking health checks
- application returning failure
- wrong target registration
- startup incomplete

Investigate the target path before replacing the load balancer.

---

# 45. OBJECT STORAGE

Object storage is designed around objects stored within provider-defined containers such as buckets.

Typical uses include:

- static assets
- backups
- logs
- build artifacts
- exports
- large files

Object storage is not the same abstraction as a local block device.

Do not treat:

```text
Object Storage
```

as:

```text
Remote Hard Drive
```

without understanding the service semantics.

---

# 46. OBJECT STORAGE ACCESS

Object access may depend on:

```text
Workload Identity
↓
Permission Policy
↓
Storage Resource Policy
↓
Encryption Permissions
↓
Object
```

A permission failure may therefore occur even when:

```text
Network works

Bucket exists

Object exists
```

Identity is part of infrastructure troubleshooting.

---

# 47. OBJECT STORAGE SECURITY

Consider:

- public access
- workload access
- encryption
- versioning
- lifecycle
- retention
- logging
- deletion protection where supported

Never assume a bucket/container is private simply because its name looks internal.

Verify policy.

---

# 48. BLOCK STORAGE

Block storage provides block-device semantics to compute workloads.

Conceptually:

```text
Cloud Block Volume
↓
Attached to Compute
↓
Operating System Block Device
↓
Partition / Filesystem
↓
Mount
↓
Application
```

A cloud console showing:

```text
Attached
```

does not prove:

```text
Filesystem is mounted and application can write.
```

---

# 49. STORAGE TROUBLESHOOTING ACROSS LAYERS

If an application reports:

```text
No space left on device
```

investigate:

```text
Cloud Volume Exists?
↓
Correct Volume Attached?
↓
OS Sees Device?
↓
Partition Correct?
↓
Filesystem Correct?
↓
Mounted?
↓
Capacity Available?
↓
Inodes Available?
↓
Permissions Correct?
```

Cloud and Linux troubleshooting meet here.

---

# 50. STORAGE PERFORMANCE

Block storage may have provider-defined limits for:

- throughput
- IOPS
- size
- attachment
- instance compatibility

A larger volume or different storage class may have different performance characteristics.

Do not assume:

```text
Disk exists
=
Disk is fast enough
```

---

# 51. MANAGED DATABASES

Managed database services reduce some operational responsibility.

The provider may manage parts of:

- underlying hosts
- infrastructure replacement
- patching mechanisms
- backups
- replication capabilities

But the application team still has responsibilities.

These may include:

- database selection
- network access
- authentication
- schema
- connection behavior
- backup policy
- restore testing
- performance
- cost
- application compatibility

Managed does not mean ownerless.

---

# 52. DATABASE NETWORK PLACEMENT

A common production model is:

```text
Internet
    ↓
Public Entry Point
    ↓
Private Application
    ↓
Private Database
```

The database usually does not require direct public client access for a normal application architecture.

Access should reflect the required relationship:

```text
Application Tier
→ Database Port
→ Database
```

---

# 53. DATABASE AVAILABILITY

A managed database may offer:

- single-zone placement
- multi-zone resilience
- replicas
- automated backups
- failover capabilities

These features differ by engine, provider, region, and service tier.

Never write:

```text
Managed database
=
Highly available
```

without verifying its configuration.

---

# 54. DATABASE BACKUP IS NOT DATABASE RECOVERY

A backup existing does not prove recovery works.

The engineering lifecycle is:

```text
Backup
↓
Retention
↓
Restore Procedure
↓
Restore Test
↓
Application Validation
```

Recovery is demonstrated by restoration and verification.

---

# 55. DNS

DNS connects human-readable names to service endpoints.

A production flow may begin:

```text
app.example.com
↓
DNS
↓
Load Balancer Endpoint
↓
Application
```

DNS configuration therefore belongs to application infrastructure.

---

# 56. DNS RECORD OWNERSHIP

Know:

```text
Which zone contains the record?

Which account owns the zone?

Which record points to the application?

What is its TTL?

Who can change it?

What happens during rollback?
```

DNS changes can affect production traffic globally.

---

# 57. DNS AND LOAD BALANCERS

A common pattern is:

```text
Application DNS Name
↓
Provider-Supported DNS Mapping
↓
Load Balancer
```

Do not hard-code transient infrastructure addresses if the provider expects a managed DNS target or another stable mechanism.

Use the provider-supported method.

---

# 58. IDENTITY

Cloud infrastructure has two major security questions:

```text
Who are you?
```

and:

```text
What are you allowed to do?
```

Identity and authorization affect:

- engineers
- CI/CD
- virtual machines
- containers
- applications
- automation
- cloud services

---

# 59. HUMAN AND WORKLOAD IDENTITIES

Distinguish:

```text
Human Identity
```

from:

```text
Workload Identity
```

An application should not normally operate using an engineer's personal administrative credentials.

Workloads should use identities intended for workloads.

---

# 60. LEAST PRIVILEGE

A reporting service that only needs to read objects should not automatically receive:

```text
Delete all storage

Modify IAM

Create compute

Change networking
```

Permissions should reflect actual responsibilities.

The relationship is:

```text
Required Operation
↓
Required Permission
↓
Assigned Identity
```

---

# 61. IDENTITY IS PART OF THE REQUEST PATH

Consider:

```text
Application
↓
Network reaches object storage
↓
TLS succeeds
↓
Storage API receives request
↓
Identity evaluated
↓
Permission denied
```

This is not a routing failure.

Cloud troubleshooting must distinguish connectivity from authorization.

---

# 62. TEMPORARY CREDENTIALS

Where supported, workload identity mechanisms and temporary credentials can reduce dependence on long-lived static credentials.

Avoid embedding permanent secrets in:

- machine images
- source code
- bootstrap scripts
- repositories

Use the provider's supported identity mechanisms.

---

# 63. ENCRYPTION

Cloud encryption is commonly discussed in two broad contexts:

```text
Encryption in Transit
```

and:

```text
Encryption at Rest
```

In-transit encryption protects data moving between systems through protocols such as TLS.

At-rest encryption protects stored data according to the storage service's encryption model.

---

# 64. ENCRYPTION DOES NOT REMOVE ACCESS CONTROL

Encrypted storage can still be accessed by an identity with valid authorization.

Therefore:

```text
Encryption
≠
Authorization
```

Both matter.

---

# 65. ENCRYPTION KEYS

Cloud services may support:

- provider-managed keys
- customer-managed keys
- service-specific key models

Customer-managed keys can provide additional control but also introduce additional responsibilities:

- permissions
- rotation
- availability
- deletion protection
- audit
- recovery

More control creates more operational responsibility.

---

# 66. KEY PERMISSION FAILURES

A workload may have permission to read a storage object but still fail if it lacks required permission to use the encryption key protecting that object.

Troubleshoot the complete authorization chain.

---

# 67. TAGGING AND LABELING

Cloud resources should carry useful metadata.

Depending on provider, these may be called tags or labels.

Examples:

```text
environment=production

service=payments

owner=platform-team

managed-by=terraform

cost-center=engineering
```

Exact naming conventions are organization-specific.

---

# 68. WHY TAGGING MATTERS

Metadata can support:

- ownership
- inventory
- cost allocation
- automation
- policy
- incident response
- lifecycle management

An untagged resource may leave operators asking:

```text
Who owns this?

Can it be deleted?

Why does it exist?

Which service depends on it?
```

---

# 69. TAGS ARE NOT SECURITY BOUNDARIES BY THEMSELVES

A tag reading:

```text
environment=production
```

does not automatically secure a resource.

Tags may participate in provider or organization policies where explicitly configured, but a label alone is metadata.

Do not confuse classification with enforcement.

---

# 70. QUOTAS AND SERVICE LIMITS

Cloud resources are not infinitely available.

Providers enforce quotas and service-specific limits.

These may apply at scopes such as:

- account
- project
- subscription
- region
- zone
- resource
- API

The exact scope varies.

---

# 71. QUOTAS ARE PART OF CAPACITY PLANNING

Suppose autoscaling wants:

```text
20 additional instances
```

but available quota allows:

```text
5
```

The scaling configuration may be correct while capacity cannot be created.

Therefore:

```text
Autoscaling Design
+
Quota Capacity
=
Usable Scaling Capacity
```

---

# 72. QUOTA FAILURES

A quota failure can look like:

```text
Deployment failed.

Resource creation rejected.

Scaling stopped.

New IP unavailable.

Database creation failed.
```

Do not immediately assume:

```text
Terraform is broken.
```

or:

```text
Cloud provider outage.
```

Read the provider error.

---

# 73. QUOTAS CAN HAVE DIFFERENT SCOPES

Do not assume:

```text
Quota = account-wide
```

A quota may be:

```text
Global

Regional

Zonal

Per Resource

Per API

Per Identity
```

depending on the provider and service.

Always verify the actual quota dimension.

---

# 74. SERVICE LIMIT VERSUS CURRENT USAGE

Understand:

```text
Maximum Allowed
```

and:

```text
Currently Consumed
```

A deployment may fail because:

```text
Usage + Requested Capacity > Available Quota
```

Monitor important quotas before they become incidents.

---

# 75. COST IS AN ENGINEERING CONSTRAINT

Cloud infrastructure decisions create recurring cost.

Cost should be considered alongside:

- reliability
- performance
- security
- maintainability

Not after deployment.

---

# 76. COMMON COST DRIVERS

Costs may include:

- compute runtime
- compute size
- managed databases
- storage capacity
- storage operations
- load balancers
- NAT/egress services
- public IP resources
- data transfer
- backups
- logs
- monitoring
- cross-zone or cross-region traffic where applicable

Provider pricing changes.

Always verify current pricing before making a cost-sensitive decision.

---

# 77. IDLE RESOURCES

Common waste may include:

```text
Unused virtual machines

Unattached storage

Old snapshots

Unused public IPs

Forgotten load balancers

Oversized databases

Excessive retained logs
```

Do not delete resources merely because they appear unused.

Verify:

```text
Ownership

Dependency

Recovery Need

Retention Requirement
```

first.

---

# 78. COST VERSUS RELIABILITY

Cheapest is not always correct.

Most redundant is not always correct.

Engineering asks:

```text
What reliability does this service require?

What failure is acceptable?

What recovery time is required?

What does additional resilience cost?
```

A development environment and a critical production service may reasonably make different choices.

---

# 79. COST VERSUS PERFORMANCE

Oversized compute may waste money.

Undersized compute may cause:

- latency
- throttling
- instability
- emergency scaling

Use evidence.

```text
Observe
↓
Measure
↓
Right-size
↓
Verify
```

---

# 80. COST ALLOCATION

Useful tagging or account boundaries can help answer:

```text
Which service created this cost?

Which environment?

Which team?

Which project?
```

Cost visibility is part of production ownership.

```text

↓
```


Read the exact provider error before choosing remediation.

# 145. CONTROL PLANE VERSUS DATA PLANE

A useful distinction is:

```text
Control Plane
→ create/configure/manage resources
```

and:

```text
Data Plane
→ actual workload/service traffic
```

A cloud console may successfully show a resource through the control plane while application traffic through the data plane is failing.

Do not confuse:

```text
I can see the resource.
```

with:

```text

```

# 149. SHARED RESPONSIBILITY

Cloud providers secure and operate parts of the underlying platform.

Customers remain responsible for other parts.

The exact boundary depends on the service model.

For example, responsibilities differ between:

```text
Virtual Machine

Managed Database

Serverless Service
```

Do not assume:

```text
Cloud provider manages it
```

means:

```text
Customer has no security or operational responsibility.
```

---

# 150. MANAGED SERVICE TRADEOFF

Managed services can reduce operational burden.

They can also introduce:

- provider-specific behavior
- quotas
- pricing models
- configuration constraints
- migration considerations

Evaluate:

```text
Operational Burden

Reliability

Cost

Control

Security

Portability

Team Capability
```

rather than choosing managed or self-managed by ideology.

---

# 151. BUILD VERSUS MANAGED SERVICE

For example:

```text
Self-Managed Database on VM
```

provides significant control but also transfers more operational responsibility to the team.

A:

```text
Managed Database Service
```

may reduce responsibility for parts of the infrastructure lifecycle.

The correct choice depends on requirements.

---

# 152. CLOUD COST AND ARCHITECTURE

Architecture decisions create billing consequences.

For example:

```text
More Zones
→ potentially greater resilience
→ possibly additional transfer/resource cost
```

or:

```text
More Logging
→ greater diagnostic evidence
→ greater storage/ingestion cost
```

Do not optimize one dimension without understanding another.

# 162. COMPLETE TROUBLESHOOTING SCENARIO

Symptom:

```text
Production application cannot be reached externally.
```

Do not start changing security rules.

Use:

```text
1. Confirm DNS

2. Confirm public endpoint

3. Confirm load balancer listener

4. Confirm backend registration

5. Confirm backend health

6. Confirm security path

7. Confirm application port

8. Confirm application process

9. Confirm application logs

10. Confirm dependency health
```

At each stage collect evidence.

---

# 163. EXAMPLE EVIDENCE TABLE

| Layer | Expected | Observed | Conclusion |
|---|---|---|---|
| DNS | Resolves to public service endpoint | Correct | DNS likely not blocking path |
| Public endpoint | Accepts HTTPS | Correct | Frontend reachable |
| Load balancer | Has healthy targets | Zero healthy | Investigation moves backend |
| Compute | Instances running | Running | Compute state alone not root cause |
| App port | Listening on expected port | Not listening | Strong root-cause evidence |

The important behavior is narrowing the problem.

---

# 164. DO NOT REPAIR BEFORE UNDERSTANDING

Suppose the application is not listening.

Restarting it may restore service.

But ask:

```text
Why did it stop?

Did it crash?

Did configuration change?

Did dependency startup fail?

Did the host run out of memory?

Did deployment fail?
```

Restoration and root-cause investigation are related but different activities.

---

# 165. COMPLETE ROUTING SCENARIO

Symptom:

```text
Private application cannot download required package.
```

Evidence:

```text
Application process healthy

DNS resolves package host

Connection times out

Private subnet has no usable egress route
```

Root cause:

```text
Missing required egress path.
```

Corrective action:

```text
Restore intended route / egress architecture.
```

Verification:

```text
Route present

Connection succeeds

Package endpoint reachable

Application operation succeeds
```

---

# 166. COMPLETE IDENTITY SCENARIO

Symptom:

```text
Application cannot upload report to object storage.
```

Evidence:

```text
Storage DNS resolves

Storage endpoint reachable

Request receives authorization failure

Workload identity lacks required object-write permission
```

Root cause:

```text
Missing required authorization.
```

Corrective action:

```text
Grant only the required permission according to provider policy.
```

Verification:

```text
Test object upload succeeds

Test object readable as required

No unnecessary administrative permission added
```

---

# 167. COMPLETE LOAD BALANCER SCENARIO

Symptom:

```text
Users receive service-unavailable responses.
```

Evidence:

```text
DNS correct

Load balancer reachable

All targets unhealthy

Application responds locally on port 8080

Health check configured for port 80
```

Root cause:

```text
Health-check port mismatch.
```

Corrective action:

```text
Align health-check configuration with intended application endpoint.
```

Verification:

```text
Targets become healthy

Public request succeeds

Monitoring confirms recovery
```

---

# 168. COMPLETE QUOTA SCENARIO

Symptom:

```text
Autoscaling requests new instances but capacity does not increase.
```

Evidence:

```text
Scaling policy triggered

Desired capacity increased

Instance creation requests rejected

Provider reports quota exhaustion
```

Root cause:

```text
Relevant compute quota exhausted.
```

Corrective action depends on requirements:

```text
Request appropriate quota increase

or

Reduce unnecessary consumption

or

Change capacity plan
```

Do not simply keep retrying.

---

# 169. COMPLETE WRONG-REGION SCENARIO

Symptom:

```text
Engineer cannot find production load balancer.
```

Evidence:

```text

CLI configured for different region

Load balancer is regional
```

Root cause:

```text
Wrong regional context.
```

No infrastructure change is required.

This is why context verification belongs before remediation.

# 182. WHAT NOT TO DO

Do not:

```text
Create resources until something works.

Open every port to troubleshoot.

Assign administrator permission to fix authorization.

Give private workloads public IPs to bypass routing problems.

Restart resources before collecting evidence.

Assume running means healthy.

Assume managed means highly available.

Assume multiple instances mean multiple failure domains.

Assume quotas are unlimited.

Assume cloud resources disappear when compute is deleted.

Assume encryption means access control.

Assume AI-generated cloud configuration is correct.
```
