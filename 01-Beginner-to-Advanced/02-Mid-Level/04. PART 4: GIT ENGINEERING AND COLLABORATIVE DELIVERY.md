# PART 4: GIT ENGINEERING AND COLLABORATIVE DELIVERY

## Goal

Move beyond basic Git usage into reliable team-based source, infrastructure, configuration, and production change management.

At the junior level, Git is often learned as a sequence of commands:

```text
Clone
↓
Edit
↓
Add
↓
Commit
↓
Push
```

That foundation is necessary, but it is not enough for production engineering.

At Mid-Level, Git becomes part of the engineering control system around production change.

A repository may determine:

- what application version is deployed
- which infrastructure exists
- which Kubernetes workloads run
- which Helm values are applied
- which pipeline performs deployment
- which configuration reaches production
- which automation executes
- which engineers must approve a change
- which release can be reproduced
- which change must be reverted during an incident

A small Git mistake can therefore become a production mistake.

The Mid-Level question is no longer only:

```text
How do I commit this change?
```

It becomes:

```text
What am I changing?
↓
Why is it changing?
↓
Which branch should contain it?
↓
What does the diff actually do?
↓
Who must review it?
↓
What automation will run because of it?
↓
What systems can it affect?
↓
How will it be tested?
↓
How will it be released?
↓
How will it be recovered if it is wrong?
```

The engineering model for this Part is:

```text
Intent
↓
Branch
↓
Change
↓
Commit
↓
Diff
↓
Review
↓
Automated Validation
↓
Approval
↓
Merge
↓
Release
↓
Deployment
↓
Observation
↓
Recovery if Required
```

The objective is not to create engineers who know many Git commands.

The objective is to create engineers who can safely manage collaborative changes whose consequences may reach production.

---

# 1. GIT AS AN ENGINEERING CONTROL SYSTEM

Git is a distributed version-control system.

It records changes as commits and allows development histories to branch, diverge, and later be combined.

In production engineering, however, Git has a larger operational role.

Consider an infrastructure repository:

```text
infrastructure/
├── terraform/
├── kubernetes/
├── helm/
├── pipelines/
└── automation/
```

Changing one line may:

- delete infrastructure
- expose a network service
- change an IAM permission
- replace a database
- reduce Kubernetes replicas
- modify a production image
- alter a deployment pipeline
- change secret references
- modify autoscaling
- change backup behavior

Therefore:

```text
Small Diff
≠
Small Impact
```

and:

```text
Large Diff
≠
Large Risk Automatically
```

Risk must be determined from semantics, not line count.

---

# 2. THE REPOSITORY AS A SYSTEM OF RECORD

Many engineering organizations use Git repositories as an important record of intended system state.

Examples include:

```text
Application Repository
→ application source and tests

Terraform Repository
→ infrastructure definitions

Kubernetes Repository
→ workload and platform manifests

Helm Repository
→ charts and values

Pipeline Repository
→ delivery automation

Configuration Repository
→ application or environment configuration

Automation Repository
→ operational scripts and tooling
```

This creates an important operational principle:

```text
Repository State
↓
Automation
↓
Potential Production State
```

Not every repository automatically controls production.

But whenever automation consumes repository state, changing Git may eventually change running systems.

---

# 3. WORKING TREE, INDEX, COMMITS, AND REFERENCES

Before managing complex history, understand the main Git states.

A simplified model is:

```text
Working Tree
↓
Staging Area / Index
↓
Commit
↓
Branch Reference
```

The working tree contains checked-out files.

The index represents the content prepared for the next commit.

A commit records a snapshot plus metadata and parent relationships.

A branch is a movable reference to a commit.

This distinction becomes critical during recovery.

Commands that affect:

```text
Working Tree
```

are not necessarily equivalent to commands that affect:

```text
Index
```

or:

```text
Commit History
```

---

# 4. INSPECT BEFORE CHANGING

A strong Git habit is:

```text
Observe
↓
Understand
↓
Change
```

not:

```text
Run Recovery Command
↓
Hope
```

Begin with:

```bash
git status
```

Then, where relevant:

```bash
git log --oneline --decorate --graph --all
```

Inspect unstaged changes:

```bash
git diff
```

Inspect staged changes:

```bash
git diff --staged
```

The first recovery question should usually be:

```text
What state is the repository actually in?
```

---

# 5. COMMITS ARE ENGINEERING UNITS

A useful commit should represent a coherent change.

Weak commit:

```text
update stuff
```

Better:

```text
Increase API deployment replicas from 3 to 5
```

Better still, where the repository convention supports it, the commit message or pull request explains:

```text
Why was this necessary?

What behavior changes?

What does not change?

What operational consequence is expected?
```

Commit quality matters because history may later be used during:

- incident investigation
- regression analysis
- rollback
- audit
- release reconstruction
- ownership investigation

---

# 6. ATOMIC COMMITS

An atomic commit contains one logically coherent change.

Suppose an engineer:

1. fixes a Terraform security-group rule
2. reformats 40 unrelated files
3. upgrades a Helm dependency
4. changes pipeline timeout behavior

and commits everything together.

Review becomes difficult.

Recovery becomes difficult.

The safer pattern is often:

```text
Commit A
→ Security-group correction

Commit B
→ Helm dependency update

Commit C
→ Pipeline timeout adjustment
```

Formatting should also be controlled so it does not hide meaningful changes.

---

# 7. WHY LARGE MIXED COMMITS ARE DANGEROUS

Imagine:

```text
1,800 lines changed
```

Most changes are formatting.

Hidden among them:

```text
replicas: 4
```

becomes:

```text
replicas: 1
```

A reviewer may miss it.

This produces an important review principle:

```text
Reviewability Is a Safety Property
```

Changes should be structured so reviewers can understand them.

---

# 8. COMMIT HISTORY

History is not merely a record that files changed.

Good history helps answer:

```text
When was this introduced?

Why?

By which change?

What came before it?

Which release contains it?

Which changes depend on it?

Can it be reverted independently?
```

Inspect history:

```bash
git log
```

Compact form:

```bash
git log --oneline
```

Graph:

```bash
git log --oneline --graph --decorate --all
```

---

# 9. INSPECT A COMMIT

Use:

```bash
git show <commit>
```

This can reveal:

- commit metadata
- parent relationship
- message
- diff

Do not rely only on the commit message.

The diff is the actual recorded change.

---

# 10. BRANCHES

A branch is a movable reference identifying a line of development.

A common workflow is:

```text
main
  │
  ├── feature/change-a
  │
  └── fix/change-b
```

Branches allow work to proceed without immediately changing the primary integration branch.

But branches do not automatically make changes safe.

Safety comes from the complete workflow around them.

---

# 11. BRANCHING STRATEGY

A branching strategy defines how a team organizes parallel work and integrates changes.

There is no single correct strategy for every organization.

The strategy should support:

- release frequency
- deployment model
- team size
- testing model
- compliance requirements
- hotfix handling
- maintenance requirements
- repository architecture

Common approaches include:

- short-lived feature branches
- trunk-oriented development
- release branches
- environment-related branches in some workflows
- long-lived development branches in some models

The Mid-Level engineer should understand the consequences rather than memorizing one strategy as universally correct.

---

# 12. SHORT-LIVED BRANCHES

A common pattern is:

```text
main
  │
  └── feature/update-api-timeout
```

The branch:

1. starts from an appropriate base
2. receives a focused change
3. is tested
4. is reviewed
5. is merged
6. is removed when no longer needed

Advantages can include:

- smaller divergence
- easier review
- fewer conflicts
- faster integration

Long-lived branches accumulate divergence and can make integration increasingly difficult.

---

# 13. BRANCH NAMES

Branch naming should communicate purpose.

Examples:

```text
feature/add-readiness-check
fix/proxy-timeout
infra/add-private-subnet
security/restrict-storage-policy
hotfix/payment-timeout
```

Exact conventions vary.

Consistency matters more than copying one naming scheme everywhere.

---

# 14. CREATE A BRANCH

Modern Git supports:

```bash
git switch -c feature/example
```

Equivalent workflows may use:

```bash
git checkout -b feature/example
```

Repository conventions determine which style teams prefer.

Before branching, know:

```text
Which commit should this branch start from?
```

---

# 15. WRONG BASE BRANCH

Suppose the intended structure is:

```text
main
  ↓
feature-a
```

but the engineer creates the branch from:

```text
old-release
```

The resulting pull request may contain unrelated changes.

Before beginning significant work:

```bash
git branch --show-current
```

Inspect recent history:

```bash
git log --oneline --decorate -n 10
```

Confirm the base intentionally.

---

# 16. MERGING

A merge combines histories.

Suppose:

```text
A---B---C main
     \
      D---E feature
```

A merge may produce:

```text
A---B---C------M
     \        /
      D------E
```

where `M` is a merge commit.

Merge behavior depends on the workflow and merge method being used.

---

# 17. MERGE COMMITS

A merge commit preserves the fact that separate lines of development were joined.

This can be useful when the team values explicit branch topology.

However, a repository with frequent merge commits can produce a more complex history.

That is not automatically bad.

History structure should serve the team's operational needs.

---

# 18. SQUASH MERGING

A squash workflow combines the effective changes from a branch into a smaller number of commits, often one, when integrating.

Suppose a branch contains:

```text
fix typo
fix test
actually fix test
change config
fix review comment
```

A squash workflow may integrate them as:

```text
Add API readiness probe
```

This can produce a cleaner primary-branch history.

The tradeoff is that individual branch commits are not preserved as separate commits on the target branch.

---

# 19. REBASE-BASED INTEGRATION

A rebase-based workflow can replay commits onto a newer base.

Before:

```text
A---B---C main
     \
      D---E feature
```

After rebasing the feature onto `C`:

```text
A---B---C main
         \
          D'---E' feature
```

`D'` and `E'` represent new commits.

This leads to a critical concept:

```text
Rebase Rewrites Commit History
```

---

# 20. REBASE CONCEPTS

A rebase does not simply "move" existing commits unchanged.

Git recreates commits on a new base.

Therefore commit identities change.

This matters when those commits have already been shared.

A safe mental model is:

```text
Private / Controlled History
→ Rewriting may be appropriate

Shared History
→ Rewriting requires coordination and caution
```

---

# 21. WHY REBASING SHARED HISTORY IS DANGEROUS

Suppose Engineer A and Engineer B both base work on:

```text
commit X
```

Engineer A rewrites the shared branch.

Now the repository may contain histories that represent similar changes with different commit identities.

This can cause:

- confusing divergence
- difficult synchronization
- duplicate-looking changes
- force-push risk

Do not rewrite collaborative history casually.

---

# 22. FETCH BEFORE INTEGRATION DECISIONS

Use:

```bash
git fetch
```

to update remote-tracking information without automatically merging it into the current branch.

Then inspect:

```bash
git log --oneline --graph --decorate --all
```

This is often safer than making integration decisions from stale knowledge of the remote repository.

---

# 23. MERGE VERSUS REBASE

The question is not:

```text
Which command is better?
```

The question is:

```text
What history model does this repository require?
```

Merge preserves branch integration topology.

Rebase can produce a linearized history by replaying commits.

Squash can collapse branch work into a focused integration commit.

Choose according to repository policy.

---

# 24. INTERACTIVE REBASE

Interactive rebase can reorganize local history.

For example:

```bash
git rebase -i HEAD~4
```

may allow operations such as:

- reorder
- combine
- edit
- reword
- remove selected commits

This is powerful.

It is also history rewriting.

Before using it, ask:

```text
Have these commits been shared?

Does another engineer depend on them?

Will rewriting require a force push?

Is force pushing permitted?
```

---

# 25. CHERRY-PICK

Cherry-picking applies the change represented by a selected commit onto the current branch, creating a new commit in that history.

Conceptually:

```text
main
A---B---C

release
A---B
```

Suppose commit `C` contains a critical fix that is also required on the release branch.

A controlled workflow might apply that fix:

```bash
git switch release
git cherry-pick <commit>
```

The release branch now contains a corresponding new commit.

---

# 26. CHERRY-PICK IS NOT GENERAL SYNCHRONIZATION

Cherry-picking is useful when a specific change must be transferred intentionally.

It should not become a substitute for understanding branch relationships.

Excessive cherry-picking can create:

- duplicated logical changes
- confusing ancestry
- future conflicts
- unclear release history

Use it when selective transfer is actually required.

---

# 27. CHERRY-PICK CONFLICTS

A cherry-pick can conflict if the target branch differs from the environment where the original change was created.

Git may stop and require resolution.

Inspect:

```bash
git status
```

Resolve intentionally.

Then stage resolved files:

```bash
git add <resolved-files>
```

Continue:

```bash
git cherry-pick --continue
```

If the operation should not proceed:

```bash
git cherry-pick --abort
```

Do not continue until every conflict has been understood.

---

# 28. REVERT

`git revert` creates a new commit intended to reverse the effect of an earlier commit.

Conceptually:

```text
A---B---C
        ↑
     bad change
```

After reverting `C`:

```text
A---B---C---R
```

The original commit remains in history.

`R` records the reversal.

This makes revert particularly useful when recovering from changes already shared with others.

---

# 29. WHY REVERT IS IMPORTANT IN PRODUCTION

Suppose commit `C` has:

- been merged
- passed through CI
- been deployed
- caused a production failure

Deleting `C` from history is usually not the main operational objective.

The immediate objective is:

```text
Restore Safe Production State
```

A revert provides a traceable new change that reverses the earlier one.

---

# 30. REVERT IS NOT TIME TRAVEL

After:

```text
A---B---C---D---E
```

reverting `C` must account for changes after `C`.

Later commits may depend on it.

Therefore:

```text
Revert Commit C
```

does not always mean:

```text
Repository becomes exactly as it looked before C.
```

Inspect dependencies before reverting older changes.

---

# 31. REVERTING A MERGE

Merge commits have multiple parents.

Reverting them requires Git to know which parent should be treated as the mainline.

This is more complex than reverting a normal single-parent commit.

Do not copy a merge-revert command without understanding:

- which merge is being reverted
- which parent represents the intended mainline
- what later work depends on the merge

Merge reverts should be tested carefully.

---

# 32. RESET

`git reset` moves a branch reference and can also modify the index and working tree depending on the selected mode.

This makes it useful.

It also makes it dangerous.

The important distinction is:

```text
Revert
→ Add new history that reverses an earlier change

Reset
→ Move history/reference state
```

---

# 33. RESET MODES

Common modes include:

```text
--soft
--mixed
--hard
```

Their effects differ.

A simplified mental model:

```text
--soft
→ move HEAD
→ retain changes staged

--mixed
→ move HEAD
→ reset index
→ retain working-tree changes

--hard
→ move HEAD
→ reset index
→ reset working tree
```

`--hard` can discard uncommitted working-tree changes.

Do not run it as a generic troubleshooting command.

---

# 34. RESET SAFETY QUESTION

Before reset, answer:

```text
What exact state am I trying to change?

Commit history?

Staging area?

Working files?

All three?
```

Then ask:

```text
Has the commit been pushed?

Is anyone else using this history?

Do I have uncommitted work?

Can the operation destroy work?
```

---

# 35. NEVER TEACH `git reset --hard` AS A UNIVERSAL FIX

A common bad pattern is:

```text
Git looks confusing.

Run:
git reset --hard
```

This destroys evidence and may destroy work.

The correct sequence is:

```text
Inspect Status
↓
Inspect Diff
↓
Inspect History
↓
Understand Desired State
↓
Choose Recovery Operation
```

---

# 36. RESTORING FILE CONTENT

When the objective is to restore file content rather than rewrite branch history, modern Git provides `git restore`.

Examples depend on the intended source and state.

Before using it, distinguish:

```text
Restore working-tree content

Unstage a change

Restore from another commit

Rewrite branch history
```

These are different operations.

---

# 37. RECOVERING FROM AN INCORRECT LOCAL COMMIT

Scenario:

A commit was created locally with the wrong files.

It has not been pushed.

First inspect:

```bash
git status
git log --oneline -n 5
git show HEAD
```

Then decide what needs correction.

Possibilities include:

- amend the commit
- move HEAD while retaining changes
- restore specific files
- create another corrective commit

The correct method depends on whether history is still private.

---

# 38. AMENDING A COMMIT

For an unshared most-recent commit, amendment may be appropriate.

For example:

```bash
git commit --amend
```

This creates a replacement commit.

Therefore:

```text
Amend
=
History Rewrite
```

Do not casually amend a commit already shared with collaborators.

---

# 39. ACCIDENTAL COMMIT TO WRONG BRANCH

Suppose work intended for:

```text
feature/network-fix
```

was committed to:

```text
main
```

Do not panic.

First determine:

```text
Was it pushed?

Was it merged?

Did automation run?

Was it deployed?

Is the history shared?
```

Recovery depends on these answers.

---

# 40. WRONG BRANCH, NOT PUSHED

A controlled local recovery may involve:

1. preserving the commit on the correct branch
2. restoring the original branch reference appropriately

For example, depending on repository state:

```bash
git branch feature/network-fix
```

can preserve the current commit under another branch reference before any destructive history movement.

Then inspect:

```bash
git log --oneline --graph --decorate --all
```

Only after confirming the commit is safely referenced should history correction continue.

---

# 41. WRONG BRANCH, ALREADY SHARED

If the change is already on a shared protected branch:

```text
Do Not Pretend It Never Happened
```

Determine:

- whether it must be reverted
- whether deployment occurred
- whether another corrective change is required
- whether security or incident response is involved

Shared history should usually be corrected through collaborative, traceable operations.

---

# 42. REFLOG

Git's reflog records updates to local references and can be extremely valuable when recovering from accidental local history movement.

Inspect:

```bash
git reflog
```

This may help locate commits that are no longer visible from the branch's current position.

A useful mental model is:

```text
git log
→ history reachable from references

git reflog
→ local record of reference movement
```

Reflog availability and retention should not be treated as permanent backup.

---

# 43. LAB: RECOVER FROM INCORRECT COMMIT

Create a disposable repository.

Create:

```text
commit A
commit B
commit C
```

Then intentionally perform an incorrect local history operation.

Use:

```bash
git reflog
```

to identify the previous reference position.

Recover the intended commit.

Verify:

```bash
git log --oneline --graph --decorate --all
```

The objective is to understand recovery, not memorize one hash.

---

# 44. TAGS

Tags identify particular points in repository history.

They are commonly used for:

- releases
- milestones
- deployment references
- version identification

Example:

```text
v2.4.0
```

might identify a release commit.

---

# 45. LIGHTWEIGHT AND ANNOTATED TAGS

Git supports lightweight and annotated tags.

A lightweight tag behaves primarily as a named reference to a commit.

An annotated tag stores additional tag-object metadata.

For release processes, annotated tags are often useful because they can carry additional release information and can be signed.

Repository policy determines what should be used.

---

# 46. CREATE AN ANNOTATED TAG

Example:

```bash
git tag -a v2.4.0 -m "Release v2.4.0"
```

Inspect:

```bash
git show v2.4.0
```

Do not create release tags casually.

Tags may trigger:

- release pipelines
- artifact publication
- container builds
- deployments

---

# 47. RELEASE TAGGING

A release tag should identify the exact commit intended for release.

The process should answer:

```text
Which commit?

Which version?

Which tests passed?

Which artifacts correspond to it?

Which environment received it?

Can we reproduce it?
```

A tag is useful only when the release process gives it reliable meaning.

---

# 48. INCORRECT RELEASE TAG

Suppose:

```text
v3.2.0
```

is accidentally created on the wrong commit.

Do not immediately delete and recreate it without understanding consequences.

Ask:

```text
Was the tag pushed?

Did automation trigger?

Was an artifact published?

Was a container image produced?

Was anything deployed?

Did another system cache or consume the tag?
```

The problem may already extend beyond Git.

---

# 49. TAG IMMUTABILITY AS AN OPERATIONAL PRINCIPLE

Release processes are easier to reason about when a release identifier consistently refers to the same content.

Moving an already-consumed release tag can create ambiguity:

```text
What did v3.2.0 mean yesterday?

What does v3.2.0 mean now?
```

A safer release process often treats published release tags as immutable and creates a new corrected version when appropriate.

Exact policy depends on the organization.

---

# 50. RELEASE BRANCHES

A release branch may represent a maintained release line.

Example:

```text
main
 │
 ├── release/2.4
 │
 └── ongoing development
```

A production fix might need to be applied to:

```text
release/2.4
```

while development continues independently on:

```text
main
```

This is one legitimate use case for controlled cherry-picking.

---

# 51. RELEASE BRANCH TRADEOFFS

Release branches can support:

- maintenance of older versions
- stabilization periods
- controlled patch releases

But they also create:

- additional divergence
- more backporting
- more testing combinations
- more release coordination

Do not create long-lived branches without an operational reason.

---

# 52. MERGE CONFLICTS

A conflict occurs when Git cannot safely determine how competing changes should be combined.

A conflict is not Git malfunctioning.

It means:

```text
Human Intent Is Required
```

---

# 53. CONFLICT MARKERS

A conflicted file may contain markers similar to:

```text
<<<<<<< HEAD
replicas: 3
=======
replicas: 5
>>>>>>> feature/scale-api
```

Do not resolve by automatically deleting the markers and choosing whichever side looks newer.

Ask:

```text
Why did one branch choose 3?

Why did the other choose 5?

Which requirement is current?

Do both changes need to be combined?
```

---

# 54. SEMANTIC CONFLICTS

The most dangerous conflicts are not always Git conflicts.

Git may merge two changes automatically even when the resulting system is logically wrong.

Example:

Engineer A changes:

```text
application port:
8080 → 9000
```

Engineer B changes:

```text
reverse proxy timeout:
30 → 60
```

Git may merge both without conflict.

But if another required proxy configuration still points to `8080`, the resulting system can fail.

Therefore:

```text
No Git Conflict
≠
No Engineering Conflict
```

---

# 55. RESOLVING COMPLEX CONFLICTS

Use this workflow:

```text
Identify Conflicted Files
↓
Understand Base State
↓
Understand Our Change
↓
Understand Their Change
↓
Determine Intended Final State
↓
Edit
↓
Validate Syntax
↓
Run Tests
↓
Inspect Final Diff
↓
Continue Operation
```

Never make conflict resolution purely textual.

---

# 56. ABORTING A FAILED MERGE

If a merge is in progress and should not continue:

```bash
git merge --abort
```

may restore the pre-merge state when Git has sufficient information to do so.

Inspect:

```bash
git status
```

before and after.

Do not use abort commands without confirming which Git operation is currently active.

---

# 57. ABORTING A REBASE

If a rebase should not continue:

```bash
git rebase --abort
```

Likewise, inspect:

```bash
git status
```

The repository tells you which operation is in progress.

Read it.

---

# 58. PULL REQUESTS ARE ENGINEERING REVIEW UNITS

A pull request is not merely:

```text
Please merge my branch.
```

A production-quality pull request should communicate:

```text
Intent

Scope

Impact

Risk

Validation

Operational Consequences

Rollback
```

The reviewer should not have to reverse-engineer the purpose from the diff.

---

# 59. PULL REQUEST DESIGN

A strong pull request answers:

### What?

What is changing?

### Why?

What problem or requirement justifies it?

### Where?

Which services, environments, infrastructure, or users are affected?

### Risk?

What could go wrong?

### Validation?

What evidence shows the change behaves as intended?

### Rollback?

How will safe state be restored if necessary?

---

# 60. EXAMPLE INFRASTRUCTURE PULL REQUEST

```text
Title:
Increase production API capacity from 4 to 6 replicas

Reason:
Sustained peak utilization is approaching the existing capacity threshold.

Scope:
Production API deployment only.

Changes:
replicas: 4 → 6

Expected impact:
Two additional API Pods will be scheduled.

Validation:
Manifest validation passes.
Staging configuration was tested.
Production cluster has sufficient requested capacity.

Risk:
Additional compute consumption.
Potential scheduling failure if capacity assumptions are incorrect.

Rollback:
Restore replica count to 4 through a reviewed revert or corrective change.

Post-change verification:
Confirm six Ready replicas.
Confirm service endpoints include healthy replicas.
Observe application error rate and latency.
```

The exact implementation depends on the environment.

The important lesson is the reasoning structure.

---

# 61. PULL REQUEST SIZE

Smaller pull requests are generally easier to reason about.

Large changes increase:

- review time
- cognitive load
- hidden-change risk
- conflict probability
- rollback complexity

But artificial fragmentation can also be harmful.

A pull request should be:

```text
Small Enough to Understand

Large Enough to Be Coherent
```

---

# 62. REVIEW THE DIFF, NOT JUST THE DESCRIPTION

A good description can still accompany a dangerous diff.

The review must inspect:

```text
Claimed Intent
```

against:

```text
Actual Change
```

Ask:

```text
Does the diff contain only what the description claims?
```

---

# 63. THE REVIEW FRAMEWORK

Use:

```text
Intent
↓
Diff
↓
Impact
↓
Dependencies
↓
Risk
↓
Tests
↓
Rollback
```

This is the core review workflow for this Part.

---

# 64. REVIEW: INTENT

First understand:

```text
What problem is this change solving?
```

If the intent is unclear, the rest of the review becomes difficult.

Example:

```text
Intent:
Allow application workloads in the private application subnet
to connect to the managed database on the required database port.
```

That is reviewable.

---

# 65. REVIEW: DIFF

Inspect what actually changes.

Use:

```bash
git diff <base>...<branch>
```

or the repository platform's pull-request diff.

Look for:

- unexpected files
- unrelated formatting
- generated files
- deleted configuration
- changed permissions
- environment-specific changes
- secret material
- dependency updates
- workflow changes

---

# 66. REVIEW: IMPACT

Ask:

```text
If merged, what can this change affect?
```

Impact may include:

- one function
- one service
- one namespace
- one cloud account
- every production environment
- every pipeline
- organization-wide access

Impact is not determined by diff size.

---

# 67. REVIEW: DEPENDENCIES

Ask:

```text
What must already be true for this change to work?
```

Examples:

- new container image exists
- DNS record exists
- secret exists
- IAM role exists
- database migration completed
- Kubernetes CRD installed
- Terraform provider supports configuration
- target environment has capacity

A correct change can still fail if its dependencies are absent.

---

# 68. REVIEW: RISK

Consider:

```text
Availability

Security

Data

Performance

Cost

Recovery

Blast Radius

Irreversibility
```

A one-line change can have high risk.

---

# 69. REVIEW: TESTS

Ask:

```text
What evidence demonstrates correctness?
```

Possible evidence:

- unit tests
- integration tests
- configuration validation
- linting
- policy checks
- Terraform plan
- Helm rendering
- Kubernetes schema validation
- staging deployment
- security scan
- smoke test

Tests should correspond to the type of change.

---

# 70. REVIEW: ROLLBACK

Ask:

```text
If this fails after merge or deployment, how is safe state restored?
```

Possible answers include:

- revert commit
- redeploy previous immutable artifact
- restore previous configuration
- roll back release
- apply a forward fix
- restore data

Not every change is safely reversible through Git alone.

---

# 71. CODE OWNERSHIP

Code ownership maps areas of a repository to people or teams responsible for reviewing or maintaining them.

Conceptually:

```text
terraform/networking/
→ Network / Platform Owners

kubernetes/production/
→ Platform Owners

.github/workflows/
→ Delivery Owners

security/
→ Security Owners
```

The objective is:

```text
Sensitive Change
↓
Relevant Expertise
↓
Required Review
```

---

# 72. OWNERSHIP DOES NOT REPLACE GENERAL REVIEW

A code owner approving a file does not automatically prove:

- architecture is correct
- tests are sufficient
- deployment is safe
- business requirement is correct

Ownership identifies responsibility and expertise.

It does not eliminate engineering judgment.

---

# 73. REQUIRED REVIEWS

Important branches may require approval before changes are integrated.

This helps prevent:

```text
Author
↓
Self-Approve
↓
Production
```

from becoming the default path.

The number and type of reviewers should reflect risk and organizational requirements.

More reviewers do not automatically create better review.

Review quality matters.

---

# 74. PROTECTED BRANCHES

Important branches should usually have controls preventing casual modification.

Depending on repository platform and policy, controls may include:

- blocking direct pushes
- requiring pull requests
- requiring reviews
- requiring status checks
- restricting force pushes
- restricting deletion
- requiring signed commits
- requiring code-owner review

The engineering principle is:

```text
Important Branch
↓
Controlled Change Path
```

---

# 75. WHY FORCE PUSHING IS DANGEROUS

Force pushing can replace remote branch history.

On a private personal branch, this may sometimes be intentional.

On a shared production branch, it can destroy or obscure collaborative history.

Before any force push, ask:

```text
Is this branch shared?

Is rewriting permitted?

Could another person's commits be removed?

Is the branch protected?

Why is rewriting necessary?
```

---

# 76. `--force-with-lease`

Where history rewriting is authorized, `--force-with-lease` provides an additional safety check compared with an unconditional force push because it can refuse to overwrite a remote reference that has changed unexpectedly.

It is not permission to rewrite shared history casually.

The repository's policy still controls whether rewriting is appropriate.

---

# 77. SIGNED COMMITS

Git commits can be cryptographically signed.

A hosting platform can use signature verification to provide evidence associated with commit authenticity.

The important concept is:

```text
Commit Exists
```

versus:

```text
Commit Has Verifiable Signature Evidence
```

Signed commits can strengthen provenance controls.

They do not prove that the code itself is correct or safe.

---

# 78. SIGNED TAGS

Release tags can also be signed.

This can strengthen release provenance by allowing consumers to verify that the tag was created by a trusted signing identity.

Again:

```text
Valid Signature
≠
Correct Release
```

The release still requires testing and review.

---

# 79. REPOSITORY HYGIENE

A production repository should avoid unnecessary noise and dangerous content.

Repository hygiene includes:

- appropriate `.gitignore`
- no credentials
- no private keys
- no generated temporary files unless intentionally tracked
- no local editor state unless required
- no build output unless intentionally versioned
- consistent structure
- meaningful documentation
- controlled binary files
- maintained dependencies
- understandable history

---

# 80. `.gitignore`

`.gitignore` helps prevent selected untracked files from being added accidentally.

Examples may include:

```text
.env
*.log
.terraform/
terraform.tfstate*
```

But ignore patterns must match repository requirements.

Do not copy a generic `.gitignore` blindly.

---

# 81. `.gitignore` IS NOT A SECURITY BOUNDARY

If a secret is already committed, adding it to `.gitignore` does not remove it from history.

This distinction is critical:

```text
Ignored
≠
Never Committed
```

and:

```text
Deleted from Current File
≠
Removed from Repository History
```

---

# 82. SECRET ACCIDENTALLY COMMITTED

Treat an exposed secret as a security incident according to organizational procedure.

The first concern is not Git history aesthetics.

The first concern is:

```text
Credential May Be Compromised
```

Therefore:

```text
Detect Exposure
↓
Assess Scope
↓
Revoke / Rotate Credential
↓
Prevent Further Use
↓
Investigate Exposure
↓
Remove from Repository Where Required
↓
Prevent Recurrence
```

Rotation comes before assuming history cleanup solved the problem.

---

# 83. WHY DELETING THE SECRET IS NOT ENOUGH

Suppose:

```text
Commit A:
secret added

Commit B:
secret deleted
```

The secret may still exist in Commit A.

Anyone with access to that history may still retrieve it.

Therefore:

```text
Current File Clean
≠
Historical Secret Removed
```

---

# 84. HISTORY REWRITING FOR SECRET REMOVAL

Removing sensitive material from repository history may require history-rewriting tools and coordinated repository procedures.

This can affect:

- commit IDs
- branches
- tags
- forks
- clones
- open pull requests
- automation

Do not perform organization-wide history rewriting casually.

Most importantly:

```text
History Cleanup
Does Not Replace
Credential Revocation
```

---

# 85. PREVENT SECRET COMMITS

Prevention can include:

- secret-management systems
- environment injection
- pre-commit scanning
- CI secret scanning
- repository push protection
- code review
- developer training

The safest secret is one that never enters repository history.

---

# 86. INFRASTRUCTURE REPOSITORIES

Infrastructure repositories require especially careful review because configuration often describes future production state.

Examples include:

```text
Terraform

Kubernetes

Helm

CI/CD Pipelines

Application Configuration

Automation
```

Each category has different review risks.

---

# 87. TERRAFORM REPOSITORIES

A Terraform diff may change:

- networks
- instances
- databases
- IAM
- DNS
- load balancers
- storage
- security controls

Source review alone is insufficient.

The reviewer should also inspect the resulting plan when appropriate.

The important relationship is:

```text
Terraform Code
↓
Terraform Evaluation
↓
Plan
↓
Potential Infrastructure Change
```

---

# 88. TERRAFORM REVIEW QUESTIONS

Ask:

```text
Which resources change?

Create?

Update?

Replace?

Destroy?

Why?

Does state behavior matter?

Does provider behavior matter?

Does this change permissions?

Does this expose a network path?

Does it affect data?

Can it be rolled back safely?
```

Never approve Terraform merely because:

```text
Syntax looks correct.
```

---

# 89. DANGEROUS TERRAFORM CHANGE

Suppose a pull request says:

```text
Update database naming convention
```

but the plan indicates:

```text
database replacement
```

The engineering impact is much larger than the pull-request title suggests.

The plan is critical evidence.

---

# 90. KUBERNETES REPOSITORIES

Kubernetes changes may affect:

- images
- replicas
- resources
- probes
- Services
- ports
- configuration
- secrets references
- RBAC
- security contexts
- storage
- scheduling
- disruption behavior

Review the operational consequence.

---

# 91. KUBERNETES DANGEROUS DIFF

A large manifest diff contains:

```yaml
replicas: 6
```

changed to:

```yaml
replicas: 1
```

The YAML remains valid.

The application may still deploy.

But production redundancy may be reduced dramatically.

Validation is not the same as operational correctness.

---

# 92. KUBERNETES IMAGE REVIEW

Changing:

```yaml
image: example/api:2.4.1
```

to:

```yaml
image: example/api:latest
```

may change release reproducibility and deployment behavior.

Reviewers should understand:

- image identity
- tag mutability
- artifact provenance
- rollout behavior

Exact image policy depends on the organization.

---

# 93. HELM REPOSITORIES

Helm repositories may contain:

- charts
- templates
- default values
- environment values
- dependencies

A small values change may produce a large rendered manifest difference.

Therefore review may require:

```text
Values Diff
↓
Rendered Output
↓
Kubernetes Impact
```

Do not review only the template source when the generated output determines deployment.

---

# 94. PIPELINE REPOSITORIES

Pipeline changes deserve high scrutiny because they can modify how every later change is:

- built
- tested
- signed
- published
- deployed
- approved

A pipeline change may be more dangerous than the application change it accompanies.

---

# 95. DANGEROUS PIPELINE CHANGE

Imagine:

```text
run tests
↓
build
↓
approval
↓
deploy
```

becomes:

```text
build
↓
deploy
```

The YAML may still be valid.

The pipeline may run successfully.

But a major safety control has disappeared.

Review semantics, not syntax.

---

# 96. APPLICATION CONFIGURATION REPOSITORIES

Configuration can control:

- endpoints
- feature flags
- timeouts
- concurrency
- logging
- authentication
- dependency locations

Configuration changes may not require application compilation, yet they can cause immediate production impact.

Treat configuration as production code when its effect is production behavior.

---

# 97. AUTOMATION REPOSITORIES

Automation scripts can:

- create resources
- delete resources
- rotate credentials
- deploy applications
- restart services
- modify users
- change permissions

Review:

```text
Inputs

Privileges

Targets

Error Handling

Idempotency

Dry-Run Capability

Logging

Failure Behavior

Rollback
```

---

# 98. REVIEW THE CHANGE TRIGGER

A Git change can trigger automation.

Ask:

```text
What happens when this branch receives a push?

What happens when this PR merges?

What happens when this tag is created?

What happens when this path changes?
```

A reviewer who understands only the files but not the automation trigger may miss the actual impact.

---

# 99. PATH-BASED AUTOMATION

Some pipelines execute only when selected paths change.

Example conceptually:

```text
terraform/**
→ infrastructure pipeline

app/**
→ application pipeline
```

A repository move or renamed directory may therefore alter which automation runs.

Review path-trigger changes carefully.

---

# 100. REVIEW DEPENDENCY FILES

Changes to dependency declarations or lock files can alter the software supply chain.

Review:

- dependency added
- dependency removed
- version changed
- source changed
- checksum/lock changes
- transitive effect where tooling exposes it

Do not dismiss large lock-file changes without understanding why they occurred.

---

# 101. BINARY FILES

Git can store binary files, but ordinary line-based review is less effective for them.

Ask:

```text
Should this binary be stored here?

Can it be reproduced?

Can its provenance be verified?

Is it too large?

Could it contain sensitive information?
```

Repository hygiene includes deciding what should not be committed.

---

# 102. GENERATED FILES

Generated files create review challenges.

If generated output is tracked, establish:

```text
What generated it?

Which source controls it?

How can reviewers reproduce it?

Should manual edits be prohibited?
```

A generated diff without reproducibility weakens review.

---

# 103. LARGE DIFFS

When reviewing a large diff:

1. inspect file list first
2. group files by function
3. identify high-risk paths
4. separate generated changes
5. inspect security-sensitive changes
6. inspect deployment-sensitive changes
7. inspect deletions
8. inspect dependency changes
9. inspect automation changes
10. compare against stated intent

Do not begin by scrolling from line one to line ten thousand.

---

# 104. FIND THE DANGEROUS CHANGE

Suppose a pull request changes:

```text
87 documentation files
14 formatting files
3 tests
1 Terraform file
```

The Terraform file may be the highest-risk part.

Risk-weighted review means spending attention according to consequence, not file count.

---

# 105. REVIEW DELETIONS CAREFULLY

Added lines naturally attract attention.

Deleted lines can be equally important.

A deletion may remove:

- validation
- authentication
- backup configuration
- monitoring
- health checks
- resource limits
- tests
- security controls

Review deletions intentionally.

---

# 106. REVIEW PERMISSION CHANGES

Infrastructure and configuration reviews should pay particular attention to:

```text
IAM permissions

RBAC

filesystem permissions

network access

secret access

pipeline permissions
```

A change from:

```text
read one resource
```

to:

```text
administer all resources
```

may involve very few lines.

Its blast radius is enormous.

---

# 107. REVIEW DEFAULTS

A default-value change can affect many consumers.

Example:

```text
default replica count:
3 → 1
```

If dozens of environments inherit the default, one line may affect all of them.

Ask:

```text
Who inherits this value?
```

---

# 108. REVIEW SHARED MODULES

A Terraform module, Helm chart, pipeline template, or shared automation library may have many consumers.

Therefore:

```text
Change Location
```

does not equal:

```text
Impact Location
```

A change inside one shared module may affect dozens of systems.

---

# 109. CODE OWNERSHIP FOR INFRASTRUCTURE

Sensitive paths can have explicit owners.

Conceptually:

```text
/networking/
→ networking team

/iam/
→ security/platform team

/production/
→ production platform team

/.github/workflows/
→ delivery/platform team
```

Ownership should correspond to engineering responsibility.

---

# 110. REVIEW IS NOT APPROVAL THEATER

A pull request with:

```text
Approved
```

is not necessarily safe.

Review quality requires the reviewer to understand enough to make a meaningful judgment.

Weak review:

```text
Looks good.
```

Strong review:

```text
I verified the intended security-group change is limited to
application-subnet traffic on the required database port.

The Terraform plan shows one in-place security-group update,
no resource replacement, and no unrelated infrastructure changes.

Rollback is the previous rule set.
```

---

# 111. REVIEWER RESPONSIBILITY

The reviewer should ask:

```text
Do I understand this?

Am I qualified to approve this part?

Is another owner required?

Do I have enough evidence?

Are tests meaningful?

Is risk documented?

Is rollback realistic?
```

Approval should not be automatic because the author is senior.

---

# 112. AUTHOR RESPONSIBILITY

The author should make review easier.

Before requesting review:

```text
Read Your Own Diff
```

Then:

- remove accidental files
- remove debugging output
- remove secrets
- remove unrelated changes
- validate configuration
- run relevant tests
- explain risk
- document rollback

A reviewer should not be the first person to inspect the final diff.

---

# 113. SELF-REVIEW

Use:

```bash
git diff <base>...HEAD
```

Review the change as if another engineer created it.

Ask:

```text
Would I approve this?

What would I question?

What is unexplained?

What could fail?
```

---

# 114. REQUIRED STATUS CHECKS

Repository platforms can require automated checks before changes enter protected branches.

Checks may include:

- tests
- linting
- builds
- security scanning
- infrastructure validation
- policy checks

The engineering principle is:

```text
Change
↓
Automated Evidence
↓
Human Review
↓
Integration
```

Automation and human review complement each other.

---

# 115. PASSING CI DOES NOT MEAN SAFE

CI proves only what its checks actually test.

If CI validates:

```text
YAML syntax
```

it does not prove:

```text
production architecture is correct.
```

If tests verify application logic, they may not prove:

```text
Terraform will not replace the database.
```

Understand test scope.

---

# 116. FAILED MERGE

A merge can fail because histories conflict.

Do not immediately force the operation.

Inspect:

```bash
git status
```

Then identify:

- conflicted files
- current operation
- intended target branch
- source branch
- repository policy

Resolve only after understanding the conflicting intent.

---

# 117. CONFLICTING HISTORY

A branch may diverge:

```text
Remote:
A---B---C

Local:
A---B---D
```

Neither side is automatically wrong.

The question is:

```text
What integration model is required?
```

Possible approaches may involve:

- merge
- rebase
- controlled reset
- branch replacement

Repository policy determines the correct approach.

---

# 118. DO NOT SOLVE DIVERGENCE WITH BLIND FORCE PUSHING

A force push can make divergence disappear visually while deleting another engineer's work from the branch reference.

First:

```bash
git fetch
```

Then inspect:

```bash
git log --oneline --graph --decorate --all
```

Understand both histories.

---

# 119. WRONG TARGET BRANCH

A pull request intended for:

```text
release/2.4
```

may accidentally target:

```text
main
```

This can change:

- displayed diff
- required reviewers
- automated checks
- release destination
- merge consequence

Always verify:

```text
Base Branch

Head Branch
```

before approval.

---

# 120. ACCIDENTAL FILES

Before commit:

```bash
git status
```

Before push:

```bash
git show --stat HEAD
```

Before review:

```bash
git diff <base>...HEAD --stat
```

Look for:

- `.env`
- credentials
- state files
- logs
- local IDE files
- test artifacts
- large archives
- temporary files

---

# 121. ACCIDENTAL STAGING

If an unwanted file is staged but not committed, unstage it using the repository's appropriate Git workflow.

For modern Git, one option is:

```bash
git restore --staged <file>
```

Then inspect:

```bash
git status
```

The objective is to change the index without deleting the working file.

---

# 122. ACCIDENTAL COMMIT

Classify it first:

```text
Local and Unshared?
```

or:

```text
Already Shared?
```

This distinction determines whether history rewriting may be acceptable.

Never skip this classification.

---

# 123. ACCIDENTAL PUSH

If an incorrect change reaches a shared remote branch:

```text
Do Not Immediately Rewrite Remote History
```

Determine:

```text
Was it merged?

Did automation execute?

Was production affected?

Does it contain a secret?

Does it require immediate revert?

Who needs to be notified?
```

The event may now be operational, not merely Git-related.

---

# 124. REVERTING A DEPLOYED CHANGE

Scenario:

```text
Commit
↓
Merge
↓
Deployment
↓
Production Failure
```

A controlled recovery may be:

```text
Identify Bad Change
↓
Confirm Failure Relationship
↓
Create Revert
↓
Review
↓
Run Required Checks
↓
Merge
↓
Deploy Restored State
↓
Verify
```

Emergency procedures may differ according to organizational policy.

---

# 125. REVERT VERSUS ROLLBACK

These terms should not be treated as identical.

A Git revert changes repository history by adding a reversing commit.

A deployment rollback changes running system state to an earlier known release or configuration.

Sometimes:

```text
Git Revert
↓
Pipeline
↓
Deployment
```

performs the operational rollback.

Sometimes production rollback occurs before Git catches up.

Know which system is authoritative.

---

# 126. DATABASE CHANGES MAY NOT BE GIT-REVERSIBLE

Suppose a deployment:

```text
drops data
```

or:

```text
performs irreversible migration
```

Reverting application code does not automatically restore data.

Therefore rollback planning must include:

```text
Code

Configuration

Infrastructure

Data
```

Git alone cannot reverse every production consequence.

---

# 127. RELEASE HISTORY

A strong release history should allow an engineer to determine:

```text
Which commit was released?

Which tag identifies it?

Which artifact was produced?

Which environment received it?

Which changes were included?

What was rolled back?
```

This supports incident investigation and reproducibility.

---

# 128. TAGGING AFTER VERIFICATION

Release processes should clearly define when a tag is created.

Possible models include:

```text
Tag
↓
Build
↓
Test
↓
Release
```

or:

```text
Validated Commit
↓
Tag
↓
Publish Existing Artifact
```

The important requirement is consistency.

Do not create ambiguous release semantics.

---

# 129. BRANCH PROTECTION IS A GUARDRAIL

A protected branch should make unsafe paths harder.

It does not eliminate human error.

A reviewer can still approve a dangerous change.

A test can still miss a failure.

A valid signed commit can still contain incorrect code.

Therefore:

```text
Guardrails
+
Review
+
Testing
+
Operational Verification
```

work together.

---

# 130. PROTECT THE PROTECTION MECHANISM

Files controlling repository governance may themselves require protection.

Examples:

```text
CODEOWNERS

CI workflows

security policies

deployment workflows

repository automation
```

If an engineer can modify the review requirement and the protected change in the same unreviewed path, the control may be weakened.

Governance files deserve explicit ownership.

---

# 131. AI-ASSISTED GIT ENGINEERING

AI can assist with:

- summarizing diffs
- explaining unfamiliar files
- generating commit-message drafts
- identifying possible risky changes
- reviewing Terraform plans
- comparing configuration
- identifying missing tests
- explaining conflicts
- suggesting rollback considerations
- generating pull-request descriptions

But AI must not become the approval authority.

---

# 132. AI DIFF SUMMARIZATION

A useful AI request is:

```text
Summarize this diff by:

1. functional change
2. infrastructure impact
3. security impact
4. deployment impact
5. possible failure modes
6. missing validation
7. rollback considerations

Do not assume unchanged files are safe.
```

Then independently verify the summary against the actual diff.

---

# 133. AI CAN MISS A ONE-LINE HIGH-RISK CHANGE

Imagine a 4,000-line pull request.

AI summarizes:

```text
Primarily formatting and documentation improvements.
```

But one line changes:

```text
public_access = false
```

to:

```text
public_access = true
```

The summary is not the review.

The engineer remains accountable for the actual change.

---

# 134. AI AND MERGE CONFLICTS

AI can help explain conflicting code.

But the correct resolution depends on intent.

The model may understand:

```text
what each side says
```

without knowing:

```text
which production behavior is required.
```

Use AI to assist reasoning, not replace ownership.

---

# 135. AI AND COMMAND SAFETY

Do not execute AI-generated commands such as:

```text
git reset --hard

git push --force

git clean -fd

history-rewriting commands
```

without understanding their effect.

Before executing:

```text
What changes?

What can be destroyed?

Is history shared?

Can recovery be performed?

Is the command appropriate for this repository state?
```

# 140. LAB 5: CHERRY-PICK A CONTROLLED FIX

Create:

```text
main
```

and:

```text
release/1.x
```

Add several commits to `main`.

Only one is appropriate for the maintained release.

Identify its commit.

Switch to:

```text
release/1.x
```

Apply only that fix using controlled cherry-picking.

Verify:

At Mid-Level, Git is no longer simply where code is stored.

It is part of the production delivery system.

A commit can become an artifact.

An artifact can become a deployment.

A Terraform commit can become infrastructure.

A Kubernetes commit can become running workloads.

A pipeline commit can change how every later release reaches production.

A configuration commit can change application behavior without changing application source.

A tag can trigger a release.

A mistaken secret commit can become a security incident.

A careless force push can damage collaborative history.

A poorly reviewed one-line infrastructure change can have a larger production impact than thousands of application-code changes.

The Mid-Level engineer therefore treats repository operations as engineering decisions.

Before changing history:

```text
Understand who depends on it.
```

Before merging:

```text
Understand what the diff does.
```

Before approving:

```text
Understand the risk.
```

Before releasing:

```text
Understand exactly what is being released.
```

Before recovering:

```text
Understand where the bad state exists.
```

And after every production-affecting change:

```text
Verify the running system, not only the repository.
```

That is Git engineering and collaborative delivery.
