# PART 3: PRODUCTION NETWORKING AND TRAFFIC FLOW

## Goal

Understand production network paths well enough to troubleshoot connectivity across hosts, cloud networks, containers, proxies, load balancers, services, and application dependencies.

At Junior level, networking is often approached through foundational questions:

- What is an IP address?
- What is a subnet?
- What is a port?
- What does DNS do?
- What is HTTP?
- What is HTTPS?
- Is the application listening?
- Can the destination be reached?

At Mid-Level, those foundations must become operational reasoning.

A production request rarely travels directly from a user's computer to an application process.

A more realistic path may be:

```text
Client
  ↓
Local DNS Resolver
  ↓
Recursive DNS
  ↓
Authoritative DNS
  ↓
Public Endpoint
  ↓
Firewall / Cloud Security Boundary
  ↓
Load Balancer
  ↓
Reverse Proxy / Ingress Layer
  ↓
Service
  ↓
Application
  ↓
Database / Cache / Queue / External API
```

Every transition introduces another place where communication can fail.

The central question in this Part is therefore not:

```text
Is the network working?
```

It is:

```text
What exact path should this request take?

Which parts of that path have been proven to work?

At which layer does observed behavior stop matching expected behavior?
```

The troubleshooting model is:

```text
Symptom
   ↓
Name Resolution
   ↓
Destination Address
   ↓
Route
   ↓
Network Boundary
   ↓
Transport Connection
   ↓
TLS
   ↓
HTTP
   ↓
Proxy / Load Balancer
   ↓
Application
   ↓
Dependency
   ↓
Evidence-Supported Root Cause
```

A Mid-Level engineer must be able to reconstruct this path rather than treating "networking" as one layer.

---

# 1. NETWORKING IS A CHAIN OF DECISIONS

Consider a request to:

```text
https://app.example.com/api/orders
```

Several things must happen successfully.

The client must determine:

```text
What address represents app.example.com?
```

Then:

```text
How do I reach that address?
```

Then:

```text
Can I establish the required transport connection?
```

Then, for HTTPS:

```text
Can I establish the expected TLS session and authenticate the server identity?
```

Then:

```text
Can I send the HTTP request?
```

Then:

```text
Can the receiving proxy, load balancer, or application route it correctly?
```

Then:

```text
Can the application reach its dependencies?
```

A failure at any one of these stages may appear to the user simply as:

```text
The website is down.
```

Your job is to turn that report into a precise failure location.

---

# 2. THE PRODUCTION TRAFFIC MODEL

Use this model throughout the Part:

```text
Client
  ↓
DNS
  ↓
Destination IP
  ↓
Local Interface
  ↓
Route Selection
  ↓
Gateway / Network Path
  ↓
Firewall / Security Policy
  ↓
Destination Interface
  ↓
Listening Socket
  ↓
TLS
  ↓
HTTP
  ↓
Proxy / Load Balancer
  ↓
Application
  ↓
Dependency
```

Not every system contains every component.

A local application might be:

```text
Client
↓
Application
```

A cloud-hosted service might be:

```text
Internet Client
↓
DNS
↓
Public Load Balancer
↓
Private Application Network
↓
Application
↓
Managed Database
```

A Kubernetes application may introduce additional abstractions:

```text
Client
↓
DNS
↓
Load Balancer
↓
Ingress / Gateway
↓
Service
↓
Pod
↓
Application Container
↓
Dependency
```

The troubleshooting principle remains the same:

```text
Trace the path.

Prove each boundary.

Stop guessing.
```

---

# 3. BEGIN WITH SOURCE AND DESTINATION

Every network investigation should identify at least:

```text
Source

Destination

Protocol

Port

Expected Path
```

For example:

```text
Source:
application host

Destination:
database.internal.example

Protocol:
TCP

Port:
5432

Expected:
application should establish a TCP connection to the database
```

This is much stronger than:

```text
Database network is broken.
```

Networking problems are directional.

A host being reachable from one location does not prove it is reachable from another.

Always ask:

```text
Reachable from where?
```

---

# 4. NETWORK INTERFACES

A network interface is an operating-system representation of a network connection.

Interfaces may represent:

- physical Ethernet devices
- Wi-Fi devices
- loopback
- virtual interfaces
- bridges
- VLAN interfaces
- tunnel interfaces
- container interfaces
- cloud virtual NICs

Inspect Linux interfaces with:

```bash
ip link show
```

Inspect addresses:

```bash
ip address show
```

Short form:

```bash
ip addr
```

Do not assume the first interface displayed is the interface used for the application traffic.

---

# 5. INTERFACE STATE

An interface can exist without being operationally useful.

Inspect:

```bash
ip link show
```

You may encounter states and flags indicating whether the interface is administratively enabled and whether the operating system observes carrier or operational state.

The exact output varies by interface type and environment.

A useful distinction is:

```text
Interface Exists
≠
Interface Can Carry the Required Traffic
```

Questions include:

- Is the interface up?
- Does it have the expected address?
- Is it the interface selected by routing?
- Is the underlying network available?
- Is the application bound to an address on that interface?

---

# 6. LOOPBACK

Linux commonly provides the loopback interface:

```text
lo
```

with addresses including:

```text
127.0.0.1
```

for IPv4 loopback.

Loopback traffic remains local to the host.

This creates an important production failure pattern.

Suppose an application listens on:

```text
127.0.0.1:8080
```

A local request may succeed:

```bash
curl http://127.0.0.1:8080
```

while remote clients cannot connect.

The application is running.

The application is listening.

But it is listening only on loopback.

Therefore:

```text
Local Success
≠
Remote Reachability
```

---

# 7. IP ADDRESSES

An IP address identifies an interface within an IP network context.

Production systems may have several addresses simultaneously.

Examples include:

- loopback address
- private IPv4 address
- public IPv4 address
- IPv6 address
- container address
- virtual service address

Do not ask:

```text
What is the server's IP?
```

as if every system has exactly one.

Ask:

```text
Which address is relevant to this traffic path?
```

---

# 8. PRIVATE AND PUBLIC ADDRESSES

Cloud environments frequently separate private addressing from public reachability.

An instance might have:

```text
Private address:
10.x.x.x
```

while external traffic reaches a public endpoint that performs translation or proxying.

Therefore:

```text
Public Endpoint
≠
Necessarily the Address Bound Directly to the Application Host
```

Understanding that distinction becomes important when investigating cloud load balancers, NAT, proxies, and private subnets.

---

# 9. SUBNETS

A subnet defines an IP network range.

An address alone is insufficient to determine which destinations are considered directly reachable.

The prefix length matters.

Example:

```text
10.20.30.15/24
```

means the address is associated with a network prefix.

Do not troubleshoot production networks by guessing subnet boundaries from the visual appearance of an IP address.

Inspect the configured prefix.

```bash
ip address show
```

---

# 10. LOCAL DESTINATION OR ROUTED DESTINATION?

When sending traffic, the host must determine how to reach the destination.

Conceptually:

```text
Destination
   ↓
Routing Decision
   ↓
Directly Reachable?
   ├── Yes → Local Link
   └── No  → Appropriate Next Hop / Route
```

This is one reason subnet configuration matters.

Incorrect addressing or routing can send traffic toward the wrong path or leave the system without a usable path.

---

# 11. ROUTING

Linux maintains routing information that determines where packets should be sent.

Inspect:

```bash
ip route show
```

A routing table may contain:

- directly connected networks
- default route
- specific destination routes
- multiple routing tables in more advanced environments

The Linux `ip route` tooling operates on kernel routing tables.

---

# 12. THE DEFAULT ROUTE

A default route is used when a more specific matching route is not selected.

It may look conceptually like:

```text
default via 10.0.1.1 dev eth0
```

Do not interpret a default gateway as:

```text
Everything always goes through this gateway.
```

More specific routes may take precedence.

Routing decisions should be inspected rather than assumed.

---

# 13. ASK LINUX WHICH ROUTE IT WOULD USE

One of the most useful troubleshooting commands is:

```bash
ip route get <destination-IP>
```

For example:

```bash
ip route get 192.0.2.10
```

Depending on configuration, this can reveal information such as:

- selected route
- next hop
- interface
- source address

This answers a stronger question than merely displaying the whole routing table:

```text
How would this host attempt to reach this specific destination?
```

---

# 14. ROUTE SELECTION MATTERS

Imagine a host has:

```text
eth0 → application network

eth1 → management network
```

The destination is reachable only through `eth0`.

If routing selects `eth1`, the host can have:

```text
Two healthy interfaces
+
Correct destination address
+
Running application
```

and still fail.

The failure is path selection.

This is why interface health alone is not enough.

---

# 15. GATEWAYS

A gateway forwards traffic between networks.

A host does not need a direct Layer 2 relationship with every destination on the Internet.

Instead:

```text
Host
↓
Local Network
↓
Gateway
↓
Additional Networks
↓
Destination
```

A gateway is part of the path.

It is not the final destination.

---

# 16. NEIGHBOR DISCOVERY AND ARP CONCEPTS

For IPv4 communication on a local Ethernet-like network, the host may need to determine which link-layer address corresponds to a local IPv4 neighbor.

This is traditionally associated with ARP.

Linux exposes neighbor information using:

```bash
ip neigh show
```

The `ip neigh` command manages neighbor objects that bind protocol addresses to link-layer addresses, and Linux may report states such as `reachable`, `stale`, `incomplete`, `probe`, or `failed`.

Do not memorize neighbor states without context.

The operational question is:

```text
Can the host resolve and communicate with the required local next hop?
```

---

# 17. NEIGHBOR FAILURE

Suppose the routing decision says:

```text
Send traffic through gateway 10.0.1.1.
```

But neighbor resolution for that gateway fails.

Then the host knows:

```text
where traffic should go
```

but cannot successfully deliver it onto the local link.

This distinction is useful:

```text
Route Exists
≠
Next Hop Is Reachable
```

---

# 18. IPv6 NEIGHBOR DISCOVERY

Do not assume ARP applies to IPv6.

IPv6 uses Neighbor Discovery mechanisms rather than ARP.

At Mid-Level, the important habit is:

```text
Identify whether the traffic is IPv4 or IPv6 before applying protocol-specific assumptions.
```

This matters because modern DNS names may return both:

```text
A
```

and:

```text
AAAA
```

records.

A client may therefore attempt an IPv6 path even when an engineer is inspecting only IPv4.

---

# 19. SOCKETS

A socket is an operating-system communication endpoint.

For network services, think in terms of:

```text
Protocol
+
Local Address
+
Local Port
```

For established communication, both local and remote endpoints matter.

A web application might listen on:

```text
TCP 0.0.0.0:8080
```

A client connection may appear conceptually as:

```text
Local:
10.0.1.20:52144

Remote:
10.0.2.50:443
```

---

# 20. INSPECT SOCKETS WITH `ss`

On modern Linux systems, `ss` is commonly used to inspect sockets.

Listening TCP sockets:

```bash
ss -lnt
```

Include process information where permitted:

```bash
sudo ss -lntp
```

Established TCP connections:

```bash
ss -tn state established
```

UDP sockets:

```bash
ss -lun
```

Do not assume `sudo` is always available or authorized.

---

# 21. LISTENING SOCKET VERSUS RUNNING PROCESS

Suppose:

```bash
ps
```

shows the application process.

That proves:

```text
Process Exists
```

It does not prove:

```text
Expected Network Socket Exists
```

Check both.

The evidence chain should be:

```text
Process
↓
Expected Listening Address
↓
Expected Listening Port
↓
Application Response
```

---

# 22. BIND ADDRESS MATTERS

Compare:

```text
127.0.0.1:8080
```

with:

```text
0.0.0.0:8080
```

In a typical IPv4 context:

```text
127.0.0.1
```

means loopback only.

```text
0.0.0.0
```

used as a listening address commonly means all applicable local IPv4 addresses.

This distinction frequently explains:

```text
Works locally
but
fails remotely.
```

Do not change the bind address automatically.

First determine what exposure is intended.

A service intended only for a local reverse proxy may correctly listen on loopback.

---

# 23. PORTS

Ports identify transport-layer endpoints used by applications.

Common examples include:

```text
22    SSH
53    DNS
80    HTTP
443   HTTPS
```

These are conventions and registered/default uses, not guarantees about what a particular host is actually running.

A process can listen on many other ports.

The question is:

```text
Which protocol and port should this application use in this environment?
```

---

# 24. TCP AND UDP

TCP and UDP provide different transport behavior.

TCP provides a connection-oriented byte stream with mechanisms including:

- sequencing
- acknowledgement
- retransmission
- flow control
- congestion control

UDP is connectionless at the transport protocol level and does not provide TCP's delivery guarantees.

Do not translate this into:

```text
UDP is unreliable and therefore bad.
```

UDP is appropriate for many protocols and systems.

The correct protocol depends on application requirements.

---

# 25. TCP CONNECTION ESTABLISHMENT

A simplified TCP connection establishment is:

```text
Client                      Server

SYN ----------------------->

    <---------------- SYN-ACK

ACK ----------------------->
```

After successful establishment:

```text
ESTABLISHED
```

becomes a meaningful state.

This matters because:

```text
DNS Success
```

does not prove:

```text
TCP Connection Success
```

and:

```text
TCP Connection Success
```

does not prove:

```text
HTTP Success
```

Each layer provides different evidence.

---

# 26. TCP CONNECTION TERMINATION

A normal TCP connection can be closed through an exchange involving FIN and ACK segments.

The exact sequence can vary because each direction of a TCP connection can close independently.

The important operational point is:

```text
Connection Established
↓
Data Exchange
↓
Orderly Close
```

is different from:

```text
Connection Established
↓
Abrupt Reset
```

or:

```text
Connection Attempt
↓
Timeout
```

These failure signatures lead to different hypotheses.

---

# 27. TCP STATES

Useful TCP states may include:

```text
LISTEN
ESTABLISHED
SYN-SENT
SYN-RECV
FIN-WAIT-1
FIN-WAIT-2
CLOSE-WAIT
TIME-WAIT
LAST-ACK
```

The exact troubleshooting significance depends on:

- which side is being inspected
- connection lifecycle
- application behavior
- duration
- volume

Do not diagnose a problem merely because:

```text
There are many TIME-WAIT connections.
```

TIME-WAIT is a normal part of TCP connection lifecycle.

The useful question is whether the observed state distribution is abnormal for the workload and explains the symptom.

---

# 28. CONNECTION REFUSED

Suppose a client attempts:

```text
10.0.2.15:8080
```

and receives a connection-refused error.

This generally indicates something different from a timeout.

A refusal can indicate that the destination was reachable enough for the attempt to receive an immediate rejection, but no service accepted the connection at the requested endpoint or a network device actively rejected it.

Investigate:

```text
Is the application running?

Is it listening?

Is it listening on the correct address?

Is it listening on the expected port?

Is traffic reaching the intended host?
```

Do not immediately investigate DNS if the client has already reached the intended IP and received an explicit refusal.

---

# 29. CONNECTION TIMEOUT

A timeout tells a different story.

Possible causes include:

- traffic being dropped by a firewall
- cloud security policy
- missing route
- unreachable network
- unavailable destination
- asymmetric routing
- overloaded intermediary
- packet loss
- application or proxy timeout at a higher layer

Therefore:

```text
Timeout
≠
One Specific Root Cause
```

The important clue is:

```text
Expected response did not arrive within the allowed time.
```

Then determine at which layer.

---

# 30. CONNECTION RESET

A reset means an established or attempted TCP connection was abruptly rejected or terminated through TCP reset behavior.

Possible sources include:

- application
- operating system
- proxy
- load balancer
- firewall or intermediary

Do not record:

```text
Connection reset = server crashed.
```

Identify which component reset the connection.

Packet capture, intermediary logs, application logs, and endpoint behavior may be required.

---

# 31. UNREACHABLE DESTINATION

An unreachable result can arise when a host or network device determines that the destination or required route cannot be reached.

This is different from:

```text
Connection Refused
```

and:

```text
Application Returned HTTP 503
```

The layers are different.

---

# 32. RETRANSMISSION

TCP retransmits data when delivery is not successfully acknowledged according to its algorithms.

Retransmissions can occur because of:

- packet loss
- congestion
- path problems
- overloaded systems
- transient network conditions

A retransmission is evidence.

It is not automatically the root cause.

The stronger question is:

```text
Are retransmissions occurring at a level and time that correlates with the user-facing failure?
```

---

# 33. NETWORK LATENCY

Latency is the time required for communication.

Application latency may include several components:

```text
DNS Time
+
Connection Time
+
TLS Time
+
Proxy Time
+
Application Processing
+
Dependency Time
+
Response Transfer
```

Therefore:

```text
HTTP request took 5 seconds
```

does not prove:

```text
Network latency is 5 seconds.
```

Break the request into stages.

---

# 34. USE `curl` TO SEPARATE REQUEST PHASES

`curl` can expose useful timing information.

For example:

```bash
curl -sS -o /dev/null \
  -w 'dns=%{time_namelookup}\nconnect=%{time_connect}\ntls=%{time_appconnect}\nfirst_byte=%{time_starttransfer}\ntotal=%{time_total}\n' \
  https://example.com/
```

Interpret the fields in context.

For HTTP without TLS, TLS timing will not represent a TLS handshake.

The goal is to distinguish:

```text
Name resolution delay

Connection delay

TLS delay

Server / upstream response delay

Total request time
```

Do not treat one timing sample as a baseline.

---

# 35. DNS: NAMES ARE NOT ADDRESSES

Applications commonly use names such as:

```text
api.example.com
```

rather than fixed IP addresses.

DNS maps names to information including address records.

A simplified resolution path is:

```text
Application
↓
Operating-System Resolver
↓
Configured Recursive Resolver
↓
Cached Answer?
├── Yes → Return Cached Answer
└── No
     ↓
   DNS Hierarchy
     ↓
   Authoritative DNS
     ↓
   Answer
```

Recursive resolvers can cache answers according to DNS caching rules and TTLs.

---

# 36. RECURSIVE DNS

A recursive resolver performs resolution work on behalf of a client.

The client effectively asks:

```text
Resolve this name for me.
```

The resolver may:

- answer from cache
- contact other DNS servers
- return a failure

Do not assume every DNS query travels all the way to authoritative DNS.

Caching exists specifically to avoid that.

---

# 37. AUTHORITATIVE DNS

Authoritative nameservers provide authoritative information for the DNS zones they serve.

They represent the authoritative source for records within those zones.

This creates an important distinction:

```text
Authoritative Record Correct
```

does not necessarily mean:

```text
Every Client Already Sees the New Record
```

Caches may still hold older answers.

---

# 38. DNS RECORD TYPES

Common record types include:

### A

Maps a name to an IPv4 address.

### AAAA

Maps a name to an IPv6 address.

### CNAME

Associates an alias name with another canonical name.

### MX

Provides mail-exchange information.

### TXT

Stores textual data used for many purposes.

### NS

Identifies authoritative nameservers for a zone or delegation.

### SRV

Can describe service location information including host and port.

Different record types answer different questions.

Do not assume:

```text
DNS record
```

always means:

```text
IPv4 address.
```

---

# 39. TTL

DNS records include TTL information controlling how long DNS data may be cached before it must be refreshed according to DNS caching behavior.

This creates a major operational lesson.

Suppose:

```text
Old Address:
192.0.2.10

New Address:
192.0.2.20
```

You change the authoritative record.

Some resolvers may still legitimately return the old cached answer until relevant cached data expires.

---

# 40. "DNS PROPAGATION" NEEDS PRECISION

Engineers often say:

```text
DNS is still propagating.
```

That phrase can hide several different mechanisms.

Ask:

```text
Has the authoritative record changed?

What TTL applied to the previously cached answer?

Which resolver is being queried?

Does that resolver still have cached data?

Is there a local operating-system or application cache?

Are different resolvers returning different answers?
```

A DNS change may be correct at the authoritative source while clients continue using cached data until the applicable TTL expires.

---

# 41. DNS INSPECTION WITH `dig`

Where installed:

```bash
dig example.com
```

A shorter answer:

```bash
dig +short example.com
```

Query a particular record:

```bash
dig A example.com
```

```bash
dig AAAA example.com
```

Query a specific resolver:

```bash
dig @<resolver-IP> example.com
```

Do not assume `dig` is installed on minimal systems.

Check:

```bash
command -v dig
```

---

# 42. INSPECT AUTHORITATIVE INFORMATION

One useful troubleshooting approach is to identify authoritative nameservers:

```bash
dig NS example.com
```

Then query an authoritative server directly where appropriate:

```bash
dig @<authoritative-server> example.com A
```

This helps distinguish:

```text
Authoritative DNS State
```

from:

```text
Recursive Resolver State
```

Do not perform excessive or inappropriate queries against infrastructure you do not operate.

---

# 43. DNS FAILURE MODES

Possible DNS failures include:

- nonexistent name
- incorrect record
- stale cache
- resolver unavailable
- authoritative server problem
- incorrect search-domain behavior
- split-horizon DNS mismatch
- IPv4/IPv6 mismatch
- DNS blocked by network policy

The symptom:

```text
Could not resolve host
```

should keep your investigation at the DNS layer initially.

Do not start restarting the web server.

---

# 44. DNS LAB: STALE OR WRONG ANSWER

Use a domain or local lab DNS environment you control.

Establish expected state:

```bash
dig <lab-name> A
```

Record:

```text
Expected Address

Observed Address

Resolver Used

TTL
```

Change the lab record to a different controlled endpoint.

Then compare:

```bash
dig <lab-name> A
```

with:

```bash
dig @<authoritative-server> <lab-name> A
```

where appropriate.

The lesson is:

```text
Different DNS Observers
↓
May Temporarily Have Different Answers
↓
Because Caching Exists
```

Do not flush caches blindly before collecting evidence.

The stale answer is part of the incident evidence.

---

# 45. HTTP IS AN APPLICATION PROTOCOL

Once transport connectivity exists, an HTTP client can send an HTTP request.

A simplified request is:

```text
GET /health HTTP/1.1
Host: app.example.com
```

The server returns an HTTP response containing:

- status information
- headers
- optional body

HTTP methods express request semantics, and headers carry additional request or response information.

---

# 46. HTTP METHODS

Common methods include:

```text
GET
HEAD
POST
PUT
PATCH
DELETE
OPTIONS
```

Do not assume every method is safe to run during troubleshooting.

For example:

```text
GET /health
```

may be designed as a safe health check.

But:

```text
DELETE /users/123
```

may perform a destructive operation.

Before reproducing an HTTP request, understand its semantics.

---

# 47. HTTP STATUS CLASSES

HTTP status codes are grouped broadly as:

```text
1xx    Informational
2xx    Successful
3xx    Redirection
4xx    Client error
5xx    Server error
```

This classification is standardized in HTTP semantics.

Do not translate:

```text
5xx
```

directly into:

```text
Application code bug.
```

A 5xx response may be generated by:

- application
- reverse proxy
- gateway
- load balancer
- upstream service

Determine which component generated it.

---

# 48. COMMON STATUS CODES IN TROUBLESHOOTING

### 200

The HTTP request succeeded according to the semantics of that endpoint.

It does not prove every internal dependency is healthy unless the endpoint is designed to check them.

### 301 / 302

Redirect behavior.

Inspect the `Location` header and expected redirect policy.

### 400

The receiving HTTP component considers the request invalid in some way.

### 401

Authentication is required or the supplied authentication is not accepted according to the application's authentication scheme.

### 403

The server understood the request but refuses it.

### 404

The requested resource was not found at that HTTP endpoint.

### 429

The client is being rate limited according to the service's policy.

### 500

An internal server error occurred at the component generating the response.

### 502

A proxy or gateway received an invalid response from an upstream.

### 503

The service is unavailable.

### 504

A gateway or proxy timed out waiting for an upstream response.

The exact operational meaning still depends on architecture.

---

# 49. AN HTTP ERROR IS EVIDENCE OF SUCCESSFUL LOWER LAYERS

Suppose:

```bash
curl -i https://app.example.com/
```

returns:

```text
HTTP/1.1 503 Service Unavailable
```

Several things probably succeeded far enough to receive an HTTP response:

```text
Name Resolution
↓
Network Path
↓
Transport Connection
↓
TLS, if HTTPS
↓
HTTP Request Reached an HTTP-Speaking Component
```

The failure is now likely higher in the path.

That is useful narrowing.

---

# 50. HTTP HEADERS

Headers carry metadata and protocol information.

Inspect them with:

```bash
curl -I https://example.com/
```

or for a normal request with response headers:

```bash
curl -i https://example.com/
```

Useful headers may include:

```text
Host
Content-Type
Content-Length
Location
Authorization
Cache-Control
Retry-After
X-Request-ID
```

Actual headers vary by application and intermediary.

HTTP headers can be request, response, representation, or other protocol metadata.

---

# 51. THE `Host` HEADER

Modern HTTP infrastructure frequently hosts multiple applications behind one IP address.

The requested hostname helps the server or intermediary decide which virtual application should receive the request.

Therefore:

```text
Correct IP
+
Wrong Hostname
```

may reach the correct machine while selecting the wrong virtual host or route.

This is one reason testing only:

```bash
curl http://<IP>
```

can produce misleading results.

---

# 52. TEST A SPECIFIC IP WHILE PRESERVING THE HOSTNAME

`curl` provides mechanisms for controlled endpoint testing.

For example:

```bash
curl --resolve app.example.com:443:<IP> \
  https://app.example.com/
```

This allows testing a specific address while retaining the requested hostname for HTTP and TLS behavior.

This is often more useful than changing `/etc/hosts` during an investigation.

Understand exactly what `--resolve` changes before using it.

---

# 53. REDIRECTS

HTTP redirects use 3xx responses and typically a `Location` header to direct the client toward another URL.

Inspect without automatically following:

```bash
curl -I https://example.com/
```

Follow redirects:

```bash
curl -L https://example.com/
```

But during troubleshooting, first inspect the original response.

A redirect loop can otherwise be hidden behind the client's automatic behavior.

---

# 54. KEEP-ALIVE AND CONNECTION REUSE

Creating a new transport connection for every request adds overhead.

HTTP can reuse connections.

For HTTP/1.1, persistent connections are normal behavior unless closure is requested according to the protocol. HTTP/2 uses different connection-management mechanisms and multiplexing.

Do not treat:

```text
Keep-Alive
```

as one universal implementation detail across every HTTP version.

At Mid-Level, understand why connection reuse affects:

- latency
- connection count
- proxy behavior
- backend load
- resource consumption

---

# 55. PROXIES

A proxy is an intermediary that participates in communication between clients and servers.

Broadly:

```text
Client
↓
Proxy
↓
Destination
```

A forward proxy generally represents clients when reaching external destinations.

A reverse proxy generally represents or fronts servers.

Production systems frequently use reverse proxies.

---

# 56. REVERSE PROXIES

A reverse proxy may perform functions including:

- request routing
- TLS termination
- connection management
- header manipulation
- access logging
- authentication integration
- load distribution
- compression
- caching

A common path is:

```text
Client
↓
Reverse Proxy :443
↓
Application :8080
```

This creates two separate connections:

```text
Client ↔ Proxy
```

and:

```text
Proxy ↔ Application
```

One can work while the other fails.

---

# 57. UPSTREAMS

Reverse proxies commonly refer to backend services as upstreams.

Example:

```text
Client
↓
Nginx
↓
Upstream Application
```

If the proxy is healthy but the application is unavailable, the proxy may return an error such as:

```text
502
```

or:

```text
504
```

depending on what happened.

The correct investigation is not:

```text
Nginx returned an error, therefore Nginx is broken.
```

Instead:

```text
Did the proxy receive the client request?

Which upstream did it select?

Could it connect?

Did the upstream respond?

How long did it wait?

What do proxy and upstream logs show?
```

---

# 58. REVERSE PROXY LAB

Use a disposable Linux host.

Assume a test application is listening locally on:

```text
127.0.0.1:8080
```

Verify first:

```bash
curl -i http://127.0.0.1:8080/health
```

Then configure an approved reverse proxy such as Nginx to listen on another lab port and proxy requests to:

```text
http://127.0.0.1:8080
```

The exact installation and configuration path depends on the Linux distribution and Nginx packaging.

Verify the configuration using the installed Nginx validation mechanism before reload.

Then test:

```text
Client
↓
Nginx
↓
Application
```

Record evidence from:

- client
- proxy access log
- proxy error log
- application log
- application listening socket

---

# 59. BREAK THE UPSTREAM

Stop the application while leaving the reverse proxy running.

Now request the proxy endpoint.

Do not repair immediately.

Record:

```text
Client Result

HTTP Status

Proxy Error

Proxy Log

Application Process State

Application Socket State
```

The expected reasoning is:

```text
Client Reaches Proxy
↓
Proxy Accepts Request
↓
Proxy Cannot Successfully Reach Upstream
↓
Proxy Returns Error
```

The proxy is part of the evidence path, not automatically the root cause.

---

# 60. LOAD BALANCERS

A load balancer distributes traffic among backend targets.

Conceptually:

```text
Clients
  ↓
Load Balancer
  ├── Backend A
  ├── Backend B
  └── Backend C
```

Load balancers may operate at different networking layers and provide different capabilities.

At Mid-Level, understand:

- listeners
- target groups/backend pools
- health checks
- healthy/unhealthy targets
- routing rules
- ports
- protocols
- TLS termination
- timeouts

Exact terminology varies by product and provider.

---

# 61. LOAD BALANCER HEALTH CHECKS

A load balancer may remove a backend from active traffic if its health checks fail.

This creates an important distinction:

```text
Application Process Running
```

does not prove:

```text
Load Balancer Considers Backend Healthy
```

Check:

```text
Health Check Protocol

Health Check Port

Health Check Path

Expected Status

Timeout

Backend Reachability
```

A wrong health-check path can make a healthy application appear unavailable to the load balancer.

---

# 62. FIREWALLS

A firewall evaluates traffic against policy.

A rule may consider information such as:

- source
- destination
- protocol
- port
- connection state
- interface

The exact capabilities depend on the firewall technology.

The key troubleshooting question is:

```text
Is traffic allowed at every policy boundary in the required direction?
```

---

# 63. HOST FIREWALL VERSUS CLOUD FIREWALL

A cloud-hosted service may be affected by several independent controls:

```text
Cloud Security Policy
↓
Network ACL / Subnet Policy
↓
Host Firewall
↓
Application Bind Address
```

Passing one does not prove the others.

For example:

```text
Cloud security rule allows TCP/443
```

does not prove:

```text
Application is listening on TCP/443.
```

---

# 64. CLOUD SECURITY GROUP CONCEPTS

Cloud providers commonly provide instance or interface-level network security controls.

Exact behavior differs by provider.

Some security-group implementations are stateful.

Other network controls may behave differently.

Never copy firewall reasoning from one cloud product to another without checking the provider's current documentation.

The general model is:

```text
Source
↓
Cloud Policy
↓
Destination Interface
↓
Host Policy
↓
Listening Service
```

---

# 65. NETWORK ACL CONCEPTS

Cloud network ACLs or equivalent subnet-level controls can create another policy boundary.

Depending on provider and implementation, rules may be:

- stateless
- directional
- ordered

Do not assume the behavior is identical to a security group.

At this stage, the required skill is recognizing multiple independent network-policy layers and knowing to inspect the exact provider behavior.

---

# 66. NAT

Network Address Translation modifies addressing information as traffic crosses a translation boundary.

Common uses include:

- allowing private hosts to initiate outbound Internet connections
- translating public addresses to private infrastructure
- conserving address space
- network boundary design

A simplified outbound model is:

```text
Private Host
↓
NAT
↓
Public Network
```

The remote destination may observe the translated source rather than the original private address.

---

# 67. NAT IS NOT A GENERAL REACHABILITY GUARANTEE

Suppose a private instance can access:

```text
https://example.com
```

through outbound NAT.

That does not mean Internet clients can initiate connections back to that private instance.

Outbound translation and inbound service exposure are different requirements.

---

# 68. CONTAINER NETWORK BOUNDARIES

Containers introduce additional networking abstractions.

A container can have:

- its own network namespace
- virtual interface
- container IP
- bridge connectivity
- published host port

Conceptually:

```text
Client
↓
Host Interface
↓
Published Port / Network Rule
↓
Container Network
↓
Container Socket
↓
Application
```

This creates another classic failure:

```text
Application works inside container
but not from host.
```

or:

```text
Application works from host
but not remotely.
```

Each statement proves a different part of the path.

---

# 69. CONTAINER PORT VERSUS APPLICATION PORT

A container image may document or expose a port.

That does not cause the application to listen.

The application itself must bind a socket.

Likewise, Docker port publication does not fix an application listening only on an unsuitable interface inside its network namespace.

Always verify:

```text
Application Socket

Container Network

Published Port

Host Socket

External Policy
```

---

# 70. KUBERNETES NETWORK BOUNDARIES

Kubernetes introduces abstractions including:

```text
Pod
Service
Endpoint
Ingress / Gateway
Load Balancer
```

A production path may be:

```text
Client
↓
External DNS
↓
Cloud Load Balancer
↓
Ingress / Gateway
↓
Service
↓
Pod
↓
Application
```

At Mid-Level, troubleshooting must move beyond:

```text
The Pod is Running.
```

A Running Pod can still be:

- not Ready
- listening on the wrong port
- absent from Service endpoints
- selected incorrectly
- unable to reach a dependency

Detailed Kubernetes networking appears later in the Mid-Level curriculum.

---

# 71. TLS: ENCRYPTION PLUS AUTHENTICATED IDENTITY

HTTPS normally uses HTTP over TLS.

TLS provides mechanisms for:

- encryption
- integrity
- endpoint authentication

The simplified path is:

```text
TCP Connection
↓
TLS Handshake
↓
Certificate Validation
↓
Encrypted Application Communication
↓
HTTP
```

Therefore:

```text
TCP/443 reachable
```

does not prove:

```text
HTTPS works.
```

TLS can fail after TCP succeeds.

---

# 72. CERTIFICATES

A server certificate contains information associated with the server's identity and public key.

Client validation may involve:

- certificate validity period
- hostname identity
- trust chain
- signature validation
- trusted certificate authorities
- other policy requirements

Do not reduce certificate troubleshooting to:

```text
Certificate exists.
```

The client must be able to validate it appropriately.

---

# 73. CERTIFICATE CHAINS

A simplified chain may look like:

```text
Server Certificate
↓
Intermediate CA
↓
Trusted Root CA
```

The server generally needs to present the appropriate chain information required for clients to build a valid trust path.

A server may have a valid leaf certificate while clients still fail because the served chain is incomplete or incorrect.

---

# 74. HOSTNAME VALIDATION

Suppose the certificate is valid for:

```text
api.example.com
```

but the client requests:

```text
payments.example.com
```

The certificate may be:

```text
unexpired
```

and:

```text
cryptographically valid
```

while still failing hostname verification.

Therefore:

```text
Certificate Valid
```

must include:

```text
Valid for the identity the client requested.
```

---

# 75. CERTIFICATE EXPIRATION

Certificates have validity periods.

Inspect a remote endpoint using appropriate TLS tooling.

With OpenSSL:

```bash
openssl s_client \
  -connect example.com:443 \
  -servername example.com
```

The `-servername` option supplies the TLS server name, which is important for servers hosting multiple TLS identities.

Do not send arbitrary input after connecting unless you understand the protocol.

---

# 76. INSPECT CERTIFICATE DETAILS

A useful pipeline is:

```bash
openssl s_client \
  -connect example.com:443 \
  -servername example.com \
  </dev/null 2>/dev/null |
openssl x509 -noout -subject -issuer -dates
```

This can help inspect:

- subject
- issuer
- not-before date
- not-after date

Do not use expiration alone as proof that certificate validation succeeds.

---

# 77. TLS TERMINATION

TLS may terminate at different places.

Example:

```text
Client
↓ HTTPS
Load Balancer
↓ HTTP
Application
```

or:

```text
Client
↓ HTTPS
Load Balancer
↓ HTTPS
Application
```

or:

```text
Client
↓ HTTPS
Reverse Proxy
↓ HTTP
Application
```

This matters because the component presenting the public certificate may not be the application server.

Always ask:

```text
Where does TLS terminate?
```

---

# 78. TLS FAILURE WORKFLOW

Use:

```text
HTTPS Failure
↓
Did DNS Resolve?
↓
Did TCP Connect?
↓
Did TLS Handshake Begin?
↓
What Certificate Was Presented?
↓
Does Hostname Match?
↓
Is Certificate Within Validity Period?
↓
Can Client Build a Trusted Chain?
↓
Did Negotiation Fail for Another Reason?
```

Do not disable certificate verification merely to make the error disappear.

---

# 79. NEVER USE INSECURE TLS FLAGS AS THE "FIX"

A command such as:

```text
curl -k
```

or:

```text
curl --insecure
```

disables normal certificate verification for that request.

It can sometimes be used in a controlled diagnostic experiment when the security implications are understood.

It is not a production remediation for:

```text
certificate verification failed.
```

The proper question is:

```text
Why did verification fail?
```

---

# 80. HTTP VERSUS TLS FAILURE

Compare:

```text
certificate verify failed
```

with:

```text
HTTP/1.1 500 Internal Server Error
```

The first indicates failure during TLS validation.

The second proves communication progressed far enough to obtain an HTTP response.

These belong to different layers.

---

# 81. BUILD A FAILURE-SIGNATURE MENTAL MODEL

When a request fails, classify the failure before proposing a repair.

```text
Name cannot be resolved
→ DNS investigation

No route / unreachable
→ Routing / network-path investigation

Connection timed out
→ Path / filtering / availability investigation

Connection refused
→ Endpoint / listener / rejection investigation

TLS validation failed
→ TLS / certificate investigation

HTTP 4xx
→ HTTP request / authentication / authorization / routing investigation

HTTP 5xx
→ HTTP-serving component / upstream / application investigation

HTTP 200 but wrong behavior
→ Application / data / dependency / logic investigation
```

These are starting points, not universal final diagnoses.

---

# 82. PING HAS LIMITED MEANING

`ping` commonly uses ICMP Echo.

A successful ping can show that certain ICMP traffic successfully traversed the path.

It does not prove:

```text
TCP/443 works.
```

A failed ping does not prove:

```text
Host is down.
```

ICMP may be blocked or rate-limited while application traffic works normally.

Use the protocol relevant to the application.

---

# 83. TRACEROUTE HAS LIMITED MEANING

Tools such as:

```text
traceroute
```

or:

```text
tracepath
```

can provide information about network paths.

But production networks may:

- filter probe traffic
- hide hops
- use load-balanced paths
- use asymmetric routing
- treat probe traffic differently from application traffic

A missing hop response is not automatically evidence that the hop is broken.

---

# 84. TEST THE REAL PROTOCOL

If the application uses:

```text
HTTPS
```

test HTTPS.

If the database uses:

```text
TCP/5432
```

test that transport path using an appropriate non-destructive method.

If DNS is failing:

```text
query DNS.
```

Do not rely on unrelated protocols as definitive proof.

---

# 85. `nc` FOR TRANSPORT TESTING

Where Netcat is available, a TCP connectivity test may look like:

```bash
nc -vz <host> <port>
```

For example:

```bash
nc -vz 127.0.0.1 8080
```

Different Netcat implementations have different options and behavior.

Check:

```bash
nc -h
```

before assuming flags are portable.

A successful TCP connection proves transport reachability to that endpoint.

It does not prove the application protocol is healthy.

---

# 86. LOCAL TEST VERSUS REMOTE TEST

Suppose:

```bash
curl http://127.0.0.1:8080/health
```

works on the server.

That proves:

```text
Application responds through local loopback path.
```

It does not prove:

- remote interface reachability
- host firewall policy
- cloud firewall policy
- load balancer health
- public DNS
- public TLS

Testing from different positions is essential.

---

# 87. TEST FROM MULTIPLE OBSERVATION POINTS

A production investigation may require tests from:

```text
Application Host

Peer Host in Same Subnet

Different Internal Network

Load Balancer

External Client
```

Each observation point tests a different segment.

Example:

```text
Application Host → Application
PASS

Peer Host → Application
PASS

Load Balancer → Application
FAIL
```

Now the likely failure domain has narrowed significantly.

---

# 88. THE OBSERVATION-POINT PRINCIPLE

Every network test should record:

```text
Where was the test executed?

What destination was used?

What protocol?

What port?

What result?
```

Do not record only:

```text
curl worked.
```

Record:

```text
From application host 10.0.2.15,
curl to http://127.0.0.1:8080/health
returned HTTP 200.
```

That evidence is reusable.

---

# 89. PACKET CAPTURE

When higher-level tools cannot explain behavior, packet capture may provide lower-level evidence.

A common Linux tool is:

```text
tcpdump
```

Example:

```bash
sudo tcpdump -ni any tcp port 8080
```

This can help answer:

```text
Did traffic reach the host?

Did the host respond?

Was a TCP handshake attempted?

Were resets observed?
```

Packet capture can contain sensitive information.

Use:

- narrow filters
- approved storage
- limited duration
- proper access controls

Do not capture production traffic indiscriminately.

---

# 90. PACKET CAPTURE IS EVIDENCE, NOT MAGIC

Suppose the client reports a timeout.

Capture on the destination shows:

```text
No matching packets arrive.
```

That tells you:

```text
The destination host did not observe the tested traffic at this capture point.
```

It does not by itself tell you which upstream firewall, route, NAT, or intermediary dropped it.

You have narrowed the investigation.

---

# 91. THE FOUR-POINT TCP QUESTION

For a TCP failure, ask:

```text
1. Did the client send the connection attempt?

2. Did it reach the server?

3. Did the server respond?

4. Did the response return to the client?
```

This model is especially useful when routing is asymmetric or multiple security boundaries exist.

---

# 92. ASYMMETRIC ROUTING

The path from client to server does not always equal the path from server to client.

Conceptually:

```text
Client
  ↓
Path A
  ↓
Server

Server
  ↓
Path B
  ↓
Client
```

This can matter for:

- firewalls
- NAT
- stateful network devices
- multi-interface hosts
- complex cloud routing

Do not assume the return path is identical.

# 110. DO NOT USE "NETWORK ISSUE" AS A ROOT CAUSE

Weak incident statement:

```text
The site was down because of a network issue.
```

Stronger:

```text
The reverse proxy attempted to connect to the application on TCP/8081,
while the application was listening on TCP/8080.

Client-to-proxy connectivity remained healthy.

Proxy logs showed upstream connection failures.

Application-host socket inspection confirmed the application was healthy
and listening on TCP/8080.

Correcting the upstream port restored requests.
```

The stronger statement identifies:

- failing boundary
- expected state
- observed state
- evidence
- correction
- verification

# 111. TRACE FROM THE CLIENT INWARD

When a user reports:

```text

```

one useful workflow is:

```text

↓

↓
Confirm Returned Address
↓
Attempt Required Transport Connection
↓
Validate TLS
↓
Inspect HTTP Response
↓
Inspect Proxy / Load Balancer
↓
Inspect Application
↓
Inspect Dependency
```

This is especially useful when you know little about the failure.

---

# 112. TRACE FROM THE APPLICATION OUTWARD

If the application reports:

```text
Database connection failed.
```

start from the application environment:

```text
Application
↓
Resolve Database Name
↓
Inspect Route
↓
Test Required Port
↓
Inspect Security Boundary
↓
Inspect Database Listener
↓
```

Do not begin from the public load balancer.

It is not on that dependency path.

# 113. TRACE FROM BOTH SIDES

For difficult failures:

```text
Client → toward destination
```

and:

```text
Server → toward client
```

or:

```text
Application → dependency
```

and:

```text
Dependency → application
```

can reveal where observations stop agreeing.

This is especially useful with:

- firewalls
- asymmetric routing
- NAT
- multiple network interfaces
- load balancers

# 114. BUILD A NETWORK EVIDENCE TABLE

During an incident, maintain something like:

| Layer | Expected | Observed | Evidence | Result |
|---|---|---|---|---|
| DNS | Name resolves to LB | Correct IP | `dig` | Pass |
| Route | Client can route | Route present | route evidence | Pass |
| TCP | 443 reachable | Established | client test | Pass |
| TLS | Cert validates | Valid | TLS inspection | Pass |
| HTTP | `/health` returns 200 | 503 | `curl` | Fail |
| LB | Healthy backend | Backend unhealthy | LB health | Fail |
| App | Port 8080 listening | Listener exists | `ss` | Pass |
| Dependency | DB reachable | Timeout | dependency test | Fail |

This prevents repeatedly investigating layers already supported by evidence.

---

# 115. RECENT CHANGES MATTER

Networking incidents often follow changes such as:

- DNS record change
- certificate renewal
- firewall rule
- security-group change
- subnet route change
- load-balancer rule
- proxy configuration
- application port change
- container port mapping
- Kubernetes Service selector
- deployment
- dependency migration

Always ask:

```text
What changed before the symptom began?
```

But do not automatically conclude:

```text
Recent change = root cause.
```

Treat it as evidence requiring validation.

---

# 116. PORT CHANGES CREATE MULTI-LAYER FAILURES

Suppose an application changes from:

```text
8080
```

to:

```text
9000
```

Several components may require coordinated updates:

```text
Application Configuration
↓
Container Configuration
↓
Service Definition
↓
Reverse Proxy Upstream
↓
Load Balancer Target
↓
Health Check
↓
Firewall Rules
↓
Monitoring
```

Changing only one layer can break the traffic path.

This is why service ownership requires understanding the whole path.

---

# 117. DNS CHANGES CREATE TIME-DEPENDENT BEHAVIOR

Suppose traffic moves from:

```text
Old Load Balancer
```

to:

```text
New Load Balancer
```

through DNS.

Some clients may reach the new endpoint while others still use cached older data.

Therefore:

```text
Works for me.
```

is weak evidence.

Record:

```text
Client Location

Resolver

Returned Address

TTL

Time
```

---

# 118. PROXY HEADERS AND CLIENT IDENTITY

When requests pass through proxies, the backend may see the proxy as its immediate network peer.

Systems may use HTTP headers to carry information about:

- original host
- original scheme
- client address
- request identifiers

Examples vary by proxy and platform.

Do not blindly trust client-supplied forwarding headers.

Trusted proxy configuration is a security boundary.

At Mid-Level, understand that:

```text
Network Peer
```

and:

```text
Original Client Identity Claimed Through Proxy Metadata
```

are different concepts.

---

# 119. TIMEOUTS EXIST AT MULTIPLE LAYERS

A production request can encounter:

```text
DNS timeout

TCP connect timeout

TLS handshake timeout

Proxy connect timeout

Proxy read timeout

Application timeout

Database timeout

External API timeout
```

Therefore:

```text
Request timed out.
```

is incomplete.

Ask:

```text
Which component timed out waiting for what?
```

---

# 120. RETRIES CAN HIDE FAILURES

Applications, SDKs, proxies, and clients may retry failed operations.

A user sees:

```text
Request took 12 seconds.
```

Internally:

```text
Attempt 1
↓
Timeout

Retry
↓
Attempt 2
↓
Timeout

Retry
↓
Attempt 3
↓
Success
```

The request eventually succeeds, but latency becomes severe.

Investigate retry behavior when symptoms appear intermittent or multiplied.

Do not add retries automatically.

Retries can increase load on already failing systems.

---

# 121. TIMEOUTS AND RETRIES MUST BE REASONED ABOUT TOGETHER

Imagine:

```text
Timeout = 10 seconds
Retries = 3
```

A dependency failure may now hold resources for a substantial period.

The exact total depends on retry policy, backoff, and implementation.

The important relationship is:

```text
Slow / Failed Dependency
↓
Long Wait
↓
Retry
↓
Additional Requests
↓
More Resource Consumption
↓
Potential Cascading Failure
```

This is the beginning of distributed-systems reasoning.

---

# 122. KEEP-ALIVE CAN CHANGE INCIDENT BEHAVIOR

Connection reuse can mean existing connections continue working while new connections fail.

For example:

```text
Existing persistent connections
→ continue serving requests

New connections
→ fail
```

This can create apparently inconsistent reports.

Always ask whether the test used:

```text
Existing connection
```

or:

```text
New connection.
```

---

# 123. LOAD BALANCING CAN MAKE FAILURES INTERMITTENT

Suppose:

```text
Backend A = Healthy
Backend B = Healthy
Backend C = Broken
```

A client may observe:

```text
Request 1 → Success
Request 2 → Success
Request 3 → Failure
Request 4 → Success
```

This can appear random.

Investigate:

```text
Which backend handled each request?
```

Useful evidence may include:

- request IDs
- backend identifiers
- load-balancer logs
- application logs
- tracing

---

# 124. DNS CAN ALSO MAKE FAILURES APPEAR INTERMITTENT

A name may return multiple addresses.

If only one destination is unhealthy:

```text
Address A → Healthy
Address B → Broken
```

different requests or clients may observe different behavior.

Inspect all relevant returned records rather than testing only one.

---

# 125. IPv4 AND IPv6 CAN PRODUCE DIFFERENT RESULTS

A hostname may have:

```text
A
```

and:

```text
AAAA
```

records.

One network path may work while the other fails.

When symptoms differ by client, inspect which address family is being used.

Useful tests can include:

```bash
curl -4 https://example.com/
```

and:

```bash
curl -6 https://example.com/
```

only when the client and environment support those address families.

These flags are diagnostic controls, not permanent fixes for broken IPv6 or IPv4 connectivity.

---

# 126. APPLICATION HEALTH VERSUS NETWORK HEALTH

Suppose:

```text
TCP connection succeeds.
```

This proves a listener accepted transport connectivity.

It does not prove:

```text
Application can serve useful requests.
```

Likewise:

```text
HTTP /health returns 200.
```

may not prove:

```text
Database works.
```

unless that health endpoint intentionally validates the database.

Always understand what a health check actually measures.

---

# 127. HEALTH CHECK DESIGN AFFECTS NETWORK ROUTING

A load balancer may use:

```text
GET /health
```

If `/health` always returns:

```text
200
```

even when the application cannot perform critical work, the load balancer may continue routing traffic to a functionally broken backend.

If the health endpoint checks every external dependency, a temporary dependency problem may remove every backend simultaneously.

Health design involves tradeoffs.

Detailed reliability design comes later, but Mid-Level engineers must recognize the consequence.

- DNS query results
- connection metrics
- socket state
- load-balancer metrics
- proxy access logs
- proxy error logs

- packet captures

# 130. SECURITY WHILE TROUBLESHOOTING NETWORKS

Network evidence may contain:

- internal hostnames
- private addresses
- authentication headers
- cookies
- API tokens
- certificates
- customer requests
- personal data


Verbose HTTP output can expose headers and credentials.

Use minimum necessary evidence.

# 131. AI-ASSISTED NETWORK TROUBLESHOOTING

AI can help with:

- interpreting routing output
- explaining socket states
- reviewing proxy configuration
- analyzing sanitized DNS results
- comparing expected and observed paths
- generating hypotheses
- explaining TLS errors
- reviewing packet-capture summaries
- organizing incident timelines

AI should not replace path verification.

# 132. BAD AI NETWORKING PROMPT

```text
My website is down. Fix the network.
```

There is almost no useful evidence.

The model may guess among:

- DNS
- firewall
- TLS
- application
- load balancer
- proxy

That is not troubleshooting.

---

# 133. BETTER AI NETWORKING PROMPT

```text
Expected path:

Client
→ DNS
→ load balancer TCP/443
→ TLS termination
→ reverse proxy TCP/8080
→ application TCP/9000

Observed:

DNS returns the expected load balancer address.

TCP/443 connects successfully.

TLS certificate validates for the requested hostname.

Client receives HTTP 502.

Reverse-proxy error log reports connection refused to
10.0.4.21:9000.

On 10.0.4.21, the application process exists but
ss shows it listening on 127.0.0.1:9000.

Provide the strongest root-cause hypothesis and identify
which additional evidence should be collected before changing configuration.
```

Now the AI can reason from actual evidence.

---

# 134. VERIFY AI NETWORK RECOMMENDATIONS

AI may suggest:

```text
Open the firewall.

Disable TLS verification.

Change the subnet.

Add 0.0.0.0/0.

Restart networking.

Flush DNS.

Delete proxy configuration.

Disable IPv6.
```

These can have serious consequences.

Before applying a suggestion:

```text
What evidence supports it?

Which layer would it change?

What is the blast radius?

Could it weaken security?

Is the command correct for this operating system or cloud?

How will the change be reversed?

What evidence will prove it worked?
```

Never make a broad network change merely to test whether the problem disappears.

# 138. FAILURE: DNS DOES NOT RESOLVE

Start with:

```bash
dig <hostname>
```

or another available resolver tool.

Determine:

```text
Does the name exist?

Which resolver was queried?

What response was returned?

Which record type?

What does authoritative DNS say?

Is caching involved?
```

Do not change firewall rules.

No destination has been established yet.

---

# 139. FAILURE: DNS RESOLVES TO WRONG ADDRESS

Determine:

```text
Expected Address

Observed Address

Authoritative Answer

Recursive Answer

TTL

Recent DNS Changes
```

Then identify whether the issue is:

- incorrect authoritative record
- cached older data
- split DNS
- wrong resolver
- local override

Do not call every old cached response "broken DNS."

---

# 140. FAILURE: CONNECTION TIMES OUT

Determine:

```text
Correct destination?

Correct route?

Correct port?

Listener expected?

Firewall/security rule?

Does packet reach destination?

Does response leave destination?
```

Use evidence from both ends where possible.

---

# 141. FAILURE: CONNECTION REFUSED

Determine:

```text
Correct host?

Correct port?

Expected listener exists?

Correct bind address?

Service running?

Proxy pointing to correct port?
```

A refusal often localizes the problem much closer to the endpoint than a silent timeout.

---

# 142. FAILURE: TLS ERROR

Determine:

```text
Did TCP connect?

Which hostname was requested?

Which certificate was presented?

Does identity match?

Is certificate currently valid?

Is the chain trusted?

Where does TLS terminate?
```

Do not investigate application database queries first.

---

# 143. FAILURE: HTTP 404

Determine:

```text
Which component returned 404?

Correct hostname?

Correct path?

Correct HTTP method?

Correct virtual host?

Correct proxy route?
```

A 404 proves that an HTTP-speaking component responded.

The problem may be routing rather than network reachability.

---

# 144. FAILURE: HTTP 502

Determine:

```text
Which proxy/gateway generated it?

Which upstream was selected?

Could it connect?

Did upstream send a valid response?

What do upstream logs show?
```

Do not assume the public load balancer itself is defective.

---

# 145. FAILURE: HTTP 503

Determine:

```text
Which component generated it?

No healthy backends?

Application unavailable?

Maintenance state?

Dependency unavailable?

Rate or capacity policy?
```

The status code narrows the investigation but does not uniquely identify the root cause.

---

# 146. FAILURE: HTTP 504

Determine:

```text
Which gateway timed out?

Which upstream was it waiting for?

Did upstream receive request?

Was upstream slow?

Was dependency slow?

What timeout expired?
```

Remember:

```text
Gateway Timeout
```

can be caused by a slow dependency several layers deeper.

---

# 147. FAILURE: APPLICATION SLOW

Do not assume:

```text
Slow = network.
```

Measure:

```text
DNS

Connect

TLS

First Byte

Total
```

Then correlate:

- proxy timing
- application timing
- dependency timing
- system metrics

The slowest visible stage may narrow the investigation.

---

# 148. FAILURE: WORKS FROM SERVER, FAILS EXTERNALLY

Likely boundaries to investigate include:

```text
Bind Address

Host Firewall

Cloud Firewall

Route

Load Balancer

Public DNS

TLS

NAT / Public Exposure
```

The local success already proves something.

Use it.

---

# 149. FAILURE: WORKS BY IP, FAILS BY NAME

Investigate:

```text
DNS

Host Header

TLS Hostname

Virtual Host Routing
```

Do not conclude:

```text
DNS is definitely broken.
```

The name may resolve correctly while the hostname affects HTTP or TLS routing.

---

# 150. FAILURE: WORKS WITH HTTP, FAILS WITH HTTPS

The failure domain has narrowed.

Investigate:

```text
TLS Listener

Certificate

Certificate Chain

Hostname

TLS Termination

HTTPS Proxy Configuration
```

Basic application reachability may already be healthy.

---

# 151. FAILURE: SOME CLIENTS WORK, OTHERS FAIL

Investigate differences in:

- DNS resolver
- cached records
- IPv4 versus IPv6
- client network
- geographic endpoint
- proxy
- TLS trust store
- load-balancer backend
- network policy

Do not assume inconsistent reports mean user error.

---

# 152. FAILURE: ONE BACKEND FAILS

If traffic is load balanced:

```text
Backend A → 200
Backend B → 200
Backend C → 500
```

investigate Backend C.

Do not restart every backend.

Reduce blast radius.

---

# 153. FAILURE: DEPENDENCY CONNECTION TIMEOUT

From the application environment:

```text
Resolve Dependency
↓
Inspect Address
↓
Inspect Route
↓
Test Required Transport
↓
Inspect Network Policy
↓
Inspect Dependency Listener
↓
Inspect Dependency Health
```

Keep the public request path separate from the internal dependency path.

---

# 154. DO NOT CONFUSE AUTHENTICATION WITH NETWORK CONNECTIVITY

Suppose the database returns:

```text
authentication failed
```

That is useful evidence.

Communication succeeded far enough for the database to evaluate credentials.

Do not begin by opening firewall ports.

The failure has moved above basic connectivity.

---

# 155. DO NOT CONFUSE HTTP AUTHORIZATION WITH FIREWALLS

If the API returns:

```text
403 Forbidden
```

then an HTTP component received and evaluated the request.

A firewall change is unlikely to be the appropriate first response.

Investigate application or gateway authorization.

---

# 156. LAYERED SUCCESS NARROWS THE FAILURE

Think like this:

```text
DNS succeeded.
```

Therefore DNS is less likely to explain the immediate request failure.

```text
TCP succeeded.
```

Therefore basic transport establishment succeeded.

```text
TLS succeeded.
```

Therefore certificate negotiation succeeded.

```text
HTTP 502 returned.
```

Therefore an HTTP intermediary responded and its upstream path becomes highly relevant.

Each successful layer reduces uncertainty.

---

# 157. NEGATIVE EVIDENCE IN NETWORKING

Hypothesis:

```text
Firewall blocks client traffic.
```

Observed:

```text
Client establishes TCP connection and receives HTTP 503.
```

That evidence strongly weakens the hypothesis that a firewall is completely blocking that tested connection.

Do not continue treating every hypothesis equally after evidence contradicts it.

---

# 158. AVOID RANDOM NETWORK CHANGES

Poor troubleshooting:

```text
Flush DNS.

Restart network service.

Open firewall.

Disable TLS.

Restart proxy.

Restart application.

Try again.
```

Even if the service recovers, you may not know why.

A stronger process is:

```text
Observe
↓
Localize
↓
Hypothesize
↓
Test
↓
Change the Smallest Relevant Component
↓
Verify
```

---

# 159. DO NOT OPEN `0.0.0.0/0` JUST TO TEST

Broad firewall exposure can create a serious security risk.

If a rule is suspected:

- identify source
- identify destination
- identify protocol
- identify port
- inspect existing rule
- create the narrowest authorized diagnostic change if necessary

Security controls are part of production architecture.

Do not remove them casually to simplify troubleshooting.

---

# 160. NETWORK CHANGES REQUIRE ROLLBACK

Before changing:

- DNS
- firewall rules
- routes
- proxy configuration
- load-balancer rules
- certificates

record:

```text
Current State

Proposed State

Reason

Expected Result

Validation

Rollback
```

Network changes can affect many users simultaneously.

---

# 161. DNS ROLLBACK IS NOT ALWAYS IMMEDIATE

Suppose:

```text
A → B
```

is changed and then reverted:

```text
B → A
```

Resolvers may still have cached data from either state depending on TTL and query timing.

Therefore rollback at authoritative DNS does not guarantee instantaneous global client convergence.

This should influence change planning.

---

# 162. TLS ROLLBACK MUST PRESERVE IDENTITY

When replacing certificates, ensure rollback materials remain:

- valid
- securely stored
- correctly chained
- appropriate for the hostname

Do not wait until an incident to discover that the previous certificate has expired.

---

# 163. PROXY CONFIGURATION MUST BE VALIDATED BEFORE RELOAD

For software such as Nginx, validate configuration using the installed software's supported validation mechanism before applying it.

The general workflow is:

```text
Edit
↓
Validate Syntax
↓
Review Diff
↓
Reload Safely
↓
Verify Listener
↓
Verify Upstream
↓
Verify End-to-End
```

Do not treat successful reload as proof that application traffic works.

---

# 164. ROUTING CHANGES HAVE LARGE BLAST RADIUS

Changing a route can affect:

- application traffic
- management traffic
- monitoring
- dependencies
- backup traffic
- deployment access

Do not experiment with production routing from an active remote session without understanding how the session itself depends on that route.

# 172. LAB: VERIFY EVERY HOP

Verify each boundary independently.

For example:

```text
Client → DNS
```

Then:

```text
Client → Entry Point
```

Then:

```text
Entry Point → Proxy
```

Then:

```text
Proxy → Application
```

Then:

```text
Application → Dependency
```

Record evidence.

The healthy baseline becomes the reference for later failures.

# 173. LAB: HIDDEN FAILURE SERIES

Introduce failures one at a time.

The learner should not be told which layer is broken.

Failure bank:

```text
Wrong DNS address

Missing DNS record

Blocked transport port

Application stopped

Application bound to loopback

Wrong proxy upstream port

Broken TLS hostname

Expired certificate

Unhealthy load-balancer backend

Application HTTP 500

Dependency timeout

Wrong dependency DNS record
```

After every failure:

```text
Diagnose
↓
Record Evidence
↓
Repair
↓
Verify
↓
Restore Baseline
```

Do not introduce the next failure until the previous environment is known healthy.

# 174. REQUIRED FAILURE REPORT

For every hidden failure produce:

```text
Symptom:

Observed State:

Hypotheses Rejected:

```

The objective is not merely to make the application work.

The objective is to prove why it failed.

# 175. SCENARIO: USERS REPORT TIMEOUTS

Do not immediately say:

```text
Firewall.
```

Investigate:

```text
Does DNS resolve?

What destination is returned?

What route is selected?

Can TCP establish?

Does traffic reach the destination?

Does the destination respond?

Is there a proxy timeout?

Is the application waiting on a dependency?
```

A user-visible timeout can originate at several layers.

---

# 176. SCENARIO: USERS REPORT "CONNECTION REFUSED"

Start closer to the endpoint.

Inspect:

```text
Destination Address

Destination Port

Listening Socket

Bind Address

Service State

Proxy Upstream
```

The immediate refusal itself is valuable evidence.

---

# 177. SCENARIO: BROWSER REPORTS CERTIFICATE ERROR

Do not restart the application.

Inspect:

```text
Hostname

Certificate Presented

Certificate Validity

Certificate Chain

Trust

TLS Termination Point
```

The application process may be completely healthy.

---

# 178. SCENARIO: HTTP 502 AFTER DEPLOYMENT

Build a timeline.

```text
14:00 Deployment begins

14:02 New application version starts

14:03 Proxy begins returning 502
```

Investigate:

```text
Did application port change?

Did bind address change?

Did startup fail?

Did health checks fail?

Did proxy upstream remain old?

Can proxy reach application directly?
```

Recent deployment is relevant evidence, not automatic proof.

---

# 179. SCENARIO: HTTP 504 AFTER DEPLOYMENT

A 504 often indicates an intermediary waited too long for an upstream response.

Investigate:

```text
Which intermediary generated 504?

Did application receive request?

How long did application take?

Was application waiting on database/API?

Did timeout configuration change?

Did dependency latency change?
```

Do not simply increase the timeout before understanding why the response became slow.

---

# 180. SCENARIO: SERVICE WORKS INTERNALLY BUT NOT PUBLICLY

Healthy:

```text
Application Host → Application
```

Healthy:

```text
Proxy → Application
```

Failing:

```text
External Client → Public Endpoint
```

Focus investigation on the remaining boundaries:

```text
Public DNS

Internet Routing

Public Firewall

Load Balancer Listener

TLS

External Policy
```

Do not restart the application.

---

# 181. SCENARIO: PUBLIC ENDPOINT WORKS BUT DEPENDENCY FAILS

Path A:

```text
Client
↓
Application
```

works.

Path B:

```text
Application
↓
Database
```

fails.

Treat them as different network paths.

Investigate Path B directly.

---

# 182. SCENARIO: ONLY ONE HOST FAILS

Suppose:

```text
app01 → dependency = success
app02 → dependency = failure
```

Compare:

```text
DNS

Addresses

Routes

Interfaces

Firewall

Security Group

Proxy Environment

Certificate Trust

Application Configuration
```

A shared dependency being healthy for app01 weakens the hypothesis that the dependency is globally unavailable.

---

# 183. SCENARIO: ONLY NEW CONNECTIONS FAIL

Existing persistent connections continue working.

New connections fail.

Investigate:

```text
Listener Capacity

Connection Limits

Firewall State

NAT State

Load Balancer

File Descriptors

Connection Tracking

Backend Health
```

Do not conclude:

```text
Service is healthy because some requests still work.
```

---

# 184. SCENARIO: DNS IS CORRECT BUT CLIENT REACHES OLD SYSTEM

Investigate:

```text
Local Hosts File

Application DNS Cache

Operating-System Cache

Proxy Cache

Recursive Resolver

Multiple Records

Old Persistent Connection
```

Correct authoritative DNS is only one part of the path.

---

# 185. SCENARIO: CORRECT IP BUT WRONG APPLICATION

Possible causes include:

```text
Wrong Host Header

Virtual Host Configuration

Proxy Routing Rule

SNI / TLS Routing

Shared Load Balancer

Incorrect Path Rule
```

An IP address can host multiple applications.

Do not assume:

```text
Correct IP = Correct Application.
```

# 186. PRODUCTION NETWORK TROUBLESHOOTING COMMAND SET

A Mid-Level engineer should understand the purpose of tools such as:

```text
ip link
ip address
ip route
ip neigh
ss
dig
curl
openssl
nc
tracepath / traceroute
tcpdump
```

The objective is not command memorization.

For every tool know:

```text
Which question does it answer?

At which layer?

What does success prove?

What does failure prove?

What does it not prove?
```

---

# 187. COMMAND: `ip address`

Question:

```text
Which addresses are configured on this host?
```

Does not prove:

```text
Remote reachability.
```

---

# 188. COMMAND: `ip route`

Question:

```text
Which routes exist?
```

Does not prove:

```text
Every next hop works.
```

---

# 189. COMMAND: `ip route get`

Question:

```text
How would Linux attempt to route this destination?
```

Does not prove:

```text
The destination is reachable.
```

---

# 190. COMMAND: `ip neigh`

Question:

```text
What neighbor information does the host currently know?
```

Does not prove:

```text
End-to-end application connectivity.
```

---

# 191. COMMAND: `ss`

Question:

```text
Which sockets exist and what state are they in?
```

Does not prove:

```text
Application logic is healthy.
```

---

# 192. COMMAND: `dig`

Question:

```text
What DNS answer does this query produce?
```

Does not prove:

```text
The returned endpoint is healthy.
```

---

# 193. COMMAND: `curl`

Question:

```text
Can an HTTP/HTTPS request progress through the tested path, and what response is observed?
```

Does not automatically prove:

```text
Every backend dependency is healthy.
```

---

# 194. COMMAND: `openssl s_client`

Question:

```text
What happens during a TLS connection and what certificate information is presented?
```

Does not by itself prove:

```text
The application endpoint behaves correctly.
```

---

# 195. COMMAND: `nc`

Question:

```text
Can the tested transport connection be established?
```

Does not prove:

```text
The application protocol is functioning.
```

---

# 196. COMMAND: `tcpdump`

Question:

```text
What packets are visible at this observation point?
```

Does not automatically tell you:

```text
Why another network component behaved as it did.
```

# 197. THE EVIDENCE LADDER

Use this reasoning model:

```text
DNS Answer
↓
Route Selected
↓
Packets Leave Source
↓
Packets Reach Destination
↓
Transport Established
↓
TLS Established
↓
HTTP Request Received
↓
Proxy Routes Request
↓
Application Processes Request
↓
Dependency Responds
↓
Response Returns to Client
```

Each confirmed step narrows the remaining failure domain.

---

# 198. DO NOT OVERCLAIM

Suppose:

```bash
nc -vz app.example.com 443
```

succeeds.

Correct conclusion:

```text
A TCP connection to the tested destination and port could be established from this source at this time.
```

Incorrect conclusion:

```text
The application is healthy.
```

Precision matters.

# 199. NETWORK TROUBLESHOOTING IS TIME-SENSITIVE

Networks change.

DNS caches expire.

Connections close.

Load balancers move traffic.

Backends restart.

Routes change.

Therefore always record:

```text
Timestamp

Source

Destination

Result
```

Evidence without time context can become misleading.

# 200. NETWORK BASELINES

Useful baseline knowledge includes:

- normal DNS answers
- normal request latency
- expected ports
- expected routes
- normal backend count
- expected certificate identity
- normal proxy response time
- dependency latency
- connection volume

Without baseline:

```text
50 ms latency
```

may be difficult to interpret.

With baseline:

```text
Normal = 8–12 ms

Current = 250–400 ms
```

the observation becomes meaningful.

---

# 201. PERFORMANCE AND CONNECTIVITY ARE DIFFERENT

A connection can succeed and still perform poorly.

Therefore:

```text
Connected
```

does not mean:

```text
Healthy.
```

Investigate:

- latency
- packet loss
- retransmissions
- proxy wait
- backend processing
- dependency latency
- connection reuse

when performance is the symptom.

# 202. NETWORKING AND LINUX INTERNALS CONNECT

Part 2 and Part 3 should now connect.

Example:

```text

↓

↓
```

The symptom appears network-related.

# 203. NETWORKING AND OBSERVABILITY CONNECT

A mature investigation may combine:

```text
Load Balancer Metrics

Proxy Logs

Application Logs

Connection Metrics

DNS Evidence

Request Traces

Host Metrics
```

This allows you to move from:

```text
Requests are slow.
```

to:

```text
Client-to-proxy connection time remains normal.

Proxy-to-application connection time remains normal.

Application processing time increases only when the database call
exceeds its normal latency.

The database dependency is therefore the strongest current failure domain.
```

That is evidence-based troubleshooting.

# 204. NETWORKING AND SECURITY CONNECT

Security controls frequently determine reachability.

Examples include:

- host firewall
- cloud security group
- network ACL
- proxy authorization
- TLS certificate trust
- service identity
- application authorization

Do not weaken security controls merely to make traffic flow.

The engineering requirement is:

```text
Required Traffic
+
Authorized Source
+
Authorized Destination
+
Required Protocol
+
Required Port
+
Minimum Necessary Exposure
```

---

# 205. NETWORKING AND CHANGE MANAGEMENT CONNECT

A networking change should include:

```text
Current State

Desired State

Affected Path

Blast Radius

Validation

Rollback

Monitoring
```

Example:

```text
Change:
Reverse proxy upstream port from 8080 to 9000.

Reason:
Application release changes listener to 9000.

Dependencies:
Application must already be healthy on 9000.

Verification:
Proxy can reach application.
Health endpoint returns expected result.
User-facing request succeeds.

Rollback:
Restore upstream to 8080 if previous application version is restored.
```

This is service ownership.

# 217. MID-LEVEL NETWORKING BOUNDARY

At this stage, you are not expected to be a specialist network architect.

You are not yet expected to independently design:

- global backbone networks
- complex BGP policy
- large-scale SD-WAN
- carrier-grade routing
- advanced network overlays
- complex multi-region transit architecture
- enterprise-wide IP address management strategy

You are expected to understand the network path of the production services you operate.

You must be able to determine whether a failure belongs to:

```text
Name Resolution

Addressing

Routing

Neighbor Reachability

Network Policy

Transport

TLS

HTTP

Proxy

Load Balancer

Application

Dependency
```

and produce useful evidence.

# 218. COMPLETION STANDARD

You have completed this Part when you can trace a request through a production-style network path and identify where communication stops behaving as expected.

You should be able to move from:

```text
The network is down.
```

to:

```text
From which source?

To which destination?

Using which protocol?

On which port?

What path should the traffic take?

Which boundary fails?
```

You should be able to move from:

```text
The host is unreachable.
```

to:

```text
Does DNS resolve?

Which address is returned?

Which route is selected?

Can the next hop be resolved?

Does the transport connection establish?

Does traffic reach the destination?

Does the destination respond?
```

You should be able to move from:

```text
The website is broken.
```

to:

```text
DNS resolves correctly.

TCP/443 establishes.

TLS validates.

The reverse proxy returns HTTP 502.

Proxy logs show connection refused to the configured upstream.

The application is listening on a different port.

The failure is therefore between the reverse proxy configuration
and the application listener.
```

You should be able to distinguish:

```text
DNS Failure
```

from:

```text
Routing Failure
```

from:

```text
Timeout
```

from:

```text
Connection Refused
```

from:

```text
Connection Reset
```

from:

```text
TLS Failure
```

from:

```text
HTTP Error
```

from:

```text
Application Failure
```

from:

```text
Dependency Failure.
```

The engineering habit from this Part is:

```text
What is the source?
        ↓
What is the destination?
        ↓
Which name should resolve?
        ↓
Which address should be returned?
        ↓
Which route should be selected?
        ↓
Which network boundaries must permit the traffic?
        ↓
Which process should be listening?
        ↓
Can the transport connection be established?
        ↓
Does TLS establish and validate?
        ↓
What HTTP response is returned?
        ↓
Which proxy or load balancer handled the request?
        ↓
Did the application receive it?
        ↓
Did the application reach its dependencies?
        ↓
Where does expected behavior first differ from observed behavior?
        ↓
What evidence proves that?
        ↓
What is the smallest justified correction?
        ↓
How will end-to-end recovery be verified?
```

At Mid-Level, networking should no longer appear as a collection of IP addresses, ports, and commands.

It should appear as a sequence of communication boundaries that can be mapped, observed, tested, and verified.

When a request fails, the objective is not to say:

```text
There is a network problem.
```

The objective is to identify the exact boundary where the request stops progressing correctly, explain why it stops there, support that conclusion with evidence, make the smallest justified correction, and verify the complete traffic path afterward.

That is production network troubleshooting.
