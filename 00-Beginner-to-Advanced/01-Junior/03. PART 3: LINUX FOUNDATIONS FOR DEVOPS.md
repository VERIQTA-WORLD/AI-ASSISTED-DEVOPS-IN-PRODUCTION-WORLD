# PART 3: LINUX FOUNDATIONS FOR DEVOPS

## Goal

Understand the Linux environment where a large amount of production infrastructure and application workloads operate.

Linux appears throughout modern DevOps environments.

You will encounter it in:

- virtual machines
- cloud instances
- container hosts
- Kubernetes nodes
- CI/CD runners
- build servers
- web servers
- application servers
- database servers
- monitoring systems
- logging systems
- networking appliances
- security tooling
- automation environments

The objective of this Part is not to memorize Linux commands.

It is to build the mental model required to answer questions such as:

```text
Where am I?

Which user am I?

What permissions do I have?

Who owns this file?

Which process is running?

Who started that process?

Which service owns it?

Where is its configuration?

Where are its logs?

Why did access fail?

Why is the service stopped?

Which package installed this file?

What evidence should I inspect before changing anything?
```

By the end of this Part, Linux should begin to look less like a collection of commands and more like a system whose state can be inspected and reasoned about.

The working method throughout the Part is:

```text
Observe
   ↓
Identify Context
   ↓
Inspect State
   ↓
Collect Evidence
   ↓
Form Hypothesis
   ↓
Test Safely
   ↓
Correct
   ↓
Verify
```

# 1. LINUX IS MORE THAN A TERMINAL

A common beginner mental model is:

```text
Linux
=
Terminal Commands
```

That is incomplete.

The terminal is merely one interface through which you interact with the system.

A more useful starting model is:

```text
┌──────────────────────────────────────┐
│             APPLICATIONS             │
├──────────────────────────────────────┤
│              SERVICES                │
├──────────────────────────────────────┤
│         USERS / PERMISSIONS          │
├──────────────────────────────────────┤
│             FILESYSTEM               │
├──────────────────────────────────────┤
│             PROCESSES                │
├──────────────────────────────────────┤
│               KERNEL                 │
├──────────────────────────────────────┤
│              HARDWARE                │
└──────────────────────────────────────┘
```

This is a teaching model, not a strict architectural layering diagram.

The real relationships are more interconnected.

Applications are processes.

Services normally involve processes.

Processes access files.

Permissions influence what processes can access.

Processes request kernel operations.

The kernel manages hardware resources.

A better operational view is therefore:

```text
                     USERS
                       │
                       ▼
                 APPLICATIONS
                       │
                       ▼
                    PROCESSES
                   /    |    \
                  /     |     \
                 ▼      ▼      ▼
             FILES   NETWORK  DEVICES
                 \      |      /
                  \     |     /
                   ▼    ▼    ▼
                      KERNEL
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
         CPU          MEMORY        STORAGE
```

Linux engineering requires understanding these relationships.

---

# 2. THE KERNEL

The kernel is the core of the operating system.

Applications do not normally manipulate hardware directly.

Instead:

```text
Application
     ↓
System Call / Kernel Interface
     ↓
Linux Kernel
     ↓
Hardware / Kernel-Managed Resource
```

The kernel is responsible for major functions including:

- process scheduling
- memory management
- device interaction
- filesystems
- networking
- security enforcement
- resource management

You do not need kernel-development knowledge to operate Linux effectively.

But you must understand that the kernel is underneath almost everything you observe.

---

# 2.1 Inspect the Kernel

Run:

```bash
uname -r
```

This reports the running kernel release.

Try:

```bash
uname -a
```

This provides broader system information.

Do not confuse:

```text
Linux Distribution Version
```

with:

```text
Linux Kernel Version
```

They are related but different.

For example, a Linux distribution contains far more than the kernel:

```text
Linux Distribution
├── Linux Kernel
├── Libraries
├── Shell
├── Package Manager
├── System Utilities
├── Service Manager
├── Configuration
└── Distribution-Specific Packages
```

---

# 3. USER SPACE AND KERNEL SPACE

At a high level, Linux separates kernel execution from ordinary user-space programs.

Applications such as:

```text
nginx
ssh
bash
curl
python
git
```

normally operate in user space.

They interact with the kernel when they need operations such as:

- opening files
- allocating memory
- creating processes
- creating network sockets
- reading from devices

Conceptually:

```text
User Space

Application
    │
    │ system calls
    ▼
────────────────────
Kernel Space

Linux Kernel
    │
    ▼
Hardware / Resources
```

This distinction becomes much more important later when troubleshooting:

- memory pressure
- CPU saturation
- blocked processes
- filesystem problems
- networking failures
- containers

For now, remember:

> Applications request resources. The kernel manages them.

---

# 4. PROCESSES

When a program executes, it normally runs as one or more processes.

Consider:

```bash
sleep 300
```

`sleep` is a program.

When executed, the operating system creates a process running that program.

Conceptually:

```text
Executable
    ↓
Process Created
    ↓
PID Assigned
    ↓
Kernel Schedules Process
    ↓
Process Runs
    ↓
Process Exits
```

A process is therefore a running execution context, not simply a file on disk.

---

# 5. THE FILESYSTEM

Linux exposes files through a hierarchical filesystem.

The hierarchy begins at:

```text
/
```

called the root directory.

Do not confuse:

```text
/
```

with:

```text
/root
```

They are different.

`/` is the filesystem root.

`/root` is commonly the home directory of the root user.

---

# 5.1 Basic Filesystem Model

A simplified Linux filesystem may look like:

```text
/
├── etc
├── home
│   ├── learner
│   └── developer
├── opt
├── proc
├── root
├── run
├── sys
├── tmp
├── usr
│   ├── bin
│   ├── lib
│   └── local
└── var
    ├── log
    └── lib
```

Exact contents differ between distributions and systems.

Do not memorize the tree as if every Linux machine is identical.

Learn what major locations generally represent.

---

# 6. `/`

The root directory:

```text
/
```

is the top of the filesystem hierarchy.

Everything accessible through the normal filesystem namespace exists beneath it.

Try:

```bash
ls /
```

You may see directories such as:

```text
bin
boot
dev
etc
home
lib
opt
proc
root
run
sys
tmp
usr
var
```

The exact result varies.

# 7. `/etc`

`/etc` contains system-wide configuration and related administrative files.

Examples may include:

```text
/etc/hosts
/etc/passwd
/etc/group
/etc/ssh/
/etc/systemd/
```

depending on the system.

A useful mental model is:

```text
/etc
   ↓
System Configuration
```

But avoid assuming every application's configuration must live there.

Applications can use other locations.

---

# 7.1 Configuration Versus Runtime State

This distinction matters:

```text
Configuration
```

describes how something should operate.

```text
Runtime State
```

describes what is happening now.

For example, changing a configuration file does not automatically prove a running service has loaded the change.

Later you will repeatedly use:

```text
Configuration
     ↓
Apply / Reload / Restart
     ↓
Runtime State
     ↓
Verification
```

---

# 8. `/var`

`/var` contains variable data that changes during normal system operation.

Common examples include:

```text
/var/log
/var/lib
/var/cache
```

depending on the distribution and installed software.

A useful mental model:

```text
/var
   ↓
Changing Operational Data
```

Examples may include:

- logs
- application state
- package metadata
- caches
- spool data

---

# 9. `/var/log`

Historically and commonly, many system and application logs can be found beneath:

```text
/var/log
```

Try:

```bash
ls -l /var/log
```

However, do not develop the assumption:

```text
All Linux logs are files in /var/log.
```

On systems using `systemd`, the journal may contain important logging information accessed through `journalctl`.

Some applications also:

- log elsewhere
- send logs to remote systems
- write to standard output
- use logging agents

The broader lesson is:

```text
Need Logs
   ↓
Identify Logging Mechanism
   ↓
Locate Evidence
```

---

# 10. `/home`

Regular users commonly have home directories beneath:

```text
/home
```

Example:

```text
/home/learner
```

A user's home directory may contain:

- personal files
- shell configuration
- SSH configuration
- application configuration
- development projects

Inspect:

```bash
echo "$HOME"
```

and:

```bash
pwd
```

Do not assume the current directory is automatically your home directory.

---

# 11. `/tmp`

`/tmp` is commonly used for temporary files.

Applications and users may create temporary data there.

Important principle:

```text
Temporary
≠
Permanent Storage
```

Do not design important persistent application state around `/tmp` without understanding the operating environment and cleanup behavior.

Permissions on `/tmp` also introduce an important concept.

Try:

```bash
ls -ld /tmp
```

You may notice permissions that look different from ordinary directories.

We will return to directory permissions later.

---

# 12. `/usr`

`/usr` contains a large portion of user-space programs, libraries, and shared data.

Common locations include:

```text
/usr/bin
/usr/sbin
/usr/lib
/usr/share
/usr/local
```

You will often discover commands beneath locations such as:

```text
/usr/bin
```

Try:

```bash
command -v ls
command -v grep
command -v ssh
```

The results depend on the system.

---

# 13. `/usr/local`

`/usr/local` is commonly used for locally installed software outside the distribution's normal packaged files.

You may encounter:

```text
/usr/local/bin
/usr/local/lib
```

This becomes relevant when software is installed manually.

For example:

```text
/usr/bin/tool
```

may come from the operating system package manager, while:

```text
/usr/local/bin/tool
```

may have been installed separately.

That distinction can matter during version troubleshooting.

---

# 14. `/opt`

`/opt` is commonly used for additional or optional application software.

You may encounter software installed under structures such as:

```text
/opt/application/
```

Do not assume every third-party program uses `/opt`.

The actual location depends on how software was packaged and installed.

---

# 15. `/proc`

`/proc` is fundamentally different from an ordinary directory full of persistent files.

It is a virtual filesystem exposing kernel and process information.

Try:

```bash
ls /proc | head
```

You will see entries including numbers.

Many numeric directories correspond to process IDs.

For example:

```text
/proc/1234
```

may expose information about process PID 1234.

Conceptually:

```text
Running Process
      ↓
Kernel Maintains State
      ↓
/proc/<PID>
      ↓
Inspectable Process Information
```

---

# 15.1 `/proc` Is Runtime Information

Do not think:

```text
/proc contains ordinary files permanently stored on disk.
```

Instead think:

```text
/proc
   ↓
Kernel-Exposed Runtime View
```

This becomes extremely useful in troubleshooting.

---

# 15.2 Inspect Process Information

Find your current shell PID:

```bash
echo $$
```

Suppose the result is:

```text
1234
```

Then inspect:

```bash
ls /proc/1234
```

or directly:

```bash
ls "/proc/$$"
```

You may see entries such as:

```text
cmdline
cwd
environ
fd
status
```

depending on permissions and kernel behavior.

Try:

```bash
cat "/proc/$$/status"
```

You are now inspecting runtime information exposed by the kernel.

---

# 15.3 `/proc/cpuinfo`

Try:

```bash
cat /proc/cpuinfo
```

This can expose CPU information.

Do not memorize the entire output.

Learn that Linux exposes a great deal of system state through kernel interfaces.

---

# 15.4 `/proc/meminfo`

Try:

```bash
cat /proc/meminfo
```

This exposes memory-related information.

Later, tools such as:

```bash
free
```

will present portions of system memory information in a more convenient form.

This establishes an important pattern:

```text
Kernel State
   ↓
Kernel Interface
   ↓
System Utility
   ↓
Human-Friendly Output
```

---

# 16. `/sys`

`/sys` is another virtual filesystem.

It exposes information about kernel objects, devices, drivers, and related system relationships.

Try:

```bash
ls /sys
```

You may see:

```text
block
bus
class
devices
fs
kernel
module
```

depending on the system.

A simplified distinction is:

```text
/proc
→ process and kernel runtime information

/sys
→ kernel object, device, driver, and subsystem information
```

The boundaries are more nuanced than this simplified model, but it is enough for the foundation stage.

---

# 17. `/proc` AND `/sys` ARE NOT ORDINARY CONFIGURATION DIRECTORIES

This distinction matters.

Compare:

```text
/etc
```

with:

```text
/proc
/sys
```

A useful beginner model:

```text
/etc
→ persistent configuration and administrative files

/proc
→ runtime process/kernel information

/sys
→ runtime kernel/device/subsystem information
```

Do not casually edit entries in `/proc` or `/sys`.

Some entries can influence live kernel behavior.

At this stage, use them primarily for inspection.

# 24. CREATING DIRECTORIES

Use:

```bash
mkdir lab
```

Nested directories:

```bash
mkdir -p lab/config/nginx
```

Verify:

```bash
find lab -maxdepth 3 -type d
```

The `-p` option allows creation of required parent directories and avoids an error if the target directory already exists.

Do not memorize flags without checking:

```bash
mkdir --help
```

or:

```bash
man mkdir
```

where available.

# 25. CREATING FILES

A simple empty file:

```bash
touch example.txt
```

Verify:

```bash
ls -l example.txt
```

But understand what `touch` actually does.

Its primary purpose is updating file timestamps.

If the named file does not exist, it can create an empty file.

This distinction matters because:

```text
Common Usage
≠
Complete Meaning
```

---

# 26. WRITING TO FILES

Create content:

```bash
printf '%s\n' 'VERIQTA Linux Lab' > example.txt
```

Inspect:

```bash
cat example.txt
```

Expected:

```text
VERIQTA Linux Lab
```

Append:

```bash
printf '%s\n' 'Second line' >> example.txt
```

Inspect:

```bash
cat example.txt
```

Expected:

```text
VERIQTA Linux Lab
Second line
```

The difference is important:

```text
>
→ redirect and overwrite target content

>>
→ redirect and append
```

Careless use of `>` can destroy existing file content.

# 29. MOVING AND RENAMING

Move:

```bash
mv old-location new-location
```

Rename:

```bash
mv old-name.txt new-name.txt
```

# 30. DELETING FILES

Delete a file:

```bash
rm example.txt
```

Remove an empty directory:

```bash
rmdir empty-directory
```

Recursive deletion:

```bash
rm -r directory
```

Forceful recursive deletion exists:

```bash
rm -rf directory
```

but should never become a casual reflex.

Before destructive deletion, verify:

```bash
pwd
ls -ld target
```

Ask:

```text
What exactly is the target?

Is the path correct?

Could shell expansion change the target?

Is the data recoverable?

Am I on the correct host?
```

Suppose you need to locate:

```text
app.conf
```


Example:

```text

```

# 34. USERS

```bash

```

More detailed identity information:

```bash
id
```

Example:

```text

```

```text

→ User Identifier

```

# 35. `/etc/passwd`

Inspect:

```bash
head /etc/passwd
```

A line resembles:

```text
name:x:UID:GID:comment:home:shell
```

For example:

```text

```

Fields represent information including:

```text

Primary GID
Comment / account information

```

Do not expect password hashes to be stored directly in `/etc/passwd` on modern Linux systems.

```text

```

# 36. ROOT USER

The root user traditionally has UID:

```text

```

```bash

```

Root has extensive privileges.

That does not mean normal work should be performed as root.

A safer operating principle is:

```text
Use the Least Privilege Required
```

not:

```text
Use Root Because It Avoids Permission Problems
```

# 42. LINUX PERMISSION MODEL

A basic Unix permission model contains permissions for:

```text
User / Owner
Group
Other
```

and permissions:

```text
Read
Write
Execute
```

Displayed as:

```text
r
w
x
```

Example:

```text
-rwxr-x---
```

Break it down:

```text
-    rwx    r-x    ---
│     │      │      │
│     │      │      └── Other
│     │      └───────── Group
│     └──────────────── Owner
└────────────────────── File Type
```

---

# 43. FILE PERMISSIONS

For a regular file:

```text
r
→ read file contents

w
→ modify file contents

x
→ execute file as a program/script when other requirements are satisfied
```

These meanings differ somewhat for directories.

That distinction is important.

---

# 44. DIRECTORY PERMISSIONS

For a directory:

```text
r
→ read directory entries

w
→ create/remove/rename entries, subject to other rules

x
→ traverse/search the directory
```

Directory execute permission is frequently misunderstood.

A user may know a filename exists but still be unable to access it because a parent directory cannot be traversed.

This is a common source of:

```text
Permission denied
```

---

# 45. NUMERIC PERMISSIONS

Permissions are often represented numerically:

```text
r = 4
w = 2
x = 1
```

Therefore:

```text
7 = rwx
6 = rw-
5 = r-x
4 = r--
0 = ---
```

Example:

```bash
chmod 640 app.conf
```

means:

```text
Owner: rw-
Group: r--
Other: ---
```

Do not memorize `chmod 777` as a universal permission fix.

It is usually evidence that the permission model has not been understood.

---

# 46. SYMBOLIC PERMISSIONS

Permissions can also be modified symbolically.

Example:

```bash
chmod u+x script.sh
```

Meaning:

```text
u
→ user/owner

+x
→ add execute
```

Another example:

```bash
chmod g-w file.txt
```

removes group write permission.

Inspect before and after:

```bash
ls -l file.txt
```

---

# 47. LEAST PRIVILEGE

Least privilege means giving an identity only the permissions necessary to perform its required task.

Bad model:

```text
Permission Problem
      ↓
Give Everyone Everything
```

Better model:

```text
Permission Problem
      ↓
Which Identity?
      ↓
Which Resource?
      ↓
Which Operation?
      ↓
Which Permission Is Required?
      ↓
Grant Minimum Necessary Access
```

This principle will later apply to:

- Linux
- cloud IAM
- Kubernetes RBAC
- CI/CD
- databases
- secrets
- AI agents

---

# 48. `sudo`

`sudo` allows authorized users to execute commands with another user's privileges, commonly root.

Example:

```bash
sudo systemctl restart example.service
```

The important question is not:

```text
Can sudo make this command work?
```

It is:

```text
Should this operation require elevated privileges?
```

Never develop:

```text
Command Failed
↓
Add sudo
```

as a troubleshooting method.

---

# 49. WHY BLIND `sudo` IS DANGEROUS

Suppose:

```bash
cat application.log
```

returns:

```text
Permission denied
```

Running:

```bash
sudo cat application.log
```

may display the file.

But you have not necessarily diagnosed the problem.

Questions remain:

```text
Who should own the file?

Which group should read it?

Why does my user lack access?

Is access intentionally restricted?

Should I have access at all?
```

Privilege escalation can bypass a symptom without resolving the underlying permission design.


```bash

```

using the PID returned by your system.

# 54. PARENT AND CHILD PROCESSES

Processes have relationships.

A process may create another process.

Conceptually:

```text
Shell
PID 1000
   │
   └── sleep
       PID 2000
```

The shell is the parent.

`sleep` is the child.

Inspect:

```bash
ps -o pid,ppid,stat,cmd -p <PID>
```

Example structure:

```text
PID   PPID   STAT   CMD
2000  1000   S      sleep 300
```

`PPID` means:

```text
Parent Process ID
```

# 55. PROCESS TREE

Where available:

```bash
pstree
```

can display process relationships.

If `pstree` is unavailable, do not immediately assume something is wrong.

```bash

```

```text
Command Not Found
≠
Broken Operating System
```

# 56. PROCESS STATES

Processes can exist in different states.

You may encounter state indicators representing conditions such as:

- running/runnable
- sleeping
- uninterruptible sleep
- stopped
- zombie

Exact state notation is tool-dependent.

A beginner should understand one critical point:

```text
Process Exists
≠
Process Is Doing Useful Work
```

A process can exist while:

- waiting
- blocked
- stopped
- stuck
- consuming excessive CPU
- waiting for I/O
- waiting for another dependency

Later Parts will explore this deeply.

# 57. FOREGROUND AND BACKGROUND

Foreground:

```text
Shell
  ↓
Foreground Process
  ↓
Terminal Interaction
```

Background:

```text
Shell
  ├── accepts commands
  │
  └── background process continues
```

Shell job control is useful for interactive work.

It is not the same thing as running a production service through a service manager.

Do not confuse:

```text
command &
```

with:

```text
proper service management
```

# 58. SIGNALS

Signals allow processes to receive notifications or requests.

List signal names:

```bash
kill -l
```

Two signals you will encounter frequently are:

```text
SIGTERM
SIGKILL
```

---

# 59. SIGTERM

A normal termination request is commonly sent with:

```bash
kill <PID>
```

By default, `kill` commonly sends `SIGTERM`.

Conceptually:

```text
Operator
   ↓
SIGTERM
   ↓
Process
   ↓
Opportunity for Graceful Shutdown
```

A well-designed application may use this opportunity to:

- stop accepting new work
- finish active operations
- flush buffers
- close files
- close network connections
- clean up resources
- exit

---

# 60. SIGKILL

A forceful termination can be requested with:

```bash
kill -9 <PID>
```

This sends `SIGKILL`.

Conceptually:

```text
Kernel
↓
Terminate Process
```

The process cannot catch or ignore `SIGKILL`.

That makes it powerful.

It also means the process does not get its normal application-level cleanup opportunity.

Do not make:

```bash
kill -9
```

your default process termination method.

Use escalation intentionally.

---

# 61. SAFE PROCESS TERMINATION

A better pattern:

```text
Identify Process
      ↓
Confirm Ownership / Purpose
      ↓
Understand Impact
      ↓
Request Graceful Termination
      ↓
Observe
      ↓
Escalate Only If Necessary
      ↓
Verify
```

Before killing something in production, know what it is.

Never assume:

```text
High CPU
↓
Kill Process
```

is a diagnosis.

High CPU is evidence.

It is not automatically the root cause.

# 64. WHAT IS A SERVICE?

A service is a long-running capability managed as part of system operation.

Examples may include:

- SSH server
- web server
- database
- monitoring agent
- application daemon

A service often involves one or more processes.

But:

```text
Service
≠
Process
```

A service manager may define:

- how a service starts
- which command runs
- dependencies
- environment
- restart behavior
- user identity
- startup ordering

The running implementation may involve multiple processes.

# 65. SYSTEMD

Many modern Linux distributions use `systemd` as the system and service manager.

Not every Linux environment uses systemd.

Examples where assumptions may differ include:

- some containers
- embedded environments
- distributions using other init systems

Therefore:

```text
Linux
≠
Automatically systemd everywhere
```

On a systemd-based lab, the primary command-line management tool is:

```bash
systemctl
```

# 66. SYSTEMD UNITS

systemd manages objects represented by units.

A service unit commonly ends with:

```text
.service
```

Examples:

```text
ssh.service
nginx.service
```

Actual names vary by distribution and package.

There are also other unit types.

For this Part, focus primarily on service units.

---

# 67. CHECK SERVICE STATE

Example:

```bash
systemctl status ssh
```

On some distributions the service may instead be named differently, such as `sshd`.

Do not memorize a service name without checking the target system.

Useful discovery:

```bash
systemctl list-units --type=service
```

or:

```bash
systemctl list-unit-files --type=service
```

These answer different questions.

One concerns loaded unit runtime state.

The other concerns installed unit files and enablement information.

---

# 68. ACTIVE VERSUS ENABLED

This distinction is fundamental.

```text
Active
```

generally concerns whether the unit is currently running/active.

```text
Enabled
```

generally concerns whether it is configured to participate in startup through the relevant systemd target relationships.

Therefore:

```text
Active
≠
Enabled
```

A service can be active now without being enabled for future startup.

A service can be enabled but currently stopped.

Inspect:

```bash
systemctl is-active <service>
```

and:

```bash
systemctl is-enabled <service>
```

---

# 69. STARTING AND STOPPING SERVICES

Start:

```bash
sudo systemctl start <service>
```

Stop:

```bash
sudo systemctl stop <service>
```

Restart:

```bash
sudo systemctl restart <service>
```

Reload where the service supports it:

```bash
sudo systemctl reload <service>
```

Do not assume restart and reload mean the same thing.

Conceptually:

```text
restart
→ stop/start service processes

reload
→ request supported configuration reload without a full restart
```

Exact behavior depends on the unit and application.

---

# 70. ENABLE AND DISABLE

Enable:

```bash
sudo systemctl enable <service>
```

Disable:

```bash
sudo systemctl disable <service>
```

Again:

```text
enable
≠
start
```

Although some commands can combine operations with additional options, keep the concepts separate.

# 79. PACKAGE INSTALLATION VERSUS RUNNING SERVICE

- configured correctly

Each arrow requires evidence.

- file write permission
- file execute permission
- directory traversal permission
- ownership
- group membership
- ACLs
- security mechanisms
- filesystem restrictions
- privileged operation

```text
      ↓

      ↓

      ↓

      ↓
Permission bits?
      ↓
```

# 115. SYMBOLIC LINKS

# 117. HARD LINKS VERSUS SYMBOLIC LINKS

A symbolic link points by pathname.

A hard link is another directory entry referring to the same underlying inode where supported.

Conceptually:

```text
Hard Link:

name-a ─┐
        ├── inode ── data
name-b ─┘
```

Versus:

```text
Symbolic Link:

link
 ↓
"path/to/target"
 ↓
target inode
```

You do not need advanced link administration yet.

You should know they are not the same.

# 120. PIPES

A pipe:

```text
|
```

connects the output of one command to the input of another.

Example:

```bash

```

Conceptually:

```text
ps
↓ stdout
|
↓ stdin
grep
```

This allows small commands to be combined.

The Unix philosophy often favors tools that perform focused operations and can be composed.

```text
↓

command-c
↓
What final evidence appears?
```

This makes debugging easier.

## Step 2: Identify Service

```text

manual process?

```

For this scenario, assume systemd.

## Step 3: Check Service State

```bash

```

Read the output.

## Step 4: Inspect Logs


```bash

```

```text
User=appuser
```

```bash

```

## Step 9: Form Hypothesis

Example:

```text
The service runs as appuser.

The start script exists.

The script is owned by root.

Therefore appuser cannot execute it.
```

Now you have a testable hypothesis.

```bash

```

If the application has a health endpoint, that would provide additional evidence at a higher layer.

# 135. JUNIOR ENGINEER OPERATING BOUNDARY

At Junior level, you are not expected to understand every kernel subsystem.


# 136. WHEN TO ESCALATE

Escalate when:

- required access exceeds your authorization
- production impact is unclear
- the corrective action has significant blast radius
- the failure involves data integrity
- you cannot establish intended permissions
- root cause remains uncertain
- changes could affect other services
- kernel-level behavior requires deeper expertise
- security controls appear involved
- you suspect compromise
- runbook requires escalation

Escalation should include evidence.

This mindset is far stronger than command memorization.

# 141. FINAL PRACTICAL ASSESSMENT

You receive this report:

> The website is down. The Linux server must be broken.

You log into the server.

Your job is not to agree with the conclusion.

Your job is to gather evidence.

At minimum determine:

```text
Which host am I on?

Which user am I?

How long has the system been running?

Is the application service active?

Does its process exist?

What does systemd report?

What do the relevant logs report?

Does the expected executable exist?

Does the expected configuration exist?

Which user owns the process?

Can that identity access required files?

Are obvious system resources exhausted?

What evidence actually supports the statement that Linux itself is broken?
```

The final question is deliberately important.

An application failure does not automatically mean an operating-system failure.
