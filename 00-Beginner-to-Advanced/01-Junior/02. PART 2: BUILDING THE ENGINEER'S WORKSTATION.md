# PART 2: BUILDING THE ENGINEER'S WORKSTATION

## Goal

The goal of this section is to build and understand the local environment from which DevOps engineering work will be performed.

A workstation is not simply a laptop with several tools installed.

It is the engineer's control point.

From this environment, an engineer may eventually:

- read and modify source code
- connect to remote Linux systems
- interact with APIs
- inspect JSON responses
- build containers
- execute infrastructure code
- interact with cloud platforms
- communicate with Kubernetes clusters
- authenticate to engineering systems
- investigate production problems
- run automation
- use AI-assisted engineering tools

That makes workstation configuration part of engineering.

By the end of this section, you should be able to answer:

```text
What operating system am I using?

What shell am I running?

Where is my home directory?

What is my current working directory?

Where does this command come from?

Which executable will my shell run?

Why can my shell find it?

What version is installed?

How was it installed?

Which configuration files affect it?

Which credentials can it access?

Am I executing this command locally or remotely?

What architecture was this binary built for?

How do I verify an installation instead of assuming it worked?
```

The central engineering pattern for this Part is:

```text
Identify Environment
        ↓
Understand Requirement
        ↓
Choose Supported Installation Method
        ↓
Install
        ↓
Discover Binary
        ↓
Inspect Version
        ↓
Test Basic Operation
        ↓
Inspect Configuration
        ↓
Record Result
```

Do not build a workstation by copying a large block of installation commands from an old tutorial and hoping everything succeeds.

Understand what you are installing.

Understand where it is going.

Verify every important step.

A junior engineer may initially think of a workstation as:

```text
Laptop
+
Terminal
+
Some DevOps Tools
```

That model is too shallow.

A better model is:

```text
┌───────────────────────────────────────────────┐
│               ENGINEER                       │
├───────────────────────────────────────────────┤
│               TERMINAL                        │
├───────────────────────────────────────────────┤
│                 SHELL                         │
├───────────────────────────────────────────────┤
│          ENVIRONMENT VARIABLES                │
├───────────────────────────────────────────────┤
│        COMMAND DISCOVERY / PATH               │
├───────────────────────────────────────────────┤
│                                               │
│  Git   SSH   curl   jq   Docker   Terraform  │
│                                               │
│       Cloud CLI        kubectl                 │
│                                               │

│          OPERATING SYSTEM                     │

│              FILESYSTEM                       │

```

There are also relationships to external systems:

```text
Workstation
   │
```

Later, your workstation may hold credentials capable of interacting with these systems.

That means workstation hygiene matters.

# 2. KNOW YOUR OPERATING SYSTEM FIRST

Before installing anything, identify the operating system you are actually using.

Installation instructions differ between:

- Linux
- macOS
- Windows

They can also differ within those categories.

For example, Linux distributions may use different package managers.

Windows users may work directly in PowerShell, Git Bash, Windows Terminal, or Windows Subsystem for Linux.

macOS systems may use either Intel or Apple Silicon hardware.

Do not treat all environments as equivalent.

---

# 2.1 Linux

Linux comes in many distributions.

Examples include:

- Ubuntu
- Debian
- Fedora
- Red Hat Enterprise Linux
- Rocky Linux
- AlmaLinux
- openSUSE
- Arch Linux

Different distributions may use different:

- package managers
- package names
- repositories
- filesystem conventions
- default shells
- security mechanisms

Useful identification commands include:

```bash
uname -a
```

and on many Linux systems:

```bash
cat /etc/os-release
```

Example:

```text
NAME="Ubuntu"
VERSION="..."
ID=ubuntu
...
```

Do not memorize the exact output.

Understand what you are discovering:

```text
Operating System
Distribution
Version
Kernel
Architecture
```

---

# 2.2 macOS

Useful commands include:

```bash
sw_vers
```

and:

```bash
uname -m
```

Possible architecture output may include:

```text
arm64
```

or:

```text
x86_64
```

This distinction matters when downloading architecture-specific binaries.

An Apple Silicon Mac normally uses ARM64 binaries natively.

An older Intel Mac uses x86-64 binaries.

---

# 2.3 Windows

Windows engineers should know whether they are operating in:

```text
PowerShell
Command Prompt
Git Bash
WSL
```

These are not interchangeable execution environments.

For example:

```text
C:\Users\Engineer
```

is a Windows-style path.

Inside a typical WSL Linux environment, the home directory may instead look like:

```text
/home/engineer
```

The same physical computer can therefore contain multiple execution environments.

This becomes important when:

- installing tools
- setting PATH
- locating SSH keys
- locating configuration files
- running scripts
- accessing Docker
- using cloud CLIs

---

# 2.4 Identify CPU Architecture

Before manually downloading a binary, identify the machine architecture.

On Linux or macOS:

```bash
uname -m
```

Common results include:

```text
x86_64
arm64
aarch64
```

Terminology differs between vendors.

You may encounter:

```text
x86_64
amd64
```

used for the 64-bit x86 architecture, and:

```text
arm64
aarch64
```

used for 64-bit ARM.

The naming convention used by a download page matters.

Do not assume the first binary is correct for your machine.

# 3. THE TERMINAL

## 3.1 What Is a Terminal?

A terminal is an interface through which you interact with command-line programs.

When you open a terminal application, you typically see something similar to:

```text
engineer@workstation:~$
```

or:

```text
engineer@macbook ~ %
```

or a PowerShell prompt such as:

```text
PS C:\Users\Engineer>
```

The terminal itself is not necessarily the shell.

This distinction matters.

---

# 3.2 Terminal Versus Shell

A useful mental model is:

```text
Engineer
   ↓
Terminal
   ↓
Shell
   ↓
Command
   ↓
Operating System
```

The terminal provides the interface.

The shell interprets commands.

Examples of shells include:

- Bash
- Zsh
- Fish
- PowerShell

On Linux and macOS, you can inspect the current shell context using commands such as:

```bash
echo "$SHELL"
```

But be careful with interpretation.

`$SHELL` commonly indicates the user's configured login shell. It does not always prove which shell process is currently executing every command.

You can also inspect the current process context using operating-system tools.

For this Part, the important lesson is simply:

```text
Terminal
≠
Shell
```

---

# 4. THE SHELL

The shell accepts commands and launches programs.

Suppose you enter:

```bash
git --version
```

Conceptually:

```text
You Type Command
      ↓
Shell Parses Input
      ↓
Shell Determines What "git" Means
      ↓
Executable Located
      ↓
Process Started
      ↓
Git Processes --version
      ↓
Output Returned
```

This becomes important when troubleshooting:

```text
command not found
```

The error does not necessarily mean:

```text
The software is definitely not installed.
```

It may mean:

```text
The shell cannot currently locate the executable.
```

Those are different conclusions.

---

# 5. THE FILESYSTEM

Before operating DevOps tools, understand where files live.

A filesystem organizes files and directories.

A simplified Unix-like filesystem looks like:

```text
/
├── bin
├── etc
├── home
│   └── engineer
├── tmp
├── usr
│   ├── bin
│   └── local
│       └── bin
└── var
```

The exact filesystem varies by operating system.

---

# 5.1 Absolute Paths

An absolute path identifies a location from the filesystem root.

Example:

```text
/home/engineer/project
```

or:

```text
/usr/local/bin/terraform
```

On Windows:

```text
C:\Users\Engineer\project
```

---

# 5.2 Relative Paths

A relative path is interpreted relative to the current working directory.

Example:

```text
./scripts/deploy.sh
```

The `.` represents the current directory in common Unix-like shell contexts.

---

# 5.3 Current Working Directory

Use:

```bash
pwd
```

to print the current working directory on Unix-like systems.

Example:

```text
/home/engineer/projects
```

This answers:

```text
Where am I?
```

That sounds basic.

It is not trivial.

Many destructive mistakes happen because an engineer executes a command from the wrong directory or against the wrong environment.

---

# 5.4 Home Directory

On common Unix-like systems:

```bash
echo "$HOME"
```

may produce:

```text
/home/engineer
```

or on macOS:

```text
/Users/engineer
```

The home directory commonly contains user-specific configuration.

Examples you will encounter later include:

```text
~/.ssh/
~/.gitconfig
~/.kube/
```

depending on the tools being used.

The tilde:

```text
~
```

commonly expands to the current user's home directory in Unix-like shells.

---

# 6. ENVIRONMENT VARIABLES

Environment variables provide named values to processes.

Inspect one:

```bash
echo "$HOME"
```

Another important one is:

```bash
echo "$PATH"
```

Environment variables may influence:

- executable discovery
- application behavior
- configuration locations
- language runtimes
- cloud tooling
- proxies
- credentials

For example:

```bash
export DEMO_ENV="development"
```

Then:

```bash
echo "$DEMO_ENV"
```

Expected:

```text
development
```

The exact syntax differs between shells and operating systems.

---

# 6.1 Environment Variables Are Inherited by Processes

A useful mental model is:

```text
Shell
│
├── PATH
├── HOME
└── DEMO_ENV
       ↓
Command Started by Shell
       ↓
Command Receives Environment
```

This is why changing an environment variable can affect commands launched afterward.

---

# 6.2 Environment Variables Can Contain Secrets

This creates a security consideration.

You may eventually encounter environment variables containing credentials or tokens.

Do not assume:

```text
It's only an environment variable.
```

means:

```text
It is safe to print publicly.
```

Be careful when:

- sharing terminal screenshots
- copying logs
- asking AI for assistance
- posting command output
- recording demonstrations

---

# 7. PATH

`PATH` is one of the most important concepts in workstation troubleshooting.

Inspect it:

```bash
echo "$PATH"
```

A Unix-like result may resemble:

```text
/usr/local/bin:/usr/bin:/bin:/home/engineer/.local/bin
```

The exact value depends on the system.

Conceptually:

```text
PATH
=
Directory A
:
Directory B
:
Directory C
:
Directory D
```

When you type:

```bash
terraform
```

the shell searches locations according to its command-resolution rules, commonly including directories listed in `PATH`.

Conceptually:

```text
terraform
   ↓
Search PATH
   ↓
/usr/local/bin/terraform ?
   ↓
/usr/bin/terraform ?
   ↓
...
   ↓
Executable Found
```

---

# 7.1 Why PATH Matters

Imagine Terraform exists here:

```text
/home/engineer/tools/terraform
```

but `PATH` contains only:

```text
/usr/local/bin:/usr/bin:/bin
```

Typing:

```bash
terraform
```

may fail even though the file exists.

This is the difference between:

```text
Binary Missing
```

and:

```text
Binary Exists but Is Not Discoverable Through Current Command Resolution
```

---

# 7.2 PATH Ordering Matters

Suppose:

```text
/usr/local/bin/terraform
```

contains Terraform version A.

And:

```text
/home/engineer/bin/terraform
```

contains version B.

If both directories appear in `PATH`, ordering can influence which binary is selected.

This creates a common problem:

> I upgraded Terraform, but `terraform version` still shows the old version.

Possible explanation:

```text
Multiple Terraform Binaries
        ↓
Different PATH Locations
        ↓
Shell Resolves Unexpected Binary
```

---

# 7.3 Discover Which Command Will Run

On common Unix-like shells:

```bash
command -v git
```

Example:

```text
/usr/bin/git
```

Try:

```bash
command -v ssh
command -v curl
command -v jq
command -v docker
command -v terraform
command -v kubectl
```

This is more useful than merely asking whether a command appears to work.

You want to know:

```text
Which executable am I actually invoking?
```

Depending on the shell, other discovery tools may exist, but `command -v` is a useful shell-oriented starting point on common POSIX-style environments.

---

# 8. COMMAND DISCOVERY

When a command fails, do not immediately reinstall it.

Investigate.

Example:

```text
terraform: command not found
```

Possible causes:

```text
Terraform Not Installed

OR

Terraform Installed Outside PATH

OR

PATH Misconfigured

OR

Wrong Shell Configuration Loaded

OR

Binary Name Different

OR

Installation Incomplete
```

Use evidence.

Example workflow:

```bash
command -v terraform
```

If nothing useful is returned, inspect:

```bash
echo "$PATH"
```

Then determine where the binary was installed.

The exact search technique depends on the operating system and installation method.

---

# 9. SHELL CONFIGURATION FILES

Shells often load configuration from files.

Examples may include:

```text
~/.bashrc
~/.bash_profile
~/.profile
~/.zshrc
```

Which files are loaded depends on:

- shell
- operating system
- login versus non-login shell
- interactive versus non-interactive execution

Do not blindly add the same line to every file.

First determine:

```text
Which shell am I configuring?

Which startup file does this shell read in this situation?
```

A common workstation mistake is editing one file while the active shell loads another.

---

# 10. LOCAL VERSUS REMOTE EXECUTION

This distinction must become automatic.

Suppose your prompt initially shows:

```text
engineer@laptop:~$
```

You connect to a remote server.

The prompt becomes:

```text
ubuntu@lab-server:~$
```

Now:

```bash
pwd
```

runs on the remote server.

So does:

```bash
ls
```

So does:

```bash
cat /etc/os-release
```

So would a destructive command.

Always know:

```text
Where am I executing this?
```

---

# 10.1 A Useful Mental Model

```text
LOCAL WORKSTATION
      │
      │ SSH
      ▼
REMOTE SERVER
      │
      ├── Remote Filesystem
      ├── Remote Processes
      ├── Remote Network
      └── Remote Configuration
```

Opening an SSH session does not somehow merge the two machines.

You are controlling a shell on another system.

---

# 10.2 Never Trust the Prompt Alone

Prompt customization can be misleading.

Verify when necessary:

```bash
hostname
```

and:

```bash
whoami
```

and:

```bash
pwd
```

These answer different questions:

```text
hostname
→ Which host?

whoami
→ Which user?

pwd
→ Which directory?
```

Before a consequential operation, those three pieces of context can matter enormously.

Package managers install and maintain software packages.

Examples include:

```text
Debian / Ubuntu    → apt
Fedora / RHEL      → dnf
Arch Linux         → pacman
macOS              → commonly Homebrew when installed
Windows            → WinGet and other package-management options
```

This is not an exhaustive list.

---

# 11.1 What a Package Manager Does

Conceptually:

```text
Package Request
      ↓
Repository Metadata
      ↓
Package Resolution
      ↓
Download
      ↓
Verification
      ↓
Installation
      ↓
Files Placed on System
```

Package managers may also manage:

- dependencies
- upgrades
- removal
- package metadata

---

# 11.2 Package Manager Versus Manual Binary

Some tools can be installed either through a package manager or by downloading a binary directly.

For example:

```text
Package Manager
      ↓
Install Tool
```

versus:

```text
Vendor Download
      ↓
Select OS
      ↓
Select Architecture
      ↓
Download Binary / Archive
      ↓
Verify
      ↓
Install Into Appropriate Location
```

Neither method is universally correct.

Use the supported installation method appropriate for your environment.

Docker, for example, recommends platform-specific supported installation procedures; its documentation warns that manual static binary installation is primarily suited to testing and requires more manual maintenance.

# 13. GIT

## Why Install Git?

Git provides distributed version control.

Later you will use it to work with:

- source code
- infrastructure code
- scripts
- CI/CD configuration
- Kubernetes manifests
- Terraform
- documentation

For now, install it and verify it.

The Git project publishes OS-specific installation guidance, and Linux distributions commonly provide Git through their package managers.

---

# 13.1 Verify Git

After installation:

```bash
git --version
```

Expected form:

```text
git version <installed-version>
```

Do not require a specific version unless the curriculum or project actually depends on one.

Then:

```bash
command -v git
```

on a compatible Unix-like shell.

Now you know both:

```text
Version
+
Executable Location
```

---

# 13.2 Configure Git Identity

Git commits record author identity.

Configure your real development identity as appropriate:

```bash
git config --global user.name "Your Name"
```

and:

```bash
git config --global user.email "you@example.com"
```

Use the email address appropriate for the repositories you will work with.

Git documents `user.name` and `user.email` as fundamental per-user configuration used in commits.

Verify:

```bash
git config --global user.name
```

and:

```bash
git config --global user.email
```

Inspect configuration and origin:

```bash
git config --list --show-origin
```

This is particularly useful when multiple configuration files define the same setting. Git has system, global, and repository-local configuration scopes, with more specific configuration capable of overriding broader configuration.

---

# 13.3 Configure a Sensible Initial Branch Name

Where appropriate:

```bash
git config --global init.defaultBranch main
```

Git supports configuring the default initial branch name through `init.defaultBranch`.

This does not rename existing repositories.

---

# 13.4 Do Not Configure What You Do Not Understand

You may find internet dotfiles containing hundreds of Git aliases and configuration options.

Do not copy them all.

Start with what you understand.

Complex workstation customization can wait.

# 14. SSH

SSH is fundamental to infrastructure engineering.

You may use it to:

- access Linux servers
- administer remote systems
- authenticate to Git hosting
- transfer files through related tools
- create secure remote sessions

A simplified SSH model is:

```text
Local Workstation
       │
       │ SSH
       ▼
Remote SSH Server
       │
       ▼
Authentication
       │
       ▼
Remote Session
```

---

# 15. SSH PASSWORD AUTHENTICATION VERSUS KEY AUTHENTICATION

SSH can support different authentication mechanisms depending on server configuration.

One important mechanism is public-key authentication.

Conceptually:

```text
Private Key
Stays With You
       │
       │ proves possession
       ▼
SSH Authentication
       ▲
       │
Public Key
Registered Remotely
```

The public and private keys have different security properties.

---

# 16. PUBLIC AND PRIVATE KEYS

A key pair contains:

```text
Private Key
+
Public Key
```

The private key must be protected.

The public key is intended to be distributed to systems that should recognize the corresponding identity.

OpenSSH documentation explicitly treats private identity files as files that should not be readable by other users, while corresponding public-key files can be placed on remote systems for public-key authentication.

---

# 16.1 Generate a Key Pair

A common modern choice in environments that support it is Ed25519:

```bash
ssh-keygen -t ed25519 -C "you@example.com"
```

You will be prompted for:

- output location
- passphrase

A common default location is:

```text
~/.ssh/id_ed25519
```

with the public key:

```text
~/.ssh/id_ed25519.pub
```

Do not blindly overwrite an existing key.

If the path already exists, stop and determine what it is used for.

---

# 16.2 Inspect the Files

After generation:

```bash
ls -la ~/.ssh
```

You may see:

```text
id_ed25519
id_ed25519.pub
```

Remember:

```text
id_ed25519
→ PRIVATE
```

```text
id_ed25519.pub
→ PUBLIC
```

Do not paste the private key into:

- GitHub issues
- chat rooms
- documentation
- AI prompts
- screenshots
- tickets

---

# 17. PRIVATE KEY PERMISSIONS

On Unix-like systems, private SSH key files should be protected from access by other users.

A common permission setting is:

```bash
chmod 600 ~/.ssh/id_ed25519
```

Conceptually:

```text
Owner:
Read + Write

Group:
No Access

Others:
No Access
```

Do not memorize `600` without understanding why the file is sensitive.

The security goal is:

```text
Private Key
↓
Accessible Only to Intended User
```

---

# 18. KNOWN_HOSTS

SSH authentication is not only about the server checking you.

You also need to care which server you are connecting to.

SSH records host identities in a file commonly located at:

```text
~/.ssh/known_hosts
```

Conceptually:

```text
You Request Connection
        ↓
Server Presents Host Key
        ↓
SSH Checks Known Host Identity
        ↓
Match?
   ┌────┴────┐
   │         │
  Yes       No / Changed
   │         │
Continue   Warning / Verification Needed
```

This helps protect against connecting unknowingly to an unexpected system.

---

# 18.1 Do Not Blindly Accept Host-Key Warnings

You may see something similar to:

```text
The authenticity of host ... can't be established.
```

Do not develop the habit:

```text
Type yes every time.
```

The correct question is:

```text
How do I know this host key belongs to the system I intended to reach?
```

In a managed environment, the expected fingerprint may be provided through trusted documentation or another verified channel.

---

# 18.2 Changed Host Keys

A changed host key can occur legitimately.

For example:

- server rebuilt
- host replaced
- key intentionally rotated

But it can also indicate that you are not connecting to the system you think you are.

Do not immediately delete the old `known_hosts` entry just to remove the warning.

Investigate first.

---

# 19. SSH AGENT

A private key can be protected by a passphrase.

Entering that passphrase repeatedly can become inconvenient.

`ssh-agent` can hold private-key identities for authentication so applications can request authentication operations through the agent. OpenSSH documents `ssh-agent` as a program for holding private keys used for public-key authentication.

A common Unix-like workflow is:

```bash
eval "$(ssh-agent -s)"
```

then:

```bash
ssh-add ~/.ssh/id_ed25519
```

Inspect loaded identities:

```bash
ssh-add -l
```

The exact integration varies by operating system and desktop environment.

Do not start multiple agents unnecessarily just because a tutorial says to run the command every time.

Your environment may already manage an agent.

---

# 19.1 Agent Forwarding Is Not Automatically Safe

SSH agent forwarding can make local authentication identities available for use through remote sessions.

That can be convenient.

It also expands the trust implications of the remote system.

Do not enable agent forwarding globally without understanding why it is required.

Convenience should not automatically expand authentication exposure.

---

# 20. REMOTE SSH SESSION

A basic SSH connection has the form:

```bash
ssh username@hostname
```

For example:

```bash
ssh learner@lab.example
```

Do not use this example hostname unless your lab actually provides it.

After connecting, verify context:

```bash
whoami
hostname
pwd
```

Then inspect:

```bash
cat /etc/os-release
```

on an appropriate Linux host.

You should now be able to explain:

```text
My terminal is local.

My SSH client was launched locally.

The authenticated session is remote.

Commands entered inside that session execute on the remote host.
```

---

# 21. SSH CONFIGURATION

As the number of remote systems grows, repeatedly typing full connection parameters becomes inefficient.

OpenSSH clients support per-user configuration, commonly through:

```text
~/.ssh/config
```

A conceptual example:

```text
Host lab
    HostName lab.example
    User learner
    IdentityFile ~/.ssh/id_ed25519
```

Then:

```bash
ssh lab
```

could use those settings.

Do not copy this literally unless those values match your environment.

The lesson is that connection configuration can be recorded explicitly instead of relying on memory.

# 22. CURL

`curl` is a command-line data transfer tool.

DevOps engineers frequently use it to interact with:

- HTTP endpoints
- APIs
- health checks
- downloadable files

For now, verify:

```bash
curl --version
```

Then locate it:

```bash
command -v curl
```

---

# 22.1 Basic HTTP Request

Try an approved public test endpoint or an application you control.

Conceptually:

```bash
curl https://example.com
```

This sends a request and prints the response body.

To inspect headers:

```bash
curl -I https://example.com
```

Later you will use `curl` more extensively for APIs and troubleshooting.

For now understand:

```text
curl
↓
Network Request
↓
Remote Endpoint
↓
Response
```

---

# 22.2 Be Careful With `curl | shell`

You will sometimes encounter installation instructions resembling:

```text
curl <some-url> | sh
```

This downloads content and immediately sends it to a shell for execution.

The convenience is obvious.

The trust implication should also be obvious:

```text
Remote Content
↓
Immediate Local Execution
```

# 55. TROUBLESHOOTING: SSH AUTHENTICATION FAILURE

Scenario:

```text

```

Investigate systematically.

## Step 1: Destination

Confirm:

```text
Hostname:
Username:
Port:
```

Wrong username can produce authentication failure even with a valid key.

## Step 2: Identity

Which key is being offered?

Use verbose SSH diagnostics when appropriate:

```bash

```

More verbose levels exist, but start with enough information to understand authentication behavior without generating unnecessary noise.

## Step 3: Agent

Check:

```bash
ssh-add -l
```

if using an agent.

## Step 4: Public Key Registration

Confirm the corresponding public key is authorized on the destination.

## Step 5: Permissions

Check local private-key permissions.

## Step 6: Server Policy

The server may restrict:

- users
- authentication methods
- keys

## Step 7: Escalate

If server-side access is required and you do not have it, provide evidence to the system owner.

# 68. BUILD A WORKSTATION VERIFICATION SCRIPT

Do not automate installation yet.

Automate inspection.

Create:

```bash
mkdir -p "$HOME/veriqta-workstation"
cd "$HOME/veriqta-workstation"
```

Create:

```text
verify-workstation.sh
```

with:

```bash
#!/usr/bin/env bash

echo "=== VERIQTA Workstation Verification ==="
echo

echo "User:"
whoami
echo

echo "Host:"
hostname
echo

echo "Architecture:"
uname -m
echo

echo "Shell:"
printf '%s\n' "${SHELL:-unknown}"
echo

echo "Tool discovery:"

for tool in git ssh curl jq docker terraform kubectl; do
    printf '%-12s' "$tool"
    if command -v "$tool" >/dev/null 2>&1; then
        command -v "$tool"
    else
        echo "NOT FOUND"
    fi
done
```

Make it executable:

```bash
chmod +x verify-workstation.sh
```

Run:

```bash
./verify-workstation.sh
```

# 68.1 Why This Script Does Not Install Anything

The script is deliberately read-oriented.

It gathers evidence.

It does not:

- install packages
- modify PATH
- change permissions outside itself
- configure cloud credentials
- access production
- modify infrastructure

This reflects the curriculum's troubleshooting philosophy:

```text

```
