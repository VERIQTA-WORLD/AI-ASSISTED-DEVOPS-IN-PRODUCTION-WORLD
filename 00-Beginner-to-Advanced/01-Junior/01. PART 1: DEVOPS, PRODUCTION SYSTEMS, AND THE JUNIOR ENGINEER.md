# PART 1: DEVOPS, PRODUCTION SYSTEMS, AND THE JUNIOR ENGINEER

## Goal

The goal of this section is to understand what DevOps work actually involves, how software moves from source code to a running production service, where a junior engineer fits into that system, and how to reason safely when something goes wrong.

By the end of this section, you should understand that DevOps is not simply a collection of tools.

Knowing Git does not automatically make someone a DevOps engineer.

Knowing Docker does not automatically make someone a DevOps engineer.

Knowing Kubernetes, Terraform, Jenkins, AWS, Azure, or another cloud platform does not automatically make someone a DevOps engineer.

These technologies solve particular engineering problems inside a much larger system.

The first skill you need is the ability to see that system.

You should begin developing a mental model that connects:

```text
Source Code
     ↓
Version Control
     ↓
Build
     ↓
Testing
     ↓
Artifact
     ↓
Infrastructure
     ↓
Deployment
     ↓
Runtime
     ↓
Network
     ↓
User
```

You should also begin developing the operational habit that will be used throughout the entire VERIQTA curriculum:

```text
Observe
   ↓
Collect Evidence
   ↓
Form a Hypothesis
   ↓
Test Safely
   ↓
Make the Smallest Justified Change
   ↓
Verify
```

That habit matters more than memorizing hundreds of commands.

# 1. WHAT DEVOPS IS

## 1.1 Start With the Problem

Before discussing DevOps, consider a simple software company.

The development team writes an application.

The application works on a developer's laptop.

Eventually the application must be made available to real users.

That creates a completely different set of problems.

Someone must answer questions such as:

- Where will the application run?
- How will the application be built?
- How will releases be created?
- How will configuration be supplied?
- How will credentials be protected?
- How will users reach the application?
- How will new versions be deployed?
- How will failed deployments be detected?
- How will a previous version be restored?
- How will the application be monitored?
- How will infrastructure be created?
- How will infrastructure changes be reviewed?
- What happens when a server fails?
- What happens when traffic increases?
- What happens when storage fills?
- What happens when a certificate expires?
- What happens when a dependency becomes unavailable?
- Who investigates when users report a problem?
- How can the same process be repeated tomorrow without depending on someone's memory?

Writing the application is therefore only one part of delivering a useful software service.

A production system has an entire lifecycle.

```text
Plan
  ↓
Develop
  ↓
Build
  ↓
Test
  ↓
Package
  ↓
Provision
  ↓
Deploy
  ↓
Operate
  ↓
Observe
  ↓
Improve
  └──────────────→ back into planning and development
```

DevOps exists in this broader lifecycle.

---

# 1.2 Development and Operations

Historically, many organizations separated software development and IT operations into distinct groups with different responsibilities.

A simplified model looked like this:

```text
DEVELOPMENT

Write Code
   ↓
Test Code
   ↓
Package Release
   ↓
"Give it to Operations"


OPERATIONS

Receive Release
   ↓
Deploy Release
   ↓
Run Infrastructure
   ↓
Handle Production Problems
```

This separation can create organizational and technical friction.

Imagine a developer saying:

> The application works on my machine. The problem must be production.

Operations may respond:

> The servers are healthy. The problem must be the application.

Meanwhile, users still cannot use the service.

The real production system does not care which organizational team owns the problem.

If a user request travels through:

```text
DNS
 ↓
Load Balancer
 ↓
Application
 ↓
Database
```

then failure at any of those layers can affect the user.

Effective software delivery therefore requires development and operational concerns to be considered together.

DevOps emerged from this need for better collaboration, faster feedback, greater automation, repeatability, and shared responsibility across the software lifecycle.

A useful working definition is:

> DevOps is a combination of engineering practices, collaboration, automation, feedback, and operational responsibility used to deliver and operate software reliably and repeatedly.

It is not one product.

It is not one cloud provider.

It is not synonymous with Kubernetes.

It is not synonymous with CI/CD.

And it is not simply another name for a system administrator.

---

# 1.3 DevOps Is Not Just a Job Title

You will see job titles such as:

- DevOps Engineer
- Cloud DevOps Engineer
- DevSecOps Engineer
- Platform Engineer
- Site Reliability Engineer
- Infrastructure Engineer
- Build Engineer
- Release Engineer

Organizations use these titles differently.

One company's DevOps engineer may spend most of the day maintaining Kubernetes and Terraform.

Another may focus heavily on CI/CD.

Another may primarily operate cloud infrastructure.

Another may maintain developer platforms.

Another may combine Linux administration, automation, networking, monitoring, cloud, security, and deployment work.

Therefore, do not build your understanding of DevOps from job titles alone.

Focus on the engineering problems being solved.

---

# 1.4 The Core Problems DevOps Tries to Solve

DevOps practices commonly attempt to improve several related areas.

## Delivery

How can software changes reach users reliably?

## Repeatability

Can the same process produce predictable results repeatedly?

## Automation

Which repetitive operations can be performed consistently by systems instead of manually by humans?

## Feedback

How quickly can engineers discover that a change is broken?

## Reliability

Can the service continue providing acceptable behavior?

## Observability

Can engineers understand what the system is doing?

## Recovery

When something fails, can the organization restore service safely?

## Collaboration

Can the people responsible for development, infrastructure, security, testing, and operations work from shared evidence and processes?

## Security

Can systems be delivered and operated without granting unnecessary access or exposing sensitive information?

---

# 1.5 Automation Is Not the Goal by Itself

Automation is central to DevOps, but automation is not automatically good.

Suppose an engineer manually deletes the wrong production server.

That is dangerous.

Now suppose the engineer writes automation capable of deleting 500 production servers simultaneously.

The operation has become faster.

It has not necessarily become safer.

This leads to an important principle:

```text
Automation
+
Incorrect Assumption
=
Faster Failure
```

Good automation should improve properties such as:

- repeatability
- consistency
- auditability
- speed
- verification
- recovery
- safety

Automation should not merely make actions faster.

---

# 1.6 Repeatability

Imagine deploying an application using a document containing 47 manual steps.

Engineer A performs all 47 correctly.

Engineer B accidentally skips step 23.

Engineer C performs step 31 before step 30.

Engineer D remembers an undocumented additional step.

You now have multiple versions of what was supposed to be the same process.

Repeatable engineering attempts to reduce this kind of variation.

A repeatable process should make it possible to answer:

```text
What was done?
Who or what performed it?
Which version was used?
Which configuration was used?
What result was expected?
What actually happened?
Can we perform it again?
```

This is one reason automation, version control, CI/CD, infrastructure as code, configuration management, and declarative systems become important later in the curriculum.

---

# 1.7 Feedback Loops

Engineering becomes dangerous when feedback arrives too late.

Consider:

```text
Developer writes code
        ↓
Six weeks pass
        ↓
Code reaches production
        ↓
Users discover it is broken
```

Compare that with:

```text
Developer writes code
        ↓
Automated checks run
        ↓
Problem detected
        ↓
Developer receives feedback
```

The second feedback loop is shorter.

Short feedback loops help engineers detect problems closer to the point where they were introduced.

Feedback can come from many places:

- code review
- automated tests
- build results
- security checks
- infrastructure plans
- deployment verification
- logs
- metrics
- traces
- alerts
- user reports
- incident reviews

A mature engineering system attempts to produce useful feedback before a small problem becomes a large production incident.

---

# 1.8 Delivery Speed Versus Operational Safety

A common misunderstanding is that DevOps means:

```text
Deploy Faster
```

A better model is:

```text
Deliver Useful Changes
Quickly
Reliably
Repeatably
Safely
```

Speed without safety creates instability.

Safety without the ability to change can create stagnation.

The engineering challenge is to make change routine enough, observable enough, testable enough, and reversible enough that the organization can move quickly without treating every deployment as an emergency.

This is why reliable delivery processes use automation, testing, controlled permissions, repeatable artifacts, review, monitoring, and rollback mechanisms rather than relying on speed alone. AWS describes DevOps in terms of culture, practices, and tools that improve delivery velocity while also emphasizing reliability, automation, monitoring, and repeatability.

# 2. WHAT A PRODUCTION SYSTEM LOOKS LIKE

## 2.1 Source Code Is Not a Production Service

Suppose a developer creates this application:

```text
app.py
```

The file contains source code.

Can a customer on another continent use it?

No.

The code must pass through additional systems before it becomes a usable production service.

A first mental model is:

```text
Developer
    ↓
Source Code
    ↓
Git Repository
    ↓
Build
    ↓
Artifact / Container Image
    ↓
CI/CD Pipeline
    ↓
Infrastructure
    ↓
Deployment
    ↓
Application
    ↓
Network
    ↓
Users
```

This is intentionally simplified.

Real systems may contain many additional layers.

But this model gives us somewhere to begin.

---

# 2.2 Developer

A developer creates or changes software.

Changes may include:

- application code
- tests
- dependencies
- configuration
- build definitions
- database migrations
- infrastructure definitions
- deployment manifests

The important point is that a production change usually begins as an intentional modification somewhere.

When troubleshooting later, one of the first useful questions will often be:

```text
What changed?
```

---

# 2.3 Source Code

Source code is the human-maintained representation of the software.

Depending on the application, it may include languages such as:

```text
Python
Go
Java
JavaScript
TypeScript
C#
C++
Rust
```

But source code alone is usually not the complete operational system.

The repository may also contain:

```text
Application Code
Tests
Build Files
Dependency Definitions
Container Definitions
CI/CD Configuration
Infrastructure Code
Deployment Configuration
Documentation
```

This is why production engineers often need to understand repositories even when they are not primarily application developers.

---

# 2.4 Git Repository

The repository provides controlled history for engineering changes.

At this stage, you only need the conceptual role.

A repository helps answer questions such as:

- What changed?
- Who changed it?
- When did it change?
- What did the previous version look like?
- Was the change reviewed?
- Which version should be built?

Later Parts will teach Git directly.

For now, remember:

```text
Repository
=
Recorded Engineering State and History
```

---

# 2.5 Build

Many applications require a build process.

The exact process depends on the technology.

A build might:

- compile source code
- install dependencies
- run tests
- bundle files
- create a binary
- create a package
- create a container image

Conceptually:

```text
Source
+
Dependencies
+
Build Instructions
        ↓
      Build
        ↓
Build Output
```

A build process should ideally be repeatable.

If the same source revision produces unpredictably different outputs because of uncontrolled dependencies or machine-specific conditions, release confidence decreases.

Google's SRE material on release engineering emphasizes reproducible, automated release processes and the ability to connect deployed software back to how it was built.

---

# 2.6 Artifact

The output that will eventually be delivered is often called an artifact.

Examples include:

- executable binary
- JAR file
- package
- archive
- container image

An important distinction is:

```text
Source Code
≠
Build Artifact
```

The source represents what engineers wrote.

The artifact represents something produced for execution or distribution.

A container image is one common artifact format, but not every application is delivered as a container image.

---

# 2.7 CI/CD Pipeline

CI/CD introduces automation into software integration and delivery.

At a conceptual level:

```text
Code Change
    ↓
Automated Validation
    ↓
Build
    ↓
Test
    ↓
Package
    ↓
Potential Delivery / Deployment
```

Later Parts will distinguish continuous integration, continuous delivery, and deployment more precisely.

For now, think of the pipeline as a controlled automated path through which changes can be checked and prepared for release.

A pipeline may perform:

- syntax validation
- unit tests
- security scanning
- builds
- artifact publishing
- infrastructure checks
- deployment
- post-deployment verification

A critical lesson:

```text
Pipeline Green
≠
Production Healthy
```

A pipeline can report success while users still experience failure.

Why?

Because the pipeline is only one part of the production system.

---

# 2.8 Infrastructure

The application requires somewhere to run.

Infrastructure may include:

- virtual machines
- physical servers
- container platforms
- Kubernetes clusters
- serverless runtimes
- networks
- load balancers
- storage
- databases
- DNS
- identity systems
- firewalls

Cloud platforms expose many of these as services.

Infrastructure provides the environment in which application workloads operate.

---

# 2.9 Deployment

Deployment is the process of making a particular application version available in a target environment.

Conceptually:

```text
Artifact
+
Configuration
+
Target Environment
        ↓
    Deployment
        ↓
Running Application Version
```

But notice something important.

A successful deployment command does not prove that the service works.

For example:

```text
Deployment completed successfully.
```

might only mean that the deployment system successfully submitted the requested change.

The application could still:

- crash after startup
- fail to connect to its database
- listen on the wrong port
- have invalid credentials
- return HTTP 500 errors
- be unreachable through the load balancer
- fail DNS resolution
- experience severe latency

Therefore:

```text
Deployment Success
≠
Application Health
≠
User Success
```

These are different states and must be verified independently.

---

# 2.10 Application Runtime

Eventually, something must actually execute the application.

Conceptually:

```text
Artifact
+
Configuration
+
Runtime
+
Resources
        ↓
Running Application
```

The running application may depend on:

- CPU
- memory
- filesystem
- network
- environment variables
- configuration files
- secrets
- databases
- APIs
- queues
- caches
- storage

This dependency chain matters enormously during troubleshooting.

---

# 2.11 Network

A perfectly healthy application can still be unusable if users cannot reach it.

A simplified user request might travel through:

```text
User
 ↓
DNS
 ↓
Internet / Network
 ↓
Load Balancer
 ↓
Application
 ↓
Database
```

Every arrow represents a relationship that can fail.

Therefore:

```text
Application Process Running
```

does not prove:

```text
User Can Reach Application
```

This distinction will become extremely important when we study networking.

---

# 2.12 Users

The final reason the production system exists is to provide some useful outcome.

The user normally does not care that:

```text
CPU is healthy
Pods are running
Pipeline is green
Server is reachable
Database process exists
```

if:

```text
Checkout does not work.
```

Operational engineering must eventually connect internal system state to user-visible behavior.

Google's SRE guidance explicitly distinguishes symptoms from causes and emphasizes monitoring user-facing behavior as well as internal system evidence.

---

# 3. THE SUPPORTING SYSTEMS AROUND AN APPLICATION

A production application does not exist by itself.

Consider:

```text
Application
├── Configuration
├── Secrets
├── Compute
├── Network
├── Storage
├── Logs
├── Metrics
├── Alerts
└── Security Controls
```

Each branch solves a different operational problem.

---

# 3.1 Configuration

Configuration tells the application how it should behave in a particular environment.

Examples might include:

```text
LOG_LEVEL=info
DATABASE_HOST=db.internal
API_TIMEOUT=5
FEATURE_X_ENABLED=true
```

The values above are illustrative.

Configuration often differs between environments.

Configuration errors can cause production failures even when the application code itself is correct.

---

# 3.2 Secrets

Applications frequently need sensitive information or credentials.

Examples can include:

- passwords
- API tokens
- private keys
- certificates
- access credentials

These must not be treated like ordinary public configuration.

A major operational question is:

```text
How does the application receive the authority it needs
without exposing sensitive credentials unnecessarily?
```

Later Parts will explore this properly.

For now:

```text
Configuration
≠
Secret
```

even though both may be supplied to an application.

---

# 3.3 Compute

Compute provides processing capacity.

It might be:

- a physical server
- a virtual machine
- a container host
- a Kubernetes node
- a managed runtime
- a serverless execution environment

Applications consume resources such as CPU and memory from this layer.

---

# 3.4 Network

The network connects:

- users to applications
- applications to applications
- applications to databases
- infrastructure components to each other
- engineers to systems

A network problem can therefore appear as an application problem.

---

# 3.5 Storage

Some information must survive longer than the lifetime of an individual process.

Storage may hold:

- application data
- files
- database data
- backups
- artifacts
- logs

A process disappearing and data disappearing are not the same event.

This becomes especially important when working with containers and distributed systems later.

---

# 3.6 Logs

Logs record discrete events or messages produced by systems and applications.

Examples:

```text
Application started
Authentication failed
Database connection refused
Request completed
Configuration file missing
```

Logs are evidence.

They are not automatically the truth about root cause.

For example:

```text
Database connection failed
```

could mean:

- database is down
- DNS failed
- network path failed
- credentials are invalid
- connection limit was reached
- TLS validation failed
- application configuration points to the wrong destination

Therefore:

```text
Log Message
=
Evidence
```

not necessarily:

```text
Log Message
=
Final Root Cause
```

---

# 3.7 Metrics

Metrics provide quantitative measurements over time.

Examples:

```text
CPU utilization
Memory consumption
Request count
Error count
Request latency
Disk usage
Queue depth
```

Metrics help engineers identify patterns that a single log entry may not reveal.

For user-facing services, Google's SRE guidance highlights latency, traffic, errors, and saturation as particularly useful signals.

You do not need to master these yet.

Just understand that metrics answer questions about system behavior over time.

---

# 3.8 Alerts

Alerts notify people or systems that a condition may require attention.

An alert might indicate:

```text
Error rate is above threshold.
```

That is evidence of a symptom.

It does not automatically tell you why the errors are occurring.

Therefore:

```text
Alert
↓
Investigation
```

not:

```text
Alert
↓
Random Restart
```

This distinction is fundamental.

---

# 3.9 Security Controls

Production systems need mechanisms controlling:

- who can access systems
- what they can do
- what applications can access
- which network paths are allowed
- how sensitive information is protected
- what actions are recorded

Security is not something added after the system is finished.

It exists throughout the system.

---

# 4. THE PRODUCTION SYSTEM AS LAYERS

When troubleshooting, it is useful to think in layers.

Consider:

```text
┌───────────────────────────────┐
│             USER              │
├───────────────────────────────┤
│       EXTERNAL TRAFFIC        │
├───────────────────────────────┤
│       APPLICATION ENTRY       │
├───────────────────────────────┤
│          APPLICATION          │
├───────────────────────────────┤
│        RUNTIME / PROCESS      │
├───────────────────────────────┤
│           COMPUTE             │
├───────────────────────────────┤
│           NETWORK             │
├───────────────────────────────┤
│           STORAGE             │
├───────────────────────────────┤
│      EXTERNAL DEPENDENCIES    │
└───────────────────────────────┘
```

The exact layers vary by architecture.

The important habit is to stop treating:

```text
"The application"
```

as one indivisible object.

Production is a chain of interacting systems.

# 5. ENVIRONMENTS

## 5.1 Why Environments Exist

Engineers need places to develop and test changes before exposing them to real users.

A common conceptual progression is:

```text
Local
  ↓
Development
  ↓
Testing
  ↓
Staging
  ↓
Production
```

Not every organization uses exactly these environments.

Some have fewer.

Some have more.

Names also vary.

The important concept is separation.

---

# 5.2 Local Environment

The local environment usually refers to the engineer's own workstation or local development setup.

For example:

```text
Developer Laptop
├── Source Code
├── Local Runtime
├── Local Dependencies
└── Development Tools
```

The purpose is rapid development and experimentation.

Local environments are convenient.

They are not automatically representative of production.

---

# 5.3 Development Environment

A shared development environment may allow teams to integrate and test changes away from production.

It might contain:

- shared infrastructure
- development databases
- development credentials
- test services
- temporary application versions

Its purpose is development, not production reliability.

---

# 5.4 Testing Environment

A testing environment may be used for automated or manual validation.

Tests might verify:

- functionality
- integration
- APIs
- compatibility
- security behavior
- performance

Organizations structure testing differently, so do not assume there is always one environment literally called `testing`.

---

# 5.5 Staging Environment

Staging is commonly intended to resemble production closely enough to provide meaningful pre-production validation.

For example:

```text
Staging Application
Staging Database
Staging Network Configuration
Staging Deployment Process
Staging Observability
```

But staging is rarely perfectly identical to production.

Differences can include:

- scale
- traffic
- data
- credentials
- external dependencies
- capacity
- network controls

Therefore:

```text
Works in Staging
```

increases confidence but does not mathematically prove:

```text
Will Work in Production
```

---

# 5.6 Production Environment

Production is the environment serving real business workloads or real users.

Changes here can have real consequences.

A production failure can affect:

- customers
- revenue
- data
- security
- contractual obligations
- internal operations
- reputation

This is why production access and changes are usually more controlled.

---

# 5.7 Environment-Specific Configuration

Consider:

```text
Development:
DATABASE_HOST=dev-db.internal

Staging:
DATABASE_HOST=staging-db.internal

Production:
DATABASE_HOST=prod-db.internal
```

The application may be identical while configuration changes.

This allows the same application logic to operate against different supporting systems.

But configuration differences also create failure opportunities.

If production accidentally receives:

```text
DATABASE_HOST=staging-db.internal
```

the application may technically start while behaving incorrectly.

This is why configuration is part of production engineering.

---

# 5.8 Environment-Specific Secrets

Development credentials should generally not automatically provide production authority.

Conceptually:

```text
Development Identity
        ↓
Development Resources
```

and:

```text
Production Identity
        ↓
Production Resources
```

should be separated according to the organization's security design.

A junior engineer must learn early that access is not merely a convenience.

Access is authority.

---

# 5.9 "Works on My Machine"

Suppose an application works locally but fails in production.

Possible differences include:

- operating system
- runtime version
- dependency version
- environment variables
- filesystem paths
- permissions
- network access
- DNS
- secrets
- CPU
- memory
- external services
- architecture
- configuration

Therefore:

```text
Works Locally
```

proves only:

```text
It worked under those local conditions.
```

It does not prove that production conditions are equivalent.

The engineering response is not:

> But it works on my laptop.

The engineering response is:

> What is different between the working and failing environments?

That question produces evidence.

- Which port?
- Which credentials?
- What happens if the database is unavailable?
- What does the application log?
- What metric changes?
- What does the user experience?

That is the beginning of systems thinking.

# 7. JUNIOR DEVOPS RESPONSIBILITIES

## 7.1 Junior Does Not Mean "Do Anything You Are Told"

A junior engineer is less experienced.

That does not mean the engineer should execute commands without understanding them.

A healthy junior workflow looks more like:

```text
Task
 ↓
Understand Scope
 ↓
Read Procedure / Documentation
 ↓
Inspect Current State
 ↓
Confirm Permissions and Approvals
 ↓
Perform Controlled Action
 ↓
Verify
 ↓
Document
 ↓
Escalate if Needed
```

The goal is safe participation in real engineering work while developing increasingly independent reasoning.

---

# 7.2 Inspecting Systems

A junior engineer may be asked to inspect:

- application state
- deployment state
- pipeline results
- cloud resources
- logs
- alerts
- configuration
- service status

Inspection is often lower risk than modification.

This is why evidence gathering is such an important early skill.

---

# 7.3 Following Runbooks

A runbook is operational documentation describing how to perform or investigate a known task.

For example:

```text
Alert: Application health check failing

1. Confirm affected environment.
2. Confirm affected service.
3. Inspect deployment state.
4. Inspect application logs.
5. Check recent changes.
6. Follow defined escalation path if condition persists.
```

A good junior engineer does not blindly follow the runbook.

If the observed system no longer matches the assumptions in the runbook, stop and reassess.

Documentation can become outdated.

---

# 7.4 Maintaining Scripts

Junior engineers may maintain small automation scripts.

Changes should still be:

- understood
- reviewed
- tested
- version controlled
- verified

A six-line script can still delete data if given sufficient authority.

Risk is determined by capability and context, not file length.

---

# 7.5 Making Reviewed Configuration Changes

A junior engineer may modify:

- application configuration
- pipeline configuration
- infrastructure definitions
- deployment settings

But changes should normally follow the organization's review and approval processes.

The important habit is:

```text
Before Change:
What is the current state?
What should change?
What could this affect?

After Change:
Did the intended state change?
Did anything else break?
```

---

# 7.6 Supporting Deployments

Supporting a deployment may involve:

- checking prerequisites
- confirming the intended version
- monitoring pipeline progress
- observing rollout state
- checking application health
- watching error rates
- confirming user-facing behavior
- helping gather evidence when something fails

The junior engineer should understand:

```text
Deployment Completed
```

is not the end of verification.

Production rollouts should be observed, and unexpected behavior may justify stopping or rolling back according to the organization's procedures. This principle is reflected in established SRE release practices.

---

# 7.7 Checking Pipelines

A pipeline can fail for many reasons:

- source problem
- test failure
- build failure
- dependency failure
- authentication problem
- configuration error
- infrastructure failure
- deployment problem

The correct response is not:

> Pipeline failed. Rerun it.

The first question is:

> Which stage failed, and what evidence explains the failure?

Rerunning without understanding can hide intermittent problems.

---

# 7.8 Investigating Alerts

An alert is the beginning of an investigation.

Suppose:

```text
ALERT:
HTTP 5xx rate above threshold
```

This tells us something about observed behavior.

It does not tell us:

- which code is broken
- whether a deployment caused it
- whether a database failed
- whether a dependency failed
- whether the network is involved

The engineer gathers additional evidence.

---

# 7.9 Gathering Diagnostic Evidence

A junior engineer can provide enormous value during incidents by gathering precise evidence.

Useful evidence might include:

```text
Affected service:
checkout-api

Affected environment:
production

First observed:
14:32 UTC

User symptom:
checkout requests returning errors

Recent deployment:
14:27 UTC

Observed error:
database connection timeout

Scope:
all production instances

Current status:
ongoing
```

Compare that with:

> Production is broken.

The first report gives another engineer something useful to reason from.

# 7.10 Routine Cloud Operations

Depending on the organization and permissions, junior engineers may perform controlled tasks involving:

- inspecting resources
- checking resource state
- reviewing configuration
- starting or stopping approved non-production resources
- supporting deployments
- reviewing monitoring information

The exact permissions vary by organization.

Never assume that "junior DevOps engineer" implies unrestricted cloud access.

# 7.11 Tickets and Pull Requests

Engineering work often leaves an audit trail.

A ticket may explain:

```text

```

A pull request may show:

```text

```

A pipeline may show:

```text
What validation occurred?
```

A deployment record may show:

```text
What reached the environment?
```

Monitoring may show:

```text

```

Together these become valuable evidence.

# 7.12 Documentation

Documentation is engineering work.

A junior engineer should learn to record:

- what changed
- why it changed
- relevant commands or procedures
- verification performed
- unexpected behavior
- unresolved issues

Useful documentation allows another engineer to understand what happened without reconstructing everything from memory.

# 8. OWNERSHIP, AUTHORITY, AND ESCALATION

## 8.1 Observing a Problem Does Not Authorize a Change

Suppose you observe:

```text
Production website unavailable
```

You also notice:

```text
One server is using 95% CPU.
```

Should you restart it?

Not necessarily.

You know:

```text
High CPU exists.
```

You do not yet know:

```text
High CPU caused the outage.
```

And you may not know:

```text
Restarting the server is safe.
```

These are separate questions.

---

# 8.2 Observation Versus Conclusion

Learn to separate:

```text
OBSERVATION:
CPU is 95%.
```

from:

```text
HYPOTHESIS:
CPU saturation may be contributing to request latency.
```

from:

```text
TEST:
Compare request latency, process utilization,
and behavior across affected instances.
```

from:

```text
CONCLUSION:
A specific process is saturating CPU and requests
on that instance are experiencing increased latency.
```

This prevents assumptions from becoming "facts."

---

# 8.3 Ownership

Ownership answers:

> Who is responsible for this system or decision?

Different components may have different owners.

For example:

```text
Application        → Application Team
CI/CD Platform     → Platform Team
Cloud Network      → Infrastructure Team
Database           → Database / Platform Team
Security Policy    → Security Team
```

Actual organizations vary.

A junior engineer should identify ownership instead of assuming every technical problem belongs to DevOps.

---

# 8.4 Permissions

Permissions answer:

> What am I technically allowed to do?

Examples:

```text
Read logs
Modify repository
Deploy staging
Deploy production
Read secrets
Change firewall
Delete infrastructure
```

These should not all automatically belong to the same person.

---

# 8.5 Approval

Permission and approval are different.

You may technically possess permission to perform an operation while organizational process still requires approval.

For example:

```text
Technical Permission:
Can deploy production

Process Requirement:
Production deployment requires approved change
```

Being technically capable of an action does not mean the action is authorized in every situation.

---

# 8.6 Blast Radius

Blast radius describes the potential scope of impact if something goes wrong.

Compare:

```text
Restart local development application
```

with:

```text
Restart all production application instances
```

The commands may look similar.

The consequences are not.

Think about blast radius across:

- users
- services
- environments
- regions
- data
- security
- business operations

A useful principle is:

```text
Greater Blast Radius
        ↓
Greater Need for
Evidence
Review
Control
Verification
Recovery Planning
```

---

# 8.7 Change Risk

Risk is contextual.

Deleting a temporary test resource may be low risk.

Changing a production routing rule may be high risk.

Questions to ask:

```text
What does this affect?
How many users?
Can data be lost?
Can the change be reversed?
How quickly?
Has it been tested?
Do we have evidence supporting it?
What happens if our assumption is wrong?
```

---

# 8.8 Production Access

Production access is powerful because production contains real systems and potentially sensitive information.

Good operational environments often restrict access according to role and purpose.

The junior engineer should develop a healthy respect for production authority without becoming afraid to work in production.

The goal is:

```text
Controlled Confidence
```

not:

```text
Recklessness
```

and not:

```text
Fear of Touching Anything
```

---

# 8.9 Escalation Is an Engineering Skill

Escalation is not failure.

Poor escalation:

> It's broken. Can someone check?

Better escalation:

```text
Production checkout requests began returning HTTP 500 responses at approximately 14:32 UTC.

The issue affects all three application instances.

The most recent deployment completed at 14:27 UTC.

Application logs show database connection timeouts beginning at 14:32 UTC.

I confirmed the application instances are running.

I have not changed production.

The runbook's next step requires database-level access that I do not have.

Escalating to the database/service owner with the evidence above.
```

That escalation is valuable.

It reduces investigation time and avoids unnecessary experimentation.

# 9. AI IN MODERN DEVOPS WORK

## 9.1 AI Is an Assistant, Not Production Evidence

AI can significantly accelerate engineering work.

A junior engineer might ask AI to:

- explain an unfamiliar configuration file
- explain an error message
- draft a shell script
- review code
- generate test cases
- summarize logs
- explain documentation
- suggest troubleshooting hypotheses
- draft infrastructure configuration
- improve technical documentation

These are legitimate uses.

But there is a critical distinction:

```text
AI Output
=
Proposal / Explanation / Hypothesis
```

not:

```text
AI Output
=
Verified Production Truth
```

---

# 9.2 AI Can Invent Commands

Suppose AI suggests:

```text
some-tool --repair-production
```

The command looks believable.

That does not prove the flag exists.

Before execution, ask:

```text
Does this command exist?

Does this flag exist in my installed version?

What exactly does it do?

Is it read-only or state-changing?

What permissions does it use?

What resources does it affect?

Can it be reversed?
```

For unfamiliar state-changing commands, verify against authoritative documentation and the actual installed tool version.

---

# 9.3 AI Can Invent Configuration

AI-generated YAML, JSON, Terraform, pipeline configuration, or other configuration can be syntactically convincing while still being wrong.

Possible problems include:

- nonexistent fields
- deprecated fields
- incorrect nesting
- wrong defaults
- invalid values
- wrong API versions
- insecure permissions
- incorrect assumptions

Therefore:

```text
Looks Correct
≠
Is Correct
```

---

# 9.4 AI Can Be Wrong About Versions

Technology changes.

A valid answer for one version may be incorrect for another.

Always establish context such as:

```text
Tool:
Version:
Operating System:
Provider:
Environment:
Relevant Configuration:
```

Version context becomes especially important with:

- cloud services
- Kubernetes
- Terraform providers
- CI/CD platforms
- programming runtimes
- package managers
- APIs

---

# 9.5 AI Can Misunderstand Architecture

Suppose you ask:

> Why can't my application connect to the database?

Without architecture context, AI might assume:

```text
Application
↓
Database
```

But the real path might be:

```text
Application
↓
Service Discovery
↓
Proxy
↓
Private Network
↓
Managed Database Endpoint
```

The quality of the diagnosis depends on the quality of the system context and evidence available.

---

# 9.6 AI Can Recommend Unsafe Commands

Consider a hypothetical suggestion:

```text
Delete the resource and recreate it.
```

Before doing anything, ask:

```text
What state does the resource contain?
What depends on it?
Will deletion destroy data?
How is it recreated?
Will the identity remain the same?
What is the downtime?
Is there a backup?
Has restoration been tested?
Is deletion authorized?
```

A technically valid command can still be operationally dangerous.

---

# 9.7 Sensitive Information and AI

Do not carelessly paste sensitive production information into AI systems.

Potentially sensitive information includes:

- passwords
- tokens
- private keys
- customer data
- private certificates
- internal credentials
- sensitive logs
- connection strings containing credentials

Follow your organization's approved data-handling rules and the controls of the AI system being used.

When possible, remove or replace sensitive values while preserving useful diagnostic structure.

Instead of:

```text
password=RealProductionPassword123
```

use something like:

```text
password=<REDACTED>
```

when the actual value is unnecessary for diagnosis.

---

# 9.8 AI and Automation Increase Blast Radius

An AI system that only explains an error has limited direct authority.

An AI agent that can:

- modify repositories
- execute shell commands
- access cloud APIs
- read secrets
- deploy applications
- change infrastructure

has much greater capability.

Greater capability requires stronger controls.

Modern agent guidance emphasizes guardrails, access control, approval for sensitive actions, auditability, and isolated execution where appropriate.

At junior level, remember:

```text
AI Capability
≠
AI Authority
```

---

# 9.9 A Safe AI-Assisted Engineering Pattern

Use this pattern:

```text
Problem
   ↓
Gather Context
   ↓
Gather Evidence
   ↓
Ask AI for Explanation / Hypotheses
   ↓
Inspect AI Assumptions
   ↓
Verify Against System and Documentation
   ↓
Test Safely
   ↓
Perform Approved Change
   ↓
Verify Result
```

Do not use:

```text
Problem
   ↓
Ask AI
   ↓
Copy Command
   ↓
Paste Into Production
```

# 10. EVIDENCE BEFORE ACTION

This is one of the most important sections in the entire curriculum.

You will use this reasoning pattern repeatedly.

---

# 10.1 Step 1: Observe

Start with what is actually known.

Example:

```text
Users report that checkout is failing.
```

Do not immediately convert this into:

```text
The database is down.
```

The first is an observation.

The second is a hypothesis.

---

# 10.2 Step 2: Define the Symptom Precisely

Replace vague statements.

Instead of:

> Website broken.

Ask:

```text
Which URL?

Which environment?

Which users?

What response?

What error?

When did it begin?

Is it constant or intermittent?

Is the whole site affected?

Is only one feature affected?
```

Precision reduces the search space.

---

# 10.3 Step 3: Determine Scope

Ask:

```text
One user?
Some users?
All users?

One endpoint?
One service?
Entire application?

One instance?
One zone?
One region?
All environments?
```

Scope is evidence.

If development works but production fails, that matters.

If only one application instance fails, that matters.

If all services fail simultaneously, that matters.

---

# 10.4 Step 4: Establish Expected State

You cannot identify abnormal behavior without understanding normal behavior.

Ask:

```text
What should happen?
```

Example:

```text
Expected:
GET /health returns HTTP 200.
```

Then compare:

```text
Observed:
GET /health returns HTTP 503.
```

Now you have a measurable difference.

---

# 10.5 Step 5: Gather Evidence

Evidence might include:

- logs
- metrics
- process state
- application response
- deployment history
- configuration
- events
- network observations
- pipeline history
- infrastructure state

The specific evidence depends on the system.

---

# 10.6 Step 6: Identify the Likely Layer

Use evidence to narrow the investigation.

```text
User
 ↓
DNS
 ↓
Network
 ↓
Load Balancer
 ↓
Application
 ↓
Dependency
```

Do not randomly jump between layers.

---

# 10.7 Step 7: Form a Hypothesis

A hypothesis is a testable explanation.

Example:

```text
Hypothesis:

The application is returning errors because it cannot
establish connections to the database.
```

A hypothesis is not yet root cause.

---

# 10.8 Step 8: Test Safely

Ask:

```text
What evidence would support this hypothesis?

What evidence would disprove it?

Can I test without changing production?
```

Prefer observation before modification when possible.

---

# 10.9 Step 9: Make the Smallest Justified Change

Once evidence supports a corrective action, make the smallest safe change consistent with:

- permissions
- approvals
- runbooks
- organizational process

Avoid changing five unrelated things simultaneously.

If five variables change and the system recovers, you may not know which change mattered.

---

# 10.10 Step 10: Verify

Never stop at:

```text
Command succeeded.
```

Verify:

```text
Did the expected state change?

Did the original symptom disappear?

Are users recovering?

Are errors decreasing?

Did we introduce another problem?
```

The complete pattern is:

```text
Action
   ↓
Expected State
   ↓
Inspection
   ↓
Evidence
   ↓
Conclusion
```

# 11. SYMPTOM, EVIDENCE, HYPOTHESIS, AND ROOT CAUSE

These concepts must remain separate.

## Symptom

What appears wrong.

Example:

```text
Checkout requests fail.
```

## Evidence

What was observed.

Example:

```text
Application logs show connection timeouts.
```

## Hypothesis

A possible explanation.

Example:

```text
The application may be unable to reach the database.
```

## Root Cause

The underlying condition that explains the failure after investigation.

Example:

```text
A network policy change blocked application traffic
to the database endpoint.
```

The chain might be:

```text
Root Cause
Network policy blocks traffic
        ↓
Intermediate Failure
Database connection attempts time out
        ↓
Application Behavior
Checkout API returns errors
        ↓
User Symptom
Checkout fails
```

This is why:

```text
"Checkout is broken"
```

is not a root cause.

# 16. TROUBLESHOOTING EXERCISE: "THE WEBSITE IS DOWN"

This is the main troubleshooting exercise for Part 1.

---

# 16.1 The Initial Report

You receive:

> The website is down.

Do not restart anything.

Do not redeploy anything.

Do not clear anything.

Do not change DNS.

Do not delete anything.

Do not immediately ask AI for a repair command.

First determine what the statement actually means.

---

# 16.2 Define "Down"

Possible meanings include:

```text
Browser cannot resolve hostname
Browser times out
Connection is refused
TLS warning appears
HTTP 404
HTTP 403
HTTP 500
HTTP 502
HTTP 503
Page loads but API fails
Login fails
Checkout fails
Website is extremely slow
Only some users are affected
```

These are different symptoms.

They suggest different investigation paths.

---

# 16.3 Establish Scope

Ask:

```text
One user or everyone?

One geographic location or all?

One page or whole site?

One environment or all?

One application version or all?

Constant or intermittent?
```

---

# 16.4 Establish Time

Ask:

```text
When did this begin?

Was it sudden?

Was it gradual?

Did anything change around that time?
```

Time correlation can be valuable evidence.

But correlation is not automatically causation.

If a deployment occurred at 14:00 and the outage began at 14:01, investigate the deployment.

Do not automatically declare it the root cause.

---

# 16.5 Build the Failure Layers

Start with:

```text
User
 ↓
DNS
 ↓
Network
 ↓
External Entry Point
 ↓
Application
 ↓
Dependency
```

Possible failure categories:

### User / Client

- local connectivity
- incorrect URL
- client-specific issue

### DNS

- hostname not resolving
- incorrect record

### Network

- unreachable path
- blocked traffic

### External Entry

- load balancer problem
- proxy problem
- TLS problem

### Application

- process stopped
- startup failure
- runtime error
- bad configuration

### Dependency

- database unavailable
- API unavailable
- authentication dependency unavailable
- storage unavailable

The exact architecture determines the real layers.

---

# 16.6 Example Investigation A: DNS Failure

Observed:

```text
User cannot resolve bookstore.example.
```

Application status:

```text
Healthy.
```

The website can still be "down" from the user's perspective.

Restarting the application would not fix DNS.

This demonstrates:

```text
User Symptom
does not automatically identify
Failure Layer
```

---

# 16.7 Example Investigation B: Application Failure

Observed:

```text
DNS resolves.

Network endpoint responds.

Load balancer reports no healthy backend.

Application process repeatedly exits.
```

Now evidence points toward the application/runtime layer.

DNS changes would be unjustified.

---

# 16.8 Example Investigation C: Dependency Failure

Observed:

```text
Application running.

Health endpoint responds.

Login works.

Checkout returns HTTP 500.

Application logs show payment API timeout.
```

The entire website is not actually down.

A specific business function is failing because of a dependency path.

Precision changes the investigation.

---

# 16.9 Example Investigation D: Deployment Correlation

Observed:

```text
14:00 Deployment starts
14:04 Deployment completes
14:05 Error rate rises sharply
14:06 Users report failures
```

A reasonable hypothesis is:

```text
The new deployment may have introduced the failure.
```

That is stronger than random guessing because the timing supports investigation.

But verify:

- what changed
- whether all instances received the change
- whether errors appear only on the new version
- whether rollback is defined
- whether another dependency changed simultaneously

---

During investigation, maintain something like:


# 18. READ-ONLY BEFORE STATE-CHANGING

When investigating production, distinguish two broad categories of action.

## Read / Inspect

Examples conceptually include:

```text
View logs
Inspect configuration
Check status
View metrics
Review recent changes
Inspect deployment history
```

These actions are generally intended to gather information.

## State-Changing

Examples include:

```text
Restart service
Change configuration
Deploy version
Delete resource
Modify firewall
Rotate credential
Scale workload
```

State-changing actions alter the system.

The exact risk depends on the action and environment.

A useful default troubleshooting habit is:

```text
Inspect First
Change Second
```

unless an established emergency procedure requires immediate mitigation.

# 19. CHANGE CONTROL IS NOT BUREAUCRACY BY DEFAULT

Junior engineers sometimes see review and approval as obstacles.

Consider why they exist.

A production change may affect:

- thousands of users
- business transactions
- sensitive data
- security
- dependent services

A second engineer reviewing a change may catch:

- incorrect environment
- wrong variable
- excessive permissions
- destructive operation
- missing rollback
- incomplete testing

Controls should be proportionate to risk.

But the underlying idea is important:

```text
High-Impact Change
should not depend entirely on
one person's confidence.
```

This principle also applies to automated systems and AI agents.

---

# 20. PRODUCTION SYSTEMS REQUIRE TRUST BOUNDARIES

Every system contains boundaries around authority.

Consider:

```text
Developer
   │
   ▼
Git Repository
   │
   ▼
CI/CD
   │
   ▼
Cloud / Kubernetes
   │
   ▼
Production
```

Ask:

```text
Who can push code?

Who can approve code?

Who can trigger a deployment?

What identity does the pipeline use?

What can that identity access?

Can the pipeline read secrets?

Can it modify production?

Can untrusted input reach privileged execution?
```

These are not abstract security questions.

CI/CD systems often hold significant authority. GitHub's current security guidance, for example, emphasizes least-privilege workflow credentials and warns that untrusted input or untrusted code can become dangerous when executed in privileged workflow contexts.

You do not need to configure these controls yet.

You need to understand why the boundaries exist.

# 21. COMMON JUNIOR ENGINEERING MISTAKES

## Mistake 1: Memorizing Commands Without Understanding State

Bad:

```text
I know the restart command.
```

Better:

```text
I know what component I am restarting,
why I believe restarting it is justified,
what state will be lost,
what depends on it,
and how I will verify recovery.
```

---

## Mistake 2: Treating the First Error as Root Cause

Bad:

```text
Connection refused.
Therefore the network is broken.
```

Better:

```text
Connection refused is evidence.
What component refused the connection?
Was anything listening?
Was the destination correct?
```

---

## Mistake 3: Changing Production Before Gathering Evidence

A change can destroy useful evidence.

For example, restarting a process may clear transient state or alter logs and timestamps.

Gather relevant evidence first when circumstances allow.

---

## Mistake 4: Copying AI Commands Directly

Never confuse:

```text
AI generated it
```

with:

```text
I understand and have verified it.
```

---

## Mistake 5: Assuming a Green Pipeline Means a Healthy Service

Always separate:

```text
Build Success
Test Success
Deployment Success
Application Health
User Success
```

They are related.

They are not identical.

---

## Mistake 6: Assuming "Running" Means "Healthy"

A process can exist while:

- deadlocked
- unable to reach dependencies
- returning errors
- serving extremely slowly
- using incorrect configuration

Existence is not health.

---

## Mistake 7: Hiding Uncertainty

If you do not know, say what you know and what you do not know.

Good:

```text
I confirmed the application instances are running,
but I have not yet confirmed database connectivity.
```

Poor:

```text
Everything looks fine.
```

when only one layer was checked.

---

## Mistake 8: Escalating Without Evidence

Avoid:

> Kubernetes problem. Please check.

Prefer:

```text
Production checkout Pods are running,
but requests return HTTP 500.

The errors began at 16:20 UTC.

Application logs show connection timeouts to the payment dependency.

No deployment occurred during the previous hour.

The issue is affecting all tested replicas.

I need assistance investigating the downstream dependency.
```

---

# 22. A JUNIOR ENGINEER'S FIRST PRODUCTION DECISION FRAMEWORK

Before performing a production action, ask:

```text
1. What exactly is the problem?

2. What environment am I in?

3. What is the expected state?

4. What is the observed state?

5. What evidence do I have?

6. What layer appears affected?

7. What hypothesis am I testing?

8. Is the proposed action read-only or state-changing?

9. What permissions do I have?

10. Is approval required?

11. What is the blast radius?

12. Can the action be reversed?

13. What will I check afterward?

14. If I am wrong, what happens?

15. Should I escalate instead?
```

If you cannot answer several of these questions, that is useful information.

You may not yet have enough evidence to act.

---

# 23. AI DECISION FRAMEWORK FOR THE JUNIOR ENGINEER

Before executing something suggested by AI, ask:

```text
Did I give the AI enough context?

Did it assume technologies I did not mention?

Did it assume a version?

Does the command actually exist?

Does the flag actually exist?

Is the configuration valid for my version?

Is this recommendation read-only?

Will it change state?

Could it destroy data?

Could it expose a secret?

What permissions does it require?

What resources could it affect?

What official documentation supports it?

Can I test it safely first?

How will I verify the result?
```

If you cannot answer these questions, do not convert the AI answer directly into a production action.

# 24. ENGINEERING EXERCISE: CLASSIFY THE STATEMENT

For each statement determine whether it is:

```text
Symptom
Evidence
Hypothesis
Action
Verification
```

### Statement A

> Users receive HTTP 503 responses.

Answer:

```text
Symptom / observed evidence
```

### Statement B

> The application may have no healthy backend instances.

Answer:

```text
Hypothesis
```

### Statement C

> The load balancer reports zero healthy targets.

Answer:

```text
Evidence
```

### Statement D

> Roll back the latest approved release.

Answer:

```text
Action
```

### Statement E

> After rollback, successful requests returned to normal and error rate returned to baseline.

Answer:

```text
Verification evidence
```

This distinction should eventually become automatic.

# 25. ENGINEERING EXERCISE: WHAT DO YOU KNOW?

Scenario:

```text
Alert:
CPU above 90% for five minutes.
```

What do you know?

You know:

```text
The monitored CPU signal exceeded the configured threshold.
```

What do you not yet know?

You do not necessarily know:

```text
Why CPU is high.

Which process is responsible.

Whether users are affected.

Whether high CPU is expected.

Whether CPU is the bottleneck.

Whether restarting anything is appropriate.

Whether the application is unhealthy.
```

This exercise captures the central philosophy of this Part:

```text
Evidence should constrain conclusions.
```

# 26. PRODUCTION THINKING: ASK WHAT HAPPENS NEXT

For every component, practice asking:

```text
What happens next?
```

Example:

```text
Developer pushes code.
```

What happens next?

```text
Repository records change.
```

What happens next?

```text
Pipeline may run.
```

What happens next?

```text
Tests execute.
```

What happens next?

```text
Artifact is created.
```

What happens next?

```text
Artifact may be deployed.
```

What happens next?

```text
Runtime starts application.
```

What happens next?

```text
Traffic reaches application.
```

What happens next?

```text
Application calls dependencies.
```

What happens next?

```text
Response returns to user.
```

Now reverse it during an incident.

```text
User request failed.
```

Ask:

```text
Where did the request travel?

Which layers succeeded?

Where is the first observed failure?

What evidence proves that?
```

That is the beginning of production troubleshooting.

# 27. THE JUNIOR ENGINEER'S RELATIONSHIP WITH DOCUMENTATION

Documentation should be used actively.

When you encounter an unfamiliar command, configuration field, or API:

1. identify the technology
2. identify the version when relevant
3. find authoritative documentation
4. understand the operation
5. compare documentation with your environment
6. test appropriately
7. record useful findings

AI can help explain documentation.

AI should not replace the need to verify version-sensitive or consequential technical behavior.

# 29. PART 1 PRACTICAL ASSESSMENT

You are given this incident report:

```text
Production is broken after deployment.
```

Before touching the system, write down the questions you need answered.

A strong response should investigate at least:

### Environment

```text
Which production environment?
```

### Symptom

```text
What exactly is failing?
```

### Scope

```text
Who is affected?
Which endpoints?
Which services?
```

### Time

```text
When did the failure begin?
```

### Change

```text
What deployment occurred?
What changed?
```

### Delivery

```text
Did the pipeline actually complete?
Which version was deployed?
```

### Runtime

```text
Is the application running?
Is it healthy?
```

### Network

```text
Can traffic reach the application?
```

### Dependencies

```text
Can the application reach what it depends on?
```

### Evidence

```text
What do logs, metrics, alerts, and deployment history show?
```

### Recovery

```text
Is there an approved rollback path?
```

### Authority

```text
Am I authorized to perform the required action?
```

### Verification

```text
How will we know service has actually recovered?
```

If your first instinct was simply:

```text
kubectl rollout restart ...
```

or:

```text
restart the server
```

then return to the evidence-before-action framework.

The tool comes after the diagnosis.
