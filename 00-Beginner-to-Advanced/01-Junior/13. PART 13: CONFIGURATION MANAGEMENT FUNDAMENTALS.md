# PART 13: CONFIGURATION MANAGEMENT FUNDAMENTALS

## Goal

Understand why configuration management exists and how repeatable server configuration differs from ad hoc remote commands.

By the end of this Part, the learner should understand that creating infrastructure is only the beginning of operating a system.

Terraform might create:

```text
Virtual Machine
```

but the machine may still need:

```text
Users
Packages
Directories
Configuration Files
Permissions
Services
Application Settings
Security Configuration
```

Without configuration management, engineers often perform those operations manually:

```text
SSH to Server
      ↓
Run Commands
      ↓
Edit Files
      ↓
Install Packages
      ↓
Restart Services
      ↓
Repeat on Next Server
```

That can work for one machine.

It becomes increasingly unreliable as the number of machines, environments, engineers, and configuration requirements increases.

Configuration management introduces a different model:

```text
Desired Configuration
        ↓
Configuration Management
        ↓
Managed Nodes
        ↓
Packages
        ↓
Users
        ↓
Files
        ↓
Services
        ↓
Expected State
        ↓
Verification
```

Using Ansible as the primary practical example, the learner will develop this operational model:

```text
Inventory
    ↓
Target Hosts
    ↓
Variables
    ↓
Playbook
    ↓
Tasks
    ↓
Modules
    ↓
Managed Nodes
    ↓
Observed Changes
    ↓
Verification
```

The central engineering principle of this Part is:

> Configuration management is not simply remote command execution. It is a controlled way to describe, apply, verify, and repeatedly maintain intended system configuration.

The learner should also understand:

```text
Infrastructure Exists
≠
Infrastructure Is Correctly Configured
```

and:

```text
Playbook Completed
≠
Application Is Healthy
```

and:

```text
changed=0
≠
Everything About The Server Is Correct
```

Ansible can only enforce and report the configuration represented by the automation it actually manages.

---

# 1. THE PROBLEM AFTER INFRASTRUCTURE CREATION

In Part 12, Terraform introduced the model:

```text
Configuration
    ↓
Terraform
    ↓
Provider
    ↓
Infrastructure API
    ↓
Resource
```

Suppose Terraform creates three Linux servers:

```text
web01
web02
web03
```

The servers exist.

But the application requires:

```text
nginx installed

application user created

configuration file deployed

application directory created

service enabled

service running
```

Someone must configure those machines.

---

# 2. THE MANUAL CONFIGURATION APPROACH

An engineer might connect manually:

```bash
ssh engineer@web01
```

Then run commands such as:

```bash
sudo apt update
sudo apt install nginx
sudo useradd ...
sudo mkdir ...
sudo cp ...
sudo systemctl enable ...
sudo systemctl start ...
```

Then repeat the process on:

```text
web02

web03
```

This can work.

But now ask:

```text
Did every server receive exactly the same configuration?

Did someone forget one command?

Were the same package versions available?

Were permissions identical?

Was the same configuration file deployed?

Did every service restart?

Did one engineer use a different command?

Can we reproduce the procedure tomorrow?

Can another engineer review the intended configuration?

Can we prove what each server should contain?
```

This is the problem configuration management addresses.

---

# 3. MANUAL COMMANDS DO NOT AUTOMATICALLY REPRESENT DESIRED STATE

Suppose an engineer runs:

```bash
sudo systemctl start nginx
```

That tells the system:

```text
Perform this operation now.
```

It does not necessarily express the broader configuration requirement:

```text
nginx should be installed

nginx should use this configuration

nginx should be enabled

nginx should be running
```

Configuration management encourages engineers to describe intended state more explicitly.

---

# 4. AD HOC REMOTE COMMANDS

An ad hoc command is a command executed for an immediate task rather than represented as reusable configuration automation.

Conceptually:

```text
Engineer
   ↓
Remote Command
   ↓
Server
   ↓
Immediate Result
```

Ad hoc commands can be useful for:

```text
inspection

diagnostics

one-time checks

controlled operational actions
```

But repeated configuration should generally become reproducible automation.

---

# 5. THE COPY-PASTE SERVER PROBLEM

Imagine configuring ten servers.

You copy:

```text
Command A
Command B
Command C
Command D
```

onto every host.

One host receives:

```text
A
B
C
D
```

Another receives:

```text
A
B
D
```

Another receives:

```text
A
B
C
D
E
```

Now the servers are not configured consistently.

This is configuration divergence.

---

# 6. CONFIGURATION DRIFT

Configuration drift occurs when the actual configuration of a managed system diverges from the intended configuration.

Example:

Desired:

```text
nginx worker_connections = 1024
```

Actual on `web01`:

```text
1024
```

Actual on `web02`:

```text
4096
```

Actual on `web03`:

```text
1024
```

If all three are supposed to be identical, `web02` has drifted.

---

# 7. HOW CONFIGURATION DRIFT HAPPENS

Drift can result from:

```text
manual edits

emergency changes

one-off troubleshooting

package changes

different installation procedures

scripts run on only some hosts

incorrect automation

partial automation failure

unauthorized changes

configuration copied from another environment
```

Drift is not always malicious.

It is often operational history accumulating on systems.

---

# 8. DRIFT EXAMPLE

Desired configuration:

```text
/etc/veriqta/app.conf
```

should contain:

```text
environment=lab
port=8080
```

Someone logs into one server and changes:

```text
port=9090
```

Now:

```text
Desired Configuration
        ↓
port=8080
```

but:

```text
Actual Configuration
        ↓
port=9090
```

That is drift.

---

# 9. DRIFT CAN CREATE DIFFICULT INCIDENTS

Suppose:

```text
web01 works

web02 works

web03 fails
```

The servers are assumed to be identical.

But `web03` contains a manual configuration change made three months ago.

Now troubleshooting becomes harder because:

```text
Same Application
+
Apparently Same Infrastructure
+
Different Configuration
=
Different Behavior
```

Configuration consistency reduces this class of uncertainty.

---

# 10. DESIRED CONFIGURATION

Desired configuration describes what the managed system should look like.

For example:

```text
Package:
nginx installed

User:
veriqta exists

Directory:
/opt/veriqta exists

Configuration:
/etc/nginx/conf.d/veriqta.conf contains approved content

Service:
nginx enabled and running
```

This becomes the intended state.

---

# 11. DESIRED STATE MENTAL MODEL

Think:

```text
Desired Configuration
        ↓
Inspect Current State
        ↓
Difference?
      ↙     ↘
    Yes      No
     ↓        ↓
Change      Leave
     ↓
Verify
```

A well-designed configuration-management task should avoid unnecessary changes when the desired state already exists.

---

# 12. CONFIGURATION MANAGEMENT

Configuration management is the controlled management of system configuration so that machines can be brought toward an intended state repeatedly and predictably.

Typical configuration-management responsibilities include:

```text
package installation

user management

directory creation

file deployment

permissions

service management

application configuration

scheduled tasks

selected security configuration
```

---

# 13. CONFIGURATION MANAGEMENT IS NOT ONLY INSTALLATION

A weak mental model is:

```text
Ansible installs packages.
```

A stronger model is:

```text
Ansible can express and enforce selected desired system configuration.
```

Installation is only one use case.

---

# 14. CONFIGURATION MANAGEMENT VERSUS PROVISIONING

The boundary is not absolute, because tools can overlap.

But a useful beginner model is:

```text
Terraform
→ creates/manages infrastructure resources
```

```text
Ansible
→ configures systems and software
```

Example:

```text
Terraform
    ↓
Create Linux VM
    ↓
Ansible
    ↓
Install nginx
    ↓
Create user
    ↓
Deploy configuration
    ↓
Start service
```

This distinction is conceptual rather than an absolute technical limitation.

---

# 15. TOOL CAPABILITIES CAN OVERLAP

Terraform can perform some configuration-related operations.

Ansible can provision some infrastructure resources through collections and modules.

Therefore:

```text
Terraform = Infrastructure Only
Ansible = Servers Only
```

is too rigid.

The architectural question is:

```text
Which tool should own which state?
```

For this Junior Part, the practical boundary is:

```text
Terraform
→ infrastructure lifecycle

Ansible
→ operating-system and service configuration
```

---

# 16. OWNERSHIP MATTERS

Avoid having several tools independently manage the same configuration without a deliberate design.

For example:

```text
Ansible manages /etc/nginx/nginx.conf

Shell script also modifies /etc/nginx/nginx.conf

Cloud-init also modifies /etc/nginx/nginx.conf

Engineer manually modifies /etc/nginx/nginx.conf
```

Now multiple actors can fight over the same state.

Ask:

```text
Who owns this configuration?
```

---

# 17. ANSIBLE

Ansible is an automation system commonly used for:

```text
configuration management

application deployment

orchestration

system administration

repeatable operational tasks
```

Ansible playbooks provide repeatable configuration and multi-machine automation, with plays containing ordered tasks that invoke modules.

---

# 18. THE ANSIBLE CONTROL NODE

The machine from which Ansible runs is commonly called the:

```text
control node
```

Conceptually:

```text
Control Node
     ↓
Ansible
     ↓
Managed Nodes
```

The control node contains things such as:

```text
Ansible installation

inventory

playbooks

templates

variables

configuration
```

---

# 19. MANAGED NODES

The systems Ansible targets are managed nodes, commonly called hosts.

Example:

```text
Control Node
      │
      ├── web01
      ├── web02
      └── web03
```

Ansible's inventory identifies the managed nodes available to automation.

---

# 20. ANSIBLE AND AGENTS

For normal Linux SSH-based Ansible operation, Ansible does not require a continuously running Ansible agent on every managed node.

A common path is:

```text
Control Node
      ↓
SSH
      ↓
Managed Linux Host
      ↓
Execute Required Module Work
```

This differs from configuration-management systems that rely on persistent agents.

---

# 21. AGENTLESS DOES NOT MEAN REQUIREMENT-FREE

The managed node still needs whatever is required by the selected:

```text
connection method

module

platform

authentication method
```

For typical Linux automation, requirements commonly include:

```text
network connectivity

SSH access

valid authentication

appropriate permissions

Python for many Ansible modules
```

Exact requirements depend on the module, connection plugin, platform, and Ansible version.

---

# 22. ANSIBLE CONNECTION MODEL

For ordinary Linux management, the practical model is:

```text
Ansible Control Node
        ↓
Inventory
        ↓
Target Selection
        ↓
SSH Connection
        ↓
Remote User
        ↓
Privilege Escalation If Required
        ↓
Task Execution
```

SSH is the normal/default connection path for many Unix-like managed nodes.

---

# 23. INVENTORY

Inventory describes the hosts Ansible can manage.

It can define:

```text
hosts

groups

host variables

group variables

connection information
```

Inventory can come from static files or dynamic sources.

---

# 24. INVENTORY IS NOT JUST A LIST OF IP ADDRESSES

A useful inventory may represent relationships.

Example:

```text
all
├── web
│   ├── web01
│   └── web02
└── database
    └── db01
```

This allows automation to target:

```text
all hosts

web hosts

database hosts

one specific host
```

---

# 25. INVENTORY GROUPS

Groups allow related systems to be targeted together.

Example:

```ini
[web]
web01
web02

[database]
db01
```

Now:

```text
web
```

represents:

```text
web01
web02
```

Ansible supports host and group targeting through inventory patterns.

---

# 26. INVENTORY ALIASES

Inventory names do not always have to be DNS hostnames.

Conceptually:

```yaml
web:
  hosts:
    web01:
      ansible_host: 192.0.2.10
```

Here:

```text
web01
```

is the inventory host name.

The actual connection destination is represented separately.

---

# 27. CONNECTION VARIABLES

Common connection information can include concepts such as:

```text
target hostname/address

SSH user

SSH port

connection type
```

For example, Ansible documents variables including:

```text
ansible_host

ansible_port

ansible_user
```

for common connection configuration.

---

# 28. DO NOT PUT SECRETS DIRECTLY INTO PUBLIC INVENTORY

Bad:

```yaml
web01:
  ansible_password: SuperSecretPassword123
```

in a public repository.

Inventory is configuration.

It is not automatically a secure secret store.

---

# 29. STATIC INVENTORY

Static inventory explicitly defines hosts.

Example conceptual structure:

```yaml
all:
  children:
    web:
      hosts:
        web01:
        web02:
```

This works well for a stable learning environment.

---

# 30. DYNAMIC INVENTORY

In cloud environments, hosts may appear and disappear frequently.

A static list can become stale.

Dynamic inventory can obtain host information from external systems such as cloud platforms or inventory services.

Current Ansible documentation recommends inventory plugins over older inventory scripts for dynamic inventory integrations.

At Junior level, start with static inventory.

---

# 31. INSPECT INVENTORY BEFORE AUTOMATING

Do not assume Ansible interpreted inventory the way you intended.

Use:

```bash
ansible-inventory -i inventory.yml --graph
```

This asks Ansible to display the inventory structure it sees.

Expected:

```text
The intended groups and hosts appear.
```

---

# 32. INVENTORY INSPECTION IS EVIDENCE

If:

```text
web02
```

does not appear in the inventory graph, do not troubleshoot the playbook first.

The target model itself is wrong or incomplete.

---

# 33. TARGET PATTERNS

Ansible uses patterns to select hosts from inventory.

Examples include:

```text
all

web

web01
```

More advanced combinations exist, but the Junior engineer should first master explicit, predictable targeting.

---

# 34. TARGETING IS A SAFETY BOUNDARY

This is important.

A perfectly written playbook can still cause the wrong change if it targets:

```text
production
```

instead of:

```text
lab
```

Therefore always ask:

```text
Which hosts will this run against?
```

before asking:

```text
What tasks will it run?
```

---

# 35. BLAST RADIUS

Suppose:

```text
web
```

contains:

```text
2 hosts
```

and:

```text
all
```

contains:

```text
200 hosts
```

Changing:

```yaml
hosts: web
```

to:

```yaml
hosts: all
```

can dramatically increase blast radius.

A one-line automation change can have large operational impact.

---

# 36. LIMITING EXECUTION

Ansible supports:

```text
--limit
```

for narrowing playbook execution to selected inventory targets.

For example:

```bash
ansible-playbook -i inventory.yml site.yml --limit web01
```

This does not make an unsafe playbook safe.

It reduces the current target set.

---

# 37. VERIFY TARGETS BEFORE CHANGES

Before a consequential playbook run, establish:

```text
Which inventory?

Which group?

Which hosts?

Which environment?

Which user?

Which privilege level?
```

Never discover target scope after the run.

# 42. AD HOC ANSIBLE COMMANDS

Ansible supports one-off ad hoc operations.

General form:

```bash
ansible <pattern> -i <inventory> -m <module> -a '<arguments>'
```

Ad hoc commands are useful for:

```text
connectivity tests

inspection

small controlled operations
```

But repeatable configuration belongs in playbooks.

---

# 43. THE PING MODULE

A common first connectivity check is:

```bash
ansible all -i inventory.yml -m ansible.builtin.ping
```

Do not confuse this with ICMP `ping`.

Ansible's ping module tests whether Ansible can establish the required connection/execution path and receive a usable response from the managed node.

It is an Ansible execution test, not a general network ICMP test.

---

# 44. CONNECTIVITY TEST MENTAL MODEL

When:

```bash
ansible.builtin.ping
```

succeeds, you have evidence that:

```text
inventory target resolved

connection path worked

authentication worked sufficiently

required remote execution path worked
```

It does not prove:

```text
sudo works

package installation works

service configuration works

application is healthy
```

Keep conclusions bounded.

---

# 45. PLAYBOOKS

Playbooks represent repeatable automation.

Ansible playbooks are written in YAML.

A playbook contains one or more:

```text
plays
```

Each play targets hosts and contains tasks.

---

# 46. PLAYBOOK MENTAL MODEL

```text
Playbook
   ↓
Play
   ↓
Target Hosts
   ↓
Tasks
   ↓
Modules
   ↓
Managed Nodes
```

---

# 47. A BASIC PLAY

Conceptually:

```yaml
- name: Configure web servers
  hosts: web
  become: true

  tasks:
    - name: Ensure package is installed
      ansible.builtin.package:
        name: nginx
        state: present
```

This says:

```text
Target:
web group

Privilege:
escalate where configured/required

Desired package state:
nginx present
```

---

# 48. TASKS

A task describes one automation operation.

Example:

```yaml
- name: Ensure nginx is installed
  ansible.builtin.package:
    name: nginx
    state: present
```

The task name should explain intent.

Better:

```text
Ensure nginx is installed
```

than:

```text
Run package task
```

---

# 49. MODULES

Ansible modules perform specific operations.

Examples include modules for:

```text
packages

users

files

templates

services

commands

copies
```

The module provides the implementation for the operation.

---

# 50. FULLY QUALIFIED COLLECTION NAMES

Current Ansible documentation recommends using fully qualified collection names in playbooks.

For built-in modules this commonly looks like:

```text
ansible.builtin.package

ansible.builtin.user

ansible.builtin.template

ansible.builtin.service
```

This makes the module source explicit and avoids ambiguity between collections.

---

# 51. MODULES VERSUS RAW COMMANDS

Compare:

```yaml
- name: Install nginx
  ansible.builtin.command:
    cmd: apt-get install -y nginx
```

with a package-management module:

```yaml
- name: Ensure nginx is installed
  ansible.builtin.package:
    name: nginx
    state: present
```

The second expresses:

```text
Desired State:
package present
```

rather than:

```text
Run this command.
```

This distinction is fundamental.

---

# 52. COMMAND EXECUTION IS NOT AUTOMATICALLY IDEMPOTENT

A shell or command task may execute every time unless additional logic determines otherwise.

Example:

```bash
echo "configuration" >> /etc/example.conf
```

Run once:

```text
configuration
```

Run again:

```text
configuration
configuration
```

Run again:

```text
configuration
configuration
configuration
```

That is not convergent behavior.

---

# 53. IDEMPOTENCY

At a practical configuration-management level, idempotency means repeated application of the same desired configuration should not keep producing unnecessary changes after the target reaches that state.

Conceptually:

```text
First Run:
Current ≠ Desired
        ↓
Change
```

```text
Second Run:
Current = Desired
        ↓
No Change Required
```

---

# 54. IDEMPOTENCY IS CENTRAL TO CONFIGURATION MANAGEMENT

Suppose desired state is:

```text
User "veriqta" exists.
```

First run:

```text
User absent
   ↓
Create user
```

Second run:

```text
User already exists correctly
   ↓
No creation required
```

That is much safer than blindly executing:

```bash
useradd veriqta
```

every time.

---

# 55. IDEMPOTENCY DOES NOT MEAN EVERY TASK IS IDEMPOTENT

Not every module, command, external API, or custom operation behaves idempotently.

The engineer must understand the behavior of the selected module and arguments.

Do not assume:

```text
Written in Ansible
=
Automatically Idempotent
```

---

# 56. IDEMPOTENCY DOES NOT MEAN "NOTHING EVER CHANGES"

If desired state changes:

```text
version 1
```

to:

```text
version 2
```

Ansible should make a change.

Idempotency means unnecessary repeated changes stop once the target matches the new intended state.

---

# 57. CONVERGENCE

A useful concept is convergence.

```text
Current State
      ↓
Automation
      ↓
Desired State
```

If the host drifts later:

```text
Desired State
      ≠
Actual State
```

the next automation run can bring it back toward:

```text
Desired State
```

---

# 58. FIRST RUN VERSUS SECOND RUN

The first run answers:

```text
Can the playbook make the required changes?
```

The second run asks:

```text
Does the playbook recognize that those managed changes
are already satisfied?
```

Both are important tests.

---

# 59. PLAYBOOK EXECUTION ORDER

Within a play, tasks normally execute in their defined order, with Ansible applying each task to the selected hosts before proceeding according to its execution strategy.

For the Junior engineer, think:

```text
Task 1
  ↓
Task 2
  ↓
Task 3
```

Do not assume YAML task order is irrelevant.

---

# 60. TASK FAILURE

If a task fails for a host, later tasks normally stop for that host unless error-handling behavior changes that outcome.

Therefore:

```text
Playbook Failed
```

does not necessarily mean:

```text
Nothing Changed
```

Earlier tasks may already have succeeded.

---

# 61. CONFIGURATION MANAGEMENT IS NOT TRANSACTIONAL BY DEFAULT

Suppose:

```text
Task 1: Create user       ✓
Task 2: Install package   ✓
Task 3: Deploy config     ✗
Task 4: Start service     not reached
```

The host may now contain:

```text
user created

package installed

old configuration

service unchanged
```

Do not assume automatic rollback.

---

# 62. AFTER A FAILED PLAYBOOK

Ask:

```text
Which hosts succeeded?

Which hosts failed?

Which task failed?

Which previous tasks changed state?

What is the host's current state now?

What will happen if the playbook is rerun?
```

This is the correct operational response.

---

# 63. VARIABLES

Variables allow playbooks to represent differences between hosts or environments without duplicating entire playbooks.

Ansible variables can come from several locations, and Ansible applies precedence rules when multiple definitions exist.

---

# 64. VARIABLE EXAMPLE

Instead of:

```yaml
name: veriqta-lab
```

everywhere, define:

```yaml
app_name: veriqta-lab
```

Then reference:

```text
{{ app_name }}
```

where appropriate.

---

# 65. VARIABLES REPRESENT CONTROLLED DIFFERENCES

Examples:

```text
development port:
8080
```

```text
production port:
80
```

A shared template can use a variable rather than maintaining two unrelated configuration files.

---

# 66. VARIABLE SOURCES

Variables may come from:

```text
inventory

group variables

host variables

playbooks

included variable files

roles

command-line extra variables

registered results

facts
```

This flexibility is powerful.

It can also create confusion.

---

# 67. VARIABLE PRECEDENCE

If the same variable is defined in several places, Ansible uses precedence rules to determine the effective value.

A Junior engineer does not need to memorize the entire precedence system immediately.

But they must understand:

```text
Variable value seen in one file
≠
necessarily the final effective value
```

---

# 68. TROUBLESHOOTING VARIABLES

If:

```text
app_port
```

is unexpectedly:

```text
9090
```

instead of:

```text
8080
```

ask:

```text
Where is app_port defined?

Is it in inventory?

group_vars?

host_vars?

playbook vars?

extra vars?

another included file?
```

Do not edit the first occurrence you find without understanding precedence.

---

# 69. GROUP VARIABLES

Suppose all web hosts use:

```text
app_port: 8080
```

A group variable can represent that shared configuration.

Example project:

```text
group_vars/
└── web.yml
```

This separates data from playbook logic.

---

# 70. HOST VARIABLES

If one host legitimately differs, host-specific variables can represent that difference.

But excessive host-specific exceptions can be a warning sign.

Ask:

```text
Why is this host different?
```

before normalizing every drifted host as an intentional exception.

---

# 71. FACTS

Ansible can gather information about managed nodes.

Examples may include:

```text
operating system

architecture

network information

hostname

memory

interfaces
```

These values can influence automation.

---

# 72. FACTS ARE OBSERVED DATA

Think:

```text
Variables
→ values supplied to automation
```

```text
Facts
→ values discovered from managed systems
```

The distinction is useful even though both become available through Ansible's variable system.

---

# 73. TEMPLATES

Templates generate configuration files using variables.

Ansible commonly uses Jinja templating.

Conceptually:

```text
Template
   +
Variables
   ↓
Rendered File
   ↓
Managed Node
```

---

# 74. TEMPLATE EXAMPLE

Template:

```jinja2
server {
    listen {{ app_port }};
    server_name {{ server_name }};
}
```

Variables:

```yaml
app_port: 8080
server_name: lab.example.test
```

Rendered result:

```text
server {
    listen 8080;
    server_name lab.example.test;
}
```

---

# 75. WHY TEMPLATES EXIST

Without templates, engineers may maintain:

```text
nginx-dev.conf

nginx-test.conf

nginx-staging.conf

nginx-prod.conf
```

with nearly identical content.

Templates can separate:

```text
shared structure
```

from:

```text
environment-specific values
```

---

# 76. TEMPLATES CAN ALSO CREATE RISK

A bad variable can render a syntactically valid but operationally incorrect configuration.

Example:

```text
app_port = 99999
```

A template engine may happily render the text.

The application may reject it.

Therefore:

```text
Template Rendered Successfully
≠
Configuration Valid For Application
```

---

# 77. CONFIGURATION VALIDATION

Where the application provides a configuration-test command, use it.

Conceptually:

```text
Render Candidate Configuration
        ↓
Validate
        ↓
Deploy/Activate
        ↓
Restart/Reload
        ↓
Verify
```

This is safer than blindly deploying configuration and restarting a service.

---

# 78. HANDLERS

Handlers are tasks typically triggered by changes from other tasks.

Common example:

```text
Configuration Changed
        ↓
Notify Handler
        ↓
Restart/Reload Service
```

This avoids restarting a service when nothing relevant changed.

---

# 79. HANDLER MENTAL MODEL

Suppose:

```text
nginx configuration unchanged
```

Then:

```text
no restart required
```

But if:

```text
nginx configuration changed
```

then:

```text
notify restart handler
```

This connects configuration change to necessary service action.

---

# 80. BASIC HANDLER EXAMPLE

```yaml
tasks:
  - name: Deploy nginx configuration
    ansible.builtin.template:
      src: nginx.conf.j2
      dest: /etc/nginx/conf.d/veriqta.conf
      owner: root
      group: root
      mode: "0644"
    notify: Restart nginx

handlers:
  - name: Restart nginx
    ansible.builtin.service:
      name: nginx
      state: restarted
```

The handler runs when notified by a task that reports a change, subject to Ansible's handler execution rules.

---

# 81. HANDLERS REDUCE UNNECESSARY RESTARTS

Without a handler:

```text
Run Playbook
    ↓
Restart Service
```

every time.

With a handler:

```text
Configuration Changed?
       ↙      ↘
     Yes       No
      ↓         ↓
Restart      No Restart
```

This is operationally better for many service-management workflows.

---

# 82. RESTART VERSUS RELOAD

Some services support configuration reload without full restart.

Others require restart.

Do not assume:

```text
reload
```

and:

```text
restart
```

are equivalent.

Check the application's documented behavior.

```yaml
    name: nginx
    enabled: true
    state: started
```

This expresses:

```text

enabled
```

```text

```

Suppose the inventory contains:

```text

```

# 91. SECRETS AWARENESS

Configuration management often needs access to:

```text
API tokens

database passwords

service credentials

private keys

privilege escalation credentials
```

Do not place plaintext secrets into a public Git repository.

---

# 92. ANSIBLE VAULT

Ansible provides Vault functionality for encrypting variables and files.

It can help protect sensitive values stored with Ansible content.

But:

```text
Encrypted In Repository
≠
Secret Management Problem Completely Solved
```

Key handling, access control, rotation, auditability, and runtime exposure still matter.

---

# 93. DO NOT PUT VAULT PASSWORD NEXT TO VAULT DATA

This defeats much of the protection:

```text
repository/
├── secrets.yml
└── vault-password.txt
```

if both are committed and accessible to the same unauthorized reader.

Protect decryption credentials separately.

---

# 94. `no_log` AWARENESS

Sensitive task output may need protection from logs.

Ansible provides mechanisms such as:

```text
no_log
```

for suppressing task output where appropriate.

But suppressing output can also make troubleshooting harder.

Use it intentionally for genuinely sensitive operations.

---

# 95. LOGS MAY LEAK SECRETS

Secrets can appear through:

```text
debug output

failed commands

registered variables

template content

CI/CD logs

verbose Ansible output
```

Do not assume a secret is protected merely because the source variable was encrypted.

# 96. PRIVILEGE ESCALATION

Many configuration operations require elevated privileges.

Examples:

```text
install package

create system user

write /etc configuration

manage system service
```

Ansible supports privilege escalation commonly through:

```text

```

---

# 97. `become`

Example:

```yaml
- name: Configure web servers
  hosts: web
  become: true
```

This tells Ansible to use its configured privilege-escalation mechanism for tasks in that context.

It does not automatically mean:

```text
unlimited root access will work
```

The remote identity must be authorized for the configured escalation method.

---

# 98. `become` DOES NOT FIX SSH

The sequence is:

```text
Reach Host
    ↓
Authenticate
    ↓
Establish Session
    ↓
Privilege Escalation
```

If SSH authentication fails, privilege escalation has not yet become the relevant problem.

# 99. CONNECTION USER VERSUS BECOME USER

Distinguish:

```text
Connection identity
```

from:

```text
Escalated identity
```

Example:

```text
SSH as:
automation
```

then:

```text
become:
root
```

These are different security boundaries.

# 103. PLAYBOOK RECAP

```text

```

---

# 104. `ok`

Conceptually:

```text
Task completed without requiring a managed change
```

depending on the task/module behavior.

It does not necessarily mean:

```text

```

---

# 105. `changed`

Conceptually:

```text
Ansible reports that the task changed managed state.
```

On a first configuration run, this may be expected.

On every repeated run, unexpected repeated changes may indicate poor idempotency or unstable inputs.

---

# 106. `unreachable`

An unreachable result points toward the connection path.

Investigate:

```text

DNS

route

port

SSH

authentication

host availability
```

Do not begin by debugging the package task.

The task may never have executed.

---

# 107. `failed`

A failed task means Ansible reached a stage where the task did not complete successfully.

Investigate:

```text
task name

module

module arguments

remote error

permissions

input variables

application error
```

---

# 108. `skipped`

A task may be skipped because its conditions did not require execution.

Do not assume:

```text
skipped
=
failure
```

Inspect why the task was skipped.

# 174. HOST KEY VERIFICATION

SSH host-key verification protects against connecting to an unexpected host.

Do not permanently disable it merely because automation reports a host-key problem.

# 190. EXAMPLE: UNREACHABLE

Weak:

```text
Ansible is broken.
```

Better:

```text
lab-web01 is reachable through Ansible, while lab-web02
```

That is useful engineering communication.

# 191. EXAMPLE: PRIVILEGE FAILURE

Weak:

```text
sudo doesn't work.
```

Better:

```text
Ansible successfully authenticates to lab-web01 as the
automation user, but the package task fails when privilege
escalation is attempted. Non-privileged connectivity therefore
works; the escalation configuration and authorization need
investigation.
```

# 192. EXAMPLE: BAD VARIABLE

Weak:

```text
Ansible used the wrong port.
```

Better:

```text
The rendered nginx configuration contains port 9090 while
the group default is 8080. A host-specific variable overrides
the group value for lab-web02, so the effective variable
source is causing the difference.
```

```text
More Output
≠

```

Verbose output may also expose operational details.

Do not immediately run the most verbose possible command.

# 196. DO NOT INVENT MODULE PARAMETERS

If unsure whether a module supports:

```text
parameter X
```

do not guess.

Check:

```bash

```

Automation that "looks like Ansible" can still be invalid.

---

# 197. COMMAND VERSUS SHELL

Ansible provides ways to execute commands when necessary.

But do not use shell execution merely because you already know shell commands.

Prefer modules that express desired state when appropriate.

Use command execution when the operation genuinely requires it.

---

# 198. SHELL INJECTION AWARENESS

If variables are inserted into shell commands carelessly, unexpected characters can alter command behavior.

This connects directly to Part 7.

Configuration management does not remove shell-scripting risks if the playbook invokes a shell.

---

# 199. REPEATABILITY

Repeatability means another authorized engineer should be able to use the same automation against an equivalent target and obtain the intended configuration.

That requires more than having a playbook.

It also requires understanding:

```text
inventory

variables

dependencies

versions

credentials

target assumptions
```

---

# 200. REPRODUCIBILITY VERSUS IDEMPOTENCY

These concepts are related but different.

```text
Repeatability/Reproducibility
→ can the process consistently create the intended configuration?
```

```text
Idempotency
→ does rerunning against already-correct state avoid unnecessary change?
```

A system can fail one while appearing to satisfy the other.

---

# 201. PLAYBOOKS BELONG IN VERSION CONTROL

Ansible content should normally participate in the Git workflow from Part 6:

```text
Branch
   ↓
Playbook Change
   ↓
Diff
   ↓
Review
   ↓
Validation
   ↓
Controlled Execution
```

This provides change history and reviewability.

---

# 202. REVIEW THE DIFF BEFORE RUNNING

Before running a modified playbook:

```bash
git diff
```

Ask:

```text
Which tasks changed?

Which variables changed?

Which templates changed?

Which hosts could be affected?

Could a handler now restart services?

Could permissions change?

Could users be removed?

Could packages be removed?
```

---

# 203. SMALL YAML DIFF, LARGE BLAST RADIUS

A one-line change:

```yaml
hosts: lab
```

to:

```yaml
hosts: all
```

can change the target population dramatically.

Review infrastructure automation by impact, not line count.

---

# 204. DESTRUCTIVE DESIRED STATES

Configuration management can also express absence.

Examples conceptually include:

```text
package absent

user absent

file absent
```

These can be destructive operations.

Do not assume declarative automation is always additive.

---

# 205. USER DELETION CAN BE CONSEQUENTIAL

A task that removes a user may affect:

```text
running processes

file ownership

application access

SSH access

scheduled tasks

home-directory data
```

Review destructive desired states carefully.

---

# 206. PACKAGE REMOVAL CAN BE CONSEQUENTIAL

Removing one package may affect dependencies or application behavior.

Do not approve:

```text
state: absent
```

without understanding impact.

---

# 207. FILE REMOVAL CAN BE CONSEQUENTIAL

This:

```yaml
state: absent
```

on the wrong path can remove important configuration.

Variables used in paths deserve careful review.

---

# 208. AUTOMATION MULTIPLIES BLAST RADIUS

Manual mistake:

```text
one host affected
```

Automation mistake:

```text
every targeted host affected
```

Therefore automation requires stronger review, not weaker review.

---

# 209. SAFE ROLLOUT THINKING

For consequential changes, a useful pattern is:

```text
One Lab Host
    ↓
Verify
    ↓
Small Subset
    ↓
Verify
    ↓
Broader Group
```

At Junior level, understand the concept even if advanced rolling deployment design comes later.

---

# 210. USE `--limit` DELIBERATELY

A first execution can target:

```bash
ansible-playbook -i inventory.yml site.yml --limit lab-web01
```

Then verify.

After confidence is established, target the intended group.

This reduces initial blast radius.

---

# 211. LIMIT DOES NOT CHANGE THE PLAYBOOK

Remember:

```text
--limit
```

changes the selected target subset for that execution.

It does not rewrite:

```yaml
hosts:
```

inside the playbook.

Know both.

---

# 212. CHECK MODE IS NOT APPROVAL

A check-mode run can be useful evidence.

It is not human approval.

The engineer still needs to understand:

```text
targets

tasks

variables

expected changes

service impact
```

---

# 213. DIFF MODE MAY EXPOSE SENSITIVE DATA

Suppose a template contains:

```text
database password
```

Using:

```text
--diff
```

could expose sensitive configuration in terminal or CI logs.

Do not enable diff output blindly on secret-bearing files.

---

# 214. SECRETS AND TEMPLATES

If a secret must appear in a generated configuration file, consider:

```text
how source secret is protected

who can decrypt it

destination permissions

whether logs expose it

whether diff exposes it

how it is rotated
```

Secret handling spans the entire lifecycle.

---

# 215. FILE PERMISSIONS FOR SECRET CONFIGURATION

A generated file containing credentials should not automatically use:

```text
0644
```

The required mode depends on:

```text
service user

service group

operational access requirements
```

Use least privilege.

---

# 216. CONFIGURATION OWNERSHIP

For every managed file, understand:

```text
Who owns it?

Who reads it?

Who writes it?

Which automation manages it?

Which service consumes it?
```

This makes permission decisions explainable.

---

# 217. APPLICATION CONFIGURATION OWNERSHIP

Suppose:

```text
/etc/veriqta/app.conf
```

is managed by Ansible.

Engineers should not casually edit it manually and expect the change to persist.

A later Ansible run may restore the declared version.

This ownership should be documented.

---

# 218. COMMENTS FOR MANAGED FILES

Where appropriate, generated configuration can include a comment such as:

```text
Managed by Ansible.
Manual changes may be overwritten.
```

This helps humans understand ownership.

Do not add such comments where the file format does not support them.

---

# 219. DESIRED STATE MUST BE CORRECT

Configuration management can reliably enforce the wrong state.

Example:

```text
Desired configuration:
wrong port
```

Ansible can consistently deploy that wrong port to every server.

Therefore:

```text
Consistency
≠
Correctness
```

---

# 220. IDEMPOTENTLY WRONG

A playbook can be perfectly idempotent and still be wrong.

Example:

```text
All hosts consistently expose an insecure configuration.
```

Second run:

```text
changed=0
```

That does not make the design safe.

---

# 221. AUTOMATION SUCCESS IS NOT BUSINESS SUCCESS

A playbook can report:

```text
failed=0
```

while users still receive:

```text
HTTP 500
```

Automation verification must extend to the required system behavior.

---

# 222. CONFIGURATION MANAGEMENT AND OBSERVABILITY

After configuration changes, monitoring may reveal:

```text
error rate increased

latency increased

service restarts

memory increased

connections failed
```

Configuration deployment and operational observation belong together.

Deeper observability comes later in the curriculum.

---

# 223. CONFIGURATION MANAGEMENT AND INCIDENTS

During an incident, configuration management can help:

```text
inspect expected configuration

reapply known configuration

identify drift

perform controlled changes
```

But blindly rerunning automation during an incident can also worsen the situation.

Understand the current state first.

---

# 224. "RERUN ANSIBLE" IS NOT ROOT-CAUSE ANALYSIS

Bad incident response:

```text
Application broken
      ↓
Rerun playbook
```

Better:

```text
Application broken
      ↓
Identify failing layer
      ↓
Determine whether configuration is involved
      ↓
Compare desired and actual state
      ↓
Use automation deliberately if appropriate
```

---

# 225. CONFIGURATION MANAGEMENT AND IMMUTABLE INFRASTRUCTURE

Some architectures prefer replacing machine images rather than continuously modifying long-lived servers.

Configuration management can still be useful in:

```text
image building

bootstrap

specialized system configuration

legacy environments
```

Do not assume every architecture manages long-lived servers identically.

# 243. EXAMPLE ROOT CAUSE STATEMENT

```text
Symptom:
The playbook failed while configuring lab-web02.

Scope:
lab-web01 completed successfully; only lab-web02 failed.

Evidence:
SSH connectivity to lab-web02 succeeded, but the package task
failed during privilege escalation.

Root cause:
The lab automation user on lab-web02 did not have the intended
sudo authorization required for package installation.

Corrective action:
The lab host's approved privilege configuration was corrected.

Verification:
The playbook completed successfully on lab-web02, nginx was
active, the expected HTTP response was returned, and a second
playbook run produced no unexplained changes.
```

This is far more useful than:

```text
Fixed Ansible.
```

# 256. TROUBLESHOOTING MATRIX

| Symptom | First investigation area |
|---|---|
| Host missing from run | inventory, pattern |
| Host unreachable | address, route, SSH port |
| SSH authentication rejected | user, key, authentication |
| Host-key error | host identity, known_hosts |
| `become` fails | escalation configuration, authorization |
| Undefined variable | variable source, spelling, scope |
| Wrong variable value | precedence, group/host vars |
| Template fails | syntax, variable, source |
| Wrong rendered content | variables, template logic |
| Package task fails | package name, repositories, network, permissions |
| Service task fails | package, config, service name, logs |
| One host fails | host-specific differences |
| Every host fails | shared configuration/dependency |
| Task changes every run | idempotency, dynamic input, external drift |
| Handler runs every run | notifying task changes every run |
| Playbook fails midway | inspect completed tasks/current state |
| Playbook succeeds, app fails | service/application/network verification |
| Manual edit disappears | managed configuration restored |
| Wrong hosts changed | inventory/pattern/blast-radius failure |

# 265. CONTINUOUS RECONCILIATION AWARENESS

A traditional Ansible playbook generally changes systems when Ansible is run.

It is not automatically a continuously running reconciliation loop simply because the playbook is declarative.

Conceptually:

```text
Drift Occurs
    ↓
Nothing Automatically Happens
    ↓
Ansible Runs
    ↓
Drift Repaired
```

unless additional automation schedules or triggers Ansible.

---

# 266. THIS MATTERS

Suppose drift occurs at:

```text
02:00
```

and the next playbook run is:

```text
08:00
```

The system may remain drifted for six hours.

Configuration management architecture must consider:

```text
when reconciliation runs

who triggers it

how drift is detected
```

Advanced designs come later.

---

# 267. CONFIGURATION MANAGEMENT IS NOT MONITORING

Ansible can inspect state.

But it is not automatically your monitoring platform.

Monitoring answers questions such as:

```text

Is latency rising?

Is disk filling?
```

```text

```

Different tools may cooperate.

# 268. CONFIGURATION MANAGEMENT IS NOT SECRET MANAGEMENT
