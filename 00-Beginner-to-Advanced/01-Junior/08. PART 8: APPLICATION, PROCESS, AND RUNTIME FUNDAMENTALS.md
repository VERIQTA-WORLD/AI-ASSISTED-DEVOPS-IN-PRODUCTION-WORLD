# PART 8: APPLICATION, PROCESS, AND RUNTIME FUNDAMENTALS

## Goal

Understand what DevOps engineers are actually deploying and operating.

A DevOps engineer does not merely deploy "code."

What eventually runs in an environment is the result of a chain of transformations and dependencies:

```text
Source Code
    ↓
Dependencies
    ↓
Build
    ↓
Artifact
    ↓
Configuration
    ↓
Runtime
    ↓
Process
    ↓
Listening Endpoint
    ↓
Application Behavior
    ↓
Dependencies
    ↓
User-Visible Result
```

This Part builds the mental model required to distinguish:

```text
Source code exists
≠
Application is built

Build succeeded
≠
Application can start

Process exists
≠
Application is listening

Port is listening
≠
Application is healthy

Application responds
≠
Application dependencies are healthy

HTTP response received
≠
Correct application behavior

Deployment succeeded
≠
Users can successfully use the application
```

The learner will run a small application manually, inspect it from the operating-system and application perspectives, deliberately break it, and diagnose failures using evidence.

The central engineering question throughout this Part is:

> What exactly has been proven healthy, and what has not?

---

# 1. WHAT DEVOPS ENGINEERS ACTUALLY OPERATE

A developer may write:

```text
Python

Java

JavaScript

Go

C#

Ruby

PHP

Rust

or another language
```

But source code sitting inside a Git repository is not yet a running production application.

Something must transform and execute it.

Depending on the technology, that may involve:

```text
dependency resolution

compilation

transpilation

packaging

artifact creation

runtime installation

configuration injection

process creation

network binding

dependency connections

health verification
```

The DevOps engineer needs to understand enough of this lifecycle to determine where failure occurs.

---

# 2. THE APPLICATION DELIVERY CHAIN

Use this mental model:

```text
Developer
   ↓
Source Code
   ↓
Version Control
   ↓
Dependency Resolution
   ↓
Build / Package
   ↓
Artifact
   ↓
Deployment
   ↓
Configuration
   ↓
Runtime
   ↓
Process
   ↓
Socket / Port
   ↓
Application
   ↓
Dependencies
   ↓
User
```

Every arrow represents a possible failure boundary.

For example:

```text
Source → Build
```

may fail because a dependency cannot be resolved.

```text
Artifact → Runtime
```

may fail because the required runtime version is unavailable.

```text
Runtime → Process
```

may fail because configuration is invalid.

```text
Process → Port
```

may fail because the application never binds successfully.

```text
Port → Application
```

may fail because requests produce errors.

```text
Application → Database
```

may fail because the database is unavailable.

A strong troubleshooter determines which boundary is broken.

---

# 3. SOURCE CODE

Source code is the human-readable program definition written by developers.

Examples might include:

```text
app.py

main.go

server.js

Program.cs

Main.java
```

Source code describes application behavior.

It may define:

```text
HTTP routes

business logic

database operations

authentication

validation

logging

configuration handling

dependency calls

startup behavior

shutdown behavior
```

But source code alone is not a running application.

---

# 4. SOURCE CODE IS NOT A PROCESS

Suppose:

```text
/opt/veriqta/app.py
```

exists.

That proves:

```text
A file exists.
```

It does not prove:

```text
Python is installed.

Required dependencies exist.

Configuration is valid.

The program has started.

The process is still running.

A port is listening.

HTTP requests succeed.

The database is reachable.
```

Always keep evidence narrowly scoped.

---

# 5. DEPENDENCIES

Applications rarely contain every capability they require internally.

They commonly depend on libraries or packages.

Examples:

```text
Python packages

npm packages

Java libraries

Go modules

.NET packages

operating-system libraries
```

A dependency may provide functionality such as:

```text
HTTP handling

database drivers

JSON processing

authentication

logging

cryptography

cloud SDKs

metrics
```

---

# 6. DEPENDENCY DECLARATIONS

Different ecosystems describe dependencies differently.

Examples include files such as:

```text
requirements.txt

pyproject.toml

package.json

package-lock.json

go.mod

go.sum

pom.xml

build.gradle

*.csproj
```

The exact file depends on the application ecosystem.

Do not assume every application manages dependencies the same way.

---

# 7. DIRECT AND TRANSITIVE DEPENDENCIES

Suppose your application directly depends on:

```text
Library A
```

and Library A depends on:

```text
Library B
```

Then:

```text
Application
    ↓
Library A
    ↓
Library B
```

Library B is a transitive dependency from the application's perspective.

This matters because failures and vulnerabilities may exist in software your application did not directly declare.

---

# 8. DEPENDENCY VERSION MATTERS

These are not necessarily equivalent:

```text
library version 1.0

library version 2.0
```

A newer version may introduce:

```text
API changes

behavior changes

security fixes

removed functionality

different defaults

new runtime requirements
```

Therefore:

```text
Dependency Installed
≠
Compatible Dependency Installed
```

---

# 9. DEPENDENCY REPRODUCIBILITY

Suppose two engineers build the same source code but receive different dependency versions.

Then:

```text
Same Source
+
Different Dependencies
=
Potentially Different Behavior
```

This is one reason dependency pinning and lock mechanisms exist.

The deeper dependency-management and software-supply-chain topics will appear later.

For now, understand that source code is only one input to the resulting application.

---

# 10. THE BUILD PROCESS

A build transforms source and related inputs into something that can be executed or deployed.

Depending on the technology, the build may:

```text
compile source code

resolve dependencies

run tests

generate files

bundle assets

transpile code

package binaries

create archives

produce container images
```

Not every language requires the same type of build.

---

# 11. COMPILED APPLICATION EXAMPLE

A simplified compiled workflow might be:

```text
Source Code
    ↓
Compiler
    ↓
Executable Binary
    ↓
Run Binary
    ↓
Process
```

For example, a Go application may be compiled into an executable.

The deployed system may run the resulting binary rather than the original source files.

---

# 12. INTERPRETED APPLICATION EXAMPLE

A simplified Python workflow may look more like:

```text
Python Source
    ↓
Python Runtime
    ↓
Imported Dependencies
    ↓
Running Python Process
```

This does not mean "there is no build or packaging" in every Python project.

Python applications can still involve:

```text
package building

dependency installation

container image creation

asset generation

distribution packaging
```

The point is that execution models differ.

---

# 13. BUILD SUCCESS

Suppose CI reports:

```text
Build succeeded.
```

What does this prove?

Only what that build actually tested.

It may prove:

```text
source compiled successfully
```

or:

```text
package creation succeeded
```

or:

```text
tests configured in the build passed
```

It does not automatically prove:

```text
production configuration is correct

production secrets exist

database is reachable

deployment will succeed

application will start

users can access it
```

---

# 14. ARTIFACTS

An artifact is an output produced for later deployment or execution.

Examples include:

```text
compiled binary

JAR file

WAR file

ZIP archive

package

container image

static website bundle
```

Mental model:

```text
Source
  ↓
Build
  ↓
Artifact
  ↓
Deploy
```

The artifact provides a more concrete deployable unit than an arbitrary working directory.

---

# 15. ARTIFACT IDENTITY MATTERS

When troubleshooting a deployment, ask:

```text
Which artifact is actually running?
```

Not:

```text
Which source code do we think should be running?
```

Those may differ.

Useful artifact identity may involve:

```text
version

Git commit

build number

image digest

package version

release identifier
```

Later Parts will go deeper into CI/CD and container image identity.

---

# 16. SOURCE VERSION VERSUS DEPLOYED VERSION

Suppose Git contains a fix.

That does not prove the fix is deployed.

The real chain may be:

```text
Commit
 ↓
Build
 ↓
Artifact
 ↓
Deployment
 ↓
Running Process
```

A failure anywhere in that chain can result in an older application still serving traffic.

Therefore troubleshooting should establish:

```text
Expected Version
```

and:

```text
Observed Running Version
```

where the system provides a way to do so.

---

# 17. CONFIGURATION

Applications need information that varies between environments or deployments.

Examples:

```text
listening port

database hostname

database name

API endpoint

log level

feature flags

cache address

queue address

timeouts

environment name
```

This information is configuration.

---

# 18. CODE AND CONFIGURATION ARE DIFFERENT CONCERNS

Suppose the application code contains:

```text
Connect to database at db.example.internal
```

hard-coded permanently.

Moving the application to another environment may require changing source code.

A configurable application may instead receive:

```text
DB_HOST
```

from its environment or configuration system.

Then:

```text
Same Artifact
+
Different Configuration
=
Different Environment Behavior
```

This is a common operational pattern.

---

# 19. CONFIGURATION SOURCES

Applications may receive configuration from:

```text
environment variables

command-line arguments

configuration files

secret-management systems

service discovery

platform APIs

mounted files

remote configuration services
```

The exact mechanism depends on the application.

A DevOps engineer must determine which source is authoritative for the application being operated.

---

# 20. CONFIGURATION PRECEDENCE

An application may support several configuration sources simultaneously.

For example:

```text
default value

configuration file

environment variable

command-line option
```

Which wins?

That depends on the application.

Never assume precedence.

Check application documentation or implementation.

A common troubleshooting problem is:

> I changed the configuration file, but the application still uses the old value.

Possible explanation:

```text
environment variable overrides configuration file
```

But this must be verified for the specific application.

---

# 21. ENVIRONMENT VARIABLES

Part 7 introduced environment variables from the shell perspective.

Now consider them from the application perspective.

An application process may receive values such as:

```text
APP_ENV=staging

PORT=8080

LOG_LEVEL=info

DB_HOST=db.internal
```

The application reads these values and changes its behavior accordingly.

For example, Python exposes the process environment through interfaces such as `os.environ`.

---

# 22. PROCESS ENVIRONMENTS ARE INHERITED

A simplified model is:

```text
Parent Process
     ↓
Environment
     ↓
Start Child Process
     ↓
Child Receives Environment
```

Changing a shell variable after a child process has already started does not magically rewrite that running process's environment.

This is important.

Suppose:

```text
Application started with PORT=8080.
```

Then later you run:

```text
PORT=9000
```

in your shell.

The existing application does not automatically move to port 9000.

It would need application-specific dynamic configuration support or a restart/reload with new configuration.

---

# 23. CONFIGURATION MUST EXIST AT THE RIGHT TIME

Suppose an application requires:

```text
DATABASE_URL
```

during startup.

If it is missing when the application starts, the application might:

```text
exit immediately

use a default

start partially

disable database features

log an error
```

Behavior depends on the application.

The engineer must determine the actual behavior rather than assume it.

---

# 24. CONFIGURATION VALIDATION

Good applications validate required configuration.

For example:

```text
PORT must be an integer.

DATABASE_URL must be present.

LOG_LEVEL must be one of an allowed set.
```

Failing clearly during startup can be safer than silently using an unexpected configuration.

---

# 25. SECRETS ARE CONFIGURATION WITH ADDITIONAL SECURITY REQUIREMENTS

Examples:

```text
database passwords

API tokens

private keys

credentials
```

Do not:

```text
commit them to Git

print them into logs

paste them into AI prompts

include them casually in troubleshooting screenshots
```

Secret management is covered more deeply later.

For now:

```text
Configuration
≠
Safe to expose
```

---

# 26. RUNTIME

A runtime is the execution environment required by an application.

Examples may include:

```text
Python interpreter

Java Virtual Machine

Node.js runtime

.NET runtime
```

Some applications compile to native executables and have different runtime requirements.

The important question is:

> What must exist on the system for this artifact to execute?

---

# 27. RUNTIME VERSION

Suppose an application requires a specific runtime capability.

The server has an older runtime.

The source code may be correct.

The artifact may be correct.

The deployment may be correct.

But startup can still fail.

Therefore inspect:

```text
runtime type

runtime version

application requirement
```

For example:

```bash
python3 --version
```

or the equivalent command for the runtime in use.

---

# 28. RUNTIME IS NOT THE APPLICATION

Suppose:

```bash
python3 --version
```

works.

That proves Python is available.

It does not prove:

```text
your application starts

dependencies are installed

configuration is correct

the correct Python environment is used

the application port is reachable
```

Again:

```text
Runtime Healthy
≠
Application Healthy
```

---

# 29. PROCESS

When an application executes, the operating system creates or manages one or more processes.

From Part 3:

```text
Executable / Runtime
        ↓
Process
        ↓
PID
```

The process is the running execution context.

It has properties such as:

```text
PID

parent PID

user

environment

open files

memory

CPU usage

working directory

network sockets
```

---

# 30. APPLICATION VERSUS PROCESS

These terms are related but not identical.

An application may involve:

```text
one process
```

or:

```text
many processes
```

For example:

```text
Application
   ↓
Main Process
   ├── Worker 1
   ├── Worker 2
   └── Worker 3
```

Other applications may run several separate components.

Therefore:

```text
Application
≠
Always One Process
```

---

# 31. FINDING THE APPLICATION PROCESS

Useful commands may include:

```bash
ps -ef
```

```bash
ps aux
```

```bash
pgrep -af python
```

or application-specific searches.

Do not rely only on:

```bash
ps aux | grep app
```

without understanding that the search command itself can appear in results and that names can be ambiguous.

---

# 32. PROCESS IDENTITY

When you find a process, establish:

```text
PID

user

parent

command

arguments

start time

resource usage
```

Example:

```bash
ps -o pid,ppid,user,lstart,cmd -p <PID>
```

Exact available formatting options can vary by `ps` implementation, so verify on the target system.

---

# 33. PROCESS EXISTS

Suppose:

```bash
ps -p 4217
```

shows the process.

What has been proven?

```text
A process with PID 4217 exists at the time of inspection.
```

What has not been proven?

```text
It is the expected application version.

It is correctly configured.

It is listening.

It accepts connections.

It serves correct responses.

Its database works.

Its dependencies are healthy.

Users can reach it.
```

This distinction is central to production troubleshooting.

---

# 34. PROCESS RUNNING BUT APPLICATION BROKEN

An application process can remain alive while:

```text
worker threads are deadlocked

dependency requests are hanging

database pool is exhausted

internal queues are saturated

application logic is returning errors

requests time out

health checks fail

configuration is incorrect
```

Therefore:

> Process existence is necessary for many applications, but it is not sufficient evidence of application health.

---

# 35. LISTENING PORTS

Networked applications commonly listen on a socket.

For a TCP application, this typically involves:

```text
IP address
+
TCP port
```

For example:

```text
127.0.0.1:8080
```

or:

```text
0.0.0.0:8080
```

These are not equivalent.

---

# 36. BIND ADDRESS

Suppose an application listens on:

```text
127.0.0.1:8080
```

It is bound to the local loopback interface.

A request from the same host may work.

Remote clients normally cannot reach that loopback-only listener directly.

If the application listens on:

```text
0.0.0.0:8080
```

for IPv4, it is generally accepting connections through all appropriate local IPv4 interfaces, subject to routing, firewall, platform, and other controls.

Python's development `http.server`, for example, supports explicit binding and otherwise binds to all interfaces.

---

# 37. PORT NUMBER

A port identifies a network service endpoint on a host/protocol combination.

Examples commonly include:

```text
80

443

8080

3000

5000
```

But do not assume an application uses a port merely because it is conventional.

Inspect actual configuration and socket state.

---

# 38. PORT CONFIGURATION VERSUS PORT STATE

Suppose configuration says:

```text
PORT=8080
```

That proves:

```text
The application was intended or configured to use 8080.
```

It does not prove:

```text
A process successfully bound port 8080.
```

Verify the operating-system state.

---

# 39. INSPECT LISTENING SOCKETS

On Linux, a common command is:

```bash
ss -lnt
```

This can show listening TCP sockets numerically.

To include process information where permissions allow:

```bash
ss -lntp
```

Interpret the result.

Do not merely search for the port.

Ask:

```text
Which address?

Which port?

Which process?

IPv4 or IPv6?

Is it listening at all?
```

---

# 40. PROCESS → SOCKET → PORT

Mental model:

```text
Application Process
       ↓
Creates Socket
       ↓
Binds Address + Port
       ↓
Listens
       ↓
Client Connects
```

A failure can occur between any of these states.

---

# 41. PORT CONFLICT

Suppose an application attempts to listen on port 8080.

Another process already owns the required address/port combination.

Startup may fail with an address-in-use error.

Troubleshooting path:

```text
Application fails startup
        ↓
Read application error
        ↓
Suspect bind failure
        ↓
Inspect listening sockets
        ↓
Identify current owner
        ↓
Determine expected owner
        ↓
Correct configuration or conflict
        ↓
Restart safely
        ↓
Verify listener
```

Do not kill the existing process merely because it owns the port.

First determine what that process is.

---

# 42. APPLICATION LOGS

Applications generate evidence about their behavior.

Logs may include:

```text
startup messages

configuration errors

dependency failures

request information

authentication failures

database errors

exceptions

warnings

shutdown messages
```

Application logs are different from:

```text
kernel logs

system service logs

web proxy logs

load balancer logs

database logs
```

All may be relevant to the same incident.

---

# 43. LOG DESTINATIONS

Applications may write logs to:

```text
stdout

stderr

files

system journal

logging agents

remote logging platforms
```

Do not assume:

```text
/var/log/application.log
```

exists.

Determine how the application is configured to emit logs.

---

# 44. LOGGING TO STDOUT AND STDERR

Modern applications, particularly in containerized environments, commonly write operational logs to standard streams.

Conceptually:

```text
Application
   ├── stdout
   └── stderr
```

The surrounding runtime or platform can capture those streams.

This will become important when Docker and Kubernetes are introduced later.

---

# 45. LOGS ARE EVIDENCE, NOT AUTOMATIC TRUTH

Suppose a log contains:

```text
ERROR database connection failed
```

That is strong evidence that the application observed a database connection problem.

It does not automatically prove:

```text
the database server itself is down
```

Possible causes include:

```text
wrong hostname

DNS failure

network path failure

wrong port

TLS problem

authentication failure

database unavailable

connection limit reached
```

Use logs to form hypotheses.

Then test them.

---

# 46. STARTUP

Application startup may involve:

```text
load configuration

validate configuration

initialize logging

load dependencies

connect to database

initialize connection pools

connect to cache

connect to queue

bind network port

start workers

declare readiness
```

The exact sequence is application-specific.

---

# 47. STARTED DOES NOT HAVE ONE UNIVERSAL MEANING

Consider these events:

```text
Process created

Configuration loaded

Port bound

Dependencies connected

Health endpoint passes

Application ready for traffic
```

Which one means:

```text
Application started?
```

The answer depends on context.

Therefore use precise language.

Instead of:

```text
The application started.
```

say:

```text
The process exists and is listening on TCP port 8080.
```

or:

```text
The health endpoint returned HTTP 200.
```

Evidence should determine the statement.

---

# 48. STARTUP FAILURE

An application may exit immediately because:

```text
required configuration missing

configuration invalid

dependency unavailable

runtime incompatible

file permission denied

port already in use

required file missing

secret unavailable

database migration failed
```

Troubleshooting should begin with the exact observed failure.

---

# 49. SHUTDOWN

Applications also need to stop.

Shutdown may occur because of:

```text
deployment

service restart

host shutdown

scaling

operator action

crash

resource failure

signal
```

A well-behaved application may need time to:

```text
stop accepting new requests

finish in-flight work

close database connections

flush buffered data

acknowledge or release work

close files

terminate workers
```

---

# 50. GRACEFUL SHUTDOWN

From earlier Linux Parts, remember signals.

A service manager or container runtime may signal a process to terminate.

The application may handle a termination signal and begin graceful shutdown.

Conceptually:

```text
Termination Requested
        ↓
Stop New Work
        ↓
Finish / Bound Existing Work
        ↓
Close Resources
        ↓
Exit
```

If the application does not stop within the allowed time, the surrounding system may eventually force termination.

Exact behavior depends on the runtime and platform.

---

# 51. WHY `kill -9` IS NOT A NORMAL SHUTDOWN STRATEGY

SIGKILL forces process termination and cannot be caught, blocked, or ignored by the target process.

That means the application cannot perform normal graceful cleanup in response to SIGKILL.

Therefore:

```text
Process Will Not Stop
```

does not immediately mean:

```text
kill -9
```

Investigate first.

Use the least disruptive appropriate action.

---

# 52. HEALTH

Application health is not a single universal property.

You may need to ask:

```text
Is the process alive?

Is it listening?

Can it accept a connection?

Can it answer HTTP?

Can it perform critical application work?

Can it reach required dependencies?

Can users complete important requests?
```

These are different health questions.

---

# 53. LIVENESS CONCEPT

A liveness-style question asks approximately:

> Is this application instance still functioning enough that it should continue running?

This concept becomes particularly important in Kubernetes later.

At this stage, understand that:

```text
Process Exists
```

and:

```text
Application Is Functioning
```

may differ.

---

# 54. READINESS CONCEPT

A readiness-style question asks approximately:

> Should this application instance currently receive traffic?

An application might be alive but not ready because:

```text
startup is incomplete

required dependency unavailable

internal initialization incomplete

application intentionally removed from traffic
```

Therefore:

```text
Alive
≠
Ready
```

---

# 55. HEALTH ENDPOINTS

Web applications may expose endpoints such as:

```text
/health

/healthz

/ready

/status
```

There is no universal endpoint name or universal semantics.

Never assume `/health` exists or proves everything.

Read the application's health-check contract.

---

# 56. SHALLOW HEALTH CHECK

A shallow health endpoint might simply confirm:

```text
application request handler is responding
```

For example:

```text
HTTP 200
```

This can be useful.

But it may not test:

```text
database

cache

queue

external API
```

---

# 57. DEPENDENCY-AWARE HEALTH

A deeper health check may inspect dependencies.

But deeper checks create design tradeoffs.

For example, if a noncritical analytics API is unavailable:

```text
Should the entire application be considered unhealthy?
```

That is an application and reliability design decision.

At Junior level, understand:

> A health check proves only what it actually checks.

---

# 58. HTTP RESPONSE AS EVIDENCE

Suppose:

```bash
curl http://127.0.0.1:8080/
```

returns content.

You have stronger evidence than process existence alone.

You have shown that, at that moment:

```text
a client reached the endpoint

a server accepted the request

an HTTP response was returned
```

But you still have not necessarily proven:

```text
all application features work

database operations work

external users can reach it

every dependency is healthy
```

---

# 59. CURL SUCCESS VERSUS HTTP SUCCESS

This distinction is important.

By default, `curl` does not treat an HTTP 404 or other HTTP error status as a transfer failure merely because the status code indicates an application-level error. Options such as `--fail` or `--fail-with-body` can change that behavior.

Therefore:

```bash
curl http://127.0.0.1:8080/missing
```

may successfully perform the HTTP transaction while receiving:

```text
404 Not Found
```

Distinguish:

```text
Transport worked
```

from:

```text
Application returned desired HTTP status.
```

---

# 60. INSPECT HTTP STATUS

A useful inspection pattern is:

```bash
curl -i http://127.0.0.1:8080/
```

This includes response headers.

Or:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/
```

This can report the HTTP response code.

Always understand what the command is proving.

---

# 61. EXTERNAL DEPENDENCIES

Most production applications do not operate alone.

They may depend on:

```text
databases

caches

message queues

APIs

object storage

identity providers

DNS

secret systems

other internal services
```

The application may be healthy at the process layer while unhealthy at the dependency layer.

---

# 62. DEPENDENCY GRAPH

Think of an application as a graph:

```text
             ┌──────── Database
             │
User → Application ─── Cache
             │
             ├──────── Queue
             │
             └──────── External API
```

A user request may require several nodes in that graph.

One unavailable dependency can affect only certain features.

---

# 63. DATABASES

A database commonly stores durable application data.

Examples of application interactions include:

```text
read customer

create order

update account

retrieve configuration

record transaction
```

An application may need:

```text
database hostname

port

database name

username

credential

TLS settings

connection timeout
```

A database problem can therefore originate from several layers.

---

# 64. "DATABASE DOWN" IS TOO BROAD

Suppose logs show:

```text
database connection failed
```

Possible causes include:

```text
database hostname wrong

DNS lookup failed

route unavailable

firewall blocking connection

wrong database port

database process down

TLS negotiation failure

credentials rejected

database refusing additional connections

application connection configuration wrong
```

Do not collapse all of these into:


```python
import json
import os
from http.server import BaseHTTPRequestHandler, HTTPServer

APP_NAME = os.environ.get("APP_NAME")
APP_ENV = os.environ.get("APP_ENV")
PORT_RAW = os.environ.get("PORT")


def load_configuration():
    missing = []

    if not APP_NAME:
        missing.append("APP_NAME")

    if not APP_ENV:
        missing.append("APP_ENV")

    if not PORT_RAW:
        missing.append("PORT")

    if missing:
        raise RuntimeError(
            f"Missing required environment variables: {', '.join(missing)}"
        )

    try:
        port = int(PORT_RAW)
    except ValueError as exc:
        raise RuntimeError("PORT must be an integer") from exc

    if not 1 <= port <= 65535:
        raise RuntimeError("PORT must be between 1 and 65535")

    return port


class Handler(BaseHTTPRequestHandler):
    def send_json(self, status_code, payload):
        body = json.dumps(payload).encode("utf-8")

        self.send_response(status_code)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def do_GET(self):
        if self.path == "/":
            self.send_json(
                200,
                {
                    "application": APP_NAME,
                    "environment": APP_ENV,
                    "status": "running",
                },
            )
            return

        if self.path == "/health":
            self.send_json(
                200,
                {
                    "status": "healthy",
                },
            )
            return

        self.send_json(
            404,
            {
                "error": "not found",
            },
        )


def main():
    port = load_configuration()

    server = HTTPServer(("127.0.0.1", port), Handler)

    print(
        f"Starting {APP_NAME} "
        f"environment={APP_ENV} "
        f"address=127.0.0.1 "
        f"port={port}",
        flush=True,
    )

    try:
        server.serve_forever()
    except KeyboardInterrupt:
        print("Shutdown requested", flush=True)
    finally:
        server.server_close()
        print("Server stopped", flush=True)


if __name__ == "__main__":
    main()
```

This lab intentionally uses Python's standard-library HTTP server classes so no third-party Python package is required. Python documents `HTTPServer` as a server built on `TCPServer`; the standard library's HTTP server facilities are intended for basic use and are not recommended as a production server.

This application is a teaching application.

Do not expose it as a production service.

Before declaring a dependency outage, verify what endpoint the application is actually trying to use.

---

# 128. EXPECTED STATE VERSUS OBSERVED STATE

Suppose documentation says:

```text
Application should listen on port 8080.
```

But:

```bash
ss -lntp
```

shows:

```text
127.0.0.1:9000
```

Record:

```text
Expected:
8080

Observed:
9000
```

That difference is evidence.

Do not immediately modify the system.

First determine why the states differ.

---

# 129. APPLICATION VERSION TROUBLESHOOTING

Suppose a newly added endpoint returns 404.

Possible explanations include:

```text
wrong URL

route disabled

wrong configuration

old artifact still running

request reaching another instance

proxy routing elsewhere
```

One important question is:

```text
Which application version actually handled the request?
```

Production systems should ideally make release identity observable.

---

# 130. PROCESS OWNERSHIP

The application process runs as a user.

Inspect:

```bash
ps -o pid,user,group,cmd -p <PID>
```

This matters because the process's identity affects access to:

```text
files

directories

ports

sockets

devices

other processes
```

A permission failure may therefore be an application runtime problem rather than a source-code problem.

---

# 131. WORKING DIRECTORY

A process has a working directory.

On Linux, where permissions allow, inspect:

```bash
readlink /proc/<PID>/cwd
```

Why does this matter?

An application using relative paths may look for:

```text
./config.yaml
```

relative to its working directory.

If launched from an unexpected location, it may fail to find files.

---

# 132. OPEN FILES

Applications may have open:

```text
configuration files

log files

libraries

sockets

data files
```

Where available:

```bash
lsof -p <PID>
```

can provide useful information.

`lsof` may not be installed by default.

Do not make it a hidden prerequisite.

---

# 133. EXECUTABLE IDENTITY

On Linux, `/proc` can help inspect a process.

For native executables, for example:

```bash
readlink /proc/<PID>/exe
```

may show the executable associated with the process, subject to permissions and process/runtime details.

Interpreted applications require additional reasoning because the executable may be:

```text
python3
```

while the application source appears in process arguments.

---

# 134. COMMAND LINE

Inspect:

```bash
tr '\0' ' ' < /proc/<PID>/cmdline
printf '\n'
```

This can reveal how a process was started.

Be careful:

Command-line arguments can contain sensitive information.

Do not expose them indiscriminately.

---

# 135. ENVIRONMENT SECURITY

Likewise:

```text
/proc/<PID>/environ
```

may contain:

```text
tokens

passwords

credentials

connection strings
```

Use targeted filtering in diagnostics.

Do not run:

```text
dump every environment variable
```

as your default troubleshooting strategy.

---

# 136. LOG SECURITY

Logs may accidentally expose:

```text
authorization headers

passwords

session identifiers

API tokens

personal information

database connection strings
```

Application logging must balance:

```text
operational evidence
```

with:

```text
data protection
```

More logging is not automatically better logging.

# 137. HEALTH VERSUS CORRECTNESS

Suppose:

```text
GET /health
→ 200
```

but:

```text
GET /checkout
→ 500
```

Is the application healthy?

The answer depends on what "health" means in the operational context.

You can state precisely:

```text
The health endpoint is responding successfully.
```

You cannot conclude:

```text
All application functionality is healthy.
```

---

# 138. AVAILABILITY VERSUS CORRECTNESS

An application may be available but wrong.

For example:

```text
HTTP 200
```

with:

```text
incorrect customer data
```

Availability checks may not detect logical correctness failures.

Therefore:

```text
Reachable
≠
Correct
```

---

# 139. FAST VERSUS HEALTHY

An application may respond:

```text
HTTP 200
```

but take:

```text

```

A binary success check may pass while users experience severe degradation.

Therefore application health can include:

```text
availability

latency

error rate

correctness

dependency health
```

Later observability Parts will develop this further.

# 140. PROCESS RUNNING BUT FROZEN

A process may exist but appear unresponsive because it is:

```text

waiting for network I/O

waiting for a lock

waiting for another process

blocked on dependency

deadlocked internally

stuck in CPU-intensive work

in uninterruptible kernel wait
```

```text

≠
```

Suppose:

```bash

```

```text

```

Application-level verification may still fail.

Therefore:

```text

≠

```

# 143. DEPLOYMENT SUCCESS VERSUS APPLICATION SUCCESS

Suppose a deployment tool reports:

```text
Deployment completed successfully.
```

This may mean:

```text
artifact copied

container created

manifest accepted

service restarted
```

depending on the tool.

It does not necessarily mean:

```text
users can successfully complete transactions
```

Always understand what the deployment system's success condition actually verifies.

# 144. CONFIGURATION CHANGE REQUIRES BEHAVIOR UNDERSTANDING

Suppose you change:

```text
PORT=8080
```

to:

```text
PORT=9090
```

Does the running application immediately move?

Not necessarily.

Questions:

```text
When is configuration read?

Only during startup?

Periodically?

On reload signal?

Through dynamic configuration API?
```

The application determines the answer.

---

# 145. RESTART VERSUS RELOAD

Some applications support:

```text
restart
```

and:

```text
reload
```

These are not universally equivalent.

A reload may cause an application to re-read selected configuration without replacing the entire process.

A restart normally involves stopping and starting process execution.

Exact behavior is application-specific.

Never assume a reload applies every configuration change.

---

# 146. APPLICATION STATE

Applications may hold state in:

```text
memory

local files

database

cache

external storage

queue
```

Restarting a process may therefore have consequences.

Ask:

```text
What state exists only in memory?

Will active requests be lost?

Will queued work survive?

Will sessions survive?

Can the process restart safely?
```

Do not treat restart as a consequence-free troubleshooting command.

---

# 147. STATELESS APPLICATION CONCEPT

A stateless application instance generally avoids keeping durable user/business state only inside that individual process.

Instead, durable state may live in systems such as:

```text
database

object storage

external cache/session system
```

This can make horizontal scaling and replacement easier.

But:

```text
Stateless
≠
No State Anywhere
```

It means the application instance is designed not to be the sole durable owner of important state.

---

# 148. STATEFUL APPLICATION CONCEPT

A stateful system owns or manages persistent state that must survive process replacement.

Examples commonly include:

```text
databases

some message brokers

distributed data stores
```

Operating stateful systems requires additional attention to:

```text
storage

consistency

replication

backup

recovery
```

These topics appear later.

# 161. TROUBLESHOOTING: LOG SAYS HEALTHY BUT USER FAILS

# 200. FINAL ENGINEERING PRINCIPLE

The operating system does not know whether your business application is correct.

The process table can tell you:

```text
a process exists
```

The socket table can tell you:

```text
something is listening
```

An HTTP request can tell you:

```text
an endpoint responded
```

An application log can tell you:

```text
the application observed something
```

A dependency check can tell you:

```text
a particular dependency interaction succeeded or failed
```

None of these pieces alone describes the entire system.

A DevOps engineer combines them.

The core reasoning chain is:

```text
Source
  ↓
Dependencies
  ↓
Build
  ↓
Artifact
  ↓
Configuration
  ↓
Runtime
  ↓
Process
  ↓
Socket
  ↓
Port
  ↓
Protocol
  ↓
Application
  ↓
Dependencies
  ↓
User Outcome
```

When failure occurs:

```text
Symptom
  ↓
Expected State
  ↓
Observed State
  ↓
Failure Boundary
  ↓
Evidence
  ↓
Hypothesis
  ↓
Safe Test
  ↓
Root Cause
  ↓
Corrective Action
  ↓
Verification
```

That is the transition from:

```text
"The app is down."
```

to:

```text
"I know which layer is failing, what evidence supports that conclusion, and what should be checked next."
```
