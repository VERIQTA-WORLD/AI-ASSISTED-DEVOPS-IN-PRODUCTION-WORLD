# PART 7: SHELL SCRIPTING AND AUTOMATION FUNDAMENTALS

## Goal

Automate repeatable operational tasks without turning fragile command sequences into production automation blindly.

By the end of this Part, the learner should be able to write, read, test, troubleshoot, and review small Bash scripts used for operational work.

The learner should understand that shell scripting is not simply:

```bash
command1
command2
command3
```

saved inside a file.

A production-minded script must account for:

```text
Inputs
  ↓
Validation
  ↓
Execution
  ↓
Failure Detection
  ↓
Logging
  ↓
Exit Status
  ↓
Verification
```

The central engineering principle for this Part is:

> Automation should make an operation more repeatable and understandable, not merely make it faster to execute.

A command sequence that works once on one engineer's machine is not automatically safe automation.

---

# 1. WHY SHELL SCRIPTING MATTERS IN DEVOPS

DevOps engineers repeatedly perform operations such as:

```text
checking service status

inspecting disk usage

reading logs

checking processes

validating files

testing connectivity

checking prerequisites

collecting system information

verifying deployments

preparing environments

running administrative commands
```

Suppose an engineer repeatedly runs:

```bash
hostname
uptime
df -h
free -h
systemctl status nginx
```

Running these commands manually may be acceptable during an investigation.

If the same inspection must be performed repeatedly across many situations, a script may improve consistency.

For example:

```bash
#!/usr/bin/env bash

hostname
uptime
df -h
free -h
systemctl status nginx
```

But this is only the beginning.

What happens if:

```text
nginx is not installed?

systemctl is unavailable?

the script lacks permission?

one command fails?

the output needs to be consumed by another program?

the script runs under a different PATH?

the filesystem is full?

the script is interrupted halfway through?

an expected variable is empty?
```

Automation introduces its own failure modes.

---

# 2. MANUAL COMMANDS VERSUS AUTOMATION

Consider:

```bash
rm "$file"
```

When an engineer runs this manually, they may visually inspect `$file` first.

When automated, the script may execute without that human pause.

If:

```text
file=/tmp/report.txt
```

the operation may be expected.

If a bug causes:

```text
file=
```

or causes the variable to reference the wrong location, the consequences can be very different depending on how the command is constructed.

Automation removes repeated human intervention.

That is useful.

It also removes repeated human judgment.

Therefore automation must replace missing human judgment with:

```text
validation

constraints

safe defaults

clear failure behavior

verification

logging
```


```text
What problem does the script solve?

```

# 5. SHELL EXECUTION

In Part 2, the learner distinguished the terminal from the shell.

Now that distinction becomes operational.

A shell reads commands, interprets shell syntax, performs expansions and redirections, executes commands, and makes their exit statuses available for further logic.

A script is a file containing instructions for a shell interpreter.

Example:

```bash
#!/usr/bin/env bash

printf '%s\n' "Hello from Bash"
```

Save it as:

```text
hello.sh
```

---

# 6. THE SHEBANG

The first line:

```bash
#!/usr/bin/env bash
```

is commonly called the shebang.

It tells the operating system which interpreter should be used when the script is executed directly.

Another possible form is:

```bash
#!/bin/bash
```

These are not identical approaches.

`#!/bin/bash` refers to Bash at a specific path.

`#!/usr/bin/env bash` asks `env` to locate `bash` using the environment's command search path.

Which form is appropriate depends on the environment and organizational requirements.

Do not copy a shebang without knowing which interpreter the script requires.

---

# 7. SHELL LANGUAGE MATTERS

These are not automatically interchangeable:

```text
sh

bash

dash

zsh

ksh
```

A script may use Bash-specific syntax that does not work in a strictly POSIX `sh` environment.

For this Part, examples will primarily use:

```text
Bash
```

unless explicitly stated otherwise.

That means a script using Bash-specific behavior should declare that expectation.

---

# 8. RUNNING A SCRIPT

A script can be passed explicitly to Bash:

```bash
bash hello.sh
```

In this case, Bash reads the file.

Alternatively, after making it executable:

```bash
chmod +x hello.sh
```

you can execute:

```bash
./hello.sh
```

The second form depends on:

```text
execute permission

valid interpreter declaration

correct path
```

---

# 9. WHY `./script.sh` USES `./`

Suppose:

```bash
script.sh
```

exists in the current directory.

Running:

```bash
script.sh
```

does not necessarily execute it.

The shell normally searches directories listed in:

```text
PATH
```

for command names.

The current directory is not necessarily in `PATH`.

Running:

```bash
./script.sh
```

explicitly identifies the file in the current directory.

This connects directly to the PATH knowledge from Part 2.

---

# 10. SCRIPT EXECUTION VERSUS SOURCING

These are different:

```bash
./script.sh
```

and:

```bash
source script.sh
```

or:

```bash
. script.sh
```

Normal execution runs the script in its own shell process/environment context.

Sourcing reads and executes the commands in the current shell environment.

This matters because sourced code can modify the current shell's:

```text
variables

functions

working directory

shell options

environment
```

Do not source an unfamiliar script merely because executing it produced a problem.

---

# 11. A SCRIPT IS CODE

This sounds obvious, but operationally it matters.

Do not think:

```text
Shell script = harmless command file
```

A shell script can:

```text
delete files

change permissions

stop services

modify firewall rules

create users

alter cloud resources through CLIs

change Kubernetes resources

modify infrastructure

send credentials

overwrite configuration
```

Treat shell scripts as executable code.

Review them accordingly.

---

# 12. VARIABLES

Variables store values for use later in the script.

Example:

```bash
service_name="nginx"
```

Use the variable:

```bash
printf '%s\n' "$service_name"
```

Assignment syntax matters.

Correct:

```bash
service_name="nginx"
```

Incorrect:

```bash
service_name = "nginx"
```

The shell does not interpret spaces around `=` as assignment syntax.

---

# 13. VARIABLE EXPANSION

Use:

```bash
name="VERIQTA"
printf '%s\n' "$name"
```

You may also write:

```bash
printf '%s\n' "${name}"
```

Braces can make boundaries clearer.

Example:

```bash
file="report"
printf '%s\n' "${file}.txt"
```

Without braces:

```bash
printf '%s\n' "$file.txt"
```

the interpretation may not express what the author intended because variable-name boundaries matter.

---

# 14. QUOTING IS A CORE SHELL SKILL

Many shell bugs come from misunderstanding quoting.

Three important forms are:

```text
unquoted text

"double quoted text"

'single quoted text'
```

These behave differently.

Quoting controls how the shell interprets special characters and expansions.

This is not cosmetic formatting.

It changes program behavior.

---

# 15. UNQUOTED VARIABLE EXPANSION

Consider:

```bash
file="Quarterly Report.txt"
cat $file
```

This is unsafe.

The expanded value can undergo word splitting.

The shell may effectively pass separate arguments:

```text
Quarterly

Report.txt
```

rather than one filename.

A safer form is:

```bash
cat "$file"
```

ShellCheck specifically warns about unquoted expansions because they can cause word splitting and pathname expansion.

---

# 16. DOUBLE QUOTES

Double quotes generally preserve a value as one shell word while still allowing expansions such as:

```text
variable expansion

command substitution

some backslash processing
```

Example:

```bash
name="DevOps Engineer"
printf 'User: %s\n' "$name"
```

For variable expansions representing one argument, quoting is usually the safe default.

---

# 17. SINGLE QUOTES

Single quotes preserve their contents literally.

Example:

```bash
printf '%s\n' '$HOME'
```

outputs:

```text
$HOME
```

while:

```bash
printf '%s\n' "$HOME"
```

expands the variable.

Therefore:

```text
'$HOME'
```

and:

```text
"$HOME"
```

mean different things.

---

# 18. QUOTING CHANGES BEHAVIOR

Consider:

```bash
pattern="*.log"
```

Then:

```bash
printf '%s\n' $pattern
```

may expand matching filenames.

But:

```bash
printf '%s\n' "$pattern"
```

prints the literal variable value as one argument.

Similarly, patterns passed to commands such as `find` often need quoting so that the shell does not expand them before `find` receives them.

For example:

```bash
find /var/log -name '*.log'
```

is different from allowing the local shell to expand `*.log` first.

---

# 19. QUOTING RULE OF THUMB

For Junior-level Bash scripting:

> Quote variable expansions unless you specifically require shell splitting or glob expansion and understand the consequences.

Prefer:

```bash
rm -- "$file"
```

over:

```bash
rm $file
```

Prefer:

```bash
cp -- "$source" "$destination"
```

over:

```bash
cp $source $destination
```

The `--` convention supported by many Unix commands marks the end of options, helping when a filename begins with `-`.

Do not assume every command supports `--`; verify the command's documentation.

---

# 20. COMMAND SUBSTITUTION

To capture command output:

```bash
hostname_value=$(hostname)
```

Then:

```bash
printf 'Hostname: %s\n' "$hostname_value"
```

This means:

```text
Execute command
      ↓
Capture standard output
      ↓
Assign resulting text
```

Do not confuse this with:

```bash
hostname_value=hostname
```

which assigns the literal word `hostname`.

ShellCheck explicitly distinguishes command substitution from assigning a command name as text.

---

# 21. ARGUMENTS

Scripts often need input.

Suppose:

```bash
./check-service.sh nginx
```

Inside the script:

```text
$1
```

represents the first positional argument.

Other positional parameters include:

```text
$2

$3

...
```

---

# 22. SPECIAL PARAMETERS

Useful shell parameters include:

```text
$0   script name or invocation name

$1   first argument

$2   second argument

$#   number of positional arguments

"$@" all positional arguments, preserving argument boundaries when quoted

$?   exit status of the most recently completed foreground pipeline/command context
```

These have different meanings.

Do not use them interchangeably.

---

# 23. `"$@"` IS IMPORTANT

Suppose the script receives:

```bash
./script.sh "file one.txt" "file two.txt"
```

Using:

```bash
for item in "$@"; do
    printf '%s\n' "$item"
done
```

preserves the two arguments correctly.

Argument boundaries are important.

This is another reason quoting matters.

---

# 24. VALIDATING ARGUMENT COUNT

Suppose a script requires exactly one service name.

Do not immediately use:

```bash
service_name="$1"
```

and assume the value exists.

Validate first:

```bash
if [[ $# -ne 1 ]]; then
    printf 'Usage: %s SERVICE_NAME\n' "$0" >&2
    exit 2
fi

service_name="$1"
```

Now the script has defined behavior when input is missing.

---

# 25. INPUT IS UNTRUSTED UNTIL VALIDATED

This applies even when the user is another engineer.

Input may be:

```text
missing

empty

malformed

unexpected

dangerous in context

valid syntax but wrong resource
```

A script should distinguish:

```text
received input
```

from:

```text
validated input
```

---

# 26. ENVIRONMENT VARIABLES

Shell variables exist within shell execution contexts.

An environment variable is exported so child processes can receive it.

Example:

```bash
APP_ENV="staging"
export APP_ENV
```

or:

```bash
export APP_ENV="staging"
```

A child command can then inherit it.

---

# 27. SHELL VARIABLE VERSUS ENVIRONMENT VARIABLE

Conceptually:

```text
Shell Variable
     ↓
export
     ↓
Environment Entry
     ↓
Child Process
```

Not every shell variable is automatically exported.

This distinction matters when a script works interactively but a child process cannot see the expected value.

---

# 28. ENVIRONMENT VARIABLES ARE NOT AUTOMATICALLY SECRETS

You may see environment variables used for:

```text
configuration

paths

runtime settings

credentials
```

But:

```text
Environment Variable
≠
Secret Management System
```

Whether environment variables are appropriate for sensitive information depends on the runtime, threat model, platform, process visibility, logging, debugging behavior, and secret-management architecture.

Never print environment variables indiscriminately in production diagnostics.

---

# 29. REQUIRED ENVIRONMENT VARIABLES

Suppose a script requires:

```text
APP_ENV
```

A simple validation pattern is:

```bash
if [[ -z "${APP_ENV:-}" ]]; then
    printf '%s\n' "ERROR: APP_ENV is required." >&2
    exit 2
fi
```

`${APP_ENV:-}` safely produces an empty fallback when the variable is unset or null.

This becomes especially relevant when using stricter unset-variable handling later.

---

# 30. CONDITIONALS

Automation must make decisions.

Basic Bash structure:

```bash
if condition; then
    commands
fi
```

Example:

```bash
if systemctl is-active --quiet nginx; then
    printf '%s\n' "nginx is active"
else
    printf '%s\n' "nginx is not active"
fi
```

Notice the condition checks the command's exit status.

The script does not need to parse human-readable text when the command already provides machine-usable status.

---

# 31. COMMAND SUCCESS AS A CONDITION

A useful shell pattern is:

```bash
if command; then
    success_action
else
    failure_action
fi
```

This directly tests the command's exit status.

For example:

```bash
if grep -q 'ERROR' application.log; then
    printf '%s\n' "Error entries detected"
else
    printf '%s\n' "No matching error entries detected"
fi
```

But even here, understand the command's documented exit statuses.

Some commands use different non-zero values to distinguish:

```text
no match

actual execution error
```

Do not blindly interpret every non-zero value as the same condition.

---

# 32. TEST EXPRESSIONS

Bash provides test mechanisms including:

```bash
[ ... ]
```

and Bash's:

```bash
[[ ... ]]
```

Example:

```bash
if [[ -f "$file" ]]; then
    printf '%s\n' "File exists"
fi
```

Useful tests include concepts such as:

```text
file exists

directory exists

string empty

string non-empty

values equal

numeric comparison
```

Verify exact operators when using them.

---

# 33. EMPTY VARIABLE BUGS

Problematic:

```bash
if [ -n $name ]; then
    printf '%s\n' "Name exists"
fi
```

If `$name` is empty, shell expansion can alter the expression unexpectedly.

Safer:

```bash
if [ -n "$name" ]; then
    printf '%s\n' "Name exists"
fi
```

or in Bash:

```bash
if [[ -n "$name" ]]; then
    printf '%s\n' "Name exists"
fi
```

This class of issue is specifically identified by ShellCheck.

---

# 34. `case`

When several known input values are valid, `case` can be clearer than many nested `if` statements.

Example:

```bash
case "$1" in
    start)
        printf '%s\n' "Starting"
        ;;
    stop)
        printf '%s\n' "Stopping"
        ;;
    status)
        printf '%s\n' "Checking status"
        ;;
    *)
        printf 'Usage: %s {start|stop|status}\n' "$0" >&2
        exit 2
        ;;
esac
```

The default case handles unsupported input explicitly.

---

# 35. LOOPS

Loops repeat operations.

Common Bash loops include:

```text
for

while

until
```

A simple loop:

```bash
for service in nginx ssh cron; do
    printf 'Checking %s\n' "$service"
done
```

But automation should not repeat actions blindly.

Each iteration may fail independently.

---

# 36. LOOPS NEED FAILURE THINKING

Suppose:

```bash
for host in host1 host2 host3; do
    deploy "$host"
done
```

Questions immediately arise:

```text
What if host1 succeeds?

What if host2 fails?

Should host3 still run?

Should host1 be rolled back?

Should execution stop?

How is partial success reported?

Can the operation safely be retried?
```

A loop can turn one failure into a fleet-wide failure very quickly.

---

# 37. WHILE LOOPS

Example:

```bash
while read -r line; do
    printf '%s\n' "$line"
done < input.txt
```

The `-r` option prevents `read` from treating backslashes as escapes in the usual way, which is generally desirable when reading arbitrary text.

When processing data, always ask:

```text
Can the input contain spaces?

Can it contain backslashes?

Can it contain empty lines?

Can it contain delimiters?

Can it contain unexpected characters?
```

---

# 38. DO NOT PARSE DATA CARELESSLY

This is fragile:

```bash
for file in $(find . -type f); do
    printf '%s\n' "$file"
done
```

Filenames containing spaces or other special characters can break assumptions.

Shell scripting often fails not because the main logic is wrong, but because the script assumes data has a simpler shape than reality.

Production data eventually finds your edge cases.

---

# 39. FUNCTIONS

Functions allow related logic to be grouped and reused.

Example:

```bash
log_info() {
    printf '[INFO] %s\n' "$*"
}
```

Then:

```bash
log_info "Starting system inspection"
```

Functions can improve:

```text
readability

reuse

testing

error handling

separation of responsibilities
```

---

# 40. FUNCTIONS SHOULD HAVE CLEAR RESPONSIBILITIES

Weak function:

```text
check_everything_and_fix_it()
```

Better separation:

```text
check_prerequisites

check_disk_usage

check_service

log_error

validate_input
```

A function should ideally have a clear purpose.

This makes failure easier to locate.

---

# 41. FUNCTION ARGUMENTS

Functions have positional parameters too.

Example:

```bash
check_service() {
    local service_name="$1"

    if systemctl is-active --quiet "$service_name"; then
        printf '%s is active\n' "$service_name"
    else
        printf '%s is not active\n' "$service_name"
    fi
}
```

Call:

```bash
check_service "nginx"
```

---

# 42. LOCAL VARIABLES

Inside Bash functions:

```bash
local service_name="$1"
```

limits the variable's scope to the function and its calls as Bash defines local variable behavior.

This reduces accidental modification of unrelated global variables.

Use scope intentionally.

---

# 43. EXIT CODES

Every command communicates an exit status.

For Bash's command-success model:

```text
0
=
success
```

and:

```text
non-zero
=
failure or another command-defined non-success condition
```

Bash documents exit statuses in the range 0–255 and reserves/uses some values for particular shell-level conditions; for example, command-not-found commonly results in 127 and found-but-not-executable in 126.

Do not invent universal meanings for arbitrary non-zero values.

Individual programs may define their own exit-code semantics.

---

# 44. INSPECTING THE LAST EXIT STATUS

After a command:

```bash
some-command
```

you can inspect:

```bash
printf '%s\n' "$?"
```

But `$?` changes whenever another relevant command runs.

Example:

```bash
some-command
printf '%s\n' "Checking status"
printf '%s\n' "$?"
```

The final `$?` no longer necessarily represents `some-command`.

Capture it immediately if needed:

```bash
some-command
status=$?
```

Then:

```bash
printf 'Exit status: %s\n' "$status"
```

---

# 45. PREFER DIRECT CONDITIONAL TESTING WHEN APPROPRIATE

Instead of:

```bash
systemctl is-active --quiet nginx
status=$?

if [[ $status -eq 0 ]]; then
    ...
fi
```

you can often write:

```bash
if systemctl is-active --quiet nginx; then
    ...
else
    ...
fi
```

This is clearer when the only question is whether the command succeeded.

---

# 46. YOUR SCRIPT NEEDS AN EXIT STATUS

A script is itself a command.

Other tools may depend on its exit status.

Examples include:

```text
CI/CD systems

cron jobs

monitoring systems

parent scripts

systemd units

automation platforms
```

A script that prints:

```text
ERROR: service unavailable
```

but exits with:

```text
0
```

can mislead automation.

---

# 47. MEANINGFUL EXIT CODES

For a small operational script, you might define:

```text
0 = check passed

1 = operational check failed

2 = invalid usage or missing prerequisite
```

This is your script's interface.

Document it.

Do not create dozens of undocumented exit codes unnecessarily.

---

# 48. STANDARD STREAMS

Unix-like processes normally operate with three standard streams:

```text
stdin   standard input

stdout  standard output

stderr  standard error
```

Common file descriptor numbers are:

```text
0 = stdin

1 = stdout

2 = stderr
```

Understanding these is essential for scripting.

---

# 49. STANDARD OUTPUT

Normal program output generally goes to:

```text
stdout
```

Example:

```bash
printf '%s\n' "Service is healthy"
```

A caller may capture it:

```bash
result=$(./check-service.sh)
```

Therefore stdout should be intentional.

---

# 50. STANDARD ERROR

Errors and diagnostics should commonly go to:

```text
stderr
```

Example:

```bash
printf '%s\n' "ERROR: configuration file missing" >&2
```

This allows normal output and diagnostic output to be handled separately.

---

# 51. WHY STDOUT AND STDERR SEPARATION MATTERS

Suppose a script is expected to output only:

```text
42
```

for another program to consume.

If debugging messages are also printed to stdout:

```text
Starting check...
42
Done.
```

the downstream parser may fail.

A cleaner design:

```text
stdout
→ machine-consumable result

stderr
→ diagnostics
```

when appropriate.

---

# 52. REDIRECTION

Output can be redirected.

Example:

```bash
command > output.txt
```

This redirects stdout to a file, replacing its previous contents.

Append:

```bash
command >> output.txt
```

Redirect stderr:

```bash
command 2> error.txt
```

Redirect both streams intentionally according to the shell syntax you choose.

Understand which stream you are redirecting.

---

# 53. REDIRECTION CAN DESTROY DATA

This:

```bash
command > important-file.txt
```

opens the destination for output and can truncate existing content before the command produces useful results.

Therefore:

```text
>
```

is not harmless punctuation.

Before redirecting to a file, verify the destination.

---

# 54. INPUT REDIRECTION

A command can receive input from a file:

```bash
while read -r line; do
    printf '%s\n' "$line"
done < services.txt
```

This connects:

```text
File
 ↓
stdin
 ↓
Command
```

---

# 55. PIPES

A pipe connects one command's stdout to another command's stdin.

Example:

```bash
journalctl -u nginx | grep 'error'
```

Mental model:

```text
journalctl stdout
       ↓
      pipe
       ↓
grep stdin
```

This is one of the most powerful Unix composition patterns.

---

# 56. PIPELINES ARE DATA FLOWS

Consider:

```bash
ps aux | grep nginx
```

This means:

```text
ps
↓
process listing
↓
stdout
↓
pipe
↓
grep
↓
filter matching text
```

Do not memorize pipelines as magic strings.

Understand the data passing through each stage.

---

# 57. PIPELINES CAN HIDE FAILURE ASSUMPTIONS

Suppose:

```bash
generate-data | process-data | save-data
```

If `generate-data` fails, what status does the overall pipeline report?

Shell behavior and options matter.

In Bash, by default, a pipeline's status is generally based on the final command, unless behavior such as `pipefail` is enabled. Verify exact semantics for the shell being used.

This matters because:

```text
upstream failure
```

can otherwise be obscured by:

```text
successful final command
```

---

# 58. `pipefail`

Bash supports:

```bash
set -o pipefail
```

With `pipefail`, a pipeline can report failure when a component fails rather than simply reflecting successful completion of the last command.

This can improve failure detection.

But do not add shell options mechanically without understanding how the script uses commands that legitimately return non-zero statuses.

---

# 59. TEXT PROCESSING

Shell scripts often process text using tools such as:

```text
grep

cut

sort

uniq

tr

sed

awk
```

These tools are useful.

But text parsing becomes fragile when scripts assume human-readable output is a stable machine interface.

---

# 60. PREFER STRUCTURED OUTPUT WHEN AVAILABLE

Suppose a CLI can output:

```text
human-readable table
```

or:

```text
JSON
```

For automation, structured output is often safer.

Example mental model:

```text
CLI
 ↓
JSON
 ↓
jq
 ↓
specific field
```

rather than:

```text
CLI table
 ↓
grep
 ↓
awk
 ↓
hope column spacing never changes
```

Use machine-readable interfaces when the tool provides them.

---

# 61. `grep`

`grep` searches text for patterns.

Example:

```bash
grep 'ERROR' application.log
```

Quiet mode can be useful when only the match result matters:

```bash
grep -q 'ERROR' application.log
```

Then test the exit status.

But understand `grep`'s documented exit behavior before treating every non-zero result as an execution failure.

---

# 62. `awk`

`awk` is a text-processing language commonly used for field-oriented data.

Example:

```bash
df -P / | awk 'NR==2 {print $5}'
```

This might extract filesystem usage from a predictable format.

But ask:

```text
Is this output format stable?

Could localization affect it?

Could headers change?

Could the selected filesystem differ?

Am I extracting the correct field?
```

Parsing should be deliberate.

---

# 63. `sed`

`sed` can transform streams of text.

For example:

```bash
sed 's/error/ERROR/g' file.txt
```

Before using in-place editing against configuration files, understand:

```text
backup requirements

platform differences

matching scope

what happens if pattern is absent

whether repeated execution changes the file again
```

---

# 64. `cut`, `sort`, AND `uniq`

These tools can compose simple data-processing workflows.

Example:

```bash
cut -d: -f1 /etc/passwd | sort
```

But the engineer should be able to explain:

```text
input format

delimiter

selected field

resulting output
```

A pipeline that nobody can explain is operational debt.

---

# 65. ERROR HANDLING

Weak script:

```bash
#!/usr/bin/env bash

cp config.conf /etc/example/config.conf
systemctl restart example
printf '%s\n' "Deployment complete"
```

What if `cp` fails?

Depending on shell behavior, the script may continue.

It might restart the service with the old configuration and then print:

```text
Deployment complete
```

That is misleading.

---

# 66. CHECK CRITICAL OPERATIONS

One approach:

```bash
if ! cp config.conf /etc/example/config.conf; then
    printf '%s\n' "ERROR: failed to install configuration" >&2
    exit 1
fi
```

Only continue when the prerequisite operation succeeds.

The key idea is not the exact syntax.

The key idea is:

```text
Critical Step
    ↓
Verify Result
    ↓
Continue or Stop
```

---

# 67. `&&` AND `||`

Shell operators can connect commands conditionally.

Example:

```bash
mkdir -p "$directory" && printf '%s\n' "Directory ready"
```

The second command runs only if the first succeeds.

You may also see:

```bash
command || exit 1
```

But long chains of `&&` and `||` can become difficult to reason about.

Prefer clarity over cleverness.

---

# 68. `set -e`

You will frequently encounter:

```bash
set -e
```

It is often described casually as:

> Exit whenever a command fails.

That description is too simplistic.

Bash's `errexit` behavior has important contextual rules and exceptions involving constructs such as condition tests, command lists, pipelines, and other shell contexts.

Therefore:

> Do not treat `set -e` as a substitute for understanding failure handling.

Use it only when you understand the script's control flow and have tested failure paths.

---

# 69. `set -u`

Bash supports:

```bash
set -u
```

which treats certain references to unset variables as errors.

This can catch mistakes such as:

```bash
printf '%s\n' "$SERVR_NAME"
```

when the intended variable was:

```text
SERVER_NAME
```

But scripts using optional variables must account for unset values intentionally.

---

# 70. `set -o pipefail`

As discussed earlier:

```bash
set -o pipefail
```

changes pipeline failure behavior.

It is commonly combined with other options.

You may encounter:

```bash
set -euo pipefail
```

in many scripts.

Do not teach yourself:

```text
set -euo pipefail
=
production-safe script
```

It does not validate inputs.

It does not create idempotency.

It does not protect destructive commands.

It does not verify postconditions.

It does not replace error handling.

---

# 71. STRICTER SHELL OPTIONS ARE TOOLS, NOT SAFETY CERTIFICATES

A script containing:

```bash
set -euo pipefail
```

can still contain:

```bash
rm -rf "$wrong_path"
```

The shell options do not understand your engineering intent.

Safety comes from the entire design.

---

# 72. ERROR HANDLING SHOULD BE INTENTIONAL

For every important operation ask:

```text
Can this fail?

How will I detect failure?

Should execution stop?

Should execution continue?

What state remains after failure?

What should the user see?

What exit status should the script return?

Can the operation be retried safely?
```

---

# 73. PARTIAL EXECUTION

Suppose a script performs:

```text
Step 1: create directory

Step 2: write configuration

Step 3: change ownership

Step 4: restart service

Step 5: verify health
```

If Step 3 fails:

```text
Steps 1 and 2 may already have changed the system.
```

The script has partially executed.

This is one of the central risks of automation.

---

# 74. AUTOMATION IS NOT AUTOMATICALLY TRANSACTIONAL

A shell script does not automatically roll back previous commands when a later command fails.

If:

```bash
command1
command2
command3
```

runs and `command3` fails, effects from `command1` and `command2` may remain.

Therefore:

```text
Script Failed
≠
System Returned to Original State
```

---

# 75. DESIGN FOR PARTIAL FAILURE

Possible approaches include:

```text
validate everything possible before mutation

make operations idempotent

use temporary files

perform atomic replacement where appropriate

create backups where appropriate

verify each critical transition

provide cleanup logic

document partial states

make retries safe
```

The exact strategy depends on the operation.

---

# 76. VALIDATE BEFORE MUTATING

Weak order:

```text
Delete old file
↓
Check whether new file exists
```

Better:

```text
Check new file exists
↓
Validate new file
↓
Confirm destination
↓
Perform controlled replacement
↓
Verify result
```

Move failures as early as possible before destructive actions.

---

# 77. IDEMPOTENCY

Idempotency is an important automation concept.

Informally, an idempotent operation can be applied repeatedly without continuing to produce unintended additional state changes once the desired state is reached.

Example desired state:

```text
Directory /opt/veriqta exists.
```

Using:

```bash
mkdir -p /opt/veriqta
```

is often more retry-friendly than logic that assumes the directory must not already exist.

---

# 78. IDEMPOTENCY IS ABOUT DESIRED STATE

Think:

```text
Current State
     ↓
Automation
     ↓
Desired State
```

Run again:

```text
Desired State
     ↓
Automation
     ↓
Desired State
```

The second execution should not create unnecessary damage or duplicate state.

---

# 79. NON-IDEMPOTENT EXAMPLE

Suppose:

```bash
printf '%s\n' "server1" >> servers.conf
```

Every execution appends:

```text
server1
```

After three runs:

```text
server1
server1
server1
```

If the desired state is:

> server1 should appear exactly once

then this implementation is not idempotent.

---

# 80. MORE IDEMPOTENT APPROACH

You might first inspect state:

```bash
if ! grep -Fxq 'server1' servers.conf; then
    printf '%s\n' 'server1' >> servers.conf
fi
```

Now repeated execution does not intentionally append the same line again.

But even this implementation has assumptions.

Ask:

```text
Can multiple script instances run simultaneously?

Does the file exist?

Are permissions correct?

Could comments or formatting matter?

Is exact-line matching appropriate?
```

Idempotency can become deeper than one conditional.

---

# 81. CREATE VERSUS ENSURE

This distinction is useful.

Imperative thinking:

```text
Create the directory.
```

Desired-state thinking:

```text
Ensure the directory exists with the expected ownership and permissions.
```

The second model encourages idempotent automation.

---

# 82. LOGGING

Operational scripts should communicate what they are doing.

Weak:

```bash
cp "$source" "$destination"
```

If it fails inside a larger workflow, the operator may not know which step was running.

Better:

```bash
printf '[INFO] Installing configuration: %s -> %s\n' \
    "$source" "$destination"
```

Then perform the action.

---

# 83. LOG LEVEL CONCEPTS

Simple scripts may use levels such as:

```text
INFO

WARN

ERROR
```

For example:

```bash
log_info() {
    printf '[INFO] %s\n' "$*"
}

log_warn() {
    printf '[WARN] %s\n' "$*" >&2
}

log_error() {
    printf '[ERROR] %s\n' "$*" >&2
}
```

Keep logging understandable.

Do not build an enormous logging framework for a ten-line script.

---

# 84. TIMESTAMPS

For scripts whose logs may be stored or correlated with incidents, timestamps can help.

Example:

```bash
log() {
    printf '%s %s\n' "$(date -u '+%Y-%m-%dT%H:%M:%SZ')" "$*"
}
```

This uses UTC and a clear timestamp representation.

If precise machine-readable timestamp behavior matters, verify the target system's `date` implementation and requirements.

---

# 85. DO NOT LOG SECRETS

Avoid logging:

```text
passwords

API tokens

private keys

authorization headers

full secret-bearing environment variables

sensitive command arguments
```

Debug logging can become a credential leak.

This includes AI-assisted debugging.

---

# 86. LOG ACTIONS, RESULTS, AND FAILURES

Useful logging answers:

```text
What was attempted?

Against what target?

Did it succeed?

If not, where did it fail?

What should the operator investigate next?
```

Avoid meaningless output such as:

```text
Something went wrong.
```

# 87. SCRIPT SAFETY

A safe operational script should consider:

```text

permissions

command dependencies

PATH

environment

current working directory

destructive operations

partial failure

idempotency

logging

exit codes

concurrency

cleanup

```

Not every script requires complex handling for all of these.

# 88. CURRENT WORKING DIRECTORY ASSUMPTIONS

Fragile script:

```bash

```

if the script assumes `config.yaml` is in the current working directory.

Running from another directory may fail or use the wrong file.

Ask:

```text
Should this path be relative to the caller's directory?

Relative to the script's directory?

Absolute?

Provided as an argument?
```

Make the assumption explicit.

---

# 89. SCRIPT DIRECTORY

For some Bash scripts, you may need to determine the script's own location rather than assume the caller's working directory.

This can become subtle with:

```text
symbolic links

sourcing

different invocation methods
```

Do not copy a complex "find my script directory" snippet from the Internet unless you understand the cases it handles.

For Junior scripts, prefer simple explicit paths or documented input when practical.

---

# 90. PATH DIFFERENCES

A script may work interactively but fail under:

```text
cron

systemd

CI/CD

SSH non-interactive sessions

containers

automation runners
```

because `PATH` differs.

Interactive shell configuration may not be loaded.

Therefore:

```text
Works in my terminal
≠
Works in automation
```

---

# 91. INSPECT PATH

Inside diagnostics:

```bash
printf 'PATH=%s\n' "$PATH"
```

Locate commands:

```bash
command -v curl
command -v jq
command -v systemctl
```

Do not assume a command is available simply because it exists on your workstation.

---

# 92. VALIDATE PREREQUISITES

Create a helper:

```bash
require_command() {
    local command_name="$1"

    if ! command -v "$command_name" >/dev/null 2>&1; then
        printf 'ERROR: required command not found: %s\n' \
            "$command_name" >&2
        return 1
    fi
}
```

Then:

```bash
require_command curl || exit 2
require_command jq || exit 2
```

Now missing dependencies fail early.

---

# 93. FAIL EARLY WHEN POSSIBLE

Compare:

```text
Run for 15 minutes
↓
Reach final step
↓
Discover jq missing
```

with:

```text
Validate prerequisites
↓
jq missing
↓
Exit immediately
```

Early validation reduces partial execution.

---

# 94. PERMISSIONS

A script may fail because:

```text
file is unreadable

directory is unwritable

script is not executable

service operation requires elevated privilege

user lacks access

filesystem is mounted read-only
```

Do not respond automatically with:

```bash
sudo ...
```

or:

```bash
chmod 777 ...
```

Investigate the actual permission requirement.

---

# 95. DO NOT HIDE PRIVILEGE REQUIREMENTS

If a script requires privileged operations, document them.

Ask whether the entire script needs privilege or only a specific operation.

Running everything as root increases blast radius.

Apply least privilege.

# 96. DESTRUCTIVE COMMANDS

Commands involving:

```text
rm

mv

truncate

filesystem formatting

recursive permission changes

service stopping

process termination

cloud deletion

Kubernetes deletion
```

require extra scrutiny.

Before destructive operations validate:

```text
target exists

target is expected

variable is non-empty

target is inside permitted scope

operation is actually required
```

---

# 97. NEVER TRUST A PATH VARIABLE BLINDLY

Dangerous pattern:

```bash
rm -rf "$target"
```

The quoting is good.

But quoting alone does not prove `$target` is correct.

You still need semantic validation.

For destructive automation:

```text
Correct Syntax
≠
Correct Target
```

---

# 98. SAFETY GUARDS

Suppose a lab script may clean a temporary directory.

You could require the target to match the expected lab path before deletion.

Conceptually:

```bash
if [[ "$target" != "/tmp/veriqta-lab" ]]; then
    printf 'ERROR: refusing unexpected target: %s\n' "$target" >&2
    exit 1
fi
```

Then perform the intended operation.

This is a guardrail.

It does not make arbitrary destructive scripts universally safe.

---

# 99. TEMPORARY FILES

Scripts sometimes require temporary files.

Do not casually use predictable filenames such as:

```text
/tmp/output.txt
```

when collisions or security matter.

Utilities such as:

```bash
mktemp
```

can create unique temporary files or directories.

Example:

```bash
tmp_file=$(mktemp)
```

But temporary resources should also be cleaned appropriately.

---

# 100. CLEANUP

A script may create temporary state that should be removed on exit.

Bash provides:

```bash
trap
```

for executing commands in response to signals or shell events.

A simple pattern:

```bash
tmp_file=$(mktemp)

cleanup() {
    rm -f -- "$tmp_file"
}

trap cleanup EXIT
```

The script now attempts cleanup when it exits normally or through many error paths that trigger the EXIT trap.

---

# 101. `trap` REQUIRES CARE

Trap code has its own quoting and expansion behavior.

For example, whether variables or command substitutions expand when the trap is defined or when it runs depends on how the trap command is quoted. ShellCheck specifically warns about accidental early expansion in trap definitions.

Prefer calling a defined cleanup function when possible because it is easier to read and reason about.

---

# 102. SIGNALS

Part 4 introduced signals from the Linux process perspective.

Scripts may receive signals such as:

```text
SIGINT

SIGTERM
```

Operational scripts should consider interruption.

If interrupted after:

```text
Step 1 completed

Step 2 completed

Step 3 partially completed
```

what state remains?

Signal handling is not just about printing:

```text
Interrupted.
```

It is about understanding partial execution.

---

# 103. DO NOT ASSUME CLEANUP ALWAYS RUNS

Some process termination conditions cannot be trapped or handled normally.

System crashes, abrupt power loss, and uncatchable termination conditions can leave state behind.

Therefore:

```text
Cleanup Handler
≠
Transactional Guarantee
```

Design important operations so recovery does not depend entirely on cleanup code executing.

---

# 104. VALIDATION VERSUS VERIFICATION

These words serve different purposes here.

Before action:

```text
Validation
```

asks:

> Are the inputs and prerequisites acceptable?

After action:

```text
Verification
```

asks:

> Did the system reach the expected state?

Example:

```text
Validate configuration file exists
        ↓
Install configuration
        ↓
Restart service
        ↓
Verify service is active
```

---

# 105. COMMAND SUCCESS IS NOT ALWAYS OUTCOME SUCCESS

Suppose:

```bash
systemctl restart example
```

returns success.

Does that prove the application is serving users correctly?

No.

You may still need to verify:

```text
service active

process exists

port listening

health endpoint succeeds

application logs clean

dependency connectivity works
```

depending on the operation.

This connects automation directly to the troubleshooting discipline from Parts 4 and 5.

---

# 106. ACTION → EXPECTED STATE → INSPECTION → EVIDENCE → CONCLUSION

Every important automation should support this model:

```text
Action
↓
Expected State
↓
Inspection
↓
Evidence
↓
Conclusion
```

Example:

```text
Action:
restart nginx

Expected State:
nginx becomes active

Inspection:
systemctl is-active nginx

Evidence:
command reports active and appropriate success status

Conclusion:
systemd considers nginx active
```

Notice the conclusion is deliberately narrow.

It does not claim:

```text
The entire website is healthy.
```

That would require more evidence.

# 151. `eval` REQUIRES EXTREME CAUTION

`eval` causes shell text to be interpreted again as shell code.

This can create serious correctness and injection risks when strings contain uncontrolled data.

Do not use `eval` merely because storing complex commands in strings became difficult.

Use:

```text
functions

arrays

explicit arguments
```

where appropriate.

ShellCheck specifically recommends arrays rather than storing quoted command arguments in a string and later trying to reinterpret them.

---

# 152. COMMANDS ARE NOT STRINGS

This is a fundamental shell principle.

Suppose you want arguments:

```text
-lh

My File.txt
```

Do not assume:

```bash
args='-lh "My File.txt"'
```

can later be expanded and interpreted exactly like shell source code.

The quotes inside the variable are data at that point, not necessarily shell syntax that will recreate the intended argument boundaries. ShellCheck documents this distinction directly.

For Bash, arrays are often the correct representation for argument lists.

---

# 153. ARRAYS FOR ARGUMENTS

Example:

```bash
args=(
    -H
    "Content-Type: application/json"
    --max-time
    "10"
)
```

Then:

```bash
curl "${args[@]}" "https://example.invalid"
```

Each array element remains one argument.

This is safer than constructing one large command string.

# 169. REFERENCE IMPLEMENTATION

```bash
#!/usr/bin/env bash

# Purpose:
#   Perform basic read-only Linux health checks.
#
# Usage:
#   ./system-check.sh SERVICE_NAME
#
# Exit codes:
#   0 - all checks passed
#   1 - one or more operational checks failed
#   2 - invalid usage or missing prerequisite

readonly DISK_THRESHOLD=80

log_info() {
    printf '[INFO] %s\n' "$*"
}

log_error() {
    printf '[ERROR] %s\n' "$*" >&2
}

usage() {
    printf 'Usage: %s SERVICE_NAME\n' "$0" >&2
}

require_command() {
    local command_name="$1"

    if ! command -v "$command_name" >/dev/null 2>&1; then
        log_error "Required command not found: $command_name"
        return 1
    fi
}

check_prerequisites() {
    local failed=0
    local command_name

    for command_name in systemctl df awk hostname uptime; do
        if ! require_command "$command_name"; then
            failed=1
        fi
    done

    return "$failed"
}

check_service() {
    local service_name="$1"

    if systemctl is-active --quiet "$service_name"; then
        log_info "Service is active: $service_name"
        return 0
    fi

    log_error "Service is not active: $service_name"
    return 1
}

get_root_usage() {
    df -P / | awk 'NR == 2 {gsub("%", "", $5); print $5}'
}

check_disk() {
    local usage

    usage=$(get_root_usage)

    if [[ ! "$usage" =~ ^[0-9]+$ ]]; then
        log_error "Unable to determine root filesystem usage"
        return 1
    fi

    if (( usage >= DISK_THRESHOLD )); then
        log_error "Root filesystem usage is ${usage}% (threshold: ${DISK_THRESHOLD}%)"
        return 1
    fi

    log_info "Root filesystem usage is ${usage}%"
    return 0
}

show_system_info() {
    log_info "Hostname: $(hostname)"
    log_info "Uptime: $(uptime)"
}

main() {
    local service_name
    local failed=0

    if [[ $# -ne 1 ]]; then
        usage
        return 2
    fi

    service_name="$1"

    if ! check_prerequisites; then
        return 2
    fi

    show_system_info

    if ! check_service "$service_name"; then
        failed=1
    fi

    if ! check_disk; then
        failed=1
    fi

    if (( failed != 0 )); then
        log_error "One or more checks failed"
        return 1
    fi

    log_info "All checks passed"
    return 0
}

main "$@"
```

```text
7. Use meaningful exit statuses.

8. Avoid state-changing operations.

9. Run bash syntax checking.

10. Run ShellCheck if available.

11. Test the normal path.

12. Test missing arguments.

13. Test missing files.

14. Test invalid services.

15. Test filenames containing spaces.

16. Test a missing prerequisite in a controlled environment.

17. Explain every pipeline.

18. Explain every external command.

19. Explain every assumption.

20. Verify the script fails safely.
```

# 201. FINAL ENGINEERING PRINCIPLE

The most important lesson from this Part is not Bash syntax.

It is this:

> Automation multiplies whatever engineering quality already exists in the procedure.

If the procedure is:

```text
understood

bounded

validated

observable

recoverable

verifiable
```

automation can make it reliably repeatable.

If the procedure is:

```text
unclear

unsafe

unverified

overprivileged

destructive

dependent on hidden assumptions
```

automation can make the failure faster and larger.

Therefore:

```text
Automation
≠
Safety
```

and:

```text
Automation
≠
Reliability
```

Instead:

```text
Understand
    ↓
Validate
    ↓
Automate
    ↓
Observe
    ↓
Verify
```
