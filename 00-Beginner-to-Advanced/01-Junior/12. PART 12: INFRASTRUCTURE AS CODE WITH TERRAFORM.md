# PART 12: INFRASTRUCTURE AS CODE WITH TERRAFORM

## Goal

Understand declarative infrastructure and safely perform basic infrastructure changes using Terraform.

By the end of this Part, the learner should understand that Terraform is not simply a command that creates cloud resources.

Terraform is part of an infrastructure change system involving:

```text
Configuration
    ↓
Terraform
    ↓
Provider
    ↓
Infrastructure API
    ↓
Resource
    ↓
State
```

A more complete operational model is:

```text
Engineering Requirement
        ↓
Terraform Configuration
        ↓
Format
        ↓
Initialize
        ↓
Validate
        ↓
Plan
        ↓
Human Review
        ↓
Apply
        ↓
Provider
        ↓
Infrastructure API
        ↓
Real Resource
        ↓
Terraform State
        ↓
Independent Verification
```

The learner should be able to answer:

```text
What infrastructure is Terraform expected to manage?

Which configuration declares it?

Which provider implements the resource type?

Which credentials will Terraform use?

Which account, project, subscription, region, or environment
will receive the change?

What does Terraform currently know through state?

What does the plan propose?

Which resources will be created?

Which resources will be changed?

Which resources will be replaced?

Which resources will be destroyed?

Why is Terraform proposing each action?

What is the blast radius?

Did the apply complete?

Does the real infrastructure now match the intended state?

How do I prove that?
```

The central engineering principle of this Part is:

> Never treat `terraform apply` as the first step in understanding a Terraform change.

The normal reasoning path is:

```text
Understand
    ↓
Format
    ↓
Initialize
    ↓
Validate
    ↓
Plan
    ↓
Inspect
    ↓
Approve
    ↓
Apply
    ↓
Verify
```

And the most important distinction is:

```text
terraform plan completed
≠
change is safe
```

Likewise:

```text
terraform apply completed
≠
infrastructure is proven correct
```

---

# 1. THE INFRASTRUCTURE PROBLEM

In Part 9, the learner created and operated basic cloud resources.

That may have involved actions such as:

```text
Open cloud console

Choose region

Create virtual network

Create subnet

Create compute resource

Configure network access

Add tags

Start application

Verify resource

Delete resource
```

This is useful for learning cloud concepts.

But imagine operating:

```text
10 resources

100 resources

1,000 resources

multiple environments

multiple engineers

multiple cloud accounts
```

Now manual infrastructure management becomes increasingly difficult.

Questions appear:

```text
Who created this resource?

Why does it exist?

Which settings were intended?

Was staging configured the same way as production?

Who changed the firewall rule?

What was the previous value?

Can we reproduce this environment?

Can another engineer review the change before it happens?

Can we see what Terraform intends to change?

Can we recreate the infrastructure after a failure?
```

Infrastructure as Code exists partly to make infrastructure change more explicit, repeatable, reviewable, and automatable.

---

# 2. MANUAL INFRASTRUCTURE

Manual infrastructure management might look like:

```text
Engineer
   ↓
Cloud Console
   ↓
Click
   ↓
Click
   ↓
Enter Value
   ↓
Create
```

The cloud resource is real.

But the engineering intent may exist only in:

```text
someone's memory

a ticket

a screenshot

an outdated document

the current resource configuration
```

That creates operational risk.

---

# 3. THE "CLICKOPS" PROBLEM

The informal term:

```text
ClickOps
```

is often used for infrastructure operated primarily through graphical interfaces.

The problem is not that graphical consoles are inherently bad.

Cloud consoles are extremely useful for:

```text
learning

inspection

troubleshooting

verification

exploration
```

The problem appears when important infrastructure changes depend on undocumented manual actions.

---

# 4. MANUAL CHANGES ARE HARDER TO REVIEW BEFORE EXECUTION

Suppose an engineer intends to change:

```text
TCP port 443 only
```

but accidentally configures:

```text
all ports from all sources
```

With a manual console workflow, the mistake may become real immediately.

With an IaC workflow, the proposed change can potentially be reviewed before execution.

Conceptually:

```text
Configuration Change
       ↓
Terraform Plan
       ↓
Review
       ↓
Apply
```

This does not guarantee safety.

It creates an opportunity for safer review.

---

# 5. INFRASTRUCTURE AS CODE

Infrastructure as Code, or IaC, means managing infrastructure through machine-readable configuration rather than relying exclusively on manual configuration.

Infrastructure definitions can then participate in engineering practices such as:

```text
version control

code review

automated validation

change history

CI/CD

repeatable execution
```

---

# 6. IAC DOES NOT MEAN "NO MANUAL OPERATIONS"

Infrastructure engineers still use:

```text
cloud consoles

CLI tools

API clients

monitoring systems

debugging tools
```

The goal is not:

```text
Never touch the console.
```

The goal is to make the intended managed infrastructure reproducible and reviewable.

---

# 7. TERRAFORM

Terraform is an Infrastructure as Code tool.

Terraform reads configuration describing infrastructure and interacts with providers that communicate with external APIs.

Terraform itself is not:

```text
AWS

Azure

Google Cloud

Kubernetes

GitHub

Docker
```

Terraform interacts with platforms through providers.

---

# 8. THE CORE TERRAFORM MODEL

The basic model is:

```text
Terraform Configuration
        ↓
Terraform Core
        ↓
Provider Plugin
        ↓
Platform API
        ↓
Infrastructure Resource
```

Terraform also maintains:

```text
State
```

to track relationships between Terraform resource instances and real infrastructure objects.

---

# 9. TERRAFORM IS DECLARATIVE

Terraform configuration is primarily declarative.

You describe the desired infrastructure.

Conceptually:

```text
I want:

one network

one subnet

one compute instance

one security rule
```

rather than writing every low-level API operation manually.

Terraform determines the operations required to move managed infrastructure toward the desired configuration.

---

# 10. DECLARATIVE VERSUS IMPERATIVE THINKING

Imperative thinking emphasizes steps:

```text
Create network

Create subnet

Create instance

Attach interface

Configure rule
```

Declarative thinking emphasizes desired state:

```text
These resources should exist
with these relationships
and these settings.
```

Terraform then determines an execution plan.

---

# 11. DECLARATIVE DOES NOT MEAN ORDER DOES NOT MATTER

Resources can depend on other resources.

For example:

```text
Virtual Network
      ↓
Subnet
      ↓
Network Interface
      ↓
Compute Instance
```

Terraform builds dependency relationships and uses them when determining operation order.

---

# 12. TERRAFORM CONFIGURATION LANGUAGE

Terraform configurations use the Terraform language.

Files conventionally use:

```text
.tf
```

extensions.

Example files might include:

```text
terraform.tf

providers.tf

main.tf

variables.tf

outputs.tf
```

These filenames are organizational conventions.

Terraform generally evaluates the configuration files in the working directory as one configuration rather than executing them sequentially by filename.

---

# 13. TERRAFORM FILES ARE NOT SHELL SCRIPTS

Do not think:

```text
main.tf runs first

variables.tf runs second

outputs.tf runs third
```

That is the wrong model.

Think:

```text
Terraform reads the configuration
        ↓
Builds its understanding
        ↓
Constructs dependency relationships
        ↓
Determines proposed operations
```

---

# 14. HCL

Terraform configuration is commonly written using HashiCorp Configuration Language syntax.

Example:

```hcl
resource "example_resource" "application" {
  name = "veriqta-lab"
}
```

The exact resource type and arguments depend on the provider.

Do not invent provider arguments.

Always verify them against the documentation for the provider version being used.

---

# 15. BLOCKS

Terraform configuration uses blocks.

Examples include:

```text
terraform

provider

resource

data

variable

output
```

Each has a different purpose.

---

# 16. THE `terraform` BLOCK

The `terraform` block can define Terraform-level settings such as:

```text
required Terraform version

required providers

backend configuration
```

Example structure:

```hcl
terraform {
  required_version = "..."

  required_providers {
    ...
  }
}
```

The exact version constraints should reflect the tested environment.

---

# 17. VERSION CONSTRAINTS

Infrastructure behavior can depend on:

```text
Terraform version

provider version

module version
```

Therefore, versions should not be treated casually.

A configuration tested with one provider version may behave differently after a major provider upgrade.

---

# 18. TERRAFORM VERSION

Inspect the installed Terraform version:

```bash
terraform version
```

Expected result:

```text
Terraform reports its installed version.
```

If the command is not found, Terraform may:

```text
not be installed

not be in PATH
```

Do not continue until the execution environment is understood.

---

# 19. PROVIDERS

Terraform providers are plugins that allow Terraform to interact with external systems.

Examples of provider categories include:

```text
cloud platforms

SaaS platforms

infrastructure platforms

utility providers
```

The important model is:

```text
Terraform
    ↓
Provider
    ↓
External API
```

Terraform providers are distributed separately from Terraform and have their own release versions.

---

# 20. PROVIDER RESPONSIBILITY

A provider defines the resource types and data sources Terraform can use for that platform.

Conceptually:

```text
Provider
   ├── Resource Type A
   ├── Resource Type B
   ├── Resource Type C
   ├── Data Source A
   └── Data Source B
```

Terraform Core does not independently know how every cloud API works.

The provider implements that interaction.

---

# 21. PROVIDER CONFIGURATION

Providers may require configuration such as:

```text
region

project

subscription

endpoint

credentials
```

Some configuration can also come from environment variables or provider-specific authentication mechanisms.

The exact behavior is provider-specific.

---

# 22. PROVIDER AUTHENTICATION

Terraform must ultimately authenticate to the platform it is changing.

For cloud infrastructure:

```text
Terraform
   ↓
Provider
   ↓
Credential / Identity
   ↓
Cloud API
```

If authentication fails, Terraform cannot successfully perform protected API operations.

---

# 23. AUTHENTICATION IS NOT AUTHORIZATION

Recall from previous Parts:

```text
Authentication
=
Who are you?
```

```text
Authorization
=
What are you allowed to do?
```

Terraform may authenticate successfully and still receive:

```text
permission denied

access denied

forbidden
```

because the identity lacks required authorization.

---

# 24. VERIFY IDENTITY BEFORE INFRASTRUCTURE CHANGE

Before running Terraform against cloud infrastructure, determine:

```text
Which identity am I using?

Which account?

Which project?

Which subscription?

Which region?

Which environment?
```

Do not discover this after applying the change.

---

# 25. RESOURCE

A Terraform `resource` block declares infrastructure Terraform is expected to manage.

Generic structure:

```hcl
resource "provider_resource_type" "local_name" {
  # arguments
}
```

Example conceptual address:

```text
resource_type.application
```

The first label identifies the resource type.

The second label is Terraform's local name for that resource block.

---

# 26. RESOURCE ADDRESS

Suppose a configuration contains:

```hcl
resource "example_server" "web" {
  name = "veriqta-web"
}
```

The conceptual Terraform resource address is:

```text
example_server.web
```

This address identifies the resource instance within Terraform configuration and state.

It is not necessarily the same as the remote platform's resource ID.

---

# 27. LOCAL NAME VERSUS REMOTE NAME

These can differ.

For example:

```text
Terraform address:
example_server.web
```

Remote object:

```text
veriqta-junior-lab-web
```

Terraform state helps maintain the relationship between Terraform's resource instance and the remote object.

---

# 28. RESOURCE ARGUMENTS

Resource arguments describe desired configuration.

For example, depending on provider:

```text
name

region

size

network

tags
```

The available arguments are defined by the provider.

Never assume an argument exists because another provider uses a similar term.

---

# 29. RESOURCE ATTRIBUTES

After creation, resources may expose attributes such as:

```text
ID

IP address

hostname

status
```

Some values may not be known until the provider creates or reads the resource.

Terraform may display such values during planning as values that are known only after apply.

---

# 30. DATA SOURCES

A data source allows Terraform to read information from an external system without managing that object as a Terraform-created resource.

Conceptually:

```text
Existing Infrastructure
       ↓
Provider Query
       ↓
Data Source
       ↓
Terraform Configuration
```

Terraform data sources are read-oriented; depending on dependencies and whether values are known, some reads occur during planning and some can be deferred until apply.

---

# 31. RESOURCE VERSUS DATA SOURCE

Think:

```text
Resource
=
Terraform manages an object's lifecycle
```

```text
Data Source
=
Terraform reads information for use in configuration
```

This distinction is foundational.

---

# 32. DATA SOURCE EXAMPLE

Suppose a network already exists and another team owns it.

Your Terraform configuration may need information about that network without creating or deleting it.

Conceptually:

```text
Existing Shared Network
       ↓
Data Source
       ↓
Network ID
       ↓
Application Resource
```

Do not create duplicate infrastructure merely because Terraform needs to reference existing infrastructure.

---

# 33. VARIABLES

Input variables allow configuration to receive values.

Example:

```hcl
variable "environment" {
  type        = string
  description = "Deployment environment name"
}
```

Then:

```text
var.environment
```

references that value.

---

# 34. WHY VARIABLES EXIST

Without variables:

```hcl
name = "veriqta-dev"
```

might be repeated throughout configuration.

Variables allow intentional inputs such as:

```text
environment

region

instance size

application name
```

But not every value needs to become a variable.

---

# 35. OVER-VARIABLEIZATION

Avoid turning every literal into a variable merely because Terraform supports variables.

A configuration containing dozens of unnecessary variables can become difficult to understand.

Ask:

```text
Is this value expected to vary?

Who should choose it?

What constraints apply?

Does exposing it improve reuse or create unnecessary complexity?
```

---

# 36. VARIABLE TYPES

Terraform variables can declare types.

Examples include:

```text
string

number

bool

list

set

map

object
```

At Junior level, start with simple types.

Explicit types make expected input clearer.

---

# 37. VARIABLE DESCRIPTIONS

Variables should explain their purpose.

Better:

```hcl
variable "environment" {
  type        = string
  description = "Environment name used for lab resource identification"
}
```

rather than:

```hcl
variable "environment" {
  type = string
}
```

The description becomes part of the configuration's interface.

---

# 38. VARIABLE DEFAULTS

Variables can have default values.

Example:

```hcl
variable "environment" {
  type        = string
  description = "Environment name"
  default     = "lab"
}
```

If no default exists, Terraform normally requires the value to come from another supported input mechanism.

---

# 39. VARIABLE INPUT SOURCES

Depending on workflow, values may come from:

```text
defaults

variable files

command-line options

environment variables

automation systems
```

The exact precedence rules should be checked in current Terraform documentation when they matter.

Do not guess which value Terraform selected.

---

# 40. VARIABLE VALIDATION

Input variables can include validation rules.

Conceptually:

```text
Input
   ↓
Validation Rule
   ↓
Accept / Reject
```

This can prevent obviously invalid inputs from progressing further.

---

# 41. OUTPUTS

Output values expose selected information from Terraform configuration.

Example:

```hcl
output "application_name" {
  value = var.application_name
}
```

Outputs can help expose:

```text
resource IDs

IP addresses

hostnames

URLs

other useful values
```

---

# 42. OUTPUTS ARE AN INTERFACE

Think of outputs as deliberate information exposed by a Terraform configuration.

They can be useful to:

```text
humans

automation

other configurations
```

Do not expose sensitive information unnecessarily.

---

# 43. RESOURCE REFERENCES

Terraform expressions can reference attributes from other resources.

Conceptually:

```text
Network
   ↓
Network ID
   ↓
Subnet
```

Rather than manually copying a network ID, the subnet configuration can reference the managed network resource.

---

# 44. IMPLICIT DEPENDENCIES

When one resource references another resource's attributes, Terraform can infer a dependency.

Conceptually:

```text
resource A
   ↓
attribute reference
   ↓
resource B
```

Terraform understands that B depends on information from A.

---

# 45. DEPENDENCY GRAPH

Terraform uses dependency relationships to determine valid operation ordering.

For example:

```text
Network
   ↓
Subnet
   ↓
Compute
```

Terraform can create independent resources concurrently where appropriate.

It does not simply process resource blocks from top to bottom.

---

# 46. EXPLICIT DEPENDENCIES

Terraform also provides mechanisms such as:

```text
depends_on
```

for dependencies Terraform cannot infer from normal references.

Do not add explicit dependencies everywhere.

Use them when a real dependency exists but is not otherwise visible to Terraform.

---

# 47. DEPENDENCY IS NOT FILE ORDER

This:

```text
network.tf
server.tf
```

does not mean:

```text
network.tf always executes first.
```

Terraform follows dependency relationships, not filename execution order.

---

# 48. STATE

State is one of the most important Terraform concepts.

Terraform must remember relationships between:

```text
configuration resource instances
```

and:

```text
real infrastructure objects
```

Terraform uses state to track those bindings and metadata needed to manage infrastructure.

---

# 49. STATE MENTAL MODEL

Think:

```text
Terraform Configuration
        │
        │
        ▼
Terraform State
        │
        │ maps
        ▼
Real Infrastructure
```

State helps Terraform answer:

```text
Which real object corresponds to this resource block?
```

---

# 50. STATE IS NOT JUST A CACHE

A dangerous beginner assumption is:

```text
terraform.tfstate is just temporary output.
```

It is not.

State is operationally important.

Losing, corrupting, exposing, or incorrectly modifying state can create serious infrastructure management problems.

---

# 51. LOCAL STATE

With the default local backend, Terraform stores state locally, commonly in:

```text
terraform.tfstate
```

and may maintain a backup file.

Local state is useful for simple learning exercises.

It is generally unsuitable as the collaboration model for serious team-managed infrastructure.

---

# 52. NEVER COMMIT STATE CASUALLY

Terraform state can contain:

```text
resource metadata

identifiers

infrastructure attributes

potentially sensitive values
```

State should not simply be committed to Git.

HashiCorp explicitly recommends against storing state in ordinary version control.

---

# 53. STATE MAY CONTAIN SECRETS

This is critical.

Even when Terraform hides a value from normal CLI output because it is marked:

```text
sensitive
```

the value can still exist in state.

Therefore:

```text
sensitive = true
```

does not mean:

```text
secret does not exist in state
```

HashiCorp's current documentation explicitly distinguishes output redaction from state storage.

---

# 54. DO NOT MANUALLY EDIT STATE

State is JSON-formatted data, but that does not mean:

```text
open terraform.tfstate
edit whatever looks wrong
save
```

is an appropriate repair strategy.

Terraform provides state-management commands for controlled state operations.

Manual state manipulation is outside the normal Junior workflow.

---

# 55. CONFIGURATION, STATE, AND REALITY

The learner must distinguish three things:

```text
Configuration
=
what you declared
```

```text
State
=
Terraform's recorded mapping and known information
```

```text
Real Infrastructure
=
what actually exists in the external platform
```

These are related.

They are not identical.

---

# 56. THE THREE-WAY MODEL

Use:

```text
Desired Configuration
        ↓
Terraform
        ↕
State
        ↕
Provider/API
        ↓
Real Infrastructure
```

Many Terraform problems become easier once you ask which of these layers is inconsistent.

---

# 57. INITIALIZATION

Before normal Terraform operations, initialize the working directory:

```bash
terraform init
```

Initialization prepares the working directory.

It can:

```text
initialize backend configuration

install required providers

download required modules

prepare Terraform's working metadata
```

Terraform initialization is designed to be safe to run repeatedly.

---

# 58. `.terraform` DIRECTORY

Initialization commonly creates:

```text
.terraform/
```

This directory contains Terraform-managed working data such as cached provider plugins and module information.

Do not treat it as project source code.

---

# 59. DEPENDENCY LOCK FILE

Initialization can create:

```text
.terraform.lock.hcl
```

This records provider dependency selections and checksums.

Unlike:

```text
.terraform/
```

the dependency lock file is normally appropriate to commit to version control.

This helps teams make provider selection more consistent.

---

# 60. INITIALIZATION IS NOT INFRASTRUCTURE CREATION

Running:

```bash
terraform init
```

does not mean:

```text
cloud resources were created
```

Its purpose is preparing the Terraform working directory.

Keep lifecycle stages separate.

---

# 61. INITIALIZATION FAILURE

`terraform init` can fail because of:

```text
network connectivity

provider registry access

invalid provider source

unsupported provider version constraints

backend configuration

backend authentication

module source access
```

Do not jump directly to:

```text
cloud resource problem
```

when initialization has not even completed.

---

# 62. INITIALIZATION TROUBLESHOOTING

Ask:

```text
Which initialization step failed?

Provider installation?

Module download?

Backend initialization?

Authentication?

Network access?

Version resolution?
```

Read the exact error.

---

# 63. FORMATTING

Terraform provides:

```bash
terraform fmt
```

to rewrite Terraform configuration into its canonical formatting style.

This improves consistency and readability.

---

# 64. FORMAT CHECK

In automation, you may want to check formatting without silently changing files.

Use the supported `terraform fmt` options appropriate to the workflow.

Before relying on flags, verify them against the installed Terraform version.

---

# 65. FORMATTING DOES NOT VALIDATE INFRASTRUCTURE

A configuration can be perfectly formatted and still be:

```text
invalid

unsafe

incorrect

targeting wrong environment
```

Therefore:

```text
terraform fmt
≠
terraform validate
≠
terraform plan
≠
terraform apply
```

Each answers a different question.

---

# 66. VALIDATION

Run:

```bash
terraform validate
```

to validate the configuration's syntax and internal consistency.

Terraform validation does not validate remote infrastructure APIs or prove the proposed infrastructure is operationally correct.

---

# 67. VALIDATION REQUIRES INITIALIZATION

For configurations using providers or modules, validation requires an initialized working directory.

Therefore a common development flow is:

```text
terraform init
      ↓
terraform fmt
      ↓
terraform validate
```

---

# 68. VALID CONFIGURATION DOES NOT MEAN SAFE CONFIGURATION

Terraform can consider a configuration valid even if it declares:

```text
an expensive resource

an overly permissive network rule

the wrong region

the wrong instance size

a destructive change
```

Validation checks Terraform configuration correctness.

It does not understand every organizational intention.

---

# 69. PLAN

Run:

```bash
terraform plan
```

to create an execution plan.

A plan describes the changes Terraform proposes to make to move managed infrastructure toward the declared configuration.

Running `terraform plan` by itself does not execute the proposed infrastructure changes.

---

# 70. PLAN IS THE REVIEW BOUNDARY

This is one of the most important concepts in Terraform.

Do not think:

```text
Plan
=
Preview I can ignore
```

Think:

```text
Configuration Change
       ↓
Plan
       ↓
Proposed Infrastructure Actions
       ↓
Engineering Review
```

---

# 71. PLAN ACTIONS

A Terraform plan may propose actions such as:

```text
create

update in place

replace

destroy
```

The exact output symbols and formatting depend on Terraform's CLI representation.

The learner must read the action summary and the individual resource changes.

---

# 72. CREATE

Conceptually:

```text
+ create
```

means Terraform proposes creating a managed object that does not currently exist as required by the configuration/state relationship.

Before approval ask:

```text
Did I expect this resource?

Is it in the correct environment?

Is the configuration correct?

What will it cost?

What access will it create?
```

---

# 73. UPDATE IN PLACE

An update can modify an existing resource without replacing its identity.

Conceptually:

```text
existing resource
      ↓
change selected attributes
      ↓
same managed object continues
```

Do not assume an update is harmless.

A network rule change can have substantial impact even without replacement.

---

# 74. REPLACEMENT

Some changes cannot be made in place.

Terraform may propose:

```text
destroy existing object

create replacement object
```

or an ordering supported by the provider and lifecycle configuration.

Replacement can be high impact.

---

# 75. WHY REPLACEMENT MATTERS

Suppose Terraform proposes replacing:

```text
database

compute instance

network component
```

The consequences may include:

```text
downtime

data risk

new identifiers

new IP addresses

dependency impact
```

A plan showing replacement deserves careful review.

---

# 76. DESTROY

Terraform may propose destroying a resource.

This can occur because:

```text
resource removed from configuration

resource replaced

destroy operation requested

configuration changed in a way requiring replacement
```

Never approve destruction merely because Terraform proposed it.

Understand why.

---

# 77. PLAN SUMMARY

Terraform commonly summarizes the proposed actions.

For example conceptually:

```text
Plan:
2 to add,
1 to change,
1 to destroy
```

Do not read only the summary.

You must inspect the resources and attributes involved.

---

# 78. THE PLAN REVIEW STANDARD

For every planned resource action, identify:

```text
resource address

action

reason

important changed attributes

dependencies

environment

expected impact

whether action matches intent
```

If you cannot explain an action, stop.

---

# 79. "I DIDN'T CHANGE THAT" IS A WARNING

If Terraform proposes changing a resource you did not expect:

```text
STOP
```

Investigate.

Possible explanations include:

```text
configuration change

variable change

provider behavior

provider upgrade

state difference

real infrastructure drift

wrong workspace/environment

wrong input file

dependency change
```

Unexpected plans are evidence.

---

# 80. APPLY

Run:

```bash
terraform apply
```

to execute a Terraform plan.

If no saved plan is provided, Terraform normally creates a new plan and requests approval before executing it.

---

# 81. APPLY IS A MUTATING OPERATION

Unlike:

```text
fmt

validate

plan
```

an apply can change real infrastructure.

Treat it accordingly.

Before applying:

```text
verify identity

verify environment

verify inputs

review plan

understand actions

understand blast radius
```

---

# 82. DO NOT TYPE `yes` AUTOMATICALLY

Terraform's approval prompt is not a ritual.

It is a decision boundary.

Before approval, the engineer should be able to state:

```text

I expect Terraform to update Y.

I expect no replacement.

I expect no destruction.
```

Then compare that expectation with the actual plan.

# 95. DRIFT

Drift occurs when real infrastructure differs from the intended or recorded Terraform-managed state/configuration relationship.

A common cause is changing Terraform-managed infrastructure outside Terraform.

Example:

```text
Terraform configuration:
port 443 allowed
```

Someone manually changes cloud console:

```text
port 22 allowed
```

Now reality has diverged from the declared configuration.

---

# 96. DRIFT MENTAL MODEL

```text
Terraform Configuration
        │
        │ expected
        ▼
Infrastructure
```

Manual change:

```text
Cloud Console
     ↓
Infrastructure Changes
     ↓
Configuration unchanged
```

Now:

```text
Declared State
≠
Observed Infrastructure
```

A later Terraform operation can detect relevant differences and propose reconciliation.

---

# 97. DRIFT IS NOT ALWAYS MALICIOUS

Drift can happen because of:

```text
manual emergency change

console troubleshooting

another automation system

provider/platform behavior

external controller

configuration mistake
```

The important question is:

```text
Why did reality diverge?
```

---

# 98. DO NOT "FIX" DRIFT BLINDLY

Suppose Terraform plans to revert a manual infrastructure change.

Do not immediately apply.

The manual change might have been:

```text
an emergency security control

an incident mitigation

a temporary operational repair
```

Investigate first.

---

# 99. STATE AWARENESS

A Junior engineer does not need advanced state surgery.

But they must understand:

```text
State exists.

State matters.

State may contain sensitive information.

State maps Terraform resources to real objects.

State must be protected.

State should not be casually edited.

Wrong state can mean wrong infrastructure actions.
```

---

# 100. REMOTE STATE

For team workflows, state is commonly stored remotely rather than only on one engineer's laptop.

Conceptually:

```text
Engineer A ─┐
            │
Engineer B ─┼── Terraform Backend ── State
            │
CI/CD ──────┘
```

Remote state allows team members and automation to work against a shared state location.

---

# 101. BACKEND

A Terraform backend determines how Terraform handles state storage and, depending on backend capabilities, state locking.

Examples can include:

```text
HCP Terraform

object storage backends

other supported remote systems
```

The exact backend depends on architecture.

---

# 102. STATE LOCKING CONCEPT

Imagine:

```text
Engineer A
terraform apply
```

while simultaneously:

```text
Engineer B
terraform apply
```

against the same infrastructure state.

Concurrent changes can create dangerous coordination problems.

State locking, where supported, helps prevent conflicting state operations.

Not every backend has identical locking behavior or capabilities.

---

# 103. REMOTE STATE IS NOT AUTOMATICALLY SECURE

A remote backend still requires:

```text
access control

encryption strategy

credential protection

backup/recovery consideration

locking where appropriate

auditability
```

Do not assume:

```text
remote
=
secure
```

---

# 104. STATE ACCESS IS PRIVILEGED ACCESS

Anyone who can read Terraform state may gain access to:

```text
infrastructure identifiers

internal configuration

sensitive values
```

Therefore state access should follow least privilege.

---

# 105. SENSITIVE VARIABLES

Terraform variables can be marked:

```hcl
sensitive = true
```

This helps redact values from normal CLI presentation.

But it does not necessarily prevent those values from being stored in state.

---

# 106. SENSITIVE OUTPUTS

Outputs containing sensitive information can also be marked sensitive.

This reduces accidental display in normal CLI output.

Again:

```text
Redacted From Display
≠
Absent From State
```

---

# 107. MODERN TERRAFORM AND EPHEMERAL VALUES

Current Terraform versions also support mechanisms for values that should not be persisted in state or plan files, subject to Terraform version and provider capabilities.

These include newer ephemeral/write-only patterns.

This is version-dependent functionality and should be used only after checking the exact Terraform and provider versions in use.

For this Junior Part, the essential lesson remains:

> Understand whether a secret can enter Terraform state before supplying it to Terraform.

---

# 108. DO NOT HARDCODE CREDENTIALS

Avoid:

```hcl
provider "example" {
  username = "admin"
  password = "real-password"
}
```

in source-controlled Terraform.

Use the provider's supported secure authentication mechanism.

---

# 109. `.tfvars` FILES

Variable files may contain environment-specific values.

But a `.tfvars` file is not automatically secure.

If it contains:

```text

```

do not commit it simply because the extension is:

```text

```

Security depends on contents and handling.

The exact `.gitignore` should reflect the repository.

Do not blindly copy patterns that hide files the team actually intends to version.

# 172. PARTIAL APPLY LAB CONCEPT

In a safe lab containing multiple resources, introduce a controlled failure in a later resource.

Observe whether earlier independent resources were created before failure.

Then inspect:

```bash
terraform state list
```

and the real platform.

This demonstrates:

```text
Apply Failure
≠
Zero Changes
```

---

# 173. AFTER PARTIAL APPLY

Run:

```bash
terraform plan
```

again.

Inspect what Terraform proposes from the new current state.

Do not assume it will simply repeat the original plan.

The environment has changed.

---

# 174. DO NOT DELETE STATE TO "START OVER"

A dangerous beginner reaction is:

```bash
rm terraform.tfstate
```

because something looks wrong.

Do not do this.

Deleting state does not delete real infrastructure.

It can remove Terraform's knowledge of resources it manages.

---

# 175. DO NOT DELETE `.terraform` AS UNIVERSAL TROUBLESHOOTING

Removing:

```text
.terraform/
```

may force reinitialization, but it is not a universal repair.

First understand the failure.

Random cleanup can destroy useful troubleshooting context.

---

# 176. DO NOT RUN `terraform destroy` AS A RESET BUTTON

If a plan is confusing:

```text
destroy everything and recreate
```

is not a safe general solution.

Infrastructure may contain:

```text
persistent data

shared dependencies

external consumers

expensive reconstruction

downtime-sensitive services
```

Use destroy only when destruction is intended and understood.

---

# 177. DO NOT USE TARGETING AS A NORMAL SHORTCUT

Terraform has advanced mechanisms that can restrict operations to selected resources in exceptional situations.

These should not become a beginner workaround for:

```text
I do not understand the rest of the plan.
```

If the full plan is unexpected, investigate it.

---

# 178. DO NOT USE STATE COMMANDS RANDOMLY

Commands that modify state can materially change Terraform's management relationship with infrastructure.

At Junior level:

```text
terraform state list
```

and:

```text
terraform state show
```

are useful inspection tools.

State mutation should follow documented procedures and appropriate review.

---

# 179. TERRAFORM AND VERSION CONTROL

A Terraform repository creates two histories:

```text
Git History
=
how configuration changed
```

and:

```text
Terraform State
=
current managed resource bindings and metadata
```

These are not interchangeable.

Git cannot replace Terraform state.

State cannot replace Git history.

---

# 180. GIT COMMIT DOES NOT CHANGE INFRASTRUCTURE

This:

```bash
git commit
```

records a configuration change.

It does not automatically modify infrastructure unless automation is configured to act on that commit.

Keep:

```text
Code Change
```

separate from:

```text
Infrastructure Change
```

---

# 181. TERRAFORM PLAN DOES NOT CHANGE INFRASTRUCTURE

Likewise:

```bash
terraform plan
```

does not normally execute the proposed infrastructure changes.

It provides a proposal for review.

---

# 182. TERRAFORM APPLY DOES CHANGE INFRASTRUCTURE

This is the mutating boundary.

Before apply:

```text
Know identity.

Know environment.

Know state.

Know inputs.

Know plan.

Know impact.
```

---

# 183. TERRAFORM DESTROY CHANGES INFRASTRUCTURE TOO

Destroy deserves the same or greater review discipline as creation.

Never think:

```text
destroy is just cleanup
```

It is an infrastructure change.

# 187. PLAN CAN BECOME STALE

A plan represents infrastructure knowledge at a point in time.

Between:

```text
plan
```

and:

```text
apply
```

the environment may change.

For automated workflows, saved plans can help ensure that the reviewed plan is the one applied, but teams still need appropriate controls around changing infrastructure and state.

---

# 188. PLAN IS NOT A SECURITY APPROVAL BY ITSELF

A Terraform plan can accurately show:

```text
create public network rule
```

Terraform will not necessarily know whether your organization considers that rule unacceptable.

Human review and policy controls still matter.

# 189. PLAN IS NOT A COST GUARANTEE

Terraform may show:

```text
create large compute resource
```

but Terraform plan is not inherently a complete cost-analysis system.

Cloud billing awareness from Part 9 still applies.

A tag alone does not make Terraform manage a resource.

# 194. OUTPUT VERIFICATION

```bash
terraform output
```

Do not assume an output proves the remote service is healthy.

Example:

```text

```

It does not prove the URL works.

Use:

```text
HTTP verification
```

for that.

# 195. TERRAFORM AND APPLICATION HEALTH

Recall:


# 197. TROUBLESHOOTING: INITIALIZATION FAILURE

Symptom:

```text
terraform init fails
```

Investigate:

```text
provider source

provider version constraints

network connectivity

registry access

backend configuration

backend authentication

module source
```

Do not troubleshoot resource creation yet.

Terraform has not reached that layer.

---

# 198. TROUBLESHOOTING: AUTHENTICATION

Symptom:

```text
Terraform cannot authenticate to provider API.
```

Check:

```text
credential source

credential expiration

identity configuration

environment variables

provider-specific authentication

target account
```

Never hardcode a credential as the emergency repair.

---

# 199. TROUBLESHOOTING: AUTHORIZATION

Symptom:

```text
API returns access denied.
```

Check:

```text
authenticated identity

requested action

resource scope

assigned permissions
```

Do not automatically grant administrator access.

Determine the minimum required permission.

---

# 200. TROUBLESHOOTING: INVALID CONFIGURATION

Symptom:

```text
terraform validate fails
```

Check:

```text
syntax

block structure

argument name

type

required argument

resource reference
```

Read the Terraform diagnostic carefully.

---

# 201. TROUBLESHOOTING: PROVIDER ERROR

Symptom:

```text
provider returns API/resource error
```

Check:

```text
provider version

resource documentation

API message

quota

region

resource conflict

permissions

valid argument combinations
```

Do not invent provider behavior.

Use current provider documentation.

---

# 202. TROUBLESHOOTING: STATE AWARENESS

Symptom:

```text
Terraform wants to create something that appears to exist.
```

Check:

```text
correct backend?

correct state?

correct directory?

correct environment?

resource created outside Terraform?

state lost?

different Terraform address?
```

Stop before creating a duplicate.

---

# 203. TROUBLESHOOTING: UNEXPECTED PLAN

Symptom:

```text
Terraform proposes changes you did not expect.
```

Do:

```text
Do not apply.

Inspect Git diff.

Inspect variables.

Inspect provider versions.

Inspect state context.

Inspect real infrastructure.

Identify drift.

Identify replacement causes.

Explain every action.
```

---

# 204. TROUBLESHOOTING: DEPENDENCY FAILURE

Symptom:

```text
multiple resources fail
```

Check:

```text
Which failed first?

Which resources depend on it?

Is the later failure only a consequence?
```

Trace upward through the dependency chain.

---

# 205. TERRAFORM TROUBLESHOOTING MATRIX

| Symptom | First investigation area |
|---|---|
| `terraform` command not found | installation, PATH |
| `terraform init` fails | backend, provider, module, network |
| Provider cannot install | source, version, registry access |
| `terraform validate` fails | syntax, types, references |
| Authentication error | credentials, identity |
| Access denied | authorization |
| Unexpected create | state, environment, configuration |
| Unexpected destroy | configuration, state, drift |
| Unexpected replacement | changed force-replacement attribute/provider behavior |
| Resource API rejected | provider/API configuration |
| Dependent resources fail | earliest prerequisite failure |
| Apply partially fails | current state, successful resources, failed resource |
| Resource exists but Terraform wants another | state relationship |
| Plan differs from expectation | variables, state, drift, provider, Git diff |
| Destroy includes unexpected resource | wrong state/environment or misunderstood dependency |
| Apply succeeds but service unavailable | verify infrastructure/application layers |

# 206. READ-ONLY BEFORE MUTATING

When troubleshooting, prefer inspection first.

Examples:

```text
terraform version

terraform validate

terraform plan

terraform state list

terraform state show

git diff

git status
```

These can provide evidence before changing infrastructure.

Always understand the command and its context.

---

# 207. DO NOT APPLY AS A TROUBLESHOOTING PROBE

Bad pattern:

```text
Not sure what is wrong.

Run terraform apply.

See what happens.
```

Apply is a mutating operation.

Use plan and inspection first.

---

# 208. DO NOT DESTROY AS A TROUBLESHOOTING PROBE

Likewise:

```text
Maybe recreation will fix it.
```

is not a root-cause analysis.

Destroying infrastructure can erase evidence and create downtime.

---

# 209. TERRAFORM LOGGING

Terraform can provide additional diagnostic logging when needed.

The exact environment variables and supported logging controls should be checked against the installed Terraform version and current documentation before use.

Be careful:

```text
debug logs may contain sensitive operational information
```

Do not publish them blindly.

---

# 210. ERROR MESSAGE ≠ ROOT CAUSE

Terraform might report:

```text
resource creation failed
```

because the API returned:

```text
subnet not found
```

But why was the subnet not found?

Possible causes:

```text
wrong region

wrong ID

dependency issue

wrong account

resource deleted

variable error
```

Continue until evidence supports the underlying cause.

---

# 211. TERRAFORM PLAN AS EVIDENCE

A plan is evidence of:

```text
what Terraform proposes under the current configuration,
inputs, state context, provider behavior, and observed
infrastructure information available to the operation.
```

It is not evidence that the proposed change is desirable.

That is an engineering decision.


# 233. SIXTH SCENARIO: VALIDATE PASSES, PLAN FAILS

This is possible.

Why?

Because:

```text

```

checks configuration syntax and internal consistency.

Planning can require:

```text
provider API access

credentials

state

real infrastructure information

actual variable values
```

Therefore:

```text
Validate ✓

```

is not contradictory.

# 234. SEVENTH SCENARIO: PLAN PASSES, APPLY FAILS

Also possible.

Therefore:

```text

≠
```

# 255. COMMON BEGINNER MISTAKE: ASSUMING REPLACEMENT IS UPDATE

Replacement may destroy and recreate infrastructure.

Do not read:

```text
one resource changed
```

and miss that the resource is actually being replaced.

---

# 256. COMMON BEGINNER MISTAKE: WRONG ENVIRONMENT

A perfectly valid Terraform configuration applied to the wrong account can still create the wrong infrastructure.

Always verify context.

---

# 257. COMMON BEGINNER MISTAKE: MANUAL CHANGE AFTER APPLY

Suppose Terraform creates:

```text
security rule
```

and someone immediately changes it manually.

The configuration now no longer represents reality.

If a manual emergency change is necessary:

```text
document it

understand it

reconcile Terraform intentionally
```

---

# 258. COMMON BEGINNER MISTAKE: USING AI AS PROVIDER DOCUMENTATION

AI can explain concepts.

But provider schemas change.

For exact resource arguments, supported features, defaults, and version behavior:

```text
verify current provider documentation
```

---

# 259. COMMON BEGINNER MISTAKE: THINKING STATE IS BACKUP

Terraform state is not a complete infrastructure backup strategy.

State may describe infrastructure.

It does not necessarily contain:

```text
database data

application data

filesystem contents

object data
```

Do not confuse:

```text
Terraform State
```

with:

```text
Disaster Recovery Backup
```

---

# 260. COMMON BEGINNER MISTAKE: THINKING IAC ELIMINATES DRIFT

IaC makes drift detectable and manageable.

It does not make external changes physically impossible.

Access controls, operational processes, and automation architecture determine who can change infrastructure outside Terraform.

---

# 261. COMMON BEGINNER MISTAKE: "TERRAFORM MANAGES EVERYTHING"

Terraform manages resources represented by the relevant configuration/state/provider relationship.

It does not automatically own every resource in an account.

Know the management boundary.
