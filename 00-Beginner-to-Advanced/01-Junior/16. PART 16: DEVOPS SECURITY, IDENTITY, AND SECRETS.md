# PART 16: DEVOPS SECURITY, IDENTITY, AND SECRETS

## Goal

Develop the minimum security judgment required before a junior engineer is trusted with infrastructure, credentials, pipelines, cloud systems, containers, Kubernetes workloads, source repositories, or AI tools.

This Part is not intended to turn a Junior DevOps engineer into a security architect.

It establishes something more fundamental:

**the ability to recognize trust, authority, credentials, permissions, exposure, and security consequences before taking action.**

By the end of this Part, the learner should understand that infrastructure access is not simply:

```text
Can I log in?
```

The real questions are:

```text
Who am I?

How did the system verify my identity?

What am I allowed to do?

Why am I allowed to do it?

How long should that authority exist?

Which credential proves my identity?

Where is that credential stored?

Who else can access it?

Can the credential be revoked?

Can it be rotated?

Can my actions be audited?

What happens if the credential leaks?
```

The central security model is:

```text
Identity
    ↓
Authentication
    ↓
Authorization
    ↓
Permission
    ↓
Resource
    ↓
Action
    ↓
Audit Evidence
```

The central secret-handling model is:

```text
Secret Created
      ↓
Stored Securely
      ↓
Access Controlled
      ↓
Retrieved When Needed
      ↓
Used
      ↓
Exposure Minimized
      ↓
Rotated
      ↓
Old Credential Revoked
```

The central incident model is:

```text
Secret Exposure Suspected
        ↓
Treat Credential as Compromised
        ↓
Contain
        ↓
Revoke or Disable
        ↓
Rotate
        ↓
Update Legitimate Consumers
        ↓
Verify New Credential
        ↓
Verify Old Credential Fails
        ↓
Investigate Exposure
        ↓
Review Audit Evidence
        ↓
Prevent Recurrence
```

For AI-assisted engineering:

```text
AI Capability
      ↓
Approved Data Boundary
      ↓
Approved Access
      ↓
Minimum Necessary Context
      ↓
Human Review
      ↓
Controlled Action
      ↓
Verification
      ↓
Accountability
```

The learner must leave this Part understanding:

```text
Authentication
≠
Authorization
```

```text
Permission Exists
≠
Permission Is Appropriate
```

```text
Secret Hidden
≠
Secret Protected
```

```text
Secret Removed From Current File
≠
Secret Removed From Git History
```

```text
Credential Rotated
≠
Old Credential Revoked
```

```text
Encrypted
≠
Safe From Every Threat
```

```text
AI Can Perform Action
≠
AI Should Be Allowed To Perform Action
```

---

# 1. SECURITY IS PART OF DEVOPS ENGINEERING

Security is not something added after infrastructure is built.

DevOps engineers routinely interact with:

```text
cloud accounts

servers

SSH

source repositories

CI/CD platforms

container registries

Kubernetes clusters

Terraform

Ansible

databases

monitoring platforms

DNS

load balancers

secret stores

production applications

AI assistants and agents
```

These systems contain authority.

A mistake can affect:

```text
confidentiality

integrity

availability

cost

customer data

production systems

software supply chains

organizational reputation
```

A Junior engineer does not need to design an enterprise security program.

They do need to recognize when an action crosses a security boundary.

---

# 2. SECURITY JUDGMENT

Security judgment means asking the right questions before acting.

Before granting access:

```text
Who needs access?

What exact access is required?

To which resource?

For which task?

For how long?

Can narrower access work?

How will access be removed?

How will actions be audited?
```

Before using a credential:

```text
Where did this credential come from?

Who owns it?

What can it access?

Where should it be stored?

Could it appear in logs?

Could it appear in shell history?

Could it be committed to Git?

Could another process read it?

When does it expire?

How is it revoked?
```

Before giving information to an AI system:

```text
Is this AI tool approved?

What data am I sending?

Does it contain secrets?

Does it contain customer information?

Does it contain confidential source code?

Does organizational policy permit this use?

What actions can the AI perform?

What authority has been delegated?
```

Security begins before the command is executed.

---

# 3. THREE FUNDAMENTAL SECURITY OBJECTIVES

A useful foundational model is:

```text
Confidentiality

Integrity

Availability
```

These are often called the CIA triad.

---

# 4. CONFIDENTIALITY

Confidentiality concerns preventing unauthorized disclosure.

Examples:

```text
passwords should not be publicly readable

customer records should not be exposed

private keys should remain private

API tokens should not appear in public repositories

confidential logs should not be pasted into unauthorized AI systems
```

A confidentiality failure is fundamentally:

```text
Information Reaches Someone or Something
That Should Not Have It
```

---

# 5. INTEGRITY

Integrity concerns preventing unauthorized or unintended modification.

Examples:

```text
unauthorized infrastructure changes

modified deployment artifacts

tampered configuration

altered source code

changed DNS records

modified CI/CD pipelines
```

A system can remain available while its integrity has been compromised.

---

# 6. AVAILABILITY

Availability concerns ensuring authorized users and systems can access required services when needed.

Security controls themselves can affect availability.

For example:

```text
incorrect firewall rule
→ service unreachable
```

```text
expired certificate
→ client connection failures
```

```text
incorrect IAM policy
→ deployment blocked
```

Security engineering must consider all three objectives.

---

# 7. IDENTITY

An identity represents an entity recognized by a system.

An identity may represent:

```text
human user

application

service

virtual machine

container workload

CI/CD pipeline

automation process

cloud workload

external system
```

Identity answers:

```text
Who or what is making this request?
```

---

# 8. HUMAN IDENTITIES

Examples include:

```text
developer account

DevOps engineer account

administrator account

database operator account

GitHub user

cloud user
```

Human identities should normally be attributable to specific individuals.

Shared human accounts weaken accountability.

---

# 9. SHARED ACCOUNTS

Suppose five engineers use:

```text
admin
```

with one shared password.

An audit log shows:

```text
admin deleted resource
```

Who performed the action?

Possibly any of five people.

Individual identities improve attribution.

---

# 10. SERVICE IDENTITIES

Software also requires identity.

Examples:

```text
CI pipeline deploying application

application reading object storage

Kubernetes workload accessing cloud API

monitoring system reading metrics

backup system writing backups
```

These should not normally pretend to be human users.

Use workload or service identities appropriate to the platform.

---

# 11. HUMAN IDENTITY VERSUS SERVICE IDENTITY

Human:

```text
Ann
    ↓
Authentication
    ↓
Cloud Console
```

Service:

```text
CI Pipeline
    ↓
Workload Identity / Service Credential
    ↓
Cloud API
```

The security lifecycle differs.

Humans may authenticate interactively.

Machines require controlled non-interactive authentication.

---

# 12. AUTHENTICATION

Authentication answers:

```text
Can the system verify that you are the identity you claim to be?
```

Examples include:

```text
password

SSH private-key proof

security key

one-time code

certificate

token

federated identity
```

Authentication establishes identity.

It does not automatically establish what that identity may do.

---

# 13. AUTHORIZATION

Authorization answers:

```text
What is this authenticated identity allowed to do?
```

Examples:

```text
read repository

push branch

deploy staging

read secret

restart service

create virtual machine

delete storage bucket

modify IAM policy
```

Authorization is about permitted actions.

---

# 14. AUTHENTICATION VERSUS AUTHORIZATION

This distinction is mandatory.

```text
Authentication
→ Who are you?
```

```text
Authorization
→ What are you allowed to do?
```

A user can successfully authenticate and still receive:

```text
Access denied
```

because authentication succeeded but authorization did not.

---

# 15. EXAMPLE

Request:

```text
User attempts to delete production database.
```

System verifies identity:

```text
Authentication:
SUCCESS
```

System checks permissions:

```text
Authorization:
DENIED
```

This is not an authentication failure.

The system knows who the user is.

The user simply lacks permission for that action.

---

# 16. WHY THE DISTINCTION MATTERS DURING TROUBLESHOOTING

Suppose:

```text
Deployment failed: access denied.
```

A weak response is:

```text
Credentials are broken.
```

A better investigation asks:

```text
Did authentication succeed?

Which identity was authenticated?

Which action was attempted?

Which resource was targeted?

Which policy applies?

Which permission is required?

Was access explicitly denied?
```

This prevents unnecessary credential replacement.

---

# 17. AUTHENTICATION FACTORS

Authentication factors are commonly grouped conceptually into:

```text
Something you know

Something you have

Something you are
```

Examples:

```text
password
→ something you know

hardware security key
→ something you have

biometric characteristic
→ something you are
```

Multi-factor authentication combines independent factors.

---

# 18. MULTI-FACTOR AUTHENTICATION

A password can be stolen.

Adding another factor can make account compromise more difficult.

For privileged human access, organizations commonly require stronger authentication.

A Junior engineer should understand:

```text
Password Only
```

is generally weaker than appropriately implemented:

```text
Multiple Independent Authentication Factors
```

---

# 19. AUTHORIZATION MODELS

Different systems represent authorization differently.

Common concepts include:

```text
roles

permissions

policies

groups

scopes

claims

resource permissions
```

Do not assume every platform implements them identically.

---

# 20. PERMISSION

A permission represents authority to perform some operation.

Examples:

```text
read

write

create

update

delete

execute

list

administer
```

Cloud permissions are often more specific.

Conceptually:

```text
compute.instances.read

storage.objects.create

secrets.read
```

Exact names are provider-specific.

---

# 21. ROLE

A role groups permissions into a meaningful set.

Conceptually:

```text
Deployment Operator
    ↓
Read Deployment
Update Deployment
Read Logs
```

instead of assigning each permission independently to every user.

---

# 22. ROLE DOES NOT AUTOMATICALLY MEAN SAFE

A role named:

```text
Developer
```

could contain:

```text
read everything

write everything

delete everything

manage IAM
```

The name does not prove the role is appropriately scoped.

Inspect actual permissions.

---

# 23. LEAST PRIVILEGE

Least privilege means granting only the permissions necessary to perform the required task.

Conceptually:

```text
Required Task
      ↓
Required Actions
      ↓
Required Resources
      ↓
Minimum Necessary Permissions
```

not:

```text
Required Task
      ↓
Administrator
```

---

# 24. WHY ADMINISTRATOR ACCESS IS ATTRACTIVE

Broad access is convenient.

It reduces:

```text
permission troubleshooting

policy design

initial setup effort
```

But it increases:

```text
blast radius

accidental damage

credential compromise impact

unauthorized capability
```

Convenience is not sufficient justification for unrestricted access.

---

# 25. BLAST RADIUS

Blast radius describes how much can be affected when something fails or is compromised.

Credential A:

```text
can read one staging secret
```

Credential B:

```text
can administer every production system
```

If both leak, Credential B has a much larger potential blast radius.

Least privilege helps limit blast radius.

---

# 26. RESOURCE SCOPE

Permissions should be scoped not only by action but also by resource where the platform supports it.

Compare:

```text
Read every secret
```

with:

```text
Read one secret required by this application
```

The second provides a narrower trust boundary.

---

# 27. ENVIRONMENT SCOPE

A staging deployment pipeline may need:

```text
staging deployment permissions
```

It may not need:

```text
production administrator permissions
```

Environment separation reduces unnecessary authority.

---

# 28. TIME-BOUNDED ACCESS

Some access only needs to exist temporarily.

Examples:

```text
incident response

maintenance

migration

emergency debugging
```

Where supported, temporary or just-in-time access can reduce standing privilege.

---

# 29. STANDING PRIVILEGE

Standing privilege is authority that remains available continuously.

The more powerful the permission, the more important it becomes to ask:

```text
Does this authority need to exist permanently?
```

---

# 30. PRIVILEGE ESCALATION

Privilege escalation means gaining greater authority.

In Linux:

```text
sudo
```

can allow an authorized user to perform privileged actions.

In cloud environments, assuming a more privileged role may be a form of controlled privilege elevation.

Privilege elevation should be intentional and auditable.

---

# 31. SUDO IS A SECURITY BOUNDARY

Do not use:

```bash
sudo
```

simply because a command failed.

First determine:

```text
Why did it fail?

What permission is required?

Should this task require root?

Am I authorized to perform it?
```

Turning every permission failure into:

```text
sudo <command>
```

teaches dangerous operational behavior.

---

# 32. DENIED ACCESS CAN BE CORRECT

A permission error is not automatically something to fix.

Sometimes:

```text
Access Denied
```

means the security control is working correctly.

The question is:

```text
Should this identity have this permission?
```

not merely:

```text
How do I make the error disappear?
```

---

# 33. SECRETS

A secret is sensitive information used to authenticate, authorize, encrypt, sign, or otherwise establish trust.

Examples include:

```text
passwords

API keys

access tokens

refresh tokens

private keys

database credentials

client secrets

signing keys

encryption keys
```

Some certificates may be public while their corresponding private keys must remain secret.

---

# 34. SECRET VERSUS IDENTIFIER

Not every identifier is a secret.

Example:

```text
username
```

may identify an account without proving authority.

A password associated with that username is secret.

Similarly:

```text
API endpoint
```

is not necessarily secret.

An API credential used to authenticate to it may be.

---

# 35. API KEYS

An API key is a credential commonly used by software to authenticate or identify access to an API.

Security characteristics depend on the system.

An API key may be:

```text
long-lived

short-lived

scoped

unscoped

revocable

non-revocable until regenerated
```

Do not assume all API keys behave identically.

---

# 36. TOKENS

A token can represent authenticated or delegated authority.

Examples include:

```text
access token

refresh token

CI token

personal access token

temporary cloud token
```

Tokens can differ in:

```text
scope

lifetime

audience

issuer

revocation behavior

permissions
```

Treat tokens as sensitive unless you know otherwise.

---

# 37. SHORT-LIVED CREDENTIALS

Short-lived credentials expire after a limited period.

This can reduce the useful lifetime of stolen credentials.

Conceptually:

```text
Identity
    ↓
Authentication
    ↓
Temporary Credential
    ↓
Expires
```

This is often preferable to credentials that remain valid indefinitely.

---

# 38. LONG-LIVED CREDENTIAL RISK

Suppose an access key remains valid for:

```text
three years
```

and is accidentally copied into an old script.

If the credential is never rotated or revoked, exposure can remain useful to an attacker for a long time.

Long-lived credentials require particularly careful lifecycle management.

---

# 39. SSH KEYS

SSH public-key authentication commonly uses a key pair:

```text
Private Key
    +
Public Key
```

The public key can be installed on authorized systems.

The private key must remain protected.

---

# 40. PUBLIC KEY

The public key is designed to be distributed to systems that need to recognize the corresponding identity.

It does not need the same secrecy as the private key.

---

# 41. PRIVATE KEY

The private key must remain private.

Do not:

```text
commit it to Git

paste it into tickets

send it through chat casually

include it in documentation

put it in a container image

paste it into an unapproved AI system
```

---

# 42. SSH PRIVATE KEY PERMISSIONS

On Unix-like systems, SSH clients may reject private keys with excessively open permissions.

A typical private-key permission is:

```bash
chmod 600 ~/.ssh/id_ed25519
```

This allows the owner to read and write the file while denying access to group and others.

Inspect:

```bash
ls -l ~/.ssh/id_ed25519
```

Do not blindly change permissions on files whose purpose you do not understand.

---

# 43. SSH KEY PASSPHRASE

A private key may itself be protected by a passphrase.

The passphrase provides additional protection if the key file is stolen.

Whether and how keys are protected depends on organizational policy and automation requirements.

---

# 44. SSH AGENT

An SSH agent can hold usable key material for a session so the private-key passphrase does not need to be entered for every operation.

This is convenient.

It also creates a trust consideration.

Ask:

```text
Which keys are loaded?

Which processes can interact with the agent?

How long should the key remain available?
```

Inspect loaded identities:

```bash
ssh-add -l
```

when using an SSH agent.

---

# 45. CERTIFICATES

A digital certificate can bind identity information to a public key through a trust mechanism.

Certificates are used in systems such as:

```text
HTTPS/TLS

mutual TLS

service authentication

client authentication
```

A certificate itself often contains public information.

The associated private key is sensitive.

---

# 46. CERTIFICATE LIFETIME

Certificates have validity periods.

Operational failures can occur when certificates expire.

Typical troubleshooting questions include:

```text
Is certificate currently valid?

Has it expired?

Is the system clock correct?

Does hostname match expected identity?

Is issuer trusted?

Is the correct certificate being served?
```

Certificate validation is deeper than merely checking expiry.

---

# 47. TLS AND ENCRYPTION IN TRANSIT

TLS can protect data while it moves between systems.

Conceptually:

```text
Client
    ↓
Encrypted Connection
    ↓
Server
```

This helps protect against unauthorized observation or modification during transport when configured and validated correctly.

---

# 48. ENCRYPTION AT REST

Encryption at rest protects stored data using encryption mechanisms.

Examples can include:

```text
encrypted disk

encrypted database

encrypted object storage

encrypted secret store
```

Encryption at rest does not mean every user with authorized application access is prevented from reading the data.

---

# 49. ENCRYPTION DOES NOT SOLVE EVERYTHING

A secret can be encrypted on disk and still leak when:

```text
application reads it

user displays it

pipeline prints it

debug output exposes it

AI prompt includes it
```

Therefore:

```text
Encrypted Storage
≠
No Exposure Risk
```

---

# 50. KEY MANAGEMENT CONCEPT

Encryption depends on keys.

This creates another question:

```text
Who protects the encryption key?
```

Production key-management systems address:

```text
key storage

access control

rotation

auditing

lifecycle
```

Junior engineers need the concept even if they are not designing the system.

---

# 51. ENVIRONMENT VARIABLES

Environment variables are commonly used to provide runtime configuration.

Example:

```bash
export DATABASE_HOST=db.example.internal
```

They are also sometimes used for secrets.

Example:

```bash
export DATABASE_PASSWORD='...'
```

This is better than hardcoding the credential directly into source code in many situations, but it does not automatically make the secret safe.

---

# 52. ENVIRONMENT VARIABLE RISK

Environment variables can leak through:

```text
debugging output

process inspection

crash reports

CI/CD logs

shell history

application logs

diagnostic bundles
```

depending on the operating system, platform, permissions, and tooling.

Therefore:

```text
Secret In Environment Variable
≠
Secret Fully Protected
```

---

# 53. COMMAND-LINE ARGUMENT RISK

Avoid passing secrets directly as command-line arguments when safer mechanisms exist.

For example:

```text
program --password supersecret
```

may expose the value through:

```text
process inspection

shell history

audit tooling

logging
```

Exact exposure depends on the environment.

---

# 54. SHELL HISTORY

Commands entered interactively may be recorded in shell history.

Therefore:

```text
Typing Secret Into Command
```

can create another copy of that secret.

Do not assume terminal input disappears when the command finishes.

---

# 55. CONFIGURATION FILES

Configuration files may contain sensitive values.

Example:

```text
database_password=...
```

If secrets must exist in a file, consider:

```text
file ownership

permissions

storage location

backup behavior

version control

rotation

access auditing
```

---

# 56. FILE PERMISSIONS

Inspect:

```bash
ls -l <file>
```

and, where appropriate:

```bash
stat <file>
```

Ask:

```text
Who owns this file?

Which group?

Can other users read it?

Can they modify it?
```

Do not assume a file is private simply because its filename begins with a dot.

---

# 57. HIDDEN FILE DOES NOT MEAN SECURE FILE

A file named:

```text
.secret
```

is merely hidden from some default directory listings.

It is not encrypted.

It is not automatically access-controlled.

It is not a secret store.

---

# 58. SECRET STORES

A secret store is a system designed to manage sensitive values with controls such as:

```text
authentication

authorization

encryption

auditing

rotation support

versioning

access policies
```

Examples include cloud-provider secret-management services and dedicated secret-management platforms.

The specific product matters less at this stage than understanding the security model.

---

# 59. SECRET STORE MENTAL MODEL

```text
Workload Identity
      ↓
Authentication
      ↓
Authorization
      ↓
Secret Store
      ↓
Specific Secret
      ↓
Runtime Use
```

The application should receive only the secret it actually needs.

---

# 60. SECRET STORE DOES NOT REMOVE IDENTITY PROBLEM

If an application can retrieve a secret, it needs authority to do so.

Therefore the question becomes:

```text
How does the application authenticate to the secret store?
```

Poor design can simply move:

```text
hardcoded database password
```

into:

```text
hardcoded secret-store credential
```

without solving the trust problem.

---

# 61. BOOTSTRAP PROBLEM

A workload needs credentials to retrieve credentials.

This is sometimes called a bootstrap problem.

Modern platforms often address this with workload identity mechanisms rather than permanent credentials embedded in files.

At Junior level, understand the principle:

```text
Prefer Platform-Managed Identity
Over
Embedding Long-Lived Credentials
```

where supported and appropriate.

---

# 62. SECRET LIFECYCLE

A secret has a lifecycle:

```text
Creation
    ↓
Distribution
    ↓
Storage
    ↓
Use
    ↓
Rotation
    ↓
Revocation
    ↓
Deletion
```

Security must cover the whole lifecycle.

---

# 63. SECRET ROTATION

Rotation means replacing a credential with a new credential.

Conceptually:

```text
Old Credential
      ↓
New Credential Created
      ↓
Consumers Updated
      ↓
New Credential Verified
      ↓
Old Credential Disabled
      ↓
Old Credential Verified Unusable
```

The exact order depends on the system and whether overlapping credentials are supported.

---

# 64. ROTATION VERSUS REVOCATION

Rotation:

```text
replace credential
```

Revocation:

```text
make credential unusable
```

They are related but not identical.

Creating a new password does not prove an old API key has stopped working unless the system actually invalidates it.

---

# 65. EXPIRATION

Some credentials expire automatically.

Expiration reduces long-term exposure but creates operational requirements.

Systems need to:

```text
renew

replace

refresh

re-authenticate
```

before or when credentials expire.

---

# 66. CREDENTIAL ROTATION CAN BREAK SYSTEMS

Suppose:

```text
database password changes
```

but application configuration still contains the old password.

Result:

```text
authentication failures
```

Rotation must include:

```text
consumer discovery

controlled update

verification

old credential revocation
```

---

# 67. SECRET LEAKAGE

Secret leakage occurs when a secret becomes accessible outside its intended trust boundary.

Examples:

```text
committed to Git

printed in logs

included in screenshot

pasted into chat

uploaded to ticket

included in container image

stored in public object storage

sent to unapproved AI system
```

---

# 68. ASSUME EXPOSED CREDENTIAL IS COMPROMISED

If a real credential is accidentally committed to a repository, do not rely only on:

```text
delete line

commit deletion
```

The credential may already exist in:

```text
Git history

clones

forks

CI logs

caches

backups

notifications

third-party scanners
```

The important response is credential invalidation.

---

# 69. DELETE IS NOT ROTATE

This is mandatory:

```text
Remove Secret From File
≠
Rotate Credential
```

If the credential was exposed:

```text
invalidate the exposed credential
```

according to the relevant system.

---

# 70. GIT HISTORY

Git preserves historical objects.

Suppose commit 1 contains:

```text
API_TOKEN=secret
```

Commit 2 removes it.

The secret may still exist in commit 1.

Therefore:

```text
git log
```

and historical inspection can reveal old content.

Never assume the latest working tree represents all repository history.

---

# 71. HISTORY REWRITING IS NOT THE FIRST SECURITY ACTION

If a real credential leaks, the immediate security priority is usually:

```text
Revoke / Rotate Credential
```

not:

```text
perfectly erase every Git object first
```

History cleanup may still be necessary.

But cleanup does not make a leaked credential trustworthy again.

---

# 72. LAB SAFETY RULE

The secret-detection lab uses only a fake disposable credential.

Never deliberately commit:

```text
real password

real API token

real private key

real cloud credential
```

for training.

---

# 73. LAB 1: CREATE DISPOSABLE REPOSITORY

Create:

```bash
mkdir -p ~/veriqta-security-lab
cd ~/veriqta-security-lab

git init
```

Verify:

```bash
git status
```

Create a harmless README:

```bash
printf '# VERIQTA Security Lab\n' > README.md
git add README.md
git commit -m "Initialize security lab"
```

If Git requires identity configuration, use the approved identity configuration for your lab environment.

---

# 74. CREATE FAKE SECRET

Create a deliberately fake value:

```bash
printf 'LAB_API_TOKEN=VERIQTA_FAKE_TOKEN_DO_NOT_USE_001\n' > .env
```

Verify:

```bash
cat .env
```

The value is intentionally non-functional.

---

# 75. COMMIT THE FAKE SECRET

For this controlled lab only:

```bash
git add .env
git commit -m "Add lab configuration"
```

Now the repository contains a simulated secret leak.

---

# 76. DETECT THE SECRET IN CURRENT CONTENT

Search tracked files:

```bash
git grep 'VERIQTA_FAKE_TOKEN'
```

Expected:

```text
.env:LAB_API_TOKEN=VERIQTA_FAKE_TOKEN_DO_NOT_USE_001
```

You have evidence that sensitive-looking material exists in tracked repository content.

# 80. VERIFY HISTORICAL EXPOSURE

# 81. LAB ROTATION MODEL

Because the credential is fake, simulate the response.

Original:

```text

```



in a configuration file does not itself rotate anything.

# 93. PERMISSION LAB

# 94. INTERPRET 666

Mode:

```text
666
```

means:

```text
owner:
read + write

group:
read + write

others:
read + write
```

For sensitive configuration, this is usually excessive.

# 95. REPAIR PERMISSION


Verify:

```bash

```

```text

```

Permissions must match the resource and operational need.

# 96. DIRECTORY PERMISSIONS


# 102. CI/CD IS A SECURITY BOUNDARY

# 103. PIPELINE PERMISSIONS


These are important supply-chain questions.

# 104. RUNNER OR AGENT TRUST

```text
    ↓

    ↓
```

# 105. SHARED RUNNER RISK

A Junior engineer should not assume:


Automation can execute privileged actions very quickly.

# 106. PIPELINE SECRET

A pipeline may require credentials for:

```text

```

Do not hardcode them in pipeline YAML.

Masking is useful.

Therefore:

```text
Masked
≠
```

# 108. PIPELINE LOGS

# 109. DEBUG MODE RISK

# 110. SOURCE CONTROL PERMISSIONS

# 112. CODE REVIEW AS SECURITY CONTROL

# 113. DEPENDENCY RISK

Modern applications rely on dependencies.

A dependency may introduce risk through:

```text

```

Dependency management is part of software supply-chain security.

---

# 114. DIRECT DEPENDENCY

A direct dependency is one the project intentionally declares.

Example:

```text

    ↓

```

---

# 115. TRANSITIVE DEPENDENCY

Library A may depend on:

```text
library B
```

The application may therefore execute code from B even though the developer did not explicitly choose B.

Conceptually:

```text
Application
    ↓
Library A
    ↓
Library B
    ↓
Library C
```

Supply-chain risk extends beyond direct dependencies.

---

# 116. VERSION PINNING

Dependency versions may be constrained or pinned to improve reproducibility.

But:

```text
Pinned Version
≠
Secure Version
```

A pinned dependency can still contain a known vulnerability.

---

# 117. AUTOMATIC UPDATES

Automatically updating every dependency without review also creates risk.

Updates can introduce:

```text
breaking changes

behavior changes

new vulnerabilities

compromised releases
```

The goal is controlled dependency management.

---

# 118. DEPENDENCY SOURCE

Before adding a dependency, ask:

```text
Is this the intended package?

Is the source trustworthy?

Is the package actively maintained?

Is the name correct?

Is the version expected?

Why is this dependency required?
```

Do not install packages solely because an AI suggested the package name.

---

# 119. TYPOSQUATTING

Attackers may publish packages with names similar to legitimate packages.

Example conceptually:

```text
legitimate-package
```

versus:

```text
legitmate-package
```

A single-character mistake can matter.

Verify package identity before installation.

---

# 120. AI AND PACKAGE HALLUCINATION

AI systems can invent package names.

If an engineer blindly runs:

```text
pip install invented-package
```

and a malicious package with that name exists, the result can be dangerous.

Therefore:

```text
AI Suggested Dependency
      ↓
Verify Official Package
      ↓
Verify Maintainer / Source
      ↓
Verify Documentation
      ↓
Review Version
      ↓
Install
```

# 122. IMAGE SOURCE

# 124. BASE IMAGE RISK

# 125. SECRETS IN CONTAINER IMAGES

Never intentionally bake production secrets into an image.

Bad pattern:

```dockerfile
ENV API_TOKEN=real-production-token
```

Also dangerous:

```dockerfile
COPY .env /app/.env
```

if `.env` contains secrets.

Image layers and registries can preserve sensitive content.

---

# 126. DELETE LATER DOES NOT NECESSARILY REMOVE SECRET FROM IMAGE HISTORY

A Dockerfile such as:

```dockerfile
COPY secret.txt /tmp/secret.txt
RUN use-secret
RUN rm /tmp/secret.txt
```

can still leave secret material in an earlier image layer depending on the build process.

Do not copy sensitive credentials into ordinary build layers.

Use supported build-secret mechanisms where required.

# 127. `.dockerignore`

But:

```text
.dockerignore
≠

```

# 128. CONTAINER USER


# 129. PRIVILEGED CONTAINERS

Highly privileged container configurations can weaken isolation significantly.

```text

```

Investigate the actual requirement.

# 139. KUBERNETES SECURITY FUNDAMENTALS

# 140. KUBERNETES SECRET

Kubernetes provides a resource named:

```text
Secret
```

But the name alone does not mean:

```text
secret is impossible to retrieve
```

Access control, storage configuration, cluster security, and operational handling still matter.

---

# 141. BASE64 IS NOT ENCRYPTION

Kubernetes Secret manifests may represent values using base64 encoding.

Base64 is an encoding.

It is reversible.

Therefore:

```text
Base64
≠
Encryption
```

This distinction is mandatory.

---

# 142. DEMONSTRATE BASE64

Use harmless text:

```bash
printf '%s' 'VERIQTA-LAB' | base64
```

Then decode it:

```bash
printf '%s' 'VkVSSVFUQS1MQUI=' | base64 --decode
```

Expected:

```text
VERIQTA-LAB
```

No decryption key was required.

That is why base64 should never be described as encryption.

---

# 143. KUBERNETES RBAC CONCEPT

Role-based access control can answer questions such as:

```text
Can this identity list Pods?

Can it read Secrets?

Can it update Deployments?

Can it delete namespaces?
```

Junior engineers should understand that Kubernetes API access is authorization-controlled.

Detailed RBAC design belongs later.

---

# 144. CHECK PERMISSION BEFORE ACTION

Where authorized, Kubernetes provides mechanisms for checking whether the current identity can perform an action.

For example:

```bash
kubectl auth can-i get pods
```

or:

```bash
kubectl auth can-i get secrets
```

Interpret:

```text
yes
```

as:

```text
current identity is authorized according to evaluated access controls
```

not:

```text
performing this action is automatically appropriate.
```

---

# 145. PERMISSION EXISTS VERSUS PERMISSION SHOULD EXIST

This distinction is fundamental.

```text
kubectl auth can-i delete namespaces
→ yes
```

does not answer:

```text
Should my Junior account have this authority?
```

Security review evaluates appropriateness, not only technical capability.

---

# 146. AUDIT LOGS

Audit logs record security-relevant or administrative activity.

```text

```

Audit capabilities vary by platform.

# 147. AUDIT LOG VERSUS APPLICATION LOG

```text

```

```text

```

They serve different purposes.

---

# 148. AUDITABILITY

Questions:

```text

Who deleted this resource?

Who read this secret?

Which pipeline deployed this release?

Which identity changed this policy?
```

Audit evidence supports investigation and accountability.

# 149. LOGGING SECRETS DEFEATS SECRET HANDLING

Do not write:

```text

```

into logs.

A system can store its secret securely and then immediately leak it through logging.

Security controls must be considered end to end.

# 150. CREDENTIAL LEAK INVESTIGATION

Before privileged action:

```text
[ ] I know which identity I am using.

[ ] I know which environment I am targeting.

[ ] I know why this identity needs access.

[ ] I understand the approximate permission scope.
```

---

# 258. SECURITY CHECKLIST: CREDENTIAL

```text
[ ] Credential comes from approved source.

[ ] Credential is not hardcoded into source.

[ ] Credential is not being printed.

[ ] Credential is not being committed.

[ ] Credential lifetime is understood where relevant.

[ ] Revocation method is known where relevant.
```

---

# 259. SECURITY CHECKLIST: PERMISSION

```text
[ ] Permission is required for the task.

[ ] Resource scope is appropriate.

[ ] Environment scope is appropriate.

[ ] Administrator access is not being used merely for convenience.

[ ] Change does not unintentionally expand authority.
```

---

# 260. SECURITY CHECKLIST: AI

```text
[ ] AI tool is approved for the task.

[ ] No production credential is included.

[ ] No private key is included.

[ ] No unauthorized customer data is included.

[ ] Confidential information is minimized.

[ ] AI-generated actions will be reviewed.

[ ] AI does not have unnecessary production authority.
```

# 262. SCENARIO: APPLICATION CANNOT READ SECRET

Given:

```text
Application reports:
permission denied reading database secret.
```

The learner should investigate:

```text
Which application?

Which identity?

Authentication successful?

Correct secret?

Correct environment?

Correct secret path/name?

Authorization?

Secret enabled?

Secret version?

Network access?

Secret-store health?
```

The learner should not immediately:

```text
grant administrator access
```

# 263. SCENARIO: PIPELINE CANNOT DEPLOY

Given:

```text
Pipeline:
authentication successful

Deployment:
permission denied
```

The learner should classify this primarily as:

```text

```

not:

```text
authentication investigation
```

Then determine the minimum missing permission.

---

# 264. SCENARIO: EXPIRED TOKEN

Given:

```text
Pipeline worked yesterday.

Today:
token expired.
```

Investigate:

```text
expected token lifetime

renewal mechanism

credential owner

replacement process

whether long-lived static token should be replaced by approved short-lived identity mechanism
```

Do not permanently disable expiration.

---

# 265. SCENARIO: SECRET COMMITTED

Given:

```text
real API token found in Git history.
```

Correct priorities:

```text
1. Escalate according to policy where required.

2. Treat token as compromised.

3. Revoke or disable exposed token.

4. Issue replacement if required.

5. Update legitimate consumers.

6. Verify new token.

7. Verify old token is unusable.

8. Investigate audit evidence.

9. Address repository history and residual copies.

10. Add preventive controls.
```

Do not merely delete the line.
