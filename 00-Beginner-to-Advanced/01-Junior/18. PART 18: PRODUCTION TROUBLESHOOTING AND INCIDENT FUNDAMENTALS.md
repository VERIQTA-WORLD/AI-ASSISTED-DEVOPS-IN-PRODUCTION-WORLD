# PART 18: PRODUCTION TROUBLESHOOTING AND INCIDENT FUNDAMENTALS

## Goal

Combine Linux, networking, application, container, cloud, Kubernetes, security, CI/CD, and observability knowledge into a systematic first-response troubleshooting method.

The purpose of this Part is not to turn a Junior DevOps engineer into the person who can independently repair every production failure.

The purpose is to develop something more fundamental:

**the ability to investigate an unfamiliar production symptom without guessing.**

By this point, the learner has worked with individual layers:

- Linux
- processes
- filesystems
- CPU and memory
- networking
- DNS
- applications
- dependencies
- cloud infrastructure
- containers
- CI/CD
- Terraform
- configuration management
- Kubernetes
- observability
- identity
- credentials
- AI-assisted engineering

Production incidents rarely announce which one of these layers is responsible.

A user may report:

> "The website is down."

That statement does not tell the engineer whether the failure is:

- DNS
- routing
- firewall
- load balancer
- Kubernetes Service
- container
- application
- database
- authentication
- certificate
- storage
- deployment
- configuration
- dependency

The engineer must discover the failing layer from evidence.

The central troubleshooting framework is:

```text
Symptom
    ↓
Scope
    ↓
Impact
    ↓
Recent Changes
    ↓
Expected State
    ↓
Observed State
    ↓
Relevant Layer
    ↓
Evidence
    ↓
Hypothesis
    ↓
Test
    ↓
Root Cause
    ↓
Corrective Action
    ↓
Verification
```

The production path model is:

```text
User
  ↓
DNS
  ↓
Network
  ↓
Load Balancer / Entry Point
  ↓
Host / Cluster
  ↓
Container / Process
  ↓
Application
  ↓
Dependency
  ↓
Data
```

The incident model is:

```text
Detect
  ↓
Assess Impact
  ↓
Communicate
  ↓
Collect Evidence
  ↓
Mitigate
  ↓
Verify Recovery
  ↓
Investigate Root Cause
  ↓
Learn
```

---

# 1. PRODUCTION TROUBLESHOOTING IS EVIDENCE-DRIVEN ENGINEERING

Troubleshooting is not:

```text
Symptom
   ↓
Guess
   ↓
Change Something
   ↓
Hope
```

It is:

```text
Symptom
   ↓
Evidence
   ↓
Hypothesis
   ↓
Test
   ↓
New Evidence
   ↓
Conclusion
```

This distinction matters because uncontrolled troubleshooting can make an incident worse.

---

# 2. THE FIRST QUESTION IS NOT "HOW DO I FIX IT?"

The first questions are:

```text
What exactly is happening?

What should be happening?

Who or what is affected?

When did it start?

What changed?

Which layer appears unhealthy?

What evidence supports that?
```

Only after understanding the failure should remediation begin.

---

# 3. SYMPTOM IS NOT ROOT CAUSE

Examples:

```text
Website unavailable
```

is a symptom.

```text
Application slow
```

is a symptom.

```text
Pod restarting
```

is a symptom.

```text
Pipeline failed
```

is a symptom.

```text
Disk 100% full
```

is an observed condition.

None automatically identifies the root cause.

---

# 4. START WITH THE REPORTED SYMPTOM

Record the symptom as precisely as possible.

Weak:

```text
Production is broken.
```

Better:

```text
Users report that requests to the public application return HTTP 503.
```

Better still:

```text
Beginning at approximately 14:07 UTC, requests to
https://example.test return HTTP 503 from multiple clients.
```

Precision improves investigation.

---

# 5. USER REPORTS ARE IMPORTANT BUT INCOMPLETE

A user might say:

```text
The server is down.
```

But the actual failure could be:

```text
DNS does not resolve.
```

The user is describing experience.

The engineer must translate experience into technical evidence.

---

# 6. CONFIRM THE SYMPTOM

Whenever safe and possible, reproduce or independently confirm the reported behavior.

For HTTP:

```bash
curl -v https://example.test/
```

or, where appropriate:

```bash
curl -I https://example.test/
```

The exact request should match what you are trying to test.

Do not assume:

```text
Monitoring says down
```

means:

```text
Every user path is down.
```

---

# 7. RECORD TIME

Time is evidence.

Record:

```text
2026-10-01 14:07 UTC
```

rather than:

```text
a few minutes ago
```

Precise timestamps allow correlation with:

- logs
- metrics
- deployments
- cloud events
- alerts
- authentication events
- configuration changes

---

# 8. USE A CONSISTENT TIMEZONE

UTC is commonly useful for distributed engineering systems.

Whatever standard your organization uses, be explicit.

Avoid:

```text
14:00
```

without timezone context.

Prefer:

```text
14:00 UTC
```

---

# 9. SCOPE

Determine how broadly the failure occurs.

Ask:

```text
One user?

One request?

One host?

One Pod?

One service?

One namespace?

One availability zone?

One region?

One environment?

Everyone?
```

Scope dramatically changes the investigation.

---

# 10. SCOPE REDUCES THE SEARCH SPACE

If:

```text
one user fails
```

but:

```text
other users succeed
```

then a complete global outage becomes less likely.

If:

```text
every request fails
```

across:

```text
multiple clients
```

the failure is broader.

---

# 11. COMPARE WORKING AND FAILING PATHS

One of the strongest troubleshooting techniques is comparison.

Ask:

```text
What works?

What fails?

What differs?
```

Example:

```text
localhost works

remote request fails
```

The application may be healthy while the external network path is not.

---

# 12. DIFFERENTIAL TROUBLESHOOTING

Suppose:

```text
Host A can reach service.
Host B cannot.
```

Compare:

```text
DNS result

route

firewall

source network

credentials

configuration
```

The difference can reveal the failing layer.

---

# 13. IMPACT

Scope tells you where the failure exists.

Impact tells you what it means.

Examples:

```text
Internal dashboard unavailable

Customer checkout unavailable

Background reporting delayed

Deployment blocked

One engineer cannot authenticate

All production writes failing
```

These have different operational consequences.

---

# 14. IMPACT QUESTIONS

Determine:

```text
Are customers affected?

How many?

Which functionality?

Read path?

Write path?

Data loss?

Data corruption?

Security exposure?

Revenue impact?

Operational blockage?
```

A Junior engineer may not know all business answers.

Record what is known and escalate where necessary.

---

# 15. SEVERITY AWARENESS

Organizations often classify incidents using severity levels such as:

```text
SEV1
SEV2
SEV3
SEV4
```

The exact definitions vary.

Never assume that one company's:

```text
SEV1
```

means the same thing somewhere else.

Use the organization's documented severity model.

---

# 16. SEVERITY IS NOT JUST TECHNICAL COMPLEXITY

A technically simple failure can have severe business impact.

Example:

```text
expired certificate
```

may be easy to understand but can make an important service unavailable.

Severity should reflect organizational impact, not how intellectually difficult the bug is.

---

# 17. RECENT CHANGES

Production failures frequently correlate with change.

Ask:

```text
What changed recently?
```

Possible changes include:

- application deployment
- configuration
- infrastructure
- firewall rule
- DNS
- certificate
- credential
- secret
- dependency version
- operating system package
- container image
- Kubernetes manifest
- autoscaling configuration
- CI/CD workflow
- cloud policy

---

# 18. CHANGE CORRELATION IS NOT ROOT CAUSE

Suppose:

```text
deployment at 14:02

errors begin at 14:04
```

The deployment becomes an important hypothesis.

It does not automatically become the root cause.

Verify.

---

# 19. CHECK CHANGE HISTORY

Depending on the environment, evidence may come from:

```text
Git history

CI/CD history

deployment records

cloud audit logs

Kubernetes rollout history

configuration management logs

change tickets
```

Use the system available to you.

---

# 20. EXPECTED STATE

Troubleshooting requires a definition of healthy behavior.

Examples:

```text
3 replicas should be Ready.

Application should listen on TCP 8080.

Filesystem should have sufficient free space.

DNS name should resolve to expected address.

Pipeline test stage should pass.

Credential should authenticate successfully.
```

Without expected state, observed state has little context.

---

# 21. OBSERVED STATE

Observed state is what the system actually shows.

Example:

```text
Expected:
3 Ready Pods.

Observed:
1 Ready Pod.
2 Pods in CrashLoopBackOff.
```

Now the difference is concrete.

---

# 22. EXPECTED VERSUS OBSERVED

Use:

```text
Expected
   ↓
Observed
   ↓
Difference
```

The difference helps identify the investigation layer.

---

# 23. RELEVANT LAYER

The production path may look like:

```text
User
  ↓
DNS
  ↓
Network
  ↓
Load Balancer / Entry Point
  ↓
Host / Cluster
  ↓
Container / Process
  ↓
Application
  ↓
Dependency
  ↓
Data
```

The purpose is not to check every layer mechanically.

The purpose is to locate the boundary between:

```text
working
```

and:

```text
failing
```

---

# 24. FAILURE BOUNDARY

Suppose:

```text
DNS resolves.

TCP connection succeeds.

TLS succeeds.

HTTP request reaches load balancer.

Load balancer returns 503.
```

You have already collected evidence that moves the investigation deeper than basic DNS resolution.

Do not restart DNS because the website is unavailable.

---

# 25. LAYER 1: USER

Questions:

```text
Who reports the failure?

One user or many?

Which location?

Which client?

Which request?

Authenticated or anonymous?

Browser only?

CLI also?
```

Client-side conditions can matter.

---

# 26. LAYER 2: DNS

DNS translates names into information required for routing to services.

Basic checks may include:

```bash
getent hosts example.test
```

or, when installed:

```bash
dig example.test
```

or:

```bash
nslookup example.test
```

Tool availability varies.

---

# 27. DNS QUESTIONS

Ask:

```text
Does the name resolve?

Does it resolve to expected address?

Do different resolvers agree?

Is record stale?

Is wrong hostname being queried?

Is only one client affected?
```

---

# 28. DNS SUCCESS DOES NOT PROVE APPLICATION HEALTH

If DNS resolves correctly:

```text
Name
   ↓
Address
```

has succeeded.

It does not prove:

```text
TCP connection works

TLS works

application responds

dependency is healthy
```

---

# 29. LAYER 3: NETWORK

Investigate:

```text
interface

address

route

gateway

firewall

security group

network ACL where applicable

port

TCP connectivity
```

depending on the environment.

---

# 30. NETWORK EVIDENCE

Possible tools include:

```bash
ip addr
```

```bash
ip route
```

```bash
ss -lnt
```

and appropriate connection tests.

Tool availability and output vary by operating system.

---

# 31. PING IS NOT UNIVERSAL PROOF

A failed:

```bash
ping
```

does not necessarily prove the destination is unavailable.

ICMP may be blocked.

A successful ping does not prove the application port works.

Test the protocol relevant to the application.

---

# 32. LAYER 4: LOAD BALANCER OR ENTRY POINT

Possible entry points include:

```text
cloud load balancer

reverse proxy

Ingress

Gateway

API gateway
```

Investigate:

```text
listener

backend/target health

routing rule

hostname

path

port

TLS

backend availability
```

---

# 33. LOAD BALANCER HEALTH

A load balancer may be running while every backend is unhealthy.

Therefore:

```text
Load Balancer Exists
```

does not mean:

```text
Application Available
```

Inspect backend health.

---

# 34. LAYER 5: HOST OR CLUSTER

For hosts investigate:

```text
CPU

memory

disk

inodes

I/O

network

services

processes
```

For clusters investigate:

```text
nodes

workloads

scheduling

events

resource availability
```

within your authorized scope.

---

# 35. LAYER 6: CONTAINER OR PROCESS

Ask:

```text
Does process exist?

Is container running?

Is it restarting?

What exit code?

What logs?

Is expected port listening?

Is configuration present?
```

---

# 36. PROCESS EXISTS DOES NOT MEAN APPLICATION HEALTHY

A process may be:

```text
deadlocked

waiting

misconfigured

listening on wrong interface

unable to reach dependency

returning errors
```

Presence is one piece of evidence.

---

# 37. CONTAINER RUNNING DOES NOT MEAN APPLICATION HEALTHY

A container can be:

```text
Running
```

while the application:

```text
returns 500

cannot reach database

is not Ready

is serving wrong configuration
```

Inspect application behavior.

---

# 38. LAYER 7: APPLICATION

Investigate:

```text
logs

health endpoint

configuration

environment variables

runtime

request errors

latency

startup state
```

---

# 39. APPLICATION QUESTIONS

Ask:

```text
Did it start?

Is it listening?

Is it healthy?

Is it Ready?

Is it returning expected response?

Are errors increasing?

Did configuration change?

Can it reach dependencies?
```

---

# 40. LAYER 8: DEPENDENCY

Dependencies include:

```text
database

cache

queue

external API

identity provider

object storage

another service
```

A healthy application process can still fail because a dependency is unavailable.

---

# 41. DEPENDENCY QUESTIONS

Ask:

```text
Can name resolve?

Can connection be established?

Does authentication succeed?

Is dependency responding?

Is latency abnormal?

Is application using correct endpoint?
```

---

# 42. LAYER 9: DATA

Investigate carefully.

Potential issues include:

```text
missing data

incorrect schema

unavailable storage

read-only filesystem

database capacity

corruption

incorrect migration
```

Data-layer remediation can carry significant risk.

Escalate when outside your authority.

---

# 43. EVIDENCE

Evidence can include:

```text
command output

logs

metrics

traces

events

HTTP responses

exit codes

configuration

Git diff

deployment history

audit records
```

Evidence should be:

```text
relevant

timestamped where possible

environment-specific

preserved accurately
```

---

# 44. DO NOT EDIT EVIDENCE TO FIT A THEORY

If logs contradict your hypothesis, update the hypothesis.

Do not ignore the logs.

Troubleshooting is:

```text
Evidence changes belief.
```

Not:

```text
Belief changes evidence.
```

---

# 45. HYPOTHESIS

A hypothesis is a testable explanation.

Example:

```text
Hypothesis:
The application is unavailable because the process is not listening on the expected port.
```

This predicts evidence.

---

# 46. HYPOTHESIS TEST

Possible test:

```bash
ss -lntp
```

If the expected listener is absent, the hypothesis becomes stronger.

If it is present on the expected address and port, investigate further.

---

# 47. ONE TEST SHOULD ANSWER A QUESTION

Do not run commands randomly.

Before each command, know:

```text
Question:
What am I trying to determine?

Command:
What evidence will this provide?

Interpretation:
What will different results mean?
```

---

# 48. ROOT CAUSE

Root cause should explain the failure mechanism.

Weak:

```text
Kubernetes problem.
```

Better:

```text
Deployment referenced a nonexistent container image tag,
preventing new Pods from pulling the image.
```

---

# 49. IMMEDIATE CAUSE VERSUS ROOT CAUSE

Example:

```text
Immediate failure:
Application cannot authenticate to database.

Underlying cause:
Credential expired and rotation process did not update the application secret.
```

These are related but different.

---

# 50. CONTRIBUTING FACTORS

Incidents can have more than one contributing factor.

Example:

```text
expired credential

missing expiration alert

manual rotation process

incomplete runbook
```

Avoid forcing every incident into a single-cause story.

---

# 51. CORRECTIVE ACTION

Corrective action should address the verified problem.

Examples:

```text
restore correct image

renew credential

free filesystem safely

repair DNS record

restore correct configuration

rollback deployment
```

Do not choose corrective action merely because it changes the symptom.

---

# 52. VERIFICATION

After correction:

```text
Did expected state return?

Did user-visible symptom disappear?

Did metrics recover?

Did errors stop?

Are dependencies healthy?

Did any new failure appear?
```

Verification closes the troubleshooting loop.

---

# 53. "COMMAND SUCCEEDED" IS NOT VERIFICATION

Example:

```text
kubectl apply succeeded
```

does not prove:

```text
application is healthy.
```

Continue to workload and application verification.

---

# 54. INCIDENT FUNDAMENTALS

An incident is not only a technical troubleshooting exercise.

It also involves:

```text
impact

coordination

communication

time

risk

evidence

recovery
```

---

# 55. FIRST-RESPONSE PRIORITIES

A useful first-response sequence is:

```text
Confirm
   ↓
Assess Impact
   ↓
Communicate
   ↓
Preserve Evidence
   ↓
Investigate
   ↓
Mitigate
   ↓
Verify
   ↓
Continue Root-Cause Investigation
```

Exact organizational processes may differ.

Follow the organization's incident procedures.

---

# 56. COMMUNICATION

Useful incident communication should be:

```text
factual

timestamped

concise

clear about uncertainty
```

Avoid unsupported statements.

---

# 57. BAD INCIDENT UPDATE

```text
Database is definitely broken and we're fixing it.
```

if the database has not been verified.

---

# 58. BETTER INCIDENT UPDATE

```text
14:12 UTC:
Users are receiving HTTP 503 responses.

Impact appears limited to the checkout service.

Application instances are running, but load balancer health checks are failing.

Investigation is ongoing.
```

This separates fact from uncertainty.

---

# 59. INCIDENT TIMELINE

Record meaningful events.

Example:

```text
14:02 deployment completed
14:05 latency alert fired
14:07 first 503 confirmed
14:09 incident investigation started
14:12 unhealthy backend identified
14:18 rollback initiated
14:22 health checks recovered
14:25 user requests verified
```

---

# 60. TIMELINE SOURCES

Possible sources:

```text
monitoring

CI/CD

Git

cloud audit logs

application logs

Kubernetes events

chat

incident tooling
```

Do not invent missing timestamps.

---

# 61. MITIGATION VERSUS ROOT CAUSE

Mitigation reduces impact.

Root-cause correction addresses why the incident occurred.

Example:

```text
Mitigation:
Rollback deployment.

Root cause:
New release used an invalid database endpoint.
```

Rollback may restore service before the exact defect is fully understood.

---

# 62. MITIGATION CAN BE THE CORRECT PRIORITY

During serious impact, restoring service may be more urgent than completing deep diagnosis.

But mitigation should still be controlled and evidence-informed.

---

# 63. ROLLBACK

Rollback attempts to return to a previously known state.

Before rollback ask:

```text
What exactly is being rolled back?

Was previous state healthy?

Has data changed?

Is rollback compatible?

What will verification be?
```

Rollback is not automatically safe.

---

# 64. ROLLBACK CAN FAIL

Possible reasons:

```text
database migration incompatible

old artifact unavailable

configuration changed independently

external dependency changed

rollback procedure untested
```

Therefore rollback itself requires verification.

---

# 65. ESCALATION

Escalation is an engineering skill.

Escalate when:

```text
impact exceeds authority

security incident suspected

data integrity at risk

repair requires unfamiliar high-risk action

production access insufficient

root cause remains unclear

incident severity requires senior response

change requires approval
```

---

# 66. GOOD ESCALATION

Provide:

```text
symptom

impact

scope

start time

expected state

observed state

recent changes

evidence

hypotheses tested

actions taken

current state

specific assistance needed
```

---

# 67. BAD ESCALATION

```text
Production is broken. Please help.
```

This forces the next engineer to repeat discovery.

---

# 68. EVIDENCE PRESERVATION

Before making disruptive changes, consider what evidence may disappear.

Examples:

```text
restart clears process state

Pod deletion removes immediate container context

log rotation removes logs

temporary files disappear

autoscaling changes topology
```

Collect relevant evidence first when impact and time allow.

---

# 69. DO NOT PRESERVE EVIDENCE AT THE EXPENSE OF SAFETY

If immediate action is required to protect:

```text
people

data

security

critical service
```

mitigation may take priority.

Incident handling requires judgment.

---

# 70. POST-INCIDENT LEARNING

After recovery ask:

```text
What happened?

What was the impact?

How was it detected?

What evidence mattered?

What slowed diagnosis?

What restored service?

What was root cause?

What contributed?

What should change?
```

---

# 71. POST-INCIDENT LEARNING IS NOT BLAME

Focus on:

```text
systems

controls

processes

assumptions

technical conditions
```

rather than constructing a simplistic story around one person's mistake.

# 81. LAB 2: APPLICATION SLOW

Scenario:

```text
Users report that the application is slow.
```

No root cause is provided.

---

# 82. SLOW APPLICATION: DEFINE "SLOW"

Determine:

```text
Which requests?

How slow?

Since when?

All users?

All endpoints?

Intermittent?

Constant?
```

"Slow" must become measurable.

---

# 83. CHECK OBSERVABILITY FIRST

Inspect:

```text
latency

request rate

error rate

CPU

memory

disk

network

saturation

application logs
```

Do not immediately restart.

---

# 84. CPU

High CPU may be relevant.

Ask:

```text
Which process?

How long?

Expected workload?

One host or all?

Does latency correlate?
```

---

# 85. MEMORY

Inspect:

```text
available memory

swap

process memory

OOM evidence
```

Do not conclude:

```text
memory problem
```

only because free memory appears low.

Linux uses memory for caching.

Use the broader memory evidence taught earlier.

---

# 86. DISK AND I/O

Inspect:

```text
filesystem usage

inodes

I/O pressure

application storage behavior
```

A nearly full disk can affect application behavior.

---

# 87. DEPENDENCY LATENCY

If host resources appear normal, investigate:

```text
database latency

external API

cache

queue

DNS

network
```

Application slowness may originate downstream.

---

# 88. USE AI ONLY AFTER INITIAL EVIDENCE

For this lab, first collect:

```text
latency metric

CPU/memory evidence

application logs

recent changes
```

Then ask AI for hypotheses.

---

# 89. AI REQUEST

Example:

```text
Objective:
Identify likely causes of increased application latency.

Evidence:
<sanitized metrics and logs>

Recent changes:
<known changes>

Constraint:
Do not recommend restart yet.

Task:
Generate up to five hypotheses.
For each, identify supporting evidence, contradictory evidence,
and one safe next test.
```

---

# 90. COMPARE AI AGAINST EVIDENCE

The learner must mark each AI hypothesis:

```text
Supported

Possible but unverified

Contradicted

Irrelevant
```

AI does not choose the root cause.

# 100. LAB 5: SERVER DISK FULL

# 104. DELETED-OPEN FILE CONCEPT

A process can continue holding a deleted file open.

In such cases:

```text

```

```text

```

This is an important production troubleshooting concept.

# 105. DO NOT RUN BLIND CLEANUP COMMANDS

```text

```

```text

retention policy

safe cleanup method
```

# 106. DISK FULL ROOT CAUSE

Cleaning space may mitigate the incident.


# 137. INCIDENT TRIAGE MATRIX

| Symptom | First Evidence |
|---|---|
| Name does not resolve | DNS |
| Connection refused | Listener and target port |
| Connection timeout | Network path and firewall |
| HTTP 5xx | Application/entry-point logs and metrics |
| High latency | Metrics, logs, dependencies |
| Pod Pending | Pod events and scheduling |
| ImagePullBackOff | Pod events and image reference |
| CrashLoopBackOff | Container state and logs |
| Disk full | Filesystem blocks/inodes |
| Authentication failed | Identity and credential state |
| Authorization denied | Identity and permissions |
| Pipeline failed | Failing job/step and logs |

This table provides starting points, not guaranteed root causes.

# 138. HTTP STATUS AWARENESS

HTTP status can narrow investigation.

Examples:

```text

request handled successfully at HTTP level

4xx
request/client/authentication/authorization/resource issue may be involved

5xx
server-side or upstream handling failure may be involved
```

Do not diagnose solely from status family.

Inspect context.

# 154. EVIDENCE BEFORE ROLLBACK

---

# 155. CHANGE ONE THING AT A TIME WHEN POSSIBLE

If you simultaneously:

```text

change firewall

change DNS

rotate credential
```

and service recovers, identifying which change mattered becomes difficult.

During emergencies multiple actions may be unavoidable, but record them precisely.

---

# 156. TEST THE HYPOTHESIS, NOT THE SYSTEM RANDOMLY

Bad:

```text
Maybe restarting everything works.
```

Better:

```text
Hypothesis:
Application process is wedged.

Evidence needed:
Process state, logs, health behavior.

Test:
Controlled restart only after evidence capture and approval.

Verification:
Health and request success after restart.
```

---

# 157. MINIMUM-CHANGE PRINCIPLE

Prefer the smallest safe action that tests or corrects the verified problem.

Smaller changes generally reduce:

```text
blast radius

uncertainty

rollback complexity
```

---

# 158. DO NOT CREATE A SECOND INCIDENT

Common dangerous reactions include:

```text
chmod 777

disable firewall

disable TLS verification

delete unknown files

restart entire cluster

grant administrator

delete Pods repeatedly

destroy/recreate infrastructure
```

A failing service does not justify uncontrolled remediation.

# 236. FINAL JUNIOR ENGINEER RULE

A Junior engineer does not need to know every answer.

A Junior engineer trusted around production must know how to avoid turning uncertainty into uncontrolled action.

When the answer is unknown:

```text
Do Not Guess
      ↓
Observe
      ↓
Collect Evidence
      ↓
Identify the Layer
      ↓
Form a Hypothesis
      ↓
Test Safely
      ↓
Verify
```

If the final repair requires someone more experienced:

```text
Preserve Evidence
      ↓
Document What You Know
      ↓
Explain What You Tested
      ↓
State What Remains Unknown
      ↓
Escalate Clearly
```

That is successful first-response engineering.
