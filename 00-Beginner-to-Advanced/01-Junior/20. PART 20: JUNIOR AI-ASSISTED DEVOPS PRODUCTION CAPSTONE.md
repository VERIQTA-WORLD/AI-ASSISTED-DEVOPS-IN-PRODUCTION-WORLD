# PART 20: JUNIOR AI-ASSISTED DEVOPS PRODUCTION CAPSTONE

## Goal

Demonstrate that the learner can combine the VERIQTA Junior AI-Assisted DevOps curriculum into one coherent production-style engineering workflow.

This capstone is not another guided tutorial.

Earlier Parts taught individual concepts and tools.

This Part asks whether the learner can combine them.

The learner must demonstrate that they can move through:

```text
Requirement
    ↓
Repository
    ↓
Application
    ↓
Automated Tests
    ↓
Container Image
    ↓
CI/CD
    ↓
Infrastructure as Code
    ↓
Infrastructure
    ↓
Configuration Management
    ↓
Deployment
    ↓
Application Endpoint
    ↓
Observability
    ↓
Security Review
    ↓
Controlled Change
    ↓
Failure
    ↓
Investigation
    ↓
Recovery
    ↓
Verification
    ↓
Documentation
```

The capstone must test understanding rather than the ability to follow a prepared script.

The learner should not receive a sequence such as:

```text
Run this command.

Now run this command.

Now edit this line.

Now check this output.
```

Instead, the learner receives:

- a system
- requirements
- constraints
- access
- expected outcomes
- deliberately introduced failures
- evidence sources

The learner must determine how to proceed.

The final question is not:

> Did the learner finish the lab?

It is:

> Can the learner operate a bounded production-style system using evidence, controlled changes, verification, security judgment, and appropriate escalation?

---

# 1. CAPSTONE PHILOSOPHY

The Junior curriculum has introduced many technologies.

The capstone must not become a tool-recitation exercise.

Knowing commands is useful.

Engineering requires connecting them.

For example:

```text
User reports application unavailable
```

The learner should not immediately think:

```text
Kubernetes problem.
```

They should think:

```text
What is the actual symptom?

What should be happening?

What is happening?

Which layers are involved?

What evidence exists?

Where does expected behavior stop?
```

That is the capability being assessed.

# 10. ASSESSMENT RULE: EVIDENCE IS REQUIRED

Statements such as:

```text
The application is healthy.
```

must be supported.

Possible evidence:

- HTTP response
- health endpoint
- workload state
- process state
- logs
- metrics
- successful functional test

Likewise:

```text
The deployment failed.
```

must identify what failed.

---

# 11. CLAIM → EVIDENCE

Use this throughout the capstone:

```text
Claim
   ↓
Evidence
   ↓
Interpretation
   ↓
Conclusion
```

Example:

```text
Claim:
The application process is listening on port 8080.

Evidence:
Socket inspection shows the expected process listening
on the expected address and port.

Conclusion:
The application has successfully created the expected
local listening socket.
```

This still does not prove the complete user path works.

# 18. HEALTH ENDPOINT LIMITATION

A successful health request proves only what that health implementation checks.

It does not automatically prove:

- every dependency works
- every user workflow works
- latency is acceptable
- every feature works

The learner must distinguish health checks from functional verification.

# 49. TERRAFORM STATE SAFETY

# 59. KUBERNETES CONFIGURATION

# 60. CONFIGURATION UPDATE AWARENESS

The learner must understand an important Kubernetes behavior:

If a ConfigMap is consumed as process environment variables, editing the ConfigMap does not modify environment variables inside already-running processes.

Pods must be replaced for those environment values to be refreshed.

This becomes useful during later failure investigations.

# 67. SECRET DISCOVERY DOES NOT END WITH DELETION

If a real credential was exposed:

```text
Delete From Current File
```

is not sufficient.

The credential may have been:

- committed
- pushed
- copied
- cached
- logged

The active credential must be treated according to the exposure-response process, commonly including revocation or rotation.

---

# 68. PIPELINE SECRETS

Sensitive values should not be stored directly in workflow YAML.

GitHub documents Actions secrets for sensitive workflow information and recommends least-privilege credentials and care because automatic redaction is not guaranteed in every transformation.

---

# 69. KUBERNETES SECRETS

The learner must distinguish:

```text
ConfigMap
```

from:

```text
Secret
```

A ConfigMap is not intended to provide secrecy.

The learner must also understand that placing information in a Kubernetes Secret does not eliminate the need for access control and appropriate cluster security.

---

# 70. ENVIRONMENT VARIABLES

Environment variables can be useful configuration mechanisms.

They are not automatically secure merely because they are not in source code.

Consider:

- process visibility
- debugging output
- logs
- CI output
- container inspection
- crash diagnostics

Handle sensitive values according to the approved secret mechanism.

# 93. FAILURE-INJECTION PRINCIPLE

The learner receives:

```text
Symptom
```

not:

```text
Root Cause
```

Example:

Do not say:

> The application has the wrong port. Fix it.

Say:

> The application is unavailable after deployment.

---

# 94. LEARNER VERSION VERSUS FACILITATOR VERSION

Maintain two versions of the failure exercise.

### Learner Version

Contains:

- symptom
- environment
- available access
- relevant constraints

### Facilitator Version

Contains:

- injected failure
- expected evidence
- likely investigation path
- root cause
- acceptable repair
- verification requirements

The facilitator key must not be distributed with the learner assessment.

Possible hidden injection:

```text

Runtime/service expects another.
```

Learner symptom:


# 96. FAILURE 2: BAD ENVIRONMENT VARIABLE

Possible hidden injection:

```text
Required application configuration contains an invalid value.
```

Possible symptom:

```text

```

The learner should investigate configuration and logs rather than immediately changing Kubernetes infrastructure.

# 97. FAILURE 3: FAILED SERVICE

Possible hidden injection:

```text
Required host service stopped or failed.
```

Symptom:

```text
Expected functionality unavailable.
```

The learner should inspect service state and logs.

# 98. FAILURE 4: FULL DISK

Possible hidden injection:

A disposable filesystem is filled safely for the exercise.

Possible symptoms:

- application cannot write
- logs fail
- service fails
- package operation fails

The learner should discover storage pressure through evidence.

Do not fill critical real filesystems.

# 99. FAILURE 5: BROKEN DNS

Possible hidden injection:

```text
Dependency hostname cannot resolve.
```

Possible symptom:

```text
Application cannot reach dependency.
```

The learner must distinguish:

```text
DNS failure
```

from:

```text
TCP failure
```

and:

```text
application failure.
```

# 100. FAILURE 6: INACCESSIBLE DEPENDENCY

Possible hidden injection:

```text
Dependency resolves but cannot be reached.
```

This tests whether the learner stops after DNS resolution or continues through the network path.

---

# 101. FAILURE 7: EXPIRED CREDENTIAL

Use only disposable lab credentials.

Possible symptom:

```text
Application or pipeline receives authentication failure.
```

The learner must distinguish authentication from authorization.

---

# 102. FAILURE 8: INCORRECT CONTAINER IMAGE

Possible hidden injection:

- nonexistent image
- wrong tag
- wrong application version

The learner should inspect:

- workload status
- events
- image reference
- registry access where relevant

Kubernetes troubleshooting guidance specifically uses workload state, detailed resource information, termination information, and events as evidence sources when diagnosing application failures.

# 103. FAILURE 9: PIPELINE CONFIGURATION ERROR

Possible hidden injection:

- invalid workflow configuration
- missing dependency
- incorrect secret reference
- permission problem

The learner receives:

```text
Pipeline failed.
```

They must identify the failing stage and evidence.

# 104. FAILURE 10: KUBERNETES CONFIGURATION ERROR

Possible hidden injection:

- Service selector mismatch
- wrong target port
- invalid application configuration
- missing ConfigMap reference

# 115. HYPOTHESIS

A hypothesis should be testable.

Good:

```text
The application may be unreachable because it is listening
on a different port than the Service targetPort.
```

Weak:

```text
Kubernetes is broken.
```

---

# 116. TEST

A test should distinguish between possibilities.

For the port hypothesis:

```text
Inspect the application's actual listening socket
and compare it with the Service targetPort.
```

---

# 117. ROOT CAUSE

Do not declare root cause merely because a change fixed the symptom.

The learner should explain the causal chain.

Example:

```text
The application was configured to listen on 9090.

The Service forwarded traffic to 8080.

No application process was listening on 8080.

Requests therefore could not reach the application.
```

---

# 118. REPAIR

The repair should correct the actual cause.

Do not accept unrelated actions such as:

```text
Restart everything.
```

unless evidence justifies the restart.

---

# 119. VERIFICATION

After repair, repeat the evidence path.

For example:

```text
Configuration corrected

Application restarted/redeployed

Expected port listening

Service backend healthy

HTTP request successful

Logs normal

Alert recovered
```

---

# 120. REPAIR IS NOT VERIFICATION

The learner must internalize:

```text
I changed something
```

does not mean:

```text
The problem is fixed.
```

---

# 121. EVIDENCE CHAIN

A strong investigation may look like:

```text
User Failure
     ↓
HTTP Failure Confirmed
     ↓
DNS Successful
     ↓
Network Reachability Successful
     ↓
Service Has No Healthy Backend
     ↓
Pod Running
     ↓
Application Listening on Wrong Port
     ↓
Configuration Mismatch Identified
```

This is far stronger than:

```text
I restarted the Pod and it worked.
```

---

# 122. MULTIPLE HYPOTHESES

The learner may maintain several hypotheses.

Example:

```text

H2: Service selector mismatch

H3: Application not listening

```

Then eliminate them with evidence.


---

# 124. WRONG HYPOTHESIS IS NOT AUTOMATIC FAILURE

Engineering investigations contain wrong hypotheses.

The learner should be rewarded for:

```text
forming a reasonable hypothesis

testing it safely

recognizing contradictory evidence

discarding it

updating the investigation
```

That is good troubleshooting.
