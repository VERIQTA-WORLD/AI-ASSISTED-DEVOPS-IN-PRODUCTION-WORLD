# PART 6: GIT, GITHUB, AND COLLABORATIVE ENGINEERING

## Goal

Use version control safely as part of a team engineering workflow.

By the end of this section, the learner should understand Git as more than a place to save files or a sequence of commands to memorize.

The learner should understand how an engineering change moves through a controlled workflow:

```text
Working Directory
        ↓
Staging Area
        ↓
Local Commit
        ↓
Local Branch
        ↓
Remote Branch
        ↓
Pull Request
        ↓
Review
        ↓
Automated Checks
        ↓
Merge
        ↓
Shared Repository History
```

The learner should also understand what to do when this path does not proceed normally.

Examples include:

```text
Push rejected

Merge conflict

Wrong branch

Detached HEAD

Missing remote

Authentication failure

Accidental local change

Incorrect staged file

Incorrect commit

Remote branch changed

Protected branch rejected the change
```

The objective is not:

> Memorize as many Git commands as possible.

The objective is:

> Understand repository state well enough to make, inspect, share, review, and recover engineering changes without blindly rewriting shared history or destroying someone else's work.

---

# 1. WHY VERSION CONTROL EXISTS

Imagine an engineering team maintaining:

```text
application source code
Terraform configuration
Kubernetes manifests
Helm charts
CI/CD pipelines
shell scripts
Python automation
Ansible configuration
monitoring rules
runbooks
documentation
```

Without version control, engineers might exchange files such as:

```text
deployment.yaml

deployment-new.yaml

deployment-final.yaml

deployment-final-v2.yaml

deployment-final-v2-working.yaml

deployment-final-v2-working-fixed.yaml
```

This creates immediate problems.

Which file is current?

Who changed it?

Why was it changed?

What did the previous version contain?

Was the change reviewed?

Was it tested?

Which version was deployed?

Can the previous state be recovered?

Did two engineers modify the same file independently?

Version control exists to provide a structured history of change.

---

# 2. VERSION CONTROL AS ENGINEERING EVIDENCE

A Git repository can provide evidence about:

```text
what changed

who authored the change

when the change was committed

which files changed

which lines changed

why the author says the change was made

which branch contained the work

how changes relate to earlier commits
```

When combined with a collaborative platform such as GitHub, the engineering record can also include:

```text
pull request discussion

review comments

approvals

automated checks

issue references

merge history

branch protections
```

This makes version control part of engineering governance, not merely file storage.

---

# 3. GIT AND GITHUB ARE NOT THE SAME THING

This distinction must be clear from the beginning.

## Git

Git is the distributed version control system.

Git can operate locally.

You can:

```text
create a repository

create commits

create branches

switch branches

merge branches

inspect history

compare changes
```

without GitHub.

## GitHub

GitHub is a hosted collaboration platform built around Git repositories.

It provides capabilities such as:

```text
remote repository hosting

pull requests

code review

issues

repository permissions

branch protection

rulesets

automation integration

release management

collaboration interfaces
```

Therefore:

```text
Git
≠
GitHub
```

You can use Git without GitHub.

GitHub uses Git repositories but adds collaboration and governance around them.

# 4. THE CORE GIT MENTAL MODEL

Before learning commands, understand the states through which a change moves.

```text
Working Directory
        ↓
Staging Area
        ↓
Local Repository
        ↓
Remote Repository
```

In a collaborative workflow:

```text
Edit File
   ↓
Working Directory
   ↓
git add
   ↓
Staging Area
   ↓
git commit
   ↓
Local Repository
   ↓
git push
   ↓
Remote Branch
   ↓
Pull Request
   ↓
Review / Checks
   ↓
Merge
```

If this model is unclear, Git can feel like a collection of unrelated commands.

Once the model is understood, most basic Git commands answer a simple question:

> Which state am I moving information from, and which state am I moving it to?

---

# 5. REPOSITORY

A Git repository is a directory whose history and state are managed by Git.

Create a directory:

```bash
mkdir veriqta-git-lab
cd veriqta-git-lab
```

Initialize Git:

```bash
git init
```

Git creates repository metadata in:

```text
.git/
```

The `.git` directory contains information Git needs to manage the repository.

This includes repository metadata such as:

```text
object database

references

configuration

HEAD

index
```

At Junior level, you do not need to manipulate these files manually.

In fact, you normally should not.

---

# 6. THE `.git` DIRECTORY IS IMPORTANT

Run:

```bash
ls -la
```

You should see:

```text
.git
```

This is one reason two directories containing identical visible files can behave differently.

One may be a Git repository.

The other may simply be a normal directory.

You can ask Git:

```bash
git status
```

If you are outside a repository, Git will report that it cannot find the repository metadata.

---

# 7. DO NOT RANDOMLY EDIT `.git`

A beginner may discover:

```text
.git/config

.git/HEAD

.git/refs
```

and assume these are ordinary configuration files.

They are part of Git's repository state.

Do not manually modify internal Git metadata unless you understand exactly what you are doing.

Use normal Git commands for normal repository operations.

---

# 8. WORKING TREE

The working tree is the checked-out set of files that you are currently working with.

Suppose the repository contains:

```text
README.md
scripts/
terraform/
kubernetes/
```

You edit:

```text
README.md
```

That edit first exists in your working tree.

It is not automatically committed.

This distinction is fundamental.

---

# 9. SAVING A FILE IS NOT COMMITTING IT

Suppose you edit:

```text
README.md
```

and press Save in your editor.

The file is now changed on disk.

Git can detect the change.

But:

```text
Saved File
≠
Staged Change
```

and:

```text
Saved File
≠
Committed Change
```

and:

```text
Committed Change
≠
Pushed Change
```

and:

```text
Pushed Change
≠
Merged Change
```

These are separate states.

---

# 10. `git status`

One of the most important Git commands is:

```bash
git status
```

A safe Git habit is:

```text
Before action
    ↓
git status
    ↓
Understand current state
    ↓
Perform action
    ↓
git status
    ↓
Verify new state
```

Use `git status` frequently.

It can tell you:

```text
current branch

changed files

untracked files

staged changes

unstaged changes

merge conflicts

branch relationship to upstream
```

depending on repository state.

---

# 11. THE STAGING AREA

Git provides an intermediate state between your working tree and your next commit.

This is commonly called the:

```text
staging area
```

or:

```text
index
```

The mental model is:

```text
Working Tree
     ↓
  git add
     ↓
Staging Area
     ↓
 git commit
     ↓
Repository History
```

The staging area allows you to decide what belongs in the next commit.

---

# 12. WHY STAGING EXISTS

Suppose you modified:

```text
README.md
terraform/main.tf
notes.txt
```

Perhaps:

```text
README.md
```

and:

```text
terraform/main.tf
```

belong to the same engineering change.

But:

```text
notes.txt
```

contains personal temporary notes.

You do not need to commit everything simply because everything changed.

You can stage only the intended files.

For example:

```bash
git add README.md terraform/main.tf
```

Then inspect:

```bash
git status
```

---

# 13. UNTRACKED FILES

Create:

```bash
echo "VERIQTA Git Lab" > README.md
```

Run:

```bash
git status
```

Git may report the file as:

```text
untracked
```

An untracked file exists in the working tree but is not yet part of Git's tracked history.

Stage it:

```bash
git add README.md
```

Then:

```bash
git status
```

The file is now staged for the next commit.

---

# 14. TRACKED FILES

After a file becomes part of repository history, Git tracks changes to it.

Modify:

```bash
echo "" >> README.md
echo "Learning collaborative Git workflows." >> README.md
```

Run:

```bash
git status
```

Git recognizes that the tracked file has changed.

But the new modification is not automatically staged.

---

# 15. STAGED AND UNSTAGED CHANGES CAN EXIST AT THE SAME TIME

This is a very important Git concept.

Suppose:

```bash
git add README.md
```

Then edit `README.md` again.

Now the same file can contain:

```text
staged changes
+
unstaged changes
```

The next commit contains the staged version, not automatically every later edit.

Inspect:

```bash
git status
```

Then inspect both kinds of differences.

---

# 16. `git diff`

Use:

```bash
git diff
```

to inspect unstaged changes in the working tree relative to the index.

For staged changes:

```bash
git diff --staged
```

You may also encounter:

```bash
git diff --cached
```

for the staged comparison.

Before committing, the critical question is:

> What exactly am I about to commit?

Use:

```bash
git diff --staged
```

to answer it.

---

# 17. DIFFS ARE ENGINEERING EVIDENCE

A diff shows the difference between states.

Conceptually:

```diff
-server_port=8080
+server_port=8443
```

A reviewer can immediately see the actual change.

The commit message may say:

```text
Update application configuration
```

but the diff shows what changed.

This leads to an important principle:

```text
Description
≠
Evidence
```

The diff is evidence of the content change.

---

# 18. NEVER COMMIT A CHANGE YOU HAVE NOT INSPECTED

A weak workflow:

```bash
git add .
git commit -m "update"
git push
```

A safer workflow:

```bash
git status
git diff
git add <intended-files>
git diff --staged
git status
git commit
```

The goal is intentional change.

---

# 19. `git add .` IS NOT WRONG, BUT IT REQUIRES ATTENTION

You will often see:

```bash
git add .
```

This stages changes under the current path according to Git's behavior and ignore rules.

It can be useful.

But if you do not inspect the result, you may accidentally stage:

```text
temporary files

debug output

generated files

credentials

large artifacts

unrelated modifications
```

Therefore:

```bash
git add .
git status
git diff --staged
```

is safer than:

```bash
git add .
git commit
```

without inspection.

---

# 20. COMMITS

A commit records a repository state change in Git history.

Create the first commit:

```bash
git commit -m "Add initial README"
```

A commit includes information such as:

```text
snapshot/tree information

parent relationship

author

committer

timestamps

commit message
```

Git identifies commits using cryptographic object IDs.

You commonly see abbreviated commit IDs such as:

```text
a4d9f21
```

rather than the full object ID.

---

# 21. A COMMIT IS LOCAL

This is one of the most important beginner distinctions.

After:

```bash
git commit
```

your commit exists in your local repository.

It has not automatically appeared on GitHub.

Therefore:

```text
Commit
≠
Push
```

---

# 22. COMMIT MESSAGES

A commit message should help another engineer understand the purpose of the change.

Weak:

```text
update
```

Weak:

```text
fix
```

Weak:

```text
changes
```

More useful:

```text
Add health endpoint configuration
```

or:

```text
Correct staging API port
```

or:

```text
Document database recovery procedure
```

The exact commit-message convention depends on the team.

The universal requirement is:

> The message should truthfully describe the change.

---

# 23. DO NOT LIE WITH A COMMIT MESSAGE

Suppose the message says:

```text
Update documentation
```

but the staged diff contains:

```text
README changes

Terraform security group changes

deleted Kubernetes manifest
```

The message is misleading.

Before committing:

```bash
git diff --staged
```

Then make sure the commit message describes the actual staged change.

---

# 24. COMMIT HISTORY

Inspect history:

```bash
git log
```

A compact form:

```bash
git log --oneline
```

You may see:

```text
9c31ab2 Add deployment documentation
7f12d41 Add initial README
```

History allows you to reason about how the repository evolved.

---

# 25. HISTORY IS MORE THAN A BACKUP

Git history can answer:

```text
When did this configuration change?

Which commit introduced this line?

What changed before the incident?

Who authored the change?

Which pull request introduced it?

What did the previous version contain?
```

This becomes extremely valuable during incident investigation.

# 26. BRANCHES

A branch is a movable reference to a line of development.

A beginner-friendly mental model is:

```text
main
  |
  A---B---C
```

Create a feature branch:

```text
main
  |
  A---B---C
           \
            D---E
                |
             feature
```

The new work can proceed without immediately changing `main`.

---

# 27. WHY TEAMS USE BRANCHES

Branches allow engineers to isolate work such as:

```text
feature development

bug fixes

documentation

infrastructure changes

experiments

configuration changes
```

until the work is ready for integration.

A branch does not automatically make a change safe.

It creates isolation.

Safety still depends on:

```text
review

testing

permissions

automated checks

change scope

merge controls
```

---

# 28. DEFAULT BRANCH

Repositories commonly have a default branch such as:

```text
main
```

Some older repositories may use:

```text
master
```

or another name.

Do not assume the branch is always called `main`.

Inspect the repository.

---

# 29. LIST BRANCHES

Run:

```bash
git branch
```

The current branch is marked.

You can also use:

```bash
git status
```

to see the current branch.

---

# 30. CREATE A BRANCH

A modern command is:

```bash
git switch -c feature/add-health-docs
```

This creates the branch and switches to it.

You may also encounter:

```bash
git checkout -b feature/add-health-docs
```

in existing documentation and workflows.

At Junior level, understand both forms because real repositories use both.

---

# 31. SWITCH BRANCHES

Use:

```bash
git switch main
```

Then:

```bash
git switch feature/add-health-docs
```

Before switching, inspect:

```bash
git status
```

Uncommitted changes can affect branch switching.

Do not blindly switch branches while ignoring a dirty working tree.

---

# 32. BRANCH NAMES

Teams may use conventions such as:

```text
feature/add-health-check

fix/database-timeout

docs/update-runbook

chore/update-tooling
```

There is no universal naming convention that every repository must use.

Follow the repository's documented convention.

---

# 33. THE WRONG-BRANCH PROBLEM

A common beginner mistake:

```text
Engineer intends to modify feature branch.

Engineer is actually on main.

Engineer edits files.

Engineer notices afterward.
```

Do not panic.

First:

```bash
git status
```

Then determine:

```text
Are changes committed?

Are they staged?

Are they only in the working tree?

Has anything been pushed?
```

Recovery depends on the actual state.

---

# 34. PREVENT WRONG-BRANCH CHANGES

Before starting work:

```bash
git status
```

or:

```bash
git branch --show-current
```

Confirm:

```text
repository

branch

working tree state
```

before editing.

A ten-second state check can prevent a much larger recovery.

---

# 35. MERGING

A merge integrates histories.

Suppose:

```text
main

A---B---C
         \
          D---E
```

You eventually want the changes from the feature branch integrated into the target branch.

Git may be able to merge automatically.

But not always.

---

# 36. FAST-FORWARD CONCEPT

Suppose `main` has not changed since the feature branch was created:

```text
A---B---C
         \
          D---E
```

If `main` is moved forward to `E`, no divergent history needs to be reconciled.

Conceptually:

```text
A---B---C---D---E
                |
               main
```

This is a fast-forward situation.

You do not need to memorize implementation details yet.

Understand that Git can sometimes integrate by moving a branch reference forward.

---

# 37. DIVERGED HISTORY

Now suppose:

```text
        D---E
       /
A---B---C
       \
        F---G
```

Both lines changed after their common ancestor.

Git must combine histories.

If changes do not conflict, Git can often merge automatically.

If they conflict, human input may be required.

---

# 38. MERGE CONFLICTS

A merge conflict occurs when Git cannot safely determine the intended combined result.

A common example:

Branch A:

```text
port=8080
```

Branch B:

```text
port=9090
```

Both changed the same content differently.

Git cannot know whether the correct final value is:

```text
8080
```

or:

```text
9090
```

or something else.

That is an engineering decision.

---

# 39. A MERGE CONFLICT IS NOT A GIT FAILURE

Git has successfully detected ambiguity.

That is valuable.

The conflict means:

> Git cannot safely determine the final content without human judgment.

Do not treat conflict resolution as:

> Delete the markers until Git stops complaining.

You must determine the intended final state.

---

# 40. CONFLICT MARKERS

A conflicted file may contain markers similar to:

```text
<<<<<<< HEAD
port=8080
=======
port=9090
>>>>>>> feature/change-port
```

These markers show competing content.

Your task is to produce the correct final file.

For example, if the approved configuration should be:

```text
port=8443
```

the final resolution may be neither side exactly.

Conflict resolution is about intended state, not mechanically choosing "ours" or "theirs."

---

# 41. RESOLVING A CONFLICT

The basic process is:

```text
Merge Attempt
    ↓
Conflict Detected
    ↓
Inspect Conflict
    ↓
Understand Both Changes
    ↓
Determine Intended Final State
    ↓
Edit File
    ↓
Test / Validate
    ↓
Stage Resolved File
    ↓
Complete Merge
```

Commands may include:

```bash
git status
```

Then edit the conflicted files.

Stage the resolved result:

```bash
git add <resolved-file>
```

Then complete the merge as appropriate:

```bash
git commit
```

depending on the merge state and Git version/workflow.

---

# 42. ABORTING A MERGE

If you started a merge and realize you should not continue, Git provides:

```bash
git merge --abort
```

when the repository is in a merge state where the command applies.

This attempts to return the repository to the pre-merge state.

Do not confuse:

```text
abort the merge
```

with:

```text
discard every unrelated local change
```

Always inspect state first.

---

# 43. REMOTES

A remote is a named reference to another repository location.

List remotes:

```bash
git remote -v
```

A common remote name is:

```text
origin
```

But:

```text
origin
```

is a convention, not a magical GitHub keyword.

A repository can have:

```text
origin

upstream

company

backup
```

or other remote names.

---

# 44. `origin` DOES NOT MEAN "GITHUB"

`origin` is normally the default remote name created when you clone a repository.

It could point to:

```text
GitHub

GitLab

Bitbucket

self-hosted Git server

local path

other Git-compatible location
```

Inspect:

```bash
git remote -v
```

Do not assume.

---

# 45. ADD A REMOTE

For a local repository that should connect to a remote:

```bash
git remote add origin <repository-url>
```

Verify:

```bash
git remote -v
```

Before pushing, make sure the URL points to the repository you actually intend to modify.

---

# 46. CLONING

Cloning creates a local repository from an existing repository.

Conceptually:

```text
Remote Repository
        ↓
     git clone
        ↓
Local Repository
+
Working Tree
+
Remote Configuration
```

Example structure:

```bash
git clone <repository-url>
```

Then:

```bash
cd <repository-directory>
```

Inspect:

```bash
git status
git remote -v
git branch
```

---

# 47. CLONE VERSUS DOWNLOAD ZIP

Downloading a ZIP archive gives you files.

Cloning gives you a Git repository with version-control metadata and remote relationships.

Therefore:

```text
Download ZIP
≠
git clone
```

For collaborative Git work, use the repository workflow expected by the team.

---

# 48. FETCHING

Fetching retrieves repository information and objects from a remote without automatically integrating the fetched changes into your current branch.

Conceptually:

```text
Remote Repository
       ↓
    git fetch
       ↓
Remote-Tracking References Updated
       ↓
Current Working Branch Not Automatically Merged
```

Run:

```bash
git fetch origin
```

This is valuable because it separates:

```text
obtain remote information
```

from:

```text
integrate remote information into my branch
```

---

# 49. REMOTE-TRACKING BRANCHES

After fetching, you may see references such as:

```text
origin/main
```

This is not the same as your local:

```text
main
```

Think:

```text
main
→ my local branch

origin/main
→ my local representation of the remote branch state learned from origin
```

This distinction is essential.

---

# 50. FETCH DOES NOT MEAN YOUR LOCAL BRANCH IS UPDATED

Suppose:

```text
origin/main
```

moves forward after:

```bash
git fetch origin
```

Your local:

```text
main
```

does not automatically become identical.

You can inspect the differences before integrating them.

That is one reason `fetch` is useful for careful engineering workflows.

---

# 51. PULLING

`git pull` retrieves remote changes and integrates them into the current branch according to the configured or specified reconciliation behavior.

A simplified beginner model is often:

```text
git pull
≈
fetch
+
integration
```

The integration may involve merge or rebase depending on command options and configuration.

Do not blindly memorize:

```text
pull = fetch + merge
```

as an absolute statement for every configured workflow.

---

# 52. FETCH VERSUS PULL

Think:

```text
git fetch
```

means:

> Bring remote information into my local repository so I can inspect it.

Whereas:

```text
git pull
```

means:

> Retrieve remote changes and attempt to integrate them into my current branch.

For troubleshooting or careful inspection, `fetch` often provides more control.

---

# 53. PUSHING

Pushing sends local repository references and associated objects to a remote repository.

A common first push:

```bash
git push -u origin feature/add-health-docs
```

The `-u` option can establish an upstream tracking relationship for the branch.

Later, depending on configuration:

```bash
git push
```

may be sufficient.

---

# 54. PUSH DOES NOT MEAN MERGE

Suppose you push:

```text
feature/add-health-docs
```

to GitHub.

That means the remote feature branch now contains your pushed commits.

It does not automatically mean:

```text
main changed
```

The normal team workflow may still require:

```text
Pull Request
↓
Review
↓
Checks
↓
Approval
↓
Merge
```

---

# 55. UPSTREAM BRANCH

A local branch can track an upstream branch.

Inspect:

```bash
git branch -vv
```

You may see relationships such as:

```text
feature/add-health-docs
→ origin/feature/add-health-docs
```

This relationship helps Git determine default behavior for commands such as:

```bash
git pull
git push
```

depending on configuration.

---

# 56. REJECTED PUSH

A common message is a non-fast-forward rejection.

Conceptually:

```text
Remote:

A---B---C---D

Local:

A---B---C---E
```

The remote contains `D`, which your local branch does not contain.

If Git simply replaced the remote branch with your local history, `D` could be lost from the branch history.

Git therefore rejects the ordinary push.

This is protection.

---

# 57. DO NOT RESPOND TO A REJECTED PUSH WITH FORCE

A dangerous beginner reaction:

```bash
git push --force
```

This may rewrite remote branch history.

On a shared branch, that can remove or replace commits other engineers rely on.

Instead ask:

```text
Why was the push rejected?

What changed remotely?

What is my local branch based on?

Do I need to fetch?

Do I need to merge?

Does the team use rebase?

Is the branch protected?
```

---

# 58. SAFE REJECTED-PUSH INVESTIGATION

Start:

```bash
git status
```

Then:

```bash
git fetch origin
```

Inspect:

```bash
git log --oneline --graph --decorate --all
```

You can compare:

```bash
git log HEAD..origin/<branch> --oneline
```

and:

```bash
git log origin/<branch>..HEAD --oneline
```

Then follow the repository's integration policy.

Do not rewrite shared history simply to make the error disappear.

---

# 59. `.gitignore`

A `.gitignore` file specifies patterns for intentionally untracked files that Git should ignore.

Example:

```gitignore
.env
*.log
tmp/
.DS_Store
```

Common categories include:

```text
editor files

temporary files

generated output

logs

build artifacts

local environment files
```

But `.gitignore` is not a security system.

---

# 60. `.gitignore` DOES NOT REMOVE AN ALREADY TRACKED SECRET

Suppose:

```text
credentials.env
```

was committed.

Later you add:

```gitignore
credentials.env
```

That does not erase the file from existing Git history.

This distinction is critical.

If a real secret has been committed, treat it as potentially exposed according to the organization's incident and credential-rotation procedures.

Do not assume adding the filename to `.gitignore` fixes the security problem.

---

# 61. NEVER COMMIT SECRETS INTENTIONALLY

Examples include:

```text
cloud access keys

private SSH keys

API tokens

database passwords

service-account credentials

TLS private keys

personal access tokens
```

Before committing:

```bash
git diff --staged
```

Look for sensitive material.

Repository security controls may also scan for secrets, but human responsibility remains.

---

# 62. IGNORE PATTERNS SHOULD BE INTENTIONAL

Do not copy a huge `.gitignore` file without understanding it.

An overly broad rule can hide important files.

For example:

```gitignore
*.tfvars
```

may be appropriate in one repository and incorrect in another depending on how configuration is managed.

Understand the repository's design.

---

# 63. TAGS

A Git tag names a specific point in repository history.

Tags are commonly used to identify:

```text
releases

versions

milestones

deployment references
```

Example:

```bash
git tag v1.0.0
```

List:

```bash
git tag
```

Inspect:

```bash
git show v1.0.0
```

---

# 64. LIGHTWEIGHT AND ANNOTATED TAGS

Git supports different tag forms.

A lightweight tag is essentially a name pointing at an object.

An annotated tag stores additional tag metadata.

Example:

```bash
git tag -a v1.0.0 -m "Release v1.0.0"
```

For release workflows, teams often prefer annotated or otherwise managed release tags according to their standards.

Do not invent your own tagging policy inside an established repository.

---

# 65. TAGS ARE NOT BRANCHES

A branch normally moves as new commits are added.

A tag normally identifies a particular historical point.

Conceptually:

```text
             main
              ↓
A---B---C---D---E
        ↑
      v1.0.0
```

The tag remains associated with the chosen point unless deliberately changed.

---

# 66. PULL REQUESTS

A pull request is a collaborative proposal to integrate changes from one branch into another.

Conceptually:

```text
Feature Branch
      ↓
Pull Request
      ↓
Diff
      ↓
Discussion
      ↓
Review
      ↓
Automated Checks
      ↓
Approval
      ↓
Merge
```

A pull request is not simply:

> Please copy my branch.

It creates a reviewable engineering boundary around a proposed change.

---

# 67. BASE AND HEAD BRANCHES

In a pull request:

```text
Base Branch
```

is the branch you want to change.

```text
Head / Compare Branch
```

contains the proposed changes.

Example:

```text
feature/add-health-docs
        ↓
       PR
        ↓
      main
```

Always verify the base branch before opening a pull request.

A technically correct change proposed against the wrong branch is still a workflow error.

---

# 68. A GOOD PULL REQUEST EXPLAINS INTENT

A useful pull request should help reviewers answer:

```text
What problem does this solve?

What changed?

Why was this approach chosen?

How was it tested?

What risks exist?

How can the change be verified?

Does it require deployment or migration steps?

Does rollback require special handling?
```

The exact template depends on the repository.

---

# 69. SMALL PULL REQUESTS ARE EASIER TO REASON ABOUT

A pull request containing:

```text
one focused infrastructure change
```

is usually easier to review than one containing:

```text
Terraform refactor

Kubernetes update

documentation rewrite

unrelated formatting

dependency upgrade

debug script

pipeline modification
```

all mixed together.

A useful engineering principle is:

```text
One coherent change
→
One reviewable unit
```

when practical.

---

# 70. CODE REVIEW

Code review is the process of examining proposed changes before integration.

Review is not merely:

```text
Looks good.
```

A reviewer may examine:

```text
correctness

security

failure behavior

maintainability

scope

tests

observability

backward compatibility

configuration

deployment risk

rollback implications

documentation
```

For infrastructure changes, reviewers may also examine:

```text
blast radius

resource replacement

permissions

network exposure

state changes

data impact
```

---

# 71. REVIEW THE DIFF, NOT ONLY THE DESCRIPTION

The pull request author may write:

```text
This change only updates the health check.
```

The reviewer should verify that claim against the diff.

Human descriptions can be incomplete or wrong.

AI-generated descriptions can also be wrong.

The diff remains essential evidence.

---

# 72. CODE REVIEW IS NOT PERSONAL

A review comment such as:

```text
This change grants broader permissions than the service requires.
```

is about the proposed engineering change.

Good review focuses on:

```text
system behavior

risk

evidence

requirements

maintainability
```

rather than the person.

---

# 73. PROTECTED BRANCHES

Important branches such as:

```text
main
```

may be protected.

Protection can enforce rules before changes are accepted.

Depending on repository configuration, protections can require things such as:

```text
pull requests

approving reviews

status checks

resolved conversations

signed commits

linear history

restricted push permissions
```

and can restrict actions such as branch deletion or force pushing.

The exact rules depend on repository configuration.

---

# 74. WHY PROTECT `main`

Consider:

```text
Engineer
   ↓
Direct Push
   ↓
main
   ↓
Deployment Pipeline
   ↓
Production
```

If every engineer can directly change `main`, important review and validation controls may be bypassed.

A protected workflow can instead require:

```text
Engineer
   ↓
Feature Branch
   ↓
Pull Request
   ↓
Review
   ↓
Automated Checks
   ↓
Approval
   ↓
Merge
   ↓
main
```

This creates controlled change.

---

# 75. BRANCH PROTECTION IS A GUARDRAIL

A protected branch does not guarantee good code.

It can enforce process conditions.

For example:

```text
Review happened.
```

does not prove:

```text
Reviewer noticed every defect.
```

Similarly:

```text
CI passed.
```

does not prove:

```text
Production cannot fail.
```

Controls reduce risk.

They do not eliminate engineering judgment.

---

# 76. STATUS CHECKS

A repository may require automated checks before merge.

Examples include:

```text
unit tests

integration tests

linting

format validation

security scanning

Terraform validation

policy checks

build verification
```

If a required check fails, investigate the failure.

Do not attempt to bypass the check merely because the code "looks fine."

---

# 77. MERGE STRATEGIES

GitHub repositories can support different pull-request merge strategies.

Common approaches include:

```text
merge commit

squash and merge

rebase and merge
```

Each affects repository history differently.

At Junior level, you do not need to declare one universally superior.

Follow the repository's policy.

---

# 78. MERGE COMMIT

A merge commit can preserve branch history and create an explicit merge point.

Conceptually:

```text
A---B---C-------M
     \         /
      D---E---F
```

`M` represents the merge.

---

# 79. SQUASH MERGE

A squash merge combines the pull request's changes into a single commit on the base branch.

Feature branch:

```text
D
E
F
```

may become one resulting commit:

```text
S
```

on the target branch.

This can keep target-branch history concise.

---

# 80. REBASE MERGE

A rebase-style merge places commits onto the target branch without creating a merge commit.

Conceptually, the history becomes linear.

The important Junior lesson is:

> Merge behavior is a repository policy decision. Understand the project's chosen workflow before manipulating history.

---

# 81. BASIC ROLLBACK CONCEPTS

Rollback in Git requires precision.

There are several different situations:

```text
Uncommitted change

Staged change

Local commit

Pushed commit

Merged shared commit

Production deployment
```

These are not the same problem.

Do not use one destructive command for all of them.

---

# 82. RECOVERING AN UNSTAGED FILE CHANGE

Suppose you changed:

```text
README.md
```

but have not staged the change.

First inspect:

```bash
git diff README.md
```

If you deliberately want to discard the working-tree modification:

```bash
git restore README.md
```

This can destroy the uncommitted change.

Therefore inspect first.

---

# 83. UNSTAGING A FILE

Suppose you accidentally staged:

```text
notes.txt
```

Inspect:

```bash
git status
```

You can remove it from the staging area while retaining the working-tree content:

```bash
git restore --staged notes.txt
```

Then:

```bash
git status
```

Verify the result.

---

# 84. RESTORE AND DELETE ARE NOT THE SAME THING

If you run a command that restores a tracked file to an earlier state, your current uncommitted modifications may be lost.

Before any recovery command:

```text
What state is the file in?

Is the content committed anywhere?

Is it staged?

Do I need to preserve it?

What exactly will this command modify?
```

Recovery begins with state identification.

---

# 85. REVERTING A SHARED COMMIT

For a commit already shared with others, one safe collaborative approach is often to create a new commit that reverses the earlier commit.

Git provides:

```bash
git revert <commit>
```

Conceptually:

```text
A---B---C
        ↓
     Bad Change
        ↓
A---B---C---D
            ↑
       Reverting Change
```

History remains visible.

This differs fundamentally from rewriting history.

---

# 86. REVERT DOES NOT ERASE HISTORY

If commit `C` introduced a bad change and commit `D` reverts it:

```text
A---B---C---D
```

both remain in history.

This can be desirable for shared branches because the record of what happened remains.

---

# 87. RESET IS DIFFERENT

Git also provides:

```bash
git reset
```

which can move branch state and, depending on mode, affect the staging area and working tree.

Different modes have different consequences.

At Junior level:

> Do not use `git reset --hard` as a generic recovery command.

It can discard local work.

Before using reset, understand:

```text
which commit reference moves

what happens to staging

what happens to working-tree changes

whether commits have already been shared
```

---

# 88. `git reset --hard` IS NOT "UNDO"

A dangerous mental model:

```text
Something went wrong
↓
git reset --hard
```

A better model:

```text
Something went wrong
↓
Stop
↓
git status
↓
Identify state
↓
Inspect history
↓
Determine what must be preserved
↓
Choose recovery method
```

---

# 89. FORCE PUSHING

A force push allows remote history to be updated in ways an ordinary push would reject.

This can be legitimate in controlled workflows.

It can also destroy collaborators' assumptions about shared history.

At Junior level:

> Never use force push on a shared or protected branch merely to make an error disappear.

Understand the repository policy and escalate when uncertain.

---

# 90. `--force-with-lease`

You may encounter:

```bash
git push --force-with-lease
```

This provides additional safety compared with an unconditional `--force` because it checks expected remote state before replacing it.

However:

```text
Safer Than --force
≠
Automatically Safe
```

It still rewrites branch history.

Do not use it without understanding why history rewriting is required.

---

# 91. DETACHED HEAD

Normally, `HEAD` refers through the currently checked-out branch.

Conceptually:

```text
HEAD
 ↓
main
 ↓
Commit C
```

In a detached HEAD state:

```text
HEAD
 ↓
Commit B
```

without being attached to a normal local branch.

---

# 92. HOW DETACHED HEAD CAN HAPPEN

For example, checking out a specific historical commit can place you in detached HEAD state.

You may do this intentionally to:

```text
inspect old code

test an earlier state

investigate a regression
```

Detached HEAD is not automatically an error.

It is a repository state you must understand.

---

# 93. WHY DETACHED HEAD MATTERS

You can create commits while detached.

But those commits are not automatically part of a normal named branch.

If the work matters, create a branch pointing to it before moving away.

For example:

```bash
git switch -c recovery/my-work
```

when appropriate.

The exact recovery depends on current state.

---

# 94. DETACHED HEAD AWARENESS

If Git tells you:

```text
You are in 'detached HEAD' state
```

do not ignore the message.

Ask:

```text
Why am I here?

Am I intentionally inspecting history?

Have I created new work?

Do I need to preserve that work on a branch?
```

# 95. AUTHENTICATION

Git operations against remote services may require authentication.

Depending on repository configuration and hosting service, this can involve:

```text
SSH

HTTPS credentials/tokens

credential helpers

organization authentication controls
```

Do not assume:

```text
Authentication failure
=
Repository does not exist
```

The repository may exist while your credentials or permissions are wrong.

---

# 96. SSH REMOTES

A remote might look conceptually like:

```text
git@github.com:organization/repository.git
```

Authentication commonly uses SSH keys.

Part 2 introduced SSH key handling.

Git now gives that knowledge an engineering use.

Inspect:

```bash
git remote -v
```

Then determine whether the repository uses:

```text
SSH
```

or:

```text
HTTPS
```

before troubleshooting authentication.

---

# 97. AUTHENTICATION FAILURE WORKFLOW

If push fails:

```text
1. Read the exact error.

2. Inspect remote URL.

3. Determine SSH or HTTPS.

4. Verify account identity.

5. Verify credential/key availability.

6. Verify repository permission.

7. Verify organization requirements.

8. Test authentication appropriately.

9. Retry only after identifying the failure.
```

Do not repeatedly regenerate SSH keys without evidence that the key is the problem.

---

# 98. MISSING REMOTE

Suppose:

```bash
git push
```

fails because no remote or upstream is configured.

Inspect:

```bash
git remote -v
```

If nothing appears, ask:

```text
Was this repository created locally?

Was it cloned?

Which remote repository should it connect to?
```

Do not randomly add a remote URL.

Confirm the intended repository.

---

# 99. WRONG REMOTE

A more dangerous situation is not:

```text
No remote.
```

It is:

```text
Wrong remote.
```

Before your first push in an unfamiliar repository:

```bash
git remote -v
```

Confirm:

```text
organization

repository

protocol

remote name
```

You do not want to push proprietary or sensitive work to the wrong repository.

# 100. COLLABORATIVE CHANGE WORKFLOW

A safe Junior workflow is:

```text
1. Identify repository.

2. Inspect current branch.

3. Inspect working tree.

4. Update knowledge of remote state.

5. Create appropriate branch.

6. Make one focused change.

7. Inspect working-tree diff.

8. Test change.

9. Stage intended files.

10. Inspect staged diff.

11. Commit with truthful message.

12. Inspect history/state.

13. Push feature branch.

14. Open pull request.

15. Review pull request diff.

16. Allow automated checks to run.

17. Respond to review.

18. Update branch if required.

19. Obtain approval.

20. Merge according to repository policy.

21. Verify resulting state.
```

# 140. AI-GENERATED COMMIT MESSAGES MUST BE VERIFIED

Suppose the diff changes:

```diff
-timeout = 30
+timeout = 60
```

AI says:

```text
Fix production database outage by optimizing timeout handling
```

That description is unsupported.

The diff only proves:

```text
timeout value changed from 30 to 60
```

It does not prove:

```text
outage fixed

database involved

performance improved

root cause identified
```

A better message might be:

```text
Increase service timeout from 30 to 60 seconds
```

if that accurately reflects the configuration.

---

# 141. AI-GENERATED PR DESCRIPTIONS MUST BE VERIFIED

AI may write:

```text
This change improves reliability and eliminates connection failures.
```

But if the diff only modifies:

```text
timeout: 30 → 60
```

those claims require evidence.

A truthful description:

```text
This change increases the configured request timeout from 30 seconds to 60 seconds.

The effect on production reliability has not been established by this configuration change alone.
```

Accuracy matters more than impressive wording.
