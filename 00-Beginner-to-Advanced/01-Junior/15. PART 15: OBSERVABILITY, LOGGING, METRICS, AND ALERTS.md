# PART 15: OBSERVABILITY, LOGGING, METRICS, AND ALERTS

## Goal

Learn how engineers determine what a production system is doing instead of guessing from user reports.

By the end of this Part, the learner should be able to receive a report such as:

```text
The application is slow.
```

and resist the temptation to immediately:

```text
restart the application

restart the server

add CPU

add memory

scale replicas

change configuration

redeploy

blame the network
```

Instead, the learner should establish:

```text
What is the symptom?

When did it begin?

Who is affected?

Is the problem continuous or intermittent?

What changed?

What does latency show?

What does request rate show?

What does the error rate show?

What does CPU show?

What does memory show?

What does disk show?

What does network activity show?

What do application logs show?

What do system logs show?

Did an alert fire?

What evidence changed at the same time?
```

The central engineering principle is:

```text
Reported Symptom
        ↓
Telemetry
        ↓
Evidence
        ↓
Correlation
        ↓
Hypothesis
        ↓
Test
        ↓
Root Cause
        ↓
Corrective Action
        ↓
Verification
```

not:

```text
Reported Symptom
        ↓
Guess
        ↓
Change Production
```

---

# 1. OBSERVABILITY STARTS WITH QUESTIONS

A production system is constantly changing.

Requests arrive.

Processes execute.

Memory is allocated and released.

Files are read and written.

Network connections open and close.

Dependencies respond at different speeds.

Errors occur.

Deployments happen.

Containers restart.

Users experience different outcomes.

Without telemetry, much of this activity is invisible.

When a user reports:

```text
The application feels slow.
```

that statement is valuable.

But it is not yet a diagnosis.

---

# 2. USER REPORT VERSUS ENGINEERING EVIDENCE

A user may observe:

```text
Page took 12 seconds to load.
```

The engineer needs to determine why.

Possible causes include:

```text
high application latency

database latency

external API latency

CPU saturation

memory pressure

disk I/O pressure

network problems

request queueing

traffic increase

application errors and retries

resource exhaustion

bad deployment

dependency degradation
```

The symptom alone cannot distinguish these.

Observability helps convert:

```text
Something is wrong.
```

into:

```text
The application's request latency increased at 14:07.

Request volume remained normal.

CPU remained below its normal operating range.

Memory remained stable.

The error rate did not increase.

Application logs show database queries taking several seconds.

The database dependency is therefore the current leading
investigation path.
```

That is evidence-supported reasoning.

---

# 3. MONITORING AND OBSERVABILITY

The terms are related but should not be treated as perfect synonyms.

A simple Junior-level distinction is:

```text
Monitoring
→ watching known measurements and conditions
```

while observability is concerned more broadly with using telemetry emitted by a system to understand its internal behavior.

Monitoring might answer:

```text
Is CPU above 90%?
```

Observability investigation might ask:

```text
Why did checkout latency increase only for one request path
after the latest deployment?
```

Do not turn this distinction into a vocabulary argument.

The engineering objective is:

```text
Understand System Behavior From Evidence
```

---

# 4. TELEMETRY

Telemetry is data produced about the operation and behavior of a system.

Examples include:

```text
CPU utilization

memory availability

HTTP request counts

request latency

error counts

application log records

system log records

request traces

deployment events

container restart events
```

Telemetry becomes useful when it helps answer an operational question.

---

# 5. MORE DATA DOES NOT AUTOMATICALLY MEAN BETTER OBSERVABILITY

A system can generate:

```text
millions of log lines

thousands of metrics

hundreds of dashboards

thousands of alerts
```

and still be difficult to operate.

Why?

Because useful observability requires:

```text
meaningful signals

correct instrumentation

consistent context

usable queries

retention

dashboards

alert design

operational ownership

human interpretation
```

Therefore:

```text
More Telemetry
≠
More Understanding
```

---

# 6. FOUR USEFUL SIGNAL CATEGORIES

For this Part, work with four practical categories:

```text
Logs

Metrics

Traces

Events
```

They answer different questions.

---

# 7. LOGS

A log records an event or message produced by software or infrastructure.

Examples:

```text
application started

request failed

database connection refused

configuration loaded

user authentication failed

disk mount failed

service stopped
```

Logs are often rich in detail.

---

# 8. METRICS

Metrics represent measurements over time.

Examples:

```text
CPU utilization

available memory

request count

error count

request duration

disk usage

queue depth
```

Metrics are particularly useful for understanding:

```text
trends

rates

levels

thresholds

changes over time
```

---

# 9. TRACES

A trace follows the path of work, commonly a request, through one or more operations or services.

Conceptually:

```text
User Request
    ↓
Frontend
    ↓
API
    ↓
Authentication Service
    ↓
Database
    ↓
Response
```

A trace can help determine where time was spent across that path.

---

# 10. EVENTS

An event records that something happened.

Examples:

```text
deployment started

deployment completed

Pod restarted

server rebooted

configuration changed

autoscaling action occurred

alert changed state
```

Events can provide important timeline context.

---

# 11. SIGNALS COMPLEMENT EACH OTHER

Suppose latency rises.

Metrics show:

```text
p95 latency increased
```

Logs show:

```text
database timeout
```

A trace shows:

```text
most request time spent waiting for database operation
```

A deployment event shows:

```text
new application version deployed five minutes before degradation
```

Together, these signals tell a much richer story than any one signal alone.

---

# 12. ONE SIGNAL RARELY TELLS THE WHOLE STORY

A CPU graph at 95% does not automatically prove:

```text
CPU is the root cause.
```

The CPU increase may be:

```text
expected traffic

retry storm

expensive application loop

compression work

garbage collection

background task

symptom of another failure
```

Correlation and investigation are required.

---

# 13. CORRELATION IS NOT CAUSATION

Suppose:

```text
14:05 CPU rises

14:05 latency rises
```

That is useful correlation.

It does not yet prove:

```text
CPU caused latency.
```

Both might have been caused by:

```text
traffic increase
```

or another shared event.

Observability narrows investigation.

It does not eliminate engineering reasoning.

---

# 14. THE TIME AXIS

Time is one of the most important dimensions in observability.

When investigating an incident, ask:

```text
When did the symptom begin?

What changed immediately before it?

Which signals changed at the same time?

Did they recover together?

Was the problem gradual or sudden?
```

Without accurate timestamps, correlation becomes much harder.

---

# 15. CLOCKS MATTER

Imagine:

Application log:

```text
10:04:12 database timeout
```

Infrastructure event:

```text
14:04:10 database failover
```

If one system records local time and another UTC without clear timezone information, correlation becomes confusing.

Production telemetry should make timestamps unambiguous.

UTC is commonly useful for centralized systems.

---

A useful model is:

```text

   ↓

   ↓
```

---

# 17. OBSERVABILITY SYSTEMS CAN FAIL TOO

Suppose:

```text
Dashboard shows no data.
```

Possible causes include:

```text
application stopped emitting telemetry

collector failed

scraping failed

network path failed

storage failed

query is wrong

time range is wrong

dashboard variable is wrong

permissions changed
```

Therefore:

```text
No Data
≠
No Problem
```

and:

```text
No Data
≠
Zero
```

This distinction is critical.

---

# 18. METRICS AS TIME SERIES

A metric normally becomes useful when associated with:

```text
value

timestamp

identity/context
```

Example conceptually:

```text
http_requests_total{
  method="GET",
  route="/health",
  status="200"
} 1527
```

Labels provide dimensions for querying and grouping.

---

# 19. LABELS

Metric labels add dimensions.

Example:

```text
method="GET"

route="/api/orders"

status="500"
```

This allows questions such as:

```text
How many requests failed?

Which route failed?

Which status code increased?
```

Labels are powerful.

They must also be designed carefully.

---

# 20. LABEL CARDINALITY

Every unique combination of metric labels can create another time series.

A dangerous label might be:

```text
user_id
```

if there are millions of users.

Another dangerous example:

```text
request_id
```

because it can be unique for every request.

This can create enormous numbers of time series.

At Junior level, remember:

```text
Useful Dimensions
→ Good

Unbounded Unique Values
→ Potentially Expensive
```

Do not add labels casually.

---

# 21. COMMON METRIC TYPES

Prometheus commonly exposes metric types including:

```text
Counter

Gauge

Histogram

Summary
```

For this Junior Part, concentrate mainly on:

```text
Counter

Gauge

Histogram
```

and understand Summary conceptually.

---

# 22. COUNTER

A counter represents a cumulative value that increases and can reset, for example when a process restarts.

Typical uses:

```text
requests processed

errors observed

jobs completed

bytes transferred
```

Example:

```text
http_requests_total
```

A raw counter value such as:

```text
1,500,000 requests
```

is often less operationally useful than:

```text
requests per second over the last five minutes
```

---

# 23. COUNTER RESET

Suppose:

```text
12:00  5000
12:01  5200
12:02  5400
12:03  20
```

The drop does not necessarily mean:

```text
5380 requests disappeared.
```

The process may have restarted and the counter reset.

Metric systems and queries must account for counter behavior.

---

# 24. RATE

For counters, engineers often care about how quickly the counter is increasing.

Conceptually:

```text
Counter Change
      ÷
Time
      ↓
Rate
```

For request counters:

```text
requests per second
```

is often more useful than lifetime request count.

---

# 25. GAUGE

A gauge represents a value that can move upward or downward.

Examples:

```text
memory currently used

queue depth

active connections

temperature

current number of workers
```

Conceptually:

```text
42
↓
39
↓
51
↓
45
```

is normal gauge behavior.

---

# 26. HISTOGRAM

A histogram records observations into buckets and also typically exposes count and sum information.

Latency is a common use.

Instead of storing every request duration as a separate time series value, observations can be accumulated into buckets.

This supports questions such as:

```text
What proportion completed under 500 ms?

What is approximately the 95th percentile latency?
```

---

# 27. LATENCY DISTRIBUTIONS MATTER

Suppose average latency is:

```text
200 ms
```

That sounds healthy.

But perhaps:

```text
95% of requests:
100 ms

5% of requests:
2 seconds
```

Averages can hide poor tail behavior.

Percentiles can reveal what slower portions of the request population experience.

---

# 28. PERCENTILES

Common latency percentiles include:

```text
p50

p90

p95

p99
```

Conceptually:

```text
p95 = 800 ms
```

means approximately 95% of observations are at or below that latency and about 5% are above it, subject to how the measurement is calculated.

Do not interpret:

```text
p95
```

as:

```text
95% slower.
```

---

# 29. SUMMARY

A Summary is another metric type used for observations.

Its aggregation and quantile characteristics differ from histograms.

At Junior level, know that it exists.

Do not choose between Summary and Histogram casually in production without understanding the tradeoffs.

---

# 30. CPU METRICS

CPU telemetry can help answer:

```text
How busy is the processor?

Is utilization sustained?

Did CPU behavior change when latency changed?

Is one process consuming most CPU?
```

CPU should be interpreted with context.

---

# 31. HIGH CPU IS NOT AUTOMATICALLY BAD

A compute-intensive workload may legitimately use available CPU.

The important question is:

```text
Is CPU saturation preventing required work from completing
within acceptable performance expectations?
```

High utilization alone does not answer that.

---

# 32. CPU AND APPLICATION LATENCY

Suppose:

```text
CPU:
95%

Latency:
high

Request rate:
normal
```

Possible hypothesis:

```text
application may be CPU constrained
```

Now gather additional evidence.

Do not immediately resize the machine.

---

# 33. MEMORY METRICS

Useful memory observations include concepts such as:

```text
available memory

used memory

cache

swap activity

process memory

memory pressure
```

Recall Part 4:

```text
low "free" memory
```

alone does not prove memory exhaustion.

Linux intentionally uses memory for useful caching.

---

# 34. MEMORY TREND

A time-series view can reveal:

```text
stable memory
```

versus:

```text
continuously increasing memory
```

A steadily rising application memory footprint can justify investigation.

But a graph alone does not prove a memory leak.

---

# 35. DISK METRICS

Important disk-related measurements include:

```text
filesystem utilization

available space

inode availability

I/O throughput

I/O latency

I/O pressure
```

A disk can create application problems without being:

```text
100% full.
```

Slow storage can increase request latency.

---

# 36. FILESYSTEM CAPACITY

A useful dashboard might show:

```text
Filesystem Used %

Available Bytes

Available Inodes
```

Why all three?

Because:

```text
space available
```

does not guarantee:

```text
inodes available
```

and vice versa.

---

# 37. NETWORK METRICS

Network telemetry may include:

```text
bytes received

bytes transmitted

packets

errors

drops

connection information
```

Network traffic increasing is not automatically a problem.

Ask:

```text
Is the increase expected?

Is there loss?

Is throughput near a known limit?

Does it correlate with application degradation?
```

---

# 38. REQUEST RATE

Request rate answers:

```text
How much traffic is the application receiving?
```

This is one of the most important application-level metrics.

Suppose latency increases.

Compare:

```text
request rate before incident

request rate during incident
```

If traffic increased 10×, that matters.

If traffic stayed flat, another explanation becomes more likely.

---

# 39. ERRORS

Error metrics answer questions such as:

```text
How many requests failed?

What fraction failed?

Which endpoints failed?

Which status classes increased?
```

An error count without request volume can mislead.

---

# 40. ERROR RATE

Suppose:

```text
100 errors
```

If total requests are:

```text
100
```

that is catastrophic.

If total requests are:

```text
10,000,000
```

the interpretation is different.

Therefore consider:

```text
Errors
÷
Requests
```

where appropriate.

---

# 41. LATENCY

Latency measures how long work takes.

Examples:

```text
HTTP request duration

database query duration

external API duration

queue processing duration
```

Latency is often closer to user experience than host CPU.

---

# 42. SATURATION

Saturation asks whether a resource has more demand than it can comfortably service.

Examples can include:

```text
CPU run queue pressure

full worker pools

connection pool exhaustion

queue backlog

storage I/O pressure

thread pool saturation
```

A system can experience poor performance because work is waiting, even before a simple utilization metric reaches an obvious threshold.

---

# 43. RESOURCE METRICS AND SERVICE METRICS

Separate:

```text
Host / Infrastructure Metrics
```

from:

```text
Application / Service Metrics
```

Host:

```text
CPU

memory

disk

network
```

Application:

```text
request rate

errors

latency

active requests

dependency failures
```

Both are useful.

---

# 44. USER-CENTRIC SIGNALS

When possible, begin close to user-visible symptoms:

```text
Is the service available?

Are requests succeeding?

How long are requests taking?
```

Then move downward into causes:

```text
CPU

memory

disk

network

dependency state
```

This helps avoid alerting only on internal implementation details.

---

# 45. RED METHOD

A useful conceptual model for request-driven services is:

```text
Rate

Errors

Duration
```

This is often called RED.

At Junior level, use it as a troubleshooting lens, not a rigid universal law.

---

# 46. USE METHOD

For infrastructure resources, another useful conceptual lens is:

```text
Utilization

Saturation

Errors
```

This is often called USE.

Again:

```text
framework
≠
automatic diagnosis
```

---

# 47. GOLDEN SIGNAL THINKING

Another commonly encountered operational model focuses on:

```text
latency

traffic

errors

saturation
```

Different organizations may use different frameworks.

The Junior engineer should understand the reasoning beneath them rather than memorizing names.

---

# 48. APPLICATION LOGS

Application logs originate from the application.

Examples:

```text
server started

request completed

authentication failed

dependency timeout

configuration invalid

database connection failed
```

Good application logs help explain application behavior.

---

# 49. SYSTEM LOGS

System logs provide evidence about operating-system and service behavior.

Depending on the Linux environment, tools can include:

```text
journalctl

systemd journal

traditional log files
```

Recall Part 4.

Application logs and system logs answer different questions.

---

# 50. LOG LEVELS

Common severity concepts include:

```text
DEBUG

INFO

WARNING / WARN

ERROR

CRITICAL / FATAL
```

Exact levels and semantics depend on the logging framework.

Do not assume every application uses them identically.

---

# 51. DEBUG LOGGING

Debug logs can provide detailed diagnostic information.

They can also increase:

```text
log volume

storage cost

CPU overhead

I/O

sensitive-data exposure
```

Do not enable highly verbose production logging casually.

---

# 52. INFO LOGGING

Informational logs commonly represent expected operational events.

Examples:

```text
application started

configuration loaded

worker initialized

request completed
```

An INFO message is not necessarily a problem.

---

# 53. ERROR LOGGING

An ERROR log indicates a failure according to application semantics.

But:

```text
ERROR line
≠
production incident
```

Some errors may be:

```text
expected

handled

isolated

caused by invalid client requests
```

Context matters.

---

# 54. UNSTRUCTURED LOG

Example:

```text
2026-10-01 14:22:01 ERROR checkout failed for order 1927
```

A human can read it.

Machines can parse it, but parsing may depend on fragile text patterns.

---

# 55. STRUCTURED LOG

Example:

```json
{
  "timestamp": "2026-10-01T14:22:01Z",
  "level": "ERROR",
  "service": "checkout",
  "event": "checkout_failed",
  "order_id": "1927",
  "request_id": "req-7f32",
  "message": "payment dependency timed out"
}
```

Structured logs make fields explicit.

This can improve:

```text
searching

filtering

aggregation

correlation
```

---

# 56. STRUCTURED DOES NOT MEAN GOOD

This is structured:

```json
{
  "message": "something went wrong"
}
```

It is still weak operational evidence.

Useful logging requires meaningful fields.

---

# 57. TIMESTAMPS

Every operationally useful log should have a trustworthy time context.

A timestamp should make clear:

```text
when the event occurred
```

Prefer unambiguous time representation.

Centralized systems commonly normalize timestamps.

---

# 58. LOG TIMESTAMP VERSUS INGESTION TIME

Distinguish:

```text
Event Time
```

from:

```text
Time Logging System Received Event
```

If telemetry is delayed, these can differ.

During incidents, event time is often what you need for causal ordering.

---

# 59. CORRELATION IDENTIFIERS

A correlation identifier helps connect related telemetry.

Example:

```text
request_id=req-7f32
```

The same identifier might appear in:

```text
frontend log

API log

payment service log
```

This helps trace a request across systems even without a full distributed tracing platform.

---

# 60. REQUEST ID

Suppose:

```text
User reports checkout failed.
```

Support identifies:

```text
request_id=req-7f32
```

Search:

```text
frontend
→ req-7f32

API
→ req-7f32

payment
→ req-7f32
```

This can reconstruct the request path.

---

# 61. TRACE ID

Distributed tracing systems commonly use a trace identifier to connect operations belonging to one trace.

Conceptually:

```text
trace_id=abc123
```

can connect spans across multiple services.

OpenTelemetry also supports correlation between telemetry signals, including logs and traces.

---

# 62. SPAN

A trace consists of spans representing units of work.

Example:

```text
Trace: checkout request

├── Span: frontend
├── Span: API
├── Span: inventory check
├── Span: payment request
└── Span: database write
```

Each span can contain timing and contextual information.

---

# 63. TRACE TIMING

Suppose total request duration is:

```text
2.5 seconds
```

Trace:

```text
API processing:
50 ms

inventory:
80 ms

database:
70 ms

payment provider:
2.2 s
```

This strongly narrows the latency investigation.

---

# 64. TRACES DO NOT REPLACE LOGS

A trace can show:

```text
payment operation took 2.2 seconds
```

A log might explain:

```text
upstream request timed out after retry
```

Metrics might show:

```text
payment latency increased across all requests
```

Signals complement one another.

---

# 65. EVENTS AND CHANGE CORRELATION

Imagine:

```text
13:55 deployment starts

14:00 deployment completes

14:03 error rate rises

14:04 latency rises

14:05 alert fires
```

That timeline makes the deployment relevant.

It still does not prove the deployment caused the incident.

Investigation continues.

---

# 66. DEPLOYMENT MARKERS

Dashboards become more useful when engineers can correlate operational signals with:

```text
deployments

configuration changes

failovers

maintenance

scaling actions
```

A graph without change context can hide important clues.

# 68. PROMETHEUS

Prometheus is widely used for metrics monitoring and alerting.

A simplified model:

```text
Application / Exporter
        ↓
Metrics Endpoint
        ↓
Prometheus
        ↓
Time-Series Storage
        ↓
PromQL
```

Prometheus commonly collects metrics by scraping configured HTTP endpoints.

---

# 69. GRAFANA

Grafana can query supported data sources and visualize telemetry through dashboards and panels.

Conceptually:

```text
Prometheus
    ↓
Grafana Data Source
    ↓
Dashboard
    ↓
Panels
```

Grafana is not itself the source of the application metrics in this model.

---

# 70. OPEN TELEMETRY

OpenTelemetry is a vendor-neutral observability framework for generating, collecting, and exporting telemetry.

At Junior level, understand:

```text
Application
    ↓
Instrumentation
    ↓
OpenTelemetry
    ↓
Collector / Export
    ↓
Observability Backend
```

Do not confuse OpenTelemetry with one particular storage or visualization product.

---

# 71. EXPORTERS

An exporter can expose metrics from a system that does not natively expose them in the format your monitoring system expects.

For host monitoring, a common Prometheus ecosystem component is:

```text
Node Exporter
```

It exposes host-level metrics.

---

# 72. NODE EXPORTER

Node Exporter can expose Linux host metrics such as:

```text
CPU

memory

filesystem

network
```

Prometheus can scrape those metrics.

Conceptually:

```text
Linux Host
    ↓
Node Exporter
    ↓
/metrics
    ↓
Prometheus
```

---

# 73. APPLICATION INSTRUMENTATION

Infrastructure metrics cannot answer every application question.

An application should expose useful service-level measurements such as:

```text
request count

error count

request duration
```

This requires instrumentation.

---

# 74. INSTRUMENTATION

Instrumentation means adding mechanisms that produce useful telemetry.

This can happen through:

```text
application libraries

framework integrations

agents

exporters

platform instrumentation
```

The implementation depends on the environment.

---

# 75. WHAT SHOULD BE MEASURED?

Start from operational questions.

For the Part 8 application:

```text
How many requests are arriving?

How many fail?

How long do requests take?

Is the process alive?

Is the application ready?
```

Then choose telemetry that answers those questions.

---

# 76. DO NOT START WITH "COLLECT EVERYTHING"

Collecting everything can create:

```text
cost

noise

high cardinality

storage pressure

query complexity

privacy risk

security exposure
```

Telemetry design should be intentional.

# 82. LAB APPLICATION

Create:

```text
app.py
```

with:

```python
import json
import logging
import os
import random
import time
import uuid

from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from prometheus_client import Counter, Histogram, generate_latest, CONTENT_TYPE_LATEST

APP_NAME = os.getenv("APP_NAME", "veriqta-observability-lab")
PORT = int(os.getenv("PORT", "8080"))

REQUESTS = Counter(
    "veriqta_http_requests_total",
    "Total HTTP requests",
    ["method", "route", "status"],
)

REQUEST_DURATION = Histogram(
    "veriqta_http_request_duration_seconds",
    "HTTP request duration in seconds",
    ["route"],
    buckets=(0.05, 0.1, 0.25, 0.5, 1.0, 2.0, 5.0),
)

logging.basicConfig(
    level=logging.INFO,
    format="%(message)s",
)

logger = logging.getLogger(APP_NAME)


def write_log(level, event, **fields):
    record = {
        "timestamp": time.strftime(
            "%Y-%m-%dT%H:%M:%SZ",
            time.gmtime()
        ),
        "level": level,
        "service": APP_NAME,
        "event": event,
        **fields,
    }

    message = json.dumps(record, separators=(",", ":"))

    if level == "ERROR":
        logger.error(message)
    elif level == "WARNING":
        logger.warning(message)
    else:
        logger.info(message)


class Handler(BaseHTTPRequestHandler):
    def log_message(self, format, *args):
        return

    def send_body(self, status, body, content_type="text/plain; charset=utf-8"):
        encoded = body.encode("utf-8")

        self.send_response(status)
        self.send_header("Content-Type", content_type)
        self.send_header("Content-Length", str(len(encoded)))
        self.end_headers()
        self.wfile.write(encoded)

    def do_GET(self):
        request_id = self.headers.get(
            "X-Request-ID",
            str(uuid.uuid4())
        )

        route = self.path.split("?", 1)[0]
        started = time.perf_counter()
        status = 500

        try:
            if route == "/":
                status = 200
                self.send_body(
                    status,
                    f"{APP_NAME} is running\n"
                )

            elif route == "/health":
                status = 200
                self.send_body(status, "healthy\n")

            elif route == "/slow":
                delay = random.uniform(1.0, 3.0)
                time.sleep(delay)

                status = 200
                self.send_body(
                    status,
                    f"slow response after {delay:.2f}s\n"
                )

            elif route == "/metrics":
                payload = generate_latest()

                self.send_response(200)
                self.send_header(
                    "Content-Type",
                    CONTENT_TYPE_LATEST
                )
                self.send_header(
                    "Content-Length",
                    str(len(payload))
                )
                self.end_headers()
                self.wfile.write(payload)
                return

            else:
                status = 404
                self.send_body(status, "not found\n")

        except Exception as exc:
            status = 500

            write_log(
                "ERROR",
                "request_failed",
                request_id=request_id,
                route=route,
                error=type(exc).__name__,
            )

            try:
                self.send_body(500, "internal server error\n")
            except Exception:
                pass

        finally:
            if route != "/metrics":
                duration = time.perf_counter() - started

                REQUESTS.labels(
                    method="GET",
                    route=route,
                    status=str(status),
                ).inc()

                REQUEST_DURATION.labels(
                    route=route
                ).observe(duration)

                write_log(
                    "INFO",
                    "request_completed",
                    request_id=request_id,
                    method="GET",
                    route=route,
                    status=status,
                    duration_seconds=round(duration, 6),
                )


server = ThreadingHTTPServer(("127.0.0.1", PORT), Handler)

write_log(
    "INFO",
    "application_started",
    host="127.0.0.1",
    port=PORT,
)

try:
    server.serve_forever()
except KeyboardInterrupt:
    write_log(
        "INFO",
        "application_stopping",
    )
finally:
    server.server_close()
```

# 112. HISTOGRAM QUERY

A Prometheus histogram exposes bucket series.

For this lab, approximate p95 latency can be queried with:

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(
      veriqta_http_request_duration_seconds_bucket[5m]
    )
  )
)
```

This uses histogram buckets to estimate the 95th percentile.

---

# 113. LATENCY BY ROUTE

To preserve the route dimension:

```promql
histogram_quantile(
  0.95,
  sum by (le, route) (
    rate(
      veriqta_http_request_duration_seconds_bucket[5m]
    )
  )
)
```

Now compare:

```text
/

/health

/slow
```

The `/slow` route should show substantially higher latency after enough slow requests.

# 120. CPU QUERY CONCEPT

Node Exporter exposes cumulative CPU time broken down by mode.

A common Prometheus approach estimates busy CPU by deriving a rate from non-idle CPU time.

For a simple lab:

```promql
100 * (
  1 -
  avg by (instance) (
    rate(node_cpu_seconds_total{mode="idle"}[5m])
  )
)
```

Interpret this as an estimate of CPU busy percentage over the query window.

---

# 121. MEMORY QUERY CONCEPT

A useful Linux memory-availability ratio can be calculated from:

```text
MemAvailable

MemTotal
```

For example:

```promql
100 * (
  1 -
  (
    node_memory_MemAvailable_bytes
    /
    node_memory_MemTotal_bytes
  )
)
```

This estimates percentage of memory not currently available.

Do not equate this mechanically with application memory pressure.

---

# 122. FILESYSTEM UTILIZATION QUERY

A common filesystem capacity calculation is:

```promql
100 * (
  1 -
  (
    node_filesystem_avail_bytes
    /
    node_filesystem_size_bytes
  )
)
```

Real dashboards normally filter filesystems and mount types carefully.

Do not blindly average every filesystem.

---

# 123. NETWORK TRAFFIC QUERY

Receive rate can be examined with:

```promql
rate(node_network_receive_bytes_total[5m])
```

Transmit rate:

```promql
rate(node_network_transmit_bytes_total[5m])
```

Filter or group by interface as appropriate.

Loopback and virtual interfaces can distort naive interpretation.

# 156. THRESHOLD

A threshold defines a condition such as:

```text
p95 latency > 1 second
```

or:

```text

```

Do not copy arbitrary thresholds from tutorials into production.

# 157. THRESHOLD WITHOUT DURATION

Suppose CPU briefly reaches:

```text
95%
```

for two seconds during startup.

Should someone be paged?

Probably not solely because of that observation.

Alert rules often include persistence/time considerations to avoid reacting to harmless brief spikes.

---

# 158. ALERT PERSISTENCE

Conceptually:

```text
Condition becomes true
        ↓
Remains true for meaningful period
        ↓
Alert fires
```

This can reduce noise from transient behavior.

Exact duration must match the service.

```text

```

```text
Users cannot checkout.
```

but alerting remains silent.

This is also dangerous.

Alert design balances sensitivity, specificity, and operational usefulness.

# 169. SIMPLE ALERT LAB

For the training environment, create a simple latency alert.

Example condition:

```text

```

for a short lab-appropriate period.

The threshold is intentionally chosen so `/slow` traffic can trigger it.

It is not a production recommendation.

---

# 170. PROMETHEUS ALERT RULE EXAMPLE

A training rule can resemble:

```yaml
groups:
  - name: veriqta-junior-lab
    rules:
      - alert: VeriqtaApplicationHighLatency
        expr: |
          histogram_quantile(
            0.95,
            sum by (le) (
              rate(
                veriqta_http_request_duration_seconds_bucket[2m]
              )
            )
          ) > 1
        for: 1m
        labels:
          severity: warning
        annotations:
          summary: "VERIQTA lab application latency is high"
          description: "Lab p95 request latency has exceeded 1 second."
```

These values are designed only for a short training exercise.
