# PART 9: CLOUD COMPUTING FUNDAMENTALS

## Goal

Understand the core cloud abstractions used by DevOps teams without becoming dependent on a single provider's console.

The objective is not to memorize where buttons are located in AWS, Microsoft Azure, Google Cloud, or another provider.

Interfaces change.

Service names change.

Defaults change.

New services appear.

The underlying engineering questions remain much more stable:

```text
Where will this workload run?

Which failure domain contains it?

Which network contains it?

Which subnet contains it?

How does traffic reach it?

Which identity created or operates it?

What permissions does that identity have?

Where is persistent data stored?

Which security controls apply?

What does the provider manage?

What does the customer manage?

What will the resource cost?

How will we identify, observe, change, and eventually remove it?
```

The learner should develop a portable mental model:

```text
Cloud Organization / Tenant
        ↓
Account / Project / Subscription
        ↓
Region
        ↓
Virtual Network
        ↓
Subnet
        ↓
Compute / Managed Service
        ↓
Identity + Security Controls
        ↓
Storage / Database / Dependencies
        ↓
Load Balancer / Endpoint
        ↓
Application
        ↓
Users
```

The most important principle in this Part is:

> A cloud console is an interface to resources. It is not the architecture.

---

# 1. WHAT CLOUD COMPUTING ACTUALLY CHANGES

Before public cloud platforms became common, an organization that needed infrastructure might have needed to:

```text
purchase servers

wait for delivery

rack hardware

provide power

provide cooling

configure physical networking

install operating systems

configure storage

replace failed hardware

maintain datacenter facilities
```

Cloud computing changes the consumption model.

Infrastructure capabilities can be requested through software interfaces.

For example:

```text
Need compute
        ↓
Request virtual machine
        ↓
Provider allocates infrastructure
        ↓
Instance becomes available
```

Or:

```text
Need database
        ↓
Request managed database
        ↓
Provider provisions service
        ↓
Application receives database endpoint
```

The engineer increasingly interacts with infrastructure through:

```text
web console

CLI

API

SDK

Infrastructure as Code
```

---

# 2. CLOUD IS NOT "SOMEONE ELSE'S COMPUTER"

That phrase is occasionally useful as a joke, but it is technically incomplete.

Cloud platforms provide abstractions around:

```text
compute

networking

storage

identity

databases

security

observability

automation

messaging

DNS

load balancing

serverless execution

managed platforms
```

The important engineering shift is:

```text
Infrastructure
        ↓
Programmable Resource
```

A server is no longer only a physical object.

It may be an API-created resource with:

```text
resource ID

region

zone

network

subnet

security policy

identity

tags

attached storage

lifecycle state
```

---

# 3. CLOUD RESOURCES HAVE STATE

When you request a resource, it normally progresses through provider-defined lifecycle states.

Conceptually:

```text
Requested
    ↓
Provisioning
    ↓
Available / Running
    ↓
Stopping
    ↓
Stopped
    ↓
Deleting
    ↓
Deleted
```

Exact state names vary by provider and resource type.

Never assume:

```text
API request accepted
=
resource ready
```

Provisioning is often asynchronous.

---

# 4. CLOUD CONTROL PLANE

The control plane is the set of APIs and management systems used to create, modify, inspect, and delete cloud resources.

For example:

```text
Engineer
   ↓
CLI / Console / IaC
   ↓
Cloud API
   ↓
Control Plane
   ↓
Create VM
```

Operations such as these generally involve the control plane:

```text
create instance

delete instance

change firewall rule

create subnet

attach storage

modify permissions
```

---

# 5. DATA PLANE

The data plane is where workload traffic and service operations occur.

For example:

```text
User
 ↓
Load Balancer
 ↓
Application
 ↓
Database
```

That request path is different from:

```text
Engineer
 ↓
Cloud API
 ↓
Change load balancer configuration
```

A useful distinction is:

```text
Control Plane
=
Manage Resources

Data Plane
=
Use Resources / Carry Workload Traffic
```

The terminology varies somewhat by service, but the distinction is extremely useful.

---

# 6. CONTROL-PLANE SUCCESS DOES NOT PROVE WORKLOAD SUCCESS

Suppose the provider API reports:

```text
Virtual machine creation succeeded.
```

That does not prove:

```text
SSH works

application started

firewall allows traffic

DNS is correct

HTTP works

database works
```

It proves that the requested infrastructure resource reached whatever state the provider defines as successful creation.

This repeats the Part 8 principle:

```text
Infrastructure Created
≠
Application Healthy
```

# 7. THE PROVIDER-PORTABLE MODEL

Throughout this Part, think in concepts first.

| Concept | AWS example | Azure example | Google Cloud example |
|---|---|---|---|
| Administrative boundary | Account | Subscription | Project |
| Geographic location | Region | Region | Region |
| Failure/location subdivision | Availability Zone | Availability Zone | Zone |
| Virtual network | VPC | Virtual Network | VPC network |
| Compute VM | EC2 instance | Azure Virtual Machine | Compute Engine VM |
| Object storage | S3 | Blob Storage | Cloud Storage |
| Managed relational database | RDS family | Azure SQL / managed database services | Cloud SQL |
| Traffic distribution | Elastic Load Balancing | Azure Load Balancer / Application Gateway | Cloud Load Balancing |
| Identity/access | IAM | Microsoft Entra ID + Azure RBAC | Cloud IAM |
| Resource metadata | Tags | Tags | Labels / tags depending on resource and purpose |

These examples are orientation aids.

They are not claims that every service has an exact one-to-one equivalent.

# 8. DO NOT LEARN CLOUD AS A PRODUCT DICTIONARY

Weak learning:

```text
AWS has EC2.

Azure has Virtual Machines.

Google Cloud has Compute Engine.
```

Better learning:

```text
I need compute capacity.

What execution abstraction does this provider offer?

What is its lifecycle?

Where does it run?

How is it networked?

How is it authenticated?

How is it secured?

How is it billed?

What survives when it stops?

What disappears when it is deleted?
```

That reasoning transfers between providers.

---

# 9. REGIONS

A region is a geographic cloud location containing provider infrastructure.

Examples might represent locations in:

```text
North America

Europe

Asia

Africa

Middle East

South America

Australia
```

Provider terminology and exact geographic structure differ.

AWS describes a Region as a separate geographic area and Availability Zones as isolated locations within a Region. Google Cloud similarly organizes infrastructure into regions and zones.

---

# 10. WHY REGION SELECTION MATTERS

Region choice can affect:

```text
latency

service availability

cost

capacity

regulatory requirements

data residency

disaster recovery

network architecture

operational complexity
```

Therefore:

```text
Choose nearest region
```

is not a complete architecture rule.

---

# 11. LATENCY AND REGION

Suppose users are primarily in one geographic area.

Placing an application far away may increase network latency.

But geography is only one factor.

Actual user performance can also depend on:

```text
network path

CDN

application architecture

database placement

dependency placement

caching

request count

payload size
```

Region selection is an architectural decision, not a guarantee of performance.

---

# 12. SERVICE AVAILABILITY DIFFERS BY REGION

Not every cloud service, feature, instance type, or capability is necessarily available in every region.

Before designing around a service, verify:

```text
Does the region support it?

Does the required feature exist there?

Does the required capacity exist?

Are there quota restrictions?

Are availability zones supported as expected?
```

Azure explicitly notes that service support for availability zones can vary even when the region itself provides zones.

---

# 13. REGION IS ALSO AN OPERATIONAL SCOPE

Many cloud resources are regional.

This creates a common troubleshooting failure:

```text
Engineer opens console.

Resource appears missing.

Engineer assumes resource was deleted.
```

Actual cause:

```text
Wrong region selected.
```

AWS documentation explicitly notes that regional resources are tied to the Region where they are created and that resource views depend on the selected Region.

Always ask:

```text
Which account?

Which region?

Which resource?
```

before concluding something is missing.

---

# 14. AVAILABILITY ZONES

An availability zone is a location or failure-domain concept inside a region.

Conceptually:

```text
Region
 ├── Zone A
 ├── Zone B
 └── Zone C
```

The physical implementation varies by provider.

Do not assume every provider defines zones identically.

AWS describes Availability Zones as independent locations within a Region. Azure describes them as separated groups of datacenters with independent power, cooling, and networking infrastructure. Google Cloud uses zones as subdivisions of regions.

---

# 15. WHY ZONES EXIST

Consider:

```text
Application
    ↓
Single VM
    ↓
Single Zone
```

If that zone becomes unavailable, the workload may become unavailable.

A more resilient architecture might use:

```text
              Load Balancer
               /        \
              /          \
         Zone A          Zone B
           ↓               ↓
        App VM          App VM
```

But merely deploying two resources does not automatically create resilience.

You must also consider:

```text
traffic distribution

application state

database placement

storage dependencies

health checks

capacity

failover behavior
```

---

# 16. MULTI-ZONE DOES NOT MEAN MULTI-REGION

These are different:

```text
Region A
 ├── Zone 1
 └── Zone 2
```

versus:

```text
Region A
     +
Region B
```

A multi-zone design addresses a different failure scope from a multi-region design.

Later Parts will go much deeper into availability and disaster recovery.

---

# 17. FAILURE DOMAINS

A failure domain is a boundary within which a failure may affect multiple resources.

Examples can include:

```text
process

host

rack

zone

region

provider service

network dependency
```

Cloud architecture requires asking:

> Which resources can fail together?

A system with ten VMs in one failure domain is not necessarily more resilient than a system with fewer resources distributed appropriately.

# 19. ORGANIZATIONAL HIERARCHY

Larger cloud environments may contain higher-level structures.

Conceptually:

```text

        ↓
```

```text

```

---

# 20. WHY SEPARATE ENVIRONMENTS

Suppose:

```text
Development
Production
```

share the same unrestricted administrative boundary.

A developer experimenting with networking or permissions could accidentally affect production.

Separation can reduce blast radius.

Conceptually:

```text
Organization
 ├── Production Boundary
 ├── Staging Boundary
 └── Development Boundary
```

The exact design belongs to later architecture material.

At Junior level, recognize the boundary before changing resources.

Before executing a cloud command, determine:

```text

Which account/project/subscription?

Which environment?
```

This is the cloud equivalent of checking:

```text

```

# 22. THE CLOUD CHANGE CONTEXT MODEL

Use:

```text

   ↓

   ↓

   ↓

```

A command can be syntactically correct and still be operationally wrong because the context is wrong.

---

# 23. IDENTITY

Cloud platforms need to know:

```text
Who or what is making this request?
```

An identity may represent:

```text
human user

application

virtual machine

automation system

CI/CD pipeline

managed workload
```

The exact identity mechanisms differ by provider.

---

# 24. AUTHENTICATION

Authentication answers:

```text
Who are you?
```

Examples may involve:

```text
interactive login

federated identity

short-lived credentials

tokens

certificates

keys
```

Do not reduce cloud authentication to:

```text
access key + secret key
```

Modern cloud environments commonly support and prefer stronger identity patterns appropriate to the workload.

---

# 25. AUTHORIZATION

Authorization answers:

```text
What are you allowed to do?
```

For example:

```text
Identity authenticated successfully.
```

but:

```text
Create VM
→ Denied
```

This is not necessarily an authentication failure.

The identity may be valid but insufficiently authorized.

---

# 26. AUTHENTICATION VERSUS AUTHORIZATION

Memorize:

```text
Authentication
=
Who are you?

Authorization
=
What may you do?
```

Example:

```text
Login succeeds
+
Delete resource denied
```

Likely direction:

```text
Authorization
```

not:

```text
Authentication
```

---

# 27. LEAST PRIVILEGE

An identity should receive only the permissions required for its legitimate function.

Avoid:

```text
Give administrator access because it works.
```

Instead ask:

```text
What exact actions are required?

On which resources?

Under which conditions?

For how long?
```

Least privilege reduces blast radius.

---

# 28. HUMAN IDENTITY VERSUS WORKLOAD IDENTITY

A person and an application should not automatically share credentials.

Conceptually:

```text
Engineer Identity
      ↓
Cloud Management

Application Identity
      ↓
Application Dependency Access
```

For example, an application that needs object storage should ideally receive an appropriate workload identity rather than a developer's personal credentials.

---

# 29. LONG-LIVED CREDENTIALS

Long-lived credentials create operational and security risks.

Risks include:

```text
leakage

accidental Git commit

copying between systems

poor rotation

unknown ownership

continued access after no longer required
```

Where supported and appropriate, prefer mechanisms using managed identities, roles, federation, or short-lived credentials.

Specific implementation depends on the provider.

---

# 30. NEVER COMMIT CLOUD CREDENTIALS

Do not place credentials in:

```text
Git repositories

shell scripts

README files

container images

screenshots

AI prompts

public issue trackers
```

If a credential is exposed, follow the provider and organizational incident process.

Deleting the visible text from Git later does not automatically make an exposed credential safe.

Examples:


---

# 32. VIRTUAL NETWORK IS A LOGICAL NETWORK BOUNDARY

A virtual network provides an address and connectivity structure for resources.

It may participate in defining:

```text
IP addressing

subnets

routes

security controls

connectivity

service endpoints
```

It does not mean:

```text
everything inside can automatically communicate with everything else
```

Security and routing still matter.

---

# 33. CIDR RETURNS

Part 5 introduced IP addressing and subnet concepts.

Cloud networks frequently require CIDR ranges.

Example:

```text
10.20.0.0/16
```

A subnet might use:

```text
10.20.1.0/24
```

Conceptually:

```text
Virtual Network
10.20.0.0/16
       ↓
Subnet
10.20.1.0/24
```

Do not choose ranges randomly in production.

They can affect future connectivity.

---

# 34. OVERLAPPING NETWORKS

Suppose:

```text
Network A
10.0.0.0/16
```

and:

```text
Network B
10.0.0.0/16
```

Later you need to connect them.

Overlapping address spaces can create routing problems because the same destination range represents resources in both networks.

Address planning matters.

---

# 35. SUBNETS

A subnet divides a larger network address space.

Conceptually:

```text
VPC / VNet
10.20.0.0/16
   │
   ├── Subnet A
   │   10.20.1.0/24
   │
   ├── Subnet B
   │   10.20.2.0/24
   │
   └── Subnet C
       10.20.3.0/24
```

Subnets may help organize workloads by:

```text
zone

application tier

security requirement

routing behavior

environment
```

---

# 36. SUBNETS AND ZONES

The relationship between subnets and availability zones is provider-specific.

Do not assume a subnet has identical scope across AWS, Azure, and Google Cloud.

For example, AWS subnets are associated with a single Availability Zone.

Other providers have different network resource models.

Portable engineering requires understanding the provider's actual scope rather than transferring assumptions blindly.

---

# 37. "PUBLIC SUBNET" AND "PRIVATE SUBNET"

These terms are widely used, but their exact meaning should be established through routing and exposure rather than merely through a name.

A subnet named:

```text
private-subnet
```

is not private because of its name.

A subnet named:

```text
public
```

is not automatically internet-accessible.

Inspect actual:

```text
routes

public addressing

gateways

firewall/security rules

resource configuration
```

---

# 38. ROUTING IN CLOUD NETWORKS

Cloud virtual networks use routing concepts from Part 5.

Mental model:

```text
Source Resource
      ↓
Destination IP
      ↓
Route Selection
      ↓
Next Hop / Network Path
      ↓
Destination
```

Cloud platforms may automatically create certain routes and allow custom routes.

Exact behavior varies.

---

# 39. INTERNET ACCESS IS NOT ONE SETTING

A VM may need several things for internet connectivity.

Depending on architecture:

```text
valid IP configuration

route

internet gateway or equivalent path

NAT or public address where appropriate

security rule

operating-system firewall

working DNS
```

Therefore:

```text
Has public IP
≠
Internet connectivity guaranteed
```

---

# 40. INBOUND VERSUS OUTBOUND CONNECTIVITY

These are separate questions.

```text
Can the internet initiate a connection to the VM?
```

is different from:

```text
Can the VM initiate a connection to the internet?
```

A private workload may need outbound access for:

```text
package repositories

external APIs

updates
```

without accepting arbitrary inbound internet connections.

---

# 41. PUBLIC IP ADDRESS

A public IP can provide internet-routable addressing for a resource or endpoint, depending on provider architecture.

But:

```text
Public IP
≠
Open to every port
```

Security controls still matter.

Likewise:

```text
Security rule allows port
≠
Application is listening
```

Layered reasoning remains necessary.

---

# 42. PRIVATE IP ADDRESS

Resources commonly receive private addresses inside virtual networks.

Example:

```text
10.20.1.15
```

Private addressing is used for internal communication.

A private address does not automatically mean:

```text
secure

unreachable from all external networks

correctly segmented
```

Connectivity can exist through:

```text
VPN

peering

private links

transit networks

proxies

other connected networks
```

# 49. VM RUNNING DOES NOT MEAN APPLICATION RUNNING

This is critical.

```text
VM Running
≠
Operating System Fully Ready
≠
SSH Available
≠
Application Running
≠
Port Listening
≠
Application Healthy
```

Every layer requires appropriate evidence.

---

# 50. STOP VERSUS DELETE

Stopping and deleting are not the same operation.

Conceptually:

```text
Stop
→ Resource may continue to exist.

Delete
→ Resource is removed.
```

But billing and persistence behavior vary by resource.

A stopped VM may still have billable attached resources such as:

```text
persistent disks

reserved/static IP addresses

snapshots

other services
```

Never assume:

```text
VM stopped
=
billing stopped completely
```

---

# 51. EPHEMERAL AND PERSISTENT DATA

Some storage is tied closely to compute lifecycle.

Other storage exists independently.

Ask:

```text
If this VM disappears, what data survives?
```

Do not discover the answer during an incident.

# 52. STORAGE

Foundational categories include:

```text

```

# 54. OBJECT STORAGE

Object storage stores objects in provider-managed storage services.

Conceptually:

```text
Bucket / Container
       ↓
Object Key
       ↓
Object Data + Metadata
```

Typical uses:

```text
artifacts

images

static assets

```

```text

```

---

# 55. FILE STORAGE

Managed file storage can provide shared filesystem-style access.

Potential uses include workloads requiring:

```text
shared directories

filesystem semantics

multiple clients
```

The exact protocol and service depend on provider and architecture.

---

# 56. STORAGE DURABILITY VERSUS AVAILABILITY

These are different.

Durability asks approximately:

```text
How likely is stored data to remain intact?
```

Availability asks approximately:

```text
Can I access it when needed?
```

A system can have highly durable data while experiencing temporary access disruption.

Do not treat the terms as interchangeable.

---

# 57. SNAPSHOTS ARE NOT A COMPLETE BACKUP STRATEGY

Snapshots can be useful.

But:

```text
Snapshot Exists
≠
Recovery Strategy Proven
```

Questions include:

```text
Can it be restored?

How long does restoration take?

Does it contain consistent data?

Is it protected from accidental deletion?

Is it in the required failure domain?

Has recovery been tested?
```

Backup and disaster recovery receive deeper treatment later.

# 67. SECURITY CONTROLS

Cloud networking commonly includes provider-managed traffic-control mechanisms.

Examples may be called:

```text

```

depending on provider.

They determine whether traffic matching defined conditions is permitted or denied.

---

# 68. CLOUD SECURITY RULE MENTAL MODEL

A simplified rule may consider:

```text
direction

protocol

source

destination

port

action
```

For example:

```text
Inbound

TCP

Source: trusted admin IP range

Destination: application VM

Port: 22

Action: allow
```

Exact rule models vary.

---

# 69. SECURITY RULES ARE NOT APPLICATION LISTENERS

Suppose a cloud firewall permits:

```text
TCP 8080
```

but:

```bash
ss -lnt
```

shows no listener on 8080.

The application remains unreachable.

Mental model:

```text
Cloud Rule Allows Traffic
        ↓
Traffic Reaches Host
        ↓
Expected Listener?
        ↓
No
        ↓
Connection Still Fails
```

---

# 70. APPLICATION LISTENER IS NOT ENOUGH EITHER

Suppose:

```text
0.0.0.0:8080
```

is listening.

But cloud security rules deny inbound TCP 8080.

Remote access fails.

Therefore:

```text
Listener
+
Network Path
+
Security Permission
```

are all required.

---

# 71. SECURITY LAYERS

Traffic may encounter multiple controls:

```text
Cloud Network Rule
        ↓
Subnet / Network Control
        ↓
Host Firewall
        ↓
Application Listener
        ↓
Application Authentication
```

Do not assume one allowed rule overrides all other layers.

---

# 72. DO NOT OPEN EVERYTHING TO FIX CONNECTIVITY

A dangerous troubleshooting pattern is:

```text
Connection failed.
        ↓
Allow all inbound traffic from everywhere.
```

This removes evidence and increases exposure.

Instead identify:

```text
required source

required destination

required protocol

required port
```

Then configure the smallest justified access.

# 83. PAAS


# 84. SAAS

Software as a Service provides a complete application consumed by users.

The provider manages much more of the application stack.

But customers still retain responsibilities around areas such as:

```text

identity

access

configuration
```

depending on the service and contract.

Azure's current shared-responsibility guidance explicitly shows responsibility shifting as you move from on-premises to IaaS, PaaS, and SaaS, while responsibilities such as customer data, identities, and access remain important customer concerns.

---

# 85. SHARED RESPONSIBILITY

Cloud security and operations are shared between provider and customer.

A useful simplified model:

```text
Provider
    ↓
Underlying Cloud Infrastructure

Customer
    ↓
What Customer Configures, Deploys, Stores, and Permits
```

The exact boundary changes with service type.

AWS describes this as responsibility for security "of" the cloud versus security "in" the cloud. Google Cloud similarly describes the provider as protecting underlying infrastructure while customers retain responsibility for what they bring to the cloud.

---

# 86. SHARED RESPONSIBILITY IS SERVICE-SPECIFIC



```text

```

# 188. ROOT CAUSE STATEMENT

Weak:

```text

```

Better:

```text
The VM and application process were running, and the health
endpoint returned HTTP 200 locally. However, the application
was bound only to the loopback address 127.0.0.1:8080.
Remote clients therefore could not connect to the application
through the VM's network interface.
```

This is precise.

# 221. OFFICIAL REFERENCES FOR CONTINUED STUDY

Because cloud services, regional availability, defaults, pricing, and interfaces change, provider documentation should be treated as the authoritative source for provider-specific behavior.

AWS documents Regions as separate geographic areas and Availability Zones as independent locations within Regions.

Microsoft documents Azure Availability Zones as separated groups of datacenters within supported regions and notes that zone support can differ by service and region.

Google Cloud documents its infrastructure location model in terms of regions and zones and recommends choosing locations according to requirements such as latency, availability, and durability.

For shared responsibility, AWS, Microsoft, and Google Cloud all document a division of responsibility between provider and customer, with the exact boundary depending on the service model and service being consumed.

The practical rule for this repository is:

```text
Learn the portable concept here.

Verify provider-specific implementation in current official documentation.

Never invent provider behavior from memory.
```
