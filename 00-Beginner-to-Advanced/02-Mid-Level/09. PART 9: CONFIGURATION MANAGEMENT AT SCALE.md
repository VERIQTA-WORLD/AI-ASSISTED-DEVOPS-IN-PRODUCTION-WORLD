# PART 9: CONFIGURATION MANAGEMENT AT SCALE

## Goal

Manage repeatable operating-system and application configuration across multiple systems using Ansible as the practical implementation.

Part 8 established how infrastructure changes move safely through source control, validation, planning, approval, execution, and verification.

Terraform can create infrastructure.

It does not automatically answer every question about what happens **inside** the operating systems running on that infrastructure.

After compute instances exist, engineers may still need to manage:

- operating-system packages
- users and groups
- directories
- file permissions
- application configuration
- service definitions
- service state
- monitoring agents
- logging configuration
- security settings
- scheduled tasks
- trusted certificates
- application runtime dependencies

Configuration management addresses this layer.

The central mental model is:

```text
Desired Configuration
↓
Actual Configuration
↓
Difference
↓
Reconciliation
↓
Verification
```

At small scale, an engineer might manually configure one server.

At production scale, that approach creates inconsistency.

The objective is not:

```text
Run commands on many servers.
```

The objective is:

```text
Define desired configuration
↓
Apply it predictably
↓
Detect differences
↓
Reconcile safely
↓
Verify convergence
```

By the end of this Part, you should be able to structure configuration management beyond a single monolithic playbook and operate reusable Ansible automation across multiple systems safely.

---

# 1. THE CONFIGURATION MANAGEMENT PROBLEM

Imagine three application servers:

```text
app01
app02
app03
```

They are intended to be identical.

Initially:

```text
app01 → application version 4
app02 → application version 4
app03 → application version 4
```

Over time, manual changes occur.

Later:

```text
app01
├── correct package version
├── correct application configuration
└── monitoring enabled

app02
├── newer package installed manually
├── old application configuration
└── monitoring enabled

app03
├── correct package version
├── manually modified configuration
└── monitoring disabled
```

The servers now differ.

This is **configuration drift**.

---

# 2. WHY MANUAL CONFIGURATION FAILS AT SCALE

Manual administration can work for a small number of temporary systems.

It becomes increasingly unreliable as system count and change frequency increase.

Consider:

```text
3 servers
×
20 configuration settings
=
60 configuration decisions
```

Now consider:

```text
200 servers
×
20 configuration settings
=
4,000 configuration decisions
```

Then add:

- multiple environments
- multiple operating systems
- multiple application versions
- security requirements
- different regions
- different teams
- emergency changes
- staff turnover
- repeated deployments

Human memory is not a configuration-management system.

---

# 3. WHAT CONFIGURATION MANAGEMENT PROVIDES

Configuration management allows engineers to describe expected machine state.

For example:

```text
User:
veriqta

Package:
nginx installed

Configuration:
managed configuration present

Service:
running

Boot:
service enabled

Monitoring:
agent installed and running
```

Ansible then compares the requested operation with the target system and, where the relevant module supports that behavior, changes what is necessary.

The desired result is:

```text
Declared Intent
↓
Controlled Execution
↓
Target State
↓
Verification
```

---

# 4. CONFIGURATION MANAGEMENT IS NOT REMOTE SHELL

This distinction is fundamental.

Remote shell thinking:

```text
SSH into server
↓
Run command
↓
Command succeeds
↓
Done
```

Configuration-management thinking:

```text
What state should exist?
↓
What state exists now?
↓
What difference matters?
↓
What controlled action reconciles it?
↓
How do we verify the final state?
```

Ansible can execute shell commands.

That does not mean shell commands should be the default implementation.

Prefer modules that understand the resource being managed when appropriate.

For example, managing a service through a service-management module generally provides better state semantics than repeatedly executing:

```bash
systemctl start example
```

through a generic shell task.

---

# 5. DECLARATIVE INTENT AND PROCEDURAL STEPS

Configuration management contains both declarative and procedural characteristics.

A task such as:

```yaml
- name: Ensure application service is running
  ansible.builtin.service:
    name: example-app
    state: started
```

expresses desired state:

```text
example-app should be running.
```

A raw command such as:

```yaml
- name: Run custom migration
  ansible.builtin.command:
    cmd: /opt/example/bin/migrate
```

expresses an action:

```text
Run this command.
```

Both may be necessary.

But they have different operational properties.

The first naturally describes state.

The second requires additional reasoning:

```text
Has this already run?

Can it run twice?

How do we detect success?

What happens after partial failure?

What does "changed" mean?

How is rollback handled?
```

---

# 6. ANSIBLE ARCHITECTURE

A simplified Ansible execution model is:

```text
Control Node
│
├── Inventory
├── Playbooks
├── Roles
├── Variables
├── Templates
└── Secrets
     │
     ▼
Connection
     │
     ▼
Managed Nodes
```

The control node runs Ansible.

Managed nodes are the systems being configured.

For common Linux management, Ansible frequently connects over SSH.

The exact connection mechanism can differ by platform and plugin.

---

# 7. THE CONTROL NODE

The control node contains the automation context.

This may include:

```text
Ansible

Repository

Inventory

Playbooks

Roles

Collections

Configuration

Credentials

Secret Retrieval Mechanism
```

The control node is therefore security-sensitive.

Compromising it may provide a path to many managed systems.

At scale, configuration-management security must include the execution environment itself.

---

# 8. MANAGED NODES

A managed node is a target system against which Ansible performs operations.

Examples:

```text
Application Server

Database Host

Monitoring Server

Proxy

Build Worker

Utility Host
```

Not every system should necessarily be managed by the same Ansible repository or identity.

Ownership boundaries still matter.

---

# 9. INVENTORY

Inventory answers:

```text
What systems exist from Ansible's perspective?
```

But production inventory should communicate more than a list of IP addresses.

It can model:

```text
Hosts

Groups

Environment

Function

Location

Connection Information

Selected Configuration Differences
```

Inventory design is an architecture decision.

---

# 10. BASIC INVENTORY

A simple YAML inventory might conceptually resemble:

```yaml
all:
  children:
    application:
      hosts:
        app01.example.internal:
        app02.example.internal:

    monitoring:
      hosts:
        mon01.example.internal:
```

This establishes groups.

It does not yet establish a scalable production model.

---

# 11. THE `all` GROUP

Ansible inventory includes the concept of all managed hosts.

Values genuinely common to the entire inventory may be associated with the `all` scope.

Examples might include:

```text
Organization-wide defaults

Common DNS configuration

Common monitoring endpoint

Common time configuration
```

But do not put a value in `all` merely because it is convenient.

Ask:

```text
Does every host actually share this configuration?
```

---

# 12. GROUPS

Groups allow hosts with shared characteristics to be managed together.

Possible group dimensions include:

```text
Role

Environment

Region

Operating System Family

Application

Security Boundary
```

For example:

```text
production

staging

web

application

monitoring
```

A host can belong to multiple groups.

That is powerful.

It also introduces variable-resolution complexity.

---

# 13. GROUP BY MEANINGFUL OPERATIONAL CHARACTERISTICS

A useful inventory might represent:

```text
all
├── development
├── staging
└── production

production
├── web
├── application
└── monitoring
```

But real inventory structure depends on the infrastructure.

Do not create dozens of groups without clear ownership or configuration purpose.

Every group should answer:

```text
Why does this grouping matter?
```

---

# 14. ENVIRONMENT GROUPING

Development and production often need different values.

For example:

```text
Development
├── lower worker count
├── development endpoint
└── shorter retention

Production
├── larger worker count
├── production endpoint
└── longer retention
```

The same role can use different environment data without duplicating all of its tasks.

---

# 15. FUNCTIONAL GROUPING

Systems may also be grouped by function.

Example:

```text
web
application
monitoring
```

Then a production application host might effectively receive configuration from both:

```text
production
+
application
```

This is useful, but variable collisions must be understood.

---

# 16. INVENTORY IS NOT CMDB MAGIC

Inventory only contains what its source provides.

Do not assume:

```text
Host appears in Ansible inventory
=
All metadata about the host is correct.
```

Inventory can itself become stale.

At scale, inventory lifecycle matters:

```text
Infrastructure Created
↓
Inventory Updated
↓
Configuration Applied
↓
Infrastructure Removed
↓
Inventory Reconciled
```

---

# 17. STATIC INVENTORY

Static inventory is explicitly maintained.

Advantages:

- simple
- easy to inspect
- easy to version-control when appropriate
- predictable for smaller environments

Risks:

- stale hosts
- missing new systems
- incorrect addresses
- manual synchronization

---

# 18. DYNAMIC INVENTORY

Dynamic inventory can obtain systems from another source.

Possible sources include:

```text
Cloud APIs

Virtualization Platforms

Asset Systems

Infrastructure Platforms
```

Conceptually:

```text
Infrastructure Source
↓
Inventory Plugin
↓
Ansible Inventory
```

This can reduce manual host-list maintenance.

It does not eliminate inventory design.

You still need meaningful grouping, variables, ownership, and filtering.

---

# 19. INVENTORY AS A TRUST BOUNDARY

Before executing:

```bash
ansible-playbook -i inventory/production site.yml
```

you should know what hosts the inventory resolves.

A production-safe habit is to inspect the target set before making changes.

For example:

```bash
ansible-playbook -i inventory/production site.yml --list-hosts
```

Expected result:

```text
Only the intended production hosts appear.
```

If an unexpected host appears:

```text
STOP.
```

Do not continue and hope the playbook ignores it.

---

# 20. INSPECTING COMPILED INVENTORY

Ansible provides inventory-inspection tooling.

A useful command is:

```bash
ansible-inventory -i inventory/production --graph
```

This helps inspect group relationships.

Another useful form is:

```bash
ansible-inventory -i inventory/production --list
```

The output can be large.

Use it when investigating inventory composition and effective data.

---

# 21. HOST PATTERNS

Playbooks target hosts using inventory patterns.

Example:

```yaml
- name: Configure application systems
  hosts: application
```

The pattern is an operational boundary.

A mistake here can increase blast radius dramatically.

Compare:

```text
application
```

with:

```text
all
```

One word can change the target population.

---

# 22. LIMITING EXECUTION

During controlled troubleshooting or rollout, execution can be restricted.

For example:

```bash
ansible-playbook -i inventory/production site.yml --limit app01.example.internal
```

This does not redesign the playbook.

It narrows the selected hosts for that run.

Use targeting deliberately.

---

# 23. VERIFY BEFORE MODIFY

A safe production sequence is:

```text
Select Inventory
↓
Inspect Hosts
↓
Inspect Variables
↓
Check Connectivity
↓
Preview Where Reliable
↓
Limit Initial Execution
↓
Apply
↓
Verify
↓
Expand
```

Do not begin with:

```text
Run against all production.
```

---

# 24. VARIABLES

Variables allow reusable automation to adapt to different hosts and environments.

Without variables:

```yaml
worker_count: 4
```

might be embedded everywhere.

With variables, role logic can consume a defined interface.

Conceptually:

```text
Role Logic
+
Environment Data
=
Rendered Configuration
```

---

# 25. VARIABLE DESIGN

Good variables describe meaningful configuration.

Examples:

```yaml
application_port: 8080
application_environment: production
application_worker_count: 4
```

Poor variables may expose arbitrary implementation details without clear ownership.

Variable names should communicate:

```text
What is controlled?

Who should override it?

What type is expected?

What values are valid?
```

---

# 26. VARIABLE SOURCES

Ansible variables can come from multiple places.

Common sources include:

```text
Role Defaults

Inventory

group_vars

host_vars

Play Variables

Variable Files

Facts

Registered Results

Role Parameters

Extra Variables
```

The flexibility is useful.

The flexibility can also cause difficult production failures.

---

# 27. VARIABLE PRECEDENCE

If the same variable is defined in several places, Ansible must determine which value wins.

This is variable precedence.

Conceptually:

```text
Default Value
↓
Environment Override
↓
Host-Specific Override
↓
Explicit Runtime Override
```

But Ansible's complete precedence model contains more sources than this simplified example.

Do not treat the simplified diagram as the complete precedence specification.

---

# 28. DO NOT BUILD SYSTEMS THAT REQUIRE CONSTANT PRECEDENCE MEMORIZATION

A technically valid repository can still be operationally confusing.

Bad design:

```text
application_port defined in:

role defaults
group_vars/all
group_vars/production
host_vars/app01
play vars
vars_files
extra-vars
```

Now ask:

```text
Which value is app01 using?
```

The answer may be discoverable.

But the repository has become unnecessarily difficult to reason about.

Good configuration design minimizes competing definitions.

---

# 29. VARIABLE OWNERSHIP

For each variable, decide where it logically belongs.

A useful model:

```text
Role default
→ safe reusable default

Environment/group variable
→ environment or group-specific choice

Host variable
→ genuine host exception

Secret source
→ sensitive value

Role parameter
→ explicit role invocation decision
```

This reduces ambiguity.

---

# 30. ROLE DEFAULTS

Role defaults belong in:

```text
roles/<role>/defaults/main.yml
```

They are intended to be easy to override.

Example:

```yaml
application_port: 8080
application_worker_count: 2
```

Defaults should generally be:

- safe
- documented
- unsurprising
- reusable

Do not hide production-specific secrets or hard requirements in role defaults.

---

# 31. ROLE VARIABLES

Roles can also define variables under:

```text
roles/<role>/vars/main.yml
```

These have different precedence behavior from role defaults and are harder to override through ordinary inventory data.

Use them deliberately.

A useful question is:

```text
Should a consumer reasonably be allowed to override this?
```

If yes, role defaults or an explicit interface may be more appropriate.

---

# 32. GROUP VARIABLES

A common repository structure is:

```text
inventory/
└── production/
    ├── hosts.yml
    └── group_vars/
        ├── all.yml
        ├── application.yml
        └── monitoring.yml
```

Group variables represent data shared by a group.

Example:

```yaml
application_worker_count: 8
```

for production application hosts.

---

# 33. HOST VARIABLES

Host variables represent host-specific configuration.

Example:

```text
host_vars/
└── app03.example.internal.yml
```

Use host overrides sparingly.

If 40 hosts all require the same override, the data probably belongs in a group.

---

# 34. EXCEPTIONS SHOULD REMAIN VISIBLE

Suppose one server needs:

```yaml
application_worker_count: 12
```

while every other server uses:

```yaml
application_worker_count: 8
```

A host variable can represent that exception.

But document why.

Otherwise exceptions become unexplained configuration debt.

---

# 35. EXTRA VARIABLES

Runtime extra variables can be supplied with `-e` or `--extra-vars`.

Example:

```bash
ansible-playbook site.yml -e "application_worker_count=12"
```

Extra variables have very high precedence.

That makes them useful.

It also makes casual production use dangerous.

An engineer can unintentionally override carefully designed inventory data.

Treat production extra variables as explicit change inputs, not convenient experimentation.

---

# 36. TROUBLESHOOTING VARIABLE PRECEDENCE

Symptom:

```text
Template contains unexpected value.
```

Do not immediately edit the template.

Trace:

```text
Variable Name
↓
Expected Value
↓
Actual Value
↓
All Definitions
↓
Inventory Membership
↓
Runtime Overrides
↓
Effective Value
```

Useful questions:

```text
Is the host in an unexpected group?

Is host_vars overriding group_vars?

Was -e supplied?

Did a role define the variable?

Was a fact or registered value reused?

Is the variable name duplicated?
```

Find the winning definition.

---

# 37. VARIABLE NAMESPACING

Reusable roles benefit from distinctive variable names.

Instead of:

```yaml
port: 8080
user: app
path: /opt/app
```

prefer role-oriented names such as:

```yaml
veriqta_app_port: 8080
veriqta_app_user: app
veriqta_app_root: /opt/app
```

This reduces collisions between roles and improves readability.

---

# 38. DATA TYPES MATTER

YAML values can represent:

```text
Strings

Integers

Booleans

Lists

Dictionaries

Null
```

A role should understand the type it expects.

Example:

```yaml
monitoring_endpoints:
  - metrics.example.internal
  - logs.example.internal
```

is not the same kind of data as:

```yaml
monitoring_endpoints: metrics.example.internal
```

Validate assumptions.

---

# 39. PLAYBOOKS

A playbook coordinates configuration work.

Conceptually:

```text
Playbook
↓
Play
↓
Hosts
↓
Roles / Tasks
```

A small playbook may directly contain tasks.

At scale, playbooks should increasingly orchestrate reusable roles rather than contain hundreds of unrelated tasks.

---

# 40. THE MONOLITHIC PLAYBOOK PROBLEM

Imagine:

```text
site.yml
```

contains 1,800 lines covering:

```text
Users

Packages

Application

Monitoring

Logging

Security

Certificates

Scheduled Jobs

Services
```

Problems appear:

- difficult review
- difficult testing
- unclear ownership
- hard reuse
- risky partial execution
- merge conflicts
- poor separation of concerns

This is the configuration-management equivalent of a monolithic script.

---

# 41. ROLES

Roles provide reusable structure.

A role represents a coherent configuration responsibility.

Examples:

```text
base_users

base_packages

application

monitoring_agent

logging_agent
```

Each role should have a clear purpose.

---

# 42. STANDARD ROLE STRUCTURE

A role may contain directories such as:

```text
roles/
└── application/
    ├── defaults/
    │   └── main.yml
    ├── files/
    ├── handlers/
    │   └── main.yml
    ├── meta/
    │   └── main.yml
    ├── tasks/
    │   └── main.yml
    ├── templates/
    └── vars/
        └── main.yml
```

Not every role needs every directory.

Create structure that the role actually uses.

---

# 43. ROLE RESPONSIBILITY

A good role should answer:

```text
What capability does this role own?
```

For example:

```text
monitoring_agent
```

might own:

```text
Package

Configuration

Service

Required Directories

Service Restart Handler
```

It should not unexpectedly manage unrelated application users or firewall policy unless those responsibilities are explicitly part of the role contract.

---

# 44. ROLE BOUNDARIES

Avoid both extremes.

Too broad:

```text
role: configure_everything
```

Too narrow:

```text
role: create_one_directory
role: copy_one_file
role: start_one_service
```

A useful role usually represents a coherent operational capability.

---

# 45. ROLE INTERFACE

A reusable role has an interface.

Inputs:

```text
Variables
```

Behavior:

```text
Tasks
```

Change reactions:

```text
Handlers
```

Outputs:

```text
Configured system state
```

Document the interface.

A consumer should know what the role expects without reading every task.

---

# 46. ROLE README

A production-quality role should document:

```text
Purpose

Supported Platforms

Required Variables

Optional Variables

Defaults

Dependencies

Privileges Required

Secrets Required

Tags

Expected Services

Verification

Example Usage
```

Documentation is part of maintainability.

---

# 47. TASK DESIGN

Tasks should describe intent.

Poor task name:

```yaml
- name: Run command
```

Better:

```yaml
- name: Ensure application configuration directory exists
```

Task names become operational evidence during runs.

They should tell an engineer what Ansible is trying to accomplish.

---

# 48. USE FULLY QUALIFIED COLLECTION NAMES

For reusable production content, explicit module names improve clarity.

Example:

```yaml
ansible.builtin.template
```

instead of only:

```yaml
template
```

This makes the module source explicit and reduces ambiguity where collections may contain similarly named modules.

---

# 49. MANAGING USERS

A reusable user-management role might receive structured data:

```yaml
managed_users:
  - name: deploy
    shell: /bin/bash

  - name: monitoring
    shell: /usr/sbin/nologin
```

Then loop through the desired users.

Example:

```yaml
- name: Ensure managed users exist
  ansible.builtin.user:
    name: "{{ item.name }}"
    shell: "{{ item.shell }}"
    state: present
  loop: "{{ managed_users }}"
```

This separates:

```text
Logic
```

from:

```text
Data
```

---

# 50. USER MANAGEMENT IS SECURITY-SENSITIVE

Before automating accounts, define:

```text
Who should exist?

Which groups?

Which shell?

Which SSH access?

Which sudo permissions?

What happens when access is revoked?
```

Creating accounts is only half of identity lifecycle management.

Removal and privilege reduction matter too.

---

# 51. PACKAGE MANAGEMENT

A package role may define desired packages.

Example:

```yaml
base_packages:
  - curl
  - ca-certificates
```

Then:

```yaml
- name: Ensure required base packages are installed
  ansible.builtin.package:
    name: "{{ base_packages }}"
    state: present
```

This expresses desired presence.

---

# 52. PACKAGE VERSION STRATEGY

`present` answers:

```text
Package should be installed.
```

It does not necessarily express:

```text
Exact package version must be X.
```

If exact versions matter, design version policy explicitly.

Consider:

```text
Repository availability

Security updates

Compatibility

Operating-system family

Rollback

Testing
```

Package management is part of release engineering.

---

# 53. AVOID BLIND "LATEST" UPGRADES

A task that continually requests the newest available package can introduce unreviewed change.

Ask:

```text
Should this automation converge configuration,
or perform uncontrolled software upgrades?
```

Production upgrade policy should be deliberate.

---

# 54. FILE MANAGEMENT

Configuration management frequently owns files.

Important properties include:

```text
Path

Content

Owner

Group

Permissions

Validation

Change Reaction
```

Do not manage only file content while ignoring security-relevant metadata.

---

# 55. FILE PERMISSIONS

For configuration files, explicitly reason about permissions.

Example:

```yaml
mode: '0644'
```

For sensitive files:

```yaml
mode: '0600'
```

The correct mode depends on the application and ownership model.

Do not copy permission values without understanding who needs access.

---

# 56. TEMPLATES

Templates generate configuration using variables.

Ansible's template module uses Jinja templating.

Conceptually:

```text
Template
+
Variables
↓
Rendered Configuration
↓
Managed Host
```

Example template:

```jinja2
environment={{ application_environment }}
port={{ application_port }}
workers={{ application_worker_count }}
```

---

# 57. TEMPLATE TASK

Example:

```yaml
- name: Render application configuration
  ansible.builtin.template:
    src: application.conf.j2
    dest: /etc/veriqta-app/application.conf
    owner: root
    group: root
    mode: '0644'
  notify: Restart application
```

The task manages:

```text
Content

Ownership

Permissions
```

and notifies a handler when the task reports a change.

---

# 58. TEMPLATE VALIDATION

Some configuration formats can be validated before replacing the live file.

Where the target application provides a suitable validation command and the module supports the workflow, use it.

Mental model:

```text
Render Candidate
↓
Validate Candidate
├── Invalid → Do Not Install
└── Valid
    ↓
    Replace Managed File
```

This can prevent a malformed configuration from breaking a service.

---

# 59. TEMPLATE VALIDATION IS NOT SERVICE VERIFICATION

A syntactically valid configuration may still contain:

```text
Wrong Endpoint

Wrong Credentials

Wrong Port

Wrong Environment

Wrong Dependency
```

Therefore:

```text
Template Validation
≠
Application Health
```

Continue to service-level verification.

---

# 60. JINJA LOGIC

Templates support logic.

But avoid turning configuration templates into hidden programs.

Poor pattern:

```text
Hundreds of lines of deeply nested template logic.
```

Better pattern:

```text
Prepare clear structured variables
↓
Render relatively understandable template
```

Complex business logic belongs somewhere maintainable and testable.

---

# 61. HANDLERS

Handlers perform operations in response to change.

Common example:

```text
Configuration changed
↓
Notify handler
↓
Restart or reload service
```

This prevents unnecessary service disruption when nothing changed.

---

# 62. HANDLER EXAMPLE

Task:

```yaml
- name: Render application configuration
  ansible.builtin.template:
    src: application.conf.j2
    dest: /etc/veriqta-app/application.conf
    owner: root
    group: root
    mode: '0644'
  notify: Restart application
```

Handler:

```yaml
- name: Restart application
  ansible.builtin.service:
    name: veriqta-app
    state: restarted
```

The handler is notified only when the task reports a change.

---

# 63. WHY HANDLERS MATTER

Without a handler:

```text
Playbook runs
↓
Service restarts every time
```

With a handler:

```text
Configuration unchanged
↓
No restart
```

or:

```text
Configuration changed
↓
Restart required
```

This reduces unnecessary operational impact.

---

# 64. HANDLERS ARE NOT IMMEDIATE BY DEFAULT

A common misunderstanding is:

```text
Task changes
↓
Handler immediately runs
```

Normally, notified handlers execute at defined handler-processing points later in the play.

That matters when subsequent tasks depend on the new service state.

Understand execution timing.

---

# 65. MULTIPLE NOTIFICATIONS

A handler may be notified by several tasks.

For example:

```text
Main Configuration Changed ──┐
                             ├──> Restart Application
Environment File Changed ────┘
```

The handler can avoid multiple unnecessary restarts within the same handler-processing cycle.

This is one reason handlers are preferable to repeated direct restart tasks.

---

# 66. HANDLER FAILURE SCENARIO

Suppose:

```text
Configuration task changes
↓
Handler notified
↓
Later task fails
```

Depending on play behavior, the expected handler may not execute for a host when failures intervene.

This can leave:

```text
New configuration on disk
+
Old process state
```

Troubleshooting must inspect both.

Do not assume:

```text
File changed
=
Service reloaded it.
```

---

# 67. HANDLER TROUBLESHOOTING

If a handler did not run, ask:

```text
Did the notifying task report changed?

Was the correct handler name notified?

Did the host fail before handlers executed?

Was the handler skipped by conditions?

Did another handler name conflict?

Was execution limited or tagged unexpectedly?
```

Use evidence from the run.

---

# 68. IDEMPOTENCY

Idempotency is central to configuration management.

Operationally, a task is idempotent when repeated execution against an already-correct system does not keep producing unnecessary changes.

Conceptually:

```text
First Run
↓
System Changes
↓
Desired State Reached
```

Then:

```text
Second Run
↓
System Already Correct
↓
No Change Required
```

---

# 69. WHY IDEMPOTENCY MATTERS

Idempotency supports:

```text
Repeatability

Safe Reruns

Drift Reconciliation

Predictable Automation

Reduced Service Disruption
```

Without it, configuration management becomes repeated imperative scripting.

---

# 70. IDEMPOTENCY IS NOT "PLAYBOOK DID NOT FAIL"

A playbook can succeed every time while changing something unnecessarily every time.

Example:

```text
Run 1 → changed
Run 2 → changed
Run 3 → changed
Run 4 → changed
```

Investigate why.

The desired steady state should normally converge.

---

# 71. COMMON NON-IDEMPOTENT PATTERN

Consider:

```yaml
- name: Append configuration
  ansible.builtin.shell: |
    echo "feature=true" >> /etc/example.conf
```

Every run can append another line.

Result:

```text
feature=true
feature=true
feature=true
```

This is not desired-state management.

---

# 72. PREFER STATE-AWARE MODULES

Where appropriate, use modules that understand the target resource.

Examples include managing:

```text
Users

Packages

Files

Templates

Services
```

through dedicated modules.

This gives Ansible better information about whether change is actually required.

---

# 73. COMMANDS MAY STILL BE NECESSARY

Not every application has a dedicated module.

Commands may be necessary.

When using them, explicitly define:

```text
When should command run?

How do we detect existing state?

What exit codes mean success?

What counts as change?

Can command run twice?

How do we verify outcome?
```

Do not assume command execution is automatically idempotent.

---

# 74. CONDITIONALS

Conditionals allow tasks to run only when relevant.

Example:

```yaml
- name: Configure feature for production
  ansible.builtin.template:
    src: production-feature.conf.j2
    dest: /etc/veriqta-app/feature.conf
    owner: root
    group: root
    mode: '0644'
  when: application_environment == 'production'
```

Conditionals should express legitimate configuration differences.

---

# 75. CONDITIONAL COMPLEXITY

If every task contains complicated conditions:

```text
if Ubuntu
and production
and region A
and application X
and special_host
```

the role may have poor boundaries.

Too many conditionals can indicate that unrelated behaviors have been combined.

Refactor when complexity becomes difficult to reason about.

---

# 76. LOOPS

Loops reduce repetitive task definitions.

Example:

```yaml
- name: Ensure required directories exist
  ansible.builtin.file:
    path: "{{ item }}"
    state: directory
    owner: root
    group: root
    mode: '0755'
  loop:
    - /opt/veriqta-app
    - /var/log/veriqta-app
```

This is clearer than duplicating identical tasks.

---

# 77. STRUCTURED LOOP DATA

Loops become more useful with structured data.

Example:

```yaml
application_directories:
  - path: /opt/veriqta-app
    mode: '0755'

  - path: /var/log/veriqta-app
    mode: '0750'
```

Then:

```yaml
- name: Ensure application directories exist
  ansible.builtin.file:
    path: "{{ item.path }}"
    state: directory
    owner: root
    group: root
    mode: "{{ item.mode }}"
  loop: "{{ application_directories }}"
```

Data remains explicit.

---

# 78. LOOP FAILURE

A loop may partially succeed.

Example:

```text
Item 1 ✓
Item 2 ✓
Item 3 ✗
Item 4 not reached
```

Do not think of the loop as one atomic transaction.

After failure, inspect which items changed.

---

# 79. FACTS

Facts describe information discovered about managed hosts.

Examples may include information about:

```text
Operating System

Architecture

Interfaces

Addresses

Memory

Processor

Service Manager
```

Facts allow configuration to adapt to real host properties.

---

# 80. FACT GATHERING

Facts are commonly gathered at the beginning of a play unless configured otherwise.

Conceptually:

```text
Connect
↓
Inspect Host
↓
Populate Facts
↓
Use Facts in Tasks
```

Fact gathering has a cost.

At large scale, understand when the information is needed.

---

# 81. FACT-BASED CONDITION

Conceptually:

```yaml
- name: Display operating system family
  ansible.builtin.debug:
    var: ansible_facts['os_family']
```

A role can use discovered platform information to select appropriate behavior.

Do not assume every Linux distribution uses the same:

```text
Package name

Service name

Path

Repository

Configuration format
```

---

# 82. FACTS ARE OBSERVATIONS, NOT POLICY

Facts answer:

```text
What did Ansible discover?
```

Variables may answer:

```text
What do we want?
```

Keep the distinction clear.

Example:

```text
Fact:
Host is Debian-family.
```

```text
Desired configuration:
Install the approved web package for Debian-family systems.
```

---

# 83. FACT CACHING

At larger scale, environments may cache facts to avoid gathering everything repeatedly.

Caching introduces another question:

```text
How fresh is this information?
```

Never assume cached observation is current indefinitely.

Freshness requirements depend on how the fact is used.

---

# 84. REGISTERED RESULTS

A task can register its result.

Example:

```yaml
- name: Check application health
  ansible.builtin.uri:
    url: http://127.0.0.1:8080/health
    return_content: false
    status_code: 200
  register: application_health
```

Later tasks can inspect the result.

This supports evidence-driven workflows.

---

# 85. DO NOT TURN REGISTERED OUTPUT INTO HIDDEN CONTROL FLOW

Complex chains such as:

```text
Task A registers result
↓
Task B transforms it
↓
Task C changes fact
↓
Task D conditionally includes role
↓
Task E changes another variable
```

can become difficult to debug.

Prefer understandable execution paths.

---

# 86. TAGS

Tags allow selected portions of automation to be executed.

Example:

```yaml
- name: Configure monitoring
  ansible.builtin.include_role:
    name: monitoring
  tags:
    - monitoring
```

Then an operator can select tagged content.

Tags can be useful.

They can also create partial-execution risk.

---

# 87. TAGS ARE NOT DEPENDENCY MANAGEMENT

Suppose:

```text
application configuration
depends on
base directories
```

Running only:

```text
application
```

tags may skip required setup if the repository was not designed for that execution path.

Do not assume:

```text
Task has tag
=
Task can safely run alone.
```

---

# 88. TAG DESIGN

Useful tags usually represent operationally meaningful scopes.

Examples:

```text
users

packages

application

monitoring
```

Avoid tagging every tiny task with unrelated combinations until execution becomes impossible to predict.

---

# 89. BEFORE USING TAGS IN PRODUCTION

Inspect available tags:

```bash
ansible-playbook site.yml --list-tags
```

Inspect tasks where useful:

```bash
ansible-playbook site.yml --list-tasks
```

Understand what the selected path will execute.

---

# 90. PRIVILEGE ESCALATION

Many configuration tasks require elevated privileges.

Examples:

```text
Installing packages

Creating system users

Writing /etc configuration

Managing system services
```

Ansible supports privilege escalation through `become`.

---

# 91. BECOME

Example:

```yaml
- name: Configure application hosts
  hosts: application
  become: true
  roles:
    - application
```

This means tasks in the relevant scope can execute using configured privilege escalation.

It does not mean every task everywhere should automatically run with maximum privilege.

---

# 92. LEAST PRIVILEGE

Ask:

```text
Does this task require elevation?
```

If not, unnecessary privilege increases blast radius.

At scale, automation identities should receive only the authority they require.

---

# 93. CONNECTION USER VERSUS BECOME USER

These are different concepts.

```text
Connection User
↓
Authenticates to host
```

Then:

```text
Privilege Escalation
↓
Executes task with elevated identity
```

Troubleshooting must identify which stage failed.

---

# 94. PRIVILEGE TROUBLESHOOTING

Symptom:

```text
Permission denied.
```

Investigate:

```text
Could Ansible connect?

Which remote user?

Did become occur?

Which become method?

Which target user?

Does policy permit the operation?

Does the target file or service have additional restrictions?
```

Do not immediately grant unrestricted sudo.

---

# 95. SECRETS

Configuration management frequently requires sensitive data.

Examples:

```text
API Tokens

Database Passwords

Private Keys

Service Credentials

Certificate Private Material
```

Do not store plaintext secrets casually in:

```text
Playbooks

Templates

Inventory

Git History

CI Logs
```

---

# 96. ANSIBLE VAULT

Ansible Vault can encrypt sensitive Ansible data at rest.

Conceptually:

```text
Sensitive Variables
↓
Encrypted Vault Content
↓
Repository / Storage
↓
Authorized Decryption During Execution
```

Vault protects stored content.

It does not solve every secret-management problem.

---

# 97. ENCRYPTION AT REST IS NOT COMPLETE SECRET SECURITY

After decryption, a secret may still appear in:

```text
Process environment

Rendered file

Application memory

Logs

Debug output

Diff output

Target filesystem
```

Therefore secret handling must cover the complete lifecycle.

---

# 98. VAULT PASSWORD MANAGEMENT

A Vault-encrypted file still requires a decryption mechanism.

Ask:

```text
Where is the vault password or identity source?

Who can access it?

How is it rotated?

Is it exposed to CI?

Can developers decrypt production secrets?

Is access audited?
```

Encrypting a secret while exposing its decryption key provides little protection.

---

# 99. EXTERNAL SECRET SYSTEMS

Larger environments may retrieve secrets from dedicated secret-management systems.

Conceptually:

```text
Ansible
↓
Authenticated Secret Lookup
↓
Secret System
↓
Temporary Secret Value
↓
Target Configuration
```

The implementation depends on the platform.

The engineering principle remains:

```text
Secret access should be explicit, bounded, and auditable.
```

---

# 100. `no_log`

Sensitive tasks may require suppression of normal task output.

For example:

```yaml
no_log: true
```

can help prevent sensitive values from appearing in logs.

But it also reduces troubleshooting visibility.

Use it where necessary and design surrounding diagnostics carefully.

---

# 101. DIFF MODE AND SECRETS

Diff mode can show before-and-after file content for supported modules.

That is valuable for configuration review.

It can also expose secrets.

For sensitive tasks, consider disabling diff output explicitly.

Never assume a CI log is private enough to contain secret configuration.

---

# 102. SECRET TEMPLATE EXAMPLE

Suppose:

```text
database.conf
```

contains a password.

A safe design considers:

```text
Secret source

Decryption

Template rendering

Destination permissions

Diff suppression

Log suppression

Application access

Rotation
```

Secret handling is a system, not a single encrypted file.

---

# 103. CHECK MODE

Ansible provides check mode to simulate many changes without applying them.

Example:

```bash
ansible-playbook -i inventory/staging site.yml --check
```

Mental model:

```text
Evaluate supported tasks
↓
Predict changes where possible
↓
Do not intentionally apply normal changes
```

But check mode has limitations.

---

# 104. CHECK MODE IS NOT A GUARANTEE

Not every module or task can accurately predict behavior in check mode.

Some tasks may:

```text
Report predicted changes

Skip

Produce incomplete information

Behave differently because earlier changes were not actually made
```

Therefore:

```text
Check Mode Passed
≠
Real Run Guaranteed
```

---

# 105. CHECK MODE DEPENDENCY PROBLEM

Imagine:

```text
Task 1 creates directory
Task 2 inspects file inside directory
```

During real execution:

```text
Task 1 creates directory
↓
Task 2 works
```

During check mode:

```text
Task 1 predicts directory creation
↓
Directory may not actually exist
↓
Task 2 may behave differently
```

Simulation has limits.

---

# 106. DIFF MODE

Diff mode can show supported before-and-after changes.

Example:

```bash
ansible-playbook -i inventory/staging site.yml --check --diff
```

This is especially useful for configuration files.

But inspect output for sensitive information.

---

# 107. SYNTAX CHECK

Before execution:

```bash
ansible-playbook site.yml --syntax-check
```

can detect certain syntax-level problems.

But:

```text
Syntax Valid
≠
Variables Correct
≠
Hosts Reachable
≠
Template Semantically Correct
≠
Service Healthy
```

Every validation mechanism has a boundary.

---

# 108. IDEMPOTENCY TEST

A useful lab test is:

```text
First Run
↓
Changes Expected
```

Then:

```text
Second Run
↓
No Unexplained Changes Expected
```

If the second run still reports changes, investigate each one.

Do not simply accept permanent `changed` output.

---

# 109. CONVERGENCE

Convergence means repeated configuration management drives the system toward desired state.

Conceptually:

```text
Incorrect State
↓
Run
↓
Closer to Desired State
↓
Run Again
↓
Desired State
```

A well-designed role should normally stabilize.

---

# 110. DRIFT

Drift occurs when actual configuration differs from intended configuration.

Mental model:

```text
Desired Configuration
↓
Compare
↓
Actual Configuration
↓
Difference
↓
Reconciliation
```

Examples:

```text
Package removed manually

Configuration edited manually

Service disabled manually

User created manually

Permissions changed manually
```

---

# 111. DRIFT IS NOT ALWAYS AN ACCIDENT

Drift can come from:

```text
Incident Response

Emergency Change

Manual Troubleshooting

Another Automation System

Application Self-Modification

Security Tool

Package Upgrade

Unauthorized Change
```

Before reconciling, understand why drift occurred.

---

# 112. CONFIGURATION OWNERSHIP

If Ansible owns a file:

```text
/etc/veriqta-app/application.conf
```

define that ownership clearly.

Otherwise:

```text
Ansible edits file
↓
Application edits file
↓
Human edits file
↓
Another agent edits file
```

creates competing controllers.

One resource should have a clear source of authority.

---

# 113. RECONCILIATION

Suppose desired configuration says:

```text
workers=8
```

but a human changes:

```text
workers=16
```

A later Ansible run detects the managed file difference and restores:

```text
workers=8
```

if that remains the declared desired state.

That is reconciliation.

---

# 114. DO NOT AUTOMATICALLY ERASE INCIDENT CHANGES WITHOUT CONTEXT

Imagine an engineer changes:

```text
workers=16
```

during an incident to restore capacity.

An automated reconciliation job immediately changes it back to:

```text
workers=8
```

The configuration-management system is now fighting incident response.

Mature operations need a process for emergency changes and reconciliation.

---

# 115. EMERGENCY CHANGE MODEL

Use:

```text
Incident
↓
Minimum Necessary Manual Change
↓
Record Change
↓
Verify Recovery
↓
Update Desired Configuration
or
Revert Temporary Change
↓
Reconcile
```

Configuration management should restore control after incidents, not blindly interfere during them.

---

# 116. DESIRED STATE REPOSITORY

A useful production model is:

```text
Git Repository
↓
Reviewed Configuration
↓
Ansible Execution
↓
Managed Systems
```

Manual production changes create drift away from version-controlled intent.

The repository becomes an important record of intended configuration.

---

# 117. CONFIGURATION CHANGE WORKFLOW

A mature workflow resembles:

```text
Requirement
↓
Change Role / Variables / Template
↓
Pull Request
↓
Review
↓
Lint / Syntax / Tests
↓
Check / Diff Where Appropriate
↓
Staging
↓
Verification
↓
Controlled Production Rollout
↓
Verification
```

Configuration management deserves the same delivery discipline as infrastructure code.

---

# 118. DO NOT RUN UNREVIEWED CONFIGURATION DIRECTLY FROM A LAPTOP

A production model such as:

```text
Engineer edits local file
↓
Immediately runs against 500 production hosts
```

has weak control.

Prefer version-controlled, reviewed, traceable automation for consequential changes.

---

# 119. SCALE CHANGES THE RISK MODEL

Changing one host incorrectly may affect one service instance.

Changing 500 hosts incorrectly may cause:

```text
Fleet-Wide Outage

Authentication Failure

Monitoring Loss

Configuration Corruption

Simultaneous Restart

Capacity Collapse
```

At scale, rollout strategy matters.

---

# 120. BLAST RADIUS

Before executing, ask:

```text
How many hosts?

Which environment?

Which service?

Which region?

Which failure domain?

Will services restart?

Could all replicas restart together?
```

Configuration correctness is only one dimension.

Change distribution matters too.

---

# 121. ROLLING EXECUTION

For some changes, hosts should be updated in batches.

Conceptually:

```text
Batch 1
↓
Configure
↓
Verify
↓
Batch 2
↓
Configure
↓
Verify
```

Ansible supports controls that can help implement bounded execution.

The correct batch size depends on service architecture and availability requirements.

---

# 122. `serial`

A play can limit how many hosts are processed in a batch.

Conceptual example:

```yaml
- name: Configure application fleet
  hosts: application
  serial: 2
```

This does not automatically make the deployment safe.

It simply changes execution batching.

You still need health verification and failure handling.

---

# 123. BATCH SIZE

Suppose there are six application instances.

With:

```text
serial: 2
```

the conceptual progression is:

```text
app01 + app02
↓
app03 + app04
↓
app05 + app06
```

But production safety depends on whether the remaining capacity can handle traffic.

Never choose batch size without understanding system redundancy.

---

# 124. CONCURRENCY

Ansible can operate on multiple hosts concurrently.

Concurrency improves speed.

It also increases simultaneous blast radius.

Consider:

```text
50 hosts
×
service restart
```

If all restart together, the application may disappear.

Automation speed must be balanced against availability.

---

# 125. HOST ORDER

Do not build critical correctness assumptions around accidental inventory ordering.

If execution order matters, design it explicitly through plays, batching, orchestration, or dependency logic.

"These hosts usually appear first" is not an engineering guarantee.

---

# 126. SERVICE DEPLOYMENT ROLE

A service role might own:

```text
Service User

Application Directory

Artifact Placement

Configuration

Service Definition

Service State

Health Verification
```

The role should make each responsibility visible.

---

# 127. APPLICATION ARTIFACT OWNERSHIP

Decide whether Ansible is responsible for deploying the application artifact itself.

Possible model:

```text
CI/CD
→ deploys application

Ansible
→ manages OS and service configuration
```

Another model:

```text
Ansible
→ manages both configuration and artifact
```

Both can exist.

What matters is clear ownership.

Avoid two deployment systems independently managing the same artifact.

---

# 128. SERVICE CONFIGURATION

Suppose a systemd service definition is managed by Ansible.

The workflow may be:

```text
Template unit file
↓
Unit file changes
↓
Reload service manager
↓
Restart application if required
↓
Verify service
```

The exact sequence depends on what changed.

---

# 129. RESTART VERSUS RELOAD

Do not assume every configuration change requires restart.

Some applications support reload.

Others require restart.

Some configuration changes require no process action.

Choose behavior based on application semantics.

Unnecessary restarts create avoidable risk.

---

# 130. MONITORING CONFIGURATION ROLE

A monitoring role might manage:

```text
Monitoring User

Package

Configuration

Endpoint

Labels

Service

Health
```

Useful variables may include:

```text
Environment

Service Name

Metrics Endpoint

Log Path

Region
```

This demonstrates why role reuse matters.

The same monitoring role can serve many host groups with different data.

---

# 131. OBSERVABILITY OF CONFIGURATION MANAGEMENT

A production Ansible run should provide enough evidence to answer:

```text
What inventory?

What playbook revision?

What hosts?

What roles?

What changed?

What failed?

What was skipped?

What became unreachable?

How long did it take?

Was verification successful?
```

Automation without observability becomes difficult to trust.

---

# 132. CHANGED IS NOT VERIFIED

Ansible reports task states such as:

```text
ok

changed

failed

unreachable

skipped
```

A task reporting:

```text
changed
```

means the task believes it made a change.

It does not prove the application is healthy.

---

# 133. `ok` IS NOT BUSINESS VERIFICATION

Similarly:

```text
ok
```

does not mean:

```text
Production service is correct.
```

It means the task did not report a required change or failure under its own semantics.

Verify the intended system outcome separately.

---

# 134. VERIFICATION MODEL

For every important configuration change:

```text
Action
↓
Expected State
↓
Inspection
↓
Evidence
↓
Conclusion
```

Example:

```text
Action:
Render application configuration.

Expected:
workers=8.

Inspection:
Read deployed configuration.

Evidence:
Expected value exists.

Conclusion:
Configuration file correct.
```

Then continue:

```text
Expected:
Application healthy.

Inspection:
Health endpoint.

Evidence:
HTTP success.

Conclusion:
Application accepted configuration.
```

---

# 135. CONFIGURATION FILE SUCCESS VERSUS SERVICE SUCCESS

Always distinguish:

```text
File exists
```

from:

```text
File is valid
```

from:

```text
Service loaded file
```

from:

```text
Service is running
```

from:

```text
Service is healthy
```

from:

```text
Users can reach service
```

These are different layers.

---

# 136. UNREACHABLE HOSTS

An unreachable host means Ansible could not establish the required connection path.

Possible causes include:

```text
Wrong Address

DNS Failure

Routing Failure

Firewall

SSH Failure

Wrong User

Wrong Key

Host Down

Bastion / Proxy Problem
```

Do not treat every unreachable result as an Ansible problem.

---

# 137. UNREACHABLE TROUBLESHOOTING

Use:

```text
Inventory Host
↓
Resolved Address
↓
Network Path
↓
Target Port
↓
SSH / Connection Service
↓
Authentication
↓
Remote User
↓
Python / Runtime Requirements Where Relevant
```

Classify the failing layer.

---

# 138. TESTING BASIC REACHABILITY

Ansible's ping module can test whether Ansible can execute a basic module operation against a compatible target.

Example:

```bash
ansible application -i inventory/staging -m ansible.builtin.ping
```

This is not an ICMP ping.

It tests Ansible connectivity and execution behavior.

Do not confuse it with:

```bash
ping hostname
```

---

# 139. CONNECTION SUCCESS DOES NOT PROVE PRIVILEGE SUCCESS

You may observe:

```text
Ansible ping
✓
```

then:

```text
Package installation
✗ Permission denied
```

This means:

```text
Connection path works.
```

It does not prove:

```text
Privilege escalation works.
```

Separate the layers.

---

# 140. INCORRECT TEMPLATE TROUBLESHOOTING

Symptom:

```text
Rendered configuration is wrong.
```

Trace:

```text
Source Template
↓
Variable Names
↓
Effective Variable Values
↓
Conditional Logic
↓
Filters
↓
Rendered Output
↓
Destination
```

Do not edit the generated production file manually as the permanent fix.

Correct the source of desired state.

---

# 141. TEMPLATE SYNTAX VERSUS APPLICATION SYNTAX

A template can render successfully while producing invalid application configuration.

Therefore distinguish:

```text
Jinja rendering success
```

from:

```text
Application configuration validity
```

Use application-native validation where available.

---

# 142. PARTIAL EXECUTION

Ansible operations across many hosts are not one global transaction.

Example:

```text
app01 ✓
app02 ✓
app03 ✗
app04 not completed
```

Now the fleet may contain mixed configuration.

This is a production state that must be understood.

---

# 143. PARTIAL EXECUTION RECOVERY

Use:

```text
Failure
↓
Stop
↓
Identify Successful Hosts
↓
Identify Failed Hosts
↓
Identify Unprocessed Hosts
↓
Assess Service Impact
↓
Determine Root Cause
↓
Correct Automation
↓
Re-run Safely
↓
Verify Fleet Convergence
```

Do not assume Ansible automatically rolls back earlier hosts.

---

# 144. CONFIGURATION MANAGEMENT IS NOT TRANSACTIONAL ROLLBACK

Suppose:

```text
User created
✓

Package installed
✓

Configuration written
✓

Service restart
✗
```

Ansible does not generally mean:

```text
Delete user
Uninstall package
Restore old configuration
```

automatically.

Recovery must be designed.

---

# 145. BACKUPS AND CONFIGURATION CHANGES

Some file-management operations can create backups where appropriate.

Backups may help recovery.

But:

```text
Backup exists
≠
Automatic rollback
```

You still need:

```text
Correct backup

Restoration procedure

Validation

Service recovery

Verification
```

---

# 146. BLOCKS AND ERROR HANDLING

Ansible supports grouping tasks and defining error-handling behavior.

Conceptually:

```text
Try Configuration Work
↓
Failure?
├── No → Continue
└── Yes
    ↓
    Recovery / Diagnostic Path
```

Use error handling carefully.

Do not hide failures merely to keep the playbook green.

---

# 147. `ignore_errors` IS NOT A TROUBLESHOOTING STRATEGY

A dangerous pattern is:

```yaml
ignore_errors: true
```

added whenever a task fails.

This can convert:

```text
Known Failure
```

into:

```text
Hidden Failure
```

Use error continuation only when failure is expected, understood, and explicitly handled.

---

# 148. FAILURE SEMANTICS

Some commands return exit codes that need explicit interpretation.

When generic commands are unavoidable, define:

```text
What exit code means success?

What exit code means changed?

What exit code means failure?
```

Do not blindly accept command behavior.

---

# 149. CHANGED SEMANTICS

Likewise, custom command tasks may need explicit change semantics.

If a read-only diagnostic command runs every time, it should not necessarily report that configuration changed.

Accurate change reporting matters because:

```text
Handlers

Auditing

Idempotency Tests

Operator Decisions
```

may depend on it.

---

# 150. HANDLER BEHAVIOR AFTER FAILURE

A configuration file may have changed and notified a restart.

If a later task fails before the normal handler point, the process may still be running with old configuration.

This creates a split state:

```text
Disk
→ new configuration

Process
→ old configuration
```

Troubleshooting must inspect both.

---

# 151. FORCING HANDLERS

Ansible supports mechanisms that can influence whether notified handlers run despite later failures.

Do not enable such behavior mechanically.

Ask:

```text
Is executing this handler after another task failed actually safe?
```

For example:

```text
Restarting a service after only half of its required configuration was applied
```

may make the incident worse.

---

# 152. HANDLER DESIGN PRINCIPLE

A handler should represent a coherent reaction to a successfully changed prerequisite.

Examples:

```text
Reload system manager

Restart application

Reload proxy
```

Avoid handlers that perform broad unrelated operations.

# 192. CONFIGURATION MANAGEMENT AND TERRAFORM

Terraform and Ansible solve overlapping but different problems.

A useful conceptual separation is:

```text
Terraform
↓
Infrastructure Resources
↓
Compute Exists
```

then:

```text
Ansible
↓
Operating-System / Application Configuration
↓
Host Ready
```

This is not an absolute rule.

Some providers and tools can cross these boundaries.

The important principle is clear ownership.

---

# 193. AVOID TWO SOURCES OF AUTHORITY

Dangerous pattern:

```text
Terraform manages file X
+
Ansible manages file X
```

or:

```text
Cloud-init manages service X
+
Ansible manages service X
```

or:

```text
Application manages config X
+
Ansible continuously overwrites config X
```

Competing controllers create unpredictable behavior.

Define which system owns which state.

---

# 194. BOOTSTRAP VERSUS CONTINUOUS CONFIGURATION

A common model is:

```text
Infrastructure Provisioning
↓
Minimal Bootstrap
↓
Configuration Management
↓
Application Ready
```

Bootstrap should establish enough capability for the next management layer.

Avoid placing the entire production configuration in opaque bootstrap scripts if Ansible is intended to own that configuration later.

---

# 195. IMMUTABLE INFRASTRUCTURE CONSIDERATION

Not every modern environment configures long-lived hosts continuously.

Some teams build machine images or container images and replace systems rather than modifying them in place.

Configuration management may still be used for:

```text
Image Build

Base Configuration

Legacy Systems

Utility Hosts

Network Devices

Bootstrap

Specialized Services
```

Understand the operating model before choosing the tool.

---

# 196. CONFIGURATION MANAGEMENT VERSUS IMAGE BUILDING

Mutable model:

```text
Running Host
↓
Ansible Changes Host
```

Image-based model:

```text
Source Configuration
↓
Build New Image
↓
Deploy New Instances
↓
Replace Old Instances
```

Neither model is universally correct.

Production architecture determines the appropriate approach.

---

# 197. DRIFT IN IMMUTABLE SYSTEMS

Immutable-style infrastructure reduces some forms of host drift because changed instances can be replaced.

But drift can still exist in:

```text

Secrets
```

"Immutable" does not mean "incapable of drift."

# 219. DYNAMIC TEMPLATE CONTENT

A subtle problem occurs when templates include values that change every run.

For example:

```text
Generated at current timestamp
```

inside a managed configuration file.

Every execution produces a new file.

Then:

```text
Template changed
↓
Handler notified
↓
Service restarted
```

every time.

Avoid dynamic content unless it is operationally required.

# 228. AI-GENERATED ANSIBLE

Suppose AI generates:

```yaml
- name: Fix permissions
  ansible.builtin.shell: chmod -R 777 /opt/application
```

This is syntactically plausible.

It is operationally dangerous.

The engineer must ask:

```text
Why these permissions?

Why recursive?

What files are affected?

Who should own them?

What is the security consequence?

Is there a state-aware module?

What is the blast radius?
```

Never confuse generated syntax with correct engineering.


AI-generated automation must converge too.

# 230. AI AND VARIABLE PRECEDENCE

# 237. SERVICE ACCOUNT SECURITY


```text

Content correct

```

Verification must include metadata.

# 239. PRODUCTION FAILURE: FLEET-WIDE RESTART

A configuration task changes every host.

Each host notifies:

```text
Restart application.
```

If all hosts execute together:

```text
Entire service fleet may restart.
```

This is why:

```text
Idempotency

Batching

Availability awareness

Verification
```

must work together.

---

# 240. PRODUCTION FAILURE: BAD SHARED VARIABLE

One value in:

```text
group_vars/production
```

may affect hundreds of systems.

A tiny Git diff can have huge blast radius.

Review configuration data as carefully as role logic.

---

# 241. PRODUCTION FAILURE: BAD TEMPLATE

A single shared template can distribute invalid configuration to every host.

Safe delivery should use:

```text
Validation

Small initial scope

Health checks

Batching

Stop conditions
```

before fleet-wide rollout.

---

# 242. PRODUCTION FAILURE: BAD ROLE DEFAULT

Changing a reusable default can affect consumers that never explicitly set the variable.

Therefore role default changes are API changes.

Review all consumers.

---

# 243. PRODUCTION FAILURE: WRONG GROUP MEMBERSHIP

A database server accidentally joins:

```text
application
```

and receives application configuration.

Inventory correctness is configuration correctness.

Review group membership.

---

# 244. PRODUCTION FAILURE: UNBOUNDED PRIVILEGE

A compromised automation credential with unrestricted root access across every environment creates massive blast radius.

Separate:

```text
Environment

Function

Privilege

Execution Authority
```

where practical.

---

# 245. PRODUCTION FAILURE: PARTIAL CONVERGENCE

Half the fleet runs new configuration.

Half runs old configuration.

Potential consequences:

```text
Inconsistent behavior

Protocol incompatibility

Uneven traffic

Different security policy

Difficult troubleshooting
```

Partial execution is a real system state.

Plan for it.

---

# 246. PRODUCTION FAILURE: HIDDEN MANUAL CHANGE

A manual incident fix works.

Nobody updates desired state.

Days later:

```text
Scheduled Ansible Run
↓
"Corrects" drift
↓
Incident returns
```

This is why emergency changes must be reconciled deliberately.

---

# 247. PRODUCTION FAILURE: SECRET LEAK THROUGH DIFF

An engineer enables:

```text
--diff
```

against a secret-bearing template.

The CI system stores the output.

Now the secret may exist in:

```text

Notifications

Log Exports

Artifact Systems
```

Review output sensitivity before enabling diagnostic features.
