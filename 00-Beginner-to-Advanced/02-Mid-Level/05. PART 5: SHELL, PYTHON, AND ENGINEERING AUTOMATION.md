# PART 5: SHELL, PYTHON, AND ENGINEERING AUTOMATION

## Goal

Progress from simple scripting into maintainable operational automation.

At the junior level, automation often begins by taking commands that are normally typed manually and placing them into a script:

```text
Command
↓
Command
↓
Command
↓
Command
```

That is useful, but it is only the beginning.

A script that works once on one machine under ideal conditions is not yet reliable engineering automation.

At Mid-Level, automation must be designed around real operational conditions:

```text
Inputs
↓
Validation
↓
Decision
↓
Action
↓
Verification
↓
Logging
↓
Result
```

It must also account for failure:

```text
Expected Operation
↓
Dependency Fails
↓
Failure Detected
↓
Useful Evidence Produced
↓
Unsafe Work Stops
↓
Completed Work Is Understood
↓
Recovery Is Possible
↓
Meaningful Exit Status Returned
```

The objective of this Part is not to collect more Shell commands or turn every DevOps engineer into a full-time Python software developer.

The objective is to develop the ability to answer:

```text
Should this task be automated?
```

Then:

```text
What is the correct automation mechanism?
```

Then:

```text
How should the automation behave when reality differs from the happy path?
```

By the end of this Part, automation should be treated as production engineering software rather than a convenient collection of commands.

---

# 1. FROM SCRIPTING TO ENGINEERING AUTOMATION

Consider this script:

```bash
#!/usr/bin/env bash

kubectl get pods
curl https://example.internal/health
df -h
```

It automates three commands.

But important questions remain unanswered.

What happens if `kubectl` is unavailable?

What happens if the current Kubernetes context points to the wrong cluster?

What happens if DNS resolution fails?

What happens if the HTTP request hangs?

What happens if the endpoint returns HTTP 500?

What happens if `df` succeeds but the earlier checks failed?

What does the script return to the calling system?

Can another engineer understand the result?

Can CI/CD determine whether the automation succeeded?

Can the script safely run twice?

Can two copies run simultaneously?

Can its output be searched in centralized logging?

These questions separate simple scripting from engineering automation.

A Mid-Level engineer should think in terms of:

```text
Automation
=
Code
+
Operational Assumptions
+
Failure Behavior
+
Evidence
+
Safety
```

---

# 2. AUTOMATION SHOULD SOLVE A DEFINED PROBLEM

Do not begin with:

```text
I should write a Python script.
```

Begin with:

```text
What problem am I trying to automate?
```

For example:

```text
Problem:
Engineers manually inspect 80 application endpoints every morning.
```

Then determine:

```text
Inputs:
Service inventory

Actions:
Query health endpoints

Outputs:
Health report

Failure behavior:
One unreachable service must not prevent the remaining checks

Consumers:
Operations team and CI job

Frequency:
Every 15 minutes

Security:
Authentication token required

Success:
Every expected service checked and results recorded
```

Only then should implementation begin.

---

# 3. THE AUTOMATION DESIGN MODEL

Use:

```text
Problem
↓
Inputs
↓
Preconditions
↓
Actions
↓
Expected State
↓
Verification
↓
Failure Modes
↓
Recovery
↓
Outputs
↓
Observability
```

For every automation, be able to explain each stage.

---

# 4. AUTOMATION IS NOT ALWAYS THE ANSWER

Not every manual task should be automated.

Automation introduces:

- code
- maintenance
- dependencies
- credentials
- permissions
- testing requirements
- failure modes
- operational ownership

A task performed once may not justify permanent automation.

A frequently repeated, predictable, testable task often does.

Before automating, ask:

```text
How often does this happen?

How expensive is manual execution?

How error-prone is it?

Is the procedure sufficiently understood?

Are the inputs predictable?

Can success be verified?

What happens if automation fails?

Who will maintain it?
```

Do not automate a poorly understood process merely to make it fail faster.

---

# 5. CHOOSING THE CORRECT AUTOMATION MECHANISM

A Mid-Level engineer should not solve every problem with Shell.

The available mechanisms include:

- Shell
- Python
- configuration management
- infrastructure as code
- CI/CD
- platform APIs

Each solves a different class of problem.

---

# 6. WHEN SHELL IS APPROPRIATE

Shell is strong when the task primarily coordinates existing command-line tools.

Examples include:

- checking whether commands exist
- invoking system utilities
- moving files
- inspecting local state
- connecting several Unix tools
- wrapping a small operational workflow
- performing simple environment checks

A reasonable Shell automation might:

```text
Validate Required Commands
↓
Inspect Local Filesystem
↓
Run Existing CLI
↓
Check Exit Status
↓
Produce Result
```

Shell becomes increasingly difficult to maintain when the problem requires:

- complex nested data structures
- substantial JSON transformation
- sophisticated API interaction
- complex retry logic
- significant concurrency
- large business rules
- extensive testing
- reusable libraries

At that point, Python may provide a clearer implementation.

---

# 7. WHEN PYTHON IS APPROPRIATE

Python becomes useful when automation requires richer program structure.

Examples include:

- consuming APIs
- processing JSON
- processing YAML
- complex validation
- structured data transformation
- report generation
- multiple execution paths
- retries and timeout handling
- richer error handling
- reusable modules
- unit testing

A Python automation may follow:

```text
Parse Arguments
↓
Load Configuration
↓
Validate Configuration
↓
Authenticate
↓
Call API
↓
Parse Response
↓
Inspect Infrastructure
↓
Build Structured Result
↓
Generate Report
↓
Return Exit Code
```

---

# 8. WHEN CONFIGURATION MANAGEMENT IS APPROPRIATE

Configuration-management systems are designed to manage desired configuration across systems.

Typical examples include:

- package installation
- service configuration
- file deployment
- user configuration
- repeated host configuration
- enforcing known machine state

If the problem is:

```text
Configure 200 hosts consistently.
```

a growing Shell script containing hundreds of SSH commands is usually not the strongest abstraction.

The engineering question becomes:

```text
Should this be expressed as desired configuration instead?
```

---

# 9. WHEN INFRASTRUCTURE AS CODE IS APPROPRIATE

Infrastructure as code is appropriate when the automation concerns infrastructure lifecycle and desired infrastructure state.

Examples include:

- networks
- compute resources
- load balancers
- IAM resources
- managed databases
- DNS resources
- cloud storage

Do not build a custom Python program to reproduce an infrastructure lifecycle that an established IaC workflow already manages safely.

The question is:

```text
Am I orchestrating an operational task,
or defining infrastructure state?
```

Those are different problems.

---

# 10. WHEN CI/CD IS APPROPRIATE

CI/CD is useful when automation belongs to a delivery event.

Examples:

```text
Commit
↓
Test

Pull Request
↓
Validate Infrastructure

Merge
↓
Build Artifact

Tag
↓
Publish Release

Approved Deployment
↓
Deploy
↓
Verify
```

A deployment procedure that exists only as:

```bash
./deploy-production.sh
```

on one engineer's laptop may have weaker:

- traceability
- repeatability
- access control
- review
- auditability

than a controlled delivery workflow.

---

# 11. WHEN PLATFORM APIs ARE APPROPRIATE

Many infrastructure platforms expose APIs.

Examples include:

- cloud APIs
- Kubernetes API
- Git hosting APIs
- monitoring APIs
- incident-management APIs
- artifact registries

When automation requires structured interaction with a platform, its API may be more appropriate than parsing human-oriented terminal output.

Prefer:

```text
Structured API Response
```

over:

```text
Parse Pretty Terminal Table
```

when reliable machine-readable interfaces are available.

---

# 12. DO NOT PARSE HUMAN OUTPUT UNNECESSARILY

Suppose a command displays:

```text
NAME       STATUS    AGE
api-1      Running   4h
api-2      Running   4h
```

A script could attempt to extract columns using:

```bash
awk
```

But if the tool provides JSON output, structured data is generally safer.

Human-readable output can change formatting.

Machine-readable interfaces exist specifically to make automation more reliable.

---

# 13. AUTOMATION BOUNDARIES

Automation should have a clear responsibility.

Weak automation:

```text
One 2,000-line script:

Creates infrastructure
Configures servers
Builds application
Deploys application
Changes DNS
Runs database migration
Deletes old resources
Sends report
```

This creates a large failure domain.

A stronger design may separate:

```text
Infrastructure Provisioning
↓
Configuration
↓
Build
↓
Deployment
↓
Verification
```

Separation improves:

- testing
- ownership
- troubleshooting
- recovery
- reuse

---

# 14. SHELL SCRIPT STRUCTURE

A maintainable Shell script should normally make its structure visible.

For example:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

readonly SCRIPT_NAME="${0##*/}"

log() {
    printf '%s level=%s message=%q\n' \
        "$(date -u +'%Y-%m-%dT%H:%M:%SZ')" \
        "$1" \
        "$2"
}

main() {
    log INFO "automation started"
}

main "$@"
```

The exact structure depends on the task.

The important point is that operational scripts should have deliberate structure.

---

# 15. THE SHEBANG

A script commonly begins with a shebang such as:

```bash
#!/usr/bin/env bash
```

This asks `env` to locate `bash` through the execution environment's `PATH`.

Another environment may intentionally use a fixed path such as:

```bash
#!/bin/bash
```

Neither should be copied blindly.

The runtime environment matters.

Know which shell the script requires.

---

# 16. SHELL PORTABILITY

A script written for Bash is not automatically portable POSIX shell code.

For example, Bash supports features that `/bin/sh` implementations may not support identically.

If the script requires Bash, state that requirement.

Do not write:

```bash
#!/bin/sh
```

and then assume every Bash-specific feature will work.

---

# 17. DEFENSIVE SHELL SCRIPTING

Defensive scripting assumes:

```text
Inputs can be wrong.

Commands can fail.

Files can disappear.

Dependencies can be unavailable.

Output can be malformed.

The environment can differ.

The script can be interrupted.
```

This changes how automation is written.

---

# 18. STRICT-MODE CONCEPTS

A common Bash pattern is:

```bash
set -Eeuo pipefail
```

The individual behaviors matter more than memorizing the line.

`-e` enables `errexit`.

`-u` enables `nounset`.

`pipefail` changes pipeline status behavior.

`-E` affects inheritance of `ERR` traps in Bash contexts.

These features can expose failures that might otherwise be ignored.

But they have important semantics and exceptions.

GNU Bash documents specific contexts in which `errexit` does not cause immediate shell exit, and `pipefail` changes a pipeline's status to reflect a failing command rather than only the last command when applicable.

Therefore:

```text
Strict Mode
≠
Automatic Correctness
```

---

# 19. UNDERSTAND `set -e`

Do not think of:

```bash
set -e
```

as:

```text
Every failed command always immediately terminates the script.
```

Bash has contextual rules around `if`, `while`, `until`, `&&`, `||`, pipelines, and other constructs.

Therefore the engineer must still reason about error handling.

---

# 20. UNDERSTAND `set -u`

With:

```bash
set -u
```

using an unset variable can become an error in relevant contexts.

This can expose mistakes such as:

```bash
echo "$PRODCUTION_REGION"
```

when the intended variable was:

```text
PRODUCTION_REGION
```

Without defensive handling, a typo might silently become an empty value and cause incorrect behavior.

---

# 21. UNDERSTAND `pipefail`

Consider:

```bash
producer | processor | writer
```

Without `pipefail`, the pipeline's status normally follows the final command's status.

The earlier command may fail while the final command succeeds.

With:

```bash
set -o pipefail
```

a non-zero command in the pipeline can cause the pipeline itself to report failure according to Bash's documented pipeline-status rules.

This matters when pipeline stages carry operational meaning.

---

# 22. QUOTE VARIABLE EXPANSIONS DELIBERATELY

Consider:

```bash
rm $TARGET
```

versus:

```bash
rm -- "$TARGET"
```

Quoting protects argument boundaries when values contain spaces or wildcard characters.

The `--` convention is supported by many Unix tools to mark the end of options, although support must be verified for the specific command.

Do not assume input will always look like:

```text
simple-name
```

It may contain:

```text
spaces
wildcards
leading hyphens
unexpected characters
```

---

# 23. INPUT VALIDATION

Never confuse:

```text
Input Exists
```

with:

```text
Input Is Valid
```

Suppose a script receives:

```bash
./deploy.sh production
```

Validation may need to answer:

```text
Was an argument supplied?

Is the environment allowed?

Does the required configuration exist?

Is the target known?

Is the current identity authorized?

Is the target production?
```

---

# 24. VALIDATE EARLY

A strong pattern is:

```text
Receive Input
↓
Validate Input
↓
Validate Preconditions
↓
Perform Change
```

not:

```text
Perform Three Changes
↓
Discover Fourth Input Is Invalid
```

Fail before mutation whenever possible.

---

# 25. EXAMPLE INPUT VALIDATION

```bash
environment="${1:-}"

case "$environment" in
    development|staging|production)
        ;;
    *)
        printf 'ERROR: invalid environment: %s\n' "$environment" >&2
        exit 2
        ;;
esac
```

Expected behavior:

```text
development
→ accepted

staging
→ accepted

production
→ accepted

anything else
→ rejected before operational work begins
```

---

# 26. REQUIRED COMMAND VALIDATION

If automation depends on external tools, verify them.

```bash
require_command() {
    local command_name="$1"

    if ! command -v "$command_name" >/dev/null 2>&1; then
        printf 'ERROR: required command not found: %s\n' "$command_name" >&2
        return 1
    fi
}
```

Then:

```bash
require_command curl
require_command jq
```

This provides a clearer failure than discovering a missing dependency halfway through execution.

---

# 27. PRECONDITION VALIDATION

Before performing work, validate assumptions.

Examples:

```text
Configuration file exists

Output directory is writable

Required environment variable exists

Authentication token exists

API endpoint is reachable

Expected CLI is installed

Correct environment is selected
```

Do not allow hidden assumptions to become hidden failure modes.

---

# 28. FUNCTIONS

Functions make scripts easier to:

- read
- test
- reuse
- reason about
- modify

Weak structure:

```bash
command
command
if ...
command
for ...
command
command
```

Better structure:

```text
validate_inputs()

load_configuration()

check_dependencies()

inspect_infrastructure()

generate_report()

main()
```

Function names should explain intent.

---

# 29. KEEP FUNCTIONS FOCUSED

A function called:

```text
check_service()
```

should not secretly:

- restart the service
- delete logs
- modify configuration
- send email
- reboot the host

A function should have a clear contract.

This reduces surprise.

---

# 30. RETURN STATUS VERSUS OUTPUT

In Shell, distinguish:

```text
Function Output
```

from:

```text
Function Exit Status
```

For example:

```bash
get_region() {
    printf '%s\n' "us-east-1"
}
```

produces data.

A function may also:

```bash
return 1
```

to indicate failure.

Do not mix diagnostic logging into data output carelessly if another command needs to consume that output.

---

# 31. STANDARD OUTPUT AND STANDARD ERROR

Operational scripts should distinguish normal output from error diagnostics.

Normal output:

```bash
printf '%s\n' "$result"
```

Errors:

```bash
printf 'ERROR: configuration missing\n' >&2
```

This matters because automation platforms may separately capture:

```text
stdout

stderr

exit status
```

---

# 32. EXIT CODES

Unix processes return an exit status.

Conventionally:

```text
0
→ success

non-zero
→ some form of failure
```

Automation should use exit codes meaningfully.

A CI system cannot reliably interpret:

```text
ERROR: deployment failed
```

if the script still returns:

```text
0
```

---

# 33. EXIT CODE DESIGN

A small automation may define:

```text
0
Success

1
General operational failure

2
Invalid input or configuration

3
Dependency unavailable

4
Partial result
```

There is no universal requirement for those exact values.

The important requirements are:

- documented meaning
- consistency
- useful behavior for callers

---

# 34. TRAPS

Bash `trap` can register actions for signals and shell events.

A common use is cleanup.

```bash
cleanup() {
    rm -rf -- "$temp_dir"
}

trap cleanup EXIT
```

Bash documents `EXIT` as a trap condition executed when the shell exits.

This can help ensure temporary resources are removed on normal script termination paths.

---

# 35. TRAPS ARE NOT MAGIC

Do not assume cleanup always runs.

For example, `SIGKILL` cannot be handled by the process being killed.

System crashes and abrupt runtime termination can also prevent cleanup.

Therefore:

```text
Cleanup Trap
=
Useful Safety Mechanism
```

not:

```text
Guaranteed Cleanup Under Every Failure
```

---

# 36. TEMPORARY FILES

Avoid predictable temporary names such as:

```bash
/tmp/report.tmp
```

Multiple executions may collide.

Another process may already own that path.

For Shell environments where `mktemp` is available, a pattern may be:

```bash
temp_file="$(mktemp)"
```

or:

```bash
temp_dir="$(mktemp -d)"
```

Verify `mktemp` behavior on the target operating system because command-line options can vary between implementations.

---

# 37. TEMPORARY RESOURCE CLEANUP

Example:

```bash
temp_dir=""

cleanup() {
    if [[ -n "$temp_dir" && -d "$temp_dir" ]]; then
        rm -rf -- "$temp_dir"
    fi
}

trap cleanup EXIT

temp_dir="$(mktemp -d)"
```

The sequence matters.

Do not attempt cleanup using an unsafe or uninitialized path.

---

# 38. CONCURRENCY AWARENESS

Ask:

```text
What happens if two copies run at the same time?
```

Possible problems include:

- both writing the same report
- both modifying the same configuration
- both rotating the same file
- duplicate API operations
- race conditions
- one deleting another's temporary data

Automation that works once may fail under concurrency.

---

# 39. SHARED FILE RACE

Suppose every execution writes:

```text
/tmp/infrastructure-report.json
```

Two concurrent processes may overwrite one another.

Possible approaches include:

- unique temporary paths
- locking
- atomic replacement
- per-run identifiers
- designing the operation to tolerate concurrency

The correct solution depends on the resource.

---

# 40. ATOMIC FILE REPLACEMENT CONCEPT

Instead of writing directly to an important file:

```text
Read Old
↓
Overwrite In Place
↓
Failure Halfway
↓
Corrupt File
```

a safer design may be:

```text
Write Temporary File
↓
Validate Temporary File
↓
Replace Destination
```

Filesystem and cross-filesystem behavior must still be considered.

---

# 41. STRUCTURED LOGGING

Weak log:

```text
something went wrong
```

Better:

```text
2026-10-01T12:00:00Z level=ERROR component=api-check service=payments message="request timed out"
```

Useful fields may include:

- timestamp
- level
- component
- operation
- target
- request ID
- duration
- status
- error

Do not include secrets.

---

# 42. LOG LEVELS

Common levels include:

```text
DEBUG
INFO
WARNING
ERROR
CRITICAL
```

Exact semantics depend on the automation.

A useful distinction is:

```text
INFO
→ expected operational progress

WARNING
→ unexpected condition that does not prevent completion

ERROR
→ operation failed

DEBUG
→ detailed diagnostic evidence
```

---

# 43. DO NOT LOG SECRETS

Never log:

- passwords
- API tokens
- private keys
- session tokens
- authorization headers
- sensitive environment variables

This includes debug logging.

Observability must not become credential exposure.

---

# 44. SHELL ERROR HANDLING

Weak:

```bash
curl "$endpoint"
echo "API check complete"
```

If `curl` fails, what happens?

Better automation explicitly decides:

```text
Should failure stop the script?

Should the script continue checking other endpoints?

Should it retry?

Should it report partial failure?
```

Failure behavior should be designed, not accidental.

---

# 45. PARTIAL FAILURE

Suppose the automation checks ten services.

Nine succeed.

One times out.

Is the whole run:

```text
Success?
```

Maybe not.

Is it:

```text
Complete failure?
```

Maybe not.

This is a partial failure.

The automation should represent it clearly.

For example:

```text
Checked: 10
Healthy: 9
Failed: 1
Overall Status: DEGRADED
```

Then return an exit status appropriate to its caller contract.

---

# 46. RETRIES

Retries can improve resilience against transient failures.

But:

```text
Retry Everything Forever
```

is not resilience.

Before retrying, ask:

```text
Is the operation safe to repeat?

Is the failure likely transient?

Could repeating it create duplicates?

How long should we wait?

How many attempts are acceptable?
```

---

# 47. RETRIES AND IDEMPOTENCY

A read request is often safer to retry than a state-changing operation.

For a state-changing API call:

```text
Create Resource
```

a timeout creates uncertainty:

```text
Did the server create it before the connection failed?
```

Blindly retrying could create duplicates.

The API's semantics and idempotency mechanisms must be understood.

---

# 48. TIMEOUTS

Network automation should not wait forever.

Every external dependency should prompt the question:

```text
What is the maximum acceptable wait?
```

Timeouts apply to:

- API calls
- subprocesses
- network checks
- deployment waits
- health checks

No timeout can turn a temporary dependency problem into a permanently stuck automation job.

---

# 49. PYTHON FOR DEVOPS

Python provides stronger abstractions for automation that has outgrown simple Shell coordination.

A maintainable Python program often separates:

```text
Configuration
↓
Input Validation
↓
External Interaction
↓
Business Logic
↓
Reporting
↓
Exit Behavior
```

---

# 50. BASIC PYTHON PROGRAM STRUCTURE

```python
import logging


def main() -> int:
    logging.info("automation started")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

This pattern makes the program's final exit status explicit.

---

# 51. FILESYSTEM OPERATIONS

Python's standard library provides `pathlib` for filesystem path operations.

Example:

```python
from pathlib import Path

config_path = Path("config.json")

if not config_path.is_file():
    raise FileNotFoundError(f"configuration file not found: {config_path}")

content = config_path.read_text(encoding="utf-8")
```

This expresses intent more clearly than building filesystem paths through manual string concatenation.

---

# 52. DO NOT ASSUME THE CURRENT DIRECTORY

A common automation bug is assuming:

```text
Current Working Directory
=
Script Directory
```

That is not guaranteed.

A CI runner, systemd unit, cron job, or another user may invoke the program from a different directory.

If a file location is relative to the script itself, determine that intentionally.

For example:

```python
from pathlib import Path

SCRIPT_DIR = Path(__file__).resolve().parent
```

Then construct paths from the intended base.

---

# 53. FILE ERROR HANDLING

File operations can fail because:

- file missing
- permission denied
- path is a directory
- disk full
- filesystem read-only
- invalid encoding
- malformed content

Do not reduce all failures to:

```text
Could not read file.
```

Preserve useful evidence.

---

# 54. TEMPORARY FILES IN PYTHON

Python's `tempfile` module provides high-level interfaces including `TemporaryFile`, `NamedTemporaryFile`, and `TemporaryDirectory`, with context-manager support for cleanup. Python also warns against the old insecure `mktemp()` approach.

Example:

```python
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as temp_dir:
    report_path = Path(temp_dir) / "report.json"
    report_path.write_text("{}", encoding="utf-8")
```

Use temporary-resource APIs rather than inventing predictable names.

---

# 55. JSON

JSON is common in:

- APIs
- cloud tooling
- CLI output
- configuration
- reports

Python includes JSON support in its standard library.

```python
import json

payload = '{"service": "payments", "healthy": true}'

data = json.loads(payload)

print(data["service"])
```

---

# 56. JSON FILES

```python
import json
from pathlib import Path

config_path = Path("config.json")

with config_path.open("r", encoding="utf-8") as file:
    config = json.load(file)
```

Parsing success does not prove semantic validity.

A valid JSON file could still contain:

```json
{
  "timeout": -500
}
```

Syntax validation and configuration validation are different.

---

# 57. VALIDATE CONFIGURATION SEMANTICS

After loading configuration, validate required structure.

Example:

```python
def validate_config(config: dict) -> None:
    required_keys = {"api_url", "timeout_seconds"}

    missing = required_keys - config.keys()

    if missing:
        raise ValueError(
            f"missing required configuration keys: {sorted(missing)}"
        )

    if config["timeout_seconds"] <= 0:
        raise ValueError("timeout_seconds must be greater than zero")
```

Do not allow invalid configuration to travel deep into execution.

---

# 58. YAML

YAML is common in DevOps environments.

Examples include:

- Kubernetes
- CI/CD
- application configuration
- automation configuration

Unlike JSON, YAML parsing is not provided by Python's standard library.

A commonly used third-party package is PyYAML.

For data loading, use the library's safe loading interface rather than unsafe object-construction mechanisms when arbitrary object construction is not required.

Example:

```python
import yaml

with open("config.yaml", "r", encoding="utf-8") as file:
    config = yaml.safe_load(file)
```

Dependency versions should be controlled through the project's dependency-management process.

---

# 59. YAML IS NOT AUTOMATICALLY VALID CONFIGURATION

This:

```yaml
timeout_seconds: -10
retries: fifty
```

may be syntactically valid YAML.

It may still be invalid for the application.

Therefore:

```text
Parse
↓
Validate
↓
Use
```

---

# 60. ENVIRONMENT VARIABLES

Environment variables are commonly used for runtime configuration.

Python can access them through `os.environ`.

```python
import os

api_url = os.environ.get("API_URL")
```

If required:

```python
import os

api_url = os.environ.get("API_URL")

if not api_url:
    raise RuntimeError("API_URL is required")
```

---

# 61. REQUIRED VERSUS OPTIONAL ENVIRONMENT VARIABLES

Required:

```python
api_token = os.environ.get("API_TOKEN")

if not api_token:
    raise RuntimeError("API_TOKEN is required")
```

Optional with default:

```python
timeout_seconds = int(os.environ.get("TIMEOUT_SECONDS", "10"))
```

Defaults should be deliberate.

A default should not silently direct automation toward the wrong production target.

---

# 62. SECRETS IN ENVIRONMENT VARIABLES

Environment variables are frequently used to provide credentials to processes, but they are not automatically a complete secrets-management strategy.

Consider:

- who can inspect the process environment
- how CI masks values
- whether logs expose them
- how values are rotated
- where they are stored before injection

Never print an entire environment for debugging in production without considering secret exposure.

---

# 63. COMMAND-LINE ARGUMENTS

Python's `argparse` module can create command-line interfaces.

Example:

```python
import argparse


def parse_args() -> argparse.Namespace:
    parser = argparse.ArgumentParser(
        description="Inspect infrastructure and generate a report."
    )

    parser.add_argument(
        "--config",
        required=True,
        help="Path to the configuration file.",
    )

    parser.add_argument(
        "--output",
        required=True,
        help="Path to the generated report.",
    )

    return parser.parse_args()
```

A useful CLI explains how it should be invoked.

---

# 64. ARGUMENT VALIDATION

Do not accept arbitrary values when the allowed set is known.

```python
parser.add_argument(
    "--environment",
    choices=["development", "staging", "production"],
    required=True,
)
```

Reject invalid input before performing operational work.

---

# 65. BOOLEAN FLAGS

For flags:

```python
parser.add_argument(
    "--verbose",
    action="store_true",
)
```

Then:

```text
--verbose supplied
→ True

not supplied
→ False
```

Avoid requiring users to type ambiguous string values such as:

```text
--verbose true
```

unless the interface specifically requires that design.

---

# 66. SUBPROCESS EXECUTION

Python's `subprocess` module runs external programs.

For many ordinary use cases, Python documentation recommends `subprocess.run()`. It supports return-code inspection, captured output, explicit timeouts, and `check=True` for raising an exception on non-zero completion.

Example:

```python
import subprocess

result = subprocess.run(
    ["git", "status", "--short"],
    capture_output=True,
    text=True,
    timeout=10,
    check=True,
)

print(result.stdout)
```

---

# 67. USE ARGUMENT LISTS

Prefer:

```python
subprocess.run(
    ["kubectl", "get", "pods", "-n", namespace],
    check=True,
)
```

over building a shell command:

```python
f"kubectl get pods -n {namespace}"
```

and executing it through a shell unnecessarily.

Argument lists avoid an entire class of quoting and shell-injection problems.

---

# 68. `shell=True`

`shell=True` asks Python to execute through a shell.

That may be necessary for specific shell-language features.

It also changes the security and quoting model.

Do not enable it merely because it makes a command string easier to write.

When user-controlled or external data becomes part of a shell command, injection risk must be considered carefully.

---

# 69. SUBPROCESS FAILURE

With:

```python
check=True
```

a non-zero exit code raises `subprocess.CalledProcessError`.

Handle it when the program can add useful context.

```python
import logging
import subprocess

try:
    result = subprocess.run(
        ["example-cli", "status"],
        capture_output=True,
        text=True,
        timeout=10,
        check=True,
    )
except subprocess.CalledProcessError as exc:
    logging.error(
        "command failed returncode=%s stderr=%s",
        exc.returncode,
        exc.stderr.strip() if exc.stderr else "",
    )
    raise
```

Do not catch exceptions only to hide them.

---

# 70. SUBPROCESS TIMEOUTS

```python
try:
    subprocess.run(
        ["example-cli", "status"],
        timeout=10,
        check=True,
    )
except subprocess.TimeoutExpired:
    ...
```

Python documents that a timed-out child is killed and waited for before `TimeoutExpired` is re-raised, while also noting platform limitations around interrupting initial process creation.

The operational lesson is:

```text
External Command
→ Must Have Defined Waiting Behavior
```

when indefinite execution is unacceptable.

The automation must consider more than:

```text
Can I send GET?
```

It must understand:

```text
Authentication

Timeout

Status Code

Response Body

Pagination
```

# 72. HTTP CLIENT CHOICE

Python's standard library provides HTTP functionality.

Third-party clients such as `requests` are also common.

When using a third-party library:

- declare the dependency
- control its version according to project policy
- understand its timeout behavior
- test its failure modes

The important engineering concepts are independent of the library.

# 73. API REQUEST EXAMPLE

Using `requests`:

```python
import requests

response = requests.get(
    "https://api.example.com/v1/services",
    timeout=10,
)

response.raise_for_status()

data = response.json()
```

This is only a starting point.

Production automation must still consider authentication, malformed responses, pagination, rate limiting, and partial failure.

---

# 74. ALWAYS THINK ABOUT HTTP TIMEOUTS

Avoid relying on an indefinite default wait.

Define timeout behavior intentionally.

For example:

```python
response = requests.get(
    api_url,
    timeout=10,
)
```

The exact timeout value should come from operational requirements.

Ten seconds is an example, not a universal recommendation.

---

# 75. HTTP STATUS CODES

Do not assume:

```text
Received HTTP Response
=
Success
```

A server can respond with:

```text
401
403
404
429
500
503
```

The automation should understand which responses mean:

- invalid credentials
- insufficient permissions
- missing resource
- rate limiting
- server failure
- temporary unavailability

---

# 76. MALFORMED API RESPONSES

An endpoint may return:

```text
HTTP 200
```

but provide an unexpected response body.

Therefore:

```text
HTTP Success
↓
Parse
↓
Validate Expected Structure
```

Do not assume successful transport means valid application data.

---

# 77. API PAGINATION

Some APIs return only part of a collection.

If the API reports:

```text
100 results
```

that does not necessarily mean:

```text
Only 100 resources exist.
```

Understand:

- page size
- continuation tokens
- next-page links
- maximum page limits

Automation that ignores pagination may generate incomplete reports while appearing successful.

---

# 78. RATE LIMITS

APIs may limit request frequency.

Automation should recognize rate-limit responses and follow the API's documented behavior.

Do not create:

```text
Failure
↓
Immediate Retry
↓
Failure
↓
Immediate Retry
↓
Thousands of Requests
```

Retry strategy should include bounded attempts and appropriate waiting.

---

# 79. ERROR HANDLING IN PYTHON

Weak:

```python
try:
    perform_work()
except Exception:
    pass
```

This destroys evidence.

It can make failure look like success.

A stronger approach is:

```text
Catch an error only when:

You can add context,

recover,

translate it into a meaningful program result,

or perform necessary cleanup.
```

---

# 80. CATCH SPECIFIC EXCEPTIONS

Prefer:

```python
except FileNotFoundError:
```

or:

```python
except subprocess.TimeoutExpired:
```

when those are the expected failure modes.

A broad:

```python
except Exception:
```

may be appropriate at the outer application boundary for logging an unexpected failure before returning a non-zero status, but it should not silently swallow the error.

---

# 81. PRESERVE ERROR CONTEXT

Weak:

```python
except Exception:
    raise RuntimeError("failed")
```

Better:

```python
except OSError as exc:
    raise RuntimeError(
        f"unable to read configuration from {config_path}"
    ) from exc
```

Exception chaining preserves the underlying cause.

This helps troubleshooting.

---

# 82. PYTHON LOGGING

Python's standard library includes `logging`.

Example:

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s level=%(levelname)s message=%(message)s",
)

logging.info("automation started")
logging.warning("dependency response is slow")
logging.error("infrastructure check failed")
```

Operational logs should explain what happened without exposing secrets.

---

# 83. LOG CONTEXT

Weak:

```text
ERROR request failed
```

Better:

```text
ERROR operation=health_check service=payments endpoint=/health error=timeout
```

Context reduces investigation time.

---

# 84. DO NOT LOG EVERYTHING

More logs are not automatically better.

Avoid:

- secret values
- entire environment dumps
- enormous API responses
- sensitive customer data
- repeated meaningless messages

Logging should provide useful operational evidence.

---

# 85. STRUCTURED REPORT DATA

Instead of building reports entirely from strings, maintain structured results.

Example:

```python
result = {
    "service": "payments",
    "status": "healthy",
    "latency_ms": 42,
}
```

A list of these records can later produce:

- JSON
- terminal output
- HTML
- metrics
- summaries

Separate data collection from presentation where practical.

---

# 86. IDEMPOTENCY

An idempotent operation can be repeated without continually producing unintended additional effects.

Consider:

```text
Ensure directory exists
```

versus:

```text
Create another directory every time
```

The first can often be designed idempotently.

---

# 87. CREATE VERSUS ENSURE

Weak automation thinks:

```text
Create user.
```

Maintainable automation may think:

```text
Ensure required user exists with intended properties.
```

This changes the workflow:

```text
Inspect Current State
↓
Compare Desired State
↓
Change Only if Required
↓
Verify
```

---

# 88. IDEMPOTENCY IS CONTEXTUAL

Not every action is naturally idempotent.

For example:

```text
Send notification
```

may produce a new message each time.

```text
Create database backup
```

may intentionally create a new artifact each run.

The requirement is not:

```text
Everything must be idempotent.
```

It is:

```text
Understand repeat behavior.
```

---

# 89. REPEATABILITY

Repeatability means automation behaves predictably when executed under the same defined conditions.

Repeatability requires control over:

- inputs
- versions
- configuration
- dependencies
- environment assumptions

A script depending on:

```text
whatever tool version happens to be installed
```

may not be reliably repeatable.

---

# 90. OBSERVABILITY

Automation should make its behavior visible.

At minimum, operators should be able to answer:

```text
Did it start?

What target did it operate on?

What stage is it in?

What succeeded?

What failed?

How long did it take?

What was the final result?
```

---

# 91. AUTOMATION METADATA

A useful run may record:

```text
run_id

start_time

end_time

target

environment

operation

result

failure_count
```

This becomes increasingly valuable when automation runs unattended.

---

# 92. TESTABILITY

Automation should be designed so important logic can be tested without performing real destructive operations.

For example, separate:

```text
Determine what should happen
```

from:

```text
Perform the real API change
```

This allows logic to be tested independently.

---

# 93. PURE LOGIC VERSUS SIDE EFFECTS

Consider:

```python
def should_alert(cpu_percent: float, threshold: float) -> bool:
    return cpu_percent >= threshold
```

This is easy to test.

Compare with a function that:

- reads CPU
- sends HTTP request
- writes a file
- sends an email
- changes configuration

all at once.

Separating logic from side effects improves testing.

---

# 94. DRY-RUN DESIGN

Some operational automation benefits from a dry-run mode.

Conceptually:

```text
Real Mode
→ perform change

Dry Run
→ calculate and display intended change
```

But a dry run must be honest.

If it cannot accurately predict an operation, document the limitation.

Do not display:

```text
Everything will succeed.
```

when the real external operation has not occurred.

---

# 95. FAILURE HANDLING

Design failure behavior before production use.

For each operation ask:

```text
What can fail?

How will failure be detected?

What work has already completed?

Can execution continue?

Should execution stop?

Can completed work be reversed?

What evidence should be preserved?
```

---

# 96. FAIL FAST VERSUS CONTINUE

Neither strategy is universally correct.

For a deployment:

```text
Authentication failure
```

may justify immediate termination.

For a report checking 100 independent services:

```text
One service unreachable
```

may justify continuing and recording a partial failure.

Failure policy depends on task semantics.

---

# 97. ROLLBACK AWARENESS

Automation that changes state should understand recovery.

Before:

```text
Modify
```

ask:

```text
What is the previous state?

Can it be restored?

Is the operation reversible?

Is data involved?

Would rollback itself be dangerous?
```

---

# 98. ROLLBACK IS NOT ALWAYS AUTOMATIC

Automatically reversing every failed operation can create additional damage.

Suppose:

```text
Step 1 succeeds
Step 2 succeeds
Step 3 times out
```

The timeout may mean:

```text
Step 3 failed
```

or:

```text
Step 3 succeeded remotely but response was lost.
```

Blind rollback may now act on uncertain state.

Verification is required.

---

# 99. TRANSACTION-LIKE THINKING

Infrastructure automation often cannot provide true database-style transactions.

But the engineer can still think in stages:

```text
Preconditions
↓
Action A
↓
Verify A
↓
Action B
↓
Verify B
↓
Action C
↓
Verify C
```

If B fails, know exactly which earlier state changes occurred.

---

# 100. CHECKPOINTS

Long automation can record checkpoints.

For example:

```text
Configuration loaded
[complete]

API inventory fetched
[complete]

Infrastructure checks
[partial]

Report generated
[not started]
```

This makes partial failure understandable.

---

# 101. SAFE DEFAULTS

Automation should avoid dangerous defaults.

Bad:

```text
If environment is missing:
default to production
```

Safer:

```text
If environment is missing:
fail validation
```

Production should generally require explicit intent.

---

# 102. CONFIRMATION VERSUS NON-INTERACTIVE AUTOMATION

Interactive scripts may ask:

```text
Continue? [y/N]
```

But CI/CD cannot reliably answer interactive prompts.

For unattended automation, design explicit flags and controls.

Example concept:

```text
--environment production
--apply
```

Production safety should not depend solely on someone noticing a prompt.

---

# 103. AUTHENTICATION AND AUTHORIZATION

Automation should use only the permissions it requires.

If automation only reads infrastructure inventory, it should not automatically receive permission to delete infrastructure.

Use:

```text
Least Required Authority
```

because:

```text
Automation Bug
×
Excessive Permission
=
Larger Blast Radius
```

---

# 104. CREDENTIAL LIFETIME

Prefer controlled credential mechanisms appropriate to the platform.

Where supported, short-lived workload identities can reduce risk compared with permanent credentials embedded in scripts.

Never hard-code:

```python
API_TOKEN = "real-production-secret"
```

into source code.

---

# 105. CONFIGURATION VERSUS CODE

Do not bury every environment-specific value inside code.

Weak:

```python
api_url = "https://production.example.internal"
timeout = 10
region = "example-region"
```

Better separation may use:

```text
Code
+
Configuration
+
Runtime Credentials
```

This makes the automation reusable without editing source for every environment.

---

# 106. CONFIGURATION PRECEDENCE

If automation accepts configuration from multiple places, define precedence.

For example:

```text
Command-Line Argument
↓
Environment Variable
↓
Configuration File
↓
Safe Default
```

That is only an example.

The important point is that precedence must be documented.

Otherwise an engineer may change a configuration file and wonder why an environment variable continues to override it.

---

# 107. REPORT GENERATION

A useful operational report should distinguish:

```text
Checked

Passed

Failed

Skipped

Unknown
```

Do not turn:

```text
Could not check resource
```

into:

```text
Resource healthy
```

Unknown is a legitimate operational state.

---

# 108. UNKNOWN IS NOT HEALTHY

Suppose an API call times out.

The automation cannot conclude:

```text
Service is down.
```

It may only know:

```text
Health could not be determined because the request timed out.
```

Similarly, it cannot conclude:

```text
Service is healthy.
```

Evidence boundaries matter.

# 113. LOAD CONFIGURATION

```python
from pathlib import Path

import yaml


def load_config(path: Path) -> dict:
    with path.open("r", encoding="utf-8") as file:
        data = yaml.safe_load(file)

    if not isinstance(data, dict):
        raise ValueError("configuration root must be a mapping")

    return data
```

Expected:

```text
Valid mapping
→ returned

Missing file
→ file error

Malformed YAML
→ parser error

Wrong top-level type
→ validation error
```

# 114. VALIDATE CONFIGURATION

```python
def validate_config(config: dict) -> None:
    if "api" not in config:
        raise ValueError("missing api configuration")

    if "url" not in config["api"]:
        raise ValueError("missing api.url")

    timeout = config["api"].get("timeout_seconds")

    if not isinstance(timeout, int) or timeout <= 0:
        raise ValueError(
            "api.timeout_seconds must be a positive integer"
        )
```

Validation occurs before network operations.

# 115. QUERY THE API

# 116. CHECK FILESYSTEM STATE

Python's `shutil.disk_usage()` can inspect filesystem capacity.

```python
import shutil
from pathlib import Path


def check_filesystem(path: Path) -> dict:
    usage = shutil.disk_usage(path)

    free_percent = (usage.free / usage.total) * 100

    return {
        "path": str(path),
        "total_bytes": usage.total,
        "free_bytes": usage.free,
        "free_percent": round(free_percent, 2),
    }
```

This demonstrates why Python is useful when structured calculations are required.

The Python automation should detect `TimeoutExpired` and return controlled failure evidence.

Write intermediate output.

Exit normally.

Verify that cleanup occurs after the context exits. Python documents `TemporaryDirectory` as a high-level context-managed temporary directory facility.

Then discuss what would happen under abrupt process termination.

# 140. FAILURE-INJECTION MATRIX

Create a test matrix:

| Failure | Expected Behavior |
|---|---|
| Missing config | Fail before work |
| Invalid config | Fail before work |
| API unreachable | Record unavailable result |
| API timeout | Stop waiting at configured timeout |
| HTTP 500 | Record server-side failure |
| Invalid JSON | Record parsing failure |
| Wrong JSON structure | Record contract failure |
| Subprocess non-zero | Capture return code and stderr |
| Subprocess timeout | Terminate waiting and record failure |
| Report path unwritable | Report generation fails visibly |
| One independent check fails | Preserve other results |
| Concurrent execution | No uncontrolled collision |

The automation is not complete until failure behavior has been tested.

# 141. TESTING PYTHON LOGIC

Use automated tests for logic that can be isolated.

Example:

```python
def test_low_free_space_fails():
    assert evaluate_free_space(5.0, 10.0) == "FAIL"


def test_sufficient_free_space_passes():
    assert evaluate_free_space(20.0, 10.0) == "PASS"
```

The specific testing framework depends on the project.

The principle is:

```text
Critical Decision Logic
→ Testable Without Production
```

# 174. AUTOMATION AND PRODUCTION SAFETY

Before production mutation, verify:

```text

Requested Action

Required Preconditions
```

Where risk warrants it, require stronger controls outside the script as well:

- approvals
- protected pipelines
- scoped credentials
- environment protections

Script-level checks are only one layer.

---

# 175. CHECK THEN ACT RACE CONDITIONS

This pattern can be unsafe:

```text
Check state
↓
Time passes
↓
Act assuming state did not change
```

Another process may modify the resource between the check and action.

This is a time-of-check/time-of-use problem.

Where platforms provide atomic conditional operations, version checks, locks, or optimistic concurrency controls, use them when required.

---

# 176. DO NOT BUILD YOUR OWN LOCKING CASUALLY

Concurrency control can become complex.

Before inventing a lock file, understand:

- stale locks
- process crashes
- shared filesystems
- multiple hosts
- lock ownership
- timeout behavior

Use established platform mechanisms where appropriate.

---

# 177. REPORT PARTIAL COMPLETION

If automation modifies five resources and fails after three, logs should not merely say:

```text
FAILED
```

They should make it possible to determine:

```text
Resource A
→ changed

Resource B
→ changed

Resource C
→ changed

Resource D
→ failed

Resource E
→ not attempted
```

This is essential for recovery.

---

# 178. DO NOT HIDE FAILURES BEHIND SUCCESS MESSAGES

Bad:

```bash
perform_change || true
echo "Deployment completed successfully"
```

This converts failure into apparent success.

Suppress an error only when failure is explicitly expected and handled.

---

# 179. VERIFY AFTER CHANGE

Automation should not assume:

```text
Command returned 0
```

means:

```text
Desired state exists.
```

When important, perform independent verification.

Example:

```text
Create Resource
↓
API Returns Success
↓
Query Resource
↓
Verify Expected State
```

---

# 180. ACTION VERSUS VERIFICATION

Keep these conceptually separate:

```text
Action:
Request application deployment.

Verification:
Confirm expected version becomes healthy.
```

This is stronger than:

```text
Deployment command returned 0.
```

# 181. OBSERVABILITY OF DURATION

- degraded API
- overloaded infrastructure
- DNS problems
- retries
- rate limiting
- filesystem problems

Recording operation duration can provide useful evidence.

# 182. CORRELATION IDENTIFIERS

For automation making multiple external requests, a run identifier can help correlate logs.

Example:

```text

```

Every log from that execution can include the same identifier.

This becomes useful when many executions overlap.

---

# 183. MACHINE OUTPUT VERSUS HUMAN OUTPUT

Automation may need both.

Human:

```text
3 of 4 infrastructure checks passed.
1 check could not be completed.
```

Machine:

```json
{
  "passed": 3,
  "failed": 0,
  "unknown": 1
}
```

Design output according to its consumers.

---

# 184. EXIT CODES ARE AN API

If CI/CD calls a script, the script's exit codes form part of its interface.

Changing:

```text
3
from "partial failure"
```

to:

```text
3
meaning "invalid configuration"
```

can break calling automation.

Document and maintain interfaces deliberately.

# 185. AUTOMATION INTERFACES

Automation can expose contracts through:

- command-line arguments
- environment variables
- configuration schemas
- output files
- JSON
- stdout
- stderr
- exit codes

These are interfaces.

Treat them deliberately.

---

# 186. BACKWARD COMPATIBILITY

Suppose version 1 expects:

```text
--environment
```

and version 2 silently renames it:

```text
--target
```

Existing pipelines may fail.

Automation changes can have consumers just like application APIs.

---

# 187. DEPRECATION CONCEPT

When automation is widely consumed, interface changes may require a transition period.

For example:

```text
Old option supported with warning
↓
Consumers migrate
↓
Old option removed in later release
```

This is more mature than breaking every caller unexpectedly.

---

# 188. PERFORMANCE AWARENESS

Automation itself can overload systems.

A script that queries:

```text
10,000 resources
```

one request at a time may take too long.

A script that launches:

```text
10,000 concurrent requests
```

may overload the API.

Performance and concurrency must be controlled.

---

# 189. BOUNDED CONCURRENCY

If concurrency is needed, limit it.

Think:

```text
Controlled Worker Count
```

rather than:

```text
Unlimited Parallelism
```

At Mid-Level, the learner should recognize this design requirement even if advanced concurrent-programming internals are outside the scope of this Part.

---

# 190. BATCHING

Some APIs support batch operations.

Instead of:

```text
1 request × 5,000 resources
```

a supported batch API may reduce overhead.

But batching changes failure behavior:

```text
What if 49 operations succeed and 1 fails?
```

Understand the API contract.

---

# 191. CACHING AWARENESS

Repeatedly querying information that rarely changes may waste API capacity.

But caching introduces:

- staleness
- invalidation
- consistency questions

Do not add caching automatically.

Add it only when there is a demonstrated need and clear freshness requirement.

- response was truncated

without requiring the original author to explain every step.

---

# 225. SHELL COMPLETION STANDARD

The learner can write Shell automation that demonstrates:

- deliberate interpreter choice
- defensive scripting
- input validation
- precondition validation
- appropriate strict-mode use
- correct quoting
- reusable functions
- meaningful stdout and stderr
- traps where appropriate
- safe temporary resources
- concurrency awareness
- useful logs
- meaningful exit status

The learner does not treat:

```bash
set -e
```

as a substitute for understanding failure behavior.

The learner can use Python for:

- filesystem operations
- subprocess execution
- HTTP APIs
- JSON

- environment variables
- error handling
- logging
- command-line arguments

The learner can structure the program so that:

```text
Configuration

External Interaction

Logic

Reporting

Exit Behavior
```

# 229. FAILURE-HANDLING COMPLETION STANDARD

The learner can answer:

```text
What happens when:

configuration is missing?

only half the work completes?

```

The answers must exist in code and tests, not only documentation.

# 231. TESTABILITY COMPLETION STANDARD

# 232. ROLLBACK-AWARENESS COMPLETION STANDARD

Before state-changing automation executes, the learner can explain:

```text
What changes?
```

# 233. AI COMPLETION STANDARD

The learner can use AI to assist with automation while maintaining human engineering responsibility.

# 234. MID-LEVEL BOUNDARY

This Part does not require advanced software-platform engineering.

The learner is not yet expected to design:

- enterprise automation frameworks
- organization-wide developer platforms
- complex distributed job schedulers
- large event-driven automation platforms
- advanced workflow engines
- autonomous production agents
- sophisticated distributed locking systems
- enterprise policy engines

Those belong to later engineering scope.

At Mid-Level, the requirement is:

```text
Small-to-Medium Operational Automation
+
Maintainable Design
+
Safe Failure Behavior
+
Evidence
+
Testing
+
Operational Ownership
```

---

# 235. FINAL ENGINEERING MODEL

A Junior engineer may begin automation with:

```text
Which commands do I need?
```

A Mid-Level engineer begins with:

```text
What problem am I solving?
↓
What is the correct automation mechanism?
↓
What are the inputs?
↓
What assumptions exist?
↓
What can fail?
↓
What state can change?
↓
How will success be verified?
↓
How will failure be observed?
↓
Can the operation be repeated safely?
↓
How will partial completion be handled?
↓
How will another engineer maintain it?
```

That change in thinking is the purpose of this Part.

# 236. COMPLETION STANDARD

You have completed this Part when you can design small maintainable operational automation rather than simply collecting commands into scripts.

You should be able to look at a requirement and decide whether it belongs in:

```text
Shell
```

or:

```text
Python
```

or:

```text
Configuration Management
```

or:

```text
Infrastructure as Code
```

or:

```text
CI/CD
```

or:

```text
A Platform API Workflow.
```

You should be able to write Shell automation that assumes commands can fail, input can be wrong, files can disappear, concurrent execution can occur, and cleanup may be required.

You should be able to write Python automation that reads configuration, validates it, consumes APIs, processes structured data, executes subprocesses safely, handles errors, produces logs, accepts command-line arguments, and returns meaningful exit codes.

You should understand:

```text
A successful command
≠
a verified system state.
```

You should understand:

```text
Valid JSON
≠
valid application data.
```

You should understand:

```text
HTTP response
≠
successful API operation.
```

You should understand:

```text
Retry
≠
safe recovery.
```

You should understand:

```text
Dry run
≠
guaranteed real execution.
```

You should understand:

```text
Strict Shell Mode
≠
automatic correctness.
```

You should understand:

```text
AI-generated code
≠
verified automation.
```

You should understand:

```text
Works on my machine
≠
repeatable operational automation.
```

The final workflow from this Part is:

```text
Understand the Problem
↓
Choose the Correct Automation Mechanism
↓
Define Inputs and Outputs
↓
Define Preconditions
↓
Define Failure Modes
↓
Implement Small Focused Components
↓
Validate Inputs
↓
Use Least Required Authority
↓
Apply Timeouts
↓
Handle Errors Deliberately
↓
Preserve Partial Results
↓
Produce Useful Logs
↓
Return Meaningful Exit Status
↓
Test the Happy Path
↓
Inject Failures
↓
Test Repeated Execution
↓
Test Partial Failure
↓
Review Security
↓
Verify Real Result
↓
Document Operation and Recovery
```

The defining Mid-Level question is no longer:

```text
Can I automate this command?
```

It is:

```text
Can I build automation that another engineer can understand,
run repeatedly, troubleshoot when it fails, verify when it succeeds,
and trust within its defined operational boundaries?
```

When the answer can be demonstrated with evidence, the script has begun to become engineering automation.
