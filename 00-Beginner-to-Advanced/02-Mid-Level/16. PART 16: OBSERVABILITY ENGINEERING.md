# PART 16: OBSERVABILITY ENGINEERING

## Goal

Move from passively reading logs, metrics, and dashboards to deliberately designing observability that helps engineers understand service behavior, detect user-impacting problems, investigate failures, validate deployments, and make production decisions from evidence.

At this level, observability is not:

```text
Install monitoring tools
↓
Collect everything
↓
Create many dashboards
↓
Create many alerts
```

The engineering model is:

```text
Service
↓
Produces Telemetry
├── Metrics
├── Logs
└── Traces
↓
Collection and Processing
↓
Storage / Observability Backend
↓
Queries
↓
Dashboards / Alerts / Investigation
↓
Operational Understanding
↓
Engineering Action
```

The objective is not maximum telemetry.

The objective is **useful evidence**.

A well-observed service should help answer questions such as:

```text
Is the service available?

Are users experiencing failures?

Are requests becoming slower?

How much traffic is arriving?

Is the service approaching a resource limit?

Which endpoint is failing?

Which application version is affected?

Did the problem begin after a deployment?

Which downstream dependency is slow?

Which request experienced the failure?

Where did that request spend its time?

Is the problem isolated to one instance, region, namespace,
dependency, route, or application version?

Is the condition severe enough to wake someone up?

What evidence supports the current hypothesis?
```

Observability engineering therefore connects:

```text
Application Design
+
Instrumentation
+
Telemetry
+
Service Reliability
+
Incident Response
+
Operational Decision-Making
```

---

# 1. MONITORING AND OBSERVABILITY

The terms monitoring and observability are related, but they are useful to distinguish conceptually.

Monitoring commonly focuses on known questions.

For example:

```text
Is CPU utilization above 90%?

Is the application returning errors?

Are Pods restarting?

Is disk space low?
```

Observability becomes especially valuable when you need to investigate questions that were not completely predicted when the system was instrumented.

For example:

```text
Why are checkout requests slow only for one dependency path?

Why did latency increase without CPU increasing?

Why are only requests handled by one application version failing?

Why is the service healthy from Kubernetes' perspective
while users are receiving errors?
```

The goal is not to replace monitoring.

A mature production system needs both:

```text
Known Conditions
→ Monitoring and Alerts

Unknown or Complex Conditions
→ Investigation using rich telemetry
```

---

# 2. OBSERVABILITY STARTS WITH QUESTIONS

Do not begin with:

```text
Which graphs should we create?
```

Begin with:

```text
What must an engineer be able to determine about this service?
```

For an HTTP service, useful operational questions might include:

```text
Is it receiving traffic?

How many requests?

Which routes receive traffic?

How many requests fail?

What kind of failures?

How long do requests take?

Which dependency is contributing to latency?

Are resources approaching exhaustion?

Which version is running?

Did behavior change after deployment?
```

Only then decide which telemetry is required.

The design flow is:

```text
Operational Question
↓
Required Evidence
↓
Telemetry Signal
↓
Instrumentation
↓
Collection
↓
Query
↓
Dashboard / Alert / Investigation
```

---

# 3. TELEMETRY SIGNALS

The three signals emphasized in this Part are:

```text
Metrics

Logs

Traces
```

Each answers different kinds of questions.

## Metrics

Metrics are useful for aggregate behavior.

Examples:

```text
Requests per second

Error rate

Latency distribution

CPU utilization

Memory usage

Queue depth
```

They answer questions such as:

> Is something changing across the service?

## Logs

Logs describe events.

Examples:

```text
Application started

Authentication failed

Request rejected

Dependency timed out

Configuration loaded

Graceful shutdown started
```

They answer questions such as:

> What happened around this time?

## Traces

Traces describe the path and timing of work through a system.

They answer questions such as:

> Where did this request go, and where did it spend its time?

A useful relationship is:

```text
Metric
↓
Something is wrong.

Log
↓
What events occurred?

Trace
↓
Where did this request go?
```

No signal completely replaces the others.

---

# 4. OBSERVABILITY IS NOT THE OBSERVABILITY TOOL

Prometheus is not observability.

Grafana is not observability.

OpenTelemetry is not observability.

A log backend is not observability.

A tracing backend is not observability.

These are technologies that can participate in an observability system.

The actual capability is:

```text
Useful Instrumentation
+
Reliable Collection
+
Appropriate Storage
+
Useful Queries
+
Good Dashboards
+
Actionable Alerts
+
Operational Practice
```

A poorly instrumented service remains difficult to understand even when expensive observability software surrounds it.

---

# 5. WHITE-BOX AND BLACK-BOX OBSERVATION

There are two important perspectives.

## White-Box Observation

White-box signals come from inside the system.

Examples:

```text
Application request count

Database connection pool usage

Queue depth

Internal errors

Memory allocation

Worker count
```

The system tells you about its internal state.

## Black-Box Observation

Black-box monitoring observes the service externally.

For example:

```text
Client
↓
HTTPS Request
↓
Application Endpoint
↓
Expected Response?
```

This tests externally visible behavior.

The distinction matters because:

```text
Internal Metrics Healthy
```

does not always mean:

```text
Users Can Use the Service
```

A production service benefits from both perspectives.

---

# 6. THE FOUR GOLDEN SIGNALS

A widely useful starting model for user-facing services is:

```text
Latency

Traffic

Errors

Saturation
```

These are often called the **four golden signals**.

They provide a practical service-level view.

They do not represent every metric a system will ever need.

They provide a strong starting point.

---

# 7. LATENCY

Latency measures how long operations take.

For an HTTP service:

```text
Request Received
↓
Application Processing
↓
Response Sent
```

The elapsed duration is request latency.

But:

```text
Average Latency
```

alone is often insufficient.

Imagine:

```text
99 requests = 100 ms
1 request   = 10 seconds
```

The average hides important tail behavior.

You need to understand distributions.

---

# 8. LATENCY DISTRIBUTIONS

Useful latency questions include:

```text
What is typical latency?

What latency do most users experience?

How slow are the slowest meaningful group of requests?

Which endpoint is slow?

Did latency change after deployment?

Are successful and failed requests behaving differently?
```

Common percentile concepts include:

```text
p50

p90

p95

p99
```

For example:

```text
p50 = 120 ms
```

means approximately half of observed requests completed at or below that value within the relevant measurement context.

A high percentile can expose tail latency hidden by averages.

---

# 9. DO NOT MIX SUCCESS AND FAILURE LATENCY CARELESSLY

Suppose a database dependency is unavailable.

The application may immediately return:

```text
HTTP 500
```

in:

```text
5 ms
```

Meanwhile successful requests normally take:

```text
200 ms
```

If all requests are aggregated carelessly, increased failures could make apparent average latency decrease.

That would be misleading.

Therefore distinguish:

```text
Successful Request Latency

Failed Request Latency
```

where appropriate.

---

# 10. TRAFFIC

Traffic represents demand placed on the service.

For an HTTP service:

```text
Requests per second
```

is a common traffic measurement.

Other systems may measure:

```text
Messages consumed per second

Jobs processed per minute

Transactions per second

Bytes transferred

Queries per second
```

Traffic gives context to other signals.

For example:

```text
CPU = 70%
```

means something different at:

```text
100 requests/second
```

than at:

```text
10 requests/second.
```

---

# 11. ERRORS

Errors measure unsuccessful work.

For HTTP services, errors may include:

```text
5xx responses

Selected 4xx conditions

Application exceptions

Dependency failures

Timeouts

Rejected requests
```

But error semantics depend on the service.

A `404` might be:

```text
Expected user behavior
```

or:

```text
Evidence of a broken route after deployment.
```

Instrumentation must reflect service semantics.

---

# 12. ERROR RATE

Raw error count can be misleading.

Suppose:

```text
10 errors
```

occur.

If total traffic is:

```text
20 requests
```

that is severe.

If total traffic is:

```text
10,000,000 requests
```

the interpretation is different.

A useful concept is:

```text
Error Rate
=
Failed Requests / Total Requests
```

The exact query depends on the telemetry system.

The engineering principle does not.

---

# 13. SATURATION

Saturation asks:

> How close is the system to a limiting resource?

Possible signals include:

```text
CPU pressure

Memory pressure

Disk capacity

Disk I/O pressure

Network capacity

Thread pool exhaustion

Connection pool exhaustion

Queue depth

Worker exhaustion
```

A service may become unhealthy before a resource reaches an apparent 100%.

Therefore saturation must be understood in service context.

---

# 14. INFRASTRUCTURE METRICS

Infrastructure metrics describe the environment supporting the application.

Examples include:

```text
CPU

Memory

Disk

Network

Filesystem

Node health

Container resource usage

Pod resource usage
```

These signals are valuable.

But infrastructure health alone does not prove application health.

For example:

```text
CPU normal
Memory normal
Disk normal
Pods Running
```

while:

```text
All checkout requests return HTTP 500.
```

Therefore infrastructure metrics should support service-level observation rather than replace it.

---

# 15. APPLICATION METRICS

Application metrics expose behavior known only by the application.

Examples:

```text
Requests processed

Authentication failures

Orders processed

Queue operations

Cache hits

Cache misses

Database query failures

Worker activity

Dependency calls
```

These metrics allow investigation beyond host or container state.

---

# 16. BUSINESS-RELEVANT SERVICE METRICS

Some service behaviors are important enough to measure because they reflect whether the application is performing its intended function.

Examples might include:

```text
Successful transactions

Failed transactions

Jobs completed

Messages processed

Payments authorized

Files processed
```

Do not confuse business analytics with operational monitoring.

But carefully selected domain metrics can reveal failures that infrastructure signals cannot.

For example:

```text
HTTP 200 Rate
Normal
```

while:

```text
Orders Successfully Completed
0
```

may indicate a serious application problem.

---

# 17. REQUEST METRICS

For an HTTP service, useful request dimensions may include:

```text
Method

Route

Status category

Service

Environment
```

For example:

```text
GET /health
200

GET /api/products
200

POST /api/orders
500
```

This allows investigation by operation.

But dimensions must be selected carefully.

---

# 18. METRIC TYPES

Metrics commonly model different kinds of measurements.

Important concepts include:

```text
Counter

Gauge

Histogram
```

The exact instrumentation API depends on the telemetry library.

Understanding the semantic difference is more important than memorizing one client library.

---

# 19. COUNTERS

A counter represents a value that accumulates over time.

Examples:

```text
Total requests

Total errors

Total jobs completed

Total bytes processed
```

Conceptually:

```text
0
↓
1
↓
2
↓
3
↓
4
```

Counters normally increase until the process restarts or the underlying series is otherwise reset.

You commonly derive a rate over a time window rather than treating the raw cumulative value as current traffic.

---

# 20. GAUGES

A gauge represents a value that can move up or down.

Examples:

```text
Current queue depth

Active workers

Current memory usage

Current temperature

Current in-flight requests
```

Conceptually:

```text
5
↓
9
↓
4
↓
11
↓
3
```

Use a gauge for current state where both increases and decreases are meaningful.

---

# 21. HISTOGRAMS

Histograms are useful for distributions such as:

```text
Request duration

Response size

Job duration
```

Instead of storing only:

```text
Average Request Duration
```

a histogram preserves aggregated distribution information that can support questions about:

```text
Percentiles

Latency thresholds

Distribution changes
```

Histogram design affects the questions you can answer.

Do not choose buckets or boundaries blindly.

---

# 22. METRIC NAMING

Metric names should communicate meaning clearly.

For example:

```text
http_requests
```

is less explicit than a convention that clearly indicates:

```text
what is measured

whether it is cumulative

which unit applies
```

Where Prometheus conventions are used, counters commonly use a `_total` suffix and units are represented consistently in names where appropriate.

For example:

```text
http_requests_total

http_request_duration_seconds
```

The important principle is consistency.

---

# 23. UNITS MATTER

Avoid ambiguous measurements such as:

```text
request_latency = 500
```

500 what?

```text
milliseconds?

microseconds?

seconds?
```

Use a defined unit.

A consistent observability system avoids requiring engineers to guess measurement semantics during incidents.

---

# 24. LABELS AND DIMENSIONS

Labels allow a metric to be separated by meaningful dimensions.

For example:

```text
http_requests_total{
    method="GET",
    route="/api/products",
    status_code="200"
}
```

This can answer:

```text
How many successful GET requests reached /api/products?
```

Labels are powerful.

They are also one of the easiest ways to damage a metrics system.

---

# 25. CARDINALITY

Every unique combination of metric labels can create another time series.

Suppose:

```text
method:
GET, POST
```

and:

```text
status:
200, 400, 404, 500
```

and:

```text
route:
5 values
```

The potential combinations grow.

Now imagine adding:

```text
user_id
```

with:

```text
2,000,000 users.
```

The number of potential series can explode.

This is a **cardinality problem**.

---

# 26. HIGH-CARDINALITY LABELS

Avoid unbounded or extremely high-cardinality values in metrics unless the observability architecture explicitly supports and requires them.

Dangerous examples include:

```text
user_id

email_address

request_id

trace_id

full URL containing identifiers

random UUID

session_id
```

For example, avoid:

```text
path="/users/483928/orders/98234"
```

as an unbounded metric label.

Prefer a normalized route such as:

```text
route="/users/{user_id}/orders/{order_id}"
```

where the instrumentation framework provides that concept correctly.

---

# 27. METRICS ARE AGGREGATED EVIDENCE

Metrics are excellent for questions such as:

```text
How many?

How often?

How fast?

What percentage?

Is it increasing?

Is it approaching a limit?
```

They are less suitable for:

```text
What exactly happened to request 8f20...?
```

That is where logs and traces become more useful.

---

# 28. LOGS

A log records an event.

A useful application log should communicate enough context for an engineer to understand what occurred.

A weak log:

```text
Error happened
```

A more useful event might capture:

```text
timestamp

severity

service

event

operation

error type

request or trace context
```

without exposing sensitive information.

---

# 29. STRUCTURED LOGGING

Unstructured log:

```text
Payment request failed for order 19283 because database timed out
```

Structured representation:

```json
{
  "timestamp": "2026-10-03T08:15:30Z",
  "severity": "ERROR",
  "service": "orders-api",
  "event": "order_processing_failed",
  "order_reference": "redacted-or-safe-reference",
  "error_type": "dependency_timeout"
}
```

Structured logs make machine parsing and consistent querying easier.

---

# 30. STRUCTURED DOES NOT MEAN JSON ONLY

JSON is a common structured logging representation.

The deeper requirement is that important fields have stable, machine-readable semantics.

For example:

```text
severity
service
environment
event
trace_id
```

should not require fragile text parsing every time they are queried.

---

# 31. TIMESTAMPS

Logs need timestamps.

In distributed systems, timestamp consistency matters.

Use an explicit, unambiguous time representation.

UTC is commonly useful for centralized systems.

For example:

```text
2026-10-03T08:15:30Z
```

rather than:

```text
10/03/26 8:15
```

where timezone and date interpretation may be ambiguous.

---

# 32. CLOCKS AND DISTRIBUTED SYSTEMS

Timestamps are useful but should not be treated as perfect global ordering.

Different machines can experience clock skew.

Therefore:

```text
Log A timestamp slightly before Log B
```

does not always prove the causal relationship you think it does.

Distributed tracing provides stronger request relationship information through propagated context.

Time synchronization still matters operationally.

---

# 33. LOG SEVERITY

A common severity model may include concepts such as:

```text
DEBUG

INFO

WARN

ERROR
```

Exact levels depend on logging framework.

The important requirement is consistent semantics.

For example:

```text
INFO
```

should not mean:

```text
Normal request
```

in one component and:

```text
Potential outage
```

in another without a deliberate convention.

---

# 34. DEBUG LOGS

Debug logs are useful for detailed investigation.

But enabling extremely verbose debug logging in production can create:

```text
High storage usage

Higher ingestion cost

Performance overhead

Sensitive-data exposure

Operational noise
```

Debug logging should be controlled deliberately.

---

# 35. INFO LOGS

Info-level events may describe normal but operationally useful lifecycle events.

Examples:

```text
Application started

Configuration loaded

Worker started

Graceful shutdown initiated

Background job completed
```

Do not log every insignificant operation merely because storage exists.

---

# 36. WARNING LOGS

Warnings indicate abnormal or potentially problematic conditions that do not necessarily mean the operation failed.

Examples:

```text
Retry performed

Dependency response unusually slow

Deprecated configuration detected

Queue approaching expected limit
```

Warnings should remain meaningful.

If everything is a warning, warning loses meaning.

---

# 37. ERROR LOGS

Error logs should represent meaningful failed operations or serious conditions.

Useful context may include:

```text
operation

error type

dependency

safe identifiers

trace ID

retry state
```

Avoid repeatedly logging the same error at every layer without purpose.

Otherwise one failure can generate dozens of nearly identical error events.

---

# 38. LOG EVENTS, NOT STORIES

Prefer stable event semantics.

For example:

```text
event="dependency_timeout"
dependency="inventory-api"
```

rather than relying entirely on:

```text
"Something bad happened while contacting inventory and it took too long."
```

Human-readable messages can still exist.

Structured fields make querying reliable.

---

# 39. CORRELATION IDS

A correlation identifier helps associate related events.

For example:

```text
Request enters Service A
correlation_id=abc123
```

Then:

```text
Service A log
correlation_id=abc123

Service B log
correlation_id=abc123

Service C log
correlation_id=abc123
```

An engineer can search for:

```text
abc123
```

and retrieve related events.

---

# 40. CORRELATION ID AND TRACE ID

These concepts may overlap in purpose but should not be casually treated as identical.

A trace ID identifies a distributed trace within a tracing system.

An application may also maintain another business or request correlation identifier.

The important rule is:

> Define what each identifier means and propagate it consistently.

Do not create five different identifiers with unclear ownership.

---

# 41. DO NOT USE REQUEST IDS AS METRIC LABELS

A request ID is useful in:

```text
Logs

Traces
```

It is generally dangerous as a Prometheus-style metric label because every request may create another unique series.

This distinction is important:

```text
High-cardinality request identity
→ Logs / Traces

Aggregated service behavior
→ Metrics
```

---

# 42. CENTRALIZED LOGGING

In a distributed system, logs may originate from:

```text
Pod A

Pod B

Pod C

Ingress controller

Worker

Database proxy

Other services
```

Searching each host manually is inefficient.

Centralized logging creates a pipeline such as:

```text
Application
↓
stdout / logging interface
↓
Node / Agent / Collector
↓
Log Processing
↓
Central Backend
↓
Query / Dashboard
```

The exact architecture varies.

The principle is centralized searchability.

---

# 43. KUBERNETES LOGGING AWARENESS

Containers commonly emit application logs through:

```text
stdout

stderr
```

The container runtime and node logging architecture make those streams available for collection.

A centralized logging solution can then collect and forward them.

Application teams should not assume:

```text
kubectl logs
```

is a permanent log archive.

Pod and container lifecycles are temporary.

Production log retention requires a deliberate architecture.

---

# 44. LOG RETENTION

Keeping every log forever is not a production strategy.

Retention decisions involve:

```text
Operational usefulness

Compliance

Security

Privacy

Storage cost

Investigation requirements
```

Different log classes may need different retention periods.

For example:

```text
Verbose debug logs
→ shorter retention

Security audit logs
→ potentially different controlled retention
```

The exact policy is organization-specific.

---

# 45. LOG VOLUME

Logging every request with excessive detail can create huge volumes.

Ask:

```text
Will this event help investigation?

Is this information already available elsewhere?

Is the field safe?

How frequently will this event occur?

How long must it be retained?

What will ingestion and storage cost?
```

Observability has resource and financial costs.

---

# 46. SENSITIVE DATA IN LOGS

Never assume internal logs are harmless.

Avoid logging:

```text
Passwords

API keys

Access tokens

Session tokens

Private keys

Authorization headers

Sensitive personal information

Full secret values
```

Be careful with:

```text
Request bodies

Response bodies

Headers

Query strings
```

because they may contain sensitive data.

---

# 47. REDACTION

When operational context is necessary but sensitive fields may exist:

```text
Original Event
↓
Sanitize / Redact
↓
Safe Structured Log
```

For example:

```text
authorization="<redacted>"
```

rather than storing a bearer token.

Redaction should be designed systematically rather than relying on engineers remembering every sensitive field manually.

---

# 48. LOGGING FAILURE MODES

Logging infrastructure can fail.

Examples:

```text
Collector unavailable

Backend unavailable

Network interruption

Storage full

Ingestion throttled
```

Applications should not normally become unavailable merely because a non-critical log backend is temporarily unreachable.

Logging architecture should consider buffering, backpressure, dropping policy, and failure isolation according to system requirements.

---

# 49. TRACING

Metrics tell you:

```text
Latency increased.
```

Logs may tell you:

```text
Dependency timeout occurred.
```

Tracing can show:

```text
Client Request
↓
API Gateway
↓
Orders Service
↓
Inventory Service
↓
Database
```

and how time was distributed across that path.

---

# 50. DISTRIBUTED REQUESTS

Modern applications often cross multiple boundaries.

For example:

```text
Client
↓
Ingress
↓
Frontend
↓
Orders API
↓
Inventory API
↓
Database
```

A single user action may therefore involve many network calls.

Without correlation, every service sees only its local operation.

Tracing attempts to connect those operations into one request story.

---

# 51. TRACES

A trace represents the path of an operation through a distributed system.

Conceptually:

```text
Trace
├── Frontend Span
├── Orders API Span
│   ├── Inventory API Span
│   └── Database Span
└── Response
```

The trace allows an engineer to understand the relationships between operations.

---

# 52. SPANS

A span represents a unit of work.

A span commonly contains concepts such as:

```text
Name

Start time

Duration

Status

Attributes

Parent relationship

Trace identifier

Span identifier
```

For example:

```text
Span: POST /orders
Duration: 420 ms
```

Child span:

```text
Span: inventory.reserve
Duration: 310 ms
```

This suggests much of the request duration occurred in the inventory operation.

---

# 53. PARENT AND CHILD SPANS

Consider:

```text
POST /checkout
```

which calls:

```text
payment.authorize
```

The trace may represent:

```text
POST /checkout
└── payment.authorize
```

The parent-child relationship helps reconstruct execution flow.

Without it, you may know both operations occurred but not that one happened as part of the other.

---

# 54. TRACE CONTEXT

For distributed tracing to work across service boundaries, context must travel with the request.

Conceptually:

```text
Service A
↓
Inject Trace Context
↓
HTTP / RPC Request
↓
Service B
↓
Extract Trace Context
↓
Create Related Span
```

Without propagation:

```text
Service A Trace
```

and:

```text
Service B Trace
```

may appear unrelated.

---

# 55. W3C TRACE CONTEXT AWARENESS

Modern distributed tracing commonly uses W3C Trace Context conventions for propagating trace information across HTTP boundaries.

You may encounter the header:

```text
traceparent
```

The important engineering concept is not memorizing its encoding.

It is understanding:

```text
Incoming Context
↓
Extract
↓
Create Child Work
↓
Outgoing Request
↓
Inject Context
```

Instrumentation libraries usually handle this when configured correctly.

---

# 56. BROKEN TRACE PROPAGATION

Suppose:

```text
Frontend
↓
Orders
↓
Inventory
```

but the tracing backend displays:

```text
Trace A:
Frontend → Orders

Trace B:
Inventory
```

A likely investigation area is context propagation between Orders and Inventory.

Check:

```text
Was context extracted?

Was it preserved?

Was outgoing context injected?

Does the client library support instrumentation?

Was a custom protocol used?
```

---

# 57. TRACE ATTRIBUTES

Useful span attributes may include bounded information about:

```text
Service

Operation

HTTP method

Normalized route

Response status

Dependency

Environment
```

Avoid blindly attaching:

```text
Passwords

Tokens

Sensitive request bodies

Personal information
```

Tracing systems are still data systems.

Security and privacy rules apply.

---

# 58. SPAN EVENTS

A span may include notable events that occurred during its operation.

For example:

```text
Span: checkout
├── validation completed
├── inventory request started
├── retry performed
└── dependency timeout
```

Exact capabilities depend on the tracing implementation.

Use events when they improve understanding of the operation.

---

# 59. TRACING AND LATENCY

Suppose service-level metrics show:

```text
p95 latency increased
```

A trace might reveal:

```text
Total request:        1.8 s
Authentication:       20 ms
Application logic:    40 ms
Inventory call:       1.7 s
```

This changes the investigation from:

```text
Application is slow.
```

to:

```text
Requests are spending most of their time waiting for Inventory.
```

That is much more actionable evidence.

---

# 60. TRACE SAMPLING

Tracing every request in a high-traffic service can produce large volumes of telemetry.

Sampling controls which traces are retained or exported.

Conceptually:

```text
All Requests
↓
Sampling Decision
├── Retain / Export
└── Do Not Retain / Export
```

Sampling introduces a trade-off:

```text
More traces
→ More investigation detail
→ More telemetry cost

Fewer traces
→ Lower cost
→ Less detailed evidence
```

Sampling strategy should reflect service traffic and investigation requirements.

---

# 61. SAMPLING MEANS ABSENCE IS NOT PROOF

If sampling is enabled and you cannot find a trace for one specific request, that does not necessarily prove:

```text
The request never happened.
```

It may not have been sampled or retained.

Understand telemetry collection policy before drawing conclusions from missing evidence.

---

# 62. METRICS, LOGS, AND TRACES SHOULD CORRELATE

A mature investigation flow might be:

```text
Alert
↓
Metric
↓
Dashboard
↓
Affected Service / Route / Version
↓
Trace
↓
Slow or Failed Span
↓
Correlated Logs
↓
Root-Cause Hypothesis
```

The signals become more powerful when they reinforce each other.

---

# 63. EXEMPLAR AND CROSS-SIGNAL AWARENESS

Some observability systems can associate metric observations with representative traces or otherwise allow navigation between signals.

The broader principle is:

```text
Aggregate Problem
↓
Specific Request Evidence
```

Do not depend on a particular vendor feature.

Design telemetry so signals can be correlated where practical.

---

# 64. RESOURCE IDENTITY

Telemetry should identify what produced it.

Useful resource context may include:

```text
service.name

environment

service version

cluster

namespace

region
```

Exact field conventions depend on the telemetry standard and backend.

The important requirement is being able to distinguish:

```text
Which service?

Which environment?

Which version?

Which location?
```

---

# 65. VERSION INFORMATION

Deployment information is highly valuable during incidents.

Suppose:

```text
Error Rate
     │
     │          ┌────────
     │          │
─────┴──────────┴──────────── Time
                ↑
             Deploy v2
```

Knowing the deployed version allows the team to ask:

```text
Did the error increase begin after v2?

Is v1 still healthy?

Are only v2 Pods failing?
```

Observability should support deployment correlation.

---

# 66. DASHBOARDS

A dashboard is not a collection of every graph you can create.

A dashboard should answer operational questions.

Bad dashboard design:

```text
CPU graph
Memory graph
Disk graph
Network graph
20 application graphs
40 dependency graphs
```

with no hierarchy or operational purpose.

Better design starts with:

```text
What does the operator need to know?
```

---

# 67. SERVICE OVERVIEW DASHBOARD

A useful service overview might answer:

```text
Is the service available?

How much traffic is it serving?

Are users seeing errors?

Is latency acceptable?

Is the service saturated?

Which version is deployed?

Did anything recently change?
```

This naturally suggests:

```text
Traffic

Errors

Latency

Saturation

Deployment markers
```

---

# 68. DASHBOARD HIERARCHY

A practical hierarchy can be:

```text
Service Overview
↓
Component / Endpoint Detail
↓
Dependency Detail
↓
Infrastructure Detail
```

An incident begins high in the stack.

Then engineers drill downward.

This is often more useful than placing everything on one enormous screen.

---

# 69. DASHBOARD: TRAFFIC

Questions:

```text
How much traffic?

Which routes?

Has traffic suddenly changed?

Is one operation unusually busy?
```

Possible panels:

```text
Request rate

Request rate by route

Request rate by status category
```

Keep dimensions bounded.

---

# 70. DASHBOARD: ERRORS

Questions:

```text
Are users failing?

Which endpoint?

Which version?

Which status category?

Did failures begin after deployment?
```

Possible panels:

```text
Error rate

Error count

Errors by route

Errors by version
```

---

# 71. DASHBOARD: LATENCY

Questions:

```text
Are requests slower?

Which percentile?

Which route?

Did latency change after deployment?
```

Possible panels:

```text
p50

p95

p99
```

where those measurements are meaningful and correctly derived from the available metric representation.

Do not display percentiles you do not understand.

---

# 72. DASHBOARD: SATURATION

Questions:

```text
Is the service approaching capacity?

Which resource?

Is saturation correlated with latency?
```

Possible signals:

```text
CPU

Memory

Queue depth

Connection pool usage

Worker utilization
```

Choose saturation signals that reflect actual bottlenecks.

---

# 73. DASHBOARD: DEPENDENCIES

For a service dependent on:

```text
Database

Cache

External API

Message broker
```

consider exposing:

```text
Dependency latency

Dependency error rate

Connection pool state

Timeouts

Retries
```

Do not create dependency graphs merely because they look impressive.

Each panel should answer a question.

---

# 74. DASHBOARD: DEPLOYMENTS

Include change context where possible.

Useful information may include:

```text
Deployment timestamp

Application version

Release revision

Configuration change
```

This supports questions such as:

> Did the incident begin when the system changed?

Correlation is evidence for investigation.

It is not automatic proof of causation.

---

# 75. DASHBOARD TIME WINDOWS

A metric can look completely different depending on the selected time window.

Compare:

```text
Last 5 minutes

Last hour

Last 24 hours

Last 7 days
```

A five-minute spike may disappear in a seven-day graph.

During investigation, choose time ranges that preserve relevant behavior.

---

# 76. DASHBOARD AGGREGATION CAN HIDE FAILURES

Suppose:

```text
9 Pods healthy
1 Pod failing
```

A service-wide average may appear mostly normal.

Break down by useful dimensions such as:

```text
instance

Pod

version

zone
```

when investigation requires it.

But avoid permanently creating high-cardinality dimensions without reason.

---

# 77. DASHBOARDS ARE NOT ALERTS

A dashboard requires someone to look at it.

An alert actively notifies an operator or system.

Do not design production reliability around:

```text
Someone will notice the graph.
```

For urgent conditions:

```text
Condition
↓
Alert Evaluation
↓
Notification
↓
Responsible Responder
```

must be deliberate.

---

# 78. ALERTING

An alert should represent a condition requiring attention.

A useful alert answers:

```text
What is wrong?

How severe is it?

Which service is affected?

Which environment?

How long has it been happening?

Where should I investigate?

What action might be required?
```

A poor alert:

```text
CPU HIGH
```

with no context.

---

# 79. ACTIONABLE ALERTS

Before creating an alert, ask:

```text
Who receives it?

What should they do?

How urgent is it?

What evidence supports it?

What happens if nobody responds?

Can the condition resolve safely without human intervention?
```

If nobody knows what action to take, the alert may not deserve to interrupt someone.

---

# 80. SYMPTOMS VERSUS CAUSES

This is one of the most important alerting distinctions.

## Symptom

What the user experiences:

```text
High request failure rate

High latency

Service unavailable
```

## Cause

A possible explanation:

```text
CPU high

Database connection pool exhausted

Pod restarting

Disk nearly full
```

For urgent paging, symptoms are often more reliable because they directly represent service impact.

---

# 81. WHY CAUSE-ONLY ALERTING CREATES NOISE

Imagine:

```text
CPU > 90%
```

But:

```text
Latency normal

Errors normal

Traffic normal
```

The service may be intentionally performing compute-heavy work.

Now imagine:

```text
CPU = 20%
```

while:

```text
Database unavailable

Error rate = 80%
```

CPU did not reveal the outage.

Infrastructure alerts are useful.

But they should not replace service symptoms.

---

# 82. ALERT SEVERITY

Not every alert deserves the same response.

A simple conceptual model might be:

```text
Critical
→ Immediate human response required

Warning
→ Investigation required soon

Informational
→ Useful operational event, not urgent
```

Exact severity conventions should be defined by the organization.

Severity should correspond to response expectation.

---

# 83. PAGE VERSUS TICKET

A useful distinction is:

```text
Urgent + User Impact + Human Action Required
→ Page

Important but not immediate
→ Ticket / Work Queue

Informational
→ Dashboard / Log / Report
```

Do not wake an engineer at 03:00 for a condition that can safely wait until business hours.

---

# 84. STATIC THRESHOLDS

A threshold alert might be:

```text
Error Rate > 5%
for 10 minutes
```

Thresholds are simple and understandable.

But they require careful selection.

Too low:

```text
Noise
```

Too high:

```text
Late detection
```

---

# 85. ALERT DURATION

A brief transient spike may not require human intervention.

Therefore alert conditions often include persistence.

Conceptually:

```text
Condition True
↓
Wait Required Duration
↓
Still True?
├── No  → Do Not Fire
└── Yes → Fire
```

The duration should reflect service behavior and urgency.

---

# 86. AVOID ALERTING ON SINGLE TRANSIENT EVENTS

Suppose one request fails out of millions.

An alert on:

```text
error_count > 0
```

may create constant noise.

Use:

```text
rate

ratio

duration

traffic context
```

where appropriate.

But do not hide low-volume critical operations behind percentages either.

The correct design depends on service semantics.

---

# 87. LOW-TRAFFIC SERVICES

Percentage-based alerts can behave strangely at low traffic.

Example:

```text
1 request
1 failure
```

produces:

```text
100% error rate
```

but the evidence volume is tiny.

Consider:

```text
Minimum traffic

Absolute failures

Longer windows

Synthetic checks
```

where appropriate.

---

# 88. ALERT NOISE

Alert noise occurs when responders receive too many notifications that do not require useful action.

Consequences include:

```text
Ignored alerts

Slower response

Reduced trust

Pager fatigue

Missed real incidents
```

Every noisy alert weakens the alerting system.

---

# 89. ALERT QUALITY

A useful alert should have high operational value.

Ask:

```text
Does it represent meaningful impact?

Is it actionable?

Is the signal reliable?

Does it duplicate another alert?

Is severity correct?

Does it route to the right owner?

Does it contain useful context?
```

---

# 90. ALERT DEDUPLICATION

One underlying failure can trigger many signals.

Example:

```text
Database unavailable
↓
API errors
↓
Worker errors
↓
Retry increase
↓
Queue growth
↓
Timeout increase
```

Without grouping or deduplication, responders might receive:

```text
50 alerts
```

for one incident.

Alert-management systems commonly support grouping, deduplication, inhibition, or related concepts.

The objective is:

```text
One Incident
↓
Useful Set of Notifications
```

not:

```text
One Incident
↓
Notification Storm
```

---

# 91. ALERT ROUTING

Alerts should reach the team that can act.

Routing dimensions may include:

```text
Service

Environment

Severity

Owning team

Region
```

For example:

```text
Production Checkout Critical
↓
Checkout On-Call
```

rather than:

```text
Every Alert
↓
Every Engineer
```

---

# 92. ALERT OWNERSHIP

Every important alert should have an owner.

If nobody owns:

```text
QueueDepthHigh
```

then during an incident everyone may assume somebody else is responding.

Ownership should align with service responsibility.

---

# 93. ALERT CONTEXT

An alert notification should ideally provide or link to:

```text
Service

Environment

Condition

Current value

Threshold

Duration

Dashboard

Runbook

Recent deployment information
```

The responder should not spend the first five minutes determining what the alert means.

---

# 94. RUNBOOKS

A runbook provides an investigation or response starting point.

A useful runbook might include:

```text
What the alert means

Likely impact

Immediate checks

Relevant dashboards

Relevant queries

Common causes

Safe mitigations

Escalation path
```

A runbook should guide reasoning.

It should not encourage:

```text
Restart everything.
```

---

# 95. ALERTS SHOULD EVOLVE

After an incident ask:

```text
Did the alert fire?

Did it fire early enough?

Was it actionable?

Was severity correct?

Did duplicate alerts fire?

Was the runbook useful?

Did the alert identify user impact?

What telemetry was missing?
```

Observability should improve from operational experience.

---

# 96. RECORDING AND PRECOMPUTATION AWARENESS

Some metric queries are expensive or repeatedly used.

Monitoring systems such as Prometheus support precomputed time series through recording rules.

Conceptually:

```text
Expensive / Repeated Query
↓
Evaluate Regularly
↓
Store Derived Series
↓
Dashboard / Alert Uses Derived Series
```

Use this when justified by query complexity, reuse, and operational requirements.

Do not create recording rules merely to duplicate every metric.

---

# 97. SERVICE LEVEL INDICATORS

A Service Level Indicator, or SLI, measures some aspect of service behavior relevant to reliability.

Examples include:

```text
Successful request ratio

Request latency

Successful job completion ratio

Data freshness
```

An SLI is not merely:

```text
CPU utilization.
```

It should represent something meaningful about service delivery.

---

# 98. SERVICE LEVEL OBJECTIVES

A Service Level Objective, or SLO, defines a target for an SLI over a period.

Conceptually:

```text
SLI
↓
Measured Reliability

SLO
↓
Desired Reliability Target
```

Example concept:

```text
Successful request ratio
↓
Target reliability over defined period
```

The exact objective should come from service requirements.

Do not invent an arbitrary number because another company uses it.

---

# 99. ALERTING AND SERVICE OBJECTIVES

As observability maturity grows, alerting can become more aligned with actual reliability objectives rather than isolated infrastructure thresholds.

The reasoning becomes:

```text
Are users experiencing enough failure
to threaten the service objective?
```

rather than only:

```text
Is CPU above a number?
```

Detailed SLO engineering will be developed further in the reliability Part.

---

# 100. TELEMETRY PIPELINE

Observability data itself moves through systems.

For example:

```text
Application
↓
Instrumentation
↓
Collector / Agent
↓
Processing
↓
Backend
↓
Query
↓
Dashboard / Alert
```

Every layer can fail.

Therefore:

```text
No Data
```

does not automatically mean:

```text
No Problem.
```

It may mean:

```text
Telemetry Pipeline Failed.
```

---

# 101. OBSERVE THE OBSERVABILITY SYSTEM

Important telemetry infrastructure may itself need monitoring.

Questions include:

```text
Are targets being scraped?

Are collectors healthy?

Are logs being dropped?

Is ingestion failing?

Is storage available?

Are alert rules evaluating?

Are notifications being delivered?

Is tracing export failing?
```

A monitoring system that silently stops monitoring creates dangerous confidence.

---

# 102. MISSING DATA

Missing data has several possible meanings.

For example:

```text
Metric disappeared
```

could mean:

```text
Service stopped

Target discovery failed

Scrape failed

Instrumentation changed

Metric renamed

Collector failed

Network path failed
```

Do not automatically interpret missing telemetry as zero.

---

# 103. ZERO AND ABSENT ARE DIFFERENT

This distinction is critical.

```text
requests = 0
```

can mean:

```text
Service reported zero requests.
```

But:

```text
No requests metric exists
```

may mean:

```text
Service not scraped

Instrumentation missing

Service down

Query wrong
```

Queries and alerts should account for this distinction where relevant.

---

# 104. OBSERVABILITY COST

Telemetry has costs.

Metrics consume:

```text
Memory

Storage

Query resources
```

Logs consume:

```text
Ingestion bandwidth

Storage

Indexing resources
```

Traces consume:

```text
Instrumentation overhead

Network

Storage

Processing
```

Therefore:

```text
Collect Everything Forever
```

is not a mature observability strategy.

---

# 105. TELEMETRY VALUE

Evaluate telemetry by asking:

```text
What question does this answer?

Who uses it?

Does an alert depend on it?

Does a dashboard depend on it?

Has it helped incidents?

How expensive is it?

Does it expose sensitive information?
```

Unused telemetry should be reviewed.

Some telemetry may still be valuable for rare investigations, but retention and cost should be intentional.

---

# 106. CARDINALITY AS AN OPERATIONAL RISK

Cardinality is not merely a metric design detail.

Uncontrolled cardinality can cause:

```text
Memory growth

Storage growth

Slow queries

Expensive ingestion

Monitoring instability
```

Therefore code review should consider telemetry changes.

A developer adding:

```text
user_id
```

to a metric label may accidentally create an infrastructure problem.

---

# 107. OBSERVABILITY CHANGES ARE PRODUCTION CHANGES

Instrumentation code can affect:

```text
Application performance

Telemetry cost

Storage

Sensitive-data exposure

Alert behavior

Dashboard behavior
```

Therefore instrumentation deserves:

```text
Review

Testing

Version control

Deployment discipline
```

Do not treat it as harmless decoration.

---

# 108. THE OBSERVABILITY FAILURE MODEL

When investigating telemetry, reason through:

```text
Application
↓
Instrumentation
↓
Export / Exposure
↓
Collection
↓
Processing
↓
Storage
↓
Query
↓
Visualization / Alert
```

If a dashboard is empty, the application is only one possible failure location.

# 109. TROUBLESHOOTING METRICS

Symptom:

```text
Expected metric missing.
```

Investigate:

```text
Does application expose metric?

Correct metric name?

Correct endpoint?

Collector can reach endpoint?

Target discovered?

Scrape successful?

Authentication correct?

Metric filtered?

Backend receiving data?

Query correct?
```

Find the first broken layer.

# 110. TROUBLESHOOTING INCORRECT METRIC VALUES

Suppose:

```text
Request rate appears impossible.
```

Check:

```text
Metric type

Query window

Rate calculation

Label filtering

Aggregation

Duplicate collection

Counter resets

Units

Multiple replicas

Environment
```

Do not assume the graphing system is wrong.

Verify the instrumentation and query semantics.

---

# 111. TROUBLESHOOTING CARDINALITY EXPLOSION

Symptoms may include:

```text
Sudden time-series growth

Monitoring memory growth

Slow queries

Higher telemetry cost
```

Investigate:

```text
Recent instrumentation change

New labels

Unexpected label values

Dynamic URLs

User identifiers

Request identifiers

Version or instance dimensions
```

Identify the dimension producing uncontrolled uniqueness.

---

# 112. TROUBLESHOOTING LOGS

Symptom:

```text
Application logs missing.
```

Trace:

```text
Application
↓
stdout/stderr or logging sink
↓
Container/runtime logging
↓
Collector
↓
Transport
↓
Backend
↓
Query
```

Check each boundary.

Do not immediately increase application log level.

---

# 113. TROUBLESHOOTING LOG PARSING

Symptoms:

```text
Fields missing

Severity incorrect

Timestamp wrong

JSON parsing errors

Search filters fail
```

Inspect the raw log event.

Compare:

```text
Produced Format

Expected Parser

Parsed Result
```

The backend cannot correctly structure malformed or inconsistent application logs automatically.

---

# 114. TROUBLESHOOTING TRACE GAPS

Symptom:

```text
Trace stops at Service B.
```

Check:

```text
Was Service C called?

Was trace context injected?

Was context extracted?

Is Service C instrumented?

Did sampling affect the trace?

Did export fail?

Is backend filtering involved?
```

A missing span does not automatically prove the call never happened.

---

# 115. TROUBLESHOOTING ALERTS THAT DO NOT FIRE

Check:

```text
Does underlying metric exist?

Does query return expected value?

Is threshold crossed?

For how long?

Is rule loaded?

Is rule evaluating?

Is alert manager receiving it?

Is routing configured?

Is notification integration healthy?
```

Separate:

```text
Detection
```

from:

```text
Notification.
```

---

# 116. TROUBLESHOOTING NOISY ALERTS

For an alert firing repeatedly, ask:

```text
Is the threshold too sensitive?

Is duration too short?

Is traffic volume considered?

Is the signal actually user-impacting?

Does it duplicate another alert?

Does it flap around threshold?

Can routing/grouping improve it?

Should this be a ticket rather than a page?
```

Do not simply silence every annoying alert.

Fix its design.

---

# 117. TROUBLESHOOTING DASHBOARDS

A strange graph can result from:

```text
Wrong query

Wrong aggregation

Wrong unit

Wrong time range

Wrong environment filter

Missing data

Counter reset

High-cardinality breakdown

Duplicate telemetry
```

A dashboard is a view of a query.

It is not ground truth by itself.

# 118. OBSERVABILITY DURING DEPLOYMENTS

↓

↓

# 119. VERSION-SPECIFIC OBSERVATION

Suppose:

```text
v1 = 90% traffic

v2 = 10% traffic
```

during canary deployment.

Service-wide metrics may hide a severe v2 problem.

For example:

```text
v1 error rate = 0.1%

v2 error rate = 15%
```

Aggregated service error rate may appear much less dramatic.

Canary analysis requires being able to distinguish versions safely without creating uncontrolled metric cardinality.

---

# 120. OBSERVABILITY DURING INCIDENTS

A disciplined investigation can follow:

```text
Symptom
↓
Scope
↓
Timeline
↓
Recent Change
↓
Service-Level Metrics
↓
Affected Component
↓
Trace / Logs
↓
Infrastructure Evidence
↓
Hypothesis
↓
Test
↓
Corrective Action
↓
Verification
```

Observability supports reasoning.

It should not replace reasoning.

---

# 121. EVIDENCE BEFORE HYPOTHESIS

Weak incident response:

```text
Application slow
↓
Probably CPU
↓
Restart Pods
```

Better:

```text
Application slow
↓
Confirm latency increase
↓
Identify affected route
↓
Compare error and traffic behavior
↓
Inspect trace
↓
Dependency span dominates latency
↓
Check dependency telemetry
↓
Form hypothesis
```

The difference is evidence.

---

# 122. SUPPORTING AND CONTRADICTING EVIDENCE

Suppose the hypothesis is:

```text
High CPU caused the latency increase.
```

Supporting evidence:

```text
CPU increased before latency.

Affected Pods show CPU throttling.

Latency improves as CPU pressure falls.
```

Contradicting evidence:

```text
CPU remained normal.

Trace shows database wait dominates request duration.

Database latency increased at incident start.
```

Actively search for evidence that could disprove the hypothesis.

---

# 123. CORRELATION IS NOT CAUSATION

Suppose:

```text
Deployment at 14:00

Latency increase at 14:02
```

The deployment is an important hypothesis.

But:

```text
Temporal Correlation
≠
Proof of Cause
```

Investigate:

```text
Version-specific metrics

Traces

Logs

Dependency behavior

Configuration changes
```

before declaring root cause.

concepts well enough to recognize that service reliability should ultimately be measured through meaningful service behavior rather than arbitrary infrastructure thresholds.

```text
Log analysis

Query explanation

Trace interpretation

Alert drafting

Dashboard review

Hypothesis generation
```

without treating AI conclusions as verified root cause.

The final question is not:

```text
Can I install Prometheus?

Can I create a Grafana dashboard?

Can I search logs?
```

It is:

```text
Can I design telemetry around meaningful operational questions,
measure the behavior users actually depend on,
control metric cardinality,
produce safe and searchable structured logs,
follow requests across service boundaries,
build dashboards that expose service health,
create alerts that deserve human attention,
correlate metrics, logs, traces, deployments, and infrastructure,
detect when the observability system itself is failing,
and use that evidence to move from symptom to verified engineering
conclusion without guessing?
```

When the answer is yes, you have moved beyond reading monitoring screens into **observability engineering**.
