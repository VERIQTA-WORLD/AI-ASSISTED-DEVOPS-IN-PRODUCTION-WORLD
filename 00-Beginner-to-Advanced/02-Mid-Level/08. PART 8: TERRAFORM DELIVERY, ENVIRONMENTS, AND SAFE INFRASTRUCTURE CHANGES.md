# PART 8: TERRAFORM DELIVERY, ENVIRONMENTS, AND SAFE INFRASTRUCTURE CHANGES

## Goal

Integrate infrastructure as code into controlled engineering workflows.

Part 7 established how Terraform configuration, modules, providers, state, remote infrastructure, imports, drift, and resource lifecycle fit together.

Part 8 addresses the next production problem:

**How does a team safely deliver Terraform changes repeatedly across development, staging, and production?**

A Terraform configuration can be technically correct and still be delivered unsafely.

An engineer can:

- use the wrong credentials
- target the wrong environment
- initialize against the wrong state
- approve an unexpected replacement
- run two conflicting applies
- expose a plan containing sensitive information
- apply code that was never reviewed
- approve production based on a development result
- mistake a successful Terraform apply for a healthy application
- attempt to "roll back" infrastructure without understanding whether the old configuration can safely recreate the previous state

Production infrastructure delivery therefore requires more than:

```text
terraform plan
terraform apply
```

It requires a controlled path from proposed source-code change to verified infrastructure state.

The central mental model for this Part is:

```text
Pull Request
↓
Format
↓
Validate
↓
Security / Policy Checks
↓
Plan
↓
Human Review
↓
Approval
↓
Apply
↓
Verification
```

For real production engineering, expand that model further:

```text
Change Requirement
↓
Correct Repository
↓
Correct Environment
↓
Correct Identity
↓
Correct State
↓
Pull Request
↓
Static Validation
↓
Security / Policy Checks
↓
Terraform Plan
↓
Plan Artifact
↓
Human Review
↓
Risk Assessment
↓
Approval
↓
Controlled Apply
↓
Terraform Result
↓
Infrastructure Verification
↓
Application Verification
↓
Observability
↓
Change Record
```

The important principle is:

> Infrastructure delivery is not complete when Terraform finishes. It is complete when the intended infrastructure and service behavior have been independently verified.

---

# 1. FROM TERRAFORM EXECUTION TO TERRAFORM DELIVERY

A local learning workflow often looks like this:

```text
Engineer
↓
Edits Terraform
↓
terraform plan
↓
terraform apply
```

That can be appropriate in a disposable lab.

A production team has additional concerns:

```text
Who requested the change?

Who wrote it?

Who reviewed it?

Which environment will it affect?

Which identity will Terraform use?

Which state will Terraform access?

What exactly does the plan contain?

Were security controls checked?

Will anything be destroyed?

Will anything be replaced?

Who is allowed to approve?

Is the reviewed plan the one being applied?

What happens if apply partially fails?

How is success verified?

How is the change recorded?
```

The delivery system exists to answer these questions consistently.

---

# 2. INFRASTRUCTURE DELIVERY IS A CONTROL SYSTEM

A useful model is:

```text
Human Intent
↓
Version-Controlled Configuration
↓
Automated Validation
↓
Terraform Planning
↓
Risk Evaluation
↓
Human / Policy Authorization
↓
Terraform Execution
↓
Infrastructure
↓
Independent Verification
```

Each stage reduces a different class of risk.

Version control provides history.

Formatting reduces unnecessary review noise.

Validation detects configuration problems.

Security checks detect selected unsafe patterns.

Policy checks enforce selected organizational constraints.

Planning exposes Terraform's proposed actions.

Human review evaluates context and consequences.

Approval authorizes execution.

State locking can help protect concurrent state-writing operations when the backend supports it.

Verification establishes whether the intended result was actually achieved.

No single stage replaces all the others.

---

# 3. ENVIRONMENTS

Most production systems use multiple environments.

Common examples include:

```text
Development

Staging

Production
```

Some organizations also use:

```text
Test

QA

Integration

Performance

Pre-production

Sandbox
```

Environment names vary.

The important concept is that different environments represent different purposes, risks, identities, and operational boundaries.

---

# 4. DEVELOPMENT ENVIRONMENT

A development environment exists primarily to support engineering work.

Typical characteristics may include:

- smaller infrastructure
- lower cost
- synthetic or non-production data
- broader experimentation
- faster change frequency
- reduced capacity
- fewer availability requirements
- temporary resources
- controlled failure testing

Development should still be secure.

"Development" does not mean:

```text
No access control

Public databases

Hard-coded credentials

Unrestricted networking

Untracked changes
```

It means the environment has a different purpose and risk profile.

---

# 5. STAGING ENVIRONMENT

Staging should provide meaningful evidence about whether a change is likely to behave correctly before production.

Ideally, staging resembles important production characteristics closely enough to expose relevant problems.

These may include:

```text
Architecture

Network Path

Deployment Model

Authentication Model

Terraform Structure

Application Configuration Pattern

Observability

External Integration Pattern
```

Exact production scale may be unnecessary or too expensive.

The objective is **representative behavior**, not necessarily identical capacity.

---

# 6. PRODUCTION ENVIRONMENT

Production serves real workloads or business operations.

Production usually requires stronger controls around:

- identity
- approval
- availability
- data protection
- auditability
- change management
- recovery
- monitoring
- state protection
- destructive operations

A production Terraform pipeline should make accidental changes harder, not easier.

---

# 7. ENVIRONMENTS ARE NOT JUST VARIABLE FILES

A common beginner model is:

```text
Same Terraform
+
dev.tfvars
staging.tfvars
prod.tfvars
```

Variable differences can be part of environment management.

But an environment is larger than its variable file.

An environment may also have different:

```text
Cloud Account / Project / Subscription

Terraform State

Backend

Credentials

Permissions

DNS

Network

Secrets

Data

Quotas

Approval Requirements

Change Windows

Recovery Requirements
```

Therefore:

```text
Environment
≠
Variable File
```

---

# 8. ENVIRONMENT SEPARATION

Environment separation limits the chance that activity in one environment affects another.

A weak model is:

```text
One Account
One Identity
One State
Everything Mixed Together
```

A stronger model may separate:

```text
Development
├── Identity
├── State
├── Variables
└── Infrastructure

Staging
├── Identity
├── State
├── Variables
└── Infrastructure

Production
├── Identity
├── State
├── Variables
└── Infrastructure
```

The exact implementation depends on the organization and cloud platform.

The principle is blast-radius control.

---

# 9. ENVIRONMENT SEPARATION HAS MULTIPLE DIMENSIONS

Do not think of separation as one setting.

Consider:

```text
Source Structure

State

Cloud Boundary

Identity

Permissions

Variables

Secrets

Network

DNS

Approval

Pipeline

Observability
```

Two environments can use the same module code while remaining operationally separate.

---

# 10. SOURCE-CODE STRUCTURE

One possible repository structure is:

```text
terraform/
├── modules/
│   ├── network/
│   ├── application/
│   └── database/
│
└── environments/
    ├── development/
    ├── staging/
    └── production/
```

Each environment root module can call shared modules.

Conceptually:

```text
Shared Modules
      │
      ├──────── Development Root
      │
      ├──────── Staging Root
      │
      └──────── Production Root
```

This is one pattern, not a universal requirement.

---

# 11. ENVIRONMENT ROOT MODULES

An environment root module can express environment-specific composition.

For example:

```text
environments/
└── production/
    ├── terraform.tf
    ├── providers.tf
    ├── backend.tf
    ├── variables.tf
    ├── main.tf
    └── outputs.tf
```

The root module might call:

```hcl
module "network" {
  source = "../../modules/network"

  environment = "production"
}

module "application" {
  source = "../../modules/application"

  environment = "production"
  network_id   = module.network.network_id
}
```

The exact resources and arguments depend on the real provider and module interfaces.

---

# 12. DUPLICATION VERSUS ENVIRONMENT CLARITY

Separate environment roots may introduce some repeated configuration.

That is not automatically bad.

A dangerous abstraction is one that hides important production differences merely to remove repeated lines.

For example:

```text
Less Duplication
```

is not automatically more important than:

```text
Clear Environment Boundaries
```

Use modules to share stable infrastructure capabilities.

Allow environment roots to express meaningful differences.

---

# 13. DO NOT COPY ENTIRE ENVIRONMENTS CARELESSLY

The opposite extreme is also problematic:

```text
development/
  2,000 lines

staging/
  copied 2,000 lines

production/
  copied 2,000 lines
```

Now fixing a bug may require three separate changes.

Environment architecture should balance:

```text
Reuse
+
Isolation
+
Clarity
+
Independent Change
```

---

# 14. STATE SEPARATION

Development, staging, and production should not accidentally share the same Terraform state when they represent separate infrastructure.

Conceptually:

```text
Development Configuration
↓
Development State
↓
Development Infrastructure
```

```text
Staging Configuration
↓
Staging State
↓
Staging Infrastructure
```

```text
Production Configuration
↓
Production State
↓
Production Infrastructure
```

This is a critical boundary.

---

# 15. WHY STATE SEPARATION MATTERS

If unrelated environments share inappropriate state boundaries, a Terraform operation can gain a much larger blast radius.

State separation helps reduce risks such as:

```text
Development Change
↓
Unexpected Production Plan
```

or:

```text
Production Lock
↓
Blocks Unrelated Development Work
```

or:

```text
Broad State Access
↓
Unnecessary Access to Sensitive Production Information
```

State design is part of environment design.

---

# 16. STATE SEPARATION DOES NOT AUTOMATICALLY MEAN SECURITY SEPARATION

Separate state files alone do not prove that environments are securely isolated.

For example:

```text
dev state
prod state
```

may still be accessible using the same highly privileged credential.

Therefore evaluate both:

```text
State Separation
```

and:

```text
Identity / Permission Separation
```

---

# 17. PROVIDER CONFIGURATION

Terraform providers determine where and how Terraform communicates with infrastructure APIs.

Environment-specific provider configuration may determine:

- account
- project
- subscription
- region
- authentication context
- provider aliases
- endpoints

A provider configuration error can send a valid Terraform configuration toward the wrong target.

---

# 18. WRONG ENVIRONMENT CAN STILL PRODUCE VALID TERRAFORM

Consider:

```text
Terraform syntax
✓

terraform validate
✓

Provider authentication
✓

Plan generated
✓
```

But Terraform authenticated to the wrong cloud account.

The configuration can be valid while the execution context is wrong.

Therefore validation must include **environment identity**.

---

# 19. VERIFY EXECUTION CONTEXT

Before production planning or application, the workflow should establish evidence for:

```text
Environment

Account / Project / Subscription

Region

Terraform State

Backend

Identity

Repository Revision
```

The exact commands used to verify cloud identity depend on the provider.

Do not assume successful authentication proves the correct target.

---

# 20. VARIABLE STRATEGY

Environment-specific values may include:

```text
Environment Name

Region

Network Ranges

Capacity

Instance Sizes

Feature Settings

DNS Names

Scaling Limits

Retention Settings
```

These values need a deliberate source.

Possible sources include:

- version-controlled non-sensitive variable files
- environment-specific root configuration
- CI/CD variables
- platform-managed variables
- secret stores for sensitive values

Do not choose a source only because it is convenient.

---

# 21. VARIABLE OWNERSHIP

For every input, ask:

```text
What is this value?

Who owns it?

Is it sensitive?

Does it differ by environment?

Should it be reviewed in Git?

Should the pipeline inject it?

Should a secret system provide it?
```

This prevents environment configuration from becoming an uncontrolled collection of values.

---

# 22. NON-SENSITIVE ENVIRONMENT CONFIGURATION

Values such as:

```text
environment = "production"

region = "example-region"

replica_count = 3
```

may be appropriate to version-control when they contain no sensitive information.

The benefit is reviewability:

```text
Production capacity changed
3 → 5
```

becomes visible in source history.

---

# 23. SENSITIVE VARIABLES

Secrets require different treatment.

Do not casually commit:

```text
Passwords

Private Keys

API Tokens

Long-Lived Cloud Credentials

Database Credentials
```

to Terraform repositories.

Even if the repository is private, source control should not become the default secret store.

---

# 24. TERRAFORM STATE AND SECRETS

Part 7 established an important principle:

```text
Sensitive CLI Display
≠
Secret Absent From State
```

Part 8 adds the delivery consequence:

```text
Pipeline Handles Terraform
↓
Pipeline May Handle Sensitive State / Plans / Outputs
↓
Pipeline Security Matters
```

Protect:

- state
- saved plans
- logs
- artifacts
- environment variables
- credentials

according to their contents.

---

# 25. PIPELINE IDENTITY

A Terraform pipeline requires an identity capable of performing the operations in its plan.

A poor model is:

```text
One Permanent Administrator Credential
↓
Used Everywhere
↓
Development
Staging
Production
```

This creates unnecessary blast radius.

A stronger model separates authority.

---

# 26. LEAST PRIVILEGE

The pipeline identity should receive the permissions required for its responsibility.

Conceptually:

```text
Development Pipeline Identity
↓
Development Resources
```

```text
Production Pipeline Identity
↓
Production Resources
```

Avoid allowing development automation to modify production merely because the same Terraform code is reused.

---

# 27. SHORT-LIVED CREDENTIALS

Where the platform and CI system support it, prefer temporary or workload-federated credentials over manually stored long-lived cloud access keys.

Conceptually:

```text
CI Job
↓
Trusted Identity Exchange
↓
Temporary Cloud Credential
↓
Terraform Operation
↓
Credential Expires
```

This reduces risks associated with permanently stored credentials.

The exact mechanism is provider and CI-platform specific.

---

# 28. AUTHENTICATION IS NOT AUTHORIZATION

A pipeline can successfully authenticate and still lack permission.

Distinguish:

```text
Authentication
Who is the pipeline?
```

from:

```text
Authorization
What may the pipeline do?
```

This distinction is critical during troubleshooting.

---

# 29. DEVELOPMENT AND PRODUCTION SHOULD NOT HAVE IDENTICAL AUTHORITY BY ACCIDENT

A development pipeline may legitimately be allowed to:

```text
Create

Modify

Destroy
```

disposable development infrastructure.

Production may require:

```text
Restricted Identity

Protected Branch

Approved Plan

Human Authorization

Additional Policy Checks
```

Environment criticality should influence delivery controls.

---

# 30. THE TERRAFORM DELIVERY PIPELINE

A mature Terraform delivery workflow can be represented as:

```text
Developer Changes Terraform
↓
Pull Request
↓
Repository Checks
↓
terraform fmt -check
↓
terraform init
↓
terraform validate
↓
Security Checks
↓
Policy Checks
↓
terraform plan
↓
Plan Published for Review
↓
Human Reviews Infrastructure Effect
↓
Approval
↓
Apply
↓
Post-Apply Verification
```

Each stage has a specific purpose.

---

# 31. PULL REQUEST AS CHANGE BOUNDARY

The pull request should answer:

```text
What is changing?

Why?

Which environment?

What infrastructure is affected?

What risk exists?

What evidence supports the change?

What is the expected plan?

How will success be verified?

How will failure be handled?
```

A pull request should not merely say:

```text
Update Terraform.
```

---

# 32. REVIEW INTENT BEFORE SYNTAX

A reviewer should understand the requested outcome before inspecting Terraform details.

Use:

```text
Intent
↓
Configuration Diff
↓
Plan
↓
Operational Consequence
```

Without intent, reviewers cannot reliably decide whether the plan is correct.

---

# 33. FORMAT CHECK

A pipeline may run:

```bash
terraform fmt -check
```

This verifies Terraform formatting conventions for relevant configuration files.

Failure means the configuration needs formatting.

It does not mean the infrastructure design is incorrect.

Likewise:

```text
terraform fmt -check passes
≠
Infrastructure is safe
```

---

# 34. INITIALIZATION

Automation commonly initializes Terraform before validation or planning:

```bash
terraform init -input=false
```

The `-input=false` option is useful in automation because CI jobs should not wait for interactive input.

Initialization prepares the working directory, including required provider and module dependencies and backend initialization as appropriate to the workflow.

---

# 35. LOCK FILE REVIEW

If initialization changes:

```text
.terraform.lock.hcl
```

the change should be understood.

Ask:

```text
Did a provider version change?

Was the change intentional?

Does the configuration constraint permit it?

Was an upgrade deliberately requested?
```

Do not hide unexpected dependency changes inside unrelated infrastructure pull requests.

---

# 36. VALIDATION

A pipeline can run:

```bash
terraform validate
```

to validate configuration-level correctness after appropriate initialization.

Validation is useful, but its scope is limited.

A successful result does not prove:

```text
Correct Account

Correct State

Correct Permissions

Safe Plan

Healthy Infrastructure
```

---

# 37. STATIC SECURITY CHECKS

Terraform pipelines can include static security analysis.

Possible checks may detect selected patterns such as:

```text
Public Exposure

Unencrypted Storage

Overly Broad Network Rules

Missing Required Settings

Unsafe Defaults
```

The exact tools and rules depend on the organization.

Static security analysis should be treated as evidence, not as proof that infrastructure is secure.

---

# 38. POLICY CONCEPTS

Policy-as-code allows organizations to express selected infrastructure rules programmatically.

Conceptually:

```text
Terraform Plan
↓
Policy Evaluation
↓
Allowed / Warned / Blocked
```

Examples of policy intentions may include:

```text
Approved Regions Only

Required Encryption

Required Tags

No Public Database Exposure

Restricted Resource Types

Required Backup Settings
```

Policy systems and enforcement capabilities differ by platform.

---

# 39. POLICY IS NOT ARCHITECTURE

A policy can reject known undesirable conditions.

It cannot automatically prove that the entire architecture is correct.

For example:

```text
Policy:
Storage must be encrypted.
```

Passing that policy does not prove:

```text
Correct IAM

Correct Network Design

Correct Backup

Correct Recovery

Correct Application Architecture
```

Policy is one control layer.

---

# 40. ADVISORY AND BLOCKING CONTROLS

Policy systems may support different enforcement behavior.

Conceptually:

```text
Advisory
↓
Warn
↓
Run May Continue
```

versus:

```text
Mandatory
↓
Violation
↓
Run Stops
```

Some platforms also support controlled override mechanisms.

The exact terminology depends on the policy system.

---

# 41. POLICY OVERRIDES REQUIRE GOVERNANCE

If a blocking policy can be overridden, an override should not mean:

```text
The policy was inconvenient.
```

An override should answer:

```text
Why is the exception necessary?

Who authorized it?

What risk is accepted?

How long is the exception valid?

Is remediation required?

Is the override recorded?
```

Exceptions should remain exceptional.

---

# 42. TERRAFORM PLAN IN CI

Automation can create a saved plan:

```bash
terraform plan -input=false -out=tfplan
```

This produces a plan intended for later application.

A CI system can also produce a speculative plan for pull-request review without intending to apply that exact plan.

Understand the distinction.

---

# 43. SPECULATIVE PLAN

A pull-request plan may be used to answer:

```text
If this configuration were applied against the current target,
what would Terraform propose?
```

That is useful review evidence.

But infrastructure or state may change before the pull request is finally applied.

Therefore an old speculative plan should not automatically be treated as permanent authorization.

---

# 44. FINAL APPLY PLAN

The final apply workflow must ensure that the actual infrastructure operation is still acceptable at execution time.

A safe model is:

```text
Reviewed Source Revision
↓
Final Plan
↓
Review / Approval
↓
Apply That Controlled Plan
```

Do not assume a plan generated hours or days earlier remains accurate after unrelated infrastructure changes.

---

# 45. SAVED PLAN ARTIFACT

A saved plan can connect review and execution.

Conceptually:

```text
terraform plan -out=tfplan
↓
Review Plan
↓
Approve
↓
terraform apply tfplan
```

When Terraform applies a saved plan, it executes the operations represented by that plan rather than generating a new interactive plan at that point.

This makes saved plans useful in controlled automation.

---

# 46. SAVED PLAN SECURITY

Saved plan files can contain sensitive information.

Treat them as potentially sensitive artifacts.

Do not automatically:

```text
Commit tfplan to Git

Upload tfplan publicly

Publish tfplan in issue attachments

Retain tfplan indefinitely
```

Artifact retention and access should be deliberate.

---

# 47. HUMAN-READABLE PLAN

Reviewers need understandable plan information.

The review should expose enough information to identify:

```text
Resources Created

Resources Updated

Resources Replaced

Resources Destroyed

Sensitive Changes Where Safely Displayable

Important Attribute Changes
```

Do not reduce review to:

```text
Plan generated successfully.
```

---

# 48. MACHINE-READABLE PLAN

Terraform can represent a saved plan in machine-readable JSON using appropriate CLI functionality.

This enables automation to inspect planned actions.

For example, a pipeline can reason about:

```text
Create

Update

Delete

Replacement
```

and use that information for policy or risk controls.

Machine analysis complements human review.

---

# 49. PLAN REVIEW IS INFRASTRUCTURE REVIEW

The reviewer should ask:

```text
Does this plan match the stated intent?

Why is every changed resource changing?

Are any resources being destroyed?

Are any resources being replaced?

Is stateful infrastructure affected?

Are identities changing?

Are network boundaries changing?

Are security controls weakening?

Will DNS or endpoints change?

Could availability be reduced?

Could data be lost?

Could cost increase materially?
```

The plan is an operational artifact.

---

# 50. EXPECTED CHANGE BUDGET

Before planning, define expected change.

Example:

```text
Intent:
Increase application replicas from 3 to 4.
```

Expected infrastructure effect:

```text
One additional application instance
or equivalent scaling change.
```

Observed plan:

```text
1 create
2 replace
1 destroy
```

The correct response is:

```text
STOP
```

The mismatch itself is evidence.

---

# 51. DESTRUCTIVE CHANGE

A destructive plan may contain:

```text
Delete

Replace

Recreate

Remove Stateful Resource

Change Identity-Bearing Resource

Remove Network Path
```

Not all destructive operations are wrong.

But they require deliberate review.

---

# 52. DESTRUCTION MUST NEVER HIDE IN THE SUMMARY

Suppose a plan says:

```text
Plan: 18 to add, 7 to change, 1 to destroy.
```

The most consequential operation may be the single destruction.

Review counts do not represent risk.

One destroyed database may matter more than 100 newly created stateless resources.

---

# 53. REPLACEMENT IS ALSO DESTRUCTIVE

A replacement is not merely an update.

Conceptually:

```text
Existing Resource
↓
Replacement Required
↓
Old Resource Removed
+
New Resource Created
```

The exact order depends on lifecycle configuration, dependencies, and provider behavior.

Treat replacement as a destructive event until its operational impact is understood.

---

# 54. DESTRUCTIVE CHANGE GATE

A pipeline may classify plans containing destructive actions for additional review.

Conceptually:

```text
Plan
↓
Contains Delete / Replacement?
├── No → Normal Review
└── Yes
    ↓
    Additional Approval
    ↓
    Data / Availability Review
```

The exact implementation depends on the delivery platform.

---

# 55. APPROVAL GATES

An approval gate separates:

```text
Terraform proposes change
```

from:

```text
Terraform is authorized to execute change
```

This distinction matters.

A pipeline should not automatically interpret:

```text
Plan succeeded.
```

as:

```text
Apply authorized.
```

---

# 56. APPROVAL SHOULD HAVE CONTEXT

An approver needs evidence.

At minimum:

```text
Source Revision

Target Environment

Terraform Plan

Policy Results

Security Results

Expected Impact

Destructive Actions

Verification Plan
```

An approval button without context provides weak protection.

---

# 57. APPROVAL IS NOT CEREMONIAL

Bad approval:

```text
Pipeline is green.
Approve.
```

Better approval:

```text
Intent understood.

Plan reviewed.

Unexpected actions explained.

Risk understood.

Recovery considered.

Correct environment confirmed.

Proceed.
```

Human review is valuable only when the human has useful evidence.

---

# 58. SEPARATION OF DUTIES

Some organizations require the engineer who proposes a production change to be different from the person who approves it.

Conceptually:

```text
Author
↓
Pull Request
↓
Reviewer
↓
Infrastructure Plan
↓
Authorized Approver
↓
Apply
```

The required separation depends on organizational risk and compliance requirements.

The broader principle is preventing one uncontrolled action from carrying excessive authority.

---

# 59. CI EXECUTION

CI turns infrastructure delivery into a reproducible workflow.

Instead of every engineer manually performing:

```text
terraform init
terraform plan
terraform apply
```

from an uncontrolled workstation, the organization can define a consistent execution environment.

Benefits may include:

```text
Known Terraform Version

Known Provider Dependencies

Controlled Credentials

Central Logs

Repeatable Checks

Approval Enforcement

Change History
```

---

# 60. CI DOES NOT AUTOMATICALLY MAKE TERRAFORM SAFE

A dangerous pipeline can execute mistakes faster than a human.

For example:

```text
Merge
↓
Auto Apply Production
↓
No Plan Review
↓
Database Destroyed
```

Automation amplifies both good and bad process.

The goal is **controlled automation**.

---

# 61. PIPELINE STAGES

A practical pipeline can separate stages such as:

```text
Validate
↓
Plan
↓
Review
↓
Apply
↓
Verify
```

Each stage should have explicit entry and exit conditions.

---

# 62. VALIDATE STAGE

Possible responsibilities:

```text
Checkout Source

Verify Terraform Version

terraform fmt -check

terraform init

terraform validate

Static Security Checks

Policy Prechecks
```

Expected outcome:

```text
Configuration is suitable to proceed to planning.
```

Not:

```text
Infrastructure is proven safe.
```

---

# 63. PLAN STAGE

Responsibilities:

```text
Authenticate

Select Correct Environment

Access Correct Backend

Initialize

Load Approved Inputs

Generate Plan

Capture Reviewable Output

Store Controlled Plan Artifact if Applicable
```

Expected outcome:

```text
Proposed infrastructure changes are visible.
```

---

# 64. REVIEW STAGE

Responsibilities:

```text
Compare Intent to Plan

Identify Destruction

Identify Replacement

Review Security

Review Availability

Review Data Risk

Review Cost

Review Policy Results

Review Environment
```

Expected outcome:

```text
The proposed change is understood.
```

---

# 65. APPLY STAGE

Responsibilities:

```text
Confirm Approval

Confirm Correct Artifact / Revision

Acquire State Lock Where Supported

Execute Terraform Apply

Capture Result

Protect Logs

Record Failure if Any
```

Expected outcome:

```text
Terraform has attempted the authorized infrastructure operations.
```

That is not yet final success.

---

# 66. VERIFY STAGE

Responsibilities:

```text
Inspect Infrastructure

Check Terraform State

Check Service Health

Check Load Balancer Health

Check Monitoring

Check Logs

Check Critical Dependency Paths

Check Intended Capacity / Configuration
```

Expected outcome:

```text
The intended production result is proven.
```

---

# 67. CHANGE ARTIFACTS

A Terraform delivery process produces evidence.

Useful artifacts may include:

```text
Commit SHA

Pull Request

Terraform Version

Provider Lock File

Plan

Plan Summary

Policy Results

Security Results

Approval Record

Apply Log

Verification Evidence
```

These artifacts help answer:

```text
What changed?

Who approved it?

What was expected?

What actually happened?
```

---

# 68. ARTIFACTS HAVE DIFFERENT SENSITIVITY

Do not expose every artifact equally.

For example:

```text
Pull Request Metadata
→ often broadly visible internally
```

while:

```text
Saved Terraform Plan
→ potentially sensitive
```

and:

```text
Pipeline Credential
→ secret
```

Artifact handling is part of pipeline security.

---

# 69. SOURCE REVISION

Every plan should be traceable to the exact source revision that produced it.

Conceptually:

```text
Commit A
↓
Plan A
```

Do not accidentally:

```text
Review Plan A
↓
Change Source to Commit B
↓
Apply B without equivalent review
```

The reviewed configuration and executed configuration must remain connected.

---

# 70. PLAN AND APPLY IDENTITY

Another important relationship is:

```text
Plan
+
Environment
+
State
+
Inputs
+
Provider Context
```

A plan only makes sense in its execution context.

Do not treat a plan as a context-free file.

---

# 71. AUTOMATED PLAN COMMENTS

Some CI workflows publish Terraform plan information directly to the pull request.

This can improve visibility.

But ensure that sensitive information is not exposed through:

```text
PR Comments

CI Logs

Artifacts

Notifications
```

Convenient review must not create data leakage.

---

# 72. PIPELINE LOGGING

Pipeline logs should answer:

```text
Which job ran?

Which revision?

Which environment?

Which stage?

Did Terraform initialize?

Did validation pass?

Did plan succeed?

Was approval granted?

Did apply succeed?

Did verification succeed?
```

But logs should avoid unnecessarily exposing secrets.

---

# 73. PIPELINE CREDENTIALS

A Terraform pipeline may require credentials for:

```text
Cloud Provider

Terraform Backend

Secret Store

Artifact Store

Policy Service

Git Repository
```

These are different trust relationships.

Do not assume one credential should access everything.

---

# 74. CREDENTIAL SCOPE

For each credential determine:

```text
Identity

Purpose

Environment

Permissions

Lifetime

Storage

Rotation / Expiration

Auditability
```

This makes pipeline identity understandable.

---

# 75. PIPELINE CREDENTIAL TROUBLESHOOTING

Symptom:

```text
Terraform pipeline cannot access provider.
```

Do not immediately regenerate credentials.

Investigate:

```text
Which authentication step failed?

Which identity should be used?

Was identity exchange successful?

Is credential expired?

Is secret unavailable?

Is environment variable missing?

Is trust policy incorrect?

Is this authentication or authorization?
```

Collect evidence first.

---

# 76. BACKEND CREDENTIALS AND PROVIDER CREDENTIALS MAY DIFFER

Terraform may need one trust path to access state and another to modify infrastructure.

Conceptually:

```text
Terraform
├── Backend Access
│   └── State
│
└── Provider Access
    └── Infrastructure API
```

A backend access failure is not automatically a provider failure.

---

# 77. STATE ACCESS FAILURE

Symptoms may include:

```text
Cannot read state

Cannot acquire lock

Backend authentication failure

Backend authorization failure

Backend unavailable
```

Troubleshoot:

```text
Backend Configuration
↓
Network Access
↓
Backend Identity
↓
Permissions
↓
State Location
↓
Locking Service if Applicable
↓
Backend Health
```

Do not modify infrastructure before understanding whether Terraform has the correct state.

---

# 78. NEVER APPLY WHEN EXPECTED STATE CANNOT BE CONFIRMED

Suppose:

```text
Cloud infrastructure exists.

Pipeline cannot read expected state.

Terraform appears ready to create resources.
```

Stop.

The dangerous response is:

```text
Maybe Terraform will figure it out.
```

It will operate according to the state and configuration available to it.

State uncertainty is an infrastructure ownership problem.

---

# 79. CONCURRENT OPERATIONS

Two Terraform runs against the same state can create coordination problems.

Conceptually:

```text
Pipeline A
↓
Reads State
↓
Plans Change A
```

while:

```text
Pipeline B
↓
Reads Same State
↓
Plans Change B
```

If both attempt state-writing operations concurrently, safe coordination becomes essential.

---

# 80. STATE LOCKING

Where supported, Terraform automatically uses backend locking for operations that can write state.

Conceptually:

```text
Pipeline A
↓
Acquire Lock
↓
Apply
↓
Update State
↓
Release Lock
```

while:

```text
Pipeline B
↓
Attempts Lock
↓
Cannot Proceed Concurrently
```

Not every backend has identical locking capabilities.

Verify the selected backend.

---

# 81. LOCKING DOES NOT SOLVE EVERY CONCURRENCY PROBLEM

Consider:

```text
Plan A generated at 10:00

Plan B applied at 10:05

Plan A approved at 10:10
```

Even if apply operations are serialized, Plan A may have been generated against an earlier infrastructure condition.

Therefore safe delivery also needs:

```text
Plan Freshness

Source Revision Control

State Awareness

Execution Coordination
```

Locking is necessary in many workflows but not sufficient by itself.

---

# 82. PIPELINE SERIALIZATION

Some teams serialize apply operations for a particular state or environment.

Conceptually:

```text
Production State
↓
One Apply at a Time
```

This reduces conflicting infrastructure mutations.

The exact mechanism depends on the CI/CD or Terraform platform.

---

# 83. CONCURRENT OPERATION TROUBLESHOOTING

Symptom:

```text
Pipeline waits for or fails to acquire state lock.
```

Investigate:

```text
Which run owns the lock?

Is it still running?

Which environment?

Which state?

Did a previous run fail?

Did automatic unlock fail?

Is backend healthy?
```

Do not immediately disable locking.

---

# 84. FORCE UNLOCK IS RECOVERY, NOT NORMAL DELIVERY

If a state lock is genuinely stale, Terraform provides recovery mechanisms.

Before forcing unlock:

```text
Identify Lock

Identify Owner

Confirm Original Operation Ended

Confirm No Active Writer

Confirm Correct State

Record Recovery Action
```

Unlocking a state actively used by another process can allow multiple writers.

---

# 85. ENVIRONMENT MISMATCH

One of the most dangerous Terraform pipeline failures is correct code targeting the wrong environment.

Example:

```text
Pull Request:
Development cleanup
```

Actual pipeline context:

```text
Production credentials
+
Production state
```

Terraform may produce a completely valid destructive plan.

The problem is not Terraform syntax.

The problem is execution context.

---

# 86. ENVIRONMENT IDENTITY SHOULD BE PROVEN

Before apply, verify multiple independent signals where practical:

```text
Pipeline Environment

Backend / State Identifier

Cloud Account / Project / Subscription

Region

Credential Identity

Expected Resource Naming / Tags
```

Do not rely on one variable called:

```text
ENV=production
```

as the only evidence.

---

# 87. ENVIRONMENT MISMATCH TROUBLESHOOTING

If a plan contains resources from the wrong environment:

```text
STOP
↓
Do Not Apply
↓
Inspect Working Directory
↓
Inspect Backend
↓
Inspect State
↓
Inspect Variables
↓
Inspect Provider Configuration
↓
Inspect Credentials
↓
Inspect Account / Project / Subscription
↓
Correct Context
↓
Generate New Plan
```

Never attempt to "fix" a wrong-environment plan by manually ignoring resources.

---

# 88. DRIFT DETECTION

Infrastructure can change outside the normal Terraform workflow.

Possible causes:

```text
Emergency Manual Change

Cloud Console Change

External Automation

Provider-Side Change

Another Terraform Configuration

Incident Response

Unauthorized Modification
```

Delivery workflows should account for drift.

---

# 89. DRIFT CHECKS

A scheduled or event-driven workflow can periodically compare configuration with observed infrastructure through Terraform planning or platform-specific drift capabilities.

Conceptually:

```text
Scheduled Check
↓
Refresh / Observe Infrastructure
↓
Compare With Configuration
↓
No Difference?
├── Yes → Record Healthy
└── No
    ↓
    Report Drift
    ↓
    Investigate
```

Do not automatically remediate every detected difference without understanding its cause.

---

# 90. DRIFT IS AN OWNERSHIP SIGNAL

Unexpected drift asks:

```text
Who changed this resource?

Why?

Was the change authorized?

Is Terraform still authoritative?

Is another system managing the same attribute?

Was this an incident mitigation?
```

Drift may reveal process problems, not merely configuration differences.

---

# 91. DRIFT DETECTION DOES NOT MEAN AUTOMATIC APPLY

Dangerous workflow:

```text
Drift detected
↓
Automatically apply Terraform
```

Imagine an incident responder manually changed a production route to restore service.

An automatic Terraform job could revert it immediately.

A safer model is:

```text
Drift Detected
↓
Classify
↓
Determine Intent
↓
Choose Reconciliation Direction
↓
Review
↓
Apply if Appropriate
```

---

# 92. ROLLBACK LIMITATIONS

Application deployments often support a mental model such as:

```text
Version 12 fails
↓
Deploy Version 11
```

Infrastructure is more complicated.

Terraform does not provide a universal:

```text
terraform rollback
```

that safely restores every previous infrastructure condition.

Infrastructure rollback must be reasoned about resource by resource.

---

# 93. WHY INFRASTRUCTURE ROLLBACK IS DIFFICULT

Suppose a change:

```text
Replaces a database

Migrates storage

Changes network addressing

Deletes a resource

Rotates identity

Changes DNS

Changes provider behavior
```

Returning Git to the previous commit does not necessarily reconstruct the previous operational reality.

Therefore:

```text
Git Revert
≠
Infrastructure Rollback
```

---

# 94. REVERTING CONFIGURATION

A Git revert can restore earlier Terraform configuration.

Then a new Terraform plan can show what Terraform proposes to make infrastructure match that earlier configuration.

This is valuable.

But the plan must still be reviewed.

Conceptually:

```text
Bad Change Applied
↓
Revert Configuration
↓
terraform plan
↓
Review Proposed Recovery
↓
Apply if Safe
↓
Verify
```

Do not skip the new plan.

---

# 95. WHY OLD CONFIGURATION MAY NOT RESTORE OLD REALITY

After an infrastructure change:

```text
Resource IDs may have changed.

Data may have changed.

A deleted object may be unrecoverable.

DNS may have propagated.

External systems may reference new endpoints.

Provider defaults may differ.

State may now represent new objects.
```

Therefore a previous Git commit is not a time machine.

---

# 96. ROLLBACK VERSUS RECOVERY

Use these concepts carefully.

**Rollback** means returning toward a previous configuration or deployment state.

**Recovery** means restoring acceptable service after failure.

They may not be the same.

Example:

```text
New Database Configuration Fails
↓
Previous Database Cannot Simply Be Recreated With Data
↓
Restore Backup
↓
Reconnect Application
↓
Verify
```

That is a recovery process involving data restoration, not merely Terraform configuration rollback.

---

# 97. INFRASTRUCTURE RECOVERY

Recovery planning should answer:

```text
What can be recreated?

What must be restored?

What identities must be preserved?

What data is external to Terraform?

Which resources have backups?

Which dependencies must be restored first?

How will Terraform state be reconciled afterward?
```

Terraform is one component of recovery.

---

# 98. RECREATABLE INFRASTRUCTURE

Some infrastructure may be safely recreated.

Examples might include certain:

```text
Stateless Compute

Ephemeral Workers

Replaceable Load-Balancer Targets

Temporary Development Resources
```

But even stateless infrastructure may have dependencies.

Verify rather than assume.

---

# 99. STATEFUL INFRASTRUCTURE

Stateful systems require additional recovery planning.

Examples include:

```text
Databases

Persistent Volumes

Object Storage

Message Systems

Stateful Services
```

Terraform can create infrastructure containers for data.

Terraform does not automatically guarantee recovery of the business data stored inside them.

---

# 100. BACKUP AND TERRAFORM STATE ARE DIFFERENT

Terraform state answers:

```text
What infrastructure objects does Terraform manage?
```

A data backup answers:

```text
How can required application data be recovered?
```

Do not confuse them.

---

# 101. FAILED APPLY

Terraform apply may fail after some operations have already succeeded.

Example:

```text
Create Network
✓

Create Subnets
✓

Create Security Controls
✓

Create Load Balancer
✗

Configure DNS
not reached
```

This is a partial apply.

---

# 102. TERRAFORM APPLY IS NOT ONE UNIVERSAL TRANSACTION

Do not assume:

```text
One resource failed
↓
Terraform automatically reverses everything
```

Infrastructure provider APIs do not behave like one global database transaction.

After a failure, some remote changes may remain.

---

# 103. PARTIAL APPLY RECOVERY MODEL

Use:

```text
Apply Fails
↓
Stop Additional Changes
↓
Read Exact Error
↓
Determine Which Operations Succeeded
↓
Inspect Terraform State
↓
Inspect Real Infrastructure
↓
Determine Service Impact
↓
Correct Root Cause
↓
Generate New Plan
↓
Review New Plan
↓
Continue / Recover Deliberately
↓
Verify
```

Do not immediately destroy the environment.

---

# 104. STATE AFTER PARTIAL APPLY

Terraform generally records successful managed-resource changes as operations progress, but failures can still create situations requiring careful reconciliation, particularly when provider/API behavior or state persistence itself encounters problems.

The safe response is evidence-driven:

```text
What does state contain?

What does the provider contain?

What does the next plan propose?
```

Never assume.

---

# 105. FAILED PARTIAL APPLY TROUBLESHOOTING

Suppose the pipeline reports:

```text
3 resources created
1 resource failed
```

Investigate:

```text
Which three succeeded?

Are they in state?

Do they exist remotely?

Why did the fourth fail?

Was failure authentication?

Authorization?

Quota?

Invalid configuration?

Dependency readiness?

Provider/API failure?

What does a fresh plan show?
```

Then choose the smallest safe corrective action.

---

# 106. DO NOT DELETE STATE AFTER PARTIAL FAILURE

Deleting state can cause Terraform to lose management bindings for infrastructure that actually exists.

That can turn:

```text
One failed resource
```

into:

```text
Unknown infrastructure ownership
+
Duplicate creation risk
+
Manual reconciliation
```

State deletion is not normal failure recovery.

---

# 107. DO NOT DESTROY EVERYTHING AUTOMATICALLY

A development lab may sometimes be rebuilt.

Production requires a different mindset.

Destroying everything can:

- increase downtime
- destroy data
- remove forensic evidence
- change resource identities
- break dependencies
- make recovery harder

Investigate before choosing remediation.

---

# 108. UNEXPECTED DESTRUCTIVE PLAN

Scenario:

```text
Requested Change:
Add one monitoring tag.
```

Plan:

```text
2 to add
3 to change
4 to destroy
```

This should trigger investigation.

---

# 109. DESTRUCTIVE PLAN TROUBLESHOOTING

Use:

```text
Unexpected Destruction
↓
Identify Every Destroyed / Replaced Address
↓
Find Triggering Configuration Change
↓
Check Resource Address Changes
↓
Check count / for_each Identity
↓
Check Module Refactor
↓
Check Provider Upgrade
↓
Check State
↓
Check Environment
↓
Check Drift
↓
Check Immutable Attributes
↓
Determine Root Cause
```

Do not approve because "Terraform knows what it is doing."

Terraform is executing the model it has been given.

---

# 110. CI FAILURE CLASSIFICATION

A failed Terraform pipeline should first be classified.

Possible layers:

```text
Source / Git

CI Platform

Terraform CLI

Module / Configuration

Backend

State Lock

Provider Authentication

Provider Authorization

Provider API

Quota

Policy

Infrastructure

Post-Apply Verification
```

Correct classification prevents random remediation.

---

# 111. PIPELINE FAILURE BEFORE PLAN

If failure occurs before a plan exists, investigate:

```text
Checkout

Terraform Version

Initialization

Provider Download

Module Download

Backend

Credentials

Validation

Security Checks
```

There is no infrastructure plan yet.

Do not troubleshoot this as an apply failure.

---

# 112. PIPELINE FAILURE DURING PLAN

Investigate:

```text
State Access

Provider Read Operations

Authentication

Authorization

Variables

Configuration

Dependency Graph

Provider Errors
```

Remember that planning can require remote reads.

---

# 113. PIPELINE FAILURE DURING APPLY

Now determine:

```text
What already changed?

What failed?

What remains pending?

What state was written?

What does infrastructure show?

What is service impact?
```

This is operationally more serious than a validation failure.

---

# 114. PIPELINE FAILURE DURING VERIFICATION

Terraform may have succeeded while verification fails.

Example:

```text
terraform apply
✓

Load balancer created
✓

Targets healthy
✗
```

Do not report the delivery as successful.

Terraform resource success and application readiness are different states.

---

# 115. POST-APPLY VERIFICATION

Verification should test the requirement that caused the change.

If the requirement was:

```text
Increase application capacity.
```

verify:

```text
Expected capacity exists.

Instances are healthy.

Load balancer recognizes them.

Application responds.

Monitoring shows expected behavior.
```

Do not stop at:

```text
Terraform says 1 added.
```

---

# 116. VERIFY FROM OUTSIDE TERRAFORM

Terraform is one source of evidence.

Use independent evidence where appropriate:

```text
Cloud Provider API

Service Health Endpoint

DNS Resolution

Network Test

Application Request

Monitoring

Logs

Metrics
```

The verification method should match the change.

---

# 117. CHANGE OBSERVATION

Some failures appear after the apply.

A change may initially look healthy and later cause:

```text
Latency

Resource Exhaustion

Error Rate Increase

Connection Failure

Cost Increase

Capacity Problem
```

Production delivery should include an observation period appropriate to the risk.

---

# 118. SAFE CHANGE SIZE

Smaller infrastructure changes are often easier to:

```text
Review

Understand

Approve

Troubleshoot

Recover
```

Avoid combining unrelated operations such as:

```text
Network redesign

Database replacement

Provider major upgrade

Module refactor

Security-policy rewrite
```

into one change unless there is a strong reason.

---

# 119. SEPARATE REFACTOR FROM BEHAVIORAL CHANGE

A particularly useful discipline is:

```text
Refactor Terraform Structure
↓
Plan Shows No Infrastructure Change
↓
Merge
```

then separately:

```text
Change Infrastructure Behavior
↓
Review Actual Infrastructure Plan
```

This reduces ambiguity.

---

# 120. PROVIDER UPGRADES AS DELIVERY CHANGES

A provider upgrade can change planning or resource behavior even when infrastructure configuration appears mostly unchanged.

Therefore:

```text
Provider Upgrade
=
Infrastructure Delivery Change
```

Review:

```text
Version Change

Upgrade Notes

Lock File

Plan Difference

Deprecated Behavior

Replacement Risk
```

---

# 121. MODULE UPGRADES AS DELIVERY CHANGES

A module version change can alter:

```text
Resources

Defaults

Naming

Tags

Security Controls

Lifecycle Behavior
```

Therefore module upgrades deserve explicit plan review.

Do not hide them inside unrelated changes.

---

# 122. PRODUCTION CHANGE WINDOW

Some infrastructure changes may need controlled timing.

Examples:

```text
Database modification

Network routing change

Cluster upgrade

Major load balancer change

Stateful resource replacement
```

The change window should consider:

```text
User Impact

Staff Availability

Rollback / Recovery Time

Dependency Teams

Monitoring Coverage
```

Not every Terraform change requires a formal maintenance window, but risk should determine process.

---

# 123. EMERGENCY CHANGES

Incidents sometimes require urgent infrastructure modification.

Urgency may reduce process latency.

It should not eliminate accountability.

A useful emergency model is:

```text
Incident
↓
Minimum Necessary Change
↓
Authorized Emergency Path
↓
Record Action
↓
Verify Recovery
↓
Reconcile Terraform
↓
Post-Incident Review
```

---

# 124. MANUAL EMERGENCY CHANGE

Suppose an engineer changes a route manually during an outage.

After service recovery:

```text
Manual Change
↓
Document
↓
Determine Whether Temporary or Permanent
↓
Update Terraform if Permanent
or
Revert Manual Change if Temporary
↓
Plan
↓
Reconcile
```

Do not leave unexplained drift indefinitely.

---

# 125. POLICY EXAMPLE: REQUIRED TAGGING

An organization may require metadata such as:

```text
Environment

Owner

Service

Cost Center
```

A policy could inspect proposed resources and reject those missing required metadata.

The value is consistency.

But policy logic should be tested just like other code.

---

# 126. POLICY EXAMPLE: APPROVED REGION

Suppose an organization allows production only in approved regions.

A policy can inspect planned infrastructure and block unsupported locations.

This helps prevent accidental deployment.

But the policy must correctly understand:

```text
Provider

Resource

Region

Exceptions
```

Poor policy can create false confidence.

---

# 127. POLICY EXAMPLE: PUBLIC EXPOSURE

A policy may attempt to detect:

```text
Publicly Accessible Database

Broad Ingress Rule

Public Storage
```

This can prevent common mistakes.

However, policy checks should not replace architecture review.

Network exposure can depend on several interacting resources.

---

# 128. POLICY TESTING

Policies are production code.

Test:

```text
Known Allowed Plan
→ Pass
```

```text
Known Forbidden Plan
→ Fail
```

```text
Exception Case
→ Expected Behavior
```

A policy that has never been tested may block safe work or allow unsafe work.

---

# 129. PIPELINE CODE IS PRODUCTION CODE

Terraform may be correct while the pipeline is wrong.

Pipeline errors can include:

```text
Wrong Directory

Wrong Variable File

Wrong Backend

Wrong Credentials

Wrong Artifact

Wrong Branch

Wrong Environment

Skipped Approval

Unprotected Apply Job
```

Review pipeline configuration with the same seriousness as Terraform.

---

# 130. APPLY PERMISSIONS

A useful control is separating:

```text
Permission to Propose
```

from:

```text
Permission to Apply Production
```

Developers may be able to open pull requests and generate plans without automatically receiving unrestricted production mutation rights.

Exact permission models depend on the platform.

---

# 131. PROTECTED PRODUCTION DELIVERY

A production apply path may require:

```text
Protected Branch

Required Reviews

Successful Validation

Successful Security Checks

Successful Policy Checks

Approved Plan

Authorized Identity

Environment Approval
```

The specific combination depends on organizational risk.

---

# 132. DO NOT PUT PRODUCTION APPLY CREDENTIALS IN UNTRUSTED PR EXECUTION

Pull requests can contain code that changes pipeline behavior.

Be extremely careful when workflows triggered by untrusted or externally contributed code can access privileged infrastructure credentials.

The trust boundary is:

```text
Untrusted Code
↓
CI Runner
↓
Credential?
```

Privileged credentials should not be exposed merely because a pull request needs validation.

---

# 133. PLAN-ONLY VERSUS APPLY AUTHORITY

A strong architecture may distinguish:

```text
Pull Request Pipeline
↓
Plan Authority
```

from:

```text
Protected Apply Pipeline
↓
Production Mutation Authority
```

This limits the consequences of unreviewed code.

---

# 134. PIPELINE RUNNER SECURITY

A runner executing Terraform may have access to:

```text
Cloud Credentials

Backend State

Plan Artifacts

Repository

Internal Network
```

Therefore runner compromise can become infrastructure compromise.

Protect:

```text
Runner Isolation

Software Supply Chain

Credential Lifetime

Network Access

Logs

Artifacts
```

according to risk.

---

# 135. THIRD-PARTY ACTIONS AND PIPELINE DEPENDENCIES

CI pipelines often consume external actions, plugins, containers, or scripts.

These become part of the infrastructure delivery supply chain.

Evaluate:

```text
Source

Version Pinning

Trust

Permissions

Update Process
```

Do not treat pipeline dependencies as harmless convenience.

---

# 136. TERRAFORM VERSION PINNING

A team should deliberately manage Terraform CLI compatibility.

The pipeline should not silently switch versions without review.

A version change can affect:

```text
Language Behavior

Planning Behavior

State Compatibility

Available Features

Provider Compatibility
```

Version changes deserve controlled testing.

---

# 137. ENVIRONMENT PROMOTION

A common delivery model promotes a change through:

```text
Development
↓
Staging
↓
Production
```

This does not necessarily mean copying state or copying plan files.

It means progressively validating the same intended infrastructure change under increasingly production-like conditions.

---

# 138. DO NOT PROMOTE STATE BETWEEN ENVIRONMENTS

Environment promotion normally means promoting:

```text
Code

Module Version

Configuration Intent
```

not:

```text
Development State
→ Production State
```

Each environment maintains its own infrastructure ownership and state.

---

# 139. DO NOT ASSUME THE SAME PLAN ACROSS ENVIRONMENTS

Development and production may differ in:

```text
Capacity

Network IDs

Resource Counts

Regions

Existing State

Data

Provider Context
```

Therefore production requires its own plan.

A development plan is evidence about development.

It is not the production plan.

---

# 140. PROMOTION EVIDENCE

Before production, useful evidence may include:

```text
Development Tests Passed

Staging Apply Succeeded

Staging Verification Passed

Production Plan Reviewed

Security Checks Passed

Policy Checks Passed

Recovery Procedure Ready
```

The exact requirements should match change risk.

---

# 141. CHANGE ARTIFACT IMMUTABILITY

Once a plan has been approved for apply, uncontrolled modification of its associated source or inputs should not silently occur.

Think:

```text
Approved Revision
+
Approved Environment
+
Approved Plan
```

as a controlled change unit.

If material context changes, regenerate and review.

---

# 142. STALE PLAN THINKING

A plan can become operationally stale if the environment changes before execution.

Possible causes:

```text
Another Terraform Apply

Manual Infrastructure Change

Provider-Side Change

Changed State

Changed Dependencies
```

Do not assume that approval lasts forever regardless of changing conditions.

---

# 143. PLAN REVIEW CHECKLIST

Before approving:
