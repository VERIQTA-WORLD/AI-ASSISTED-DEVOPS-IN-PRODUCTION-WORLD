# PART 2: LINUX INTERNALS AND ADVANCED SYSTEM TROUBLESHOOTING

## Goal

Move beyond basic Linux administration into deeper system-level investigation.

At the Junior level, you learned to inspect Linux systems safely. You learned how to identify processes, check CPU and memory use, inspect filesystems, examine services, read logs, investigate common resource problems, and collect evidence before changing a system.

At Mid-Level, the expectation changes.

It is no longer enough to report:

```text
CPU is high.
```

or:

```text
Memory is almost full.
```

or:

```text
The service failed.
```

Those are observations.

A Mid-Level engineer must be able to continue:

```text
Which process is responsible?

What is that process doing?

Is it running, waiting, blocked, stopped, or repeatedly failing?

Is the host actually CPU-saturated?

Are runnable processes waiting for CPU time?

Is memory genuinely under pressure, or is Linux using available RAM for cache?

Is swap merely allocated, or is the system actively moving pages between memory and swap?

Is the filesystem out of capacity, out of inodes, or suffering from I/O latency?

Did the application fail first, or is systemd only reporting the consequence?

Did the kernel terminate the process?

Has the application exhausted a resource limit?

Is the application itself healthy but blocked on a dependency?
```

The troubleshooting model for this Part is:

```text
Application Symptom
        ↓
Process State
        ↓
Resource State
        ↓
Kernel / OS Evidence
        ↓
Application Evidence
        ↓
Dependency Evidence
        ↓
Evidence-Supported Root Cause
        ↓
Corrective Action
        ↓
Verification
```

The purpose of this Part is not to turn you into a Linux kernel developer.

The purpose is to teach you how to move below surface-level Linux metrics and investigate what the operating system is actually doing.

---

# 1. THINK IN SYSTEM BEHAVIOR, NOT COMMANDS

Linux troubleshooting is often taught as a collection of commands:

```text
top
free
df
ps
journalctl
systemctl
```

Knowing those commands is useful.

Knowing why to run them is more important.

A stronger troubleshooting model is:

```text
Question
↓
Required Evidence
↓
Inspection
↓
Observation
↓
Interpretation
↓
Next Question
```

For example:

> Is the application slow because CPU capacity is exhausted?

That question may require evidence about:

- number of CPUs
- CPU utilization
- runnable processes
- application CPU consumption
- thread behavior
- workload changes
- request latency

Only then should you decide whether CPU saturation is supported by the evidence.

Do not begin an investigation by running every Linux command you know.

Begin by understanding the symptom.

---

# 2. LINUX BENEATH THE APPLICATION

Applications run in user space, but they depend constantly on the operating system.

A simplified view is:

```text
Application
    ↓
Runtime / Libraries
    ↓
System Calls
    ↓
Linux Kernel
    ↓
CPU
Memory
Storage
Network
Devices
```

When an application:

- reads a file
- writes a log
- opens a network socket
- accepts a connection
- allocates memory
- starts another process
- sleeps
- waits for input
- writes to storage

the operating system participates.

This is why an application-level symptom can originate at another layer.

For example:

```text
Application Slow
```

could be caused by:

```text
Application Code
```

or:

```text
CPU Saturation
```

or:

```text
Memory Pressure
```

or:

```text
Storage Latency
```

or:

```text
Network Delay
```

or:

```text
Dependency Latency
```

or several of these together.

A Mid-Level engineer learns to distinguish among them using evidence.

---

# 3. START WITH THE SYMPTOM

Do not translate a user report directly into a technical diagnosis.

If someone reports:

> The server is slow.

That is not yet a useful technical description.

Clarify:

- Which application or operation is slow?
- What normally happens?
- What happens now?
- How long does it take?
- Is the issue affecting one user or everyone?
- One process or every workload on the host?
- One host or several hosts?
- Did the behavior begin suddenly or gradually?
- Is it constant or intermittent?
- Was there a recent deployment, configuration change, package update, traffic increase, or dependency incident?

Convert:

```text
Server is slow.
```

into something measurable, such as:

```text
HTTP requests that normally complete in approximately 200 ms
are now taking 8–12 seconds on all requests handled by one host.
```

That statement gives you something to investigate.

---

# 4. PROCESS LIFECYCLE AND PROCESS IDENTITY

A process is a running instance of a program.

Linux tracks information about each process, including:

- process ID
- parent process ID
- user and group identity
- process state
- memory mappings
- open file descriptors
- threads
- environment
- resource limits
- executable
- working directory
- scheduling information

A simplified lifecycle is:

```text
Process Created
      ↓
Runnable
      ↓
Scheduled on CPU
      ↓
Running
      ↓
Waiting / Sleeping
      ↓
Runnable Again
      ↓
Exit
      ↓
Parent Collects Exit Status
```

Understanding this lifecycle is important because a process that exists is not necessarily a healthy process.

---

## Parent and Child Relationships

Processes exist in relationships.

Inspect them with:

```bash
ps -eo pid,ppid,user,stat,etime,cmd
```

Important fields include:

```text
PID      Process ID
PPID     Parent Process ID
USER     Process owner
STAT     Process state
ETIME    Time since process start
CMD      Command
```

A process tree can help explain how a workload was started.

Where available:

```bash
pstree -p
```

or:

```bash
ps -ef --forest
```

may show relationships such as:

```text
systemd
  └─ application
       ├─ worker
       ├─ worker
       └─ worker
```

This matters when troubleshooting worker pools, wrapper scripts, child-process failures, service managers, and unexpected background processes.

---

## Do Not Identify a Process by PID Alone

PIDs are reused.

A statement such as:

```text
PID 4217 is our application.
```

may become false after the process exits and another process receives the same PID.

When identifying an important process, correlate several properties:

```bash
ps -p <PID> -o pid,ppid,user,lstart,etime,stat,cmd
```

Where appropriate, also inspect:

```bash
readlink -f /proc/<PID>/exe
```

and:

```bash
readlink -f /proc/<PID>/cwd
```

Permission restrictions may apply.

A stronger identity is therefore:

```text
PID
+
Executable
+
Command
+
User
+
Start Time
+
Service
```

---

# 5. PROCESS STATES: WHAT IS THE PROCESS ACTUALLY DOING?

Linux exposes process states through tools such as `ps` and `/proc/<PID>/status`.

Common states include:

```text
R    Running or runnable
S    Interruptible sleep
D    Uninterruptible sleep
T    Stopped or traced
Z    Zombie
```

Additional states and modifiers exist.

The goal is not to memorize letters.

The goal is to understand what they tell you about progress.

Linux documents process-state information through `/proc/<PID>/status`; for example, `R`, `S`, `D`, `Z`, and `T` represent different execution or waiting states.

---

## Running or Runnable

A process in `R` state may be:

- executing on a CPU
- ready to execute but waiting to be scheduled

Therefore:

```text
R
≠
This process is continuously executing right now.
```

If many processes remain runnable while all CPUs are heavily utilized, CPU contention becomes a stronger hypothesis.

---

## Interruptible Sleep

A process in `S` state is waiting.

That is often completely normal.

A server may sleep while waiting for:

- network requests
- timer expiration
- pipe input
- child-process activity
- another interruptible event

Therefore:

```text
Sleeping Process
≠
Broken Process
```

Many healthy applications spend much of their lives waiting.

---

## Uninterruptible Sleep

A process in `D` state is in an uninterruptible sleep in the kernel.

This is often associated with I/O or other kernel waits.

Do not simplify this into:

```text
D state means disk problem.
```

The correct question is:

```text
What is the task waiting for?
```

A high number of tasks in uninterruptible wait, combined with storage latency and application symptoms, may support an I/O-related hypothesis.

The state alone does not prove the root cause.

---

## Stopped Processes

A process may be stopped because of:

- job control
- debugging/tracing
- signals such as `SIGSTOP`

A stopped process can still exist in the process table while doing no useful work.

---

# 6. ZOMBIES AND ORPHANED PROCESSES

## Zombie Processes

A zombie is a process that has already exited but whose parent has not yet collected its termination status.

The sequence is:

```text
Child Process Runs
        ↓
Child Exits
        ↓
Kernel Retains Minimal Exit Information
        ↓
Parent Has Not Reaped Child
        ↓
Zombie Remains
```

A zombie is not a normally executing process.

It is not consuming CPU performing application work.

You can inspect zombies with:

```bash
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'
```

If zombies exist, investigate their parent processes.

The useful question is:

```text
Why is the parent failing to collect terminated children?
```

Sending `SIGKILL` to the zombie itself does not solve that problem because the child has already terminated.

---

## Orphaned Processes

An orphaned process is a process whose original parent exits while the child continues running.

Linux arranges for such processes to be adopted so their lifecycle can continue to be managed.

Operationally, unexpected orphaned processes may indicate:

- broken wrapper scripts
- incorrect process management
- unexpected background execution
- daemonization mistakes

The question is:

```text
Why is this process still running,
and what now controls its lifecycle?
```

---

# 7. SIGNALS AND PROCESS TERMINATION

Signals provide a mechanism for notifying processes about events.

Common signals encountered operationally include:

```text
SIGTERM
SIGINT
SIGHUP
SIGKILL
SIGSTOP
SIGCONT
```

Applications may handle some signals.

Others cannot be caught or ignored.

---

## SIGTERM

`SIGTERM` is conventionally used to request termination.

For example:

```bash
kill -TERM <PID>
```

A well-designed service may respond by:

- stopping new work
- completing in-flight work
- flushing state
- closing resources
- exiting cleanly

Exact behavior is application-specific.

---

## SIGKILL

`SIGKILL` forcefully terminates a process and cannot be handled by the target process.

```bash
kill -KILL <PID>
```

This prevents ordinary application-level cleanup.

Therefore this workflow is weak:

```text
Process Does Not Stop Immediately
↓
SIGKILL
```

A better investigation is:

```text
Termination Requested
↓
Did Signal Delivery Succeed?
↓
What State Is the Process In?
↓
What Do Shutdown Logs Show?
↓
Is the Process Waiting in the Kernel?
↓
Are Child Processes Involved?
↓
Is the Service Manager Restarting It?
```

Use forceful termination when justified, not as the first troubleshooting reaction.

---

# 8. THREADS

A process may contain multiple threads.

Threads share significant process resources, including the process address space and open file descriptors, while maintaining individual execution state.

This matters for troubleshooting because:

```text
Process CPU = 300%
```

on a multi-CPU Linux system may reflect several threads executing concurrently.

Inspect threads with:

```bash
ps -L -p <PID> -o pid,tid,psr,stat,pcpu,comm
```

or, where available:

```bash
top -H -p <PID>
```

Questions include:

- Is one thread consuming most CPU?
- Are many threads running?
- Are threads mostly sleeping?
- Did thread count grow unexpectedly?

Do not treat every multi-threaded application problem as a process-wide problem.

---

# 9. PROCESS PRIORITY

Linux scheduling includes priority concepts.

For normal scheduling policies, the `nice` value influences scheduling preference.

Inspect:

```bash
ps -eo pid,ni,pri,pcpu,stat,comm
```

A simplified conceptual relationship is:

```text
Lower Nice Value
      ↓
Greater Scheduling Preference

Higher Nice Value
      ↓
Lower Scheduling Preference
```

Do not change process priority simply because a workload consumes substantial CPU.

First ask:

- Is this workload expected?
- Is the host saturated?
- Are other workloads being delayed?
- Is the CPU demand temporary?
- Is the application malfunctioning?

Priority adjustment is not a substitute for identifying why the demand exists.

---

# 10. FILE DESCRIPTORS

Linux processes access many kernel-managed objects through file descriptors.

File descriptors may represent:

- regular files
- sockets
- pipes
- devices
- event objects

The standard descriptors are typically:

```text
0    standard input
1    standard output
2    standard error
```

Applications open additional descriptors as they operate.

A web server may hold:

- listening socket
- client sockets
- log files
- database sockets
- configuration files
- pipes

---

## Why File Descriptors Become a Production Problem

Suppose an application continuously opens sockets but fails to close them.

Its descriptor usage may grow:

```text
40
↓
200
↓
1,000
↓
5,000
↓
Configured Limit
↓
New Opens Fail
```

Symptoms may include:

```text
Too many open files
```

or failures to:

- accept connections
- open logs
- connect to dependencies
- create temporary files

The host may still have:

```text
Healthy CPU
Healthy Memory
Available Disk Space
```

and the application can still fail.

---

## Inspect Open Descriptors

For an authorized process:

```bash
ls -l /proc/<PID>/fd
```

Count descriptors:

```bash
find /proc/<PID>/fd -maxdepth 1 -type l 2>/dev/null | wc -l
```

If `lsof` is available:

```bash
lsof -p <PID>
```

can provide a more readable view.

Do not assume `lsof` exists on minimal systems.

---

## Inspect Descriptor Limits

The current shell may show:

```bash
ulimit -n
```

but the running application may have different limits.

Inspect the process itself:

```bash
grep -i 'open files' /proc/<PID>/limits
```

This distinction is important:

```text
Current Shell Limit
≠
Running Service Limit
```

---

# 11. OPEN FILES AND DELETED FILES

Linux allows an open file to remain allocated after its directory entry has been deleted.

Consider:

```text
Application Opens Large Log
        ↓
File Is Deleted
        ↓
Application Keeps Descriptor Open
        ↓
Filesystem Blocks Remain Allocated
```

This can produce a confusing condition where:

```bash
df -h
```

reports substantial filesystem consumption while directory scans do not show the expected file.

If `lsof` is installed:

```bash
lsof +L1
```

can help identify open files whose link count has dropped below one.

Do not manipulate a live process's file descriptors without understanding the application.

Often the correct solution is to correct log rotation or restart/reopen the application through an approved procedure.

---

# 12. PROCESS ENVIRONMENT

A process may receive configuration through environment variables.

Linux exposes the environment of an accessible process through:

```text
/proc/<PID>/environ
```

Values are NUL-separated.

For a known non-sensitive variable:

```bash
tr '\0' '\n' < /proc/<PID>/environ | grep '^APP_ENV='
```

Be careful.

Process environments can contain:

- passwords
- tokens
- database URLs
- private endpoints
- API credentials

Do not dump entire production environments into tickets, terminals that are being recorded, or unapproved AI systems.

---

# 13. CPU: MOVE BEYOND "CPU IS HIGH"

CPU troubleshooting requires several questions:

```text
Is the host actually saturated?

Which processes consume CPU?

Are runnable processes waiting?

Is work happening in user space or kernel space?

Is the demand expected?

Did traffic change?

Did a deployment change CPU behavior?

Are only some threads responsible?
```

A CPU percentage alone cannot answer these questions.

---

# 14. CPU UTILIZATION

Linux monitoring tools commonly divide CPU time into categories such as:

- user time
- system time
- idle
- I/O wait
- interrupt-related time
- steal time in virtualized environments

Exact labels and accounting details vary by tool and platform.

The important principle is that different CPU categories tell different stories.

---

## User Time

High user CPU may indicate work such as:

- application computation
- data transformation
- encryption
- compression
- serialization
- busy loops
- application-level processing

It does not automatically indicate an error.

A batch processor may legitimately use nearly all available CPU.

---

## System Time

System CPU represents time executing kernel work.

Elevated system time may be associated with:

- networking
- filesystem operations
- heavy system-call activity
- process creation
- kernel work

Further evidence is required.

---

## I/O Wait

I/O wait is frequently misunderstood.

It is a CPU accounting category associated with CPUs being idle while I/O is outstanding.

It does not mean:

```text
20% I/O wait
=
Every application spends 20% of its time waiting for disk.
```

Interpret it with:

- process states
- device latency
- queueing
- throughput
- application behavior

---

# 15. LOAD AVERAGE

Load average is not the same thing as CPU utilization.

Linux load includes runnable tasks and tasks in certain uninterruptible waits.

Inspect:

```bash
uptime
```

or:

```bash
cat /proc/loadavg
```

The values usually represent several time windows.

A load average of `8` does not have a universal meaning.

Compare it with:

```bash
nproc
```

or:

```bash
lscpu
```

and then inspect process states.

For example:

```text
Load = 8
CPUs = 2
```

may indicate substantial contention.

But:

```text
Load = 8
CPUs = 64
```

has a very different interpretation.

Even then, CPU count alone is insufficient because uninterruptible tasks can contribute to load.

---

# 16. RUNNABLE PROCESSES AND CPU SATURATION

CPU saturation occurs when CPU demand exceeds immediately available processing capacity and runnable work must wait.

One useful tool is:

```bash
vmstat 1
```

The `r` field can help show runnable work.

Do not interpret one sample.

Observe behavior over an interval.

A strong CPU-saturation case may look like:

```text
High CPU Utilization
+
Persistent Runnable Queue
+
CPU-Heavy Application Process
+
Application Latency
+
Little Idle CPU
```

The evidence becomes stronger when several signals agree.

---

# 17. CONTEXT SWITCHING

Linux switches execution among tasks.

Context switching is normal.

A high context-switch rate may become important when correlated with:

- excessive threads
- very small units of work
- lock contention
- scheduling overhead
- high CPU consumption

But:

```text
Many Context Switches
≠
Root Cause
```

Compare with baseline and workload behavior.

`vmstat` commonly exposes context-switch information along with runnable tasks, interrupts, memory, and CPU accounting.

---

# 18. CPU LAB: DIAGNOSE SATURATION

Use a disposable Linux environment.

Do not deliberately saturate a shared or production host.

## Establish the Baseline

Run:

```bash
nproc
uptime
vmstat 1 5
ps -eo pid,ppid,stat,pcpu,pmem,etime,cmd --sort=-pcpu | head
```

Record:

- CPU count
- load
- runnable work
- top CPU consumers

Do not create load before understanding normal state.

---

## Create Controlled CPU Demand

In one terminal:

```bash
python3 -c 'while True: pass'
```

Record its PID from another terminal:

```bash
pgrep -af "python3 -c"
```

Now inspect:

```bash
ps -eo pid,ppid,stat,pcpu,pmem,etime,cmd --sort=-pcpu | head
```

and:

```bash
vmstat 1
```

Observe:

- process CPU
- overall CPU behavior
- runnable queue
- load average over time

On a machine with several logical CPUs, one single-threaded busy loop may saturate only one logical CPU.

That distinction is important.

---

## Increase Contention Carefully

If the disposable environment has multiple CPUs and the lab is specifically designed for saturation, start additional controlled CPU workers one at a time.

Observe after each addition.

Do not blindly launch dozens of processes.

The goal is to see the relationship:

```text
Runnable Work Increases
↓
CPU Headroom Decreases
↓
Runnable Queue Persists
↓
Latency Can Increase
```

---

## Stop and Verify Recovery

Terminate only the lab processes.

Verify:

```bash
vmstat 1 5
```

and:

```bash
ps -eo pid,stat,pcpu,cmd --sort=-pcpu | head
```

Record:

```text
What changed?

Which evidence showed saturation?

Which evidence returned to normal?
```

# 19. MEMORY: UNDERSTAND WHAT "USED" ACTUALLY MEANS

Linux memory investigation requires distinguishing:

```text
Physical Memory
Virtual Memory
Resident Memory
Page Cache
Buffers
Available Memory
Swap
Memory Pressure
OOM
```

These terms are related but not interchangeable.

---

# 20. PHYSICAL MEMORY

Physical memory is the system's RAM.

Start with:

```bash
free -h
```

and:

```bash
cat /proc/meminfo
```

`/proc/meminfo` provides detailed kernel memory accounting.

Do not rely only on the `used` percentage.

Linux deliberately uses otherwise available memory for caching.

---

# 21. VIRTUAL MEMORY

Processes operate within virtual address spaces.

A process can have a very large virtual address space without occupying an equivalent amount of physical RAM.

Therefore:

```text
Large VSZ
≠
Equivalent RAM Consumption
```

Inspect process memory with:

```bash
ps -eo pid,comm,vsz,rss,pmem --sort=-rss | head
```

---

# 22. RSS

RSS means resident set size.

It represents process-associated pages currently resident in physical memory, subject to accounting details such as shared memory.

Linux exposes memory information such as `VmRSS`, `RssAnon`, `RssFile`, and other fields through `/proc/<PID>/status`; the exact available fields depend on the running kernel.

Inspect:

```bash
grep -E 'VmSize|VmRSS|RssAnon|RssFile|RssShmem|VmSwap|Threads' /proc/<PID>/status
```

Do not assume every field exists on every kernel release.

---

# 23. PAGE CACHE AND AVAILABLE MEMORY

Linux uses memory to cache filesystem data.

That behavior can make:

```text
free memory
```

appear small even when the system is healthy.

This is why `available` memory is usually more useful than asking only:

```text
How much RAM is completely unused?
```

A system may have:

```text
Low Free Memory
+
Healthy Available Memory
+
No Active Swap Pressure
+
Normal Application Latency
```

and be operating normally.

Do not "fix" healthy cache use by clearing caches.

---

# 24. BUFFERS AND CACHE

Different Linux tools and kernel versions may present buffer/cache accounting differently.

At this level, understand the larger principle:

```text
Used RAM
≠
Application Memory Alone
```

RAM may be used by:

- applications
- page cache
- kernel structures
- shared memory
- filesystem metadata
- other operating-system functions

Investigation requires more than a percentage.

---

# 25. SWAP

Swap provides backing storage that Linux can use for memory pages.

Inspect configuration:

```bash
swapon --show
```

and usage:

```bash
free -h
```

Several conditions must be distinguished:

```text
No Swap Configured
```

```text
Swap Configured but Unused
```

```text
Swap Contains Pages but Little Current Activity
```

```text
Active Swap-In / Swap-Out Under Pressure
```

These are not the same situation.

---

# 26. SWAP USAGE IS NOT SWAP PRESSURE

Seeing:

```text
1 GiB swap used
```

does not prove that swapping is currently causing performance problems.

Use interval evidence:

```bash
vmstat 1
```

and inspect swap-in and swap-out activity where supported by the installed implementation.

The key distinction is:

```text
Swap Occupancy
≠
Active Swapping
```

A page may remain in swap even after the period of pressure has ended.

---

# 27. MEMORY PRESSURE

Memory pressure describes the effect of memory scarcity and reclaim work on running workloads.

A stronger memory-pressure investigation combines:

- available memory
- process RSS
- reclaim behavior
- swap activity
- workload latency
- PSI where available
- OOM evidence
- cgroup or container limits where relevant

Do not reduce memory pressure to:

```text
Memory usage > 90%
```

---

# 28. PRESSURE STALL INFORMATION

On Linux systems where Pressure Stall Information is available, the kernel can expose resource-stall information through:

```text
/proc/pressure/
```

Common interfaces include:

```text
/proc/pressure/cpu
/proc/pressure/memory
/proc/pressure/io
```

PSI is designed to quantify time lost because tasks are stalled by CPU, memory, or I/O contention.

Check availability:

```bash
ls /proc/pressure
```

Then, where present:

```bash
cat /proc/pressure/memory
```

or:

```bash
cat /proc/pressure/io
```

Do not assume PSI exists or is visible in every container, kernel, or restricted environment.

---

## `some` and `full`

PSI commonly reports categories such as:

```text
some
```

and, for certain resources:

```text
full
```

At a high level:

- `some` indicates that at least some work experienced stalls because of the resource.
- `full` represents more severe periods where all non-idle work was simultaneously stalled by the resource.

Use the kernel documentation for exact semantics on the running platform.

The important operational idea is:

```text
Resource Consumption
≠
Resource Pressure
```

PSI helps answer whether contention is actually delaying useful work.

---

# 29. OUT-OF-MEMORY BEHAVIOR

Memory exhaustion can reach a point where the kernel cannot reclaim enough memory to satisfy allocation needs.

Linux may then invoke the OOM killer and select a task to terminate in an attempt to recover memory.

Therefore:

```text
Application Process Disappeared
```

does not automatically mean:

```text
Application Bug Caused Normal Crash
```

Check operating-system evidence.

---

## Search for OOM Evidence

On systemd-based systems, where permissions allow:

```bash
journalctl -k | grep -i -E 'oom|out of memory|killed process'
```

You may also inspect:

```bash
dmesg | grep -i -E 'oom|out of memory|killed process'
```

Access to kernel logs may be restricted.

Absence of output from one command is not proof that no OOM event occurred.

---

## Host OOM Versus Workload Limit

Modern workloads may have memory constraints imposed by cgroups, containers, or orchestrators.

For example:

```text
Host RAM = 32 GiB
Container Limit = 512 MiB
```

The container may hit its memory boundary even though the host still has substantial free memory.

Always identify which resource boundary is being exhausted.

Detailed cgroup and container investigation appears later in the Mid-Level path.

# 30. MEMORY LAB: GROWING MEMORY AND EXHAUSTION

This lab must run in a disposable, intentionally bounded environment.

Do not intentionally exhaust the RAM of:

- your primary workstation
- a shared server
- a production host

## Establish a Baseline

Run:

```bash
free -h
vmstat 1 5
```

If PSI exists:

```bash
cat /proc/pressure/memory
```

Record:

- available memory
- swap configuration
- swap activity
- memory pressure

---

## Create a Controlled Memory Consumer

Create:

```python
import time

blocks = []

while True:
    blocks.append(bytearray(10 * 1024 * 1024))
    print(f"allocated approximately {len(blocks) * 10} MiB")
    time.sleep(1)
```

```text
Does it have free inodes?
```

```text
Disk issue.
```

# 32. BLOCK DEVICES, FILESYSTEMS, AND MOUNTS

Inspect block devices:


Inspect mounts:

```bash

```

A useful model is:

```text
Block Device / Storage
        ↓
Filesystem
        ↓
Mount Point
        ↓
Application Path
```

Suppose an application writes to:

```text
/var/lib/application/data
```

You need to know which filesystem backs that path.

Do not assume it is the root filesystem.

# 33. FILESYSTEM CAPACITY

Inspect:

```bash
df -h
```

A full filesystem can produce failures such as:

- application write failure
- log failure
- database failure
- package-manager failure
- temporary-file failure
- service startup failure

Always identify the specific filesystem.

Example:

```text
/
has free capacity

/var
is separate and full
```

An application writing to `/var` can fail even though `/` is healthy.

# 34. `df` AND `du` ANSWER DIFFERENT QUESTIONS

Conceptually:

```text
df
↓
Filesystem allocation/accounting
```

while:

```text
du
↓
Space associated with directory-tree entries you can traverse
```

The numbers may differ.

Possible reasons include:

- deleted-but-open files
- mount boundaries
- permissions
- files hidden beneath mount points
- filesystem accounting details

Do not assume one command is wrong because the numbers differ.

# 35. INODES

A filesystem can have free byte capacity while being unable to create additional files because it has exhausted available inodes.

Inspect:

```bash
df -i
```

This explains a classic scenario:

```text
Application:
"No space left on device"

df -h:
Free bytes remain
```

Next question:

```text
Are inodes exhausted?
```

---

## Why Inodes Become Exhausted

A workload may generate huge numbers of very small files.

Examples include:

- broken temporary-file cleanup
- cache objects
- session files
- application-generated fragments
- badly configured logging

The bytes consumed may be small while metadata objects are exhausted.

# 38. STORAGE I/O: SPACE CAN BE HEALTHY WHILE PERFORMANCE IS NOT

A filesystem can have:

```text
70% free space
```

and still suffer severe I/O latency.

Capacity and performance are different.

Two important concepts are:

### Throughput

How much data can be transferred over time?

### Latency

How long does an operation take?

A device may move significant data overall while individual operations experience unacceptable latency.

# 40. FILESYSTEM PERMISSIONS

File access depends on more than the target file.

Suppose the application needs:

```text
/opt/veriqta/config/app.conf
```

It must be able to traverse the relevant directories and access the file.

Where available:

```bash
namei -l /opt/veriqta/config/app.conf
```

can help inspect permissions across the path.

Also use:

```bash
stat /opt/veriqta/config/app.conf
```

or:

```bash
ls -l /opt/veriqta/config/app.conf
```

Do not respond to a permission failure with:

```bash
chmod 777 ...
```

That removes useful protection without diagnosing the actual ownership or permission requirement.

## Additional Access-Control Layers

Traditional owner/group/mode bits may not be the entire security decision.

Depending on the system, access may also involve:

- ACLs
- SELinux
- AppArmor
- mount options
- container boundaries

Recognize that these layers exist.

Deep security-policy engineering is outside this Part.

# 41. `/proc`: PROCESS AND KERNEL EVIDENCE

`/proc` is a pseudo-filesystem that exposes process and kernel information.

It is not an ordinary disk-backed directory tree.

Useful files include:

```text
/proc/cpuinfo
/proc/meminfo
/proc/loadavg
/proc/uptime
/proc/mounts
/proc/pressure/
/proc/<PID>/
```

Visibility can depend on:

- permissions
- namespaces
- kernel version
- procfs mount options

Linux's own documentation notes that tools such as `ps` obtain process information from procfs and that `/proc/<PID>/status` provides detailed process information.

---

## `/proc/<PID>/status`

Inspect:

```bash
cat /proc/<PID>/status
```

Useful information may include:

- process state
- PID
- PPID
- UIDs/GIDs
- thread count
- memory information
- signal-related information

Use it when a high-level command does not expose enough detail.

---

## `/proc/<PID>/cmdline`

Inspect:

```bash
tr '\0' ' ' < /proc/<PID>/cmdline
echo
```

Be careful.

Poorly designed applications sometimes place sensitive values in command-line arguments.

---

## `/proc/<PID>/fd`

Inspect:

```bash
ls -l /proc/<PID>/fd
```

This helps investigate:

- sockets
- pipes
- open files
- deleted files
- descriptor exhaustion

---

## `/proc/<PID>/limits`

Inspect:

```bash
cat /proc/<PID>/limits
```

This may expose limits such as:

- open files
- process count
- stack
- locked memory

Use the running process's values instead of assuming the interactive shell has identical limits.

---

## `/proc/<PID>/io`

Where available and permitted:

```bash
cat /proc/<PID>/io
```

can expose process I/O counters.

The kernel documentation describes fields for read/write-related accounting in this interface.

Use it as supporting evidence, not as a complete storage-performance diagnosis.

---

# 42. `/sys`: KERNEL OBJECTS AND DEVICES

`/sys` is another pseudo-filesystem.

It exposes information about kernel objects and devices, including areas related to:

- block devices
- network devices
- kernel subsystems
- power
- device configuration

The important operational rule is:

```text
Read Before Write
```

Many kernel interfaces are writable.

That does not mean troubleshooting should begin by changing them.

Never apply a kernel tuning value simply because:

- a blog suggested it
- an AI model suggested it
- it solved a superficially similar incident elsewhere

First determine:

- what the setting controls
- current value
- kernel-version behavior
- blast radius
- persistence
- rollback
- evidence that the change is relevant

# 43. SYSTEM CALLS: THE APPLICATION–KERNEL BOUNDARY

Applications request operating-system services through system calls.

Conceptually, these operations include:

- opening files
- reading
- writing
- creating sockets
- connecting
- accepting connections
- waiting
- mapping memory
- creating processes
- sending signals

You do not need to memorize the system-call table.

You need to understand the relationship:

```text
Application Behavior
↓
Runtime / Library Calls
↓
System Calls
↓
Kernel Behavior
```

This provides another troubleshooting layer when application logs are insufficient.

Where installed and permitted, `strace` can observe system calls.

## Failed System Calls

You can search a trace for failures:

Context matters.

# 45. KERNEL LOGS

Kernel evidence may reveal events such as:

- OOM handling
- filesystem problems
- device errors
- driver issues
- hardware events
- network-driver events
- kernel warnings

On systemd-based environments:



# 46. SYSTEM LOGS, SERVICE LOGS, AND APPLICATION LOGS

Troubleshooting requires distinguishing several evidence sources.

### Kernel

```text
journalctl -k
```

### System / Boot

```text
journalctl -b
```

### Service

```text
journalctl -u <unit>
```

### Application

The location depends on how the application logs.

Examples include:

- journald
- log files
- container logs
- centralized logging platform

The most useful evidence often comes from correlating these sources by time.

# 47. TIME-BOUND LOG INVESTIGATION

Do not begin every investigation by reading thousands of old log lines.

If the incident began approximately ten minutes ago:

```bash
journalctl --since "10 minutes ago"
```

For one service:

```bash
journalctl -u <unit> --since "10 minutes ago"
```

Use timestamps from the incident.

This helps build a sequence:

```text
14:02 Deployment

14:03 Process Restart

14:03 Configuration Error

14:04 Restart

14:04 Restart

14:05 Start Limit Reached
```

The timeline can reveal the initiating failure.

# 48. RESOURCE LIMITS

Linux processes can be constrained by resource limits.

Inspect the current shell:

```bash

```

But remember:

```text
Your Shell
≠
The Service's Execution Environment
```

For a running process:

```bash

```

A resource-limit failure may appear even when the host still has plenty of global capacity.

For example:

```text

=
Application failure
```

# 49. FILE DESCRIPTOR EXHAUSTION LAB

Use a disposable environment.

Start a new shell:

```bash
bash
```

Check:

```bash
ulimit -n
```

Set a deliberately small soft limit for the lab shell:

```bash
ulimit -n 64
```

Verify:

```bash
ulimit -n
```

Now create:

```python
import time

files = []

try:
    while True:
        files.append(open("/dev/null", "rb"))
        print(f"opened: {len(files)}")
        time.sleep(0.05)
except OSError as exc:
    print(f"open failed after {len(files)} additional descriptors: {exc}")
    time.sleep(30)
```

Save it as:

```text
fd_exhaustion.py
```

Run:

```bash
python3 fd_exhaustion.py
```

The script should eventually fail to open another descriptor.

The exact count will be lower than `64` because the process already owns descriptors.

## Investigate Before the Process Exits

From another terminal:

```bash
pgrep -af fd_exhaustion.py
```

Then:

```bash
grep -i 'open files' /proc/<PID>/limits
```

and:

```bash
ls /proc/<PID>/fd 2>/dev/null | wc -l
```

Your evidence chain should become:

```text
Application Reports Descriptor Failure
        ↓
Process Has Low Open-File Limit
        ↓
Descriptor Count Is Near Limit
        ↓
Failure Mechanism Confirmed
```

## Production Lesson

Do not automatically fix this by dramatically increasing the limit.

Ask:

```text
Is the application leaking descriptors?

```

Those are different problems.

# 50. `systemd` AT MID-LEVEL

At Junior level, you may have used:

```bash
systemctl status
systemctl start
systemctl stop
systemctl restart
journalctl -u
```

At Mid-Level, you need to understand what systemd is doing.

systemd acts as a system and service manager and, when used as PID 1 for the system instance, starts and maintains user-space services.

You now need to reason about:

- unit types
- dependencies
- ordering
- targets
- execution environment
- restart policies
- failure states
- journal evidence

---

# 51. UNIT TYPES

systemd manages several unit types.

Common examples include:

```text
.service
.socket
.target
.mount
.timer
.path
```

Do not assume every unit represents a continuously running process.

For example:

- a `.service` may run a process
- a `.timer` may schedule activation
- a `.target` may group units or represent a synchronization point

---

# 52. INSPECT THE ACTUAL UNIT

Use:

```bash
systemctl cat <unit>
```

This is useful because a service may have:

- vendor unit file
- local override
- drop-in configuration

Do not inspect one file manually and assume it represents the complete effective configuration.

For detailed properties:

```bash
systemctl show <unit>
```

Filter when appropriate:

```bash
systemctl show <unit> \
  -p ActiveState \
  -p SubState \
  -p MainPID \
  -p ExecMainStatus \
  -p NRestarts
```

Some properties depend on systemd version.

---

# 53. DEPENDENCIES AND ORDERING ARE NOT THE SAME THING

This distinction is essential.

Common directives include:

```text
Requires=
Wants=
After=
Before=
```

`Requires=` and `Wants=` describe dependency relationships.

`After=` and `Before=` describe ordering relationships.

Therefore:

```ini
After=database.service
```

does not by itself mean:

```text
Starting this service will automatically start database.service.
```

Ordering and requirement are separate concepts.

---

## Inspect Dependencies

Use:

```bash
systemctl list-dependencies <unit>
```

Where supported:

```bash
systemctl list-dependencies --reverse <unit>
```

Ask:

```text
What does this service require?

What only affects ordering?

What depends on this service?
```

---

# 54. TARGETS

Targets represent logical synchronization/grouping points.

Inspect:

```bash
systemctl list-units --type=target
```

and:

```bash
systemctl get-default
```

Do not think of a target as a process.

A target helps organize relationships among units.

---

# 55. SERVICE EXECUTION ENVIRONMENT

A systemd service may behave differently from the same command run interactively.

Why?

Because systemd may define:

- user
- group
- working directory
- environment variables
- environment files
- resource limits
- security restrictions
- restart behavior

A classic symptom is:

```text
Works in my shell.
Fails under systemd.
```

Investigate:

```bash
systemctl cat <unit>
```

and examine directives such as:

```text
User=
Group=
WorkingDirectory=
Environment=
EnvironmentFile=
ExecStart=
```

Also inspect process permissions and files.

---

# 56. RESTART BEHAVIOR

A service may define:

```text
Restart=
RestartSec=
```

which control automatic restart behavior.

If the application repeatedly fails:

```text
Application Starts
↓
Application Exits
↓
Restart Policy Applies
↓
Application Starts Again
↓
Application Exits Again
```

the restart policy is not necessarily the root cause.

Ask:

```text
Why does the process exit?
```

---

# 57. RESTART LOOPS CAN HIDE THE FIRST FAILURE

A timeline might look like:

```text
Invalid Configuration
↓
Process Exits
↓
systemd Restarts Process
↓
Process Exits
↓
systemd Restarts Process
↓
Start Attempts Become Rate-Limited
```

If you inspect only the final state, you may see:

```text
Start request repeated too quickly
```

and incorrectly conclude that systemd is the problem.

Go back to the first relevant failure.

# 60. PROCESS STUCK WAITING

A process can exist and still appear frozen.

Possible explanations include:

- waiting for disk I/O
- waiting for network input
- waiting for a pipe
- waiting for a lock
- waiting for another process
- sleeping normally
- stopped by a signal
- deadlocked in application logic
- spinning on CPU
- blocked on an external dependency

Do not use:

```text
Process exists
↓
Application must be healthy.
```

Process existence proves very little about progress.

# 61. WAITING PROCESS LAB

Create a FIFO:

```bash
mkfifo /tmp/veriqta-wait-lab
```

In one terminal:

```bash
cat /tmp/veriqta-wait-lab
```

The command waits for input.

From another terminal:

```bash
pgrep -af 'cat /tmp/veriqta-wait-lab'
```

Then:

```bash
ps -p <PID> -o pid,ppid,stat,wchan:32,etime,cmd
```

The `wchan` field may expose a kernel wait-channel symbol when available and permitted.

Now inspect descriptors:

```bash
ls -l /proc/<PID>/fd
```

You should see evidence connecting the process to the FIFO.

```bash
echo "continue" > /tmp/veriqta-wait-lab
```

Then remove the FIFO:

```bash
rm -f /tmp/veriqta-wait-lab
```

The lesson is:

```text
Appears Frozen
↓
Process Exists
↓
Process Is Waiting
↓
Open Descriptor Shows FIFO
↓
Process Receives Input
↓
Process Continues
```

No restart was required.

# 64. ADVANCED TROUBLESHOOTING: EXCESSIVE SWAPPING

Do not diagnose from swap occupancy alone.

A stronger case may contain:

```text
Low Available Memory
+
Sustained Swap-In / Swap-Out
+
Increased I/O
+
Application Latency
+
Memory Pressure
```

Then investigate why the working set no longer fits within the intended memory boundary.

Possible causes include:

- workload growth
- memory leak
- too-small resource allocation
- too many colocated workloads
- unexpected process

The diagnosis should identify the mechanism.

# 65. ADVANCED TROUBLESHOOTING: FULL FILESYSTEM

Use:

```text
Write Failure
↓

↓
Which Mount?
↓
Byte Capacity?
↓
Inodes?
↓
Largest Relevant Consumers?
↓
Deleted Open Files?
↓
Growth Source?
↓

↓
Prevention
```

Do not respond with:

```text
rm -rf old files
```

before knowing what those files are and who owns them.

---

# 66. ADVANCED TROUBLESHOOTING: INODE EXHAUSTION

Symptom:

```text
No space left on device
```

Evidence:

```bash
df -h
```

shows available bytes.

Next:

```bash
df -i
```

If inode availability is exhausted, investigate which path is creating extreme numbers of files.

The root cause should not be recorded merely as:

```text
No inodes.
```

Ask:

```text
Why did the filesystem consume all available inodes?
```

---

# 67. ADVANCED TROUBLESHOOTING: I/O LATENCY

Use:

```text
Application Slow
↓
Are Tasks Waiting?
↓
What Is Process State?
↓
Is Storage Activity Elevated?
↓
Which Device?
↓
What Are Latency / Queueing Indicators?
↓
Which Workload Produces the I/O?
↓
Does That Explain the Application Symptom?
```

Avoid changing CPU or memory resources when the evidence points elsewhere.

---

# 68. ADVANCED TROUBLESHOOTING: FILE DESCRIPTOR EXHAUSTION

Use:

```text
Application Fails to Open File / Accept Connection
↓
Inspect Error
↓
Identify Process
↓
Inspect Process Limit
↓
Count Descriptors
↓
Classify Descriptors
↓
Check Growth
↓
Determine Leak or Legitimate Capacity Need
```

Then choose correction.

For a leak:

```text
Fix lifecycle behavior.
```

For legitimate concurrency:

```text
Review appropriate limits and system capacity.
```

These are different engineering decisions.

# 69. ADVANCED TROUBLESHOOTING: RESTARTING APPLICATION

```text

↓

↓

↓

↓
```

# 70. ERROR CHAINS

Many incidents form causal chains.

Example:

```text
Filesystem Full
↓
Application Cannot Write
↓
Application Exits
↓
systemd Restarts Application
↓
Application Fails Again
↓
Repeated Restarts
↓
Service Becomes Unavailable
```

If you begin from the final symptom:

```text
Service repeatedly restarting
```

you may misdiagnose the service manager.

Follow the timeline backwards.

---

# 71. CORRELATE MULTIPLE EVIDENCE SOURCES

Suppose users report latency.

You observe:

```text
Application:
database calls are slow

Process:
low CPU use

Host:
CPU and memory healthy

Storage:
normal

Network:
connection established

Dependency monitoring:
database latency elevated
```

A CPU-saturation hypothesis is not supported.

A dependency-latency hypothesis is stronger.

This is Mid-Level troubleshooting:

```text
Evidence From Multiple Layers
↓
Competing Hypotheses
↓
Eliminate Weak Explanations
↓
Test Strongest Explanation
```

---

# 72. NEGATIVE EVIDENCE MATTERS

Evidence does not only confirm hypotheses.

It can eliminate them.

Hypothesis:

```text
CPU saturation causes the application latency.
```

Observed:

```text
CPU mostly idle
Runnable queue low
Application process CPU low
```

That does not reveal the final root cause.

But it weakens the CPU hypothesis.

That is valuable progress.

---

# 73. RESOURCE UTILIZATION VERSUS SATURATION

High utilization can be healthy.

For example:

```text
CPU = 85%
```

may be acceptable if:

- latency remains normal
- no sustained runnable queue exists
- the workload is expected
- capacity remains adequate

Saturation is about work being delayed because demand exceeds immediately available capacity.

Similarly:

```text
Memory = 90% used
```

does not automatically indicate memory pressure.

Ask whether workload progress is being affected.

---

# 74. RESOURCE INTERACTIONS

Resources influence one another.

Example:

```text
Memory Pressure
↓
Page Reclaim
↓
Possible Swap Activity
↓
Additional Storage I/O
↓
Higher Latency
↓
Application Slows
```

Another:

```text
Traffic Increase
↓
More Connections
↓
More File Descriptors
↓
Descriptor Limit Reached
↓
New Connections Fail
```

Another:

```text
Application Logging Bug
↓
Logs Grow Rapidly
↓
Filesystem Fills
↓
New Writes Fail
↓
Application Fails
```

A Mid-Level engineer learns to recognize these chains.

---

# 75. DO NOT USE BROAD REMEDIATION AS DIAGNOSIS

Several common actions can hide the real failure.

## Restart

May restore service but erase useful process state.

## Reboot

Changes many variables simultaneously and may remove evidence.

## Kill

Can restore capacity while hiding why the process consumed it.

## Increase Limits

Can delay failure without fixing a leak.

## Disable Swap

Changes memory behavior without proving swap caused the problem.

## Drop Caches

Can hurt performance and does not diagnose memory pressure.

## Tune Kernel Parameters

Can create wider impact than the original problem.

Use mitigation when necessary.

Do not confuse mitigation with root cause.

---

# 76. MITIGATION, CORRECTIVE ACTION, AND PREVENTION

These are different.

Example: descriptor leak.

### Mitigation

```text
Restart application.
```

This releases descriptors and may restore service.

### Corrective Action

```text
Fix the code or component that fails to close descriptors.
```

### Prevention / Detection Improvement

```text
Add descriptor-use monitoring or alerting if justified.
```

An incident may require all three.

---

# 77. ROOT CAUSE MUST EXPLAIN THE MECHANISM

Weak:

```text
Root cause: high memory.
```

Stronger:

```text
The application process grew continuously from approximately
300 MiB RSS to the workload's configured memory limit.

Memory pressure increased and the workload was eventually terminated
by the memory-control boundary.

Service logs show the process restarting immediately afterward.

The memory growth began after the new application release.
```

The stronger statement describes:

- what happened
- where
- how
- evidence
- timing

It still leaves room for deeper application investigation into why memory grew.

# 81. COMMAND DISCIPLINE

For every command, ask:

```text
Why am I running this?

What question am I trying to answer?

What result do I expect?

What result would weaken the hypothesis?
```

# 85. AI-ASSISTED LINUX INVESTIGATION

AI can help with:

- interpreting command output
- explaining process states
- proposing hypotheses
- explaining `/proc` fields
- reviewing systemd units
- suggesting non-destructive evidence collection
- organizing incident evidence

But AI does not automatically know:

- your kernel version
- your distribution
- your application architecture
- your workload baseline
- your resource limits
- your system ownership boundaries
- your recent changes

Therefore a request such as:

```text
My Linux server is slow. What is wrong?
```

cannot support a reliable diagnosis.

---

## A Better AI Investigation Request

For example:

```text
Environment:
Ubuntu Linux VM, 4 logical CPUs.

Symptom:
API latency increased from approximately 200 ms to 4 seconds.

Scope:
All requests handled by one application host.

Observed evidence:
- CPU remains around 95%
- vmstat shows persistent runnable work
- application process is the largest CPU consumer
- available memory remains healthy
- no sustained swap activity observed
- filesystem capacity is normal
- issue began immediately after application deployment

Provide the strongest hypotheses and identify additional
non-destructive evidence that would distinguish among them.
Do not propose remediation yet.
```

This provides evidence instead of asking AI to guess.

- application CPU

# 91. PRACTICAL ASSESSMENT: SYSTEMD

Given a failing unit, inspect:

- unit definition
- effective configuration
- dependencies
- ordering
- main PID
- process exit status
- restart behavior
- journal timeline
- application evidence

Then explain whether systemd is:

```text
the failure source,
the messenger,
or the recovery mechanism.
```

---

# 92. PRACTICAL ASSESSMENT: FILE DESCRIPTOR EXHAUSTION

Given:

```text
Too many open files
```

identify:

- affected process
- open-file limit
- current descriptor count
- descriptor types
- whether usage grows over time
- whether the demand is legitimate or indicates leakage

Do not simply increase the limit.

---

# 93. PRACTICAL ASSESSMENT: STUCK PROCESS

Given:

```text
Process exists but application appears frozen.
```

determine whether the process is:

- runnable
- sleeping
- stopped
- in uninterruptible wait
- consuming CPU
- waiting on a file/pipe
- waiting on a socket
- likely blocked on a dependency

Do not kill the process before collecting evidence unless incident severity requires immediate mitigation.

---

# 94. PRACTICAL ASSESSMENT: ROOT-CAUSE QUALITY

A weak conclusion:

```text
Linux ran out of files.
```

A stronger conclusion:

```text
The application stopped accepting new client connections because
the process reached its configured open-file limit.

The process limit was 1,024 descriptors, and the descriptor count
had grown to approximately that boundary when failures began.

Most of the additional descriptors were sockets.

Restarting the service released the descriptors and restored
availability, but that was mitigation. The connection lifecycle
must be investigated because descriptor use continued increasing
rather than returning to a stable range.
```

A useful root-cause statement explains the mechanism.

# 95. COMPLETION STANDARD

You have completed this Part when you can investigate Linux process and resource problems beyond surface-level percentages.

You should be able to move from:

```text
CPU is high.
```

to:

```text
Which process or threads are consuming CPU?

How many CPUs are available?

Is runnable work waiting?

Is the demand expected?

Does the CPU evidence actually explain the application symptom?
```

You should be able to move from:

```text
Memory is almost full.
```

to:

```text
How much memory is available?

Which processes hold resident memory?

Is the system reclaiming aggressively?

Is swap actively moving pages?

Are workloads experiencing memory stalls?

Was anything killed by OOM handling?

Is the relevant limit host-wide or workload-specific?
```

You should be able to move from:

```text
Disk is broken.
```

to:

```text
Which filesystem backs the application path?

Is byte capacity exhausted?

Are inodes exhausted?

Is the expected mount present?

Is storage latency elevated?

Are deleted-open files retaining space?

Does the application have permission to write?
```

You should be able to move from:

```text
systemd keeps restarting my application.
```

to:

```text
Why does the application exit?

What does the unit configuration specify?

Which dependency or environment condition is involved?

What happened first in the journal timeline?

Is systemd causing the failure or responding to it?
```

The engineering habit from this Part is:

```text
What is the application reporting?
        ↓
Which process represents the application?
        ↓
What state is the process in?
        ↓
Is the process progressing or waiting?
        ↓
Which resource could explain that behavior?
        ↓
What does Linux report?
        ↓
What does the kernel report?
        ↓
What does the application report?
        ↓
What do the dependencies report?
        ↓
Which hypothesis explains all available evidence?
        ↓
How can that hypothesis be tested safely?
        ↓
What corrective action addresses the actual mechanism?
        ↓
What evidence proves recovery?
```

At Mid-Level, Linux should no longer appear as a dashboard containing CPU, memory, and disk percentages.

It should begin to appear as a running system whose processes, resources, limits, kernel interfaces, service manager, and logs provide evidence about why an application behaves the way it does.

That system-level reasoning is the foundation for the next layer: understanding how production traffic moves between systems.
