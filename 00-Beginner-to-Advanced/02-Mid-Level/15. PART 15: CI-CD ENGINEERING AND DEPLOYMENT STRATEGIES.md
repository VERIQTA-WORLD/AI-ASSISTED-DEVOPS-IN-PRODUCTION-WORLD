# PART 15: CI/CD ENGINEERING AND DEPLOYMENT STRATEGIES

## Goal

Design, operate, review, and troubleshoot robust software delivery pipelines, and understand how deployment strategy changes production risk, availability, blast radius, recovery options, and verification requirements.

At this level, CI/CD is no longer treated as:

```text
Commit
↓
Run Script
↓
Deploy
```

A production delivery system is a controlled chain that transforms source code into a verified running change.

The complete mental model is closer to:

```text
Source Change
↓
Review
↓
Continuous Integration
↓
Build
↓
Test
↓
Security Validation
↓
Artifact Creation
↓
Artifact Publication
↓
Deployment Preparation
↓
Environment Authorization
↓
Deployment
↓
Runtime Verification
↓
Observation
↓
Promotion / Continue / Stop / Roll Back
```

The central failure-handling model is:

```text
Deploy
↓
Verify
↓
Observe
↓
Healthy?
├── Yes → Continue
└── No  → Stop / Roll Back / Recover
```

The important engineering principle is:

> A pipeline is not merely automation. It is a controlled path through which a proposed change becomes a production change.

A mature delivery system must answer:

```text
What changed?

Who changed it?

Which source revision produced the artifact?

Which tests ran?

Which security checks ran?

Which artifact was approved?

Which identity deployed it?

Which environment received it?

Which configuration was used?

Which deployment strategy controlled exposure?

What evidence proved the deployment healthy?

What happens when verification fails?

Can the previous application version still run safely?

Can the system recover if rollback is insufficient?
```

---

# 1. CONTINUOUS INTEGRATION AND CONTINUOUS DELIVERY ARE RELATED BUT DIFFERENT

CI and CD are often written together:

```text
CI/CD
```

but they solve different parts of the delivery problem.

## Continuous Integration

Continuous Integration focuses on validating changes as engineers integrate them into a shared codebase.

Conceptually:

```text
Developer Change
↓
Build
↓
Static Validation
↓
Tests
↓
Security Checks
↓
Integration Evidence
```

The question CI tries to answer is:

> Is this change suitable to integrate with the shared codebase according to the evidence we currently have?

## Continuous Delivery

Continuous Delivery extends the process toward producing software that can be deployed through a controlled, repeatable process.

Conceptually:

```text
Validated Source
↓
Build
↓
Test
↓
Package
↓
Publish Artifact
↓
Deployment Preparation
↓
Environment Controls
↓
Deployable Release
```

## Continuous Deployment

Continuous deployment usually refers to a model in which qualifying changes can progress into production automatically after satisfying the required controls.

That does not mean:

```text
Every commit
↓
Immediately production
```

with no safety controls.

A mature automated production path can still contain:

```text
Automated tests
Security controls
Policy checks
Progressive delivery
Automated health analysis
Automatic stopping conditions
Rollback or recovery mechanisms
Auditability
```

The amount of human approval depends on:

```text
Risk

Regulation

Organizational policy

Deployment maturity

Application criticality

Change type
```

---

# 2. PIPELINE SYNTAX IS NOT PIPELINE ENGINEERING

Knowing how to write:

```yaml
steps:
  - run: test
  - run: build
  - run: deploy
```

does not mean you understand delivery engineering.

Pipeline engineering requires reasoning about:

```text
Execution order

Dependencies

Artifacts

Failure propagation

Security boundaries

Credentials

Environment boundaries

Concurrency

Caching

Parallelism

Approvals

Deployment strategy

Verification

Recovery

Auditability
```

A pipeline can be syntactically valid and operationally dangerous.

---

# 3. THE DELIVERY CHAIN

Treat delivery as a chain of transformations.

For example:

```text
Git Commit
↓
Source Checkout
↓
Dependency Resolution
↓
Build
↓
Tests
↓
Container Image
↓
Registry
↓
Helm Configuration
↓
Deployment
↓
Kubernetes
↓
Application
```

Each arrow represents:

```text
Dependency

Trust boundary

Possible failure

Evidence requirement
```

If the application fails after deployment, the pipeline engineer must determine which layer introduced the failure.

---

# 4. DELIVERY PIPELINE AS A GRAPH

Real pipelines are usually not simple linear sequences.

For example:

```text
                     ┌── Unit Tests ────────┐
                     │                       │
Commit → Validation ─┼── Static Analysis ───┼→ Build
                     │                       │
                     └── Security Scan ──────┘
                                              ↓
                                           Artifact
                                              ↓
                           ┌──────────────────┴───────────────┐
                           ↓                                  ↓
                    Integration Tests                 Artifact Scan
                           └──────────────────┬───────────────┘
                                              ↓
                                           Staging
                                              ↓
                                           Verify
                                              ↓
                                           Approval
                                              ↓
                                          Production
```

This is a dependency graph.

Some jobs can run independently.

Some cannot start until required predecessors complete.

---

# 5. JOB DEPENDENCIES

Suppose:

```text
Build
↓
Integration Test
↓
Deploy
```

The integration test depends on the build artifact.

Deployment depends on successful validation.

If deployment starts before the artifact has been properly tested, the dependency graph is incorrect.

Every job should have a clear reason for its dependencies.

Ask:

```text
What does this job consume?

What must already be true?

What evidence must exist before it runs?

What does it produce?

Who consumes its output?
```

---

# 6. PIPELINE STAGES

A practical delivery pipeline might contain:

```text
Validate
↓
Test
↓
Build
↓
Scan
↓
Package
↓
Publish
↓
Deploy Staging
↓
Verify Staging
↓
Approve
↓
Deploy Production
↓
Verify Production
```

The exact names are not important.

The engineering boundaries are.

---

# 7. VALIDATION STAGE

The earliest stage should reject obvious problems cheaply.

Possible checks include:

```text
Formatting

Linting

Configuration syntax

Schema validation

Terraform validation

Helm linting

Helm rendering

Kubernetes manifest validation

Shell syntax

Python static checks
```

The principle is:

```text
Cheap Failure
↓
Early
```

rather than:

```text
Obvious Error
↓
Build
↓
Publish
↓
Deploy
↓
Discover Error
```

---

# 8. TEST STAGES

Tests should provide evidence at different levels.

A useful model is:

```text
Unit Tests
↓
Component Tests
↓
Integration Tests
↓
Deployment Tests
↓
Runtime Verification
```

These are not interchangeable.

## Unit Tests

Validate small pieces of application behavior.

## Integration Tests

Validate interaction between components.

## Deployment Tests

Validate that the packaged application can be deployed correctly.

## Runtime Verification

Validates the deployed system in its actual environment.

A pipeline with thousands of unit tests can still deploy a broken Kubernetes Service selector.

---

# 9. TESTS SHOULD ANSWER SPECIFIC QUESTIONS

Avoid thinking:

```text
Tests passed.
```

Ask:

```text
Which tests?

What behavior did they cover?

Which dependencies were real?

Which were mocked?

Which environment?

Which artifact?

Which risks remain untested?
```

Testing increases confidence.

Testing does not create certainty.

---

# 10. BUILD STAGE

The build stage transforms source into a deployable artifact.

For the application used throughout the previous Parts:

```text
Application Source
↓
Container Build
↓
Container Image
```

The image becomes the deployment artifact.

A strong delivery principle is:

> Build once, promote the same artifact.

---

# 11. BUILD ONCE, PROMOTE

Avoid:

```text
Source
↓
Build Development Image

Source
↓
Build Staging Image

Source
↓
Build Production Image
```

because these builds may not be identical.

Prefer:

```text
Source Revision
↓
Build Once
↓
Artifact A
     │
     ├── Development
     │
     ├── Staging
     │
     └── Production
```

Environment configuration should normally be supplied separately from rebuilding application code.

---

# 12. ARTIFACT IDENTITY

A deployable artifact should be identifiable.

For a container image, this may involve:

```text
Repository

Tag

Digest

Build metadata

Source revision
```

For reproducibility and high-confidence promotion, immutable artifact identity is preferable to relying entirely on mutable tags.

Conceptually:

```text
Commit
↓
Build
↓
Immutable Artifact
↓
Test
↓
Promote
↓
Deploy
```

---

# 13. ARTIFACTS

Pipeline artifacts are outputs intentionally produced for later consumption.

Examples include:

```text
Compiled binary

Container image

Helm chart package

Terraform plan

Test report

Coverage report

SBOM

Security scan report

Rendered manifests

Deployment metadata
```

Artifacts should have a defined lifecycle.

Ask:

```text
Who produces it?

Who consumes it?

How long is it retained?

Is it sensitive?

Can it be modified?

How is integrity established?
```

---

# 14. ARTIFACTS ARE NOT CACHES

This distinction is important.

## Artifact

An intentional output of a pipeline job.

Example:

```text
Build
↓
application.tar.gz
```

or:

```text
Terraform Plan
```

## Cache

Reusable data intended primarily to accelerate future work.

Example:

```text
Downloaded package dependencies
```

Therefore:

```text
Artifact
≠
Cache
```

Do not depend on an unreliable cache as the authoritative release artifact.

---

# 15. CACHING

Caching can reduce:

```text
Dependency download time

Build time

Repeated compilation

Network usage
```

Example:

```text
Pipeline Run 1
↓
Download dependencies
↓
Populate cache

Pipeline Run 2
↓
Restore cache
↓
Avoid unnecessary download
```

But caching introduces correctness concerns.

---

# 16. CACHE INVALIDATION

A cache key should reflect the inputs that make cached content valid.

Conceptually:

```text
Dependency Definition Changes
↓
Cache Key Changes
↓
New Cache
```

Otherwise:

```text
Old Cache
+
New Dependency Definition
=
Unexpected Build Behavior
```

The exact cache implementation varies by CI platform.

The principle does not.

---

# 17. CACHE POISONING AWARENESS

Caches cross execution boundaries.

Therefore, consider:

```text
Who can write the cache?

Who can read it?

Can untrusted branches influence trusted builds?

Can stale or malicious data enter later jobs?
```

A performance feature can become a security boundary.

Do not grant untrusted pipeline execution uncontrolled influence over production release inputs.

---

# 18. PARALLEL JOBS

Independent checks can often run simultaneously.

Instead of:

```text
Unit Tests
↓
Lint
↓
Security Scan
↓
Build
```

you might have:

```text
          ┌── Unit Tests ─────┐
          │                    │
Commit ───┼── Lint ────────────┼→ Continue
          │                    │
          └── Security Scan ───┘
```

This can reduce total pipeline duration.

---

# 19. PARALLELISM MUST RESPECT DEPENDENCIES

Do not parallelize jobs merely because the platform allows it.

For example:

```text
Build Artifact
↓
Artifact Scan
```

cannot be meaningfully reversed.

Ask:

```text
Does Job B actually require output from Job A?
```

If yes, encode that dependency.

---

# 20. FAIL FAST VERSUS COMPLETE EVIDENCE

Sometimes you want the pipeline to stop immediately after a critical failure.

Sometimes you want independent checks to finish so engineers receive more evidence.

Example:

```text
Lint fails

Unit tests can still run

Static security analysis can still run
```

Running independent checks may provide multiple actionable results in one pipeline.

The choice should be deliberate.

---

# 21. REUSABLE PIPELINES

Large engineering environments should avoid duplicating the same delivery logic across every repository.

Instead of:

```text
Repository A → copied pipeline

Repository B → copied pipeline

Repository C → copied pipeline
```

consider:

```text
Approved Reusable Pipeline Components
        ↑
        │
 ┌──────┼──────┐
 │      │      │
 A      B      C
```

Reusable workflows can centralize:

```text
Build conventions

Security checks

Artifact publication

Cloud authentication

Deployment logic

Policy enforcement
```

---

# 22. REUSE REDUCES DUPLICATION, NOT RESPONSIBILITY

A reusable pipeline does not mean application teams should stop understanding deployment behavior.

Teams still need to know:

```text
What is executed?

Which permissions are requested?

Which inputs are accepted?

Which artifacts are produced?

Which environment is modified?

How failures propagate?
```

Centralization without transparency creates hidden operational risk.

---

# 23. VERSION REUSABLE PIPELINE COMPONENTS

A shared pipeline can itself change.

Therefore:

```text
Application Source Version
```

and:

```text
Pipeline Logic Version
```

are separate change dimensions.

Where the CI platform supports it, reusable components should be referenced through deliberate versioning or immutable references appropriate to the platform and organizational policy.

Avoid silently changing the deployment behavior of hundreds of repositories without review.

---

# 24. PIPELINE CHANGES ARE PRODUCTION CHANGES

A pipeline file may control:

```text
Production deployment

Cloud authentication

Secret access

Artifact publishing

Terraform apply

Kubernetes changes
```

Therefore:

```text
Pipeline Code
=
Security-Sensitive Production Code
```

Changes to delivery configuration require appropriate review.

---

# 25. ENVIRONMENTS

A delivery environment represents a deployment target or operational context.

Common examples:

```text
Development

Testing

Staging

Production
```

An environment should not be only a string in a pipeline.

It should correspond to meaningful boundaries around:

```text
Configuration

Credentials

Infrastructure

Permissions

Data

Risk

Approvals
```

---

# 26. ENVIRONMENT SEPARATION

A useful model is:

```text
Development
↓
Staging
↓
Production
```

but promotion does not necessarily mean rebuilding.

Prefer:

```text
Same Approved Artifact
↓
Development Configuration
↓
Verification
↓
Same Artifact
↓
Staging Configuration
↓
Verification
↓
Same Artifact
↓
Production Configuration
```

This separates:

```text
Artifact
```

from:

```text
Environment Configuration
```

---

# 27. ENVIRONMENT PROMOTION

Promotion means increasing confidence and exposure.

Conceptually:

```text
Artifact Built
↓
Automated Tests
↓
Development
↓
Integration Verification
↓
Staging
↓
Production-Like Verification
↓
Production
```

Each transition should answer:

```text
What new evidence justifies moving forward?
```

---

# 28. STAGING IS NOT VALUABLE MERELY BECAUSE IT EXISTS

A staging environment that differs radically from production can provide false confidence.

Compare:

```text
Kubernetes version

Deployment mechanism

Ingress/Gateway behavior

Security policies

Configuration model

Storage model

External dependencies

Resource constraints
```

Exact equality is rarely possible or necessary.

But important production characteristics should be represented deliberately.

---

# 29. PIPELINE SECRETS

Pipelines may require access to:

```text
Registries

Cloud APIs

Kubernetes

Artifact repositories

External services

Signing systems
```

Avoid hardcoding credentials in:

```text
Pipeline YAML

Repository files

Dockerfiles

Shell scripts

Logs
```

Use the CI platform's approved secret-management mechanisms or external secret systems.

---

# 30. SECRET MASKING IS NOT COMPLETE SECURITY

A CI system may attempt to mask secrets in logs.

Do not treat masking as a guarantee.

Secrets can still leak through:

```text
Debug output

Encoded values

Generated files

Artifacts

Process arguments

Environment dumps

Third-party tools

Malicious scripts
```

The safest secret is one the job never receives unless it genuinely needs it.

---

# 31. LONG-LIVED CREDENTIALS

A traditional pipeline might store:

```text
Cloud Access Key
+
Cloud Secret Key
```

as long-lived CI secrets.

This creates rotation and exposure risk.

Where the platform and cloud provider support workload federation, prefer short-lived credentials obtained for the specific workload identity and execution context.

---

# 32. FEDERATED PIPELINE IDENTITY

The model is:

```text
CI Job Identity
↓
Identity Token
↓
Cloud Trust Policy
↓
Short-Lived Cloud Credential
↓
Authorized Action
```

This avoids storing a permanent cloud credential in the repository's CI configuration.

The exact implementation is provider- and CI-platform-specific.

---

# 33. IDENTITY IS NOT AUTHORIZATION

Successfully authenticating the pipeline answers:

```text
Who is this workload?
```

Authorization answers:

```text
What may it do?
```

A pipeline identity should not automatically receive:

```text
Administrator
```

permissions.

Use least privilege.

---

# 34. SERVICE IDENTITIES

Different delivery functions may deserve different identities.

For example:

```text
Build Identity
→ read source, push image

Staging Deployment Identity
→ modify staging

Production Deployment Identity
→ modify production

Terraform Planning Identity
→ read infrastructure

Terraform Apply Identity
→ modify approved infrastructure
```

This limits blast radius.

---

# 35. DO NOT USE ONE SUPERUSER IDENTITY FOR EVERYTHING

Avoid:

```text
One CI Credential
↓
Registry Admin
Cloud Admin
Kubernetes Admin
Secret Admin
Production Admin
```

If compromised, the blast radius becomes enormous.

Prefer bounded identities aligned to actual job responsibilities.

---

# 36. PIPELINE PERMISSIONS

Consider permissions at several layers:

```text
Source repository

CI platform

Artifact registry

Cloud provider

Kubernetes cluster

Secret manager

Infrastructure state backend

Deployment environment
```

A secure pipeline requires all of them to be considered.

---

# 37. UNTRUSTED CODE AND PRIVILEGED PIPELINES

Pull requests from untrusted sources require special care.

A pipeline that executes arbitrary changed code while simultaneously exposing production credentials can create a direct credential-theft path.

Separate:

```text
Untrusted Code Validation
```

from:

```text
Privileged Deployment Execution
```

using the CI platform's supported security model.

---

# 38. THIRD-PARTY PIPELINE COMPONENTS

CI ecosystems often allow external actions, plugins, templates, images, or extensions.

These execute inside the delivery chain.

Therefore:

```text
Third-Party Pipeline Component
=
Supply-Chain Dependency
```

Review:

```text
Publisher

Source

Version

Permissions

Inputs

Network access

Maintenance

Integrity controls
```

Use deliberate version pinning according to platform capabilities and organizational policy.

---

# 39. APPROVAL GATES

Some environments require explicit authorization before deployment.

Conceptually:

```text
Validated Release
↓
Production Deployment Requested
↓
Approval Gate
↓
Authorized?
├── Yes → Deploy
└── No  → Stop
```

An approval should be based on evidence.

---

# 40. APPROVAL IS NOT A DECORATIVE BUTTON

A useful approval should expose information such as:

```text
Source change

Artifact identity

Test results

Security results

Infrastructure changes

Rendered deployment changes

Target environment

Known risks

Recovery plan
```

Otherwise the approver is being asked to approve something they cannot meaningfully evaluate.

---

# 41. SEPARATION OF DUTIES

For higher-risk systems, the person proposing a production change may not be the only person authorized to approve it.

This can reduce:

```text
Accidental changes

Unauthorized changes

Single-person control

Insufficient review
```

The required model depends on organizational and regulatory requirements.

---

# 42. CHANGE ARTIFACTS

A production change should leave useful evidence.

Possible change artifacts include:

```text
Commit SHA

Pull request

Build identifier

Test results

Container digest

SBOM

Security scan

Helm chart version

Rendered manifest

Terraform plan

Approval record

Deployment record

Release revision

Verification result
```

These help answer:

```text
What exactly happened?
```

during later investigation.

---

# 43. TRACEABILITY

A strong release chain allows movement in both directions.

Forward:

```text
Commit
↓
Build
↓
Artifact
↓
Deployment
↓
Production
```

Backward:

```text
Production Workload
↓
Artifact
↓
Build
↓
Commit
↓
Change Review
```

If an engineer sees a running Pod, they should ideally be able to identify which artifact and source revision produced it.

---

# 44. SECURITY SCANNING

Security checks can operate at multiple layers.

Examples include:

```text
Source scanning

Dependency scanning

Secret scanning

Container image scanning

Infrastructure-as-code scanning

Kubernetes manifest scanning

SBOM generation

Policy evaluation
```

A single scanner does not cover every layer.

---

# 45. SCANNER RESULTS REQUIRE POLICY

Finding vulnerabilities is not enough.

The delivery process needs rules for:

```text
Severity

Exploitability

Exceptions

False positives

Accepted risk

Expiration of exceptions

Remediation ownership
```

Otherwise teams may either:

```text
Ignore everything
```

or:

```text
Block everything
```

Neither is mature risk management.

---

# 46. SECURITY CHECK SUCCESS DOES NOT PROVE SECURITY

A successful scanner means:

```text
The scanner did not detect a blocking issue
according to its rules and available data.
```

It does not mean:

```text
The application is secure.
```

Security scanning is evidence, not proof.

---

# 47. INFRASTRUCTURE STAGES

Application delivery may depend on infrastructure.

For example:

```text
Terraform Validate
↓
Terraform Plan
↓
Plan Review
↓
Infrastructure Apply
↓
Infrastructure Verification
↓
Application Deployment
```

Do not casually mix infrastructure mutation into every application pipeline if ownership and lifecycle differ.

---

# 48. INFRASTRUCTURE AND APPLICATION LIFECYCLES

Ask:

```text
Does this infrastructure change with every application release?

Who owns it?

Does it require separate approval?

Could its failure prevent application rollback?

What is its blast radius?
```

A shared network or production database should not necessarily be recreated or modified every time an application image changes.

---

# 49. DEPLOYMENT VERIFICATION

Deployment is not the end of the pipeline.

A stronger model is:

```text
Deploy
↓
Verify
↓
Observe
↓
Promote
```

Verification might include:

```text
Rollout status

Pod readiness

Service endpoints

HTTP checks

Application smoke tests

Dependency checks

Metrics

Logs

Error rates
```

---

# 50. VERIFY THE RELEASE THAT WAS ACTUALLY DEPLOYED

Do not merely verify:

```text
Application responds HTTP 200.
```

Also establish:

```text
Expected version is running.

Expected artifact is running.

Expected configuration is active.

Expected replicas are Ready.

Expected traffic reaches the new version.
```

Otherwise you may accidentally verify an old healthy version.

---

# 51. READINESS IS NECESSARY BUT LIMITED

Kubernetes readiness probes help determine whether a Pod should receive Service traffic.

They do not necessarily validate:

```text
Every user workflow

All external dependencies

Business correctness

Error-rate regression

Performance regression
```

Deployment verification should extend beyond readiness where risk justifies it.

---

# 52. SMOKE TESTS

A smoke test asks whether essential functionality works after deployment.

For example:

```text
Can application endpoint respond?

Can required dependency be reached?

Can a basic application operation complete?
```

Smoke tests should be:

```text
Fast

Reliable

Non-destructive where possible

Specific enough to provide useful evidence
```

---

# 53. POST-DEPLOYMENT OBSERVATION

Some failures emerge only after real traffic reaches the new version.

Observe:

```text
Error rate

Latency

Request volume

Resource utilization

Restart count

Dependency failures

Application-specific health indicators
```

The appropriate observation period depends on application behavior and deployment risk.

---

# 54. HEALTHY IS A DEFINED CONDITION

Do not encode:

```text
Healthy = pipeline command returned 0
```

Define release health using relevant evidence.

For example:

```text
Rollout complete
AND
Ready replicas expected
AND
Smoke test passes
AND
Error rate acceptable
AND
No critical new alert
```

The exact criteria are application-specific.

---

# 55. FAILURE HANDLING

The core model is:

```text
Deploy
↓
Verify
↓
Observe
↓
Healthy?
├── Yes → Continue
└── No  → Stop / Roll Back / Recover
```

The correct failure response depends on what changed.

---

# 56. STOP

Sometimes the safest response is simply:

```text
Do not promote further.
```

For example:

```text
Canary is unhealthy
↓
Stop increasing traffic
```

Stopping progression can be safer than immediately making another change.

---

# 57. ROLLBACK

Rollback attempts to return application configuration or artifact selection to a known previous state.

For Kubernetes/Helm:

```text
New Release
↓
Failure
↓
Previous Release
```

But remember Part 14:

```text
Helm Rollback
≠
Complete System Rollback
```

---

# 58. ROLLBACK LIMITATIONS

Rollback may not reverse:

```text
Database migration

Data deletion

External API side effect

Message already published

User transaction

Secret rotation

Infrastructure mutation

Persistent format change
```

Therefore every pipeline should avoid assuming:

```text
Deployment failed
↓
Rollback
↓
Everything restored
```

---

# 59. FORWARD FIX

Sometimes the safest recovery is a new corrected release rather than reverting.

This is sometimes called:

```text
Roll forward
```

For example, if a database migration cannot safely be reversed, the team may deploy an application correction compatible with the new schema.

The decision depends on evidence and recovery design.

---

# 60. PARTIAL DEPLOYMENT FAILURE

A deployment can fail after changing some resources.

For example:

```text
ConfigMap updated
✓

Deployment updated
✓

New Pods created
✓

Readiness
✗
```

The environment is no longer necessarily in its old state.

Troubleshooting must determine:

```text
What changed?

What did not?

Which version is receiving traffic?

Which resources are partially reconciled?
```

---

# 61. PIPELINE FAILURE DOES NOT ALWAYS MEAN DEPLOYMENT FAILURE

A pipeline can report failure because:

```text
Post-deployment verification failed
```

while the application deployment itself completed.

Or:

```text
Notification step failed
```

after a healthy deployment.

Therefore:

```text
Pipeline Failed
```

does not automatically mean:

```text
Production Deployment Failed
```

Find the exact failing stage.

---

# 62. PIPELINE SUCCESS DOES NOT ALWAYS MEAN APPLICATION SUCCESS

The reverse is also true.

A pipeline may report success even though:

```text
Verification was insufficient

Wrong environment was targeted

Old application was tested

Important metrics were ignored

Background processing is failing
```

Pipeline status is one evidence source.

---

# 63. DEPLOYMENT STRATEGY

Deployment strategy controls how a new application version replaces or coexists with the previous version.

The strategy affects:

```text
Availability

Blast radius

Infrastructure capacity

Rollback speed

Operational complexity

Traffic control

Verification opportunity
```

There is no universally best strategy.

---

# 64. RECREATE DEPLOYMENT

Conceptually:

```text
Version A
↓
Stop Version A
↓
Start Version B
```

Traffic model:

```text
A A A
↓
- - -
↓
B B B
```

This is simple.

It can create downtime.

---

# 65. WHEN RECREATE MAY BE ACCEPTABLE

Recreate may be reasonable when:

```text
Downtime is acceptable

Old and new versions cannot coexist

Environment is non-production

Application is low criticality

Maintenance window exists
```

It is not inherently wrong.

Its availability trade-off must be understood.

---

# 66. RECREATE RISKS

If Version B fails:

```text
Version A
↓
Removed
↓
Version B
↓
Fails
```

there may be no healthy application serving traffic.

Recovery requires restoring a working version.

---

# 67. KUBERNETES RECREATE

Kubernetes Deployments support a `Recreate` strategy.

Conceptually:

```yaml
spec:
  strategy:
    type: Recreate
```

Do not copy this into production merely to simplify deployment behavior.

Choose it because the application's requirements justify it.

---

# 68. ROLLING DEPLOYMENT

A rolling deployment gradually replaces old instances with new instances.

Conceptually:

```text
A A A A
↓
A A A B
↓
A A B B
↓
A B B B
↓
B B B B
```

This can maintain availability while the deployment progresses.

---

# 69. KUBERNETES ROLLINGUPDATE

Kubernetes Deployments support:

```text
RollingUpdate
```

and it is the normal/default Deployment strategy.

Two important controls are:

```text
maxUnavailable

maxSurge
```

These influence how many Pods may be unavailable and how many additional Pods may temporarily exist during the rollout.

---

# 70. `MAXUNAVAILABLE`

Conceptually:

```text
How much existing capacity may be unavailable during rollout?
```

A more aggressive value can increase rollout speed while reducing available capacity.

A stricter value can preserve more availability but may slow rollout or require additional capacity.

---

# 71. `MAXSURGE`

Conceptually:

```text
How much extra temporary capacity may be created during rollout?
```

Higher surge can allow faster replacement but requires:

```text
Cluster capacity

Quota

Application dependency capacity
```

The setting must match the environment's actual capacity.

---

# 72. ROLLING UPDATE DOES NOT MEAN ZERO DOWNTIME

Zero downtime depends on more than deployment strategy.

It can require:

```text
Enough replicas

Correct readiness probes

Graceful termination

Adequate capacity

Compatible application versions

Compatible database schema

Traffic draining

Healthy dependencies
```

Therefore:

```text
RollingUpdate
≠
Guaranteed Zero Downtime
```

---

# 73. VERSION COEXISTENCE

During a rolling deployment:

```text
Version A
```

and:

```text
Version B
```

may run simultaneously.

Therefore ask:

```text
Can both versions use the same database?

Can both consume the same messages?

Can both understand the same data format?

Can both serve requests consistently?
```

This is a critical application design requirement.

---

# 74. BACKWARD-COMPATIBLE DATABASE CHANGES

Suppose Version B requires a new database column.

A safer migration may follow:

```text
Add backward-compatible schema
↓
Deploy application that understands old + new state
↓
Migrate usage
↓
Remove old compatibility later
```

rather than:

```text
Break old schema
↓
Deploy new application
```

while Version A is still running.

Deployment strategy and data migration strategy must be designed together.

---

# 75. GRACEFUL TERMINATION DURING ROLLING UPDATES

When old Pods terminate, applications should handle termination signals appropriately.

Recall Part 10:

```text
SIGTERM
↓
Application stops accepting new work
↓
In-flight work completes where possible
↓
Application exits
```

Poor signal handling can turn an otherwise correct rolling deployment into user-visible failures.

---

# 76. BLUE-GREEN DEPLOYMENT

Blue-green deployment maintains two application environments or versions.

Conceptually:

```text
              ┌── Blue: Version A
Users → Traffic Switch
              └── Green: Version B
```

Initially:

```text
Users
↓
Blue
```

Green is deployed and validated separately.

Then traffic changes:

```text
Users
↓
Green
```

Blue may remain temporarily available for rapid traffic reversal.

---

# 77. BLUE-GREEN MENTAL MODEL

```text
Deploy New Environment
↓
Verify New Environment
↓
Ready?
├── No  → Keep Traffic on Old Environment
└── Yes
     ↓
Switch Traffic
     ↓
Observe
     ↓
Healthy?
├── Yes → Continue
└── No  → Switch Back if Safe
```

---

# 78. BLUE-GREEN BENEFITS

Potential benefits include:

```text
Pre-traffic validation

Rapid traffic switching

Clear old/new separation

Fast application traffic reversal
```

But these benefits depend on architecture.

---

# 79. BLUE-GREEN COSTS

Blue-green can require additional:

```text
Compute

Memory

Network capacity

Load-balancer configuration

Operational complexity
```

because both environments may exist simultaneously.

---

# 80. BLUE-GREEN DOES NOT DUPLICATE ALL STATE AUTOMATICALLY

The application environments may still share:

```text
Database

Object storage

Message broker

External services
```

Therefore switching traffic does not necessarily restore old data state.

Again:

```text
Traffic Rollback
≠
Data Rollback
```

---

# 81. BLUE-GREEN WITH KUBERNETES

A simplified Kubernetes model might use:

```text
Blue Deployment
Green Deployment
        +
Service
```

The Service selector determines which environment receives traffic.

For example:

```text
Service
selector:
  version=blue
```

then later:

```text
Service
selector:
  version=green
```

Production implementations may use more sophisticated controllers or traffic-management systems.

---

# 82. CANARY DEPLOYMENT

Canary deployment exposes a new version to a limited portion of traffic or users before broader promotion.

Conceptually:

```text
Version A → 95%
Version B → 5%
```

Then:

```text
Version A → 75%
Version B → 25%
```

Then:

```text
Version A → 50%
Version B → 50%
```

Eventually:

```text
Version B → 100%
```

if evidence remains acceptable.

---

# 83. CANARY IS ABOUT CONTROLLED EXPOSURE

The core idea is:

```text
New Version
↓
Small Exposure
↓
Measure
↓
Healthy?
├── Yes → Increase Exposure
└── No  → Stop / Reverse
```

This limits initial blast radius.

---

# 84. CANARY REQUIRES MEANINGFUL OBSERVABILITY

If you cannot distinguish:

```text
Version A metrics
```

from:

```text
Version B metrics
```

then canary analysis becomes difficult.

Useful evidence may include:

```text
Error rate by version

Latency by version

Request count by version

Resource behavior

Business metrics

Dependency failures
```

Canary deployment without observability can become slow rolling deployment with extra complexity.

---

# 85. CANARY TRAFFIC CONTROL

Traffic splitting may be implemented through technologies such as:

```text
Ingress controllers

Gateway implementations

Service meshes

Load balancers

Progressive-delivery controllers
```

Exact capability depends on the platform.

A standard Kubernetes Deployment by itself does not provide full percentage-based application traffic management.

---

# 86. PROGRESSIVE DELIVERY

Canary and advanced blue-green workflows are often described as forms of progressive delivery.

A progressive system may support:

```text
Traffic steps

Pause

Manual promotion

Automated metric analysis

Automatic abort

Experimentation
```

This extends beyond basic Deployment rolling behavior.

---

# 87. CANARY ANALYSIS

Suppose:

```text
Stable Version Error Rate = normal

Canary Version Error Rate = significantly elevated
```

The system may decide:

```text
Do not promote.
```

But analysis requires carefully chosen thresholds.

Poor thresholds can:

```text
Promote unhealthy releases

Reject healthy releases

Flap between states
```

---

# 88. CANARY SAMPLE SIZE

A canary receiving:

```text
3 requests
```

may not provide enough evidence to assess behavior.

Therefore consider:

```text
Traffic volume

Observation duration

Metric variability

User distribution

Workload diversity
```

Do not promote solely because:

```text
Canary ran for 30 seconds without error.
```

unless that provides meaningful evidence for the application.

---

# 89. FEATURE FLAGS

Feature flags separate:

```text
Code Deployment
```

from:

```text
Feature Exposure
```

Conceptually:

```text
New Code Deployed
↓
Feature Disabled
↓
Enable for Internal Users
↓
Enable for Small Audience
↓
Observe
↓
Expand
```

This provides another risk-control mechanism.

---

# 90. DEPLOYMENT IS NOT RELEASE

With feature flags:

```text
Deployment
=
Code entered environment
```

while:

```text
Release
=
Capability became available to users
```

These can occur at different times.

---

# 91. FEATURE FLAG USE CASES

Flags can support:

```text
Gradual feature rollout

Internal testing

Limited user exposure

Operational kill switches

Experimentation
```

But they introduce complexity.

---

# 92. FEATURE FLAG DEBT

Long-lived flags can create:

```text
Dead code

Conflicting branches

Testing explosion

Unknown behavior combinations

Operational confusion
```

Flags should have ownership and lifecycle.

Ask:

```text
Who owns this flag?

When should it be removed?

What is the safe default?

What happens if flag service is unavailable?
```

---

# 93. FEATURE FLAG IS NOT A UNIVERSAL ROLLBACK

Turning off a feature may stop new use of a code path.

It may not reverse:

```text
Database changes

Data mutations

Messages emitted

External side effects
```

Again:

```text
Disable Feature
≠
Undo Everything Feature Did
```

---

# 94. COMPARING DEPLOYMENT STRATEGIES

| Strategy | New and Old Coexist? | Traffic Control | Extra Capacity | Initial Blast Radius |
|---|---|---|---|---|
| Recreate | Normally no | Minimal | Low | Potentially full |
| Rolling | Yes temporarily | Pod replacement based | Moderate | Progressive by instances |
| Blue-green | Yes | Environment switch | Often high | Controlled at switch |
| Canary | Yes | Progressive | Varies | Intentionally limited |
| Feature flags | Same code can expose different behavior | Application-level | Usually low infrastructure impact | Can be highly targeted |

These are conceptual differences.

Actual behavior depends on implementation.

---

# 95. CHOOSING A STRATEGY

Consider:

```text
Availability requirement

Application architecture

Database compatibility

Traffic volume

Observability maturity

Infrastructure capacity

Rollback capability

Deployment frequency

Risk tolerance

Cost

Operational complexity
```

Do not choose canary because it sounds more advanced.

Use the simplest strategy that satisfies the system's requirements safely.

---

# 96. STRATEGIES CAN BE COMBINED

For example:

```text
Rolling Deployment
+
Feature Flag
```

or:

```text
Canary Deployment
+
Feature Flag
```

or:

```text
Blue-Green
+
Database Expand/Contract Migration
```

These solve different risk dimensions.

---

# 97. CONCURRENCY

Two deployments targeting the same environment simultaneously can create unpredictable results.

Example:

```text
Pipeline A
↓
Deploy Version 10

Pipeline B
↓
Deploy Version 11
```

If they overlap:

```text
Which version should win?
```

The delivery system needs an explicit concurrency model.

---

# 98. SERIALIZE ENVIRONMENT MUTATION WHERE REQUIRED

For a production environment, it is often safer to ensure only one conflicting deployment operation modifies the same release at a time.

Conceptually:

```text
Production Deployment Lock
↓
Pipeline A
↓
Complete
↓
Pipeline B
```

Exact concurrency controls are CI-platform-specific.

---

# 99. NEWER CHANGE OVERTAKING OLDER CHANGE

Suppose:

```text
Commit A
↓
Slow pipeline

Commit B
↓
Fast pipeline
```

Without controls:

```text
B deploys
↓
A finishes later
↓
A deploys
```

Production is now running older code.

Delivery systems should deliberately handle stale deployments.

---

# 100. PIPELINE CANCELLATION

Cancelling an obsolete pipeline can save resources.

But cancellation during deployment can be dangerous.

Ask:

```text
Was the job still validating?

Was artifact publication in progress?

Had production mutation begun?

Could cancellation leave partial state?
```

Do not assume cancellation means nothing happened.

---

# 101. TIMEOUTS

Every external operation can hang.

Examples:

```text
Build

Test

Registry push

Terraform operation

Helm upgrade

Rollout verification

Smoke test
```

Use deliberate timeouts.

But do not use extremely short timeouts that convert normal slow behavior into false failures.

---

# 102. RETRIES

Retries can help with transient failures.

Suitable examples might include:

```text
Temporary registry network failure

Transient API response

Temporary dependency download failure
```

Retries are dangerous for non-idempotent operations.

Ask:

```text
If the first attempt actually succeeded but the response was lost,
what happens when we repeat it?
```

---

# 103. DO NOT RETRY UNKNOWN MUTATIONS BLINDLY

Suppose:

```text
Deploy request
↓
Timeout
```

You do not yet know whether:

```text
Nothing happened
```

or:

```text
Deployment succeeded but response was lost.
```

First inspect the environment.

Then decide whether retry is safe.

---

# 104. PIPELINE OBSERVABILITY

The pipeline itself is a production system.

Monitor:

```text
Pipeline duration

Failure rate

Queue time

Runner availability

Cache performance

Artifact publication failures

Deployment frequency

Deployment failures
```

Operational visibility helps distinguish:

```text
Application failure
```

from:

```text
Delivery platform failure
```

---

# 105. JOB LOGGING

Logs should show enough context to troubleshoot:

```text
Stage

Job

Artifact identifier

Environment

Relevant non-sensitive inputs

Command outcome

Verification result
```

Avoid dumping:

```text
Entire environment

Secrets

Tokens

Kubeconfigs

Cloud credentials
```

for convenience.

---

# 106. PIPELINE EVIDENCE

For each job, preserve useful evidence.

For example:

```text
Unit Test Job
→ test report

Image Build
→ digest

Image Scan
→ vulnerability report

Helm Validation
→ rendered manifest

Terraform Plan
→ reviewed plan artifact

Deploy
→ release revision

Verify
→ test and health evidence
```

This makes the pipeline explainable.

---

# 107. PIPELINE FAILURE CLASSIFICATION

When a pipeline fails, classify it before fixing it.

Possible classes:

```text
Source failure

Dependency failure

Test failure

Build failure

Security failure

Artifact failure

Authentication failure

Authorization failure

Infrastructure failure

Deployment failure

Runtime failure

Verification failure

CI-platform failure
```

This prevents random remediation.

---

# 108. SOURCE FAILURE

Examples:

```text
Syntax error

Formatting violation

Compilation failure

Invalid configuration
```

The environment may not have been touched.

Fix the source.

---

# 109. TEST FAILURE

A test failure means the tested expectation was not met.

Investigate:

```text
Which test?

Expected behavior?

Observed behavior?

Code regression?

Flaky test?

Environment dependency?

Test data?
```

Do not automatically rerun until green without understanding why it failed.

---

# 110. BUILD FAILURE

Possible causes:

```text
Dependency unavailable

Compiler error

Dockerfile problem

Architecture mismatch

Missing file

Wrong build context

Runner resource exhaustion
```

Determine whether failure is:

```text
Source-dependent
```

or:

```text
Build-environment-dependent
```

---

# 111. ARTIFACT PUBLICATION FAILURE

Suppose:

```text
Build
✓

Tests
✓

Image Push
✗
```

Production has not necessarily been changed.

Investigate:

```text
Registry authentication

Authorization

Network

Repository existence

Quota

Artifact naming
```

Do not troubleshoot Kubernetes yet.

---

# 112. PIPELINE CREDENTIAL FAILURE

Distinguish:

```text
Authentication failure
```

from:

```text
Authorization failure
```

Authentication:

```text
Who are you?
```

Authorization:

```text
You are known, but may you perform this action?
```

The remediation is different.

---

# 113. EXPIRED CREDENTIALS

Symptoms may include:

```text
Previously working pipeline suddenly cannot authenticate

Token expiration errors

Cloud authentication rejection

Registry login failure
```

Prefer identity models that minimize long-lived secret rotation where supported.

---

# 114. WRONG IDENTITY

A pipeline can authenticate successfully using the wrong identity.

Then it may:

```text
Lack required access
```

or worse:

```text
Have unintended access.
```

Inspect:

```text
Identity

Role

Environment

Trust conditions

Permissions
```

---

# 115. WRONG ENVIRONMENT

One of the highest-risk failures is:

```text
Correct deployment
↓
Wrong target
```

Examples:

```text
Staging artifact deployed to production unexpectedly

Production deployment sent to wrong cluster

Wrong cloud account

Wrong namespace

Wrong Helm release
```

Always verify target context before mutation.

---

# 116. ENVIRONMENT GUARDRAILS

Useful controls can include:

```text
Protected environments

Dedicated identities

Explicit environment variables

Approval gates

Cluster/account identifiers

Namespace restrictions

Policy checks

Separate state
```

Do not rely only on naming conventions.

---

# 117. FAILED PARTIAL APPLY

Infrastructure or deployment operations may fail after partial success.

Example:

```text
Resource A
✓

Resource B
✓

Resource C
✗
```

Do not assume automatic rollback.

Inspect actual state.

For Terraform, recall:

```text
Apply Failure
≠
Automatic Reversal of Every Completed Change
```

For Kubernetes:

```text
Deployment Failure
≠
No Resources Changed
```

---

# 118. UNEXPECTED DESTRUCTIVE CHANGE

A pipeline may expose a plan showing:

```text
Delete

Replace

Recreate

Scale to zero

Remove persistent resource
```

The correct response is:

```text
Stop
↓
Understand why
```

not:

```text
Approve because pipeline generated it.
```

Automation does not authorize destruction.

---

# 119. DRIFT DETECTION

Infrastructure and runtime state can drift from declared configuration.

Possible drift sources include:

```text
Emergency manual changes

Unauthorized changes

External automation

Provider/controller behavior

Configuration mistakes
```

Delivery workflows can periodically compare:

```text
Declared State
```

with:

```text
Observed State
```

and report differences.

---

# 120. DRIFT DETECTION IS NOT AUTOMATIC REMEDIATION

A drift detector may discover:

```text
Production differs from Git.
```

That does not immediately answer:

```text
Which state is correct?
```

The manual production change may have been an emergency correction.

Determine intent before reconciliation.

---

# 121. DATABASE MIGRATIONS IN DELIVERY PIPELINES

Database changes are one of the most important deployment-risk areas.

A dangerous pipeline assumes:

```text
Deploy Application
+
Run Migration
+
Rollback Application If Needed
=
Safe
```

Not necessarily.

Database migration may be irreversible.

---

# 122. EXPAND AND CONTRACT CONCEPT

A safer compatibility pattern is:

```text
EXPAND
↓
Introduce backward-compatible schema
↓
Deploy code supporting old + new
↓
Migrate usage/data
↓
Confirm old path unused
↓
CONTRACT
↓
Remove old schema later
```

This can support rolling, canary, and blue-green deployments where versions coexist.

---

# 123. MIGRATION OWNERSHIP

A pipeline should know:

```text
Who owns migrations?

When do they run?

Can they run twice?

Can they be retried?

Are they backward compatible?

How are failures recovered?

Can old application versions still run afterward?
```

Do not hide migrations inside opaque startup scripts without understanding their operational consequences.

---

# 124. DEPLOYMENT WINDOWS

Some systems restrict high-risk changes to defined periods.

A deployment window may consider:

```text
Support availability

Traffic patterns

Business events

Dependency maintenance

On-call coverage
```

This is an operational control, not a substitute for technical safety.

---

# 125. FREEZE PERIODS

Organizations may temporarily prevent production changes during:

```text
Major business events

Financial close

Peak traffic

Regulatory periods

Known infrastructure instability
```

Emergency changes may require a separate controlled path.

---

# 126. MANUAL DEPLOYMENTS

Manual does not automatically mean safe.

An engineer manually running:

```text
helm upgrade
```

can still make an unsafe change.

Automation can improve:

```text
Repeatability

Auditability

Consistency

Verification
```

The goal is not automation for its own sake.

The goal is controlled delivery.

---

# 127. AUTOMATION DOES NOT REMOVE HUMAN ACCOUNTABILITY

A pipeline may execute the change.

Humans remain responsible for:

```text
Intent

Review

Policy

Risk acceptance

Architecture

Recovery design

Verification standards
```

The automation is an execution mechanism.

---

# 128. DELIVERY SECURITY MODEL

A useful trust model is:

```text
Source Identity
↓
Reviewed Change
↓
Trusted Pipeline
↓
Trusted Build Environment
↓
Verified Artifact
↓
Authorized Deployment Identity
↓
Protected Environment
↓
Verified Runtime
```

A weakness at any stage can undermine the chain.

---

# 129. BUILD RUNNER SECURITY

Runners execute code.

Therefore consider:

```text
Isolation

Persistence between jobs

Network access

Credential access

Host access

Cache access

Artifact access
```

Self-hosted runners require especially deliberate lifecycle and isolation design because the organization controls their operating environment.

---

# 130. EPHEMERAL EXECUTION

Where appropriate, ephemeral workers can reduce cross-job contamination.

Conceptually:

```text
Job
↓
Fresh Worker
↓
Execute
↓
Destroy Worker
```

This can reduce persistence of:

```text
Credentials

Build files

Malicious modifications

Cross-job state
```

but does not remove all pipeline security concerns.

---

# 131. DEPENDENCY PINNING

Pipeline reproducibility depends on controlled dependencies.

Examples include:

```text
Container build images

CI actions/plugins

Package dependencies

Helm charts

Terraform providers

Reusable workflows
```

Avoid uncontrolled dependency movement where reproducibility matters.

---

# 132. REPRODUCIBLE RELEASE QUESTION

For a production release, ask:

> Can we identify the exact source, pipeline logic, dependencies, artifact, configuration, approval, and deployment evidence that produced this running version?

If not, incident reconstruction becomes harder.

The final question is not:

```text
Can I write a CI/CD pipeline?
```

It is:

```text
Can I design a delivery system that takes a reviewed source change,
produces a traceable and immutable artifact,
validates that artifact through meaningful evidence,
protects credentials and production permissions,
promotes the same artifact through controlled environments,
chooses a deployment strategy appropriate to the application's
availability, compatibility, data, and recovery requirements,
detects failures at the correct layer,
limits blast radius,
stops unsafe promotion,
and proves that the production system reached the intended state?
```
