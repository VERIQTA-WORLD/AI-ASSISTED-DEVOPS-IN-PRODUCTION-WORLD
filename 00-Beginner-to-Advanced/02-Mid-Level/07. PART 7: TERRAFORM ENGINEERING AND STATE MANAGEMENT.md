# PART 7: TERRAFORM ENGINEERING AND STATE MANAGEMENT

## Goal

Move from basic Terraform usage into maintainable infrastructure engineering.

At an introductory level, Terraform often appears simple:

```text
Write configuration
↓
terraform init
↓
terraform plan
↓
terraform apply
↓
Infrastructure exists
```

That workflow is useful for learning, but production Terraform engineering involves a much larger problem.

Infrastructure changes over time.

Multiple engineers work on it.

Cloud resources may be modified outside Terraform.

Modules evolve.

Provider versions change.

Resources may already exist before Terraform begins managing them.

A configuration change may update one resource in place while replacing another resource completely.

State may be stored remotely.

A failed operation may leave infrastructure and state requiring careful investigation.

A seemingly harmless refactor can change resource addresses and produce an unexpected destruction plan.

Terraform therefore must be understood as more than a tool that creates infrastructure.

It is a system for reconciling **desired infrastructure configuration**, **Terraform's recorded state**, and **real infrastructure**.

The central model for this Part is:

```text
Terraform Configuration
Desired State
        │
        │
        ▼
Terraform Planning Engine
        │
        ├──────── Terraform State
        │
        └──────── Provider APIs
                         │
                         ▼
                 Real Infrastructure
```

A Mid-Level engineer must understand all three.

If configuration is understood but state is not, Terraform is dangerous.

If state is understood but provider behavior is not, Terraform plans can be misinterpreted.

If the real infrastructure is ignored, drift can remain hidden until the next refresh or plan.

The objective is to reach this engineering workflow:

```text
Understand Requirement
↓
Understand Existing Infrastructure
↓
Design Terraform Structure
↓
Write or Modify Configuration
↓
Format
↓
Validate
↓
Initialize
↓
Plan
↓
Read the Entire Plan
↓
Assess Risk and Replacement
↓
Apply Through the Approved Workflow
↓
Verify Real Infrastructure
↓
Verify Terraform State
↓
Monitor for Drift
↓
Maintain Safely
```

---

# 1. TERRAFORM AS A DECLARATIVE SYSTEM

Terraform configuration describes a desired infrastructure state.

You generally describe **what should exist**, rather than writing every low-level API operation required to create it.

For example:

```hcl
resource "example_server" "app" {
  name = "app-server"
  size = "small"
}
```

Conceptually, this means:

```text
Desired State

A server should exist
with these characteristics
```

Terraform then works with the provider to determine what operations are necessary.

The engineering model is:

```text
Configuration
↓
Desired Infrastructure
↓
Terraform compares desired and observed state
↓
Execution Plan
↓
Provider API operations
↓
Infrastructure changes
```

The resource type above is intentionally generic. Real resource arguments and lifecycle behavior are provider-specific and must be verified against the provider documentation.

---

# 2. DECLARATIVE DOES NOT MEAN SIMPLE

Declarative configuration removes some procedural work, but it does not remove engineering responsibility.

A configuration may be syntactically valid while being operationally dangerous.

For example:

```text
Valid Terraform
↓
Valid Provider Request
↓
Destructive Infrastructure Change
```

Terraform successfully executing a plan does not prove that the plan was appropriate.

The engineer still owns:

```text
Architecture

Security

Availability

Cost

Change Risk

State Safety

Data Safety

Verification

Recovery
```

---

# 3. THE THREE STATES YOU MUST REASON ABOUT

Terraform troubleshooting becomes much easier when three different forms of state are separated.

## Configuration

What the code declares should exist.

## Terraform State

Terraform's recorded relationship between configuration resource addresses and remote objects, plus associated metadata and attributes.

## Real Infrastructure

What actually exists in the provider.

Conceptually:

```text
Configuration
"What should exist"

Terraform State
"What Terraform currently tracks"

Real Infrastructure
"What actually exists"
```

A healthy Terraform workflow attempts to reconcile these views.

---

# 4. TERRAFORM CONFIGURATION STRUCTURE

A maintainable Terraform root module commonly contains files such as:

```text
terraform/
├── terraform.tf
├── providers.tf
├── variables.tf
├── locals.tf
├── main.tf
├── outputs.tf
└── versions.tf
```

This is an organizational convention, not a requirement of the Terraform language.

Terraform evaluates the relevant `.tf` files in a directory together as a module.

The filenames help humans organize the configuration.

Do not confuse file boundaries with Terraform dependency boundaries.

---

# 5. TERRAFORM BLOCK

Terraform settings can be declared in a `terraform` block.

For example:

```hcl
terraform {
  required_version = ">= 1.6.0"
}
```

Production configurations should deliberately manage compatibility rather than silently assuming that every engineer and CI runner uses a compatible Terraform version.

Version constraints must be selected according to the project's tested requirements.

Do not copy a version constraint simply because it appears in an example.

---

# 6. PROVIDERS

Providers allow Terraform to interact with external APIs.

Conceptually:

```text
Terraform
↓
Provider
↓
Remote API
↓
Infrastructure
```

A provider understands resource-specific operations such as:

```text
Create

Read

Update

Delete
```

Terraform itself does not independently understand every cloud service.

Provider implementations translate Terraform's resource model into interactions with the target platform.

---

# 7. PROVIDER REQUIREMENTS

A configuration should define the providers it requires.

Conceptually:

```hcl
terraform {
  required_providers {
    example = {
      source  = "example/example"
      version = "~> 1.0"
    }
  }
}
```

The provider above is illustrative.

Real provider source addresses and version constraints must come from current provider documentation.

---

# 8. PROVIDER VERSION CONTROL

Provider behavior can change between versions.

Therefore:

```text
Terraform Configuration
+
Provider Version
+
Terraform Version
```

together influence behavior.

Do not treat provider versions as incidental implementation details.

A provider upgrade can introduce:

```text
New arguments

Removed behavior

Changed defaults

Schema changes

Deprecations

State migrations

Different planning behavior
```

Review upgrade documentation before changing important provider versions.

---

# 9. THE DEPENDENCY LOCK FILE

After initialization, Terraform can create:

```text
.terraform.lock.hcl
```

The dependency lock file records provider dependency selections and checksums used by Terraform.

For normal Terraform repositories, this file should generally be reviewed and committed to version control so provider selections are reproducible.

Do not confuse:

```text
.terraform.lock.hcl
```

with:

```text
terraform.tfstate
```

They serve completely different purposes.

---

# 10. DO NOT COMMIT THE WORKING DIRECTORY

Terraform initialization commonly creates:

```text
.terraform/
```

This directory contains local working data such as downloaded provider plugins and module information.

It normally does not belong in version control.

Repository hygiene should distinguish:

```text
Configuration
→ commit

Dependency lock file
→ normally commit

.terraform directory
→ ignore

Local state
→ do not commit

Sensitive variable files
→ do not commit unless deliberately safe
```

---

# 11. RESOURCES

A `resource` block declares infrastructure Terraform should manage.

General structure:

```hcl
resource "<TYPE>" "<LOCAL_NAME>" {
  # arguments
}
```

The combination of resource type and local name forms part of the Terraform resource address.

For example:

```hcl
resource "example_server" "app" {
  name = "production-app"
}
```

might have the address:

```text
example_server.app
```

The resource address matters because Terraform state associates that address with a real remote object.

---

# 12. RESOURCE ADDRESS IS NOT JUST A LABEL

Consider:

```hcl
resource "example_server" "app" {
  name = "production-app"
}
```

Terraform may conceptually track:

```text
example_server.app
↓
Remote object ID
↓
Real server
```

Changing configuration structure can therefore affect how Terraform identifies managed objects.

Refactoring Terraform must consider state addresses, not only HCL appearance.

---

# 13. DATA SOURCES

A managed resource generally represents infrastructure Terraform is responsible for managing.

A data source reads information.

Conceptually:

```text
resource
→ Terraform manages lifecycle
```

while:

```text
data source
→ Terraform reads information
```

Example:

```hcl
data "example_network" "shared" {
  name = "shared-network"
}
```

Then another resource may reference:

```hcl
data.example_network.shared.id
```

The exact data source and arguments depend on the provider.

---

# 14. WHEN DATA SOURCES ARE USEFUL

Data sources are useful when infrastructure already exists and another system owns its lifecycle.

For example:

```text
Central Network Team
↓
Owns Shared Network
↓
Application Terraform
↓
Reads Network Information
↓
Deploys Application Resources
```

The application configuration does not necessarily need to manage the shared network.

It may only need its identifier.

---

# 15. DATA SOURCE IS NOT IMPORT

These solve different problems.

```text
Data Source
→ Read an object managed elsewhere
```

```text
Import
→ Bring an existing object under this Terraform configuration/state
```

Do not import infrastructure merely because you need to reference it.

First determine ownership.

---

# 16. INPUT VARIABLES

Variables form the input interface of a module.

Example:

```hcl
variable "environment" {
  description = "Deployment environment"
  type        = string
}
```

Then:

```hcl
resource "example_server" "app" {
  name = "${var.environment}-app"
}
```

Variables allow configuration to receive information rather than embedding every value directly.

---

# 17. VARIABLES ARE INTERFACES

A good variable communicates:

```text
What value is required?

What type?

Why?

Is there a default?

What values are valid?

Is it sensitive?
```

Poor interface:

```hcl
variable "x" {}
```

Better interface:

```hcl
variable "environment" {
  description = "Deployment environment name."
  type        = string
}
```

Interfaces should be understandable without reverse-engineering the module.

---

# 18. VARIABLE TYPES

Terraform supports rich type constraints.

Common examples include:

```text
string

number

bool

list(...)

set(...)

map(...)

object(...)

tuple(...)
```

Types make assumptions explicit.

Instead of accepting arbitrary input, define the structure expected by the module.

---

# 19. COMPLEX INPUTS

A module may accept structured data.

Example:

```hcl
variable "services" {
  type = map(object({
    port     = number
    replicas = number
  }))
}
```

Possible input:

```hcl
services = {
  api = {
    port     = 8080
    replicas = 3
  }

  worker = {
    port     = 9090
    replicas = 2
  }
}
```

Structured inputs can make interfaces expressive, but excessive complexity can make modules difficult to understand.

---

# 20. VARIABLE DEFAULTS

A default makes an input optional for callers.

Example:

```hcl
variable "environment" {
  type    = string
  default = "development"
}
```

Defaults should represent safe, meaningful behavior.

Do not create a production-impacting default merely to reduce typing.

---

# 21. VARIABLE VALIDATION

Inputs can be validated.

Example:

```hcl
variable "environment" {
  type = string

  validation {
    condition = contains(
      ["development", "staging", "production"],
      var.environment
    )

    error_message = "environment must be development, staging, or production."
  }
}
```

Validation moves certain mistakes earlier in the workflow.

Instead of allowing invalid input to propagate into provider operations, the configuration can reject it.

---

# 22. SENSITIVE VARIABLES

A variable can be marked sensitive:

```hcl
variable "api_token" {
  type      = string
  sensitive = true
}
```

This helps Terraform suppress the value from some normal CLI output.

However:

```text
sensitive = true
```

does **not** mean:

```text
The value cannot exist in Terraform state.
```

This distinction is operationally critical.

Sensitive values require careful state protection.

---

# 23. LOCALS

Local values let a module define reusable expressions.

Example:

```hcl
locals {
  name_prefix = "${var.environment}-${var.application_name}"
}
```

Then:

```hcl
resource "example_server" "app" {
  name = "${local.name_prefix}-server"
}
```

Locals are useful for:

- derived values
- naming
- repeated expressions
- normalized input
- common tags or labels

---

# 24. VARIABLES VERSUS LOCALS

Use a variable when:

```text
Caller should provide or control the value.
```

Use a local when:

```text
The module derives the value internally.
```

A useful design question is:

```text
Is this part of the module's public interface?
```

If yes, it may belong as an input.

If no, it may belong as an internal local.

---

# 25. OUTPUTS

Outputs expose values from a module.

Example:

```hcl
output "application_endpoint" {
  description = "Application endpoint."
  value       = example_load_balancer.app.endpoint
}
```

Outputs can:

- show useful values
- expose child-module information
- connect modules
- support automation

Outputs should represent meaningful interfaces, not expose every internal attribute automatically.

---

# 26. MODULE OUTPUTS AS CONTRACTS

Suppose a network module creates:

```text
Virtual Network

Private Subnets

Public Subnets
```

An application module may only require:

```text
network_id

private_subnet_ids
```

The network module can expose those values.

Conceptually:

```text
Network Module
↓
Outputs
↓
Root Module
↓
Inputs
↓
Application Module
```

This creates a deliberate interface.

---

# 27. EXPRESSIONS

Terraform expressions calculate values.

They may use:

- references
- operators
- conditional expressions
- functions
- collection transformations
- `for` expressions

Example:

```hcl
locals {
  full_name = "${var.environment}-${var.application_name}"
}
```

Expressions are powerful, but readability matters.

Infrastructure code should not become a puzzle.

---

# 28. CONDITIONAL EXPRESSIONS

A conditional expression follows the conceptual form:

```hcl
condition ? true_value : false_value
```

Example:

```hcl
locals {
  instance_size = var.environment == "production" ? "large" : "small"
}
```

Whether such a decision should actually be encoded this way depends on the infrastructure design.

The syntax is easy.

The engineering question is whether the abstraction is understandable and maintainable.

---

# 29. FOR EXPRESSIONS

A `for` expression transforms collection values.

Example:

```hcl
locals {
  service_names = [
    for name, service in var.services : name
  ]
}
```

They can be useful for preparing data structures consumed by resources or modules.

Avoid deeply nested transformations that make infrastructure intent difficult to inspect.

---

# 30. IMPLICIT DEPENDENCIES

Terraform infers dependencies from references.

Consider:

```hcl
resource "example_network" "main" {
  name = "production-network"
}

resource "example_server" "app" {
  network_id = example_network.main.id
}
```

Because the server references:

```text
example_network.main.id
```

Terraform can infer:

```text
Network
↓
Server
```

The reference creates a dependency relationship.

---

# 31. DEPENDENCY GRAPH

Terraform builds a dependency graph.

Conceptually:

```text
Network
├── Subnet A
│   └── App A
│
└── Subnet B
    └── App B

App A ──┐
        ├── Load Balancer
App B ──┘
```

Independent resources can often be processed in parallel.

Dependent resources must respect ordering constraints.

This is why references are more than convenient variable substitution.

They help describe infrastructure relationships.

---

# 32. EXPLICIT DEPENDENCIES

Terraform also provides:

```hcl
depends_on = [...]
```

for dependencies that cannot be adequately represented through normal references.

Example concept:

```hcl
resource "example_application" "app" {
  depends_on = [
    example_policy.application_access
  ]
}
```

Use explicit dependencies deliberately.

Do not add `depends_on` everywhere simply to force Terraform into a procedural order.

Prefer natural references when they accurately represent the dependency.

---

# 33. DEPENDENCY DOES NOT MEAN READINESS

An important production distinction:

```text
Resource Created
≠
Service Ready
```

Terraform may know that a database resource must exist before an application resource is created.

That does not automatically prove:

```text
Database schema initialized

Application credentials valid

Application dependency healthy

Service ready for traffic
```

Infrastructure dependency ordering and application readiness are different concerns.

---

# 34. COUNT

`count` allows multiple instances of a resource or module to be declared from one block.

Example:

```hcl
resource "example_server" "app" {
  count = 3

  name = "app-${count.index}"
}
```

Conceptually:

```text
example_server.app[0]

example_server.app[1]

example_server.app[2]
```

`count` is appropriate when instances are substantially similar and naturally represented by numeric indexes.

---

# 35. COUNT AND RESOURCE IDENTITY

Resource identity matters.

Suppose:

```hcl
variable "servers" {
  default = [
    "api",
    "worker",
    "metrics"
  ]
}
```

and indexes determine identity.

Conceptually:

```text
[0] api
[1] worker
[2] metrics
```

If the list changes:

```text
api
metrics
```

indexes may shift.

This can affect resource addresses and therefore planning behavior.

The issue is not that `count` is bad.

The issue is that numeric identity may be inappropriate when objects have meaningful stable identities.

---

# 36. FOR_EACH

`for_each` creates instances based on map keys or set members.

Example:

```hcl
resource "example_server" "app" {
  for_each = {
    api     = "small"
    worker  = "medium"
    metrics = "small"
  }

  name = each.key
  size = each.value
}
```

Conceptual addresses:

```text
example_server.app["api"]

example_server.app["worker"]

example_server.app["metrics"]
```

The keys become part of resource identity.

---

# 37. COUNT VERSUS FOR_EACH

Use `count` when instances are naturally represented by quantity or stable numeric indexing.

Use `for_each` when instances have meaningful distinct keys.

Think:

```text
Three identical workers
→ count may be appropriate
```

versus:

```text
api
worker
metrics
→ for_each may express identity better
```

Do not select between them merely based on which syntax looks shorter.

---

# 38. FOR_EACH KEYS ARE OPERATIONALLY IMPORTANT

Suppose:

```hcl
for_each = {
  api = {}
}
```

The resource address contains:

```text
["api"]
```

Changing the key to:

```text
["backend"]
```

changes the Terraform address.

Even if the underlying infrastructure concept is the same, Terraform must understand how the old and new addresses relate.

Refactoring keys therefore requires plan review and potentially state-aware migration techniques.

---

# 39. FOR_EACH VALUES MUST BE SUITABLE FOR PLANNING

Terraform must know the `for_each` instance keys before performing remote resource operations.

Do not design a `for_each` expression around values whose identities are unavailable until apply.

Resource identity must be planable.

---

# 40. COUNT AND FOR_EACH CANNOT BE COMBINED ON THE SAME BLOCK

A single resource or module block does not use both simultaneously.

Choose the instance model that correctly represents the resources.

---

# 41. DYNAMIC BLOCKS

Some provider resources contain repeatable nested blocks.

Terraform's `dynamic` construct can generate certain nested blocks programmatically.

Conceptually:

```hcl
dynamic "rule" {
  for_each = var.rules

  content {
    # nested arguments
  }
}
```

Dynamic blocks can reduce repetition.

They can also make configuration harder to read.

---

# 42. WHEN DYNAMIC BLOCKS ARE APPROPRIATE

Use dynamic generation when:

```text
The provider requires repeatable nested blocks
+
The input is genuinely variable
+
The abstraction remains understandable
```

Do not use dynamic blocks simply to make Terraform look sophisticated.

A few explicit blocks may be clearer than a deeply abstract transformation.

---

# 43. ABSTRACTION HAS A COST

Terraform code can become over-engineered.

Warning signs include:

```text
Many nested locals

Deeply nested maps

Several transformations before a resource

Dynamic blocks inside dynamic structures

Variables that expose provider internals directly

Modules requiring dozens of unrelated inputs
```

The objective is reusable infrastructure, not maximum abstraction.

---

# 44. MODULES

A module is a collection of Terraform configuration managed as a unit.

Every Terraform configuration has a root module.

A root module can call child modules.

Conceptually:

```text
Root Module
├── Network Module
├── Application Module
└── Observability Module
```

Modules help organize and reuse infrastructure.

---

# 45. MODULE PURPOSE

A useful module usually represents a coherent infrastructure capability.

Examples:

```text
Application Network

Application Compute

Load Balancing

Database

Monitoring Integration
```

A module should have a reason to exist beyond:

```text
We wanted fewer files.
```

Modules define boundaries.

---

# 46. MODULE BOUNDARIES

Good boundaries often align with:

```text
Ownership

Lifecycle

Responsibility

Reusability

Security Boundary

Rate of Change
```

Poor boundaries may create unnecessary coupling.

For example:

```text
One Giant Module
├── Network
├── Compute
├── Database
├── DNS
├── Monitoring
├── IAM
└── Unrelated Shared Services
```

may become difficult to change independently.

---

# 47. A MODULE IS NOT JUST A DIRECTORY

A directory becomes a meaningful module when it has a coherent interface.

Think:

```text
Inputs
↓
Module Implementation
↓
Outputs
```

The caller should not need to understand every internal resource to use the module safely.

---

# 48. MODULE INPUT INTERFACE

Suppose a network module needs:

```text
Network CIDR

Environment

Availability Zones
```

Its variables should expose those concepts clearly.

Avoid making callers configure every internal implementation detail unless that flexibility is genuinely required.

---

# 49. MODULE OUTPUT INTERFACE

A network module might expose:

```text
network_id

private_subnet_ids

public_subnet_ids
```

An application module can consume those values.

This forms:

```text
Network Module
↓
Output
↓
Root Module
↓
Input
↓
Application Module
```

Terraform can infer dependencies from these references.

---

# 50. ROOT MODULE RESPONSIBILITY

The root module commonly composes infrastructure.

Example:

```hcl
module "network" {
  source = "./modules/network"

  environment = var.environment
}

module "application" {
  source = "./modules/application"

  network_id = module.network.network_id
}
```

The root module becomes the composition layer.

It connects capabilities without requiring one child module to know everything about another.

---

# 51. MODULE DIRECTORY STRUCTURE

Example:

```text
terraform/
├── main.tf
├── variables.tf
├── outputs.tf
├── providers.tf
├── versions.tf
└── modules/
    ├── network/
    │   ├── main.tf
    │   ├── variables.tf
    │   └── outputs.tf
    │
    └── application/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
```

This is one maintainable pattern, not a Terraform requirement.

---

# 52. REUSABLE DOES NOT MEAN UNIVERSAL

A common mistake is attempting to create:

```text
One Module
That Can Build Every Possible Network
```

This often produces:

```text
40 variables

20 conditionals

Complex nested objects

Many optional behaviors

Difficult testing

Difficult upgrades
```

Prefer a module with a clear purpose.

Reuse should reduce maintenance burden, not create a configuration language inside Terraform.

---

# 53. MODULE COHESION

Resources inside a module should have a meaningful reason to change together.

Ask:

```text
Do these resources represent one capability?

Do they share lifecycle?

Do they share ownership?

Would callers normally need them together?
```

If not, reconsider the boundary.

---

# 54. MODULE COUPLING

A module becomes tightly coupled when it knows too much about unrelated systems.

For example, a generic network module should probably not need to understand:

```text
Application container image

Database password

CI/CD repository

Application release version
```

unless those concepts genuinely belong to its responsibility.

---

# 55. MODULE VERSIONING

Reusable modules change over time.

A remote module source should be consumed using an intentional versioning strategy supported by that source type.

The important production principle is:

```text
Reusable Module
↓
Versioned Change
↓
Consumer Reviews Upgrade
↓
Plan
↓
Apply
```

Avoid allowing critical infrastructure consumers to silently pick up unreviewed module changes.

---

# 56. MODULE VERSION IS PART OF INFRASTRUCTURE CHANGE

Suppose:

```text
Application Configuration
→ unchanged
```

but:

```text
Network Module
v2.3
→ v3.0
```

The resulting infrastructure plan may still change significantly.

Module upgrades require the same plan review discipline as direct HCL changes.

---

# 57. MODULE DOCUMENTATION

A reusable module should explain:

```text
Purpose

Requirements

Inputs

Outputs

Dependencies

Examples

Version Compatibility

Important Lifecycle Behavior

Security Assumptions
```

A module should not require reading every internal resource before it can be used safely.

---

# 58. TERRAFORM STATE

State is operationally critical.

Terraform uses state to associate resource instances in configuration with real remote objects.

Conceptually:

```text
Terraform Address
example_server.app
        ↓
Terraform State
        ↓
Remote Object Identifier
server-12345
        ↓
Real Infrastructure
```

Without this relationship, Terraform cannot reliably know which real object corresponds to a managed resource address.

---

# 59. STATE IS NOT JUST A CACHE

A dangerous misunderstanding is:

```text
State is temporary Terraform output.
```

It is not.

State contains the bindings Terraform uses to manage infrastructure.

Losing or corrupting state can create serious operational problems.

Treat state as infrastructure data.

---

# 60. LOCAL STATE

By default, the local backend stores state locally.

A learning repository may therefore contain:

```text
terraform.tfstate
```

after applying infrastructure.

Local state can be acceptable for isolated learning.

It becomes problematic for team infrastructure because:

```text
Engineer A has one copy

Engineer B has another copy

CI has another copy
```

Now there is no reliable shared coordination point.

---

# 61. NEVER COMMIT STATE AS A TEAM-SHARING STRATEGY

Do not solve collaboration by placing:

```text
terraform.tfstate
```

in Git.

State may contain sensitive information.

Git is also not a Terraform state-locking system.

A proper remote-state design should be used for collaborative infrastructure.

---

# 62. REMOTE STATE

Remote state stores Terraform state in a shared remote backend or Terraform platform.

Conceptually:

```text
Engineer A ──┐
             │
Engineer B ──┼── Terraform Backend ── State
             │
CI/CD ───────┘
```

This creates a shared state location.

Remote state does not eliminate every concurrency problem by itself.

The backend's locking and consistency behavior also matters.

---

# 63. BACKENDS

A backend determines how Terraform stores state and, depending on the backend, may provide state-locking capabilities.

Backend configuration is therefore an architectural choice.

Evaluate:

```text
Storage Durability

Access Control

Encryption

Locking Support

Recovery

Auditability

Operational Ownership
```

Do not choose a backend only because a tutorial used it.

---

# 64. REMOTE STATE SECURITY

State can contain sensitive infrastructure information.

Potential examples include:

```text
Resource identifiers

Network information

Configuration values

Provider-returned attributes

Potential secrets
```

Therefore protect remote state with:

```text
Strong access control

Encryption

Restricted administrative access

Backup/version recovery where supported

Auditability
```

Treat state access as privileged.

---

# 65. SENSITIVE OUTPUT DOES NOT SANITIZE STATE

Marking an output or variable as sensitive controls certain forms of Terraform display.

It does not guarantee that the underlying value is absent from state.

Therefore:

```text
Hidden CLI Output
≠
Secret Removed From State
```

This is why backend protection matters.

---

# 66. STATE LOCKING

When supported by the selected backend, state locking prevents concurrent operations that could otherwise attempt to write the same state simultaneously.

Conceptually:

```text
Engineer A
↓
Acquires Lock
↓
Terraform Operation
↓
Releases Lock
```

while:

```text
Engineer B
↓
Attempts Conflicting Operation
↓
Cannot Acquire Lock
↓
Waits or Fails According to Workflow
```

Locking protects shared state coordination.

---

# 67. NOT EVERY BACKEND HAS IDENTICAL LOCKING BEHAVIOR

Do not teach:

```text
Remote State
=
Automatic Locking Everywhere
```

Backend capabilities differ.

Verify the backend currently being used.

---

# 68. NEVER DISABLE LOCKING CASUALLY

Terraform provides options that can disable locking for certain operations.

Do not treat:

```text
-lock=false
```

as a routine solution to lock problems.

A lock may exist because another legitimate operation is modifying infrastructure.

Bypassing it can create concurrent writers.

---

# 69. STATE LOCK TROUBLESHOOTING

If Terraform reports that state is locked, use:

```text
Lock Error
↓
Read Lock Information
↓
Identify Operation
↓
Identify Owner
↓
Determine Whether Operation Is Still Running
↓
Check CI/CD
↓
Check Other Engineers
↓
Confirm Lock Is Stale
↓
Only Then Consider Recovery
```

Do not immediately force-unlock.

---

# 70. FORCE UNLOCK

Terraform provides:

```bash
terraform force-unlock <LOCK_ID>
```

for situations where automatic unlocking failed and a lock is known to be stale.

This is a recovery operation.

Before using it, establish:

```text
No active Terraform operation owns the lock.

The lock ID is correct.

The backend is healthy.

No CI/CD operation is running.

No engineer is applying infrastructure.
```

Unlocking active state can allow multiple writers.

---

# 71. STATE INSPECTION

Terraform provides state-oriented commands for inspecting managed resources.

For example:

```bash
terraform state list
```

This lists resource addresses currently tracked in state.

Example conceptual output:

```text
module.network.example_network.main
module.network.example_subnet.private["a"]
module.network.example_subnet.private["b"]
module.application.example_server.app["api"]
```

Actual addresses depend on the configuration.

---

# 72. INSPECT A RESOURCE IN STATE

A resource can be inspected with:

```bash
terraform state show '<RESOURCE_ADDRESS>'
```

Use quoting where the shell requires it, particularly for addresses containing index syntax.

This can help answer:

```text
Is the resource in state?

Which attributes are recorded?

Which resource address owns it?
```

---

# 73. STATE LIST IS NOT PROVIDER INVENTORY

If:

```bash
terraform state list
```

does not show a resource, that does not prove the resource does not exist in the cloud.

It means the current Terraform state does not track that resource address.

Always distinguish:

```text
Not in State
```

from:

```text
Does Not Exist
```

---

# 74. STATE INSPECTION IS NOT DIRECT EDITING

Terraform state is represented internally as structured data, but production engineers should not normally edit state files manually.

Use supported Terraform operations.

Direct state-file editing can damage Terraform's resource mappings.

---

# 75. STATE BACKUP AWARENESS

State is critical enough that recovery must be considered before an incident.

Understand:

```text
Where is state stored?

Does the backend provide version history?

Who can restore it?

What happens if state is accidentally modified?

How is recovery tested?

What is the recovery procedure?
```

Do not discover these answers after state loss.

---

# 76. STATE BACKUP IS NOT A SUBSTITUTE FOR CORRECT WORKFLOW

A backup can support recovery.

It does not make unsafe state manipulation acceptable.

Use:

```text
Safe Workflow
+
State Protection
+
Recovery Capability
```

rather than relying on backups to compensate for uncontrolled operations.

---

# 77. DRIFT

Drift occurs when real infrastructure differs from what Terraform configuration and its managed state relationship expect, often because infrastructure was changed outside the normal Terraform workflow.

Example:

```text
Terraform Configuration
instance_size = "small"
```

Someone manually changes the remote object:

```text
Real Infrastructure
instance_size = "large"
```

Now there is a difference.

---

# 78. HOW TERRAFORM DETECTS DRIFT

During normal planning behavior, Terraform communicates with providers to refresh its understanding of managed remote objects before determining proposed changes.

Conceptually:

```text
State
↓
Provider Read
↓
Observed Infrastructure
↓
State Refreshed for Planning
↓
Compare With Configuration
↓
Plan
```

The resulting plan may reveal that infrastructure has changed outside Terraform.

---

# 79. DRIFT IS NOT AUTOMATICALLY BAD

Not every difference has the same cause.

Drift may result from:

```text
Emergency Manual Change

Unauthorized Change

Provider-Side Behavior

External Automation

Operational Recovery

Configuration Error

Resource Replacement

Intentional Temporary Intervention
```

The engineering question is:

```text
Why did the difference occur,
and which state should become authoritative?
```

---

# 80. DO NOT REPAIR DRIFT BLINDLY

Suppose Terraform proposes:

```text
Change production setting back to old value.
```

Before applying:

```text
Who changed the real infrastructure?

Why?

Was it an emergency fix?

Is the configuration outdated?

Would reverting it recreate the incident?
```

The correct response may be:

```text
Update configuration to match intended reality
```

rather than:

```text
Apply Terraform immediately.
```

---

# 81. DRIFT RECONCILIATION

Use:

```text
Detect Difference
↓
Determine Cause
↓
Determine Intended State
↓
Update Configuration or Infrastructure Safely
↓
Plan
↓
Review
↓
Apply if Required
↓
Verify
```

Terraform should reconcile toward the intended state, not blindly toward whichever representation happens to be older.

---

# 82. REFRESH-ONLY AWARENESS

Terraform supports workflows that can update state to reflect remote changes without proposing configuration-driven infrastructure modifications.

These are advanced operational tools and must be used deliberately.

The key lesson is:

```text
Updating Terraform's knowledge
```

and:

```text
Changing Infrastructure
```

are not always the same operation.

Before using state-refresh workflows, understand exactly what discrepancy is being accepted.

---

# 83. TERRAFORM LIFECYCLE

A managed resource may experience:

```text
Create

Read

Update

Replace

Destroy
```

Not every configuration change produces an in-place update.

Provider schemas and remote APIs determine whether particular attributes can be changed without replacement.

---

# 84. CREATE

Terraform proposes creation when configuration contains a managed resource instance for which there is no corresponding managed object binding in state.

Conceptually:

```text
Configuration Exists

State Binding Missing

Real Managed Object Missing
↓
Create
```

But this model requires care when infrastructure already exists.

Existing unmanaged infrastructure may need import rather than duplicate creation.

---

# 85. UPDATE IN PLACE

Some arguments can be changed without replacing the remote resource.

Conceptually:

```text
Existing Resource
↓
Change Attribute
↓
Provider Update
↓
Same Logical Resource Continues
```

Always inspect the plan rather than assuming a change is in-place.

---

# 86. REPLACEMENT

Some changes require Terraform to replace a resource.

Conceptually:

```text
Old Resource
↓
Destroy / Replace Lifecycle
↓
New Resource
```

The exact ordering may depend on Terraform lifecycle behavior and provider capabilities.

Replacement is one of the most important things to identify during plan review.

---

# 87. WHY REPLACEMENT MATTERS

Replacement can affect:

```text
Availability

IP Addresses

DNS

Attached Storage

Data

Dependencies

Certificates

Identity

Cost

Downtime
```

A one-line HCL change can therefore represent a major production operation.

---

# 88. PLAN SYMBOLS ARE OPERATIONAL INFORMATION

Terraform plan output distinguishes operations such as:

```text
Create

Update

Destroy

Replace
```

Do not review a plan by reading only:

```text
Plan: X to add, Y to change, Z to destroy.
```

That summary is useful, but insufficient.

Read the resource-level changes.

---

# 89. REPLACEMENT REVIEW

Whenever replacement is planned, ask:

```text
Why is replacement required?

Which argument triggered it?

Does the resource contain stateful data?

What depends on its identity?

Will there be downtime?

Will the address change?

Will DNS change?

Will storage survive?

Is rollback possible?

Is create-before-destroy supported and safe?
```

Replacement deserves deliberate review.

---

# 90. DESTROY

Terraform may destroy a resource when the desired configuration no longer includes a managed resource instance or when replacement requires destruction.

Destruction is not automatically wrong.

But it is consequential.

Before approving destruction:

```text
Why is Terraform destroying this?

Is the resource intentionally removed?

Does it contain data?

Is it shared?

Is it recoverable?

Is the plan using the expected state?
```

---

# 91. LIFECYCLE META-ARGUMENT

Terraform provides lifecycle controls for certain resource behaviors.

Example:

```hcl
resource "example_server" "app" {
  lifecycle {
    create_before_destroy = true
  }
}
```

This can change replacement ordering.

But lifecycle configuration is not a universal safety switch.

Provider constraints and resource uniqueness requirements still matter.

---

# 92. CREATE_BEFORE_DESTROY

Default replacement behavior may involve destroying an existing object before creating its replacement when required.

`create_before_destroy` can instruct Terraform to attempt creation first.

Conceptually:

```text
Default Replacement

Old
↓
Destroy
↓
Create New
```

versus:

```text
Create Before Destroy

Old
+
Create New
↓
Move Dependents / Complete Replacement
↓
Destroy Old
```

Whether this succeeds depends on resource constraints.

---

# 93. CREATE_BEFORE_DESTROY CAN FAIL

Suppose the provider requires a globally unique resource name.

Terraform may attempt:

```text
Create new resource with same unique name
```

before deleting the old one.

The provider may reject it.

Therefore:

```text
create_before_destroy
≠
Guaranteed Zero Downtime
```

Lifecycle behavior must match provider reality.

---

# 94. PREVENT_DESTROY

Terraform supports:

```hcl
lifecycle {
  prevent_destroy = true
}
```

for protecting configured resources against certain Terraform plans that would destroy them.

This can be useful for critical resources.

But it is not a substitute for:

```text
Backups

Access Control

Plan Review

Recovery Procedures
```

Also understand its configuration-dependent behavior before relying on it.

---

# 95. IGNORE_CHANGES

Terraform can be instructed to ignore selected attribute changes.

This may be appropriate when another authorized system legitimately manages part of a resource.

Example conceptual use:

```text
Terraform manages resource
+
External controller manages one attribute
```

But misuse can hide important drift.

Before ignoring an attribute ask:

```text
Who owns this attribute?

Why is Terraform not authoritative?

Could ignoring it hide dangerous changes?

How will the external owner be monitored?
```

---

# 96. IGNORE_CHANGES IS NOT A DRIFT FIX

Bad pattern:

```text
Terraform keeps showing a change.
↓
Ignore it.
```

Correct reasoning:

```text
Why is the attribute changing?
↓
Who should own it?
↓
Is the difference expected?
↓
Then decide whether ignore_changes is appropriate.
```

Do not hide unexplained behavior.

---

# 97. DEPENDENCY ORDERING

Terraform determines operation order from the dependency graph.

Suppose:

```text
Network
↓
Subnet
↓
Application
↓
Load Balancer Target
```

Terraform uses relationships to determine safe ordering where possible.

Do not attempt to reproduce procedural deployment scripts by placing `depends_on` everywhere.

Describe real dependencies.

---

# 98. DESTROY ORDERING

Dependencies also matter during destruction.

If:

```text
Application
depends on
Subnet
```

Terraform must account for that relationship when removing infrastructure.

This is another reason accurate references matter.

---

# 99. REFACTORING TERRAFORM

Infrastructure code evolves.

A flat configuration may begin:

```text
main.tf
├── network
├── subnets
├── application
├── load balancer
└── storage
```

As ownership and complexity grow, it may be refactored:

```text
Root Module
├── Network Module
├── Application Module
└── Storage Module
```

But moving configuration into modules can change resource addresses.

That matters to state.

---

# 100. REFACTORING WITHOUT STATE AWARENESS

Suppose state currently tracks:

```text
example_network.main
```

After refactoring, the desired address becomes:

```text
module.network.example_network.main
```

Terraform sees different addresses unless the relationship is migrated appropriately.

A careless refactor can therefore produce:

```text
Destroy old address

Create new address
```

even though the engineer intended:

```text
Same infrastructure
New code organization
```

---

# 101. MOVED BLOCKS

Terraform provides configuration mechanisms for recording certain resource-address moves during refactoring.

Conceptually:

```hcl
moved {
  from = example_network.main
  to   = module.network.example_network.main
}
```

This communicates:

```text
Old Address
↓
Same Managed Object
↓
New Address
```

rather than requiring Terraform to interpret the new address as unrelated infrastructure.

Use current Terraform documentation to verify supported refactoring scenarios.

---

# 102. REFACTORING PRINCIPLE

Before moving resources between modules:

```text
Record Current Plan
↓
Record Current State Addresses
↓
Design New Module Boundary
↓
Map Old Addresses to New Addresses
↓
Use Supported Refactoring Mechanism
↓
Plan
↓
Expect No Unintended Infrastructure Replacement
```

A code refactor should not silently become an infrastructure replacement.

---

# 103. IMPORTING EXISTING INFRASTRUCTURE

Real environments often contain infrastructure created before Terraform.

Examples:

```text
Manual cloud resource

Legacy automation

Another IaC system

Emergency-created resource

Acquired environment
```

Terraform can import supported existing resources so they can become associated with Terraform resource addresses.

---

# 104. IMPORT IS A BINDING OPERATION

Conceptually:

```text
Existing Remote Object
resource-123
        +
Terraform Address
example_resource.app
        ↓
Import
        ↓
State Binding
```

Import does not magically design the correct Terraform configuration.

The configuration still needs to represent the intended managed resource.

---

# 105. CONFIGURATION-DRIVEN IMPORT

Modern Terraform supports `import` blocks.

Conceptual example:

```hcl
import {
  to = example_resource.app
  id = "resource-123"
}
```

The exact import identifier depends on the provider resource.

Never guess it.

Consult the provider documentation.

---

# 106. IMPORT REQUIRES A DESTINATION

The imported object needs a Terraform resource address that represents where it will be managed.

Conceptually:

```hcl
resource "example_resource" "app" {
  # intended managed configuration
}

import {
  to = example_resource.app
  id = "resource-123"
}
```

Terraform can then plan the import relationship.

---

# 107. CLI IMPORT

Terraform also provides the CLI import workflow:

```bash
terraform import <RESOURCE_ADDRESS> <IMPORT_ID>
```

Example structure only:

```bash
terraform import example_resource.app resource-123
```

The CLI import command associates the remote object with state.

It does not replace the need for appropriate configuration.

---

# 108. DO NOT IMPORT BLINDLY

Before import determine:

```text
Who owns the resource?

Should Terraform own it?

Which root module/state should own it?

What is the correct resource type?

What is the correct import identifier?

What configuration represents its intended state?

What will the first post-import plan propose?
```

Importing into the wrong state creates an ownership problem.

---

# 109. ONE OBJECT SHOULD HAVE ONE TERRAFORM OWNER

Avoid binding the same remote infrastructure object into multiple independent Terraform resource addresses or states.

Conceptually:

```text
State A
↓
Resource X

State B
↓
Same Resource X
```

creates competing management.

Each Terraform-managed object should have a clear owner.

---

# 110. POST-IMPORT PLAN

After import, run a plan.

The objective is not merely:

```text
Import succeeded.
```

The objective is:

```text
Terraform Configuration
+
Imported State
+
Real Infrastructure
↓
Expected Plan
```

If Terraform immediately proposes major changes or replacement, stop and investigate.

---

# 111. RECONCILING IMPORTED INFRASTRUCTURE

An existing resource may have many attributes.

Your configuration may initially describe only part of them.

The reconciliation process is:

```text
Inspect Existing Resource
↓
Understand Required Arguments
↓
Write Configuration
↓
Import
↓
Plan
↓
Compare Proposed Changes
↓
Adjust Configuration Where Appropriate
↓
Repeat
```

Do not blindly copy every provider-reported attribute into configuration.

Some may be:

- computed
- defaults
- provider-managed
- read-only
- unnecessary

---

# 112. GENERATED IMPORT CONFIGURATION

Terraform supports workflows that can generate configuration for import scenarios.

Generated configuration is a starting point.

It still requires engineering review.

Ask:

```text
Which arguments are required?

Which are computed?

Which defaults should remain implicit?

Which values should become variables?

Which values are sensitive?

Which module should own this resource?

What naming and tagging standards apply?
```

Generated code is not automatically publication-quality infrastructure code.

---

# 113. MIGRATION AWARENESS

Infrastructure may need to move:

```text
Manual
→ Terraform
```

or:

```text
Old Terraform State
→ New State Boundary
```

or:

```text
Flat Configuration
→ Modules
```

or:

```text
Old Module
→ New Module
```

Migration requires state-aware planning.

The objective is often:

```text
Change Management Model
Without Recreating Infrastructure
```

---

# 114. STATE MOVEMENT OPERATIONS

Terraform provides state commands that can change resource bindings.

These operations are powerful.

Treat them as production changes.

Before modifying state:

```text
Understand Current Address

Understand Desired Address

Protect State

Stop Concurrent Operations

Review Exact Command

Execute

Inspect State

Run Plan

Verify No Unexpected Infrastructure Change
```

Do not experiment with state manipulation against production.

---

# 115. TERRAFORM PLAN

`terraform plan` is one of the most important engineering controls in the workflow.

It answers:

```text
Given configuration,
current state,
provider observations,
and current inputs,

what does Terraform propose to do?
```

The plan is not paperwork.

It is the infrastructure change review.

---

# 116. PLAN REVIEW MODEL

Review:

```text
Intent
↓
Resource Address
↓
Action
↓
Changed Attributes
↓
Replacement?
↓
Dependencies
↓
Security Impact
↓
Availability Impact
↓
Data Impact
↓
Cost Impact
↓
Rollback / Recovery
```

Never approve a plan based only on the total resource count.

---

# 117. EXPECTED VERSUS UNEXPECTED CHANGE

Before running the plan, know approximately what you expect.

Example:

```text
Change Request:
Increase application capacity from 2 to 3 instances.
```

Expected plan:

```text
One additional application instance
```

Observed plan:

```text
1 create
4 replace
1 destroy
```

Stop.

The mismatch is evidence.

---

# 118. PLAN REVIEW QUESTION: WHY?

For every unexpected action ask:

```text
Why is Terraform proposing this?
```

Do not move to:

```text
How do I force Terraform to stop showing it?
```

until the reason is understood.

---

# 119. SAVED PLANS

Terraform can save a generated plan for later application.

Conceptually:

```bash
terraform plan -out=tfplan
```

then:

```bash
terraform apply tfplan
```

This can help ensure that the reviewed plan is the plan being applied within an appropriately controlled workflow.

The exact workflow must also account for state changes and collaboration between planning and applying.

---

# 120. PLAN FILES MAY CONTAIN SENSITIVE INFORMATION

Treat saved Terraform plans as potentially sensitive artifacts.

Do not casually:

```text
Commit them to Git

Upload them publicly

Attach them to public issues
```

Protect them according to the information they may contain.

---

# 121. APPLY IS A CHANGE OPERATION

`terraform apply` is not simply the next command after `terraform plan`.

It is authorization to execute infrastructure changes.

Before apply:

```text
Correct Repository?

Correct Branch?

Correct Workspace/State?

Correct Account?

Correct Environment?

Correct Plan?

Required Approval?

Acceptable Change Window?

Recovery Plan Ready?
```

Then apply through the approved workflow.

---

# 122. SUCCESSFUL APPLY IS NOT FINAL VERIFICATION

Terraform may report successful completion.

You still need to verify the intended operational outcome.

Use:

```text
Terraform Apply
↓
Provider Reports Success
↓
Inspect Resource State
↓
Test Service
↓
Check Monitoring
↓
Confirm Intended Outcome
```

Infrastructure creation and service correctness are different things.

---

# 123. AUTHENTICATION

Terraform providers need credentials or workload identity appropriate to the target platform.

Authentication should be provided using supported secure mechanisms.

Avoid embedding credentials directly in `.tf` files.

Bad pattern:

```hcl
provider "example" {
  access_key = "hard-coded-secret"
}
```

Credentials committed to source control can become a security incident.

---

# 124. AUTHENTICATION FAILURE

If Terraform cannot authenticate:

```text
Do not change resources.

Do not recreate state.

Do not reinitialize everything randomly.
```

Investigate:

```text
Which provider?

Which identity?

Which credential source?

Credential expired?

Wrong account?

Missing environment variable?

Workload identity unavailable?

Permission to call required API?
```

Separate authentication from authorization.

---

# 125. AUTHENTICATION VERSUS AUTHORIZATION

Authentication asks:

```text
Who is Terraform acting as?
```

Authorization asks:

```text
Can that identity perform this operation?
```

A provider may authenticate successfully but fail when Terraform attempts to create or read a resource.

That is not necessarily an authentication problem.

---

# 126. PROVIDER MISMATCH

Provider-related problems may involve:

```text
Wrong provider version

Unsupported argument

Changed schema

Wrong provider alias

Wrong region

Wrong subscription/account/project

Module expecting different provider configuration
```

Start with exact error evidence.

---

# 127. PROVIDER INITIALIZATION

When provider or module requirements change, Terraform initialization may need to update the working directory.

Common command:

```bash
terraform init
```

Provider upgrade workflows may intentionally use additional options, but upgrades should not be performed casually against production configurations.

Review the dependency lock file after provider selection changes.

---

# 128. MODULE INPUT PROBLEMS

Suppose Terraform reports a module input error.

Investigate:

```text
Required Input Missing?

Wrong Type?

Wrong Object Shape?

Null Where Value Required?

Validation Failure?

Caller Using Old Module Interface?

Module Version Changed?
```

Do not modify the module internally until confirming that the caller is using the interface correctly.

---

# 129. OUTPUT PROBLEMS

An output may fail because:

```text
Referenced Resource Changed

for_each Address Changed

Module Output Removed

Value Type Changed

Conditional Resource No Longer Exists
```

Trace:

```text
Output
↓
Expression
↓
Referenced Resource/Module
↓
Current Address
↓
Current Type
```

---

# 130. DEPENDENCY ISSUES

A dependency problem may appear when Terraform cannot determine values needed during planning.

Ask:

```text
Which value is unknown?

When does it become known?

Is the value being used to determine resource identity?

Is there a real dependency cycle?

Has configuration coupled resources incorrectly?
```

Do not automatically add `depends_on`.

---

# 131. CIRCULAR DEPENDENCIES

A cycle conceptually looks like:

```text
Resource A
depends on
Resource B

Resource B
depends on
Resource A
```

Terraform cannot establish a valid ordering.

The fix is architectural:

```text
Identify why both resources require each other
↓
Break unnecessary coupling
↓
Expose an intermediate value differently
↓
Restructure modules/resources
```

A dependency cycle is usually not solved by adding more dependencies.

---

# 132. UNEXPECTED REPLACEMENT

Scenario:

```text
Change:
One small configuration value

Plan:
Resource replacement
```

Do not apply immediately.

Investigate:

```text
Which attribute changed?

Does provider mark it replacement-required?

Did resource address change?

Did for_each key change?

Did count index shift?

Did module path change?

Did provider version change?

Did state mapping change?
```

Replacement may be valid, but it must be understood.

---

# 133. MISSING STATE

Scenario:

```text
Infrastructure exists.

Configuration exists.

Terraform plans to create everything.
```

Possible explanation:

```text
Terraform is using empty or wrong state.
```

Before applying:

```text
STOP
```

Investigate:

```text
Correct backend?

Correct state key/path?

Correct workspace if applicable?

Backend initialized correctly?

State migrated?

State accidentally deleted?

Wrong working directory?

Wrong environment?
```

Applying against missing state can attempt duplicate infrastructure creation.

---

# 134. MISSING STATE IS NOT FIXED BY IMPORTING EVERYTHING IMMEDIATELY

If expected state disappears, first determine whether it actually exists elsewhere.

Check:

```text
Backend configuration

State history/versioning

Environment

Workspace

Repository

Recent migration

Recent backend changes
```

Recovery from existing state is often preferable to rebuilding resource mappings manually.

---

# 135. STATE LOCK TROUBLESHOOTING LAB

In a disposable lab with a backend that supports locking, observe lock behavior during a state-writing operation.

Do not intentionally corrupt the backend.

Record:

```text
Lock Holder

Operation

Timestamp

State Identifier
```

# 171. STATE BOUNDARIES

Not every infrastructure resource in an organization should necessarily live in one Terraform state.

A huge shared state can increase:

```text

Lock Contention

Plan Size

Ownership Confusion

Change Coupling
```

But excessive state fragmentation can create:

```text
Complex Dependencies

Many Interfaces

Operational Overhead
```

State boundaries should reflect meaningful operational ownership and lifecycle.

# 172. MID-LEVEL STATE BOUNDARY THINKING

At Mid-Level, ask:

```text
Which team owns this infrastructure?

Which resources change together?

Which resources share lifecycle?

What is the blast radius of this state?

Who needs write access?

How frequently does it change?
```

Enterprise-wide state architecture belongs to later levels, but these questions should already influence application infrastructure.

# 173. CROSS-STATE DATA

Separate Terraform configurations may need information from each other.

For example:

```text
Network State
↓
Network ID
↓
Application Infrastructure
```

Terraform supports remote-state data access in some workflows.

However, direct state consumption can expose more state information than a consumer actually requires.

Prefer deliberate interfaces appropriate to the environment.

Possible patterns include publishing required values through:

```text

Service Discovery

Provider Data Sources

Platform APIs

Explicit Outputs
```

depending on the architecture.

---

# 174. STATE ACCESS IS A SECURITY DECISION

If an application infrastructure pipeline can read another team's complete state, ask:

```text
Does it need that level of access?

Does the state contain sensitive information?

Can the required value be exposed through a narrower interface?
```

Convenience should not silently expand trust boundaries.

---

# 175. TERRAFORM AND SECRETS

Terraform often needs to configure resources that reference secrets.

Minimize unnecessary secret material flowing through Terraform.

Ask:

```text
Does Terraform need the secret value?

Can Terraform reference a secret identifier instead?

Can the workload retrieve the secret at runtime?

Will the value enter state?

Who can read that state?
```

Infrastructure automation and secret distribution should be designed deliberately.

# 217. CHANGE OWNERSHIP

# 221. DO NOT USE DESTROY AS ROUTINE RECOVERY

Destroying and rebuilding a lab may be acceptable.

Destroying and rebuilding production whenever Terraform becomes confusing is not an engineering strategy.

Production systems may contain:

```text
Data

Stable identities

DNS dependencies

External integrations

Certificates

Audit requirements

Long-lived endpoints
```

Understand the problem first.

---

# 222. DO NOT CONFUSE RECREATABLE WITH DISPOSABLE

Infrastructure as code can make infrastructure reproducible.

That does not mean every resource can be destroyed without consequence.

For example:

```text
Terraform can recreate a database resource.
```

does not mean:

```text
Terraform can recreate the lost business data.
```

Configuration reproducibility and data recoverability are separate concerns.

---

# 223. DO NOT CONFUSE STATE WITH BACKUP OF THE SERVICE

Terraform state is not an application data backup.

It does not replace:

```text
Database backups

Object retention

Volume snapshots

Disaster recovery
```

State protects Terraform's infrastructure mapping.

Application data requires its own recovery strategy.

# 242. MID-LEVEL BOUNDARY

This Part establishes maintainable Terraform engineering for production application infrastructure.

It does not require organization-wide mastery of:

```text
Enterprise Terraform platform architecture

Large-scale policy-as-code governance

Organization-wide module registries

Complex multi-account provider architecture

Mass state migration programs

Enterprise-wide infrastructure platform design

Advanced custom provider development
```

Those belong primarily to later Senior and Architect scope.

At Mid-Level, the engineer should be able to own Terraform for a production service or bounded infrastructure domain safely.
