# PART 13: KUBERNETES STORAGE, STATE, AND APPLICATION CONFIGURATION

## Goal

Understand how stateful applications interact with Kubernetes storage, persistent data, configuration, and workload lifecycles.

The objective is to move beyond the assumption that:

```text
Pod has a volume
=
Data is safe
```

and develop a production-oriented model of state:

```text
Application
↓
Filesystem Path
↓
Volume Mount
↓
Volume
↓
PersistentVolumeClaim
↓
PersistentVolume
↓
StorageClass / Provisioner
↓
Storage System
↓
Durability / Backup / Recovery
```

By the end of this Part, you should be able to answer:

```text
Where is the application writing data?

Is that location persistent or ephemeral?

Which Kubernetes object represents the storage request?

Which storage resource satisfies that request?

Which storage system holds the actual bytes?

What happens when the container restarts?

What happens when the Pod is replaced?

What happens when the Pod moves to another node?

What happens when the workload object is deleted?

What happens when the PVC is deleted?

What happens when the PV is released?

What does the reclaim policy do?

Is the data backed up?

Can the backup actually be restored?

Does persistent data make the application highly available?

Which configuration belongs in a ConfigMap?

Which data belongs in a Secret?

What happens when configuration changes?

Where exactly is a failed mount or storage request failing?
```

The central principle is:

```text
Workload Lifecycle
≠
Storage Lifecycle
≠
Data Lifecycle
≠
Backup Lifecycle
```

These lifecycles interact, but they are not the same thing.

---

# 1. STATE CHANGES THE OPERATING MODEL

Stateless workloads are comparatively simple to replace.

If a stateless application Pod disappears:

```text
Old Pod
↓
Deleted / Failed
↓
Replacement Pod
↓
Application Continues
```

provided that the replacement can obtain everything it needs from external systems and configuration.

A stateful workload introduces another question:

```text
Where is the state?
```

For example:

```text
Database files

Uploaded files

Message data

Indexes

Application-generated content

Durable queues

Repository data

Persistent application metadata
```

If that state exists only inside a replaceable container filesystem, replacing the container can destroy the application state.

---

# 2. COMPUTE AND DATA HAVE DIFFERENT LIFECYCLES

Kubernetes is designed around replaceable Pods.

Persistent application data frequently needs to survive those replacements.

Therefore the architecture should distinguish:

```text
Compute Lifecycle
```

from:

```text
Data Lifecycle
```

A useful model is:

```text
Pod A
↓
Persistent Storage
↑
Pod B
```

Pod A can disappear.

Pod B can replace it.

The data can remain.

That is fundamentally different from:

```text
Pod A
↓
Local Container Filesystem
↓
Pod A Deleted
↓
Data Lost
```

---

# 3. THE FIRST QUESTION: WHERE ARE THE BYTES?

When troubleshooting a stateful application, begin with:

```text
Where are the bytes actually stored?
```

Do not begin with:

```text
Does the YAML contain a volume?
```

The YAML describes intended relationships.

The actual data might exist in:

```text
Container writable layer

emptyDir

Node-local storage

Persistent block storage

Network filesystem

Distributed storage system

Object storage

External database

Memory

Remote managed service
```

These have different persistence and failure characteristics.

---

# 4. CONTAINER FILESYSTEM

A container image provides filesystem layers used to start the container.

At runtime, the container normally also has a writable layer.

Conceptually:

```text
Container Image
├── Read-only Image Layers
└── Runtime Writable Layer
```

An application can write files into the writable layer.

For example:

```text
/app/cache.db

/tmp/output

/var/lib/application/data
```

may appear to work perfectly while the container is running.

That does not make those files durable application storage.

---

# 5. CONTAINER WRITABLE LAYER IS EPHEMERAL

Think:

```text
Container Writable Layer
→ belongs to that container instance
```

not:

```text
Container Writable Layer
→ permanent application disk
```

When Kubernetes replaces a container, the new container receives a new writable layer.

Therefore important application data should not depend on the old writable layer surviving.

---

# 6. CONTAINER RESTART VERSUS POD REPLACEMENT

This distinction matters.

A process inside a container can terminate and the kubelet can restart the container within the same Pod.

That is different from the Pod itself being deleted and replaced.

Storage behavior depends on the storage mechanism.

For example:

```text
Container Restart
↓
same Pod
↓
emptyDir can remain
```

but:

```text
Pod Deleted
↓
emptyDir deleted with Pod
```

and:

```text
Pod Deleted
↓
PersistentVolume-backed data may remain
```

depending on the PVC, PV, reclaim policy, storage system, and deletion operations.

---

# 7. EPHEMERAL STORAGE

Kubernetes nodes provide local ephemeral storage.

It can be consumed by things such as:

```text
Container writable layers

Container and Pod logs

Disk-backed emptyDir volumes
```

Ephemeral means:

```text
No long-term durability guarantee
```

It does not mean:

```text
Data disappears immediately after every process restart.
```

Lifecycle boundaries matter.

---

# 8. LOCAL EPHEMERAL STORAGE IS A NODE RESOURCE

Ephemeral storage consumes resources on the node.

Conceptually:

```text
Node
├── Container Images
├── Container Writable Layers
├── Pod Logs
├── emptyDir Data
└── Other Node Storage Use
```

If workloads consume excessive local storage, the node can experience storage pressure.

This can lead to Pod eviction.

Storage is therefore also a resource-management concern.

---

# 9. EPHEMERAL-STORAGE REQUESTS AND LIMITS

Containers can request and limit local ephemeral storage.

Example:

```yaml
resources:
  requests:
    ephemeral-storage: "256Mi"
  limits:
    ephemeral-storage: "1Gi"
```

This is conceptually different from:

```yaml
resources:
  requests:
    memory: "256Mi"
```

and different again from:

```yaml
resources:
  requests:
    storage: 10Gi
```

inside a PersistentVolumeClaim.

These represent different resources.

---

# 10. DO NOT CONFUSE EPHEMERAL-STORAGE WITH PVC CAPACITY

This:

```yaml
resources:
  limits:
    ephemeral-storage: "1Gi"
```

controls local ephemeral-storage consumption where Kubernetes can enforce and measure it.

This:

```yaml
resources:
  requests:
    storage: 10Gi
```

inside a PVC requests persistent storage capacity.

They are not interchangeable.

---

# 11. `EMPTYDIR`

An `emptyDir` volume provides storage associated with a Pod.

Example:

```yaml
volumes:
  - name: scratch
    emptyDir: {}
```

Container:

```yaml
volumeMounts:
  - name: scratch
    mountPath: /scratch
```

Conceptually:

```text
Pod Created
↓
emptyDir Created
↓
Containers Use It
↓
Pod Remains
↓
Data Remains
↓
Pod Removed
↓
emptyDir Data Removed
```

---

# 12. `EMPTYDIR` SURVIVES CONTAINER RESTARTS

This is an important distinction.

If a container crashes and is restarted within the same Pod:

```text
Container A
↓
Crash
↓
Container A Restarted
```

the Pod's `emptyDir` can remain.

Therefore:

```text
Container Restart
≠
Pod Deletion
```

But if the Pod is removed:

```text
Pod Removed
↓
emptyDir Removed
```

Do not use `emptyDir` for data that must survive the Pod lifecycle.

---

# 13. `EMPTYDIR` USE CASES

Appropriate uses can include:

```text
Scratch files

Temporary processing

Caches

Shared temporary files between containers in one Pod

Intermediate build or transformation data
```

provided that losing the data when the Pod disappears is acceptable.

---

# 14. MEMORY-BACKED `EMPTYDIR`

An `emptyDir` can use memory-backed storage:

```yaml
emptyDir:
  medium: Memory
```

This uses a tmpfs.

That can be useful for certain temporary workloads.

However, memory-backed `emptyDir` consumes memory rather than ordinary local disk-backed ephemeral storage.

It must therefore be considered in memory capacity and limit planning.

---

# 15. VOLUMES

A Kubernetes volume provides storage that containers in a Pod can mount.

The Pod defines the volume:

```yaml
volumes:
  - name: application-data
    ...
```

A container defines where it is mounted:

```yaml
volumeMounts:
  - name: application-data
    mountPath: /var/lib/application
```

Conceptually:

```text
Volume
↓
Volume Mount
↓
Container Filesystem Path
```

---

# 16. VOLUME AND VOLUMEMOUNT ARE DIFFERENT

This defines:

```text
What storage exists for the Pod?
```

```yaml
volumes:
```

This defines:

```text
Where does a particular container see it?
```

```yaml
volumeMounts:
```

A volume can exist in the Pod specification but be useless to an application if it is mounted at the wrong path.

---

# 17. MOUNT PATH CHANGES WHAT THE APPLICATION SEES

Suppose an image contains:

```text
/app/data/default.db
```

and a volume is mounted at:

```text
/app/data
```

The mounted filesystem becomes what the process sees at that path.

Files from the image that were previously visible beneath that mount path can be hidden by the mount.

This can create failures such as:

```text
Application starts without expected files

Default configuration disappears

Initialization scripts cannot find packaged data
```

Always understand the relationship between:

```text
Image Filesystem

Mount Path

Mounted Volume Contents
```

---

# 18. VOLUME DOES NOT AUTOMATICALLY MEAN PERSISTENT

This is one of the most important rules in the Part:

```text
Volume
≠
PersistentVolume
```

Kubernetes supports many volume types.

Some are ephemeral.

Some expose configuration.

Some expose Secrets.

Some reference persistent storage.

Therefore:

```text
"I mounted a volume"
```

does not answer:

```text
"Will the data survive Pod replacement?"
```

---

# 19. PERSISTENT STORAGE MODEL

The Kubernetes persistent-storage model separates the application request from the storage resource.

Conceptually:

```text
Pod
↓
PersistentVolumeClaim
↓
PersistentVolume
↓
Storage Implementation
```

With dynamic provisioning:

```text
Pod
↓
PVC
↓
StorageClass
↓
Provisioner
↓
PV
↓
Storage System
```

This separation is central to Kubernetes storage.

---

# 20. PERSISTENTVOLUME

A PersistentVolume, or PV, represents storage available to the cluster through Kubernetes.

Conceptually:

```text
PersistentVolume
→ Kubernetes representation of storage
```

The underlying storage might be backed by:

```text
Cloud block storage

Network filesystem

CSI-provided storage

Local storage

Enterprise storage platform
```

depending on the environment.

A PV is cluster-scoped rather than namespaced.

---

# 21. PERSISTENTVOLUMECLAIM

A PersistentVolumeClaim, or PVC, is a request for storage.

Conceptually:

```text
Application
↓
"I need storage with these requirements"
↓
PVC
```

A PVC can request characteristics such as:

```text
Capacity

Access mode

StorageClass

Volume mode
```

depending on the workload.

PVCs are namespaced.

---

# 22. THE CLAIM MODEL

Think:

```text
PVC
=
Storage Requirement
```

rather than:

```text
PVC
=
Physical Disk
```

The claim says:

```text
I need storage that satisfies these requirements.
```

Kubernetes and the storage integration attempt to satisfy that request.

---

# 23. POD TO PVC RELATIONSHIP

A Pod can reference a PVC:

```yaml
volumes:
  - name: data
    persistentVolumeClaim:
      claimName: veriqta-data
```

The container can mount it:

```yaml
volumeMounts:
  - name: data
    mountPath: /data
```

The path becomes:

```text
Application
↓
/data
↓
Volume Mount
↓
PVC
↓
PV
↓
Underlying Storage
```

---

# 24. PVC AND POD NAMESPACE

A Pod references a PVC in the same namespace.

For example:

```text
Namespace: production

Pod:
database-0

PVC:
database-data
```

works when both are in the required relationship.

A Pod does not simply mount an arbitrary PVC from another namespace by naming it.

Namespace must therefore be checked during troubleshooting.

---

# 25. PVC BINDING

A PVC progresses toward a storage binding.

Common states include:

```text
Pending
```

and:

```text
Bound
```

A bound PVC means Kubernetes has associated the claim with a PV.

It does not prove:

```text
Pod successfully mounted it.

Filesystem is healthy.

Application can write.

Data is backed up.

Application is available.
```

---

# 26. STORAGE BINDING MODEL

Conceptually:

```text
PVC
↓
Find / Provision Suitable Storage
↓
PV
↓
Bound
```

Matching and provisioning depend on properties such as:

```text
StorageClass

Capacity

Access modes

Volume mode

Topology

Provisioner behavior
```

---

# 27. STATIC PROVISIONING

With static provisioning, an administrator creates storage resources ahead of the application's claim.

Conceptually:

```text
Administrator
↓
Creates Storage
↓
Creates PV
↓
Application Creates PVC
↓
PVC Matches PV
```

This requires administrators to manage available storage explicitly.

---

# 28. DYNAMIC PROVISIONING

Dynamic provisioning allows storage to be created in response to a PVC.

Conceptually:

```text
PVC Created
↓
StorageClass Selected
↓
Provisioner Receives Request
↓
Storage Created
↓
PV Created
↓
PVC Bound
```

This removes the need to manually create a PV for every ordinary storage request.

It does not remove the need for storage governance.

---

# 29. STORAGECLASS

A StorageClass describes a class of storage offered by the cluster.

It can define or influence characteristics such as:

```text
Provisioner

Storage-system parameters

Reclaim policy

Volume binding mode

Expansion behavior
```

Exact parameters are provisioner-specific.

---

# 30. STORAGECLASS IS AN ABSTRACTION

A StorageClass named:

```text
fast
```

does not have a universal Kubernetes meaning.

Another organization might use:

```text
premium-rwo
```

or:

```text
general-purpose
```

or:

```text
encrypted-database
```

The cluster administrator defines what a class represents.

Therefore:

```text
StorageClass Name
≠
Universal Storage Capability
```

Inspect the actual StorageClass.

---

# 31. INSPECT STORAGECLASSES

Use:

```bash
kubectl get storageclass
```

or:

```bash
kubectl get sc
```

Inspect one:

```bash
kubectl describe storageclass <storage-class>
```

Ask:

```text
Which provisioner?

What reclaim policy?

What volume binding mode?

Can volumes be expanded?

Which parameters are configured?

Is this the intended class?
```

---

# 32. DEFAULT STORAGECLASS

A cluster can have a default StorageClass.

A PVC that does not explicitly request a class may use the default according to cluster configuration and API behavior.

Do not assume:

```text
No storageClassName
=
No StorageClass
```

Inspect the resulting PVC and cluster defaults.

For production workloads, be deliberate about storage requirements rather than depending blindly on whichever class happens to be default.

---

# 33. DYNAMIC PROVISIONING DOES NOT MEAN INFINITE STORAGE

A dynamic provisioner automates creation.

It does not eliminate:

```text
Cloud quotas

Storage-system capacity

Regional capacity

Account limits

CSI failures

Permissions

Topology constraints

Cost
```

A PVC can remain Pending even when dynamic provisioning is configured.

---

# 34. STORAGE REQUEST EXAMPLE

A simple PVC might resemble:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: veriqta-data
  namespace: veriqta-storage-lab
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: <lab-storage-class>
  resources:
    requests:
      storage: 1Gi
```

This requests:

```text
1 GiB

using the specified StorageClass

with ReadWriteOnce access semantics
```

Whether the environment can satisfy it depends on the storage implementation.

---

# 35. ACCESS MODES

Persistent storage can advertise access modes such as:

```text
ReadWriteOnce      RWO

ReadOnlyMany       ROX

ReadWriteMany      RWX

ReadWriteOncePod   RWOP
```

These describe mounting/access capabilities used by Kubernetes when matching and controlling storage.

They do not mean every storage driver supports every mode.

---

# 36. READWRITEONCE

`ReadWriteOnce` means the volume can be mounted read-write by a single node.

It does not necessarily mean:

```text
Only one Pod in the entire cluster can ever use it.
```

Multiple Pods on the same node can potentially access an RWO volume.

This distinction is important.

---

# 37. READWRITEONCEPOD

`ReadWriteOncePod` is designed for strict single-Pod read-write access across the cluster.

Conceptually:

```text
RWOP
↓
One Pod
↓
Read / Write
```

It is supported for compatible CSI storage.

For workloads where strict single-writer semantics matter, do not incorrectly assume `ReadWriteOnce` provides the same guarantee.

---

# 38. READONLYMANY

`ReadOnlyMany` represents storage that can be mounted read-only by multiple nodes where supported.

Conceptually:

```text
Node A Pod
↓ read

Shared Storage

Node B Pod
↓ read
```

Support depends on the storage implementation.

---

# 39. READWRITEMANY

`ReadWriteMany` represents storage that can be mounted read-write by multiple nodes where supported.

This is often associated with shared filesystem-style storage, but exact capabilities depend on the storage system and driver.

Do not assume every block-storage provider supports RWX.

---

# 40. ACCESS MODE DOES NOT REPLACE APPLICATION COORDINATION

Even if storage permits:

```text
Multiple Writers
```

the application must be designed to safely handle multiple writers.

Storage capability does not automatically provide:

```text
Database consistency

File locking correctness

Distributed coordination

Application-level concurrency control
```

Never choose RWX simply because multiple replicas need data without understanding whether the application supports that architecture.

---

# 41. ACCESS MODES ARE NOT ORDINARY FILE PERMISSIONS

Do not interpret:

```text
ReadWriteOnce
```

as equivalent to Linux:

```text
chmod
```

Access modes participate in Kubernetes storage selection and attachment/mount semantics.

They are not a replacement for:

```text
Filesystem permissions

UID/GID ownership

Application authorization
```

Those are separate layers.

---

# 42. VOLUME MODE

Persistent storage can be exposed as:

```text
Filesystem
```

or, for supported storage:

```text
Block
```

Most ordinary application examples use filesystem mode.

Raw block devices are appropriate only when the application and storage architecture explicitly require them.

Do not use raw block storage simply because it appears more "low level."

---

# 43. STORAGE TOPOLOGY

Storage can have physical or logical location constraints.

For example:

```text
Region

Availability zone

Node

Storage appliance location
```

A volume created in one topology may not be attachable to a Pod scheduled somewhere incompatible.

This creates an important relationship:

```text
Storage Placement
↔
Pod Scheduling
```

---

# 44. `VOLUMEBINDINGMODE`

StorageClass can define a volume binding mode.

A common concept is:

```text
Immediate
```

versus:

```text
WaitForFirstConsumer
```

With delayed binding, Kubernetes can consider Pod scheduling constraints before storage is provisioned or bound.

This is especially important for topology-constrained storage.

---

# 45. STORAGE AND SCHEDULING ARE CONNECTED

A Pod can be unschedulable because of storage.

For example:

```text
PVC requires volume in Zone A

Pod constraints require Node in Zone B

No compatible placement
```

The visible symptom may be:

```text
Pod Pending
```

but the root cause is a storage/scheduling relationship.

Always inspect events.

---

# 46. STORAGECLASS PROVISIONER

A StorageClass identifies a provisioner.

In modern environments this is commonly associated with a CSI storage driver.

Conceptually:

```text
PVC
↓
StorageClass
↓
Provisioner
↓
Storage API
↓
Actual Volume
```

Kubernetes does not create cloud disks or enterprise storage from nothing.

A storage integration performs that work.

---

# 47. CSI AWARENESS

Container Storage Interface, or CSI, provides a standard interface for integrating storage systems with container orchestration platforms such as Kubernetes.

At Mid-Level, understand the responsibilities:

```text
Kubernetes
→ declares storage intent

CSI components
→ integrate Kubernetes with storage system

Storage backend
→ stores actual data
```

Deep CSI driver architecture belongs later.

---

# 48. STORAGE CONTROL PLANE AND DATA PLANE

Storage has control-plane and data-path concerns.

Control-plane operations include:

```text
Provision

Attach

Detach

Mount

Resize

Snapshot requests where supported
```

Data-path operations include:

```text
Application reads

Application writes
```

A volume can provision successfully but still fail during attachment or mount.

Therefore:

```text
PVC Bound
≠
Storage Fully Usable
```

---

# 49. STORAGE LIFECYCLE MODEL

Use:

```text
Request
↓
Provision
↓
Bind
↓
Attach
↓
Mount
↓
Application Read / Write
↓
Unmount
↓
Detach
↓
Release / Reclaim
```

Not every storage implementation exposes each step identically.

But this model is extremely useful for troubleshooting.

---

# 50. RECLAIM POLICY

A PersistentVolume has a reclaim policy that influences what happens to the storage resource after its claim is released.

Important policies include:

```text
Retain
```

and:

```text
Delete
```

This decision has data-lifecycle consequences.

---

# 51. `DELETE` RECLAIM POLICY

With an appropriate dynamically provisioned volume and `Delete` reclaim policy, deleting the claim can ultimately cause the backing storage asset to be deleted.

Conceptually:

```text
PVC Deleted
↓
PV Released
↓
Reclaim Policy: Delete
↓
Backing Storage Deleted
```

Exact behavior depends on the storage implementation and lifecycle.

This is potentially destructive.

---

# 52. `RETAIN` RECLAIM POLICY

With `Retain`:

```text
PVC Deleted
↓
PV Released
↓
Underlying Storage Retained
```

The data is not automatically made ready for another workload.

Administrative recovery or reuse steps may still be required.

Therefore:

```text
Retain
≠
Automatic Recovery
```

---

# 53. STORAGECLASS RECLAIM POLICY

Dynamically provisioned PVs normally inherit the reclaim policy configured by the StorageClass.

If a StorageClass does not specify a reclaim policy, the default is `Delete`.

This is why engineers must inspect the actual StorageClass before assuming data will remain after PVC deletion.

---

# 54. PVC DELETION IS A DATA-RISK OPERATION

Before deleting a PVC, answer:

```text
Which PV is bound?

What is its reclaim policy?

Which storage asset backs it?

Is the data backed up?

Has restore been tested?

Is the application still using it?

Will deletion remove the underlying storage?

What recovery procedure exists?
```

Do not use PVC deletion as a casual troubleshooting technique.

---

# 55. PERSISTENTVOLUME PROTECTION

Kubernetes includes storage object protection mechanisms intended to reduce accidental deletion of storage objects while they are still in active use.

That protection should not be treated as a backup system.

It does not replace:

```text
Correct reclaim policy

Backups

Snapshots

Restore testing

Change review
```

---

# 56. STORAGE CAPACITY

PVC capacity is not just YAML metadata.

A storage request such as:

```text
10Gi
```

must be satisfiable by the selected storage system.

A claim can remain Pending because:

```text
No suitable PV exists

Provisioning failed

Requested size is unsupported

Quota is exceeded

Storage backend lacks capacity

StorageClass is wrong

Topology cannot be satisfied
```

---

# 57. VOLUME EXPANSION

Some storage implementations support expanding volumes.

A StorageClass can advertise:

```yaml
allowVolumeExpansion: true
```

where supported.

Expansion is storage-driver-dependent.

Kubernetes volume expansion is generally about growing storage, not shrinking it.

Never assume every PVC can be resized.

---

# 58. FILESYSTEM EXPANSION MAY BE PART OF THE OPERATION

Increasing the backing volume capacity and making the additional filesystem space usable are related but distinct concerns.

Depending on:

```text
Storage driver

Filesystem

Kubernetes version

Workload state
```

filesystem expansion behavior can differ.

Always verify:

```text
PVC requested capacity

PVC reported capacity

Filesystem-visible capacity
```

after expansion.

---

# 59. "DISK FULL" HAS MULTIPLE POSSIBLE MEANINGS

A workload can report:

```text
No space left on device
```

because of:

```text
Persistent volume capacity exhausted

Container writable layer exhausted

emptyDir exhausted

Node ephemeral storage pressure

Filesystem inode exhaustion

Storage quota

Application-specific quota
```

Do not immediately resize the PVC.

First identify which filesystem is full.

---

# 60. FILESYSTEM INSPECTION INSIDE THE CONTAINER

Useful checks may include:

```bash
df -h
```

and where appropriate:

```bash
df -i
```

and:

```bash
du -sh <path>
```

Interpret them carefully.

Ask:

```text
Which mount is full?

Is this the PVC mount?

Is this root filesystem?

Are inodes exhausted?

Does du explain df usage?

Is the application writing where expected?
```

---

# 61. WRONG WRITE PATH

One of the most dangerous storage mistakes is:

```text
PVC mounted successfully
```

but:

```text
Application writes somewhere else.
```

Example:

```text
PVC mounted:
/data
```

Application writes:

```text
/var/lib/app/data
```

The application appears healthy.

Data is created.

But the data is stored in the container writable layer.

After replacement:

```text
Data disappears.
```

Always verify the application's actual write path.

---

# 62. VERIFY PERSISTENCE WITH DATA, NOT YAML

Do not prove persistence by saying:

```text
PVC is Bound.
```

Prove it:

```text
Write Known Data
↓
Read Known Data
↓
Delete Pod
↓
Replacement Pod Starts
↓
Read Same Data
↓
Compare
```

This verifies the intended outcome.

---

# 63. PERSISTENCE TEST

Example concept:

```text
Create file:
/data/persistence-test.txt

Contents:
known unique value
```

Record the value.

Delete the Pod.

Allow the controller to recreate it.

Then inspect:

```text
/data/persistence-test.txt
```

Expected:

```text
Same value exists.
```

This proves more than simply inspecting the PVC status.

---

# 64. POD DELETION DOES NOT NECESSARILY DELETE PVC

If a Pod using an ordinary PVC is deleted:

```text
Pod Deleted
↓
PVC Remains
↓
PV Remains
↓
Replacement Pod Can Reuse Claim
```

assuming the controller configuration and storage relationships remain correct.

This is one of the main reasons persistent storage can outlive replaceable Pods.

---

# 65. WORKLOAD DELETION AND STORAGE DELETION ARE DIFFERENT

Deleting:

```text
Pod
```

is not the same as deleting:

```text
Deployment
```

which is not the same as deleting:

```text
StatefulSet
```

which is not the same as deleting:

```text
PVC
```

which is not the same as deleting:

```text
PV
```

which is not necessarily the same as deleting:

```text
Underlying Storage Asset
```

Know exactly which object is being changed.

---

# 66. STATEFULSET STORAGE CONCEPTS

StatefulSets are designed for workloads where Pods need stable identity and may need persistent storage associated with that identity.

Conceptually:

```text
database-0
↓
data-database-0

database-1
↓
data-database-1

database-2
↓
data-database-2
```

Each Pod can have storage associated with its stable ordinal identity.

---

# 67. STATEFULSET DOES NOT MAKE AN APPLICATION STATEFUL

A StatefulSet provides Kubernetes workload semantics useful for stateful applications.

It does not automatically create:

```text
Database replication

Data consistency

Leader election

Quorum

Backups

Disaster recovery

Application-level failover
```

The application still needs the correct stateful architecture.

---

# 68. STATEFULSET IDENTITY

A StatefulSet maintains stable Pod identity.

Pods commonly follow:

```text
<statefulset-name>-0

<statefulset-name>-1

<statefulset-name>-2
```

Unlike Deployment replicas, these identities are intentionally not interchangeable in the same way.

---

# 69. `VOLUMECLAIMTEMPLATES`

StatefulSets can use:

```yaml
volumeClaimTemplates:
```

to create PVCs for their Pods.

Conceptually:

```text
StatefulSet
↓
Pod 0
↓
PVC 0
```

```text
StatefulSet
↓
Pod 1
↓
PVC 1
```

Each Pod can therefore maintain its own persistent storage identity.

---

# 70. STATEFULSET STORAGE EXAMPLE

A simplified pattern:

```yaml
volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes:
        - ReadWriteOnce
      storageClassName: <storage-class>
      resources:
        requests:
          storage: 1Gi
```

Container:

```yaml
volumeMounts:
  - name: data
    mountPath: /var/lib/application
```

The StatefulSet controller creates claims associated with Pod identities.

---

# 71. STATEFULSET POD REPLACEMENT

Suppose:

```text
database-0
```

fails.

The replacement remains:

```text
database-0
```

and can be associated with its existing persistent claim.

Conceptually:

```text
Old database-0
↓
Fails
↓
Replacement database-0
↓
Existing PVC
↓
Existing Data
```

This stable relationship is one of the reasons StatefulSets are useful for stateful workloads.

---

# 72. STATEFULSET PVC RETENTION

StatefulSet PVC lifecycle deserves explicit attention.

Current Kubernetes supports a PersistentVolumeClaim retention policy for StatefulSets.

The policy can control PVC deletion behavior when:

```text
StatefulSet is deleted
```

or:

```text
StatefulSet is scaled down
```

The default retention behavior is `Retain`.

Do not assume StatefulSet PVCs are always deleted or always retained without inspecting the configuration and cluster behavior.

---

# 73. RETENTION POLICY AND RECLAIM POLICY ARE DIFFERENT

These two concepts operate at different lifecycle points.

StatefulSet PVC retention asks:

```text
Should the StatefulSet-associated PVC be deleted?
```

PV reclaim policy asks:

```text
After the claim releases the PV, what should happen to the backing storage?
```

Therefore:

```text
StatefulSet PVC Retention
≠
PV Reclaim Policy
```

Both can affect eventual data survival.

---

# 74. SCALE-DOWN IS A DATA-LIFECYCLE EVENT

Suppose a StatefulSet has:

```text
database-0
database-1
database-2
```

and is scaled from:

```text
3
```

to:

```text
1
```

Pods 2 and 1 are removed according to StatefulSet ordering.

What happens to their PVCs depends on the StatefulSet PVC retention configuration.

Never scale down a stateful workload without understanding:

```text
Application replication

Data placement

PVC retention

Recovery requirements
```

---

# 75. STATEFULSET DOES NOT EQUAL HIGH AVAILABILITY

This deserves its own rule:

```text
StatefulSet
≠
Highly Available Application
```

Three database Pods do not automatically mean:

```text
Three safe database replicas.
```

The database must know how to replicate, coordinate, recover, and maintain consistency.

Kubernetes cannot invent application-level replication semantics.

---

# 76. PERSISTENT STORAGE DOES NOT EQUAL HIGH AVAILABILITY

Another critical distinction:

```text
Persistent
≠
Highly Available
```

A single persistent volume may preserve data while still becoming an availability dependency.

For example:

```text
Application Pod
↓
Single Persistent Volume
↓
Storage Failure
↓
Application Unavailable
```

The data might persist and the service might still be down.

---

# 77. AVAILABILITY AND DURABILITY ARE DIFFERENT

Use:

```text
Availability
=
Can the application serve now?
```

and:

```text
Durability
=
Will the data survive expected failures?
```

An application can be:

```text
Available
but poorly durable
```

or:

```text
Unavailable
but data remains safe
```

These are different engineering properties.

---

# 78. BACKUP IS ANOTHER PROPERTY

Add a third dimension:

```text
Persistence

Availability

Recoverability
```

Persistent storage provides a mechanism for data to survive certain workload lifecycle events.

It does not automatically provide a recoverable historical copy.

That requires backup or another recovery mechanism.

---

# 79. BACKUP IS NOT THE SAME AS PERSISTENT STORAGE

A persistent volume contains live application data.

A backup provides recoverable data from another recovery point or protected copy.

If an application corrupts:

```text
/data/database
```

the corruption can be written successfully to persistent storage.

Persistence faithfully preserves the bad write.

Therefore:

```text
Persistent Volume
≠
Backup
```

---

# 80. REPLICATION IS NOT BACKUP

Suppose a database replicates:

```text
Primary
↓
Replica A

Primary
↓
Replica B
```

If the application accidentally deletes critical data and the deletion replicates:

```text
Primary
→ deleted

Replica A
→ deleted

Replica B
→ deleted
```

replication did exactly what it was designed to do.

It did not provide historical recovery.

Therefore:

```text
Replication
≠
Backup
```

---

# 81. SNAPSHOT IS NOT AUTOMATICALLY A COMPLETE BACKUP STRATEGY

Snapshots can be valuable recovery mechanisms where supported.

But a snapshot alone does not answer:

```text
Was application state consistent?

Where is the snapshot stored?

How long is it retained?

Can it survive storage-account failure?

Can it survive region failure?

Who can delete it?

Can it actually be restored?

What is the recovery time?
```

Treat snapshots as part of a recovery architecture, not as a magic checkbox.

---

# 82. APPLICATION-CONSISTENT BACKUPS

For stateful applications, filesystem-level copying may not be enough.

Databases and other stateful systems can have:

```text
In-memory state

Write-ahead logs

Journals

Transactions in progress

Multiple related files
```

A backup must respect application consistency requirements.

The exact backup method is application-specific.

---

# 83. RPO AND RTO AWARENESS

Two useful recovery concepts are:

```text
RPO
Recovery Point Objective
```

and:

```text
RTO
Recovery Time Objective
```

RPO asks approximately:

```text
How much recent data loss can the system tolerate?
```

RTO asks approximately:

```text
How long can recovery take?
```

Storage architecture should eventually be evaluated against both.

Detailed disaster recovery engineering comes later, but these concepts should already influence storage decisions.

---

# 84. CONFIGURATION IS ALSO APPLICATION STATE

Not all application state is business data.

Applications also depend on configuration.

Examples:

```text
Environment name

Feature settings

Backend addresses

Logging configuration

Timeouts

Port configuration

Credentials

Certificates

API tokens
```

Kubernetes provides configuration mechanisms including:

```text
ConfigMap

Secret
```

---

# 85. CONFIGMAP

A ConfigMap stores non-confidential configuration data.

Conceptually:

```text
Application Image
+
ConfigMap
=
Environment-Specific Runtime Configuration
```

This allows the same image to be used in different environments without rebuilding it for every configuration change.

---

# 86. CONFIGURATION SHOULD BE SEPARATED FROM IMAGE CONTENT

Prefer:

```text
Same Application Image
+
Development Configuration
```

```text
Same Application Image
+
Staging Configuration
```

```text
Same Application Image
+
Production Configuration
```

rather than:

```text
Development Image

Staging Image

Production Image
```

when the only difference is runtime configuration.

This improves artifact consistency across environments.

---

# 87. CONFIGMAP EXAMPLE

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: veriqta-config
  namespace: veriqta-storage-lab
data:
  APP_ENV: "lab"
  LOG_LEVEL: "info"
  application.conf: |
    feature_enabled=true
    request_timeout_seconds=10
```

A ConfigMap can expose individual values or file-like content.

---

# 88. CONFIGMAP AS ENVIRONMENT VARIABLES

A container can reference values:

```yaml
env:
  - name: APP_ENV
    valueFrom:
      configMapKeyRef:
        name: veriqta-config
        key: APP_ENV
```

Or multiple entries can be imported with:

```yaml
envFrom:
  - configMapRef:
      name: veriqta-config
```

Use the method that creates the clearest application contract.

---

# 89. CONFIGMAP AS FILES

A ConfigMap can be mounted as files.

Conceptually:

```text
ConfigMap
↓
Volume
↓
/etc/veriqta/application.conf
```

This is useful for applications that expect configuration files rather than environment variables.

---

# 90. ENVIRONMENT VARIABLE CONFIGURATION DOES NOT LIVE-UPDATE THE PROCESS

If a ConfigMap value is consumed as an environment variable, changing the ConfigMap does not retroactively change the environment of an already-running process.

The Pod generally needs replacement or another application-specific reload mechanism.

Therefore:

```text
ConfigMap Updated
≠
Running Process Automatically Reconfigured
```

---

# 91. MOUNTED CONFIGMAP UPDATES

ConfigMap data mounted through a volume can be updated in the mounted representation after Kubernetes propagates the change.

However:

```text
Mounted File Updated
≠
Application Reloaded Configuration
```

The application must detect, watch, poll, or reload the file appropriately.

Propagation is not instantaneous.

---

# 92. `SUBPATH` CONFIGURATION CAVEAT

When a ConfigMap or Secret volume is mounted using `subPath`, the mounted file does not receive the ordinary automatic update behavior associated with the full projected volume.

This matters when designing runtime configuration reload.

Do not assume every ConfigMap-mounted file updates identically.

---

# 93. IMMUTABLE CONFIGURATION

ConfigMaps and Secrets can be marked immutable.

This can prevent accidental mutation of configuration objects that should not change in place.

An immutable object must generally be replaced rather than edited to change its data.

This can support safer versioned configuration patterns.

---

# 94. SECRET

A Secret stores confidential data such as:

```text
Passwords

Tokens

Keys

Credentials
```

Conceptually:

```text
ConfigMap
→ non-confidential configuration
```

```text
Secret
→ confidential configuration
```

Do not place sensitive credentials in a ConfigMap simply because it is convenient.

---

# 95. BASE64 IS NOT ENCRYPTION

Kubernetes Secret manifests commonly represent values using base64 encoding.

This is not encryption.

Therefore:

```text
Base64
≠
Confidentiality
```

Anyone who can decode base64 can recover the value.

Do not commit real Secret manifests containing sensitive values to a public repository.

---

# 96. SECRET STORAGE SECURITY

Kubernetes Secrets require security controls around:

```text
API access

RBAC

etcd encryption at rest

Namespace access

Pod creation permissions

Logging

Git repositories

CI/CD output
```

Secrets are sensitive objects.

Treat Secret read permissions as privileged access.

---

# 97. POD CREATION CAN IMPLY SECRET ACCESS

If a user can create a Pod in a namespace and cause that Pod to consume a Secret, that capability can effectively provide access to Secret data.

Therefore Secret security is not only about:

```text
Can the user run kubectl get secret?
```

It is also about:

```text
What workloads can the user create or modify?
```

This is an important authorization relationship.

---

# 98. SECRET AS ENVIRONMENT VARIABLE

A Secret can provide environment variables.

Example pattern:

```yaml
env:
  - name: DATABASE_PASSWORD
    valueFrom:
      secretKeyRef:
        name: database-credentials
        key: password
```

But environment variables have operational implications.

Applications, debugging tools, process inspection, crash reports, or accidental logging can expose values if handled poorly.

---

# 99. SECRET AS MOUNTED FILE

Secrets can also be mounted as files.

Conceptually:

```text
Secret
↓
Volume
↓
/run/secrets/...
```

Whether environment variables or mounted files are preferable depends on:

```text
Application behavior

Rotation requirements

Security architecture

Operational tooling
```

Do not declare one universally superior without context.

---

# 100. APPLICATION MUST PROTECT SECRET AFTER READING IT

Kubernetes can deliver a Secret to an authorized Pod.

After that, the application must avoid:

```text
Logging it

Returning it in API responses

Writing it to insecure files

Sending it to untrusted systems

Including it in telemetry
```

Secret handling remains an application responsibility.

---

# 101. CONFIGURATION ERROR VERSUS STORAGE ERROR

Suppose a Pod fails because:

```text
Configuration file references wrong database path.
```

That is not necessarily a storage provisioning failure.

Separate:

```text
Can storage be mounted?
```

from:

```text
Does the application configuration point to the correct mounted path?
```

This distinction will appear repeatedly in production incidents.

---

# 102. APPLICATION CONFIGURATION PATH

A stateful application may depend on:

```text
ConfigMap
↓
Application Configuration
↓
Data Directory Setting
↓
Mounted PVC
```

For example:

```text
DATA_DIR=/data
```

must agree with:

```text
volumeMount.mountPath=/data
```

A mismatch can cause the application to write outside persistent storage.

---

# 103. CONFIGURATION CAN DETERMINE DATA SAFETY

Consider:

```text
PVC mounted at:
/data
```

but configuration says:

```text
DATA_DIR=/tmp/data
```

The application may work.

Tests may pass.

But data may be ephemeral.

Therefore configuration review is part of storage review.

---

# 104. STORAGE PERMISSIONS

A mounted filesystem can exist while the application cannot write to it.

Symptom:

```text
Permission denied
```

Possible causes include:

```text
Filesystem ownership

UID/GID mismatch

Security context

fsGroup behavior

Storage-driver behavior

Read-only mount

Application user
```

Do not change permissions to `777` as a default troubleshooting response.

Identify the required ownership model.

---

# 105. SECURITY CONTEXT AND STORAGE

A container might run as:

```text
UID 10001
```

while mounted data is owned by:

```text
root:root
```

with permissions that prevent writes.

The application can then fail despite:

```text
PVC
Bound

Volume
Mounted
```

Storage troubleshooting must include filesystem authorization.

---

# 106. `FSGROUP` AWARENESS

Pod security context can include:

```yaml
securityContext:
  fsGroup: 2000
```

where appropriate.

This can influence ownership/access behavior for supported volume types.

Exact behavior can depend on the storage driver and filesystem.

Do not add `fsGroup` blindly.

First understand:

```text
Application UID

Application GID

Filesystem ownership

Required write permissions

Storage implementation
```

---

# 107. READ-ONLY MOUNTS

A container can mount a volume read-only where appropriate.

Example concept:

```yaml
volumeMounts:
  - name: configuration
    mountPath: /etc/application
    readOnly: true
```

Read-only mounts can reduce accidental modification of configuration or shared data.

But they will break applications that legitimately need writes.

Design the mount according to application behavior.

---

# 108. FAILED MOUNT

A Pod can remain unable to start because Kubernetes cannot mount required storage.

The Pod may show:

```text
Pending
```

or:

```text
ContainerCreating
```

for an extended period.

Inspect:

```bash
kubectl describe pod <pod-name> -n <namespace>
```

Events are critical.

---

# 109. STORAGE EVENTS

Events can reveal failures involving:

```text
Provisioning

Attachment

Mounting

Missing claims

Topology

Permissions

Driver failures
```

Use:

```bash
kubectl get events -n <namespace> --sort-by=.lastTimestamp
```

where useful.

Remember that events are retained for a limited period determined by cluster configuration.

Capture important evidence during incidents.

---

# 110. TROUBLESHOOTING MODEL FOR STORAGE

Use:

```text
Application
↓
Mount Path
↓
Pod Volume
↓
PVC
↓
PV
↓
StorageClass
↓
Provisioner / CSI
↓
Storage Backend
```

Move layer by layer.

Do not jump directly to the storage provider when the PVC name is wrong.

---

# 111. FAILURE LAYER: APPLICATION

Symptoms:

```text
Application cannot find data

Application writes to wrong directory

Application reports permission denied
```

Investigate:

```text
Configured data path

Mounted path

Runtime UID/GID

Filesystem permissions

Application logs
```

---

# 112. FAILURE LAYER: VOLUME MOUNT

Symptoms:

```text
Expected path missing

Wrong filesystem mounted

Configuration hidden

Read-only unexpectedly
```

Investigate:

```text
volumeMounts

mountPath

subPath

readOnly

Volume name
```

---

# 113. FAILURE LAYER: PVC REFERENCE

Symptom:

```text
Pod references nonexistent claim
```

Inspect:

```bash
kubectl get pvc -n <namespace>
```

Compare:

```text
Pod claimName
↔
PVC metadata.name
```

Also verify namespace.

---

# 114. FAILURE LAYER: PVC PENDING

```bash
kubectl describe pvc <claim> -n <namespace>
```

```text
Which StorageClass?

Which capacity?

Which access mode?

Which volume mode?

Which events?

Is WaitForFirstConsumer involved?
```

---

# 115. FAILURE LAYER: PV

Inspect:

```bash
kubectl get pv
```

Then:

```bash
kubectl describe pv <pv-name>
```

Ask:

```text
Status?

Capacity?

Access modes?

StorageClass?

Reclaim policy?

Claim reference?

Volume mode?

Node affinity or topology?
```

---

# 116. FAILURE LAYER: STORAGECLASS

Inspect:

```bash
kubectl get storageclass <class> -o yaml
```

Ask:

```text
Correct provisioner?

Correct class?

Reclaim policy?

Binding mode?

Expansion allowed?

Provider-specific parameters correct?
```

---

# 117. FAILURE LAYER: STORAGE DRIVER

If:

```text
PVC configuration
✓

StorageClass
✓

Scheduling requirements
✓
```

but provisioning, attachment, or mounting still fails, storage-driver evidence becomes relevant.

Depending on permissions and cluster design, investigate:

```text
CSI controller components

CSI node components

Storage-provider events

Driver logs

Cloud or storage API errors
```

Do not begin here unless higher layers have been checked.

---

# 118. FAILURE LAYER: BACKEND STORAGE

Possible problems include:

```text
Quota exceeded

Storage system unavailable

Volume missing

Attachment limit reached

Zone mismatch

Account permissions

Provider API failure

Backend capacity exhausted
```

At this layer, Kubernetes may only be surfacing an external storage-system failure.

---

# 119. FAILURE: INCORRECT CLAIM

Suppose the Pod specifies:

```yaml
claimName: veriqta-data
```

but the PVC is:

```text
veriqta-app-data
```

The storage system may be completely healthy.

The failure is the Kubernetes object relationship.

Correct diagnosis:

```text
Pod references nonexistent PVC.
```

Not:

```text
Cloud storage is broken.
```

---

# 120. FAILURE: WRONG STORAGECLASS

Suppose:

```text
PVC
→ requests fast-storage
```

but the cluster provides:

```text
standard
```

and:

```text
encrypted
```

The claim can remain unsatisfied.

Inspect the exact StorageClass name and provisioning events.

Do not invent class names from another cluster or tutorial.

---

# 121. FAILURE: UNSATISFIABLE CAPACITY

Suppose a PVC requests:

```text
100Ti
```

in a lab environment incapable of satisfying it.

The PVC may remain Pending or provisioning may fail.

This is a capacity request failure, not an application problem.

---

# 122. FAILURE: ACCESS MODE MISMATCH

Suppose the workload requests:

```text
ReadWriteMany
```

but the selected storage system does not support RWX.

The claim may not be satisfiable as intended.

Do not "fix" the manifest by changing to RWO until you understand why multiple-writer access was requested.

The architecture may need to change.

---

# 123. FAILURE: VOLUME ATTACHMENT

A PV can be bound while the Pod cannot use it.

Possible causes include:

```text
Volume already attached incompatibly

Node/zone mismatch

Provider attachment failure

Attachment limit

CSI issue
```

This proves why:

```text
PVC Bound
≠
Pod Storage Ready
```

---

# 124. FAILURE: MOUNT

Attachment and mount are separate conceptual stages.

A volume can reach the node but fail to mount because of:

```text
Filesystem problems

Mount options

Driver errors

Permissions

Missing device

Corruption

Unsupported filesystem
```

Read events carefully.

---

# 125. FAILURE: FILESYSTEM FULL

Application symptom:

```text
No space left on device
```

Workflow:

```text
Identify exact filesystem
↓
Confirm usage
↓
Confirm PVC capacity if relevant
↓
Identify growth source
↓
Check expansion capability
↓
Choose mitigation
↓
Verify
↓
Prevent recurrence
```

Do not immediately delete application data.

---

# 126. FAILURE: INODE EXHAUSTION

A filesystem can have free byte capacity while running out of available inodes.

Symptoms can resemble:

```text
No space left on device
```

despite:

```text
df -h
```

showing available capacity.

Check:

```bash
df -i
```

where applicable.

This is especially relevant for workloads creating very large numbers of small files.

---

# 127. FAILURE: PERMISSION DENIED

Workflow:

```text
Identify application UID/GID
↓
Inspect mount permissions
↓
Inspect securityContext
↓
Inspect readOnly settings
↓
Understand storage-driver ownership behavior
↓
Correct least-privilege access
↓
Verify
```

Avoid:

```bash
chmod -R 777
```

as a production solution.

---

# 128. FAILURE: DATA DISAPPEARS AFTER POD REPLACEMENT

Investigate:

```text
Where was application writing?

Was a volume mounted there?

What type of volume?

Was it emptyDir?

Was it container writable layer?

Was PVC actually mounted?

Was replacement using same claim?
```

The root cause is often:

```text
Data never reached persistent storage.
```

---

# 129. FAILURE: WRONG DATA AFTER REPLACEMENT

Suppose persistence works, but the replacement Pod sees unexpected old or incorrect data.

Investigate:

```text
Which PVC is mounted?

Which PV is bound?

Was wrong claim referenced?

Did StatefulSet ordinal change?

Was old retained storage reused?

Was initialization logic run against existing data?
```

Persistent storage can preserve mistakes as effectively as correct data.

---

# 130. FAILURE: STALE CONFIGURATION

Symptoms:

```text
ConfigMap changed

Application still uses old value
```

Investigate:

```text
Environment variable or volume?

If environment variable:
Was Pod recreated?

If volume:
Has projected file updated?

Does application reload configuration?

Was subPath used?
```

Do not assume Kubernetes will restart the application automatically for every configuration change.

---

# 131. FAILURE: SECRET UPDATED BUT APPLICATION STILL FAILS

Investigate:

```text
How is Secret consumed?

Environment variable?

Mounted file?

External secret integration?

Does application reload?

Does Pod need replacement?

Is correct Secret referenced?

Is correct key referenced?
```

Also verify that troubleshooting output does not expose the secret value.

# 212. WHAT THIS PART SHOULD CHANGE IN YOUR THINKING

Before this Part, you might think:

```text

```

After this Part, think:

```text
My application writes to a specific filesystem path.

That path may or may not be a volume mount.

That volume may or may not be persistent.

If persistent, a PVC expresses the application's storage request.

A PV represents the storage bound to that request.

A StorageClass and provisioner may determine how storage is created.

The storage backend holds the actual data.

The workload lifecycle is separate from the storage lifecycle.

The storage lifecycle is separate from backup and recovery.

Every layer must be understood and verified.
```

```text
ReadWriteOncePod
```

as the stricter single-Pod access mode for supported CSI storage.
