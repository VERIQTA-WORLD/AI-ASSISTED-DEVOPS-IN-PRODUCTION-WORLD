# PART 10: PRODUCTION CONTAINER ENGINEERING

## Goal

Understand container images and runtimes deeply enough to build safer, smaller, reproducible, observable, and predictable production workloads.

At the Junior level, it is enough to understand the basic workflow:

```text
Dockerfile
↓
Build Image
↓
Run Container
↓
Expose Application
```

At Mid-Level, that is no longer enough.

A production engineer must understand what happens underneath that workflow:

```text
Source Code
↓
Build Context
↓
Dockerfile Instructions
↓
Build Stages
↓
Image Layers
↓
Image Configuration and Metadata
↓
Registry
↓
Image Reference
↓
Container Runtime
↓
Container Process
↓
Filesystem + Mounts
↓
Resource Boundaries
↓
Signals and Termination
↓
Health
↓
Logs and Runtime Evidence
```

The important question is no longer:

```text
Can I build a Docker image?
```

It becomes:

```text
Can I explain exactly what I built,
what is inside it,
where it came from,
how it starts,
which identity it uses,
which resources it can consume,
how it terminates,
where its data lives,
how it fails,
and whether the exact same artifact
can be trusted and reproduced in production?
```

---

# 1. A CONTAINER IS NOT A SMALL VIRTUAL MACHINE

One of the most important container concepts is understanding what a container is not.

A container is not normally a complete independent operating system with its own kernel.

On Linux, containerized processes use the host Linux kernel while isolation and resource controls are provided through operating-system mechanisms and the container runtime.

A useful simplified model is:

```text
Physical / Virtual Host
│
├── Linux Kernel
│
├── Container Runtime
│
├── Container A
│   └── Application Processes
│
├── Container B
│   └── Application Processes
│
└── Container C
    └── Application Processes
```

Containers package application userspace and runtime dependencies.

They do not normally package a separate Linux kernel.

This matters when troubleshooting.

If a process inside a container experiences:

- memory pressure
- CPU throttling
- filesystem behavior
- signals
- networking behavior
- process scheduling

the host kernel is still involved.

---

# 2. IMAGE VERSUS CONTAINER

An image and a container are related but different objects.

Think of an image as:

```text
Packaged Application Artifact
+
Filesystem Content
+
Runtime Configuration
+
Metadata
```

A container is a runtime instance created from an image.

Conceptually:

```text
Image
↓
Create Container
↓
Add Runtime Configuration
↓
Add Writable Container Layer
↓
Start Process
```

One image can create many containers:

```text
Image
├── Container A
├── Container B
├── Container C
└── Container D
```

Changing one running container does not rewrite the original image.

---

# 3. IMAGE CONTENT AND IMAGE CONFIGURATION

A production image contains more than application files.

It may also define configuration such as:

- default command
- entrypoint
- environment variables
- working directory
- runtime user
- exposed-port metadata
- labels
- health-check configuration

This means reviewing an image requires more than asking:

```text
What files are inside it?
```

Also ask:

```text
How is this image configured to run?
```

---

# 4. INSPECTING AN IMAGE

Use image inspection to understand image configuration and metadata.

For example:

```bash
docker image inspect veriqta/container-lab:v1
```

Useful information may include:

- image ID
- architecture
- operating system
- environment configuration
- command
- entrypoint
- working directory
- user
- labels
- layer information

Do not assume the Dockerfile is the only evidence.

Inspect the artifact that was actually built.

---

# 5. IMAGE LAYERS

Container images are built from layers.

A simplified image might look like:

```text
Application Image
│
├── Application Source Layer
├── Dependency Layer
├── Package Layer
├── Base Image Layer
└── Lower Base Layers
```

Dockerfile instructions contribute to image construction and filesystem changes.

For example:

```dockerfile
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]
```

The resulting image is not simply one giant filesystem copy.

It is assembled from content-addressed image data and associated configuration.

---

# 6. WHY LAYERS MATTER

Layers influence:

- build caching
- image distribution
- storage reuse
- build performance
- image size
- security analysis
- debugging
- reproducibility

If several images share layers, those layers may be reused locally rather than independently stored and transferred every time.

---

# 7. INSPECTING IMAGE HISTORY

A useful command is:

```bash
docker image history veriqta/container-lab:v1
```

This helps investigate how an image was constructed.

Use it to ask:

```text
Which build operations contributed significant content?

Which layers are unexpectedly large?

Did package installation add unnecessary content?

Did a later command attempt to remove files created earlier?
```

---

# 8. DELETING A FILE LATER DOES NOT NECESSARILY REMOVE IT FROM EARLIER IMAGE HISTORY

Consider this simplified pattern:

```dockerfile
COPY large-file /tmp/large-file
RUN process /tmp/large-file
RUN rm /tmp/large-file
```

It is tempting to think:

```text
File deleted
=
File never contributes to image history.
```

That is not generally how layered images work.

The earlier layer may still contain the file data.

A later layer records the changed filesystem state.

This is one reason Dockerfile construction affects final image size and exposure.

---

# 9. BUILD CACHE

Container builds can reuse previously computed results.

Conceptually:

```text
Instruction 1
↓
Cached Result

Instruction 2
↓
Cached Result

Instruction 3
↓
Changed
↓
Rebuild

Later Instructions
↓
May Need Rebuilding
```

Cache behavior is important for build speed.

But production engineering requires understanding **why** a cache is reusable or invalidated.

---

# 10. CACHE INVALIDATION

Consider:

```dockerfile
COPY . .
RUN pip install -r requirements.txt
```

Now modify:

```text
README.md
```

Even though application dependencies did not change, the broad `COPY` input changed.

That can invalidate subsequent work.

A better dependency-oriented pattern may be:

```dockerfile
COPY requirements.txt .
RUN pip install -r requirements.txt

COPY . .
```

Now ordinary source changes do not necessarily invalidate the dependency-installation step.

---

# 11. ORDER DOCKERFILE OPERATIONS BY CHANGE FREQUENCY

A useful principle is:

```text
Stable Inputs
↓
Expensive Operations
↓
Frequently Changing Inputs
```

For example:

```text
Base Image
↓
Dependency Manifest
↓
Install Dependencies
↓
Application Source
```

This can significantly improve incremental build performance.

But never sacrifice correctness merely to preserve cache.

---

# 12. CACHE IS AN OPTIMIZATION, NOT SOURCE OF TRUTH

A cached build succeeding does not prove a clean build will succeed.

This becomes important when:

```text
Developer Laptop
→ warm cache

CI Runner
→ clean environment
```

A hidden dependency may be masked locally.

Production build verification should periodically test from clean conditions.

---

# 13. BUILD CONTEXT

When running:

```bash
docker build -t veriqta/container-lab:v1 .
```

the final:

```text
.
```

identifies the build context.

The build context determines which filesystem content the build can access through ordinary context-based operations.

This boundary is fundamental.

---

# 14. BUILD CONTEXT IS NOT JUST "THE FOLDER CONTAINING THE DOCKERFILE"

The Dockerfile and build context are related but distinct concepts.

For example:

```bash
docker build -f docker/Dockerfile .
```

Here:

```text
Dockerfile:
docker/Dockerfile

Build Context:
.
```

Understanding this distinction helps diagnose:

```text
COPY failed

File not found

Build works from one directory but not another
```

---

# 15. KEEP BUILD CONTEXT SMALL AND INTENTIONAL

An unnecessarily large build context can include:

- Git metadata
- local virtual environments
- test output
- build artifacts
- editor files
- logs
- temporary files
- local credentials
- unrelated source trees

This creates performance and security concerns.

Use `.dockerignore` to exclude unnecessary content.

Example:

```text
.git
.venv
__pycache__
*.log
.env
coverage/
dist/
```

Adapt the file to the actual project.

Do not copy ignore patterns blindly.

---

# 16. `.dockerignore` IS A BUILD BOUNDARY CONTROL

A good `.dockerignore` helps:

```text
Reduce Context
↓
Reduce Transfer
↓
Reduce Accidental Inputs
↓
Improve Cache Behavior
↓
Reduce Exposure Risk
```

But it is not a substitute for proper secret management.

A secret should not become safe merely because someone remembered to add it to `.dockerignore`.

---

# 17. NEVER ASSUME LOCAL SECRET FILES ARE HARMLESS

Suppose the repository contains:

```text
.env
private-key.pem
cloud-credentials.json
```

and the Dockerfile contains:

```dockerfile
COPY . .
```

Without appropriate exclusions and secret-management practices, sensitive material may become build input or image content.

Production build systems must treat build context as security-sensitive.

---

# 18. MULTI-STAGE BUILDS

A build environment often requires more tools than the application needs at runtime.

For example:

```text
Build Stage
├── compiler
├── package manager
├── headers
├── test tools
└── source code

Runtime Stage
├── runtime
├── required libraries
└── application artifact
```

Multi-stage builds separate these concerns.

---

# 19. BASIC MULTI-STAGE MODEL

```dockerfile
FROM some-builder-image AS build

WORKDIR /src

COPY . .

RUN build-command


FROM some-runtime-image AS runtime

WORKDIR /app

COPY --from=build /src/output /app/

CMD ["./application"]
```

The final runtime stage does not automatically contain every tool and file from the build stage.

Only the required artifacts are copied forward.

---

# 20. WHY MULTI-STAGE BUILDS MATTER

Benefits may include:

- smaller runtime images
- fewer unnecessary packages
- reduced attack surface
- separation of build and runtime dependencies
- cleaner production artifacts
- reduced distribution cost

The objective is not:

```text
Use multiple FROM statements because it looks advanced.
```

The objective is:

```text
Keep build-time requirements out of runtime
when runtime does not need them.
```

---

# 21. MULTI-STAGE DOES NOT AUTOMATICALLY MEAN SECURE

A multi-stage build can still:

- use vulnerable dependencies
- run as root
- expose secrets
- use mutable inputs
- copy unnecessary files
- use an untrusted base
- contain dangerous runtime configuration

Multi-stage construction is one control.

It is not a security guarantee.

---

# 22. BASE IMAGE SELECTION

The base image becomes part of the application supply chain.

Choosing:

```dockerfile
FROM some-image
```

means trusting content provided by that image source.

Evaluate:

- source
- publisher
- maintenance
- update cadence
- operating-system/runtime requirements
- package availability
- compatibility
- vulnerability posture
- architecture support
- image size
- debugging requirements

---

# 23. SMALLER IS NOT AUTOMATICALLY BETTER

A smaller image can reduce:

- transfer time
- storage
- unnecessary packages
- some attack surface

But extreme minimalism can introduce:

- compatibility problems
- missing certificates
- missing timezone data
- debugging difficulty
- missing runtime libraries

Choose the smallest image that still meets operational and compatibility requirements.

Do not optimize size blindly.

---

# 24. BASE IMAGE COMPATIBILITY

Changing:

```text
Full Distribution
```

to:

```text
Minimal Distribution
```

may change more than image size.

Potential differences include:

- C library
- package manager
- shell availability
- certificates
- system utilities
- library versions
- debugging tools

Test the actual application.

---

# 25. BASE IMAGE UPDATES

Pinning an old base forever is not reproducibility.

It is stagnation.

A mature strategy separates:

```text
Reproducibility
```

from:

```text
Update Policy
```

For example:

```text
Production deployment
→ exact reviewed image

Build process
→ controlled dependency updates

Security process
→ regularly evaluates new vulnerabilities

Release process
→ produces new reviewed artifact
```

---

# 26. IMAGE TAGS

An image may be referenced with a tag:

```text
registry.example.com/team/app:1.4.2
```

The tag is a human-friendly reference.

Other examples:

```text
app:latest
app:stable
app:production
app:2026.10.02
```

Tags can be useful.

But a tag is not inherently immutable.

---

# 27. MUTABLE TAGS

A registry tag can generally be associated with different image content over time unless registry policy prevents that operation.

For example:

```text
Monday

app:production
↓
Digest A
```

Later:

```text
Friday

app:production
↓
Digest B
```

The string:

```text
app:production
```

did not change.

The referenced content did.

---

# 28. IMAGE DIGESTS

Image content can be addressed using a cryptographic digest.

Conceptually:

```text
registry.example.com/team/app@sha256:<digest>
```

The digest identifies specific content.

This allows a deployment to say:

```text
Run this exact artifact.
```

rather than:

```text
Run whatever this mutable tag points to when you pull it.
```

---

# 29. TAG VERSUS DIGEST

Use the mental model:

```text
Tag
→ human-friendly reference

Digest
→ immutable content identity
```

Tags are useful for workflows.

Digests are important for exact artifact identity.

Production systems frequently need both concepts.

---

# 30. VERSION TAGS ARE STILL POLICY

A tag such as:

```text
1.4.2
```

looks immutable.

Technically, whether it can be overwritten depends on registry capabilities and policy.

A production organization may enforce:

```text
Published release tags must never be moved.
```

That is an operational policy.

Digest identity remains stronger evidence of exact content.

---

# 31. REGISTRIES

A registry stores and distributes container artifacts.

Simplified flow:

```text
CI Build
↓
Container Image
↓
Registry
↓
Deployment Platform
↓
Pull Image
↓
Run Container
```

Production registry concerns include:

- authentication
- authorization
- repository boundaries
- encryption in transit
- retention
- immutability policies
- vulnerability analysis
- provenance
- replication
- availability
- auditability

---

# 32. REGISTRY AUTHENTICATION

Pushing an image requires appropriate authorization.

Do not embed registry credentials inside:

```text
Dockerfile

Image

Repository

Build Arguments

Shell History
```

Use the authentication mechanism provided by the execution environment.

CI credentials should be:

```text
Scoped

Short-lived where possible

Protected

Audited

Rotatable
```

---

# 33. IMAGE NAMING

A complete image reference can conceptually include:

```text
Registry
/
Repository
:
Tag
```

For example:

```text
registry.example.com/payments/api:1.8.3
```

or:

```text
Registry
/
Repository
@
Digest
```

Understanding the full reference prevents confusion about which registry and artifact are actually being used.

---

# 34. IMAGE METADATA

Useful image metadata can describe:

- source repository
- revision
- version
- build information
- maintainer or owning team
- documentation
- license information

OCI-compatible labels are commonly used for standardized metadata.

Metadata improves traceability.

But metadata must be trustworthy.

A label claiming:

```text
revision=abc123
```

is useful only if the build process correctly populated it.

---

# 35. TRACEABILITY

A strong artifact trail looks like:

```text
Source Commit
↓
Build
↓
Tests
↓
Image
↓
Digest
↓
Registry
↓
Deployment
```

During an incident, engineers should be able to answer:

```text
Which source revision produced this running image?
```

---

# 36. CONTAINER STARTUP

A container is useful only if it starts the intended process correctly.

The runtime combines:

```text
Image Configuration
+
Runtime Overrides
↓
Container Process
```

Important Dockerfile instructions include:

```text
ENTRYPOINT

CMD
```

Understanding their interaction is essential.

---

# 37. `CMD`

`CMD` defines default command or arguments for a container image.

For example:

```dockerfile
CMD ["python", "app.py"]
```

A runtime command can replace the default `CMD`.

Therefore:

```text
CMD
=
default behavior
```

not:

```text
CMD
=
unconditionally fixed command
```

---

# 38. `ENTRYPOINT`

`ENTRYPOINT` defines the executable around which the container is structured.

A common pattern is:

```dockerfile
ENTRYPOINT ["python"]
CMD ["app.py"]
```

Conceptually:

```text
ENTRYPOINT
+
CMD
↓
python app.py
```

Runtime overrides interact differently with `ENTRYPOINT` and `CMD`.

Understand those semantics before designing an image interface.

---

# 39. EXEC FORM

A recommended form for application startup is often the JSON/exec form:

```dockerfile
CMD ["python", "app.py"]
```

rather than:

```dockerfile
CMD python app.py
```

The difference matters because shell-form commands involve shell interpretation and can change process and signal behavior.

---

# 40. SHELL FORM

A shell-form command may effectively introduce a shell:

```text
Container PID 1
↓
Shell
↓
Application
```

instead of:

```text
Container PID 1
↓
Application
```

That can affect signal propagation and termination behavior.

Do not choose shell form merely because it looks familiar.

---

# 41. WHEN A SHELL IS ACTUALLY REQUIRED

Some startup behavior genuinely requires:

- variable expansion
- conditional logic
- initialization
- file generation
- privilege adjustment
- argument transformation

A startup script may then be appropriate.

But the script must be engineered correctly.

---

# 42. ENTRYPOINT SCRIPT

Example conceptual pattern:

```sh
#!/bin/sh
set -eu

# perform bounded initialization

exec "$@"
```

The final:

```sh
exec "$@"
```

replaces the shell process with the application.

This allows the final application to become the container's main process rather than remain an unnecessary child of the shell.

---

# 43. PID 1

Inside a container, one process occupies PID 1 in the container's PID namespace.

PID 1 has special operational significance.

The container's lifecycle is strongly tied to its main process.

When the main process exits:

```text
Container
↓
Stops
```

Even if the application previously created other processes, losing the container's main process normally means the container is no longer running.

---

# 44. PID 1 AND SIGNALS

Container runtimes send termination signals to the container's main process.

Therefore, the process hierarchy matters.

Bad startup design:

```text
Runtime
↓
Signal
↓
Shell PID 1
↓
Application Child
```

If the shell does not correctly forward the signal, the application may not receive it as expected.

Better design:

```text
Runtime
↓
Signal
↓
Application PID 1
```

or use a properly designed init/entrypoint strategy where necessary.

---

# 45. SIGNALS

Signals are part of container lifecycle management.

Common examples include:

```text
SIGTERM

SIGKILL
```

A normal graceful-stop sequence conceptually resembles:

```text
Stop Requested
↓
Termination Signal
↓
Grace Period
↓
Application Exits
```

If the application does not exit before the configured timeout:

```text
Forced Termination
```

may follow.

Exact timeout and stop behavior depend on the runtime and orchestration configuration.

---

# 46. GRACEFUL TERMINATION

A production application should usually handle termination deliberately.

A service may need to:

```text
Stop accepting new work

Finish or abandon in-flight work according to policy

Close connections

Flush buffered data

Release resources

Exit
```

The exact sequence depends on application semantics.

---

# 47. TERMINATION IS AN APPLICATION CONCERN TOO

Docker cannot magically make an application graceful.

The application must participate.

Ask:

```text
Does the application handle SIGTERM?

How long does shutdown normally take?

What happens to active requests?

What happens to background jobs?

What happens to partially written data?

Does the process actually exit?
```

---

# 48. TEST TERMINATION

Do not wait for production to discover signal problems.

Run the container.

Generate activity.

Request termination.

Observe:

```text
Signal received?

Application logs shutdown?

Connections close?

Process exits?

How long?

Any corrupted work?
```

Graceful shutdown should be tested.

---

# 49. CHILD PROCESSES

Some applications create child processes.

Now process management becomes more important.

Questions include:

```text
Who receives signals?

Who waits for children?

Can zombie processes accumulate?

Does the application behave correctly as PID 1?
```

For workloads that require it, a minimal init process may be appropriate.

Do not add one automatically without understanding why.

---

# 50. CONTAINER EXIT

A container exiting is not itself a root cause.

It is an observation.

The first questions are:

```text
What was PID 1?

What exit code was returned?

Was termination expected?

Was a signal involved?

Did the application crash?

Did initialization fail?

Was memory exhausted?

Did a required dependency fail?
```

---

# 51. INSPECTING EXIT STATE

Useful evidence includes:

```bash
docker ps -a
```

and:

```bash
docker inspect <container>
```

Inspect runtime state rather than assuming why the container stopped.

Also inspect application logs:

```bash
docker logs <container>
```

---

# 52. EXIT CODES

Exit codes communicate process outcomes.

Do not memorize every possible code as a universal diagnosis.

Instead ask:

```text
Which process exited?

Which code?

What does that application define the code to mean?

Was the process terminated by a signal?

What do the logs show immediately before exit?
```

Application-specific evidence matters.

---

# 53. FILESYSTEM MODEL

An image provides read-only image layers.

A running container receives a writable layer above them.

Conceptually:

```text
Container Writable Layer
────────────────────────
Image Layer
Image Layer
Image Layer
────────────────────────
```

Writes that are not directed to external storage normally affect the container's writable layer.

---

# 54. CONTAINER WRITABLE LAYER IS NOT DURABLE APPLICATION STORAGE

Suppose the application writes:

```text
/app/data/database.db
```

to the container's writable layer.

The container is then removed and recreated.

The replacement container starts from the image again.

The old writable layer is not the application's durable storage strategy.

Do not design important persistent data around container identity.

---

# 55. EPHEMERAL CONTAINER THINKING

A production container should generally be treated as replaceable.

Think:

```text
Container fails
↓
Replace container
```

rather than:

```text
Container fails
↓
SSH into it
↓
Manually repair it forever
```

Important state should be stored through an appropriate external persistence mechanism.

---

# 56. VOLUMES

Docker-managed volumes provide persistent storage independent of an individual container lifecycle.

Conceptually:

```text
Container A
     │
     ▼
   Volume
     ▲
     │
Replacement Container B
```

The volume can outlive Container A.

---

# 57. VOLUME USE CASES

Volumes can be appropriate for data such as:

- database files in suitable standalone scenarios
- application state requiring persistence
- shared local runtime data where supported
- data that must survive container recreation

Whether a volume is the correct production storage architecture depends on the application and platform.

---

# 58. BIND MOUNTS

A bind mount maps a host path into the container.

Conceptually:

```text
Host:
/srv/config

      ↓

Container:
/app/config
```

Bind mounts can be useful.

They also couple the container to host filesystem structure.

---

# 59. BIND MOUNT SECURITY

A writable bind mount may allow a containerized process to modify host files accessible through that mount.

Therefore ask:

```text
Does the container need write access?

Can this mount be read-only?

What host path is exposed?

Which runtime user accesses it?

What happens if the application is compromised?
```

Mounts are security boundaries.

---

# 60. MOUNTS CAN HIDE IMAGE CONTENT

Suppose an image contains:

```text
/app/config/default.conf
```

Then a mount is placed at:

```text
/app/config
```

The mounted content can obscure the image content at that path.

This frequently causes confusion:

```text
The file exists in the image,
but disappears when the container runs.
```

Inspect mounts.

---

# 61. VOLUME PERMISSION PROBLEMS

A common production failure is:

```text
Image runs as UID 10001

Mounted storage owned by UID 10002
```

Result:

```text
Permission denied
```

The image may be correct.

The mount may be correct.

The ownership relationship is not.

Always reason across both image and runtime configuration.

---

# 62. RUNTIME USERS

A container process should not run as root merely because root is convenient.

Where the application does not require root, define a non-root runtime user.

Conceptually:

```dockerfile
USER appuser
```

The actual user and UID strategy should be intentional.

---

# 63. ROOT INSIDE A CONTAINER

Container isolation reduces some risk.

It does not make root privileges meaningless.

A compromised process running with unnecessary privilege can increase impact, especially when combined with:

- dangerous mounts
- added capabilities
- privileged mode
- exposed runtime sockets
- weak host configuration

Use least privilege.

---

# 64. BUILD USER VERSUS RUNTIME USER

The build may need privileges that the runtime does not.

For example:

```text
Build Stage
→ install dependencies

Runtime Stage
→ execute application as non-root
```

Do not carry build-time privilege assumptions into production runtime unnecessarily.

---

# 65. FILE OWNERSHIP

Switching to:

```dockerfile
USER appuser
```

without preparing filesystem permissions can break the application.

For example:

```text
/app/cache
owned by root
```

while the application runs as:

```text
appuser
```

The result may be:

```text
Permission denied
```

Non-root execution must be designed, not merely declared.

---

# 66. COPY OWNERSHIP

When appropriate, ownership can be established during build.

For example:

```dockerfile
COPY --chown=appuser:appgroup app.py /app/app.py
```

Exact user and group creation depends on the base image and operating system.

Verify resulting ownership.

---

# 67. DO NOT SOLVE PERMISSION FAILURES WITH `chmod 777`

A common anti-pattern is:

```bash
chmod -R 777 /app
```

This avoids understanding the problem.

Instead identify:

```text
Which process?

Which UID/GID?

Which path?

Which owner?

Which group?

Which operation?

Read?

Write?

Execute?
```

Then grant the minimum permissions required.

---

# 68. RESOURCE LIMITS

Containers share host resources.

Without appropriate controls, a workload may consume more resources than intended.

Important resources include:

- memory
- CPU
- process count
- storage
- I/O

At this level, focus primarily on understanding CPU and memory controls and their failure behavior.

---

# 69. MEMORY LIMITS

A container can be started with a memory limit.

For example:

```bash
docker run --memory=256m veriqta/container-lab:v1
```

This creates a memory constraint.

It does not mean the application will perform correctly with 256 MiB.

Resource values require testing and capacity understanding.

---

# 70. MEMORY LIMITS ARE NOT MEMORY RESERVATIONS

A maximum answers:

```text
How much memory may this workload consume before enforcement?
```

It does not necessarily answer:

```text
How much memory is guaranteed to be physically available at every moment?
```

Understand the semantics of the platform being used.

---

# 71. OUT-OF-MEMORY FAILURES

When memory constraints are exceeded, processes may be terminated according to kernel/runtime behavior.

A container disappearing under load may therefore be:

```text
Application crash
```

or:

```text
Memory-related termination
```

or another cause.

Inspect runtime state and host/runtime evidence.

Do not rely only on application logs.

A process killed externally may not have time to log a useful application error.

---

# 72. CPU LIMITS

CPU can also be constrained.

Example:

```bash
docker run --cpus=1.0 veriqta/container-lab:v1
```

A CPU limit can produce:

```text
Higher latency

Reduced throughput

CPU throttling
```

without necessarily crashing the process.

Resource troubleshooting must distinguish:

```text
Application bug
```

from:

```text
Application starved of resources.
```

---

# 73. TEST UNDER REALISTIC RESOURCE CONSTRAINTS

An application tested only with unrestricted laptop resources may behave differently under production limits.

Test:

```text
Startup

Steady load

Peak load

Memory growth

Graceful shutdown

Health checks
```

under realistic constraints.

---

# 74. HEALTH CHECKS

A health check provides a runtime signal about container or application health.

Example conceptual Dockerfile:

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD ["some-health-command"]
```

The exact health command depends on the application.

---

# 75. HEALTH IS NOT THE SAME AS RUNNING

A process can be running while the application is unusable.

For example:

```text
PID exists
✓

HTTP server accepts requests
✗
```

Therefore:

```text
Process Running
≠
Application Healthy
```

---

# 76. HEALTH CHECK DESIGN

A health check should answer a meaningful question.

Poor check:

```text
Does the process exist?
```

Better, depending on the application:

```text
Can the application serve its basic health endpoint?
```

But avoid turning every health check into a complete dependency audit.

---

# 77. HEALTH CHECKS CAN CAUSE LOAD

Suppose:

```text
100 containers
×
health check every second
×
expensive database query
```

The health system itself may create load.

Health checks should be:

```text
Fast

Bounded

Reliable

Meaningful

Low-cost
```

---

# 78. HEALTH CHECK DEPENDENCY DESIGN

Consider an application that can continue serving cached data while an external analytics system is unavailable.

If its health check fails whenever analytics is unavailable, the platform may treat otherwise useful instances as unhealthy.

Health semantics must reflect actual service requirements.

---

# 79. HEALTH CHECK TOOL DEPENDENCY

A health check requiring:

```text
curl
```

will fail if the runtime image does not contain `curl`.

Do not add large toolchains merely for one health check without considering alternatives.

The check mechanism must match the runtime image.

---

# 80. HEALTH CHECK FAILURE TROUBLESHOOTING

Ask:

```text
Is the container running?

What health command is configured?

Can the command execute?

Does required binary exist?

Which address is checked?

Which port?

Which path?

What timeout?

What exit code?

Is application still starting?

Is dependency required?
```

Inspect evidence.

---

# 81. STARTUP VERSUS HEALTH

An application may require time to initialize.

A health check beginning too aggressively may report temporary failure.

Understand:

```text
Container Started
↓
Application Initializing
↓
Application Ready
```

These are different states.

This becomes especially important when moving into orchestration systems.

---

# 82. LOGGING

Containerized applications should normally make operational logs accessible through the runtime's logging mechanism.

A common pattern is:

```text
Application
↓
stdout / stderr
↓
Container Runtime
↓
Logging System
```

Avoid treating files buried in the writable container layer as the only source of application logs.

---

# 83. STDOUT AND STDERR

Applications should use output streams meaningfully.

For example:

```text
stdout
→ normal application events

stderr
→ errors or diagnostics
```

Exact conventions vary by application.

The important principle is that runtime logs should be observable without manually entering the container.

---

# 84. LOGGING IS NOT PERSISTENCE BY ITSELF

Running:

```bash
docker logs <container>
```

can be useful.

It does not automatically provide a complete production logging architecture.

Production environments need to consider:

- collection
- retention
- rotation
- centralization
- access
- search
- sensitive data

Those topics become deeper in the observability Part.

---

# 85. IMAGE REPRODUCIBILITY

A reproducible build aims to reduce uncontrolled variation between builds.

Sources of variation can include:

- mutable base tags
- unpinned dependencies
- external repositories
- timestamps
- generated content
- changing package indexes
- build architecture
- build tool versions

The objective is not merely:

```text
The Dockerfile is in Git.
```

The objective is:

```text
We understand and control the inputs that determine the artifact.
```

---

# 86. DEPENDENCY LOCKING

Application ecosystems provide different dependency-locking mechanisms.

Examples include lockfiles and exact package versions.

Use the mechanism appropriate to the language and build system.

A production image build should not silently resolve completely different dependency versions every time unless that is an intentional policy.

---

# 87. DO NOT CONFUSE PINNING WITH PATCH MANAGEMENT

Pinning improves control.

But:

```text
Dependency pinned
```

does not mean:

```text
Dependency remains safe forever.
```

A vulnerability can be disclosed tomorrow.

Production engineering needs both:

```text
Controlled versions
+
Controlled update process
```

---

# 88. BUILD-TIME SECRETS

Some builds require temporary credentials to access private dependencies.

Do not casually pass secrets using mechanisms that may persist them in image configuration, build history, logs, or artifacts.

Modern build systems provide secret-mounting mechanisms for appropriate use cases.

The principle is:

```text
Secret needed during build
↓
Available only where required
↓
Not copied into final image
↓
Not persisted in image metadata
```

---

# 89. `ARG` IS NOT A SECRET STORE

Build arguments are useful for build parameters.

They should not be treated as a secure secret-management mechanism.

Never assume:

```dockerfile
ARG PASSWORD
```

means:

```text
Password is protected.
```

Use dedicated build-secret mechanisms where required.

---

# 90. IMAGE VULNERABILITIES

Container images may contain vulnerable:

- operating-system packages
- language dependencies
- libraries
- application components

Image scanning can help identify known vulnerabilities.

But scanner output must be interpreted.

---

# 91. VULNERABILITY SCANNING IS NOT A BINARY PASS/FAIL TRUTH

A scanner may report:

```text
CVE

Severity

Affected Package

Installed Version

Fixed Version
```

But engineering decisions may also require:

- exploitability
- reachability
- environment
- exposure
- compensating controls
- fix availability
- application compatibility

Do not ignore severe findings.

Do not treat severity labels as complete risk analysis either.

---

# 92. NO FINDINGS DOES NOT MEAN NO RISK

A clean vulnerability report does not prove:

```text
Image is secure.
```

It may not detect:

- application logic flaws
- leaked credentials
- insecure runtime configuration
- excessive privilege
- malicious dependencies not yet identified
- unknown vulnerabilities
- weak network exposure

Scanning is one security control.

---

# 93. SBOM

A Software Bill of Materials records information about software components in an artifact.

Conceptually:

```text
Container Image
↓
Component Inventory
↓
Packages and Versions
↓
Security / License / Supply-Chain Analysis
```

An SBOM improves visibility into what is actually present.

---

# 94. WHY SBOMs MATTER

Suppose a new vulnerability is announced in:

```text
library-x version 4.2
```

Without component inventory:

```text
Which images contain it?
```

may be difficult to answer.

With suitable SBOM data:

```text
Image A → library-x 4.2
Image B → library-x 4.1
Image C → no library-x
```

investigation becomes faster.

---

# 95. PROVENANCE

Provenance describes information about how an artifact was built.

Conceptually:

```text
Source
+
Build Process
+
Build Environment
+
Inputs
↓
Artifact
```

Provenance helps answer:

```text
Where did this image come from?
```

It complements:

```text
What is inside this image?
```

---

# 96. SUPPLY-CHAIN MODEL

A production image has a chain of trust:

```text
Source Repository
↓
Dependencies
↓
Base Image
↓
Build System
↓
Build Inputs
↓
Image
↓
Registry
↓
Deployment
↓
Runtime
```

Compromise at any stage can affect the final workload.

Container security does not begin at runtime.

---

# 97. TRUSTED BASE IMAGES

Before adopting a base image, ask:

```text
Who publishes it?

Where is it hosted?

How is it maintained?

Is the source expected?

Does the project receive updates?

What software does it contain?

Can exact content be identified?

How will updates be evaluated?
```

Do not choose an image only because its name looks official.

---

# 98. MINIMIZE UNNECESSARY SOFTWARE

Every unnecessary package can add:

- size
- maintenance
- vulnerabilities
- complexity
- unexpected utilities available to an attacker

Production runtime images should contain what the application needs.

But operational requirements still matter.

Minimal does not mean dysfunctional.

---

# 99. DEBUGGING MINIMAL IMAGES

A minimal image may lack:

```text
shell

curl

ps

package manager

network utilities
```

Do not respond by automatically installing a full debugging environment into every production image.

Instead design an operational debugging strategy appropriate to the platform.

The production artifact and the debugging environment do not always need to be identical.

---

# 100. IMAGE ARCHITECTURE

Images target particular operating-system and CPU-platform combinations.

Common architectures include:

```text
linux/amd64

linux/arm64
```

A developer may build on one architecture while CI or production runs another.

---

# 101. "WORKS ON MY MACHINE" AND ARCHITECTURE

Example:

```text
Developer Laptop
↓
ARM64

Production Host
↓
AMD64
```

A locally built artifact may not behave as expected if architecture was not considered.

Architecture becomes part of artifact identity.

---

# 102. MULTI-PLATFORM IMAGES

A registry reference can represent multiple platform-specific image manifests through an image index.

Conceptually:

```text
app:1.0
│
├── linux/amd64 → Image A
└── linux/arm64 → Image B
```

The runtime can select the appropriate platform variant.

This means the same tag may resolve to different platform-specific image manifests depending on platform.

---

# 103. VERIFY ARCHITECTURE

Useful inspection can include:

```bash
docker image inspect <image>
```

For multi-platform registry artifacts, build and registry inspection tools can provide platform information.

When diagnosing:

```text
exec format error
```

architecture mismatch should be one hypothesis.

It is not the only possible cause.

---

Compare environments.

The production process must still start correctly.

```text
↓
Root Cause
↓
Corrective Action
↓
Verification
```

Container troubleshooting becomes much easier when the failing layer is identified first.

# 154. CONTAINER TROUBLESHOOTING LAYERS

A useful layer model is:

```text

↓

↓
Dockerfile
↓

↓

↓

↓

↓

↓
Filesystem / Mount
↓

↓

↓

↓
Dependency
```

Do not jump directly to:

```text
Docker is broken.
```

# 155. SCENARIO: IMAGE BUILDS LOCALLY BUT FAILS IN CI

Start with:

```text
What differs?
```

Compare:

```text
Source Revision

Build Context

Dockerfile

Builder Version

Platform

Cache

Secrets

Network

Environment

Dependency Sources
```

A reproducibility problem is often an input-control problem.

---

# 156. SCENARIO: CONTAINER EXITS

Inspect:

```text
Container State

Exit Code

Logs

Configured Command

Entrypoint

Environment

Mounts

Resource State
```

Then classify:

```text
Expected Exit?

Startup Failure?

Application Crash?

Signal?

Resource Termination?
```

---

# 157. SCENARIO: `EXEC FORMAT ERROR`

Possible hypotheses include:

```text
Wrong CPU architecture

Invalid executable format

Script interpreter/shebang problem
```

Inspect the artifact and runtime platform.

Do not assume architecture without evidence.

---

# 158. SCENARIO: PERMISSION DENIED

Determine:

```text
Process UID/GID

Filesystem path

Image ownership

Mount ownership

Permissions

Required operation
```

Then correct the actual ownership or permission model.

Do not default to root.

---

# 159. SCENARIO: SLOW TERMINATION

Determine:

```text
PID 1

Process tree

ENTRYPOINT

CMD

Shell wrapper

Signal

Application handler

Shutdown timeout
```

Reproduce in a disposable environment.

---

# 160. SCENARIO: HEALTH CHECK FAILS

Determine:

```text
Health command

Binary availability

Endpoint

Port

Timeout

Startup duration

Application state

Dependency behavior
```

Then test the exact health command manually inside an appropriate debugging environment where necessary.

---

# 161. SCENARIO: DATA DISAPPEARS

Ask:

```text
Where was data written?

Writable layer?

Named volume?

Bind mount?

External service?
```

If it existed only in a removed container's writable layer, disappearance may be expected lifecycle behavior rather than storage corruption.

---

# 162. SCENARIO: FILE EXISTS IN IMAGE BUT NOT RUNNING CONTAINER

Inspect mounts.

A mount may obscure the path.

Compare:

```text
Image Filesystem
```

with:

```text
Runtime Filesystem + Mounts
```

The image itself may be correct.

---

# 163. SCENARIO: IMAGE IS TOO LARGE

Inspect:

```text
Base Image

Layer History

Copied Files

Build Tools

Package Caches

Source Files

Multi-Stage Boundaries
```

Measure each improvement.

Do not optimize by deleting arbitrary files without understanding their purpose.

---

# 164. SCENARIO: VULNERABILITY SCANNER REPORTS CRITICAL ISSUE

Determine:

```text
Which package?

Which version?

Which layer/source introduced it?

Is a fixed version available?

Is base image update required?

Will remediation affect compatibility?

Can the image be rebuilt and redeployed?
```

Then verify the rebuilt artifact.

---

# 165. SCENARIO: TAG POINTS TO UNEXPECTED IMAGE

Determine:

```text
Registry

Repository

Tag

Current Digest

Expected Digest

Who pushed?

When?

Deployment pull behavior
```

This is why production traceability must include digests.

---

# 166. CONTAINER SECURITY MODEL

A production image should be reviewed across several boundaries:

```text
Source Security

Dependency Security

Build Security

Image Security

Registry Security

Runtime Security

Host Security
```

Securing only the Dockerfile is insufficient.

---

# 167. LEAST PRIVILEGE

Review:

```text
Runtime User

Linux Capabilities

Filesystem Access

Mount Access

Secrets

Network Access

Runtime Socket Access
```

At this level, understand that privilege can come from more than UID 0.

Deep runtime hardening will continue later.

---

# 168. DOCKER SOCKET WARNING

Giving a container access to a container-runtime management socket can provide extremely powerful control over the host's container environment.

Do not mount such sockets casually.

Treat runtime control-plane access as highly privileged.

---

# 169. PRIVILEGED CONTAINERS

Running containers with broad privileged access removes important isolation boundaries.

Do not use privileged mode as a generic fix for:

```text
Permission denied

Device access

Networking problem

Mount problem
```

Determine the minimum required capability.

---

# 170. SECRETS AT RUNTIME

Do not bake production secrets into images.

Bad model:

```text
Build Image
↓
Embed Production Password
↓
Push Registry
```

Now anyone with sufficient image access may potentially recover the secret.

Runtime secrets should be delivered through an appropriate secret-management mechanism.

---

# 171. ENVIRONMENT VARIABLES AND SECRETS

Environment variables are commonly used for runtime configuration.

But sensitive environment values can be exposed through:

- process/runtime inspection
- debugging
- crash reports
- application logs
- misconfigured diagnostics

Use the secret mechanism appropriate to the deployment platform and threat model.

---

# 172. READ-ONLY ROOT FILESYSTEM

Applications that do not need to modify their root filesystem can potentially run with a read-only root filesystem.

This can reduce some forms of runtime modification.

But the application may still require writable locations for:

```text
Temporary files

Caches

Sockets

Application data
```

Design those paths explicitly.

Do not enable read-only mode without testing startup and runtime behavior.

---

# 173. TEMPORARY DATA

Not all writable data requires persistence.

Examples:

```text
Temporary processing files

Caches

Runtime scratch data
```

These may be appropriate for ephemeral storage.

Classify data:

```text
Persistent?

Ephemeral?

Secret?

Reconstructable?

Shared?
```

before selecting storage.

---

# 174. IMAGE IMMUTABILITY

A production artifact should normally be promoted rather than rebuilt independently for each environment.

Weak model:

```text
Build for Development

Build again for Staging

Build again for Production
```

Now each environment may receive different bytes.

Stronger model:

```text
Build Once
↓
Test Artifact
↓
Identify Digest
↓
Promote Same Artifact
↓
Development
↓
Staging
↓
Production
```

Runtime configuration can differ without rebuilding the application artifact.

---

# 175. BUILD ONCE, CONFIGURE AT RUNTIME

Avoid baking environment-specific production values into separate images when they can safely be supplied at runtime.

Prefer:

```text
Same Application Image
+
Development Configuration
```

and:

```text
Same Application Image
+
Production Configuration
```

where application architecture supports it.

This improves artifact consistency.

---

# 176. RELEASE TRACEABILITY

For a production release, record:

```text
Application Version

Source Commit

Image Repository

Image Tag

Image Digest

Build ID

Build Time

Platform

SBOM

Provenance

Vulnerability Assessment
```

This provides evidence for incidents and rollbacks.

---

# 177. ROLLBACK

Container images make artifact rollback easier only when previous artifacts remain available and compatible.

A rollback model may be:

```text
Release Digest B
↓
Problem Detected
↓
Redeploy Reviewed Digest A
↓
Verify
```

But this does not automatically roll back:

```text
Database migrations

External state

Messages

Schema changes

Side effects
```

Artifact rollback and system rollback are different problems.

---

# 178. IMAGE RETENTION

If old images are deleted immediately after deployment, rollback options may disappear.

Registry retention policy should consider:

```text
Rollback Window

Security

Storage Cost

Compliance

Release Traceability
```

Do not retain everything forever without policy either.

A production build should produce evidence such as:


The exact evidence depends on the organization's tooling.

The principle is:

```text
Artifact creation should be traceable.
```

# 185. AI AND SECURITY

AI may recommend:

```text

chmod 777

Disable verification

Use privileged mode

Embed token in ARG

Install debugging tools permanently
```

Production engineering requires asking:

```text

```

Never trade unexplained security controls for convenience.

# 198. COMPLETION STANDARD

You have completed this Part when you can engineer and review container images intended for production use rather than simply writing Dockerfiles that happen to build.

You should understand:

```text
Image
≠
Container
```

You should understand:

```text
Container
≠
Virtual Machine
```

You should understand:

```text
Image Layer
≠
Ordinary Mutable Directory
```

You should understand:

```text
Deleting a file in a later build step
≠
Guarantee that earlier layer content never existed
```

You should understand:

```text
Build Cache
=
Optimization
```

not:

```text
Proof of clean reproducibility
```

You should understand:

```text
Build Context
=
Build Input Boundary
```

You should be able to use `.dockerignore` deliberately.

You should understand why:

```dockerfile
COPY . .
```

deserves careful review.

You should understand:

```text
Multi-Stage Build
=
Separation of Build and Runtime Concerns
```

not:

```text
Automatic Security
```

You should understand:

```text
Small Image
≠
Automatically Good Image
```

and:

```text
Large Image
≠
Automatically Bad Image
```

The question is whether the content is necessary, maintained, secure, and operationally appropriate.

You should understand:

```text
Tag
≠
Immutable Artifact Identity
```

and:

```text
Digest
=
Exact Content Identity
```

You should understand how registries participate in artifact delivery.

You should understand:

```text
Published Image
≠
Trusted Image
```

Trust requires evidence.

You should understand image metadata and traceability.

You should understand:

```text
ENTRYPOINT

CMD

Exec Form

Shell Form
```

and how they affect startup behavior.

You should understand:

```text
PID 1
```

and why it matters for container lifecycle.

You should understand:

```text
SIGTERM
↓
Graceful Shutdown
↓
Exit
```

and know how to test it.

You should understand that:

```text
Container Running
≠
Application Healthy
```

You should be able to design and troubleshoot a meaningful health check.

You should understand:

```text
Image Filesystem
+
Container Writable Layer
+
Runtime Mounts
=
Observed Container Filesystem
```

You should understand:

```text
Container Writable Layer
≠
Durable Storage Strategy
```

You should understand when volumes and bind mounts change filesystem behavior.

You should be able to troubleshoot mount-related permission failures without resorting to:

```text
chmod 777
```

You should be able to run applications as non-root where appropriate and prepare filesystem ownership correctly.

You should understand:

```text
Root inside container
≠
Harmless root
```

You should understand CPU and memory constraints.

You should understand:

```text
Container slow
≠
Automatically application-code problem
```

and:

```text
Container exited
≠
Automatically Docker problem
```

You should be able to diagnose:

```text
Image builds locally but fails in CI

Container exits

Incorrect architecture

Permission failures

Signal handling problems

Health check failures

Volume problems
```

using evidence.

You should understand:

```text
Vulnerability scan
≠
Complete security assessment
```

You should understand what an SBOM provides.

You should understand what provenance provides.

You should understand:

```text
SBOM
→ What is inside?

Provenance
→ How did it get built?

Digest
→ Which exact artifact?
```

You should understand the supply-chain path:

```text
Source
↓
Dependencies
↓
Base Image
↓
Build
↓
Image
↓
Registry
↓
Deployment
↓
Runtime
```

You should be able to take a poor Dockerfile and improve:

```text
Image Size

Caching

Build Context

Security

Runtime User

Reproducibility

Health Behavior

Startup Behavior

Signal Handling

Supply-Chain Visibility
```

and explain why every change was made.

You should be able to verify the resulting artifact rather than trusting the Dockerfile alone.

The defining question is no longer:

```text
Can I containerize this application?
```

It is:

```text
Can I build an application artifact
whose contents,
identity,
dependencies,
runtime user,
startup behavior,
signal handling,
storage,
resource assumptions,
health,
security posture,

replace it,
```

When the answer is yes, you have moved from basic container usage into **production container engineering**.
